ACTANT INTEGRATION KNOWLEDGE - PACK / CODEENTRY TERMINOLOGY TRANSITION

Owner
-----
Actant integration thread.

Purpose
-------
This records the current terminology and the semantic mapping needed while
legacy design documents still use older names. It is coordination knowledge,
not a design-document amendment.

Current terminology
-------------------
Pack is the complete packaged extension/content unit. It corresponds to what a
"mod" normally means in games: one package may contain executable code, data,
assets, manifests, configuration, and other content.

CodeEntry is an executable language entry belonging to a Pack. It is de-facto a
language code file at the package/source boundary, but Actant loads it through a
language adapter into whatever executable/runtime instance or unit that language
recognizes. Its architectural meaning is the executable participant Actant can
give execution turns to through lifecycle callbacks, capabilities, Hooks, and
other supported call surfaces; it is not defined by one universal runtime object
model across languages.

CodeEntryContext is the context Actant supplies for one call/turn into a
CodeEntry. It is call-specific and carries the authority and environment for
that invocation, including the relevant Application, Pack/CodeEntry identity,
memory view, and other mediated Actant facilities defined by the applicable
design. A loaded CodeEntry may be long-lived while CodeEntryContext is fresh for
each Actant-controlled call and invalid after that call ends.

Legacy terminology mapping
--------------------------
Older design used "mod" for the executable code unit itself as well as language
around packaged modification. ModCallContext originates from that older naming.

For semantic interpretation during the transition:
- old executable-unit "mod" -> CodeEntry;
- ModCallContext -> CodeEntryContext;
- current Pack -> the whole packaged mod/extension/content unit, not merely its
  executable code file.

Do not infer a separate modern architectural object called Mod merely because a
legacy DA uses ModCallContext or refers to executable mod code. Read the
contract semantically and apply the current CodeEntry terminology where the
concept is unchanged.

Design-update policy
--------------------
Do not perform a terminology-only search-and-replace over the legacy DA corpus
now. The design documents will be updated when implementation pressure exposes
requirements that justify revisiting the relevant design area. At that time the
terminology change should be integrated together with the substantive design
update so relationships, responsibilities, and newly discovered requirements
can be reviewed as a whole.

Until such an update occurs, legacy terminology remains textually present and
must not by itself be classified as a semantic implementation/design mismatch.
The integration reconciliation process should translate the terminology first,
then compare the actual contracts.
