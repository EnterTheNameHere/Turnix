ACCEPTED REQUIREMENTS
---------------------
Reuse existing hardware telemetry; avoid duplicate collectors.
Monitor ordinary inference and variability, not only optimizer experiments.
Measure whole-system CPU, RAM, GPU and VRAM under normal competing workloads.
Keep engine-specific instrumentation with the engine integration, not generic
backend. Unused engines must not load their monitoring.
Future hardware providers may include AMD/Radeon and Intel; initial NVIDIA
support must not become a universal dependency.
When unused, optional monitoring must not keep polling or retaining histories.
Shared collection must honor active consumers independently.
Monitoring never authorizes server restarts or optimizer experiments.
Backend versus Pack placement remains open to actual implementation pressure.
Optimization should consider speed, latency, memory headroom and variability.

APPLICATION OBSERVATION BOUNDARY (TELEMETRY NOTE, 2026-10-29)
------------------------------------------------------------
The user relayed the telemetry conversation's architectural clarification:
ordinary inference observation must not require an Application to know which
hardware telemetry provider is available or how that provider is shared.
An Application requests observations appropriate to its needs. Implementation
resolves whether these come from an existing service, an optionally activated
provider, or no available provider. Provider discovery, activation mechanics and
sharing remain behind that application-facing boundary. Hardware unavailability
must be explicit and must not be represented as a zero-valued measurement.

Preserve this contract if implementation later moves between backend and Packs.
Reusing TelemetryService is a candidate implementation mechanism, not a required
Application dependency. The note does not establish new Pack activation authority,
require automatic provider activation, or resolve the three scoping decisions
below. This remains working coordination knowledge, not canonical DA/IS design.

STREAMED-TEXT MEASUREMENT (ACCEPTED)
------------------------------------
Normal inference monitoring must remain useful without engine-native token
counters. Timestamp delivered text using a monotonic clock; expose observed
characters/second and optionally words/second, plus first-text latency and
delivery variation. Stream chunks are not necessarily model tokens; network
or buffering effects may cause bursts. Use time windows for meaningful plots.
Do not present words/second or characters/second as actual tokens/second or
convert them with an arbitrary universal ratio. When reliable engine token
measurements exist, preserve them separately. Generic stream observation can
work across providers; engine-specific metrics remain optional.
Do not retain generated content solely to calculate rates, and avoid additional
work when no consumer has enabled monitoring.

   TelemetryConfiguration is fixed per service, and history sampling starts a
   thread when configured; PM-01 now supplies the per-consumer subscription API.
   Define independent consumer ownership and bounded retention so ending one
   consumer does not stop another, and the last monitoring consumer releases
   monitoring-owned polling/history without stopping unrelated consumers.
2. DONE for the bounded backend contract: accepted PM-02 provides the stream seam.
   Original scope: add an opt-in provider-neutral observer at the existing LLM stream boundary
   (LlmProcessingPipeline._streamResolved is a candidate, subject to accepted

   Words/sec may be deferred. Preserve native token metrics separately if made

   observer, retain no monitoring history and do no monitoring-specific per-event

   stream duration uses monotonic_ns(); directly comparing those values is wrong.
   Choose a monotonic timestamp or an explicit clock-correlation contract, with
   clear semantics for clock jumps. No second hardware collector is justified.

telemetry consumers. Runtime tests and exact refs/results must be reported before

BOUNDARY DECISIONS - INTEGRATION PROPOSALS FOR DESIGN REVIEW
------------------------------------------------------------
These proposals incorporate the telemetry note and are accepted, with the
clarification recorded in the design-owner decision below. Concrete task
boundaries and verification now live in the prepared work packages.

1. Access authority and placement: expose provider-neutral observation requests
   through an invocation-authorized Application facade. A returned observation
   session needs explicit lifetime authority if it can outlive that invocation;
   it must not retain an invalid CodeEntryContext. Host composition resolves
   shared infrastructure behind the facade. Do not require Applications to select
   hardware providers or construct/share TelemetryService. Optional activation
   must use the applicable existing activation authority; its availability and
   policy still need agreement. Physical backend/Pack placement stays replaceable.
2. Consumer lifecycle: use independently releasable subscriptions with bounded
   retention. Run-scoped monitoring releases its own claim on completion, failure
   or cancellation. Ending the last monitoring subscription stops only work owned
   by monitoring; pre-existing telemetry consumers retain their own claims. Agree
   how existing service ownership participates before modifying its lifecycle.
3. Clock alignment: use host-process monotonic sample timestamps for hardware and
   stream correlation, retaining wall-clock time separately for display. Define
   the timestamp as observation time and expose sampling gaps rather than implying
   simultaneous collection. Wall-clock changes must not alter rates or ordering.
   Monotonic values from different processes/hosts require an explicit correlation
   contract and are outside the first local-process slice.

DESIGN-OWNER DECISION - ACCEPTED (2026-10-29)
----------------------------------------------
The three Integration boundary proposals above are accepted for the initial
local-process passive monitoring implementation, with this clarification:
long-lived observation is permitted when it has independent valid lifetime
ownership; it must not retain an expired invocation CodeEntryContext.

1. Application-facing, provider-neutral observation requests through an
   authorized facade. Applications specify needed observations without choosing
   hardware vendors or managing collection providers. Invocation authority
   must not be implicitly stretched beyond its lifetime; ongoing observation
   uses explicit valid session/owner authority. Backend versus Pack physical
   placement and optional provider activation policy remain open.
2. Independently releasable, bounded observation subscriptions. Run-scoped
   claims release on success, failure or cancellation; unrelated consumers'
   claims persist. Different sampling requirements must not cause duplicate
   collectors or let one consumer invalidate another. Select the mechanism
   during implementation against existing TelemetryService ownership.
3. Host-process monotonic timestamps for sampling and inference alignment;
   separate wall clock for display; gaps and non-simultaneous collection are
   explicit. Cross-process/host clock correlation is deferred.

Integration may now decompose and delegate the three bounded implementation
areas with named owners, exact refs, dependency contracts and architectural
tests. This acceptance authorizes scoping/delegation, not an unrestricted
implementation of automatic optimization, UI, tuning or server restarts.
