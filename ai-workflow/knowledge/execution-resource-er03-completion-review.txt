R1-A: invocation can execute while composition owns the activation
------------------------------------------------------------------
providerComposition.invocationBoundary calls requireCompositionReady before
entering invokeCapability/runJob. ApplicationRuntime.requireCompositionReady
checks _compositionAttempt while holding runtime._lane, then releases that lane.
The decorated method acquires its execution lane later; no atomic admission or
second protected validation ties the gate check to execution.

Deterministic reproduction:
1. A real active runtime starts invokeCapability. Pause immediately after the
   original requireCompositionReady has successfully returned.
2. On a second thread activate an empty batch through public PackLoader.activate.
   Hold its trusted composer with an Event, after the runtime entered composing.
3. Resume the prechecked invocation. Its actual capability handler runs and reads
   _compositionAttempt.phase == 'composing', rather than rejecting.

This violates the authorized public invocation exclusion during prepare/compose.
It allows arbitrary application code/mutation to overlap the outside-lock
composition snapshot. The reproducer uses real runtime gates, registration and
activation; the monkeypatch only introduces an Event pause after the real check.
No sleeps, fake ownership assertions or production-source changes are involved.

R1-B: runtime close/stop can finalize a provider during composition
------------------------------------------------------------------
prepareLlmClose calls requireNoPendingComposition before registry revocation and
finishClose. That check does not atomically reserve a shutdown phase that excludes
ActivationAttempt construction. The attempt constructor rejects _closed/current
attempt, but not a shutdown already past its preflight check. A new activation can
therefore start between the shutdown check and its callbacks/legacy teardown.

Deterministic reproduction (both public runtime.close and runtime.stop):
1. Create a real hosted/composed runtime and explicitly materialize A using the
   real grant/domain path and fake owned process/HTTP.
2. Start shutdown, pausing immediately after the original no-pending check returns.
3. Start a later public empty activation batch and hold its composer with an Event.
4. Resume shutdown. It terminates the owned process while the callback is still
   outstanding; it does not retain that object until the composer unwinds.

Both cases fail 'Shutdown finalized provider during composition'. This violates
authorization sections 1/2 and contradicts the worker's pending-attempt cleanup
claim. The outer lifetimeBoundary's later check cannot undo finishClose callbacks
already invoked by prepareLlmClose.

Required correction / source bounds
------------------------------------
Serialize activation admission, invocation entry and shutdown admission closure
at their actual use boundary. Use a runtime-owned gate/issued state or equivalent
atomic protocol, not another detached preflight check with the same race. Set
shutdown exclusion before any provider finalizer can run. An activation that wins
must retain its objects while composing; a shutdown that wins must prevent a new
attempt from starting. Likewise the invocation/activation winner must be decided
before arbitrary capability/Job code enters the protected region.

Preserve immediate pending/typed errors, no waiting across lanes, outside-lock
composition/provider cleanup, existing Job/transaction serialization and per-batch
rollback. Do not simply hold the runtime lane around composer callbacks, poll,
retry, remove architectural assertions, or revoke unrelated old work on a failed
later batch. Audit equivalent host close/stop, direct PackLoader close/activation,
standalone initialization and failed-composition paths for the same gap. Copied or
reentrant invocation scopes must not become new activation authority.
This remains the authorized ER-03 lifecycle seam, not a new grant/admission design.
If correction actually requires broader ER-01/02 changes, report exact evidence
before expanding; otherwise implement/test/report R1 directly.
