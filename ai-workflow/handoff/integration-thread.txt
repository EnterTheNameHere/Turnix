Reconciliation results
----------------------
ManualActivationPlan + mechanical PackLoader preserve the DA-14/DA-29 authority
shape and are an intentionally incomplete PackManager substitute.

CodeEntryContext substantially preserves DA-30 ModCallContext lifetime and
mediation semantics for the currently implemented facade subset.

LlmProcessingPipeline is a fixed LLM-specific partial materialization of DA-31.
The exercised Evil path correctly nests its ProcessingRun transaction under the
outer Job transaction. Direct runProcessing() against the committed root can,
however, make ProcessingRun completion the effective authoritative commit
boundary; do not make that the final generic ProcessingPipeline contract.

The previously flagged runJob() memory-before-I/O ordering is classified more
precisely. DA-04 and DA-24 explicitly allow already committed state to remain
authoritative even when the owning OrchestrationUnit later fails. A repository
regression test deliberately requires a failed Job with
 authoritativeStateAccepted=True after managed-I/O publication failure. This is
therefore not an accidental ordering defect. The incomplete part is DA-07:
current ManagedIo is not yet the full IoManager with identity-bearing rollback
points, provider system, root enforcement, and recovery semantics. Do not claim
cross-domain memory+filesystem atomicity that does not exist.

SaveBundle/ApplicationStore match DA-20 identity shape but materialize only the
committed-value portion of the designed durable closure. Immutable generation
and current-pointer recovery mechanics are candidate implementation-spec design
for later promotion.

Producer/validity/provenance/dependency identity and SourceObservation remain
candidate newer implementation design awaiting documentation integration.

Evil execution graph findings
-----------------------------
One outer evilAnalysis.run@1 Job owns the whole configured batch. Every
per-window LlmProcessingPipeline.runProcessing() is a child transaction because
the CodeEntry LLM facade passes the current invocation memory view. Its
completeWindow capability stages application result identity in that same child
transaction. ProcessingRun success therefore promotes into the still-speculative
outer Job; it does not independently publish Application state in the exercised
path.

Per-window result export is not actually an immediate irreversible side effect:
evilAnalysis.results@1 writes through the same outer Job ManagedIoTransaction,
so files remain staged until Job I/O publication. Export exceptions are caught
per window and represented as result evidence; they do not currently fail the
Job. This is Evil application policy.

After Job return the CLI separately calls saveApplication() whenever
 authoritativeStateAccepted is true. Therefore authoritative value acceptance,
result-JSON publication, and SaveBundle generation publication are three
separate boundaries. On managed-I/O failure after memory commit, the Job fails
but the CLI still saves the accepted Application state before re-raising the
error.

Prompt preview uses prepareProcessing() inside a Job, saves accepted reusable
preparation after Job return, then writes preview files as CLI-owned diagnostic
projections outside that Job transaction.

The reusable shape to carry into materialization testing is the outer
OrchestrationUnit -> child ProcessingRun -> optional transactional completion
spine, not Evil's prompt/chat/window algorithms.

Shared llama.cpp findings
-------------------------
first-party/llmDrivers/llamaCpp is the correct shared provider for both active
applications. It owns one long-lived driver per loaded CodeEntry, supports
managed/external server operation and model switching, and exposes exact token
estimation plus streaming chat completion.

Current dedicated tests cover parallelSlots and exact token estimation only.
The provider and its test file predate the new source-documentation rules:
codeEntry.py has many undocumented classes/helpers/lifecycle functions, and
 test_llamaCpp.py lacks the required first-line path/version marker. Any code
change there must bring touched files into the current source rules and expand
coverage appropriate to the change.

Processing tests reviewed
-------------------------
Current tests deliberately cover reusable QueryItem carry-forward, failure
rollback, filter-as-subset semantics, provider-profile-before-build ordering,
historical run snapshot retention when a stable QueryItem identity changes,
observer failure as evidence rather than processing failure, opaque query
payload evidence, completionInput forwarding without automatic retention,
completion failure rollback, and child capability memory not escaping a failed
ProcessingRun.

These tests validate the currently materialized LLM pipeline strongly, but they
are not tests for the full DA-31 generic ProcessingPipeline: no Hook
registration/participation plan, retry/restart, generic processor definition,
or checkpoint semantics exists yet.
