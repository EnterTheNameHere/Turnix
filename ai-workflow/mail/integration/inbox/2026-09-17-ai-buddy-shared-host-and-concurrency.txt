SUBJECT
AI Buddy pressure: shared long-lived host, concurrent applications, and interruptible shared model execution

STATUS
request

CONTEXT
AI Buddy has been established as a new application workstream on branch
actant-ai-buddy. The first implementation will intentionally be small, but the
application is expected to be long-lived and to coexist with Actant Completion.
Materialization Test may also run temporarily while both remain logically available.

Current source inspection confirms that RuntimeHost already owns zero or more
ApplicationRuntime instances, which makes it the current natural host-level lifetime
boundary. However, each ApplicationRuntime still creates and owns its own capability
registry, LLM provider registry/pipeline, PackLoader, process-tool registry, and loaded
CodeEntries. The current first-party llama.cpp CodeEntry therefore owns its own
LlamaCppDriver/server lifetime inside one ApplicationRuntime.

Completion has already reported the overlapping requirement that managed model/server
lifetime move to or be mediated by a host/shared Actant authority. AI Buddy turns that
from a future Completion/Materialization coexistence concern into an immediate
multi-application runtime concern: Completion and AI Buddy are both expected to remain
running, while heavy temporary work may compete for the same model/GPU resources.

AI Buddy exploration also expects work with different latency classes. Slow cognition
may be running while a low-latency path receives user speech or another interruption
signal and decides whether the active work should be cancelled. For this to be useful,
cancellation eventually needs to reach active provider inference rather than merely
marking its eventual result stale.

REQUEST / INFORMATION
Please treat the following as shared Integration pressure:

1. Preserve and strengthen one host-level authority capable of knowing about multiple
   simultaneously active Actant applications. Applications should not become separate
   Actant universes with mutually unaware shared-resource ownership.

2. Shared drivers/services/Packs whose semantics are cross-application need a lifetime
   above one ApplicationRuntime when appropriate. In particular, llama.cpp managed
   server/model residency must not be multiplied once per application merely because
   each ApplicationRuntime owns its own current provider registry/PackLoader.

3. The shared authority needs enough knowledge to arbitrate expensive runtime
   resources across at least these usage shapes:
   - Completion: persistent, interactive, latency-sensitive;
   - AI Buddy: persistent, mixed interactive and opportunistic cognition;
   - Materialization Test: temporary, potentially large/heavy model execution.
   The final policy/scheduler is not requested here; this is pressure on ownership and
   visibility boundaries.

4. Cancellation/interruption should become a reusable execution concern. AI Buddy may
   run low-latency interrupt classification beside slower cognition and needs a path
   which can request cancellation of the active model inference. Provider-specific
   realization may differ, but application logic should not own the low-level abort
   mechanism.

5. Keep specialist capabilities provider-independent. Future AI Buddy ASR/TTS/vision
   may be native Windows facilities, dedicated local engines, optional runtimes such as
   vLLM, or cloud providers. Applications should request the semantic capability and
   let driver/provider selection realize it. This is direction/pressure only; AI Buddy
   is not asking Integration to materialize ASR/TTS now.

HOST/CLIENT DESIGN DIRECTION
This is advice for early evaluation, not a requirement to implement the existing
specification verbatim.

DA-28 already defines RuntimeHost as a running host boundary and explicitly allows it
to host zero, one, or multiple ApplicationRuns. IS-03..IS-06 already explore concrete
workspace ownership/host locking, command/startup modes, discovery/connection to an
existing host, and local/LAN clients. IS-05 in particular has interactiveHost,
oneShotCommand, serve, connect, test, and launcher startup modes composed from shared
operations such as DiscoverExistingRuntimeHost, ConnectRuntimeHost, StartRuntimeHost,
CreateApplicationRun, and StartApplicationRun.

That existing family appears directionally relevant now because the immediate
application pressure wants something close to a long-lived Actant executable/host:
- it may start because an application needs it;
- it may remain while at least one application exists;
- a persistent/background mode may later keep it available for commands;
- later invocations or tools may act as clients/control surfaces rather than creating
  another independent authority;
- shared drivers/resources can then be owned and arbitrated in one place.

However, do not treat DA-28 or IS-03..IS-06 as preservation requirements. They are
EVOLVING design material. This project already accepts that live implementation
pressure can reveal a better design than an earlier DA/IS draft; in that case the
better materialized design should later be integrated back into the design corpus.
The same rule used for replacing weak immature implementation should apply to weak or
premature ideas. The recommendation is therefore to inspect and reuse the useful
host/client concepts early, not to freeze their current shape.

OWNERSHIP EXPECTATION
Integration owns reusable RuntimeHost/shared-runtime/resource/cancellation facilities.
AI Buddy owns its application-specific cognition, scheduling policy where genuinely
application-specific, terminal/TTS interaction behavior, and later avatar/personality
semantics. If scheduler/event semantics prove generally reusable, ownership should be
reconsidered based on the concrete contract rather than where the first experiment was
written.

BLOCKING
No for the first tiny AI Buddy materialization if it can run alone using current
facilities. Becomes blocking when AI Buddy and Completion need concurrent shared model
use, when model residency must move between them and Materialization Test, or when
interruptible inference is required for usable interactive behavior.
