REQUESTED FIRST PACKAGE: EX-01 AND EX-02 TOGETHER
Deliver a minimal, genuinely runnable, first-party Actant Experiment Runner
Application with a terminal entry path and declarative experiment inputs.
Do not implement EX-03/04/05 in full in this first package.

EX-01: experiment definition and validation
- Define a small, explicit, versioned input structure for a named experiment:
  named authorized execution configurations; immutable ordered conversation
  inputs; per-call/provider defaults and permitted overrides; bounded repetitions
  (initially one); and clear stop/error policy. Keep the conceptual distinction
  between definition and individual execution/result.
- Validate structural shape, unique names/IDs, ordered roles/turns, references,
  supported option types/bounds, startup-vs-per-call distinction and conflicting
  unsupported settings before starting llama-server. A configuration name is
  not the model/descriptor compatibility key.
- Keep configuration/profile authority host-trusted; untrusted experiment input
  must not supply arbitrary argv, model paths, environment, process commands,
  driver.stop/ensureModel, ports, grant identities or host selectors.
- No demand for physical retained KV, guaranteed physical cold context, generic
  reproducibility or universal thinking-control effectiveness. Reject unsupported
  REQUIRED guarantees explicitly rather than silently weakening them.

EX-02: minimal real Actant Application
- Own Application/Pack semantics, lifecycle, terminal invocation and basic result
  inspection. Consume approved ctx.llm/session and resource facilities, not a raw
  llama.cpp client. Use host-installed trusted LlamaCppComposition, immutable
  actual-owner grants, explicit initial profile transition and existing provider
  estimation/inference/cancellation cleanup.
- First actual acceptance milestone: ONE named authorized profile, ONE immutable
  conversation of at least TWO input turns, with correct ordered conversation
  history and model replies carried according to a declared history policy.
  Test both construction of the outgoing requests and the resulting turn
  sequence; do not flatten multi-turn into unrelated independent prompts.
- Store result for that specific execution distinctly from its definition:
  per-turn input/answer, separately returned reasoning if any, model/provider
  metadata, requested and actually resolved settings/evidence, completion or
  failure outcome, duration and bounded usage where available. Don't log raw
  prompts/reasoning/secrets globally or expose them through shared monitoring.
  Implement only the minimum persistence/results seam needed by the first demo;
  full durable archive/export/comparison is EX-04/05 follow-on.
- Let the Application control conversation/history policy; separate reasoning
  is NOT automatically reinjected as future assistant text. Repeated runs,
  multiple configurations, exclusive multi-turn reservation policy and comparison
  are EX-03/05, except for interfaces that should be shaped now to avoid needless
  redesign. Do not let a single call's normal success stand in for entire run
  success or claim safe cleanup from a Job terminal outcome.
