SUBJECT
Completion pressure: external ingress and host-owned managed model residency

STATUS
request

CONTEXT
Actant Completion source inspection on branch actant-completion established the live runtime path before application implementation begins.

The current RuntimeHost owns zero or more ApplicationRuntime instances and each ApplicationRuntime owns its own PackLoader and LlmProviderRegistry. The current first-party llama.cpp CodeEntry creates a LlamaCppDriver during onLoad, immediately starts the configured default managed model, registers the provider, and stops the process during onUnload. LlamaCppDriver owns the llama-server subprocess, activeModelName, model switching through stop()+_startModel(), readiness polling, and request streaming.

The current backend tree contains no live external transport/RPC/WebSocket/server layer in the newer runtime execution spine. Completion therefore needs an external request ingress, but should not establish a Completion-owned endpoint as Actant's application model or resurrect the superseded web runtime as authority.

REQUEST / INFORMATION
Please treat the following as shared Integration requirements exposed concretely by Completion and overlapping Materialization Test:

1. Managed model/server lifetime must move to or be mediated by a host/shared Actant authority above one application's llama.cpp CodeEntry lifetime. Completion, Materialization Test, and later AI Buddy must be able to request model execution without independently owning mutually unaware llama-server processes.

2. The shared authority must eventually support acquisition/release and replacement of expensive resident models. The immediate proving-ground operation can remain process stop/start because current llama.cpp only gives us that practical unload mechanism, but application/provider code should not become the arbitration authority.

3. Applications need a production-shaped externally initiated activation/dispatch boundary. Completion must be addressable while logically available even if expensive model resources are absent. Incoming VS Code work targets Actant/Completion first; model acquisition and provider execution are separate downstream operations.

4. Request cancellation/staleness must eventually cross activation/model execution. Current LlmProcessingPipeline has a streamObserver but no cancellation contract, and the urllib llama.cpp streaming call has no Actant cancellation primitive. Completion can initially run explicit manual requests without cancellation, but automatic inline completion will require it.

For the first Completion materialization, this workstream intends to use a narrow application-owned transport adapter around the current RuntimeHost rather than claiming that adapter is the final shared Actant transport. Likewise it can consume the existing llama.cpp provider while resource conflicts are absent, but will not duplicate or fork the managed-server implementation locally.

OWNERSHIP EXPECTATION
Integration owns the reusable runtime/model-resource/activation abstractions. Completion owns VS Code-specific observation/request/insertion behavior and application-specific completion semantics.

BLOCKING
No for the first explicit/manual Completion request path if one model is used without concurrent application pressure. Blocking once Completion must coexist dynamically with Materialization Test model residency, or when dormant/wake/cancellation semantics are required.
