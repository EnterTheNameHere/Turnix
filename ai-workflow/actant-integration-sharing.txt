ACTANT IMPLEMENTATION KNOWLEDGE, STATE AND HANDOFF SHARING
==========================================================

01. PURPOSE
-----------

01.01. Actant is currently being materialized under pressure from three cooperating implementation threads: Actant integration, Evil birthday paper analysis application, and model materialization test application.

01.02. The integration thread owns Actant internal implementation, shared first-party reusable Packs, integration integrity, and shared tests. The application threads own application-specific iteration and act as independent design-pressure sources.

01.03. Repository documents are the durable communication mechanism between threads and also provide restart/handoff state when a conversation must continue in a new thread. Chat context alone is not shared implementation authority.

02. SHARING MODEL
-----------------

02.01. Use small purpose-specific documents with a small index rather than one continuously growing handoff file. GitHub retrieval may use bounded line ranges; smaller documents reduce unrelated retrieval and make complete retrieval easier to verify.

02.02. Every participating thread MUST treat the shared index as the entry point for cross-thread knowledge. The index identifies current documents, ownership, purpose, and retrieval guidance.

02.03. Each document MUST have one clear knowledge role. Split documents that become too broad or too long and update the index. Do not preserve a monolithic layout for compatibility.

03. DOCUMENT CLASSES
--------------------

03.01. INDEX documents are small routing documents containing participating areas, branch relationships where relevant, document paths, ownership, descriptions, retrieval guidance, and pointers to current state/handoff documents. An index is not a duplicate summary of everything it indexes.

03.02. KNOWLEDGE documents contain durable facts/contracts needed by more than one thread: integration rules, ownership boundaries, materialized interfaces, temporary production-shaped cheats, and shared-Pack contracts. They describe things another thread may safely rely on and SHOULD NOT become chronological diaries.

03.03. STATE documents describe what is materially true now for an implementation area: implemented facilities, exercised framework surfaces, temporary substitutions, known gaps, integration dependencies, exported requirements, and useful integration points. Replace obsolete statements rather than accumulating historical states; Git provides history.

03.04. HANDOFF documents preserve active continuation context: current objective, completed/in-progress work, decisions not durable elsewhere, unresolved questions, failures/test results, branch/commit position, and exact recommended next actions. Handoffs are disposable operational documents. Move durable information into knowledge/state rather than growing the handoff indefinitely.

03.05. Application integration-state documents MUST NOT duplicate full application handoffs. They record only what other threads need to know about that application as an Actant consumer and design-pressure source.

04. OWNERSHIP
-------------

04.01. Each shared document MUST have a declared owner in the index or document.

04.02. Actant integration owns shared Actant/internal contracts, reusable first-party Pack state, integration rules, and integration handoff. Each application thread owns its application-specific state and handoff.

04.03. Ownership means responsibility for semantic correctness, not exclusive write permission. Another thread may make a necessary coordinated edit during an authorized project-wide change.

04.04. When changing another owner's document, preserve the distinction between observed application state and framework-owned requirements. If uncertain, record a requirement/question for the owner rather than inventing application state.

05. READING RULES
-----------------

05.01. Before a change whose correctness depends on another thread's implementation, read the shared index and relevant state/knowledge document. Do not load every handoff merely because it exists; retrieve the smallest complete relevant set.

05.02. For long documents, ranged retrieval is encouraged, but verify the complete relevant section was retrieved and extend the range when dependencies cross it.

05.03. Do not infer current implementation state from old chat summaries when repository state exists.

05.04. DA, DD, ODA, IS and successor design documents remain design authority. Shared implementation documents describe materialization and coordination and do not silently amend specifications.

05.05. When implementation differs because a feature is not materialized, preserve the production-shaped contract and explicitly document the temporary substitution. Do not redefine design around a shortcut.

06. WRITING RULES
-----------------

06.01. Update shared state as part of the change that makes old state false. Do not knowingly leave sibling threads with stale integration knowledge.

06.02. Record semantic facts rather than source trivia directly discoverable from nearby code, unless needed to understand a temporary contract or integration hazard.

06.03. Clearly distinguish designed behavior, currently implemented behavior, temporary/manual substitution, planned but unimplemented behavior, and open questions.

06.04. Do not retain obsolete state for historical interest. Git is the history mechanism.

06.05. When application work exposes reusable behavior, record it in shared integration state/knowledge and move implementation to Actant internal/shared code when that is the correct ownership boundary.

06.06. When integration changes a consumer-facing contract, migrate affected consumers and update their integration-state documents. Backwards compatibility is not a goal for immature implementation unless explicitly required by a design contract.

07. CROSS-THREAD REQUIREMENTS
-----------------------------

07.01. An application may discover a requirement without owning its solution. Record the use case, required framework/shared behavior, current workaround if any, blocking status, and relevant source/tests in its integration-state document.

07.02. Integration decides the Actant/shared abstraction and may alter project-wide implementation. Prefer a non-local reusable solution when a requirement exposes a general weakness; existing code shape is not a reason to preserve a weak abstraction.

07.03. After integration provides the solution, remove/narrow application workarounds and update state so the requirement is no longer unresolved.

07.04. Similar independent requirements from both applications are strong evidence for Actant internal/shared first-party Pack ownership unless their semantics are genuinely application-specific.

08. BRANCH COORDINATION
-----------------------

08.01. The Actant integration branch is the parent integration line for shared framework and reusable-Pack work. Application branches consume integration changes by rebase, merge, or equivalent explicit synchronization appropriate to the current workflow.

08.02. Application-specific iteration remains on application branches. Framework/shared changes discovered there SHOULD ultimately enter integration and then become available to both consumers.

08.03. State/handoff documents SHOULD record synchronization commits when the exact integration point matters. Never assume similarly named files on sibling branches contain identical state; check the branch/ref.

09. THREAD START AND HANDOFF PROCEDURE
--------------------------------------

09.01. A new/resumed implementation thread SHOULD retrieve: (1) shared index, (2) this sharing contract, (3) its current state, (4) its handoff if present, and (5) only cross-thread state/knowledge needed for immediate work.

09.02. Before ending substantial work, ensure current state is accurate, changed shared contracts are updated, cross-thread requirements are recorded, handoff identifies unfinished work and exact next action, and the index reflects added/split/moved/retired documents.

09.03. A handoff must let a replacement conversation continue without reconstructing implementation history from chat logs. It need not teach all of Actant; durable background is routed through index/knowledge documents.

10. CORE INTEGRATION PRINCIPLE
------------------------------

10.01. Evil analysis and materialization-test are deliberate independent pressure tests, not merely downstream clients. Their requirements may expose missing or misplaced framework behavior and may justify project-wide breaking changes.

10.02. Do not add compatibility layers, local patches, duplicate abstractions, or consumer-specific framework behavior merely to preserve existing immature code.

10.03. Materialize only Actant portions required by current work, but keep production shape capable of receiving fuller designed implementation without forcing consumers to be rewritten around today's shortcuts.

10.04. Temporary manual behavior substitutes for an unimplemented authority; it does not become a new authority. A manually supplied ActivationPlan, for example, may stand in for unimplemented PackManager graph preparation while consumers continue against the intended activation shape.

11. PYTHON SOURCE RULES
-----------------------

11.01. Actant Python source targets Python 3.15. Python 3.15 is currently pre-release, but it is the production language target rather than an older-version compatibility target.

11.02. Every Python code file MUST begin on its first line with a repository-path and source-version comment in this form:

       # file: path/to/file.py ; version: 1

11.03. The path MUST identify the file's repository path. The integer version begins at 1 for a newly governed source file and MUST be incremented whenever that file's code changes.

11.04. Source-file version is independent of Git history, Pack version, API version, schema version, and release version. It is a lightweight explicit revision marker for the code file itself.

11.05. Python classes and functions MUST have proper production-quality docstrings. This includes private functions/methods; privacy is not an exemption from documentation.

11.06. Magic methods/functions MUST also have docstrings. Their language-defined purpose may be obvious, but their Actant-specific behavior, invariants, side effects, ownership, or lifecycle role still requires documentation where applicable.

11.07. Docstrings SHOULD explain the semantic contract rather than merely restating the identifier or signature. Document arguments, return behavior, exceptions, state mutation, lifecycle/ownership constraints, and non-obvious invariants where they are relevant to correct use.

12. TEST EXECUTION
------------------

12.01. Tests are part of Actant implementation and integration work and SHOULD be added or updated with behavior changes where tests provide useful protection.

12.02. The AI implementation threads currently do not have a suitable Python 3.15 runtime environment and therefore MUST NOT claim that Python 3.15 tests were executed when they were not.

12.03. The user performs Python 3.15 test execution when requested. The implementation thread may continue coding without requesting every intermediate test run when the remaining work can be reasoned about safely.

12.04. The implementation thread decides when a test run becomes necessary for safe continuation or integration. Relevant factors include uncertainty about runtime semantics, broad refactors, dependency interactions, migrations, failures whose cause cannot be established statically, and reaching an integration point where further work would compound an unverified assumption.

12.05. When a test run is required, provide the user with the exact relevant command(s) and state what result or uncertainty the run is intended to resolve. After receiving results, record material failures or integration conclusions in the appropriate state/handoff document.

12.06. Lack of local Python 3.15 execution is not a reason to omit tests, weaken production code, target an older Python version, or add compatibility machinery unless such compatibility is independently required by design.
