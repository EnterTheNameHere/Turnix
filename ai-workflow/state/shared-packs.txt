llama.cpp shared-runtime materialization
----------------------------------------
Managed llama.cpp lifetime is no longer inherently CodeEntry/ApplicationRuntime-local.
The active structured CodeEntry keeps an application-local provider facade, but
manageServer=true acquires a RuntimeHost-owned shared driver lease.

The same compatible managed configuration may therefore be consumed concurrently by
multiple ApplicationRuns without starting mutually unaware llama-server processes.
Pack activation no longer eagerly starts the default model; actual provider work
materializes the selected model through the existing ensureModel() path.

This is an ownership/lifetime seam, not a resource scheduler. Incompatible managed
configurations currently conflict rather than being arbitrated.

The structured llama.cpp provider now also participates in generic Job-owned
cancellation. During an active inference HTTP stream it registers a stop callback on
the generic CancellationSignal and closes that response when cancellation is
requested. Job/ProcessingRun outcome classification remains outside the provider.
Model startup/readiness before the stream is not yet interruptible.


Next shared-provider pressure
-----------------------------
The planned arbitration layer remains outside llama.cpp provider semantics.
SharedServiceRegistry continues to own shared driver lifetime. A provider-neutral
execution-resource layer is expected to arbitrate residency/active claims; llama.cpp
will be the first concrete adapter for model materialization/replacement.

The initial intended behavior is deliberately limited: idle incompatible residency may
be replaced automatically, while incompatible actively used residency must surface
explicit contention. Any future active preemption must use the owning Job cancellation
path rather than terminating llama.cpp execution behind Job lifecycle semantics.
