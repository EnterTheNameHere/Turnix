ACTANT INTEGRATION STATE - SHARED FIRST-PARTY PACKS

Owner
-----
Actant integration thread.

Current verified shared provider
--------------------------------
first-party/llmDrivers/llamaCpp is a separate first-party Pack/provider and is
activated by the Evil Birthday application's manual activation plan as
llmDrivers.llamaCpp. It is not owned by the Evil analysis Packs.

This separation makes the llama.cpp driver a shared integration surface for the
Evil analysis application and the materialization/model-test application.
Changes required by either consumer should prefer this shared provider boundary
when the behavior is provider-level rather than application-specific.

Current application-specific Packs
----------------------------------
The Evil Birthday application currently activates these application-owned Packs:
- evilBirthdayAnalysis.prompts
- evilBirthdayAnalysis.transcript
- evilBirthdayAnalysis.chat
- evilBirthdayAnalysis.chatSemantics
- evilBirthdayAnalysis.identity
- evilBirthdayAnalysis.tokenBudget
- evilBirthdayAnalysis.results
- evilBirthdayAnalysis.analysis

They are design-pressure sources, not automatically reusable framework Packs.
If the materialization application exposes the same semantic need, integration
should decide whether the abstraction belongs in Actant core or a reusable
first-party Pack rather than copying an Evil-specific Pack.

Analysis wrapper caution
------------------------
evilBirthdayAnalysis.analysis/codeEntry.py currently loads and re-exports a
large _implementation.py and then replaces/adapts selected behavior. Source
comments explicitly describe this as a way to replace focused hot paths and
boundary adapters without rewriting the large source module in place.

Therefore _implementation.py must not be interpreted as an independently
current implementation surface merely because definitions remain present.
Determine effective behavior through the wrapper and live capability path.
