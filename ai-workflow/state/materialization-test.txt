ACTANT INTEGRATION STATE - MATERIALIZATION / MODEL TEST APPLICATION

Owner
-----
Materialization/model-test application thread owns application-specific test
workflow. Actant integration owns this integration-facing summary.

Required application modes
--------------------------
The application is intended to support both:

1. Classic mode: reproduce the model test as though turns were manually run in
   LM Studio, preserving the ordinary turn-by-turn behavior.

2. Actant mode: execute the same broader workflow through Actant facilities so
   state, orchestration, persistence, and later checkpointing/UI can be tested as
   framework behavior.

Current UI constraint
---------------------
The current application generation is CLI/terminal execution only. It should
read its configuration/data and perform the selected configured work. Do not
invent an interactive terminal chooser for prompts/tests merely because future
UI will allow selection/composition, file selection, saving, and export.

Prompt/test material
--------------------
The first implementation may keep complete copy/paste-ready prompts in JSON.
Later versions may decompose/combine prompt material once doing so has a concrete
benefit.

Checkpoint direction
--------------------
A future Actant-mode run may place checkpoints through a longer test and resume
from the last accepted checkpoint after interruption. This is not required for
the first iteration. Do not prematurely distort current orchestration/persistence
interfaces around an unimplemented checkpoint subsystem.

Configured external tools
-------------------------
Actant now owns the shared completed-process boundary required for Ruff/ty static
analysis. Host/runtime configuration maps logical tool names under processTools
to absolute executable paths. CodeEntry code invokes only the logical tool name
through ctx.process; it cannot select an arbitrary executable or shell command.

ctx.process.run() accepts an argument vector, optional working directory, and
optional timeout. A normally completed invocation returns generic evidence with
the logical tool name, configured/resolved executable, exact arguments, resolved
working directory, timing, exit code, stdout, and stderr. Nonzero exit is a
normal completed result, so Ruff/ty findings remain distinct from Actant
infrastructure failure. Resolution, launch, communication, and timeout failures
raise ProcessExecutionError.

The external process itself is irreversible. Its returned evidence becomes
authoritative only if the owning workflow stores and accepts that evidence
through normal Actant transaction/orchestration boundaries. Aborting later state
cannot un-run the external tool.

The process substrate and ApplicationRuntime/CodeEntryContext path were exercised
on the user's Python 3.15 Windows environment on 2026-09-12 together with the
ApplicationRuntime regression tests and were reported green. The subsequent
context-construction cleanup preserves that same process contract and should be
rechecked before the materialization branch consumes its final integration SHA.

Shared integration pressure
---------------------------
The application should reuse the shared first-party llama.cpp provider rather
than introduce an application-owned equivalent. Needs that overlap Evil's
application should be evaluated for Actant/shared-Pack ownership rather than
copied locally.

The model-test workflow is expected to create additional pressure on generic
multi-turn orchestration, exact prompt/response evidence, model execution
configuration, persistence/resume, and eventual checkpoint semantics. Record
those requirements here as they become concrete before changing shared
contracts.
