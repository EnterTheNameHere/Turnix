===============================================================================
ACTANT DESIGN - PLATFORM IDENTITY AND PRINCIPLES
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines Actant's platform identity, motivations, and enduring principles.

Purpose:
--------
Explains why Actant exists and the boundaries shared by its subsystems.
It does NOT prescribe detailed algorithms, storage, APIs, or runtime protocols.


===============================================================================
01. PLATFORM IDENTITY
===============================================================================

01.01. Actant is a standalone, local-first runtime platform for modular
       Applications. It provides orchestration, controlled execution,
       continuity, and explicit authority boundaries.
01.02. Actant is AI-oriented because AI applications frequently combine
       models, tools, long-running work, memory, and independent activities.
       The platform also supports non-AI applications and workloads.
01.03. A model, assistant, Application, Pack, runtime Host, and Actant
       platform are different concepts. None alone defines the platform.
01.04. Actant's identity comes from its contracts and guarantees rather
       than a language, user interface, process, transport, or vendor.


===============================================================================
02. THE PROBLEM ACTANT ADDRESSES
===============================================================================

02.01. A conversation transcript is not a complete execution model.
       Work may be concurrent, ongoing, interrupted, or independent of
       conversational turns and user-visible responses.
02.02. Independent Applications may need to cooperate, use shared engines,
       and preserve meaningful state across activity and lifetime changes.
02.03. Actant provides common foundations for these problems rather than
       requiring every creator to invent its own lifecycle, storage,
       communication, and diagnostic conventions.
02.04. The objective is reusable, comprehensible platform guarantees,
       not to hide all uncertainty or automate every domain decision.


===============================================================================
03. CONTINUITY AND AUTHORITY
===============================================================================

03.01. Persistence-first means that continuity requirements constrain
       system design from the beginning, including state, communications,
       recovery, and handling of incomplete operations.
03.02. Persistence is not a universal promise that every transient
       observation or operation is durably recorded. Contracts define
       the required evidence and durability at each boundary.
03.03. Authoritative committed state, runtime memory, trace evidence,
       acknowledgement, and domain-confirmed outcomes are distinct.
03.04. Missing information does not prove an action never occurred.
       Recovery must preserve uncertainty where evidence is insufficient.
03.05. An outward-facing failure does not erase Actant's responsibility
       for unfinished contractual obligations or safe cleanup.
03.06. Platform and domain authorities remain explicit. Infrastructure
       cannot silently replace the creator's definition of domain success.


===============================================================================
04. MODULARITY AND LANGUAGE INDEPENDENCE
===============================================================================

04.01. Packs package deployable Applications, content, tests, and code.
       CodeEntries identify code that appropriate adapters may execute.
04.02. Adapters realize execution in particular language environments
       without creating a separate Actant platform for each language.
04.03. Python is the current execution implementation focus.
       JavaScript/TypeScript browser sandbox and C# are intended adapter
       directions, not assertions of completed implementation.
04.04. Language-specific interfaces may adapt naturally to their host
       language while maintaining shared platform meanings and guarantees.
04.05. Sharing an implementation language does not grant Pack-provided
       code the same authority as platform implementation code.
04.06. A replaceable component remains accountable for the contracts
       of the boundary it implements. Replaceability is not permission
       to alter externally meaningful behavior.


===============================================================================
05. MULTIPLE APPLICATIONS AND ORCHESTRATION
===============================================================================

05.01. A Host can operate multiple Applications with independent identities
       and lifecycles while managing common facilities where appropriate.
05.02. Applications can share managed resources such as an AI model server
       without becoming owners of each other's complete lifecycle.
05.03. Actant supports ongoing activities beyond request-response chat.
       A communication peer may be temporarily unavailable while work
       governed by separate authority continues.
05.04. Flow coordinates communication relationships, Invocations,
       Subscriptions, Emits, and the obligations imposed by contracts.
       Domains retain ownership of intentions and semantic outcomes.
05.05. Transport is a communication mechanism, not the enduring meaning
       of a Flow relationship. Transport changes need not erase identity.
05.06. Implementation and resource decisions are permitted only within
       the continuity and authority guarantees of the relevant design.


===============================================================================
06. OBSERVABILITY AND ENGINEERING DISCIPLINE
===============================================================================

06.01. 'Trace or it did not happen' means that unrecorded events cannot
       later be established as recorded evidence merely by inference.
06.02. Tracing is structured runtime evidence, not a replacement for
       authoritative state or a demand to trace every machine instruction.
06.03. Useful failure reports preserve context. Local error handling
       should not silently erase diagnostically meaningful information.
06.04. Architectural Tests exercise accepted invariants, including
       interruption and recovery. Optimization cannot redefine them.
06.05. Creators have broad freedom. Actant favors clear interfaces,
       observable failures, and containment over needless prohibition.

07. DESIGN BOUNDARIES
===============================================================================

07.01. This document establishes platform identity and cross-cutting
       principles. It does not specify concrete data formats, APIs,
       storage layouts, transports, adapter internals, or Flow protocols.
07.02. The relevant owning design area defines exact subsystem semantics.
       Avoid promoting examples into platform-wide requirements.
07.03. For the orientation and document map, begin with:
file: design/index.txt

file: docs/design/DA-01_PROJECT_INVARIANTS_AND_PHILOSOPHY.txt

file: docs/design/DD-02_TURNIX_INTERFACE_DESIGN_RULES.txt
file: docs/design/DD-03_TURNIX_CROSS_LANGUAGE_INTERFACE_DOCTRINE.txt
07.05. For tracing semantics, consult:
file: design/area/tracing.txt
07.06. For detailed persistence and Flow contracts, consult the
       applicable design-area specifications and their accepted working
       references. Do not infer completed implementation from design.
