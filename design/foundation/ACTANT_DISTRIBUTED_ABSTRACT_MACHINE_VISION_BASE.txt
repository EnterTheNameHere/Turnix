===============================================================================
ACTANT_DISTRIBUTED_ABSTRACT_MACHINE_VISION_BASE
===============================================================================

Purpose
-------

This document preserves a high-level abstraction that may be useful when
reasoning about Actant:

    Actant can resemble a distributed programming-language runtime or a
    distributed abstract machine.

This is not a proposal to create a new textual programming language.

It is a conceptual lens for understanding why Actant increasingly needs to
define many of the same things a programming language and runtime define:

- values
- operations
- callable interfaces
- scope
- lifetime
- state
- mutation
- transactions
- control flow
- composition
- error propagation
- concurrency
- ordering
- execution targets
- modules
- replacement
- extension
- runtime semantics

The difference is that Actant's logical instructions may be implemented across:

- different host languages
- different language runtimes
- different processes
- different adapters
- different transports
- potentially different machines

This abstraction is useful because it encourages semantic rigor.

It is also dangerous because it may encourage Actant to become unnecessarily
universal, overly transparent, or detached from practical implementation.

This document therefore records both:

- what the programming-language analogy reveals
- where that analogy must stop


===============================================================================
01. THE VIEW FROM VERY HIGH UP
===============================================================================

From a sufficiently high level, Actant no longer resembles only:

- an LLM framework
- a plugin loader
- an RPC system
- a persistence layer
- a pipeline library
- a mod manager

It begins to resemble a machine whose operations are defined by platform
contracts and whose execution is distributed across modular targets.

A conventional machine executes instructions against values.

A programming-language runtime executes functions, methods, expressions, and
control flow against language objects and state.

Actant may execute:

- capabilities
- services
- operations
- actions
- pipelines
- stages
- Pack participants
- Memory transactions
- streams
- commands
- jobs
- adapter invocations

These are not CPU instructions.

They are platform-level semantic instructions.


===============================================================================
02. ACTANT AS AN ABSTRACT MACHINE
===============================================================================

A programming language normally defines or implies an abstract machine.

For example, an abstract machine may contain:

- values
- environments
- scopes
- stack frames
- functions
- objects
- exceptions
- modules
- execution rules

Actant's abstract machine may contain:

- Packs
- services
- capabilities
- operations
- actions
- pipelines
- stages
- participants
- Memory layers
- transactions
- handles
- streams
- jobs
- adapters
- Application identities
- ApplicationRun identities
- trace records

These concepts may be realized differently in different environments.

The semantic object remains an Actant concept even when its physical
implementation changes.


===============================================================================
03. THE PLATFORM CONTRACT AS INSTRUCTION
===============================================================================

A machine instruction has a defined meaning independent of the individual
transistors that realize it.

Similarly, an Actant capability contract may have one platform meaning
independent of the implementation language.

Example:

    llm.stream@1

This can be understood as a platform-level instruction:

    invoke the selected implementation of the llm.stream@1 contract

The implementation may be:

- local Python
- remote Python
- JavaScript
- WebAssembly
- native code
- another future adapter target

The implementation mechanism changes.

The platform instruction remains recognizable.


===============================================================================
04. DISTRIBUTED INSTRUCTION EXECUTION
===============================================================================

A conventional function call may conceptually perform:

    load arguments
    invoke function
    receive result

An Actant-level invocation may require:

    resolve capability contract
    select accepted implementation
    create invocation identity
    create execution context
    create child Memory layer
    attach trace context
    dispatch through adapter
    transfer values or handles
    execute implementation
    stream intermediate outputs
    process cancellation
    collect result
    resolve child Memory
    commit or roll back
    emit trace evidence
    return or retain result

This remains one logical operation even though it may involve many physical
messages and several execution targets.

The logical instruction is distributed over:

- distributed inputs
- distributed outputs
- distributed execution
- multiple authority domains
- multiple lifetimes


===============================================================================
05. CENTRALLY ORCHESTRATED, PHYSICALLY DISTRIBUTED
===============================================================================

Actant may be distributed in execution without being authority-free.

Physical work may happen in:

- backend Python
- adapter processes
- JavaScript runtimes
- browser environments
- subprocesses
- remote services
- future machines

However, backend internals remain the authoritative orchestrator for platform
truth.

The backend determines or mediates:

- accepted Pack graph
- capability availability
- service registration
- implementation selection
- Memory authority
- transaction resolution
- persistent commit
- permission checks
- valid handles
- lifecycle
- trace ingestion
- retained state

A useful description is:

    a centrally orchestrated distributed abstract machine

Another possible description is:

    a distributed execution platform with centralized semantic authority

Neither phrase is necessarily intended as public terminology.

They are reasoning aids.


===============================================================================
06. PACKS AS LANGUAGE-LIKE MODULES
===============================================================================

Packs resemble several programming-language mechanisms at once.

A Pack may:

- define data
- provide a service
- implement a capability
- add a pipeline participant
- replace an implementation
- extend another Pack
- patch behavior
- contribute configuration
- provide commands
- add migrations
- contribute UI
- add validation

This resembles combinations of:

- modules
- packages
- interfaces
- implementations
- traits
- libraries
- middleware
- decorators
- compiler passes
- plugins
- dynamic linking
- link-time replacement

The analogy is useful because Packs are not merely loaded code.

They participate in a larger semantic environment.


===============================================================================
07. PACK GRAPH AS LINKER AND RESOLUTION SYSTEM
===============================================================================

The accepted Pack graph resembles a combination of:

- dependency resolver
- module graph
- linker
- method-resolution order
- build graph
- execution plan
- plugin ordering system

It may determine:

- which Packs are accepted
- which versions are selected
- which implementation replaces another
- which capability implementation is active
- which participant runs before another
- activation order
- shutdown order
- configuration precedence
- data precedence
- migration order

Unlike a conventional linker, the graph may remain relevant during runtime.

It may control dynamic operation propagation.


===============================================================================
08. MEMORY LAYERS AS SCOPE
===============================================================================

Layered Memory resembles scope.

A child layer can see parent state.

It may add or shadow values locally.

Its writes do not become parent truth until accepted.

Example:

    parent scope
        x = 1

    child scope
        reads x -> 1
        writes x = 2

Before commit:

    parent x = 1
    child x = 2

After child commit:

    parent x = 2

After child rollback:

    parent x = 1

This resembles:

- lexical scope
- dynamic environment
- copy-on-write state
- nested transaction
- speculative execution
- savepoint

The analogy is incomplete because Memory layers are also authority and
persistence boundaries.


===============================================================================
09. COMMIT AS SCOPE RESOLUTION
===============================================================================

A nested Actant operation may create nested state environments:

    persistent state
        └── operation
              └── pipeline
                    └── participant

Each environment can propose changes.

Commit means accepting the proposal into the parent environment.

Rollback means discarding it.

This resembles an evaluation rule:

    evaluate child work under environment M_child

    if accepted:
        merge M_child delta into M_parent

    otherwise:
        discard M_child delta

Only the outer persistence authority updates durable truth.


===============================================================================
10. PIPELINES AS CONTROL FLOW
===============================================================================

A pipeline resembles programmable control flow.

It has:

- input
- ordered stages
- participants
- carried values
- side effects through Memory
- termination
- failure
- result

Example:

    input
        -> PrepareInput
        -> BuildPrompt
        -> EngineCall
        -> ParseResponse
        -> Finalize
        -> result

Participants may:

- transform values
- read Memory
- write Memory
- invoke capabilities
- emit streams
- stop propagation
- fail
- request retry

This resembles:

- function composition
- middleware
- compiler passes
- event propagation
- effect handling
- multimethod dispatch

The distinctive Actant property is that participants may run in different
language runtimes while remaining part of one logical flow.


===============================================================================
11. CAPABILITIES AS DYNAMICALLY LINKED FUNCTIONS
===============================================================================

A capability resembles a callable function whose implementation is selected by
the runtime.

The caller knows:

- contract identity
- version
- input shape
- output shape
- stream behavior
- error behavior

The caller does not need to know:

- implementation language
- adapter
- process
- transport
- physical location

This resembles:

- interface dispatch
- virtual methods
- dynamic linking
- dependency injection
- service discovery
- function tables

Actant adds:

- permission mediation
- transactional context
- tracing
- Pack ownership
- Application context
- adapter lifecycle


===============================================================================
12. SERVICES AS RUNTIME OBJECTS
===============================================================================

A service resembles a longer-lived object implementing one or more contracts.

It may hold local implementation state.

It may expose capabilities.

It may be registered and selected dynamically.

A local service may be a Python object reference.

A remote service may be represented by:

- implementation identity
- adapter session
- remote object handle
- interface list
- operation mapping

The service is therefore a platform object whose realization may be local or
remote.


===============================================================================
13. ADAPTERS AS GENERALIZED CALLING CONVENTIONS
===============================================================================

A programming language uses calling conventions and foreign-function
interfaces to cross execution boundaries.

Actant adapters serve a broader role.

They may need to transfer:

- values
- handles
- context
- streams
- errors
- cancellation
- tracing
- lifecycle

A conventional FFI may cross:

    language A
        -> ABI
        -> language B

Actant may cross:

    platform contract
        -> language binding
        -> adapter
        -> canonical invocation model
        -> channel
        -> transport
        -> target runtime

The adapter is therefore part:

- FFI
- marshaller
- proxy provider
- scheduler
- lifecycle manager
- trust boundary
- error translator
- trace producer


===============================================================================
14. BACKEND AS DISTRIBUTED INTERPRETER
===============================================================================

The backend's role resembles an interpreter or runtime kernel.

It may:

- resolve names and contracts
- select implementations
- create operation scopes
- create Memory layers
- schedule participants
- enforce ordering
- dispatch calls
- validate handles
- enforce permission
- manage transactions
- propagate cancellation
- collect results
- persist accepted state
- reconstruct traces

The backend does not execute every instruction directly.

It interprets and orchestrates platform instructions, some of which are executed
by external runtimes.


===============================================================================
15. DISTRIBUTED INPUTS
===============================================================================

An operation's inputs may come from several locations.

Examples:

- caller-provided values
- persistent Memory
- adapter-local state
- service registrations
- capability resolution
- configuration layers
- client input
- stream input
- remote object handles
- prior operation results

These inputs may differ in:

- authority
- lifetime
- serialization
- availability
- mutability
- persistence

The runtime must preserve those distinctions.


===============================================================================
16. DISTRIBUTED OUTPUTS
===============================================================================

One operation may produce several outputs at once.

Example LLM operation:

- token stream to a client
- parsed result to a pipeline
- staged Memory writes
- trace records
- provider-local cache changes
- final metadata
- retained result reference

These outputs have different meanings.

Some may be:

- transient
- user-visible
- tentative
- persistent
- trace-only
- adapter-local
- authoritative
- discardable

The runtime must not collapse them into one generic return value.


===============================================================================
17. EFFECTS
===============================================================================

Programming languages distinguish pure computation from effects.

Actant operations may produce effects such as:

- Memory reads
- Memory writes
- capability calls
- service registration
- stream emission
- trace emission
- client updates
- external I/O
- configuration changes
- Pack activation
- command execution

This suggests that Actant may benefit from explicitly classifying effects.

Possible uses:

- permission checks
- tracing
- scheduling
- retry safety
- parallel-safety declaration
- transaction rules
- debugging

No formal effect system is proposed here.

The analogy only reveals that effect ownership matters.


===============================================================================
18. TYPES AND CONTRACTS
===============================================================================

A language defines what kinds of values and operations are valid.

Actant may need:

- canonical value types
- interface contracts
- capability contracts
- service contracts
- stream item types
- error types
- handle types
- lifecycle types
- result types

This may lead to:

- schemas
- IDL
- generated bindings
- runtime validation
- introspection

The exact mechanism remains open.


===============================================================================
19. LIFETIME
===============================================================================

A language runtime manages object lifetime.

Actant must manage lifetimes across distributed boundaries.

Possible lifetimes include:

- one call
- one participant invocation
- one stage
- one pipeline run
- one operation
- one ApplicationRun
- one adapter session
- one RuntimeHost run
- durable persistent identity

Examples:

    ModCallContext handle
        invocation-scoped

    transaction handle
        operation-scoped

    stream handle
        stream-scoped

    Application identity
        durable

    adapter object handle
        adapter-session-scoped

Lifetime must be explicit because remote references cannot rely on one garbage
collector.


===============================================================================
20. ERRORS AS CROSS-RUNTIME CONTROL FLOW
===============================================================================

Exceptions are a form of control flow inside programming languages.

Across adapters, native exceptions cannot remain native objects.

The platform must represent:

- domain failure
- remote exception
- adapter failure
- transport failure
- cancellation
- timeout
- serialization failure
- invalid handle
- permission rejection

The runtime must decide:

- which layer failed
- which Memory layer rolls back
- whether parent work continues
- whether retry is allowed
- what trace evidence is emitted
- what result is surfaced

This is analogous to exception propagation, but distributed.


===============================================================================
21. CONCURRENCY
===============================================================================

A programming-language runtime defines concurrency semantics.

Actant may execute:

- participants sequentially
- sibling participants in parallel
- multiple pipelines concurrently
- remote streams
- simultaneous clients
- multiple adapters
- asynchronous callbacks
- free-threaded Python code

The runtime must define:

- visibility
- ordering
- conflict
- cancellation
- merge
- trace ordering
- deterministic or nondeterministic behavior

Concurrency is not merely an implementation detail when it changes visible
semantics.


===============================================================================
22. OPERATIONAL-SEMANTICS STYLE DESCRIPTION
===============================================================================

Actant operations may eventually benefit from language-like semantic
descriptions.

An abstract operation could be described as:

    evaluate operation O
    under context C
    against Memory layer M
    using participant graph G

    producing:
        result R
        Memory delta D
        trace evidence T
        terminal outcome X

Then:

    if X is accepted:
        merge D into parent(M)

    otherwise:
        discard D

This is not intended as final notation.

It demonstrates that Actant's design may be reasoned about through operational
semantics.


===============================================================================
23. WHY THE ANALOGY IS USEFUL
===============================================================================

The programming-language lens forces clarity about:

- what values exist
- what operations mean
- who owns state
- when state becomes visible
- how scopes nest
- how failures propagate
- how lifetimes end
- what ordering means
- what effects are allowed
- how implementations are selected
- what is portable across languages

Without this rigor, the system may become a collection of loosely connected
APIs whose interactions are ambiguous.


===============================================================================
24. DANGER: INVENTING A TEXTUAL LANGUAGE
===============================================================================

The analogy does not imply Actant needs new source-code syntax.

Host languages already provide:

- expressions
- functions
- classes
- control flow
- type systems
- tooling
- debuggers
- editors

Actant may be a platform language without being a textual programming language.

Its "language" may consist of:

- contracts
- manifests
- graph declarations
- APIs
- runtime semantics

Creating a new textual syntax could:

- distract from the platform
- duplicate host-language features
- require a parser and compiler
- create major tooling burden
- reduce adoption
- obscure the actual interoperability problem


===============================================================================
25. DANGER: TRYING TO REPLACE HOST LANGUAGES
===============================================================================

Actant should not try to replace Python, JavaScript, Rust, or other implementation
languages.

Those languages remain appropriate for implementing Pack logic.

Actant should define how implementations participate in one platform.

It should not attempt to become a universal implementation language.


===============================================================================
26. DANGER: TRANSPARENT DISTRIBUTED OBJECTS
===============================================================================

The programming-language analogy may tempt the design toward objects that look
fully local while actually being remote.

This can hide:

- latency
- timeout
- disconnect
- partial failure
- cancellation races
- serialization
- object expiry
- retry duplication

Language-native facades are useful.

They should not conceal semantic differences that affect correctness.


===============================================================================
27. DANGER: ONE ABSTRACTION FOR EVERY KIND OF WORK
===============================================================================

A language analogy may encourage one universal operation model.

But different work may naturally require:

- unary call
- stream
- subscription
- pipeline
- graph
- job
- command
- event
- transaction
- long-running coordinator

Forcing all of them into one shape may create an unusable abstraction.

Shared concepts are valuable.

Universal sameness is not automatically valuable.


===============================================================================
28. DANGER: UNIVERSALITY
===============================================================================

Once a system resembles a language runtime, it may seem capable of expressing
everything.

That can lead to:

- excessive scope
- endless abstraction
- delayed implementation
- difficult creator APIs
- speculative features
- insufficient focus on actual use cases

Actant should preserve its central purposes:

- modularity
- orchestration
- persistent authoritative Memory
- language-agnostic participation
- tracing and diagnostics

It does not need to become a general-purpose distributed operating system.


===============================================================================
29. DANGER: FORMALISM WITHOUT VALUE
===============================================================================

Formal semantics can improve clarity.

They can also become an academic exercise disconnected from implementation.

Formalization is useful when it helps answer practical questions such as:

- which layer sees a write
- what commits
- what rolls back
- what happens after cancellation
- whether retry duplicates work
- which participant runs first
- whether a handle is still valid

Formalism should serve design and implementation.


===============================================================================
30. DANGER: HIDING COST
===============================================================================

A platform-level instruction may appear simple:

    llm.stream@1

Its execution may involve:

- graph resolution
- capability selection
- serialization
- RPC
- remote scheduling
- Memory facade calls
- streaming
- tracing
- persistence

The API may remain simple.

The design should not forget the operational cost.

Important costs include:

- latency
- message volume
- serialization
- state synchronization
- tracing overhead
- graph computation
- transaction layers
- retries
- resource cleanup


===============================================================================
31. DANGER: SEMANTIC DETERMINISM ASSUMED FROM MESSAGE DELIVERY
===============================================================================

Sending messages is relatively easy.

Preserving coherent semantics is harder.

Questions include:

- Was the message delivered?
- Was the operation accepted?
- Did the implementation begin?
- Did it finish?
- Did its result arrive?
- Did Memory commit?
- Did the parent later roll back?
- Did late evidence arrive?
- Was a retry a duplicate or a new attempt?

Transport success does not answer these questions.

The runtime must preserve distinctions between delivery, execution, resolution,
and persistence.


===============================================================================
32. DANGER: CENTRAL ORCHESTRATOR AS BOTTLENECK
===============================================================================

Central semantic authority provides coherence.

It may also create:

- performance bottleneck
- availability bottleneck
- excessive message routing
- centralized failure
- scalability limits

Possible future mitigations may include:

- batching
- local execution optimization
- delegated narrow authority
- cached projections
- partitioned services
- specialized data planes
- local sequencing

These should not weaken platform truth accidentally.


===============================================================================
33. DANGER: OVERLY FAT CONTEXT
===============================================================================

If the runtime resembles an interpreter, it may be tempting to send the whole
execution environment to every target.

A huge context may contain:

- Memory
- configuration
- services
- capabilities
- transactions
- tracing
- identities
- permissions
- runtime state

This creates:

- large payloads
- stale state
- duplicated logic
- authority leakage
- versioning problems

The safer model is scoped facades, handles, and small immutable metadata.


===============================================================================
34. DANGER: CONFUSING TRACE WITH EXECUTION TRUTH
===============================================================================

A language runtime may expose execution history.

Actant tracing records evidence.

It should not become:

- committed Memory
- transaction authority
- replay authority by default
- lifecycle truth outside retained evidence

Trace may show tentative work that later rolled back.

The programming-language analogy must not turn trace into a hidden event-sourced
state system unless explicitly designed.


===============================================================================
35. DANGER: CALLING EVERYTHING AN INSTRUCTION
===============================================================================

The word instruction is useful at high altitude.

At lower levels, distinctions remain necessary.

These are not automatically the same:

- command
- capability call
- service method
- pipeline stage
- Pack callback
- Memory mutation
- trace event
- transport message
- stream item
- job transition

They may participate in one abstract machine while retaining distinct semantics.


===============================================================================
36. PRACTICAL INTERPRETATION
===============================================================================

A practical reading of the abstraction is:

Actant defines a platform-level execution model.

Host languages implement logic.

Adapters connect host runtimes.

Backend internals orchestrate platform truth.

Memory provides layered state.

Packs provide modular behavior.

Capabilities and services provide callable contracts.

Pipelines and operations provide control flow.

Tracing provides evidence.

This is enough for the language-runtime analogy to be useful.

It does not require Actant to become a conventional programming language.


===============================================================================
37. POSSIBLE TERMINOLOGY OPTIONS
===============================================================================

Possible internal descriptive phrases include:

- distributed abstract machine
- modular distributed runtime
- transactional orchestration runtime
- platform language
- meta-runtime
- language-agnostic execution platform
- centrally orchestrated distributed runtime

Each phrase highlights something different.

No terminology is selected here.

The terms may remain internal reasoning tools rather than documentation labels.


===============================================================================
38. WORKING PRINCIPLES
===============================================================================

1. Actant may be reasoned about as an abstract machine.

2. Platform contracts function like semantic instructions.

3. Physical execution may be distributed across languages and runtimes.

4. Backend internals remain the semantic orchestrator.

5. Packs resemble modules and implementations, not arbitrary code injection.

6. Capabilities resemble dynamically resolved callable contracts.

7. Services resemble runtime objects with implementation identity.

8. Memory layers resemble transactional scopes.

9. Pipelines resemble modular control flow.

10. Adapters resemble generalized FFIs and calling conventions.

11. Distributed inputs and outputs retain distinct authority and lifetime.

12. The analogy should improve semantic rigor.

13. The analogy does not imply a new textual language.

14. Actant should not replace host languages.

15. Remote operations must not be made falsely transparent.

16. Different orchestration forms should retain their natural semantics.

17. Formalization should serve practical design.

18. Actant should resist becoming universally general.

19. Trace remains evidence, not state authority.

20. The abstraction is a lens, not a commitment.


===============================================================================
39. REHYDRATION STARTING POINT
===============================================================================

When continuing from this abstraction:

1. Use the language-runtime analogy to ask precise semantic questions.

2. Return to concrete Actant concepts before selecting implementation.

3. Keep values, references, scopes, effects, lifetime, and errors explicit.

4. Preserve distributed failure and latency in creator-facing contracts where
   correctness requires it.

5. Do not create syntax merely because the platform resembles a language.

6. Do not collapse commands, calls, streams, pipelines, and messages into one
   undifferentiated instruction type.

7. Keep backend authority and distributed execution distinct.

8. Evaluate every abstraction against actual Memory, orchestration, modularity,
   tracing, host, client, and adapter needs.

9. Prefer a smaller coherent platform over an unlimited universal runtime.

10. Treat this document as a high-level viewpoint, not a final architecture.
