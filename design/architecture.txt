===============================================================================
ACTANT DESIGN - ARCHITECTURAL COMPONENTS AND RESPONSIBILITIES
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Maps Actant's major conceptual components and responsibility boundaries.

Purpose:
--------
Provides a concise architecture map for assistants and contributors.
Subsystem documents own exact behavior, interfaces, and protocols.

It does NOT prescribe implementation topology or internal data structures.


===============================================================================
01. ARCHITECTURAL VIEW
===============================================================================

01.01. Actant is a platform of contract-governed responsibilities, not
       a prescribed set of processes, objects, or implementation languages.
01.02. A Host operates multiple Applications and manages shared runtime
       facilities while preserving Application-specific identities.
01.03. Packs supply modular Applications, CodeEntries, content, and tests.
       Adapters execute CodeEntries in appropriate language environments.
01.04. The conceptual layers in this document are responsibility
       boundaries, not mandatory modules or execution order.


===============================================================================
02. HOST, APPLICATIONS, AND SHARED FACILITIES
===============================================================================

02.01. The Host is the execution environment for Application runtimes,
       shared services, lifecycle coordination, and resource boundaries.
02.02. Applications may run concurrently, with independent lifetimes,
       purposes, and work even when they use common managed services.
02.03. Shared capabilities, including model servers, are managed with
       explicit ownership and resource authority, not duplicated solely
       because separate Applications request them.
02.04. Jobs may have lifetimes independent of listeners and individual
       communication relationships. Do not equate all Job completion
       with completion of a request-response exchange.
02.05. Suspension of an Application or resource is not automatically
       Flow Quiescence, Unexpected Unavailability, or Termination.


===============================================================================
03. PACKS, CODEENTRIES, AND ADAPTERS
===============================================================================

03.01. A Pack is a deployable container of executable and other content.
03.02. CodeEntries are executable units loaded through adapters.
       Adapter choice reflects an execution language or environment.
03.03. The same programming language on both sides of a boundary does
       not grant Pack code platform-internal authority.
03.04. Adapters and language-specific interfaces preserve the platform
       contracts despite different native runtime facilities.
03.05. Python is the current implementation focus. JavaScript/TypeScript
       browser sandbox and C# execution are intended future directions.


===============================================================================
04. DOMAIN, FLOW, AND ACTANT RESPONSIBILITIES
===============================================================================

04.01. Domains own their intentions, independently executing Jobs,
       externally meaningful effects, and the meaning of success.
04.02. Flow owns orchestration knowledge: relationships, Messages,
       communications, attempts, acknowledgements, Results, contracts,
       progression, and outstanding contractual obligations.
04.03. Actant provides execution and lifecycle support, persistence,
       Transport and routing facilities, recovery, and resource authority.
04.04. Flow coordinates Invocations, Subscriptions, and Emits without
       becoming a universal domain workflow or purpose interpreter.
04.05. Transport is a replaceable communication realization; Transport
       receipt alone is not durable Flow admission or domain success.
04.06. A callback outcome is not automatically proof of domain-purpose
       success or of authoritative MemoryValue commitment.
04.07. A caller-visible Flow error does not end Actant's obligations
       to reconcile, recover, or safely clean up outstanding work.


===============================================================================
05. MEMORY, DURABILITY, AND RECOVERY
===============================================================================

05.01. MemoryValueSystem holds semantic values, revisions, references,
       staged changes, and authoritative commitment under its contracts.
05.02. Runtime-held information and committed persistent values are
       distinct. Durable evidence is relative to the stated recovery
       boundary, not automatically every piece of runtime state.
05.03. For applicable potentially effectful actions, record sufficient
       intent or admission before the effect boundary, and record the
       observed outcome afterward as the relevant contract requires.
05.04. On recovery, restore the last durably known semantic state first;
       reconcile it with the participants and external reality afterward.
05.05. An uncertain callback completion is not permission to execute
       the same callback again. A distinct new Job needs its own authority.
05.06. Missing history or NotFound is scoped evidence, not universal
       proof of non-execution. Retention meets contractual obligations.
05.07. Persistence degradation is a reportable condition. A Result can
       be available without having the promised durability; delivery
       and failure reporting are governed by the actual contract.


===============================================================================
06. COMMUNICATION AND CONTINUITY
===============================================================================

06.01. Logical relationship identity and operation identity persist
       across runtime and Transport changes where contracts require.
06.02. Acknowledgement of request admission, execution observation,
       domain confirmation, and authoritative commit are different facts.
06.03. Contracts define which acknowledgement or confirmation settles
       a particular obligation. Stronger confirmation is not universal.
06.04. Quiescence, Unexpected Unavailability, and Termination have
       different meanings. Absence alone does not terminate a relation.
06.05. Multiple subscribers or listeners can have distinct obligations;
       one recipient's absence need not stop unrelated domain work.
06.06. Retry of a logical Message is not automatically permission to
       repeat potentially effectful domain execution.
06.07. Exact retention, retry policy, timing, scheduling, and resource
       arbitration are owned by applicable design contracts.


===============================================================================
07. TRACING AND VERIFICATION
===============================================================================

07.01. Tracing emits structured evidence of runtime activity, identities,
       ordering, and recorded relationships for later interpretation.
07.02. Trace evidence is distinct from authoritative committed state.
       Consumers must not present inference as observed evidence.
07.03. Domain owners identify which meaningful actions require tracing.
       Trace coverage is not a command to record every implementation step.
07.04. Architectural Tests verify guarantees and interruption boundaries.
       Implementation and optimization must preserve their meaning.
