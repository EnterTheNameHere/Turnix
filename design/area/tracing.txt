===============================================================================
DESIGN AREA DA-03 - TRACING
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the implementation-independent Actant tracing substrate and its
runtime evidence-production, context, span, publication, and failure
semantics.

Purpose:
--------
This document defines what tracing is inside Actant and which guarantees the
tracing substrate provides while runtime work is occurring.

It defines:
- tracing as structured runtime evidence rather than logging
- trace producers and producer-local ordering
- trace context and correlation propagation
- trace span lifecycle semantics
- trace type registration and publication
- trace destinations and delivery isolation
- trace emission and persistence boundaries
- tracing authority and non-authority
- ownership boundaries between tracing, trace records, and trace tooling

Detailed portable trace-record semantics are defined in tracing-records.txt.
Trace reconstruction, full DAG materialization, storage inspection, and
interactive tooling are defined in tracing-tooling.txt.

This document is implementation-language neutral. Language-specific runtime
mechanics belong to implementation specifications.


===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning derives from sentence structure and document context
      rather than from RFC-style keywords.

01.03. This document migrates and supersedes the tracing-substrate meaning of
      the legacy DA-03 specification for the new design corpus.

01.04. Legacy DA-03 remains reference material during migration. It does not
      force the new design to preserve obsolete representation or tooling
      assumptions.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. Tracing records structured evidence about runtime activity.

02.02. Tracing answers, within the evidence that was emitted:

          "What happened, what was it related to, and why?"

02.03. Tracing is not logging.

02.04. Human-readable logs may be derived from, accompany, or exist beside
      trace evidence. Logs do not replace trace evidence.

02.05. The tracing substrate produces records and explicit relationships.

02.06. The tracing substrate does not require a complete trace graph to exist
      while records are being emitted.

02.07. Full causal and structural graphs are materialized by trace tooling
      from available trace evidence.

02.08. The architectural separation is:

          Tracing records relationships.
          Tooling materializes relationships.


===============================================================================
03. AUTHORITY AND EVIDENCE
===============================================================================

03.01. Trace evidence is evidence of what an Actant subsystem recorded.

03.02. Trace evidence is not authoritative committed state.

03.03. Trace evidence does not by itself define restoration, rollback,
      Replay, Resume, Retry, or object-lifecycle truth outside the evidence
      represented by the records being examined.

03.04. Explicit relationships recorded by a producer are authoritative as
      statements made by that producer within the available trace evidence.

03.05. A trace consumer does not invent an unrecorded event, relationship,
      reason, or outcome.

03.06. Absence of evidence does not prove absence of the underlying runtime
      action when evidence may be unavailable, undelivered, unretained, or
      incomplete.

03.07. Loss of trace evidence weakens evidential completeness. It does not by
      itself change committed-state correctness.

03.08. Trace presentation, reconstruction, storage, export, or debugger
      tooling does not acquire runtime authority merely by consuming trace
      evidence.


===============================================================================
04. DOMAIN TRACE OBLIGATIONS
===============================================================================

04.01. The tracing substrate defines how trace evidence is produced and
      transported.

04.02. The design area that owns a lifecycle, operation, object, workflow, or
      subsystem defines which meaningful actions require trace evidence.

04.03. A domain-required trace emission is not optional merely because trace
      retention is non-authoritative or best-effort.

04.04. An emission obligation requires the owning runtime path to attempt
      trace emission at the defined point.

04.05. An emission obligation is distinct from a persistence guarantee.

04.06. Domain-specific trace types, attributes, correlations, and causal
      references remain owned by the domain that gives them meaning unless a
      tracing document explicitly defines a substrate-level type.

04.07. The tracing substrate does not maintain a global catalog of every
      domain action that must be traced.


===============================================================================
05. TRACE PRODUCERS
===============================================================================

05.01. Trace records are emitted by trace producers.

05.02. Each trace producer has a stable identity for its producer lifetime.

05.03. Each record emitted by a producer carries that producer identity.

05.04. Each producer assigns a producer-local sequence to emitted records.

05.05. Producer-local sequence values are unique and strictly ordered for
      records successfully created by that producer.

05.06. Producer-local sequence does not define ordering between different
      producers.

05.07. A replacement or restarted producer receives a distinct producer
      identity.

05.08. A new producer does not continue another producer's local sequence as
      though both producers were one uninterrupted producer.

05.09. A producer may record descriptive predecessor information when the
      surrounding runtime knows that relationship.

05.10. Predecessor information does not merge producer identities or convert
      separate producer-local sequences into one sequence.


===============================================================================
06. TRACE CONTEXT AND CORRELATION
===============================================================================

06.01. Tracing supports ambient trace context so nested runtime work can
      inherit structural and correlation information without restating it at
      every emission point.

06.02. Trace context may contain:
      - current span identity
      - current span-start record identity
      - current span family
      - producer identity associated with structural span context
      - runtime correlation identifiers

06.03. Correlation identifiers associate trace evidence with known Actant
      runtime identities.

06.04. Correlation identifiers do not create ownership or authority over the
      correlated objects.

06.05. Correlation context may be inherited, explicitly overridden, or
      explicitly cleared by a nested runtime scope.

06.06. A nested correlation scope restores the preceding context when the
      scope ends.

06.07. Structural span context is producer-specific.

06.08. A producer does not structurally contain a new record or child span
      inside span context owned by a different producer.

06.09. An implementation may transfer structural span context across an
      execution boundary when the boundary preserves the context's identity
      and the tracing contract.

06.10. Transfer of structural context does not transfer ownership of the
       active span lifecycle unless an owning design explicitly defines such
       transfer.


===============================================================================
07. TRACE SPANS
===============================================================================

07.01. A trace span represents bounded work.

07.02. A normally completed span has one start record and one terminal record.

07.03. The start record establishes the span identity and span family.

07.04. A child span explicitly identifies its parent span.

07.05. A terminal span record identifies the corresponding span and its start
      record.

07.06. A terminal span record records an outcome.

07.07. A terminal span record may record duration when duration is available.

07.08. Span outcomes distinguish semantically different terminal conditions.

07.09. The standard tracing substrate recognizes normal completion, failure,
      error, and cancellation as distinct terminal outcome categories.

07.10. A span family may define additional generated terminal outcome types
       while preserving the span's common lifecycle semantics.

07.11. Span lifecycle ownership remains explicit.

07.12. Structural span context may be used by nested work without granting
       that work permission to terminate the active span.

07.13. Shutdown or recovery may encounter a span for which normal terminal
       evidence can no longer be emitted safely.

07.14. Such a span may be abandoned by the tracing producer.

07.15. Abandonment is represented explicitly when tracing can still emit the
       corresponding evidence.

07.16. Tracing does not fabricate a successful terminal span record merely to
       make an incomplete lifecycle appear complete.


===============================================================================
08. TRACE TYPES
===============================================================================

08.01. Every ordinary trace record refers to a registered trace type
      definition.

08.02. A trace type definition gives portable semantic identity to the kind
      of evidence represented by a record.

08.03. Trace type definitions distinguish event definitions from span-family
      definitions.

08.04. A span-family definition describes its start type and terminal outcome
      types.

08.05. Trace type definitions may describe generated types used for span
      start and outcome records.

08.06. Trace type definition identity is derived from the definition's
      canonical semantic content.

08.07. Equivalent canonical definitions have equivalent definition identity.

08.08. Changing semantic definition content produces a different definition
      identity.

08.09. Concrete canonicalization and digest algorithms are implementation or
      interoperability specification concerns unless promoted into a shared
      cross-language wire contract.

08.10. A producer does not emit an ordinary record that refers to an
       unregistered trace type definition.


===============================================================================
09. PUBLICATION AND DESTINATIONS
===============================================================================

09.01. A trace producer publishes trace definitions and records to one or
      more trace destinations.

09.02. A trace destination is a consumer boundary for live trace evidence.

09.03. A destination may display, persist, forward, inspect, analyze, or
      intentionally discard trace evidence.

09.04. Intentional discard is explicit through a destination whose defined
      behavior is to discard evidence.

09.05. A producer does not silently behave as though trace publication exists
      when no destination is configured.

09.06. Before a destination receives a record referring to a trace type
      definition, that destination receives the corresponding definition.

09.07. Repeated delivery of an equivalent definition to a destination is
      semantically idempotent.

09.08. A newly attached destination receives definitions required to
      interpret records subsequently delivered to it.

09.09. Failure of one destination does not prevent publication attempts to
      independent destinations.

09.10. Destination failure does not acquire authority to change the runtime
       operation that produced the trace evidence.

09.11. Failed definition delivery may be retried before a later dependent
       record is delivered to that destination.

09.12. Tracing records destination failure and recovery when ordinary tracing
       remains capable of doing so.

09.13. Failure reporting that cannot safely use ordinary tracing uses an
       implementation-defined emergency reporting path.

09.14. Emergency reporting is not a replacement trace destination and does
       not pretend that failed ordinary publication succeeded.


===============================================================================
10. RECURSION AND RE-ENTRANCY
===============================================================================

10.01. Destination publication does not recursively create ordinary tracing
       through the same producer publication path.

10.02. A destination does not consume producer sequence values by recursively
       invoking ordinary tracing during publication.

10.03. A destination does not mutate producer lifecycle state through a
       re-entrant publication callback when that mutation would violate the
       active publication boundary.

10.04. Recursion protection is a tracing contract. The concrete mechanism is
       implementation-specific.


===============================================================================
11. PRODUCER LIFECYCLE
===============================================================================

11.01. A trace producer has an explicit lifecycle.

11.02. Producer startup may emit evidence that the producer is ready.

11.03. Producer shutdown prevents new ordinary work from entering tracing
       lifecycle paths once shutdown has taken ownership of termination.

11.04. Shutdown handles active spans according to the tracing lifecycle
       contract rather than silently forgetting them.

11.05. Producer stopping and stopped states may themselves be trace-visible.

11.06. Producer shutdown remains safe when destinations fail.

11.07. Trace destination failure does not prevent the producer from completing
       its own lifecycle.


===============================================================================
12. EMISSION, DELIVERY, AND RETENTION
===============================================================================

12.01. Trace emission, destination delivery, and historical retention are
      distinct operations.

12.02. The tracing substrate owns trace creation and delivery attempts.

12.03. A destination owns what it does with successfully delivered evidence
      within the destination's contract.

12.04. Persistent trace storage is a destination/tooling concern unless a
      later design assigns a stronger storage contract to a specific runtime
      component.

12.05. Failure to deliver trace evidence to one destination does not by itself
      change committed-state correctness.

12.06. Tracing does not silently claim successful delivery when delivery
      failed.

12.07. Historical pruning, rotation, retention windows, continuity anchors,
      and persisted-history completeness are not runtime trace-producer
      responsibilities.

12.08. Those historical concerns are defined by tracing-tooling.txt and by
      the persistent destination that stores the evidence.


===============================================================================
13. DIAGNOSTIC AND ERROR CORRELATION
===============================================================================

13.01. Trace evidence supports diagnosis and creator feedback.

13.02. Surfaced Actant failures remain linkable to trace correlation evidence
      when the failing operation has such evidence available.

13.03. A surfaced failure does not fabricate trace evidence when correlation
      is unavailable.

13.04. User-facing diagnostics may simplify trace presentation while
      preserving the distinction between recorded evidence and interpretation.

13.05. Diagnostic presentation does not become runtime authority.

13.06. Concrete error-envelope schemas belong to the interface or protocol
      that owns those envelopes.


===============================================================================
14. NO HEURISTIC TRACE FABRICATION
===============================================================================

14.01. Tracing does not infer causal relationships from timestamps.

14.02. Tracing does not fabricate reasons or outcomes that were not recorded.

14.03. Tracing does not silently suppress evidence required by a domain trace
      obligation.

14.04. Trace enrichment does not convert inferred information into producer-
      asserted trace evidence.

14.05. Development-only enrichment remains explicit and non-authoritative.


===============================================================================
15. OWNERSHIP STOP-LINES
===============================================================================

15.01. tracing.txt owns runtime tracing-substrate semantics.

15.02. tracing-records.txt owns the portable structure and invariants of trace
      records, references, identities, type definitions, and exception
      evidence.

15.03. tracing-tooling.txt owns reconstruction of complete available evidence
      sets into graphs, storage inspection, retained-evidence completeness,
      navigation, visualization, and trace/debugger consumption boundaries.

15.04. Domain design documents own their domain-specific emission obligations
      and semantic trace types.

15.05. Implementation specifications own language/runtime mechanisms used to
      realize this design.

15.06. No implementation language, concurrency primitive, exception class,
      context-propagation primitive, collection type, or source-code API name
      is part of this design merely because the current implementation uses it.


===============================================================================
16. LOCKED MIGRATION DECISIONS
===============================================================================

16.01. LOCKED:
      - tracing is structured evidence rather than logging
      - tracing is part of platform accountability
      - trace evidence is not authoritative committed state
      - domain trace emission obligations remain domain-owned
      - emission obligation and persistence guarantee are distinct
      - temporal order does not define causality
      - explicit recorded relationships define trace relationship evidence
      - trace spans represent bounded work with explicit lifecycle evidence
      - trace producer identity and producer-local sequence are explicit
      - trace context and runtime correlation are explicit
      - trace type definitions are delivered before dependent records
      - destination failures are isolated from independent destinations
      - recursive destination publication does not recursively trace
      - known publication failure is not represented as success
      - tooling and diagnostic presentation do not create runtime authority
      - tracing records relationships; tooling materializes relationships

16.02. The legacy rule that the runtime tracing substrate itself is a
      materialized trace DAG is superseded.

16.03. The legacy generic reason field is superseded by typed trace evidence,
      generated outcomes, structured attributes, and explicit references.

16.04. The legacy generic parentEventIds representation is superseded by the
      structural span fields and explicit typed references defined in
      tracing-records.txt.
