===============================================================================
ACTANT DESIGN AREA - MEMORY VALUE SYSTEM
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the semantic-memory authority, revision, and commitment model.

Purpose:
--------
Explains persistent semantic values, reference and transaction boundaries,
authority, recovery, and separation from Flow and physical storage.

It does NOT prescribe implementation algorithms or storage layouts.


===============================================================================
01. SEMANTIC MEMORY
===============================================================================

01.01. MemoryValueSystem manages language-independent semantic values
       and their authoritative evolution, not merely storage locations.
01.02. MemoryValue identifies a logical value. MemoryValueRevision
       represents a particular revision of its semantic content.
01.03. Revision existence and authority are distinct. One authority
       scope resolves one current authoritative revision per value.
01.04. Multiple physical copies do not create multiple authorities.
01.05. Runtime availability, semantic visibility, persistence, and
       authoritative commitment are different properties.


===============================================================================
02. VALUES, REFERENCES, AND STORAGE
===============================================================================

02.01. ValueRef describes reconstruction of a concrete semantic value;
       it does not independently confer authority over that value.
02.02. ValueRef may contain inline material or depend on immutable
       stored material. Material can be shared where semantically safe.
02.03. Chunk is an optional immutable storage-material abstraction;
       it is not a required representation for every value.
02.04. MemoryStorage and IoManager have distinct responsibilities;
       IoManager is the managed I/O gateway.
02.05. Storage realization, material placement, and deduplication
       strategies do not redefine semantic identity or authority.


===============================================================================
03. DEFINITIONS, TYPES, AND RESOLUTION
===============================================================================

03.01. MemoryValueDefinition supplies value declaration information.
       MemoryValueContract is its fully resolved semantic contract.
03.02. Contract defaults are resolved deterministically from the
       applicable versioned declaration and default sources.
03.03. TypeExpression identifies semantic type structure or references
       a named TypeDefinition. Named types are nominal by default.
03.04. Type meaning and additional constraints remain distinct.
       Usage constraints may narrow, not widen, a type's valid domain.
03.05. Absence, Missing, explicit null, and Error are distinct states.
       A concrete null does not mean the value was absent.
03.06. Optional and nullable types express different semantics;
       their combination must not silently collapse those meanings.
03.07. Defaults apply only when the relevant concrete state is absent,
       not merely because a present value is null or invalid.


===============================================================================
04. TRANSACTIONS AND AUTHORITY
===============================================================================

04.01. Transactions stage changes in hierarchical overlays before
       their authoritative commitment.
04.02. Staged values, current runtime values, and committed values
       are distinct; SaveBundle persists committed values only.
04.03. An authoritative commit must not be advertised before the
       durability required by its contract has been established.
04.04. A conflict must not silently become last-writer-wins.
       Unrelated state should remain independently committable.
04.05. Concurrency, nested transactions, snapshots, and fine-grained
       conflict resolution require their owning detailed design.
04.06. Transaction rejection, abort, retry, and quarantine must not
       be confused with a successful authoritative overwrite.
04.07. Restoration uses the latest trustworthy committed semantic
       authority rather than arbitrary physical material found on disk.


===============================================================================
05. RETENTION AND RECOVERY
===============================================================================

05.01. Semantic removal and physical material collection are separate.
       Removing a value does not require immediate removal of all bytes.
05.02. Material left by interrupted publication may be orphaned.
       Orphans are not retroactively promoted into authoritative values.
05.03. Retention and collection preserve surviving references,
       contractual obligations, and required recovery evidence.
05.04. Known loss of a durability guarantee must be visible to relevant
       consumers without falsely presenting volatile state as durable.
05.05. An available Result may remain usable under a weaker guarantee
       even when promised retention failed, if its contract permits.
05.06. Restoring storage availability cannot retroactively prove
       an earlier value was durably committed.


===============================================================================
06. BOUNDARIES WITH FLOW AND OTHER DOMAINS
===============================================================================

06.01. MemoryValueSystem owns semantic value and commitment authority;
       Flow owns orchestration evidence and contractual progression.
06.02. Related recovery needs do not imply one mandatory shared ledger,
       transaction root, or universal co-commit across both systems.
06.03. Flow confirmation, callback return, and MemoryValue commit are
       different facts; a contract may require more than one.
06.04. Language adapters and Pack code access memory through applicable
       interfaces and authority boundaries, not direct implementation
       privilege from sharing a programming language.
06.05. Tracing can describe value operations but is not itself the
       source of committed MemoryValue authority.
