SUBJECT
Mediated process/tool execution required by Materialization Test

CONTEXT
The Materialization Test must run ty and Ruff against generated Python source.
The user needs explicit executable-path configuration so the test can use the
same analyzer executable as their standard Windows 11 VS Code installation.

Current CodeEntryContext mediates I/O, memory, capabilities and LLM operations,
but exposes no process execution boundary. We do not want an application Pack
to gain arbitrary subprocess authority merely because this test needs static
analysis.

The existing first-party llama.cpp driver currently uses subprocess directly to
manage llama-server, giving us a second real consumer of a generic facility.

REQUIRED MATERIALIZATION SEMANTICS
For each analyzer invocation we need enough structured result/evidence to retain:

- tool identity
- configured executable
- resolved executable
- arguments
- working directory
- exact target artifact
- start/end or duration
- exit code
- stdout
- stderr

A nonzero analyzer result containing findings is normal experimental input. A
failure to resolve/start/execute the configured executable is an application or
infrastructure failure and must be distinguishable from analyzer findings.

QUESTION
Please determine the smallest correct generic Actant-owned process/tool
execution contract for the current architecture. In particular, decide how a
CodeEntry receives invocation authority, how executable/path/environment and
working-directory handling should work, what result/error contract is returned,
and what evidence belongs to Actant versus the calling Pack.

Please pressure the current architecture rather than adding compatibility
layers. If the generic facility belongs in shared Actant, implement it on the
integration branch if appropriate and reply with the resulting contract/files
and any migration implications for this branch.

BLOCKING
Yes for proper ty/Ruff execution. Materialization-side prompt/workflow scaffolding
can proceed independently while this is resolved.
