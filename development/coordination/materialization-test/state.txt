=======================================

PURPOSE
This file is the consolidated current synchronization state for the
Materialization Test application work. Numbered files under messages/ preserve
cross-thread correspondence and rationale. Update this file when consolidated
truth changes; do not use it as an append-only conversation log.

CURRENT GOAL
Build the second independent Actant application consumer: an unattended local
LLM materialization benchmark. The first finish line is configure -> run ->
materialize -> static-analyzer/fix loop -> self-audit/fix -> questionnaire ->
export sufficient evidence for scoring.

TEST STRATEGIES
Two strategies must use the same test definition and source prompt material:

1. Classic reproduces the existing manual LM-Studio-like accumulating
   conversation as closely as practical, including the historical questionnaire
   as one 100+ question request.
2. Actant-native reconstructs each inference from authoritative state and only
   relevant QueryItems. Its questionnaire asks questions individually against
   the same final frozen materialization and requirements.

V1 PROMPT DATA
Keep prompt representation deliberately simple. JSON file(s) initially contain:

- grounding instructions
- initial mazerialization test instructions
- static analysis report template
- search for bugs and fix instructions
- questionnaire content

Do not invent a prompt-component language before requirements demand it.

CURRENT MATERIALIZATION
The first application scaffold now exists under:

  first-party/applications/materializationTest/

It contains an AppPack manifest, manual activation plan, config.json,
prompts.json, CLI runner, and materializationTest.workflow Pack.

The workflow currently supports inspection through materializationTest.describe@1
and the first Actant-native phase through materializationTest.run@1. The initial
phase constructs grounding + initial-materialization QueryItems, renders an exact
text/plain query, executes it through ctx.llm.runProcessing(), and commits the
exact initial response plus ProcessingRun identity into application memory.

Classic strategy is represented in configuration but intentionally not yet
implemented. The analyzer/fix, self-audit, questionnaire, source extraction and
export phases remain to materialize. Do not treat the current initial response
as a validated Python source artifact yet; source extraction/acceptance semantics
still need to be defined from the real manual-test response shape.

STATIC ANALYSIS REQUIREMENT
The application must run ty and Ruff against the exact generated source
artifact. Analyzer application config currently contains logical toolId plus argv
templates only; executable authority is intentionally absent pending shared
Actant process-tool integration.

Analyzer evidence should preserve at least tool identity, configured and
resolved executable, arguments, working directory, target artifact, timing,
exit code, stdout, and stderr. Analyzer findings are expected test input and
must be distinguished from failure to launch/execute the analyzer.

SHARED PROCESS CONTRACT
Integration accepted message 0001 in message 0002. V1 will expose mediated
completed-tool execution through fresh CodeEntryContext. CodeEntry invokes a
logical toolId and supplies argv/cwd; executable binding belongs to Actant/runtime
configuration outside ordinary CodeEntry authority. shell=True and arbitrary
environment mutation are outside v1. A completed process returns structured
execution evidence even for nonzero exit status; lookup/resolution/start failures
are typed Actant infrastructure errors. Actant owns generic process evidence;
the Materialization Test owns analyzer/artifact meaning.

Integration implementation is still pending. Do not add a temporary subprocess
wrapper here. Synchronize the resulting shared implementation from
actant-integration when integration reports it ready.

CURRENT PIPELINE FIT
The current QueryItem and LlmProcessingPipeline shape is sufficient for the
prompt-side first implementation. LlmProcessingPipeline records exact query and
response evidence transactionally. ApplicationRuntime.runJob plus child
ProcessingRuns provides a usable outer/inner transaction spine for v1.

CHECKPOINTS
Automatic restart/checkpointing is desired later but is not a v1 requirement.
Keep workflow phase/progression explicit enough that checkpoints can be added
without redesigning the application. Future UI may expose richer checkpoint
selection/branching; do not build UI abstractions now.
