REAL BENCHMARK DATA
The benchmark is the EventJournal Python 3.15 materialization task.

prompts.json now contains:
- groundingReference: reusable authoritative reference material;
- groundingResponseInstruction: standalone Classic first-turn instruction;
- initialMaterialization;
- staticAnalysisReport;
- searchForBugsAndFix;
- questionnaireInstructions.

The 117 questionnaire requirements exist only as explicit semantic data files:

  first-party/applications/materializationTest/questionnaire/01.json
  ...
  first-party/applications/materializationTest/questionnaire/13.json

Each file contains sectionId, title, and an explicit ordered requirements array.
Workflow codeEntry.py loads the fixed 13 files through questionnaireDirectory and
validates section identity, explicit per-section numbering, uniqueness, and the
expected 117 total. No prose/newline parser derives question boundaries.

CURRENT ACTANT-NATIVE IMPLEMENTATION
Workflow codeEntry.py version 9 implements:
1. Initial materialization.
2. Ruff + ty analysis of exact extracted source.
3. Repair loop, maximum five source-producing calls total.
4. Self-audit only after analyzer-clean initial materialization.
5. Independent Ruff + ty repair loop, maximum five source-producing calls.
6. Questionnaire regardless of source/materialization outcome when LLM remains
   callable.

Native projections use groundingReference only; the Classic-only grounding turn
instruction is no longer mixed into implementation, repair, audit, or
questionnaire inference. Repair/self-audit retain original initialMaterialization
requirements. Current source appears exactly once in a repair prompt; analyzer
reports do not duplicate it. Native questionnaire sees grounding reference,
original requirements, frozen source/failure state, common questionnaire
instructions, and exactly one requirement.

SOURCE RESPONSE / ANALYZER SEMANTICS
Every source-producing prompt requires exactly one non-empty fenced Python block
and requests no surrounding text. Extraction remains deliberately tolerant of
ordinary prose outside one otherwise-valid Python fence so protocol noncompliance
can remain raw scoring evidence without corrupting exact source extraction.

Extraction occurs only after streaming completes. No heuristic block choice,
fence repair, dedent, or newline normalization occurs. Generated Python is not
executed/imported as benchmark validation.

The application materializes exact candidate source through ctx.workspace and
runs configured Ruff and ty through ctx.process.run(). Both analyzers consume the
same scratch artifact. Nonzero exit is model/code evidence; process execution
failure is infrastructure/application evidence.

QUESTIONNAIRE SEMANTICS
Questionnaire is attempted even after materialization/self-audit model-output or
analyzer-infrastructure failure when the LLM remains callable. If no valid source
exists, Native supplies explicit failure state rather than inventing a file.
Only LlmError is classified as questionnaire inference failure; programming or
application exceptions propagate.

LATEST LEGITIMATE SOURCE
A later extraction failure retains the previous valid source. If a new valid
source is extracted but analyzer execution fails, that newly extracted source is
the latest legitimate artifact even though analyzer cleanliness is unknown.
Questionnaire uses that latest legitimate artifact.

EXPORT / PUBLICATION
Exporter is a separate Job after the benchmark Job has accepted authoritative
state and the CLI has saved it. Export failure therefore does not invalidate an
already accepted benchmark run.

materializationTest.export@1 emits:
  <outputDirectory>/<applicationId>/<applicationRunId>/evidence.json

Exporter version 2 preserves the benchmark definition as source documents:
- testDefinition.prompts is the exact prompts.json object;
- testDefinition.questionnaire.sections is the exact ordered list of 01.json
  through 13.json objects.

Evidence format remains materialization-test.evidence@1 and contains application
identity, exact test definition/configuration, authoritative workflow state, and
all referenced shared ProcessingRun snapshots. Exact model-facing prompts are
dereferenced from ProcessingRun evidence rather than reconstructed.

run.py saves accepted authoritative state before raising a Job error, preserving
the Actant rule that authoritative state may have been accepted even when the
owning Job later fails.

SHARED ACTANT CONTRACTS
Shared process and ephemeral-workspace facilities are synchronized from
actant-integration and Python-3.15 verified by the user:
- ctx.process.run(...)
- ctx.workspace.materializeText(...)
- ctx.workspace.materializeBytes(...)

Process executable authority belongs to host/runtime processTools configuration.
Configured executables are absolute paths in v1. Pack code supplies logical tool
name and arguments, not arbitrary executable/environment authority.

Shared LLM provider timing is also synchronized. Provider timing covers provider
stream creation through complete stream consumption and terminal completion
validation. ProcessingRun persists providerTiming and completion payload exposes
llm.timing. Materialization does not create a competing inference timer.
