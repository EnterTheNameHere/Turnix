CURRENT MATERIALIZATION
The application scaffold exists under:

  first-party/applications/materializationTest/

It contains an AppPack manifest, manual activation plan, config.json,
prompts.json, CLI runner, and materializationTest.workflow Pack.

Actant-native initial materialization plus the first static-analysis repair loop
are now materialized. materializationTest.run@1:
- constructs grounding + initial instruction + source-output protocol QueryItems;
- executes through ctx.llm.runProcessing() and retains complete raw responses;
- strictly extracts one Python fenced source candidate;
- materializes the exact source through invocation-private ctx.workspace;
- invokes configured Ruff and ty logical tools through ctx.process against the
  same ephemeral candidate path;
- treats nonzero analyzer exits as ordinary model/code findings;
- records generic process evidence, exact source, UTF-8 size/SHA-256 identity,
  extraction evidence, raw response, and ProcessingRun identity per attempt;
- reconstructs repair inference from grounding + current source + current
  analyzer diagnostics + historical static-analysis correction text + fixed
  source-output protocol;
- repeats until both analyzers exit zero or the five-call budget is exhausted;
- classifies extraction-failed, analyzer-limit-reached,
  analyzer-execution-failed, or clean distinctly.

The ephemeral workspace artifact is not durable evidence; exact source and its
identity are stored in application state. ProcessExecutionError is treated as
infrastructure/application failure evidence rather than analyzer findings.

Classic strategy is represented in configuration but intentionally not yet
implemented. Self-audit, questionnaire and export remain to materialize.

SOURCE RESPONSE PROTOCOL
Every source-producing inference, including initial materialization, every
analyzer repair, and self-audit, is instructed to return the complete file in
exactly one fenced Python code block using ```python.

Acceptance is deliberately strict:
- exactly one fenced code block in the complete response;
- its info string must be python;
- the fence must close normally;
- extracted source must contain non-whitespace content;
- prose/reasoning outside the one fence is allowed and retained in raw response;
- zero, multiple, wrong-language, malformed/unclosed, or empty blocks are model
  output failure for that phase;
- no heuristic recovery, block selection, Python-looking prose extraction,
  dedenting, newline normalization, or format-repair inference is allowed;
- extraction occurs only after the complete streamed response is available;
- the exact extracted body is the artifact supplied to ty/Ruff.

No Python runtime execution/import check is part of v1. Ruff and ty are the
historical validation mechanism and inspect the extracted artifact without
executing it.

CALL LIMITS AND FAILURE SEMANTICS
Initial materialization plus analyzer repairs has a maximum of five LLM calls.
Calls 1-4 may lead to another repair when ty/Ruff findings remain. If call 5
still has analyzer findings, the materialization phase fails with analyzer limit
reached. Any malformed source-producing response terminates that phase
immediately rather than consuming another call to repair formatting.

Self-audit starts only after analyzer-clean initial materialization and has an
independent maximum of five calls: self-audit is call 1, followed by at most four
analyzer repair calls under the same strict source-response protocol.

Questionnaire execution is not suppressed by materialization or self-audit
failure. Failed implementation state and subsequent questionnaire claims are
valuable scoring evidence. If no valid source was ever extracted, the harness
must not invent an empty source artifact.

STATIC ANALYSIS REQUIREMENT
The application runs ty and Ruff against the exact generated source artifact.
Analyzer application config contains logical toolId plus argv templates.
Executable authority belongs in shared Actant runtime processTools configuration,
not the workflow Pack.

Analyzer evidence preserves the generic ProcessResult snapshot, including tool
identity, configured/resolved executable, arguments, working directory, timing,
exit code, stdout, and stderr. Analyzer findings are expected test input and are
distinguished from failure to launch/execute the analyzer.

Production CodeEntry contexts expose ctx.process.run() for logical configured
tools. Runtime configuration owns logical-name -> executable binding. V1 requires
absolute executable paths. CodeEntry supplies argv, optional cwd, and optional
timeout but cannot supply arbitrary executable, shell command, or environment
replacement.

Production CodeEntry contexts also expose invocation-private
ctx.workspace.materializeText()/materializeBytes(). Workspace materialization is
immediate and process-visible but non-authoritative, non-persistent scratch state.
The context owns cleanup and callers may provide only contained relative paths.
This is the correct bridge for exact analyzer inputs and must not be replaced by
direct pathlib/open/subprocess behavior in the application Pack.

The user ran Integration's focused Python 3.15 process/context/workspace suites
and reported them green before synchronization. Materialization-specific workflow
tests have been added for strict source extraction and analyzer mediation, but
have NOT yet been reported run under Python 3.15.
