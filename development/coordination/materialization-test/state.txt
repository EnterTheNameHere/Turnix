GROUNDING SEMANTIC ISSUE FOUND
A rendered-prompt audit found that the historical grounding string combines two
different things:
1. authoritative grounding/reference material;
2. instructions for the standalone historical grounding conversation turn,
   including "do not implement yet" and a requested grounding summary.

Native must not project those turn-specific instructions into the same inference
as implementation/repair/questionnaire work. Planned data shape is:
- groundingReference: reusable authoritative material;
- groundingResponseInstruction: Classic-only first-turn instruction.

Classic later sends both as its first user turn. Native sends only
`groundingReference` with relevant requirements/state/instruction.

A second audit finding is that the generated source protocol currently tells the
model prose outside the Python fence is allowed, while the real benchmark source
prompts require no outside prose. The extraction harness should remain tolerant
and preserve outside prose as scoring evidence, but the prompt must stop
positively permitting it.

CURRENT ACTANT-NATIVE IMPLEMENTATION
Workflow codeEntry.py version 8 implements:
1. Initial materialization.
2. Ruff + ty analysis of exact extracted source.
3. Repair loop, maximum five source-producing calls total.
4. Self-audit only after analyzer-clean initial materialization.
5. Independent Ruff + ty repair loop, maximum five source-producing calls.
6. Questionnaire regardless of source/materialization outcome when LLM remains
   callable.

Native repair/self-audit projections retain the original
initialMaterialization requirements. Current source appears exactly once in a
repair prompt; analyzer reports do not duplicate it. Native questionnaire sees
grounding, original requirements, frozen source/failure state, common
questionnaireInstructions, and exactly one requirement.

SOURCE RESPONSE / ANALYZER SEMANTICS
Every source-producing response is extracted only after streaming completes.
Exactly one non-empty fenced Python block is required. No heuristic block choice,
fence repair, dedent, or newline normalization occurs. Ordinary prose outside the
single valid fence remains extraction-tolerated and preserved in raw evidence.
Generated Python is not executed/imported as benchmark validation.

The application materializes exact candidate source through ctx.workspace and
runs configured Ruff and ty through ctx.process.run(). Both analyzers consume the
same scratch artifact. Nonzero exit is model/code evidence; process execution
failure is infrastructure/application evidence.

QUESTIONNAIRE SEMANTICS
Questionnaire is attempted even after materialization/self-audit model-output or
analyzer-infrastructure failure when the LLM remains callable. If no valid source
exists, Native supplies explicit failure state rather than inventing a file.
Only LlmError is classified as questionnaire inference failure; programming or
application exceptions propagate.

LATEST LEGITIMATE SOURCE
A later extraction failure retains the previous valid source. If a new valid
source is extracted but analyzer execution fails, that newly extracted source is
the latest legitimate artifact even though analyzer cleanliness is unknown.
Questionnaire uses that latest legitimate artifact.

EXPORT / PUBLICATION
Exporter is a separate Job after the benchmark Job has accepted authoritative
state and the CLI has saved it. Export failure therefore does not invalidate an
already accepted benchmark run.

materializationTest.export@1 emits:
  <outputDirectory>/<applicationId>/<applicationRunId>/evidence.json

Evidence format is materialization-test.evidence@1 and contains application
identity, exact test definition/configuration, authoritative workflow state, and
all referenced shared ProcessingRun snapshots. Exact model-facing prompts are
dereferenced from ProcessingRun evidence rather than reconstructed.

run.py saves accepted authoritative state before raising a Job error, preserving
the Actant rule that authoritative state may have been accepted even when the
owning Job later fails.
