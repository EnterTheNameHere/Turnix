MATERIALIZATION TEST COORDINATION STATE
=======================================

OWNER
Materialization-test development thread.

BRANCH
actant-materialization-test, based on actant-integration.

PURPOSE
This file is the consolidated current synchronization state for the
Materialization Test application work. Numbered files under messages/ preserve
cross-thread correspondence and rationale. Update this file when consolidated
truth changes; do not use it as an append-only conversation log.

CURRENT GOAL
Build the second independent Actant application consumer: an unattended local
LLM materialization benchmark. The first finish line is configure -> run ->
materialize -> static-analyzer/fix loop -> self-audit/fix -> questionnaire ->
export sufficient evidence for scoring.

TEST STRATEGIES
Two strategies must use the same test definition and source prompt material:

1. Classic reproduces the existing manual LM-Studio-like accumulating
   conversation as closely as practical, including the historical questionnaire
   as one 100+ question request.
2. Actant-native reconstructs each inference from authoritative state and only
   relevant QueryItems. Its questionnaire asks questions individually against
   the same final frozen materialization and requirements.

V1 PROMPT DATA
Keep prompt representation deliberately simple. JSON file(s) may initially
contain these placeholder strings:

- grounding instructions
- initial mazerialization test instructions
- static analysis report template
- search for bugs and fix instructions
- questionnaire content

Do not invent a prompt-component language before requirements demand it.

STATIC ANALYSIS REQUIREMENT
The application must run ty and Ruff against the exact generated source
artifact. Each tool must support an explicitly configured executable path so a
user can select the same executable used by VS Code on Windows 11. Do not bake
in a username or a guessed VS Code extension path.

Analyzer evidence should preserve at least tool identity, configured and
resolved executable, arguments, working directory, target artifact, timing,
exit code, stdout, and stderr. Analyzer findings are expected test input and
must be distinguished from failure to launch/execute the analyzer.

SHARED ACTANT PRESSURE FOUND
CodeEntryContext currently mediates I/O, memory, capabilities and LLM access,
but exposes no process/tool execution facility. The Materialization Test should
not hide arbitrary subprocess authority inside its Pack merely to run ty/Ruff.
A generic Actant-owned mediated process/tool execution boundary is requested
from the integration work. The existing llama.cpp driver directly uses
subprocess to manage llama-server and is a second candidate consumer of such a
shared facility.

CURRENT PIPELINE FIT
The current QueryItem and LlmProcessingPipeline shape is sufficient for the
prompt-side first implementation. LlmProcessingPipeline already records exact
query/response evidence and allows completion logic to update application state
transactionally. ApplicationRuntime.runJob plus child ProcessingRuns provides a
usable outer/inner transaction spine for v1.

CHECKPOINTS
Automatic restart/checkpointing is desired later but is not a v1 requirement.
Keep workflow phase/progression explicit enough that checkpoints can be added
without redesigning the application. Future UI may expose richer checkpoint
selection/branching; do not build UI abstractions now.

COORDINATION PROTOCOL
- state.txt is consolidated current truth.
- messages/ contains numbered cross-thread messages and responses.
- Messages use FROM, TO, optional IN-REPLY-TO, STATUS, SUBJECT, context/question
  as useful; keep them lightweight.
- TO may be integration, materialization-test, evil-birthday-analysis, or all.
- A participant should read state.txt and new relevant messages before work.
- Shared/reusable Actant changes ultimately belong on actant-integration.
- Application-specific materialization semantics stay on this branch.

OPEN SHARED QUESTION
What is the smallest correct generic Actant process/tool execution contract for
v1, including invocation authority, executable/path handling, working directory,
arguments, captured stdout/stderr, exit status, timing/evidence, and the boundary
between expected nonzero tool findings and infrastructure execution failure?
