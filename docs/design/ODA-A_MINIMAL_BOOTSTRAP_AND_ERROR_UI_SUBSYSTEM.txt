===============================================================================
OPTIONAL DESIGN AREA ODA-A - MINIMAL BOOTSTRAP & ERROR UI SUBSYSTEM
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines a minimal bootstrap and error-presentation layer for failures that
occur before normal Pack activation, Application-facing View surfaces, or
ApplicationRun readiness.

This area is optional in tier, but strategically important for robustness,
debuggability, and user trust.

Purpose:
--------
This document defines the minimal bootstrap and error-user-interface model
used when Turnix encounters blocking failures before normal runtime surfaces
are available.

It defines:
- bootstrap stages as a conceptual startup model
- the role and scope of the minimal error UI
- Kernel-mediated error communication and action handling
- frontend handling during early blocking failures
- relationship to RPC, View, and execution adapter boundaries
- fallback behavior when minimal UI is unavailable

It does NOT define:
- core Turnix correctness semantics
- normal Application/View user-interface behavior
- PackManager behavior
- normal View runtime behavior (see DA-22)
- execution adapter boundary semantics (see DA-23)
- RPC, channel, or transport semantics (see DA-21)
- mod-defined or themeable early UI extension rules
- LLM-assisted recovery as required behavior
- a general runtime startup taxonomy

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines a minimal bootstrap and error-user-interface
      subsystem within that shared interpretation model.


===============================================================================
02. CORE PROBLEM
===============================================================================

02.1. Turnix may fail before:
      - any normal Pack activation has succeeded
      - any ApplicationRun is ready
      - normal Application-facing View surfaces exist
      - mods are loaded
      - services or capabilities are available for normal application use

02.2. Examples include:
      - corrupted Workspace/runtime configuration
      - unreadable manifest
      - schema mismatch
      - missing runtime files
      - discovery failure

02.3. Without a minimal bootstrap-facing error surface, such failures may
      become:
      - silent
      - terminal-only
      - confusing
      - harder to recover for non-technical users

02.4. This document defines an early minimal subsystem intended to reduce
      those failure modes without depending on normal pack-driven runtime
      behavior.

02.5. The minimal bootstrap error subsystem does not become the normal UI
      runtime merely because it can present errors.

02.6. The minimal bootstrap error subsystem does not belong to an
      ApplicationRun merely because it may present an error during
      Application creation or loading.


===============================================================================
03. BOOTSTRAP STAGES (LOCKED CONCEPT)
===============================================================================

03.1. Turnix startup may be understood through a stage-based conceptual
      model.

03.2. Bootstrap stages are local to this document's startup explanation.

03.3. Bootstrap stages do not define platform authority tiers.

03.4. Bootstrap stages do not define a general runtime startup taxonomy.


03.5 STAGE 0 - KERNEL BOOTSTRAP (LOCKED CONCEPT)
------------------------------------------------

03.5.1. Stage 0 includes early Kernel bootstrap responsibilities such as:
        - process startup
        - logging and early diagnostics
        - IoManager readiness needed by bootstrap paths
        - error-envelope handling
        - configuration schema loading
        - default configuration loading
        - Workspace/runtime configuration loading

03.5.2. Failures in Stage 0 are fatal.

03.5.3. No user interface is guaranteed in Stage 0.


03.6 STAGE 1 - MINIMAL UI BOOTSTRAP (LOCKED CONCEPT)
----------------------------------------------------

03.6.1. Stage 1 includes the minimal bootstrap-facing error subsystem.

03.6.2. Stage 1 responsibilities may include:
        - serving minimal bootstrap UI assets
        - serving an HTML shell or bootstrap script when used
        - establishing RPC or an equivalent bootstrap communication path
        - registering early error-reporting paths
        - rendering a minimal error UI

03.6.3. Failures in Stage 1 are severe.

03.6.4. Stage-1 failures may still allow retry, fallback, or user action
        when the surrounding bootstrap environment supports that.

03.6.5. Stage-1 frontend code, when present, remains frontend adapter code
        under DA-23 rather than Kernel authority.

03.6.6. Stage-1 communication, when RPC-backed, remains constrained by
        DA-21.


03.7 STAGE 2 - PACK DISCOVERY, APPLICATION, AND ACTIVATION
----------------------------------------------------------

03.7.1. Stage 2 includes later startup work such as:
        - content scanning
        - indexing
        - graph preparation
        - Pack activation
        - Application creation or loading
        - ApplicationRun creation and readiness

03.7.2. Failures in Stage 2 are expected to be more user-resolvable than
        Stage-0 failures because the minimal interaction layer may already
        exist by then.

03.7.3. Application and ApplicationRun lifecycle meaning remains outside
        this document's authority.


===============================================================================
04. MINIMAL ERROR UI PURPOSE (LOCKED)
===============================================================================

04.1. The minimal error UI exists only to:
      - display fatal or blocking errors
      - present recovery choices supplied by the Kernel-owned recovery path
      - return a selected decision to the Kernel-owned recovery path

04.2. The minimal error UI is not:
      - a full application UI
      - a normal View runtime surface
      - a PackManager
      - a RuntimeHost command surface
      - themeable by normal packs
      - customizable by mods

04.3. The minimal error UI does not own the meaning of actions it displays.

04.4. The minimal error UI does not own recovery authority.

04.5. The minimal error UI is a bootstrap decision surface.

04.6. The minimal error UI is not a normal Application View.


===============================================================================
05. ERROR UI CHARACTERISTICS (LOCKED)
===============================================================================

05.1. The minimal error UI is:
      - small
      - fast to load
      - independent of packs
      - independent of LLM availability
      - independent of Workspace/user-authored configuration
      - independent of SaveBundles
      - independent of asset compilation

05.2. Acceptable forms may include:
      - an Electron window
      - a browser page
      - a native dialog
      - a text overlay fallback

05.3. The exact presentation technology is an implementation choice so long
      as the minimal-bootstrap constraints in this document remain preserved.

05.4. Presentation technology does not define authority.

05.5. Browser-based minimal UI remains browser frontend code, not Kernel
      state authority.


===============================================================================
06. ERROR COMMUNICATION AND DIAGNOSTICS MODEL (LOCKED)
===============================================================================

06.1. Blocking errors classified through the Kernel-owned recovery path are
      sent to the minimal UI as:
      - the standard error envelope
      - a human-readable message
      - structured payload
      - an allowed-actions list

06.2. The UI returns:
      - the selected action
      - optional parameters
      - acknowledgement when required

06.3. Action meaning originates in the Kernel-owned recovery path rather
      than in the UI.

06.4. UI acknowledgement does not imply recovery success.

06.5. Transport acknowledgement does not imply recovery success.

06.6. Recovery outcome remains owned by the Kernel-owned recovery path.

06.7. The subsystem emits structured trace or diagnostic evidence for early
      blocking errors when the relevant bootstrap substrate is available.

06.8. The subsystem emits structured trace or diagnostic evidence for
      presented actions when the relevant bootstrap substrate is available.

06.9. The subsystem emits structured trace or diagnostic evidence for
      selected decisions when the relevant bootstrap substrate is available.

06.10. The subsystem emits structured trace or diagnostic evidence for
       fallback, unavailable-UI, timeout, and abort outcomes when the
       relevant bootstrap substrate is available.

06.11. Early trace or diagnostic loss weakens evidence.

06.12. Early trace or diagnostic loss does not by itself redefine
       committed-state correctness.


===============================================================================
07. SUPPORTED USER ACTIONS (LOCKED)
===============================================================================

07.1. Typical Kernel-provided actions may include:
      - Retry
      - Reset selected Workspace/runtime configuration to defaults when allowed
      - Ignore and continue when allowed
      - Abort startup
      - Open diagnostics/logs through a controlled host action

07.2. Available actions are provided by the Kernel-owned recovery path.

07.3. The UI does not invent actions.

07.4. The UI does not auto-confirm actions without policy authority.

07.5. Opening diagnostics or logs does not grant the minimal UI unrestricted
      filesystem authority.

07.6. Opening diagnostics or logs does not grant the minimal UI a general
      file-browser capability.


===============================================================================
08. UI AVAILABILITY GUARANTEE
===============================================================================

08.1. Stage-1 completion means the minimal bootstrap decision surface has
      been established for use.

08.2. Once Stage 1 is complete, the Kernel may attempt to use the minimal
      decision surface for blocking startup decisions.

08.3. Once Stage 1 is complete, Kernel-mediated work may pause at a
      decision point according to policy.

08.4. Stage-1 completion does not guarantee continued frontend availability.

08.5. Stage-1 completion does not guarantee successful reconnect.

08.6. Stage-1 completion does not guarantee successful recovery.

08.7. If the minimal UI is unavailable, disconnects, or times out, the
      fallback and failure rules in section 10 apply.

08.8. Before Stage 1 completes:
      - no user interaction is relied upon
      - fatal errors abort immediately unless an even earlier fallback path
        exists outside this document's guaranteed scope

08.9. Stage-1 completion does not imply normal UI readiness.

08.10. Stage-1 completion does not imply ApplicationRun readiness.

08.11. Stage-1 completion does not imply Pack activation success.


===============================================================================
09. MULTI-FRONTEND HANDLING (LOCKED)
===============================================================================

09.1. If multiple frontends connect to the minimal error subsystem:
      - the blocking error is broadcast
      - the first valid response accepted by Kernel-owned recovery wins
      - other pending presentations are dismissed

09.2. The Kernel remains the authority.

09.3. Multiple frontend presentations do not create multiple recovery truths.

09.4. Stale or already-resolved presentations are not accepted again.


===============================================================================
10. FAILURE MODES
===============================================================================

10.1. If the minimal UI fails to load:
      - Turnix may request a controlled RuntimeHost fallback surface
      - Turnix may request a controlled launcher fallback surface
      - Turnix may fall back to console reporting
      - Turnix may abort with a clear error when no safe fallback exists

10.2. If the UI disconnects:
      - execution may pause
      - reconnect may be allowed
      - timeout handling may apply when configured

10.3. If the UI becomes unavailable after Stage-1 completion, section 08
      does not preserve a stronger availability guarantee.

10.4. If the UI times out, fallback handling or abort handling applies
      according to the Kernel-owned recovery path.

10.5. UI disconnect does not automatically imply Job failure.

10.6. UI disconnect does not automatically imply adapter failure.

10.7. UI disconnect does not redefine committed-state meaning.


===============================================================================
11. OPTIONAL PACK-BASED ERROR UI (OPEN)
===============================================================================

11.1. A future design may define a special early-loaded error UI Pack model.

11.2. Such a model might:
      - load before normal Pack activation
      - require explicit whitelisting
      - replace the built-in minimal error UI

11.3. Potential advantages include:
      - themed presentation
      - extensibility
      - reuse

11.4. Potential costs include:
      - increased bootstrap complexity
      - increased dependency risk

11.5. This concept remains OPEN.

11.6. A future pack-based error UI model remains constrained by normal
      execution adapter, activation, RPC, and authority boundaries unless an
      authoritative document defines a narrower bootstrap exception.

11.7. A future pack-based error UI model does not inherit ordinary discovery
      or activation behavior merely because it is pack-based.

11.8. A future pack-based error UI model does not become PackManager,
      RuntimeHost, Kernel, or recovery authority.


===============================================================================
12. LLM-ASSISTED RECOVERY (OPEN)
===============================================================================

12.1. A future design may allow LLM-assisted explanation or guidance when an
      LLM service is available.

12.2. Constraints include:
      - LLM assistance does not block recovery
      - LLM assistance does not replace user choice
      - LLM assistance is never required for recovery

12.3. LLM assistance does not own action meaning.

12.4. LLM assistance does not own recovery authority.

12.5. This concept remains OPEN and optional.


===============================================================================
13. WHAT THIS AREA DOES NOT DO
===============================================================================

13.1. This area does not include:
      - save inspection
      - pack browsing
      - mod installation
      - normal capability invocation as a user feature surface
      - scripting
      - theming
      - normal frontend adapter lifecycle
      - normal View lifecycle
      - raw filesystem access
      - PackManager operations
      - RuntimeHost command ownership


===============================================================================
14. LOCKED SUMMARY
===============================================================================

14.1. LOCKED:
      - bootstrap stages as a conceptual model local to this document
      - the minimal error UI role
      - Kernel-mediated action authority
      - structured error-envelope communication
      - qualified decision-surface use after Stage 1
      - Stage-1 frontend code is not Kernel authority
      - presentation technology does not define authority
      - UI or transport acknowledgement does not imply recovery success
      - minimal UI diagnostics/log actions do not grant raw filesystem
        authority
      - early trace or diagnostic evidence is emitted when available

14.2. OPEN:
      - pack-based error UI
      - LLM-assisted guidance
      - user-experience refinements
