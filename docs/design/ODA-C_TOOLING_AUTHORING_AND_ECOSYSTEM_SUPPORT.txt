===============================================================================
OPTIONAL DESIGN AREA ODA-C - TOOLING, AUTHORING & ECOSYSTEM SUPPORT
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines optional tooling, authoring support, and ecosystem-facing support
surfaces that improve author productivity and ecosystem health without
changing Turnix runtime semantics.

This area is optional in tier, but strategically important for long-term
ecosystem health, author productivity, and external adoption.

Purpose:
--------
This document defines optional tooling, authoring, and ecosystem-support
expectations for Turnix.

It defines:
- authoring-experience principles
- optional manifest and config authoring tools
- optional graph-visualization and catalog tooling
- optional adapter declaration and executable-artifact tooling
- optional scaffolding and static-analysis support
- optional PackManager user-experience extensions
- optional documentation-generation and ecosystem-policy support

It does NOT define:
- runtime rules
- conflict-resolution authority
- automatic pack activation or pack inclusion
- execution adapter semantics (see DA-23)
- RPC, channel, or transport semantics (see DA-21)
- capability permission semantics (see DA-16)
- service authority or raw service-object access
- Application, ApplicationRun, or SaveBundle lifecycle semantics
- PackManager graph-preparation authority (see DA-29)
- silent conflict resolution or silent graph repair
- any new correctness guarantees or authority boundaries

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines optional tooling, authoring, and ecosystem-
      support expectations within that shared interpretation model.


===============================================================================
02. CORE PROBLEM
===============================================================================

02.01. Turnix is powerful, but it is also:
      - non-trivial to author for
      - policy-heavy
      - strict about correctness
      - adapter-mediated
      - unfamiliar to many mod authors

02.02. Without tooling support:
      - authors may make avoidable mistakes
      - specifications may be misunderstood
      - good ideas may fail because of friction
      - ecosystem cohesion may suffer

02.03. This area exists to reduce avoidable friction without weakening
      runtime truth or runtime correctness.

02.04. Tooling is allowed to explain and preview runtime rules, but tooling
      does not become a runtime authority source.


===============================================================================
03. AUTHORING-EXPERIENCE PRINCIPLE
===============================================================================

03.01. Turnix is:
      - strict at runtime
      - more forgiving during development
      - explicit rather than magical
      - explainable rather than silent

03.02. Tooling exists to:
      - surface rules early
      - guide authors
      - prevent invalid states before runtime where owning documents define
        the relevant validation rule

03.03. Tooling support does not replace runtime enforcement.

03.04. Tooling previews do not grant execution authorization, capability
      permission, activation success, ApplicationRun readiness, or
      persistence authority.

03.05. Advisory tooling does not silently repair invalid graph intent,
      invalid manifests, invalid configuration, or invalid runtime state.


===============================================================================
04. MANIFEST AUTHORING TOOLS (OPTIONAL)
===============================================================================

04.01. Optional manifest-authoring tools may include:
      - manifest schema validation
      - manifest linting
      - dependency sanity checks
      - visibility and export previews
      - executable artifact declaration checks
      - adapter binding previews

04.02. Example diagnostics may include:
      - "this pack cannot see that pack"
      - "this dependency will never resolve"
      - "this export is unreachable"
      - "this executable artifact has no adapter binding"
      - "this adapter kind requires explicit trust policy"

04.03. These tools remain advisory unless an owning document defines a hard
      validation rule.

04.04. Manifest tooling does not execute code merely because it recognizes a
      code artifact.

04.05. Manifest tooling does not make discovery, visibility, resolution,
      dependency satisfaction, activation, import, execution authorization,
      or capability permission decisions by itself.


===============================================================================
05. CONFIG AUTHORING AND MIGRATION TOOLS (OPTIONAL)
===============================================================================

05.01. Optional tools may include:
      - config schema editors
      - default-value previews
      - migration simulation from earlier stored forms to current forms
      - diff viewers

05.02. The purpose of such tools is to:
      - reduce config breakage across versions
      - make migrations more predictable
      - show likely validation or compatibility problems earlier

05.03. Migration simulation does not commit authoritative state.

05.04. Config authoring tools do not replace committed configuration,
      configuration validation, configuration migration, or transaction
      rules owned by the relevant runtime documents.


===============================================================================
06. PACK GRAPH VISUALIZATION (OPTIONAL)
===============================================================================

06.01. Optional graph tooling may show:
      - pack hierarchy and tree identity
      - manifest-authored relationships
      - discovered candidates
      - dependency edges
      - visibility boundaries
      - selected graph intent
      - accepted runtime graph structure when available
      - AppPack/AppDefinition to Application and SaveBundle relationships
        when available
      - Application and ApplicationRun relationships when viewing runtime
        evidence
      - adapter participation when trace evidence exists
      - generated documentation output

06.02. Such tooling may be useful for:
      - debugging complex setups
      - education
      - PackManager user-experience enhancements

06.03. Visualized relationships do not create authority or dependency truth
      beyond the underlying evidence.

06.04. Graph tooling distinguishes manifest-authored relationships,
      discovered candidates, selected graph intent, accepted runtime graph,
      retained runtime evidence, and generated documentation output.

06.05. Visualizing one category does not make it another category.

06.06. A selected graph preview does not become an accepted runtime graph.

06.07. Retained Application, ApplicationRun, or SaveBundle evidence does not
      become prospective graph authority merely because it is displayed near
      manifest or PackManager information.


===============================================================================
07. CAPABILITY CATALOG (OPTIONAL)
===============================================================================

07.01. A structured capability catalog may include:
      - known capabilities
      - versions
      - providers
      - permissions required
      - adapter-facing or RPC-facing usage hints when applicable

07.02. Potential benefits include:
      - discoverability
      - reduced name collisions
      - stronger ecosystem conventions

07.03. Catalog entries do not grant capability permission.

07.04. Catalog entries do not prove that a capability is available in a
      specific ApplicationRun, selected graph, activation plan, or policy
      context.


===============================================================================
08. TEMPLATES AND SCAFFOLDING (OPTIONAL)
===============================================================================

08.01. Optional generators may create:
      - a ModPack
      - an AppPack
      - a ViewPack, where ViewPacks are supported
      - a capability provider
      - a hook participant
      - an event producer or listener
      - a processor or provider where owning documents allow it
      - an execution adapter binding example
      - a frontend View example

08.02. Such scaffolds may enforce or encourage:
      - correct manifest shape
      - declared executable artifacts
      - adapter binding declarations
      - canonical entrypoints
      - suggested patterns

08.03. Scaffolds remain starting points, not runtime authority.

08.04. Ordinary Pack scaffolding uses mediated Pack-facing patterns rather
      than exposing backend service objects.

08.05. Service-provider scaffolding is limited to explicitly allowed
      internal or runtime-extension contexts.

08.06. Service-provider scaffolding does not expose raw service objects to
      ordinary Pack code.

08.07. Service-provider scaffolding does not collapse capability mediation.


===============================================================================
09. STATIC ANALYSIS AND LINTING (OPTIONAL)
===============================================================================

09.01. Optional static-analysis or linting tools may:
      - detect undeclared capability usage
      - detect unreachable exports
      - detect dead code entries
      - detect recognized code artifacts that are not declared executable
      - detect missing adapter binding metadata
      - warn about unsafe in-process adapter trust requirements
      - warn about background execution risks
      - warn about graph intent that appears unsatisfied or ambiguous

09.02. Such tooling may run:
      - in development mode
      - as CLI tooling
      - as a pre-publish check

09.03. Static analysis may be incomplete and does not replace runtime
      enforcement.

09.04. Static-analysis results remain warnings, previews, or early
      diagnostics unless an owning document defines a hard validation rule.

09.05. Static analysis does not prove runtime authority, activation success,
      execution safety, capability permission, or persistence correctness in
      all runtime contexts.


===============================================================================
10. PACKMANAGER USER-EXPERIENCE EXTENSIONS (OPTIONAL)
===============================================================================

10.01. Optional PackManager user-experience features may include:
      - explaining why a pack is excluded, unavailable, or not selectable
      - previewing the effect of a selected graph change
      - previewing prospective Pack inclusion
      - activation-plan preview
      - conflict-resolution walkthroughs
      - showing execution adapter requirements
      - showing trust or policy prompts that may be required later

10.02. These remain presentation, explanation, preparation, or preview
      layers over logic owned by the relevant runtime documents.

10.03. PackManager user-experience extensions do not become Kernel,
      resolver, loader, activator, importer, policy owner, persistence
      authority, Application lifecycle owner, SaveBundle authority, or
      Turnix identity.

10.04. A PackManager preview does not grant visibility, dependency
      satisfaction, capability permission, execution authorization,
      activation, or persistence rights.

10.05. Activation-plan preview does not load adapters, evaluate modules, run
      lifecycle callbacks, publish registrations, create Pack
      participation, mark an ApplicationRun ready, or mutate accepted
      runtime state.

10.06. If a tool executes activation-like work, that work is not an advisory
      preview.

10.07. Executed activation-like work follows the owning runtime, adapter,
      activation, policy, Job, trace, and transaction boundaries.


===============================================================================
11. DOCUMENTATION GENERATION (OPTIONAL)
===============================================================================

11.01. Optional documentation-generation tooling may derive:
      - pack summaries
      - capability lists
      - dependency trees
      - config options
      - declared executable artifact summaries
      - adapter requirement summaries
      - graph-intent summaries

11.02. Such output may be derived from:
      - manifests
      - schemas
      - selected graph intent
      - accepted runtime graph evidence
      - trace metadata where appropriate

11.03. Generated documentation does not replace the manifest, schema, trace,
      retained evidence, or runtime authority source from which it was
      derived.

11.04. Generated documentation does not silently convert advisory metadata
      into hard dependency, activation, resolution, trust, or permission
      rules.


===============================================================================
12. ECOSYSTEM POLICY SUPPORT (OPTIONAL)
===============================================================================

12.01. Optional ecosystem-policy support may include:
      - suggested pack sets
      - compatibility badges
      - soft deprecation warnings
      - advisory version constraints
      - advisory adapter trust notes

12.02. Such support remains policy-driven and is never enforced silently by
      virtue of this document alone.

12.03. Ecosystem suggestions do not grant execution authorization or
      capability permission.

12.04. Ecosystem suggestions, badges, trust notes, advisory constraints,
      and soft deprecations do not become hard dependencies, activation
      blockers, resolution constraints, trust decisions, permission
      decisions, or policy decisions unless an owning authoritative document
      explicitly defines that effect.


===============================================================================
13. WHAT THIS AREA MUST NOT DO
===============================================================================

13.01. This area does not justify:
      - changing runtime rules
      - auto-including packs
      - auto-resolving conflicts
      - auto-authorizing execution adapters
      - auto-granting capability permission
      - executing code because a file exists
      - hiding errors for convenience
      - silently repairing graph intent
      - treating advisory metadata as hard constraints

13.02. Tooling convenience does not override runtime truth.

13.03. Tooling support does not collapse PackManager, resolver, loader,
      activator, importer, policy, permission, persistence, or Kernel
      authority boundaries.


===============================================================================
14. LOCKED AND OPEN
===============================================================================

14.01. LOCKED:
      - tooling does not change runtime semantics
      - tooling is advisory rather than authoritative
      - runtime correctness wins over tooling convenience
      - code artifact recognition by tooling does not imply execution
      - adapter tooling previews do not grant adapter authority
      - activation-plan preview does not execute activation
      - PackManager user-experience tooling does not become runtime authority
      - generated documentation does not replace its source authority
      - ecosystem policy support remains advisory unless an owning document
        explicitly defines stronger effect

14.02. OPEN:
      - which tools exist
      - where they live, such as CLI, UI, or external ecosystems
      - how much is bundled versus external
      - exact adapter declaration tooling behavior
      - exact selected-graph preview behavior
      - exact generated-documentation output formats
      - exact internal or runtime-extension service scaffolding scope


===============================================================================
15. RELATION TO OTHER AREAS
===============================================================================

15.01. This area depends on higher documents such as:
      - DA-06 for configuration, schemas, and migration
      - DA-09 for root and discovery boundaries
      - DA-10 for pack identity and hierarchy
      - DA-11 for generic resolution semantics
      - DA-13 for dependency semantics
      - DA-14 for activation
      - DA-16 for capabilities and permissions
      - DA-20 for application lifecycle and runtime identity
      - DA-21 for RPC, channels, and transports
      - DA-23 for execution adapter boundaries
      - DA-29 for PackManager graph preparation and management boundaries
      - ODA-B for diagnostics surfaces

15.02. This area does not replace those documents.

15.03. When tooling displays, previews, explains, or generates material from
      another area, the owning area remains the authority for that material's
      runtime meaning.
