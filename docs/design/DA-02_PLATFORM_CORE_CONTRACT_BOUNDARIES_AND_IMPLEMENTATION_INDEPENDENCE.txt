===============================================================================
DESIGN AREA DA-02 - PLATFORM CORE, CONTRACT BOUNDARIES &
IMPLEMENTATION INDEPENDENCE
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the architectural relationship between Turnix platform truth,
platform core, Kernel authority, RuntimeHost boundaries, adapters,
interoperability envelopes, official tooling, and replaceable implementation
layers.

Purpose:
--------
This document defines how Turnix remains one platform when implementation
languages, RuntimeHost realizations, ExecutionAdapter strategies, transports,
official tooling, storage mechanisms, or first-party modular components change
over time.

It defines:
- platform identity and architectural scope
- platform core and guarantee source
- contract boundaries
- first-party modularity and official tooling boundaries
- RuntimeHost boundary position
- adapter boundaries and host-language realization
- service, capability, and ModCallContext boundary rules
- interoperability envelope role
- implementation independence and replaceability
- compact ownership stop-lines for neighboring domains

It does NOT define:
- concrete RPC schemas
- concrete transport protocols
- concrete frontend rendering rules
- concrete language adapter internals
- concrete pack loading or activation mechanics
- concrete execution adapter protocols
- payload identity, ValueRef, Chunk, or storage representation details
- configuration schemas, migrations, or file layouts
- persistent I/O provider, Reader, Writer, or backup mechanics
- UI, View, frontend runtime, debugger, or breakpoint mechanics
- Window artifact, export, comparison, Replay, Resume, Retry, or retained-
  evidence workflow mechanics
- concrete RuntimeHost commands, workspace ownership mechanics, or entry-
  surface implementation details
- detailed Application, ApplicationRun, AppDefinition/AppPack, or SaveBundle
  lifecycle semantics
- detailed ModCallContext facade semantics

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines architectural boundaries and implementation-
      independence rules within that shared interpretation model.


===============================================================================
02. PLATFORM IDENTITY AND ARCHITECTURAL SCOPE
===============================================================================

02.01. Turnix platform truth is defined by contracts, guarantees,
      orchestration semantics, authority boundaries, and continuity behavior.

02.02. Turnix platform truth is not defined by any specific implementation
      language, framework, transport, current runtime stack, or process shape.

02.03. The current implementation stack is a realization of Turnix rather
      than the identity of Turnix.

02.04. Backend language, frontend technology, RuntimeHost realization,
      adapter strategy, transport, or current implementation vehicle do not
      by themselves define what Turnix is.

02.05. Turnix remains one platform when different technical layers are
      implemented in different languages.

02.06. Architectural scope in this document includes:
      - platform core
      - Kernel authority position
      - contract boundaries
      - first-party modular components
      - official tooling boundaries
      - RuntimeHost boundary position
      - host-language adapters
      - ExecutionAdapters
      - services and capabilities at a high level
      - ModCallContext at a high level
      - interoperability envelopes

02.07. Architectural scope in this document excludes concrete schema,
      adapter-protocol, RuntimeHost command, workspace ownership, entry-
      surface, transport, payload, configuration, persistent I/O, UI,
      debugger, artifact, export, comparison, Replay, Resume, Retry, and
      retained-evidence workflow details.

02.08. Runtime authority follows this high-level ordering:
      - Kernel owns runtime authority.
      - RuntimeHost exposes controlled entry and command surfaces.
      - ExecutionAdapters run adapter-mediated Pack code.
      - Transports carry messages.
      - RPC defines the logical communication boundary.
      - Services provide runtime wiring objects.
      - Capabilities define mediated operation interfaces.
      - OrchestrationUnits coordinate mutation authority.
      - Transactions stage mutation before commit.
      - Committed-state truth is owned by the committed-state domain under
        DA-04 transaction and commit boundaries.
      - Application identifies one durable application individual.
      - ApplicationRun binds one live runtime execution period.
      - SaveBundle / durable save persistence stores accepted Application
        state and associated persistence material under the owning
        persistence-domain rules.

02.09. This ordering is architectural and survives implementation
      replacement.

02.10. RuntimeHost is a running host boundary in this ordering.

02.11. RuntimeHost is not the Kernel authority owner.

02.12. Reusable AppDefinition/AppPack material may define or contribute to
       Application and ApplicationRun creation where the owning creation model
       says so.

02.13. AppDefinition/AppPack material is not Turnix platform identity.

02.14. This document does not decide every possible ApplicationRun backing
       form.


===============================================================================
03. PLATFORM CORE AND GUARANTEE SOURCE
===============================================================================

03.01. The Turnix platform core is the source of platform guarantee meaning.

03.02. The platform core defines:
      - orchestration semantics
      - boundary semantics
      - authority semantics
      - continuity expectations
      - contract meaning
      - guarantee meaning

03.03. The platform core does not need to be monolithic to remain the source
      of platform truth.

03.04. A component belongs to the platform core when its semantics are
      required to preserve platform truth rather than merely to realize it in
      one implementation environment.

03.05. RuntimeHost realizations, adapters, envelopes, transports, official
      tooling, and host-language realizations do not redefine the meaning
      established by the platform core.

03.06. If platform guarantee meaning changes, the change is architectural
      rather than a mere implementation refactor.

03.07. The Kernel is the runtime authority owner within the runtime
      architecture.

03.08. Kernel authority may be realized by replaceable implementation code.

03.09. Kernel authority meaning is platform-semantic rather than accidental
      implementation privilege.

03.10. RuntimeHost may expose, bind, or host controlled entry surfaces.

03.11. RuntimeHost realization does not replace Kernel authority.

03.12. The platform core is not equivalent to:
       - one package
       - one process
       - one module
       - one language
       - one service object
       - one RuntimeHost realization
       - all first-party tooling
       - all official implementation code


===============================================================================
04. CONTRACT BOUNDARIES
===============================================================================

04.01. Turnix uses contract boundaries to separate platform truth from
      implementation realization.

04.02. A contract boundary defines:
      - what a component may rely on
      - what a component provides
      - what meanings remain stable across implementations
      - what outcomes are guaranteed or not guaranteed
      - which authority boundary remains preserved

04.03. Contract meaning remains primary.

04.04. Internal realization remains secondary.

04.05. If an implementation change preserves contract meaning, platform truth
      remains preserved.

04.06. If an implementation change alters contract meaning, guarantee
      behavior, or boundary truth, the change is a platform-semantic change
      rather than a mere implementation substitution.

04.07. Contract boundaries are part of platform architecture.

04.08. Contract boundaries are not decorative documentation.

04.09. Same-language implementation does not erase a contract boundary.

04.10. Same-process implementation does not erase a contract boundary.

04.11. Same-runtime implementation does not erase a contract boundary.

04.12. In-process calls may realize a boundary only when they preserve the
       same contract meaning that an explicit boundary would have provided.

04.13. Direct-call optimization may optimize dispatch mechanics.

04.14. Direct-call optimization does not bypass authority, permission,
       lifecycle, trace, structured error, capability, transaction, commit,
       Application, ApplicationRun, SaveBundle, RuntimeHost, or
       OrchestrationUnit boundaries.

04.15. RuntimeHost entry-surface, command-surface, and workspace ownership
       boundaries remain contract boundaries even when realized inside the
       same process or host-language runtime.


===============================================================================
05. FIRST-PARTY MODULARITY AND OFFICIAL TOOLING
===============================================================================

05.01. Modularity in Turnix applies to creator-provided extensions and to
      first-party platform-realized functionality where modular treatment
      preserves platform truth and controllability.

05.02. First-party modularity may include areas such as:
      - UI
      - TTS
      - LLM-facing components
      - adapters
      - RuntimeHost-facing tools or surfaces
      - PackManager surfaces
      - debugger surfaces
      - export or comparison tools
      - other platform-realized subsystems

05.03. Modularity does not remove the existence of a platform core.

05.04. A first-party component may be replaceable or modular while still
      remaining constrained by platform contracts and guarantees.

05.05. First-party modularity is acceptable only when contract truth,
      orchestration semantics, authority boundaries, and boundary discipline
      remain preserved.

05.06. Replaceable first-party realization does not imply replaceable
      platform meaning.

05.07. A first-party module that executes Pack code remains constrained by
      execution-boundary semantics rather than by implementation proximity.

05.08. A first-party module that exposes RuntimeHost control remains
      constrained by RuntimeHost boundary semantics rather than by
      implementation proximity.

05.09. Official tooling may inspect, list, explain, prepare graph intent,
      present risks, request decisions, expose Views, expose commands, expose
      capabilities, create artifacts, compare retained material, or request
      retained-evidence workflows.

05.10. Official tooling does not become Kernel authority merely because it is
       official.

05.11. Official tooling does not become RuntimeHost authority merely because
       it is official.

05.12. Official tooling does not become discovery authority, resolver, loader,
       activator, persistence authority, View authority, debugger authority,
       artifact authority, policy owner, Application lifecycle owner,
       ApplicationRun lifecycle owner, SaveBundle authority, committed-state
       authority, or Turnix identity merely because it is official.


===============================================================================
06. ADAPTER BOUNDARIES AND HOST-LANGUAGE REALIZATION
===============================================================================

06.01. A host-language adapter or realization layer expresses Turnix in a
      particular technical environment.

06.02. A host-language adapter preserves:
      - platform meaning
      - contract truth
      - boundary semantics
      - authority boundaries
      - guarantee expectations

06.03. A host-language adapter may adapt syntax, calling style, or surface
      mechanics when that adaptation does not weaken platform truth.

06.04. A host-language adapter does not silently reinterpret platform
      contracts, continuity guarantees, permission meaning, tracing
      expectations, or orchestration boundaries.

06.05. If a host-language realization cannot preserve a required platform
      guarantee, the limitation is made explicit rather than hidden behind
      host-language convenience.

06.06. Host-language convenience does not take precedence over contract truth
      or boundary truth.

06.07. Creator-facing cross-language coherence is constrained further by
      Design Doctrine documents that define language-facing doctrine.

06.08. Same host language does not imply same authority.

06.09. Same operating-system process does not imply same authority.

06.10. Pack-provided code is not platform core implementation code merely
       because it is written in the same language as the platform core.

06.11. ExecutionAdapter is the general adapter category for external or
       adapter-mediated code execution.

06.12. ExecutionAdapter semantics are defined outside this document.

06.13. RuntimeHost semantics are defined outside this document.

06.14. Host-language adaptation does not bypass ExecutionAdapter,
       activation, capability, persistence, Application, ApplicationRun,
       SaveBundle, RuntimeHost, workspace ownership, or command-surface
       boundaries.

06.15. Pack code interacts with Turnix through supported mediated surfaces.

06.16. Direct access from Pack code to trusted Turnix backend internals is not
       a supported Turnix contract.

06.17. Physical possibility in a host language does not create a Turnix
       guarantee.

06.18. Physical possibility in a host language does not grant Kernel
       authority.


===============================================================================
07. SERVICES, CAPABILITIES, AND MODCALLCONTEXT BOUNDARIES
===============================================================================

07.01. Services are runtime wiring objects.

07.02. A Service does not become capability permission.

07.03. A Service does not become execution authorization.

07.04. A Service does not become Kernel authority.

07.05. Capabilities are named, versioned, permissioned, Turnix-mediated
      operation interfaces.

07.06. Capability permission does not become execution authorization.

07.07. Capability invocation does not automatically create a Job.

07.08. Job-backed capability execution remains capability-mediated.

07.09. Same process, same runtime, same language, or direct-call optimization
      does not bypass capability mediation.

07.10. ModCallContext is scoped Pack participation in Turnix.

07.11. ModCallContext is not unrestricted backend internals access.

07.12. ModCallContext does not expose filesystem authority by default.

07.13. ModCallContext does not expose committed-state mutation except through
       mediated state and transaction surfaces.

07.14. ModCallContext does not grant capability invocation unless the
       capability boundary permits the invocation.

07.15. ModCallContext does not grant RuntimeHost control authority.

07.16. ModCallContext does not grant Kernel authority.

07.17. Detailed Service, Capability, Permission, and ModCallContext semantics
       belong to their owning design areas.


===============================================================================
08. INTEROPERABILITY ENVELOPE, RPC, AND TRANSPORT
===============================================================================

08.01. Turnix requires interoperability mechanisms for communication across
      execution domains, host-language boundaries, adapter boundaries,
      RuntimeHost entry-surface boundaries, or architectural layers.

08.02. An interoperability envelope carries structured interaction across such
      boundaries.

08.03. The interoperability envelope exists to preserve:
      - boundary clarity
      - request and response meaning
      - tracing and observability
      - permission and capability semantics
      - continuity-safe interaction
      - structured result and error handling

08.04. The interoperability envelope is an architectural boundary rather than
      incidental transport plumbing.

08.05. RPC is the logical communication boundary in the runtime architecture.

08.06. Transport is the concrete carrier of messages.

08.07. Transport does not define the authority meaning of the envelope.

08.08. RuntimeHost command-surface messages may use interoperability
      envelopes.

08.09. The envelope does not define RuntimeHost authority.

08.10. A transport acknowledgement does not prove Job creation.

08.11. Request acceptance does not prove handler completion.

08.12. Handler execution does not prove adapter execution success unless the
       owning execution boundary reports that outcome.

08.13. RuntimeHost operation acceptance does not prove final work outcome.

08.14. Job creation, Job lifecycle, handler execution, adapter execution,
       RuntimeHost operation, and final work outcome remain distinct.

08.15. Concrete message schemas, transport protocols, and wire details are not
       defined in this document.


===============================================================================
09. IMPLEMENTATION INDEPENDENCE AND REPLACEABILITY
===============================================================================

09.01. Implementation choices are pragmatic and may change.

09.02. Turnix platform truth remains valid across implementation replacement
      when platform contracts and guarantees remain preserved.

09.03. Backend replacement does not change Turnix identity when platform
      contracts and guarantees remain preserved.

09.04. Frontend replacement does not change Turnix identity when creator-facing
      contract meaning and platform guarantees remain preserved.

09.05. RuntimeHost realization replacement does not change Turnix identity
      when workspace ownership, entry-surface, command-surface, lifecycle,
      trace, and authority boundary semantics remain preserved.

09.06. Adapter replacement does not change Turnix identity when boundary
      semantics and contract truth remain preserved.

09.07. Transport replacement does not change Turnix identity when logical
      boundary semantics and contract truth remain preserved.

09.08. Payload storage replacement does not change Turnix identity when owning
      representation contracts remain preserved.

09.09. Configuration layout replacement does not change Turnix identity when
      owning configuration contracts remain preserved.

09.10. Persistent I/O backend replacement does not change Turnix identity when
       owning persistence contracts remain preserved.

09.11. Frontend runtime replacement does not change Turnix identity when UI
       and View contracts remain preserved.

09.12. Debugger surface replacement does not change Turnix identity when
       debugger contracts remain preserved.

09.13. Artifact format or export format replacement does not change Turnix
       identity when owning artifact and export contracts remain preserved.

09.14. Comparison, Replay, Resume, Retry, or retained-evidence tooling
       replacement does not change Turnix identity when owning workflow
       contracts remain preserved.

09.15. First-party management tooling replacement does not change Turnix
       identity when owning contracts remain preserved.

09.16. A replaceable implementation layer does not by itself possess authority
       to redefine platform meaning.

09.17. Implementation independence is not an aesthetic goal.

09.18. Implementation independence is a consequence of contract primacy and
       architectural truth.

09.19. If platform truth does not survive implementation replacement, the
       architecture relied too heavily on implementation accident.


===============================================================================
10. OWNERSHIP STOP-LINES FOR NEIGHBORING DOMAINS
===============================================================================

10.01. DA-02 may name neighboring domains to protect implementation
      independence.

10.02. DA-02 does not define detailed behavior for neighboring domains.

10.03. DA-03 owns trace substrate, retention, loss, trace event structure, and
      span semantics.

10.04. DA-04 owns committed-state truth, transactions, and commit boundaries.

10.05. DA-05 owns payload identity, Chunk, ChunkId, ValueRef, decode,
      integrity, and retained-root reachability.

10.06. DA-06 owns configuration, schema, materialization, migration, and
      policy storage placement.

10.07. DA-07 owns IoManager, persistent-I/O authority, Reader and Writer
      providers, root boundaries, and persistence safety.

10.08. DA-08 owns Window, SafePointWindow, ActiveWindow, AbortedWindow, and
      finalized runtime history semantics.

10.09. DA-09 owns root and discovery semantics.

10.10. Discovery is candidate production.

10.11. Discovery is not resolution, activation, import, runtime loading, or
       runtime identity.

10.12. DA-10 owns pack identity, hierarchy, and visibility semantics.

10.13. DA-11 owns generic resolution semantics.

10.14. DA-12 owns importing, module loading, and code-boundary semantics.

10.15. DA-13 owns dependency, requirement, and dependency-graph semantics.

10.16. DA-14 owns activation lifecycle and execution guarantees.

10.17. DA-16 owns Services, Capabilities, and Permissions.

10.18. DA-17 owns user decision and remembered policy semantics.

10.19. DA-18 owns debugger, inspection, breakpoint, manual-pause,
       safe-point, and debugger mutation semantics.

10.20. DA-19 owns Job lifecycle, timeout, cancellation, progress, result, and
       terminal outcome semantics.

10.21. DA-20 owns Application and ApplicationRun lifecycle and runtime
       identity semantics.

10.22. DA-21 owns RPC, channel, and transport semantics.

10.23. DA-22 owns UI, View, frontend runtime, and frontend presentation
       semantics.

10.24. DA-23 and DA-27 own ExecutionAdapter boundaries, same-language
       execution, same-process execution, direct-call optimization, adapter
       lifecycle, trust, and isolation semantics.

10.25. DA-24 owns OrchestrationUnit mutation-authority semantics.

10.26. DA-25 owns Window artifact, WindowExport, retained-evidence bundle,
       optional digest, and offline-inspection artifact semantics.

10.27. DA-26 owns comparison, ComparisonResult, Replay, Resume, Retry, and
       retained-evidence workflow semantics.

10.28. DA-28 owns RuntimeHost, workspace ownership, startup mode, command
       surface, local-first, and LAN exposure semantics.

10.29. DA-29 owns PackManager semantics.

10.30. DA-30 owns ModCallContext facade semantics where Pack invocation
       context is in scope.


===============================================================================
11. EXPLICIT EXCLUSIONS AND NON-GOALS
===============================================================================

11.01. This design area does not treat the current backend language as the
      identity of Turnix.

11.02. This design area does not treat the current frontend stack as the
      identity of Turnix.

11.03. This design area does not treat native host-language convention as
      superior to Turnix contracts or guarantees.

11.04. This design area does not treat interoperability envelopes as mere
      incidental wiring.

11.05. This design area does not treat modularity as permission to weaken
      platform guarantees or boundary discipline.

11.06. This design area does not define exact loader, adapter, protocol,
      RuntimeHost, workspace ownership, command-surface, or transport
      mechanics.

11.07. This design area does not treat FastAPI, WebSocket, browser JavaScript,
      Python, CLI, subprocesses, containers, network topology, launcher
      surfaces, or LAN clients as platform identity.

11.08. This design area does not treat direct calls as authority-valid merely
      because they are convenient.

11.09. This design area does not treat RuntimeHost realization as Kernel
      authority by itself.

11.10. This design area does not treat AppDefinition/AppPack, Application, or
       ApplicationRun identity as platform identity by itself.

11.11. This design area does not decide whether every ApplicationRun is
       necessarily AppDefinition/AppPack-backed.

11.12. Runtime identity creation rules belong to the owning lifecycle and
       runtime-creation specifications.

11.13. This design area does not define SaveBundle persistence closure
       semantics.

11.14. This design area does not define payload representation,
       configuration layout, persistent I/O provider behavior, UI rendering,
       debugger behavior, artifact packaging, export behavior, comparison,
       Replay, Resume, Retry, or retained-evidence workflows.

11.15. This design area does not define detailed PackManager, discovery,
       resolution, importing, activation, service, capability, Job,
       OrchestrationUnit, ExecutionAdapter, RuntimeHost, UI, View, debugger,
       Application, ApplicationRun, AppDefinition/AppPack, or SaveBundle
       mechanics.


===============================================================================
12. WHY THIS AREA EXISTS
===============================================================================

12.01. This area exists to prevent Turnix architecture from collapsing into
      current implementation choices, framework assumptions, host-language
      accident, or official-tooling convenience.

12.02. Without this area, specifications risk treating current technical
      realization as platform identity.

12.03. Without this area, specifications also risk weakening:
      - contract truth
      - Kernel authority meaning
      - RuntimeHost boundary meaning
      - adapter accountability
      - service and capability separation
      - ModCallContext scope
      - interoperability boundary meaning
      - first-party modularity discipline
      - implementation independence

12.04. This document anchors the architectural distinction between platform
      truth and implementation realization.
