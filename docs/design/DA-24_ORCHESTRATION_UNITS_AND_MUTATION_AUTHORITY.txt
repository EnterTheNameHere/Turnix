===============================================================================
DESIGN AREA DA-24 - ORCHESTRATION UNITS AND MUTATION AUTHORITY
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines OrchestrationUnits as kernel-tracked execution-authority units,
their mutation boundary, terminal outcomes, relationship to transactions,
Jobs, Windows, ApplicationRuns, RPC, capabilities, execution adapters,
RuntimeHost operations, PackManager-triggered work, and the single-lane
ApplicationRun mutation rule.

This document owns OrchestrationUnit lifecycle and mutation-authority
semantics. It consumes the memory, state, and transaction model defined by
DA-04.

Purpose:
--------
This document defines how Turnix identifies and controls execution that may
mutate Turnix-managed state.

It defines:
- OrchestrationUnit meaning and identity role
- mutation authority boundaries for OrchestrationUnits
- relationship between OrchestrationUnits, transactions, and committed state
- relationship between OrchestrationUnits and Jobs
- relationship between OrchestrationUnits and Windows
- relationship between OrchestrationUnits and ApplicationRuns
- relationship between OrchestrationUnits, capabilities, RPC, and execution
  adapters
- relationship between OrchestrationUnits and RuntimeHost operations
- relationship between OrchestrationUnits and PackManager-triggered work
- OrchestrationUnit terminal outcomes
- Superseded outcome semantics
- deterministic single-lane ApplicationRun mutation orchestration
- OrchestrationUnit trace reason ownership
- adapter-executed mutation re-entry boundaries
- RuntimeHost-operation mutation re-entry boundaries

It does NOT define:
- memory, state, transaction, or commit mechanics (see DA-04)
- committed-value representation, ValueRef, Chunk, ChunkId, payload identity,
  decode, or integrity semantics (see DA-05)
- configuration semantics, configuration storage layout, configuration
  migration, or policy-file placement (see DA-06)
- persistent-I/O authority, root boundaries, Reader/Writer providers,
  backup/snapshot behavior, or streaming I/O rules (see DA-07)
- trace event structure, trace DAG semantics, trace retention, trace loss, or
  span mechanics (see DA-03)
- Window finalization semantics (see DA-08)
- Window artifact, WindowExport, Minimal Audit Bundle, optional digest,
  partial export, missing-material, or offline inspection semantics
  (see DA-25)
- comparison, Replay, Resume, Retry, or audit workflow semantics (see DA-26)
- service, capability, or permission semantics (see DA-16)
- user decision and remembered policy semantics (see DA-17)
- debugger pause, breakpoint, or execution-control behavior (see DA-18)
- Job lifecycle, Job timeout, Job cancellation, or Job result semantics
  (see DA-19)
- Application or ApplicationRun lifecycle or runtime identity semantics
  (see DA-20)
- RPC, channel, or transport semantics (see DA-21)
- UI, View, or frontend runtime semantics (see DA-22)
- execution adapter boundary semantics (see DA-23)
- adapter lifecycle, trust, isolation, failure, disconnect, or adapter-domain
  trace semantics (see DA-27)
- RuntimeHost identity, workspace ownership, startup modes, entry surfaces,
  command-surface semantics, or RuntimeHost trace reason identifiers
  (see DA-28)
- PackManager catalog, management, or graph-preparation semantics (see DA-29)
- SaveBundle storage, retained material, durable Application persistence
  closure, compatibility, or recovery details

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines OrchestrationUnit lifecycle and mutation-
      authority semantics within that shared interpretation model.

01.5. This document uses OrchestrationUnit, ApplicationRun, and SaveBundle as
      canonical architecture type names where those concepts are named.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. This design area answers:

          "Which kernel-tracked execution unit may mutate Turnix-managed
           state, and how does that execution remain bounded by
           orchestration, transaction, capability, adapter, RuntimeHost,
           Job, and Window semantics?"

02.2. An OrchestrationUnit is a kernel-tracked execution unit that may be
      permitted to mutate Turnix-managed state within an ApplicationRun.

02.3. An OrchestrationUnit is an execution-authority unit.

02.4. OrchestrationUnit authority is scoped authority to own or coordinate a
      mutation flow.

02.5. OrchestrationUnit authority is not general backend authority.

02.6. OrchestrationUnit authority is not direct committed-state authority for
      arbitrary contained code.

02.7. OrchestrationUnit authority does not replace DA-04 transaction and
      commit boundaries.

02.8. OrchestrationUnit authority is scoped by:
      - ApplicationRun identity
      - capability and permission boundaries when applicable
      - transaction and commit boundaries when mutation occurs
      - adapter boundaries when work originates from adapter-executed code
      - RuntimeHost boundaries when work originates from runtime-host
        operations or command surfaces
      - policy and decision boundaries when applicable
      - persistent-I/O boundaries when persistence is involved

02.9. Work started outside Turnix orchestration is not an OrchestrationUnit
      until it re-enters through orchestration boundaries.

02.10. Turnix guarantees apply only to work that occurs within Turnix
       orchestration boundaries or re-enters through them.

02.11. Mutation outside orchestration does not acquire Turnix guarantees by
       implication.

02.12. Same-language or same-process execution does not bypass
       OrchestrationUnit authority rules.

02.13. RuntimeHost startup modes, entry surfaces, and command surfaces do
       not bypass OrchestrationUnit authority rules when they perform or may
       perform mutation-bearing work.

02.14. PackManager-triggered graph or lifecycle operations do not bypass
       OrchestrationUnit authority rules when they perform or may perform
       mutation-bearing work.

02.15. OrchestrationUnit outcome does not define Replay, Resume, Retry,
       ComparisonResult, artifact/export authority, or audit workflow outcome.

02.16. Payload, configuration, migration, persistent I/O, SaveBundle storage,
       durable persistence, and recovery implications remain owned by their
       own documents and domains.

02.17. Later sections of this document refine and apply these rules.
       They do not weaken them.


===============================================================================
03. ORCHESTRATIONUNIT IDENTITY AND SCOPE
===============================================================================

03.1. orchestrationUnitId identifies one OrchestrationUnit.

03.2. orchestrationUnitId is distinct from:
      - applicationId
      - applicationRunId
      - jobId
      - transactionId
      - viewId
      - adapter identity
      - runtimeHostId
      - RuntimeHost operation identity
      - PackManager operation identity
      - RPC message identity
      - capability identity

03.3. An OrchestrationUnit has one owning ApplicationRun when it mutates or
      may mutate ApplicationRun state.

03.4. An OrchestrationUnit may be created for non-mutating orchestrated work
      when the owning workflow requires lifecycle, trace, or policy
      boundaries.

03.5. An OrchestrationUnit may have a parent or cause relation to:
      - capability invocation
      - RPC message
      - Job
      - debugger action
      - user decision
      - adapter-mediated request
      - RuntimeHost operation
      - RuntimeHost command-surface request
      - PackManager operation
      - ApplicationRun lifecycle operation

03.6. Such relation is correlation and ownership evidence. It does not
      collapse those identities into the OrchestrationUnit identity.

03.7. OrchestrationUnit identity is used for lifecycle and causal trace
      evidence.

03.8. OrchestrationUnit identity does not define committed-state identity.

03.9. OrchestrationUnit identity does not define RuntimeHost identity or
      RuntimeHost operation identity.

03.10. OrchestrationUnit identity does not define PackManager operation
       identity.


===============================================================================
04. MUTATION AUTHORITY BOUNDARY
===============================================================================

04.1. An OrchestrationUnit may mutate Turnix-managed state only through the
      state and transaction rules defined by DA-04.

04.2. A mutation-bearing OrchestrationUnit may open or enter a transaction.

04.3. A non-mutating OrchestrationUnit does not require a transaction.

04.4. Staged mutation inside an OrchestrationUnit is not authoritative merely
      because the OrchestrationUnit exists.

04.5. Staged mutation becomes authoritative only by commit under DA-04.

04.6. An OrchestrationUnit outcome does not by itself define transaction
      commit or abort.

04.7. A transaction commit or abort does not by itself define the
      OrchestrationUnit outcome.

04.8. An OrchestrationUnit outcome does not convert already committed
      authoritative mutation into uncommitted mutation.

04.9. If committed state must be changed after an OrchestrationUnit is
      cancelled, failed, or superseded, that change is a later authoritative
      mutation.

04.10. OrchestrationUnit authority does not bypass capability permission,
       policy decisions, adapter boundaries, RuntimeHost boundaries,
       ApplicationRun lifecycle, persistent-I/O authority, or SaveBundle
       persistence boundaries.

04.11. Direct backend implementation code may create and run
       OrchestrationUnits only through Kernel-owned orchestration paths.

04.12. Pack-provided code does not create OrchestrationUnit authority by
       direct backend import, direct state mutation, or direct filesystem
       access.

04.13. RuntimeHost implementation code does not create OrchestrationUnit
       authority by host-local mutation, command-surface convenience, or
       workspace access outside Kernel-owned orchestration paths.

04.14. RuntimeHost operations that seek Turnix mutation guarantees re-enter
       through orchestration, capability, transaction, policy, persistence,
       and commit boundaries before mutation becomes authoritative.

04.15. PackManager-triggered work that seeks Turnix mutation guarantees
       re-enters through orchestration, capability, transaction, policy,
       persistence, and commit boundaries before mutation becomes
       authoritative.

04.16. OrchestrationUnit may coordinate mutation-bearing work that affects
       committed values, configuration, migration, or persisted material.

04.17. DA-24 defines OrchestrationUnit mutation-authority coordination.

04.18. DA-05 defines committed-value representation.

04.19. DA-06 defines configuration semantics and migration meaning where
       configuration is involved.

04.20. DA-07 defines persistent-I/O authority.

04.21. SaveBundle storage, retained material, durable Application persistence
       closure, compatibility, and recovery details remain outside this
       document's authority.

04.22. OrchestrationUnit existence, execution, completion, failure,
       cancellation, supersession, suspension, or trace evidence does not
       bypass the domains named in this section.


===============================================================================
05. EXAMPLE ORCHESTRATIONUNIT KINDS
===============================================================================

05.1. Example OrchestrationUnits include:
      - a pipeline run, including its stage callbacks
      - a capability handler invocation
      - an adapter-mediated capability handler invocation
      - a RuntimeHost operation that may mutate Turnix-managed state
      - a RuntimeHost command-surface request that may mutate Turnix-managed
        state
      - a PackManager-triggered graph or lifecycle operation that may mutate
        Turnix-managed state
      - a tooling-initiated mutation transaction
      - configuration mutation request processing
      - ApplicationRun lifecycle work that may mutate state
      - migration work that changes authoritative state
      - artifact/export work that requires mutation authority
      - comparison, Replay, Resume, Retry, or audit workflow work only where
        the owning workflow explicitly requires OrchestrationUnit lifecycle,
        trace, policy, or mutation boundaries

05.2. Example kinds do not lock the complete future OrchestrationUnit catalog.

05.3. The document or workflow that owns a concrete OrchestrationUnit class
      may define narrower behavior compatible with this document.

05.4. A concrete OrchestrationUnit class does not weaken the general
      mutation-authority boundary defined here.

05.5. A RuntimeHost operation being listed as an example OrchestrationUnit
      cause does not make every RuntimeHost operation an OrchestrationUnit.

05.6. A PackManager operation being listed as an example OrchestrationUnit
      cause does not make every PackManager operation an OrchestrationUnit.


===============================================================================
06. RELATION TO TRANSACTIONS
===============================================================================

06.1. A transaction is a mutation staging and commit boundary under DA-04.

06.2. An OrchestrationUnit is an execution-authority unit.

06.3. OrchestrationUnits and transactions are related but distinct.

06.4. An OrchestrationUnit may open, commit, or abort transactions under
      DA-04.

06.5. A Completed OrchestrationUnit may commit a transaction when the unit
      produced authoritative mutation.

06.6. A Completed OrchestrationUnit may produce no authoritative mutation.

06.7. A Completed OrchestrationUnit may abort or discard transactional
      staging when successful execution required no authoritative mutation.

06.8. A Failed OrchestrationUnit aborts or discards open transactional
      staging according to transaction rules.

06.9. A Cancelled OrchestrationUnit aborts or discards open transactional
      staging according to transaction rules.

06.10. A Superseded OrchestrationUnit aborts or discards open transactional
       staging according to transaction rules.

06.11. Child transaction propagation remains governed by DA-04.

06.12. Authoritative commit conflict detection remains governed by DA-04.

06.13. Transaction trace evidence remains distinct from OrchestrationUnit
       trace evidence.


===============================================================================
07. RELATION TO JOBS
===============================================================================

07.1. A Job is an observable lifecycle handle.

07.2. An OrchestrationUnit is an execution-authority unit.

07.3. A transaction is a mutation staging and commit boundary.

07.4. OrchestrationUnits, Jobs, and transactions remain distinct.

07.5. An OrchestrationUnit may be associated with a Job.

07.6. An OrchestrationUnit may execute without being associated with a Job.

07.7. A Job may coordinate more than one OrchestrationUnit only when the
      Job-owning or workflow-owning design explicitly defines that
      coordination.

07.8. An OrchestrationUnit outcome does not by itself define Job terminal
      outcome.

07.9. A Job terminal outcome does not by itself define OrchestrationUnit
      outcome.

07.10. RuntimeHost operation outcome does not by itself define Job terminal
       outcome.

07.11. PackManager operation outcome does not by itself define Job terminal
       outcome.

07.12. Job timeout is not OrchestrationUnit Superseded.

07.13. Job cancellation is not OrchestrationUnit cancellation unless the
       owning workflow maps the request to an OrchestrationUnit outcome.

07.14. DA-19 owns Job lifecycle, Job timeout, Job cancellation, progress,
       retained result, and late completion semantics.

07.15. OrchestrationUnit outcome does not define retained-result retrieval,
       artifact/export material, Replay, Resume, Retry, or audit workflow
       outcome.


===============================================================================
08. RELATION TO WINDOWS AND WINDOW-DERIVED ARTIFACTS
===============================================================================

08.1. OrchestrationUnit outcomes occur inside the current active runtime
      region when an ApplicationRun active region exists.

08.2. Transaction commit or abort evidence may contribute to later Window
      evidence.

08.3. OrchestrationUnit outcome evidence may contribute to later Window
      evidence.

08.4. OrchestrationUnit evidence may contribute to later audit material.

08.5. OrchestrationUnit Completed does not mean a SafePointWindow was
      created.

08.6. OrchestrationUnit Failed, Cancelled, or Superseded does not mean an
      AbortedWindow was created.

08.7. RuntimeHost operation outcome does not by itself create a
      SafePointWindow or AbortedWindow.

08.8. PackManager operation outcome does not by itself create a
      SafePointWindow or AbortedWindow.

08.9. SafePointWindow and AbortedWindow finalization remain owned by DA-08.

08.10. Retained OrchestrationUnit evidence inside finalized Window evidence
       remains non-authoritative evidence unless it is also committed state
       under DA-04.

08.11. OrchestrationUnit evidence does not by itself define Window artifact,
       WindowExport, Minimal Audit Bundle, digest, partial export, missing
       material, ComparisonResult, Replay outcome, Resume outcome, Retry
       outcome, or audit workflow outcome.

08.12. OrchestrationUnit terminal outcome does not by itself create
       artifact/export authority.

08.13. OrchestrationUnit Completed does not by itself mean artifact/export
       completed.

08.14. DA-25 owns artifact/export semantics.

08.15. DA-26 owns comparison, Replay, Resume, Retry, and audit workflow
       semantics.


===============================================================================
09. RELATION TO APPLICATIONRUNS
===============================================================================

09.1. ApplicationRun lifecycle and runtime identity are defined by DA-20.

09.2. An OrchestrationUnit that mutates ApplicationRun state operates inside
      the owning ApplicationRun authority context.

09.3. applicationRunId is distinct from orchestrationUnitId.

09.4. Application identity is distinct from OrchestrationUnit identity.

09.5. ApplicationRun lifecycle outcome does not by itself define
      OrchestrationUnit terminal outcome.

09.6. OrchestrationUnit terminal outcome does not by itself define
      ApplicationRun lifecycle outcome.

09.7. ApplicationRun active-region boundaries provide runtime containment for
      OrchestrationUnit execution.

09.8. ApplicationRun active-region end does not silently convert open
      OrchestrationUnits into successful completed work.

09.9. If ApplicationRun lifecycle affects active OrchestrationUnits, that
      effect is explicit and trace-visible.

09.10. RuntimeHost operations that create, start, stop, bind, migrate, or
       recover ApplicationRun state use ApplicationRun lifecycle semantics
       from DA-20 and OrchestrationUnit mutation authority from this document
       when mutation-bearing work is involved.

09.11. SaveBundle loading, persistence, recovery, and retained-material
       handling do not by themselves define OrchestrationUnit terminal
       outcome.


===============================================================================
10. RELATION TO CAPABILITIES AND RPC
===============================================================================

10.1. Capability semantics are defined by DA-16.

10.2. RPC, channel, and transport semantics are defined by DA-21.

10.3. A capability invocation may create or enter an OrchestrationUnit when
      the invocation performs orchestrated work.

10.4. An RPC message may cause a capability invocation that creates or enters
      an OrchestrationUnit.

10.5. A RuntimeHost command or operation may cause a capability invocation,
      RPC message, or Kernel-owned workflow that creates or enters an
      OrchestrationUnit.

10.6. A PackManager operation may cause a capability invocation, RPC message,
      or Kernel-owned workflow that creates or enters an OrchestrationUnit.

10.7. RPC message identity remains distinct from orchestrationUnitId.

10.8. Capability identity remains distinct from orchestrationUnitId.

10.9. RuntimeHost operation identity remains distinct from
      orchestrationUnitId.

10.10. PackManager operation identity remains distinct from
       orchestrationUnitId.

10.11. RPC transport acknowledgement does not imply OrchestrationUnit
       completion.

10.12. RPC transport timeout does not imply OrchestrationUnit failure,
       cancellation, or supersession.

10.13. RuntimeHost command acceptance does not imply OrchestrationUnit
       completion.

10.14. RuntimeHost operation completion does not by itself define
       OrchestrationUnit terminal outcome unless the owning workflow maps
       those outcomes explicitly.

10.15. PackManager operation completion does not by itself define
       OrchestrationUnit terminal outcome unless the owning workflow maps
       those outcomes explicitly.

10.16. Capability permission approval does not imply successful
       OrchestrationUnit completion.

10.17. Capability permission approval does not grant committed-state
       authority by itself.

10.18. Capability permission approval does not grant persistent-I/O authority
       by itself.

10.19. Capability permission approval does not grant artifact/export or
       workflow authority by itself.

10.20. OrchestrationUnit trace evidence may include parent capability,
       RPC message, RuntimeHost operation, and PackManager operation identity
       when available.

11. RELATION TO EXECUTION ADAPTERS
===============================================================================

11.1. Execution adapter boundary semantics are defined by DA-23.

11.2. Adapter lifecycle, trust, isolation, failure, disconnect, and adapter-
      domain trace semantics are defined by DA-27.

11.3. Adapter-executed code does not mutate committed state directly.

11.4. Adapter-executed mutation seeking Turnix guarantees re-enters through
      orchestration, capability, transaction, and commit boundaries before
      becoming authoritative.

11.5. Same-language or same-process execution does not bypass committed-state
      authority.

11.6. Same-language or same-process execution does not bypass
      OrchestrationUnit authority rules.

11.7. Direct in-process calls may carry a mutation request, but they do not
      become mutation authority by themselves.

11.8. Adapter readiness does not imply OrchestrationUnit completion.

11.9. Adapter failure does not by itself define OrchestrationUnit terminal
      outcome.

11.10. OrchestrationUnit failure does not by itself define adapter failure.

11.11. RuntimeHost entry-surface readiness does not imply OrchestrationUnit
       completion.

11.12. RuntimeHost operation failure does not by itself define adapter
       failure.

11.13. If adapter lifecycle affects an OrchestrationUnit, the relationship is
       explicit and trace-visible.

11.14. If an OrchestrationUnit affects adapter lifecycle, the relationship is
       explicit and trace-visible.

11.15. Adapter execution acceptance does not mean committed-value
       representation, configuration, persistence, artifact/export, or
       workflow success.

12.2. PackManager catalog, management, graph-preparation, and management-

      OrchestrationUnit trace evidence.

       OrchestrationUnit trace evidence.

12.11. OrchestrationUnit trace evidence does not replace RuntimeHost trace
       evidence or PackManager trace evidence.


===============================================================================
13. ORCHESTRATIONUNIT OUTCOMES
===============================================================================

13.1. An OrchestrationUnit reaches exactly one terminal outcome.

13.2. OrchestrationUnit terminal outcomes are:
      - Completed
      - Failed
      - Cancelled
      - Superseded

13.3. Completed means the OrchestrationUnit finished its execution path
      without ending as Failed, Cancelled, or Superseded.

13.4. Failed means the OrchestrationUnit ended because an unexpected or error
      outcome prevented successful completion.

13.5. Cancelled means the OrchestrationUnit ended because intentional
      cancellation stopped the unit before completion.

13.6. Superseded means the OrchestrationUnit ended because newer work, newer
      accepted input, or higher-priority work replaced it.

13.7. Superseded is not failure.

13.8. Superseded is not timeout.

13.9. Superseded does not roll back authoritative state that was already
      committed.

13.10. Completed may include:
       - committed authoritative mutation
       - no authoritative mutation
       - aborted or discarded transactional staging

13.11. Failed, Cancelled, and Superseded abort or discard open transactional
       staging according to DA-04.

13.12. RuntimeHost operation completion, failure, cancellation, detachment,
       retention, or supersession does not by itself define OrchestrationUnit
       terminal outcome unless the owning workflow maps those outcomes
       explicitly.

13.13. PackManager operation completion, failure, cancellation, retention, or
       supersession does not by itself define OrchestrationUnit terminal
       outcome unless the owning workflow maps those outcomes explicitly.

13.14. Artifact/export completion is not OrchestrationUnit completion by
       default.

13.15. ComparisonResult is not OrchestrationUnit outcome by default.

13.16. Replay outcome is not OrchestrationUnit outcome by default.

13.17. Resume outcome is not OrchestrationUnit outcome by default.

13.18. Retry outcome is not OrchestrationUnit outcome by default.

13.19. Audit workflow outcome is not OrchestrationUnit outcome by default.

13.20. The document or workflow that owns a concrete OrchestrationUnit class
       may define narrower outcome meanings that remain compatible with this
       section.

13.21. An OrchestrationUnit terminal outcome is trace-visible.


===============================================================================
14. SINGLE-LANE APPLICATIONRUN ORCHESTRATION
===============================================================================

14.1. Turnix uses a deterministic single-lane orchestration model within one
      ApplicationRun unless an explicit concurrency mode is defined elsewhere.

14.2. Within one ApplicationRun, Turnix does not execute multiple
      OrchestrationUnits concurrently when those units may mutate the same
      ApplicationRun state.

14.3. Awaited input/output, model calls, adapter calls, RuntimeHost calls,
      persistent I/O, export work, audit work, comparison work, or other I/O
      may suspend the current unit.

14.4. Suspension does not authorize another state-mutating unit to run
      concurrently in the same ApplicationRun unless an explicit concurrency
      mode permits that behavior.

14.5. Work started outside Turnix orchestration remains outside Turnix
      guarantees until it re-enters through orchestration boundaries.

14.6. Any mutation that seeks Turnix guarantees re-enters through
      orchestration boundaries before becoming authoritative.

14.7. Turnix does not imply concurrency safety merely because execution is
      asynchronous or suspended.

14.8. Turnix does not imply determinism for mutation paths that occur outside
      orchestration boundaries.

14.9. Adapter suspension, adapter disconnect, transport behavior, frontend
      behavior, RuntimeHost command-surface behavior, or RuntimeHost
      entry-surface behavior does not authorize concurrent state-mutating
      orchestration within the same ApplicationRun.

14.10. Adapter-mediated mutation follows the same single-lane ApplicationRun
       orchestration rule unless an explicit concurrency mode defines
       otherwise.

14.11. RuntimeHost-operation-mediated mutation follows the same single-lane
       ApplicationRun orchestration rule unless an explicit concurrency mode
       defines otherwise.

14.12. PackManager-operation-mediated mutation follows the same single-lane
       ApplicationRun orchestration rule unless an explicit concurrency mode
       defines otherwise.

14.13. Future concurrency modes must define:
       - mutation conflict boundaries
       - transaction interaction
       - ordering rules
       - trace obligations
       - persistence and recovery implications
       - artifact/export interaction if artifacts or exports are affected
       - Replay, Resume, Retry, and audit workflow interaction if those
         workflows are affected


===============================================================================
15. ORCHESTRATIONUNIT TRACE REASON IDENTIFIERS
===============================================================================

15.1. DA-24 owns the OrchestrationUnit trace reason identifiers used for
      OrchestrationUnit lifecycle, transaction association, and decision
      waiting inside state-mutating orchestration.

15.2. OrchestrationUnit-domain trace evidence is required as an emission
      obligation where OrchestrationUnit lifecycle, transaction association,
      and decision waiting events occur.

15.3. Trace representation, retention, pruning, and loss remain governed by
      DA-03.

15.4. The following OrchestrationUnit trace reasons are defined:

      - OrchestrationUnitCreated
      - OrchestrationUnitStarted
      - OrchestrationUnitCompleted
      - OrchestrationUnitFailed
      - OrchestrationUnitCancelled
      - OrchestrationUnitSuperseded
      - OrchestrationUnitTransactionOpened
      - OrchestrationUnitTransactionCommitted
      - OrchestrationUnitTransactionAborted
      - OrchestrationUnitDecisionPending
      - OrchestrationUnitDecisionResolved

15.5. OrchestrationUnitCreated is emitted when an OrchestrationUnit is
      created.

15.6. OrchestrationUnitStarted is emitted when OrchestrationUnit execution
      begins.

15.7. OrchestrationUnitCompleted is emitted when an OrchestrationUnit reaches
      the Completed terminal outcome.

15.8. OrchestrationUnitFailed is emitted when an OrchestrationUnit reaches the
      Failed terminal outcome.

15.9. OrchestrationUnitCancelled is emitted when an OrchestrationUnit reaches
      the Cancelled terminal outcome.

15.10. OrchestrationUnitSuperseded is emitted when an OrchestrationUnit
       reaches the Superseded terminal outcome.

15.11. OrchestrationUnitTransactionOpened is emitted when an
       OrchestrationUnit opens or enters a transaction.

15.12. OrchestrationUnitTransactionCommitted is emitted when a transaction
       associated with an OrchestrationUnit commits.

15.13. OrchestrationUnitTransactionAborted is emitted when a transaction
       associated with an OrchestrationUnit aborts or is discarded.

15.14. OrchestrationUnitDecisionPending is emitted when an OrchestrationUnit
       is waiting on a decision point that can affect its execution or
       mutation outcome.

15.15. OrchestrationUnitDecisionResolved is emitted when such a decision
       point resolves.

15.16. DA-03 defines the tracing substrate used to represent
       OrchestrationUnit trace evidence.


===============================================================================
16. ORCHESTRATIONUNIT TRACE CONTEXT
===============================================================================

16.1. OrchestrationUnit trace evidence records enough context, when available,
      to explain:
      - orchestrationUnitId
      - applicationId when applicable
      - applicationRunId when applicable
      - runtimeHostId when applicable
      - RuntimeHost operation identity when applicable
      - PackManager operation identity when applicable
      - owner or caller identity when available
      - work kind
      - parent jobId when applicable
      - parent capability identifier when applicable
      - parent RPC message identity when applicable
      - adapter identity when applicable
      - viewId when applicable
      - transactionId when applicable
      - terminal outcome when the unit reaches one
      - supersession source when applicable
      - failure reason category when applicable
      - cancellation reason category when applicable

16.2. Transaction association trace evidence records enough context, when
      available, to explain:
      - orchestrationUnitId
      - transactionId
      - applicationRunId
      - runtimeHostId when applicable
      - transaction operation
      - commit or abort outcome when applicable

16.3. Decision waiting trace evidence records enough context, when available,
      to explain:
      - orchestrationUnitId
      - decision identity
      - policy scope when applicable
      - effect on execution or mutation outcome when known

16.4. OrchestrationUnit trace evidence does not replace transaction trace
      evidence owned by DA-04.

16.5. OrchestrationUnit trace evidence does not replace payload or committed-
      value evidence owned by DA-05.

16.6. OrchestrationUnit trace evidence does not replace configuration or
      migration evidence owned by DA-06.

16.7. OrchestrationUnit trace evidence does not replace persistent-I/O
      evidence owned by DA-07.

16.8. OrchestrationUnit trace evidence does not replace Window trace or
      evidence owned by DA-08.

16.9. OrchestrationUnit trace evidence does not replace capability trace
      evidence owned by DA-16.

16.10. OrchestrationUnit trace evidence does not replace decision or policy
       trace evidence owned by DA-17.

16.11. OrchestrationUnit trace evidence does not replace Job trace evidence
       owned by DA-19.

16.12. OrchestrationUnit trace evidence does not replace Application or
       ApplicationRun trace evidence owned by DA-20.

16.13. OrchestrationUnit trace evidence does not replace RPC trace evidence
       owned by DA-21.

16.14. OrchestrationUnit trace evidence does not replace adapter trace
       evidence owned by DA-23 or DA-27.

16.15. OrchestrationUnit trace evidence does not replace artifact/export trace
       evidence owned by DA-25.

16.16. OrchestrationUnit trace evidence does not replace comparison, Replay,
       Resume, Retry, or audit workflow evidence owned by DA-26.

16.17. OrchestrationUnit trace evidence does not replace RuntimeHost trace
       evidence owned by DA-28.

16.18. OrchestrationUnit trace evidence does not replace PackManager trace
       evidence owned by DA-29.

16.19. Trace loss weakens evidential completeness. Trace loss does not by
       itself change committed-state correctness.


===============================================================================
17. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

17.1. The following are not supported:
      - mutation outside orchestration acquiring Turnix guarantees by
        implication
      - pack-provided code directly mutating committed state
      - adapter-executed code directly mutating committed state
      - RuntimeHost implementation code directly mutating committed state
        outside Kernel-owned orchestration paths
      - PackManager-triggered work directly mutating committed state outside
        Kernel-owned orchestration paths
      - same-language execution bypassing OrchestrationUnit boundaries
      - same-process execution bypassing OrchestrationUnit boundaries
      - RuntimeHost command surfaces bypassing OrchestrationUnit boundaries
      - RuntimeHost startup modes creating independent mutation semantics
      - PackManager management surfaces creating independent mutation semantics
      - RPC acknowledgement treated as OrchestrationUnit completion
      - RuntimeHost command acceptance treated as OrchestrationUnit completion
      - PackManager command acceptance treated as OrchestrationUnit completion
      - transport timeout treated as OrchestrationUnit failure
      - adapter failure treated as OrchestrationUnit failure by default
      - RuntimeHost operation failure treated as OrchestrationUnit failure by
        default
      - PackManager operation failure treated as OrchestrationUnit failure by
        default
      - Job terminal outcome treated as OrchestrationUnit terminal outcome by
        default
      - OrchestrationUnit terminal outcome treated as Job terminal outcome by
        default
      - OrchestrationUnit completion treated as SafePointWindow creation
      - OrchestrationUnit failure treated as AbortedWindow creation
      - OrchestrationUnit completion treated as artifact/export completion
      - artifact/export completion treated as OrchestrationUnit completion
      - ComparisonResult treated as OrchestrationUnit outcome
      - Replay outcome treated as OrchestrationUnit outcome
      - Resume outcome treated as OrchestrationUnit outcome
      - Retry outcome treated as OrchestrationUnit outcome
      - audit workflow outcome treated as OrchestrationUnit outcome
      - concurrent state-mutating OrchestrationUnits inside one ApplicationRun
        unless an explicit concurrency mode defines that behavior

===============================================================================
19. LOCKED SUMMARY
===============================================================================

19.1. LOCKED:
      - OrchestrationUnit is a kernel-tracked execution-authority unit
      - OrchestrationUnit authority is scoped authority to own or coordinate a
        mutation flow
      - OrchestrationUnit authority is not general backend authority
      - OrchestrationUnit authority is not direct committed-state authority for
        arbitrary contained code
      - OrchestrationUnit identity is distinct from Application,
        ApplicationRun, Job, transaction, View, adapter, RuntimeHost,
        PackManager, RPC message, and capability identity
      - mutation outside orchestration does not acquire Turnix guarantees by
        implication
      - OrchestrationUnit authority does not bypass DA-04 transaction and
        commit rules
      - OrchestrationUnit authority does not bypass DA-05 committed-value
        representation
      - OrchestrationUnit authority does not bypass DA-06 configuration
        semantics
      - OrchestrationUnit authority does not bypass DA-07 persistent-I/O
        authority
      - OrchestrationUnits, Jobs, and transactions remain distinct
      - OrchestrationUnit outcome does not by itself define Job terminal
        outcome, transaction outcome, ApplicationRun outcome, adapter outcome,
        RuntimeHost outcome, PackManager outcome, or Window finalization
      - OrchestrationUnit outcome does not by itself define artifact/export,
        ComparisonResult, Replay, Resume, Retry, or audit workflow outcome
      - transaction commit or abort does not by itself define OrchestrationUnit
        outcome
      - RuntimeHost command acceptance does not by itself define
        OrchestrationUnit completion
      - RuntimeHost operation outcome does not by itself define
        OrchestrationUnit terminal outcome unless the owning workflow maps
        those outcomes explicitly
      - PackManager operation outcome does not by itself define
        OrchestrationUnit terminal outcome unless the owning workflow maps
        those outcomes explicitly
      - OrchestrationUnit terminal outcomes are Completed, Failed, Cancelled,
        and Superseded
      - Superseded is not failure
      - Superseded is not timeout
      - Superseded does not roll back authoritative state that was already
        committed
      - adapter-executed code does not directly mutate committed state
      - RuntimeHost implementation code does not directly mutate committed
        state outside Kernel-owned orchestration paths
      - PackManager-triggered work does not directly mutate committed state
        outside Kernel-owned orchestration paths
      - adapter-executed mutation seeking Turnix guarantees re-enters through
        orchestration, capability, transaction, and commit boundaries
      - RuntimeHost-operation mutation seeking Turnix guarantees re-enters
        through orchestration, capability, transaction, policy, persistence,
        and commit boundaries
      - PackManager-operation mutation seeking Turnix guarantees re-enters
        through orchestration, capability, transaction, policy, persistence,
        and commit boundaries
      - same-language or same-process execution does not bypass committed-
        state authority
      - same-language or same-process execution does not bypass
        OrchestrationUnit authority rules
      - ApplicationRun mutation follows deterministic single-lane orchestration
        unless another mode is explicitly defined elsewhere
      - adapter suspension, adapter disconnect, transport behavior, frontend
        behavior, RuntimeHost command-surface behavior, RuntimeHost
        entry-surface behavior, or PackManager command-surface behavior does
        not authorize concurrent state-mutating orchestration within the same
        ApplicationRun
      - DA-24 owns OrchestrationUnit trace reason identifiers
      - DA-28 owns RuntimeHost-domain trace reason identifiers
      - DA-29 owns PackManager-domain trace reason identifiers
      - DA-03 owns the trace substrate, not OrchestrationUnit lifecycle
        semantics

19.2. OPEN:
      - exact concrete OrchestrationUnit envelope, API names, creation API,
        parent relation representation, and concurrency-mode taxonomy
