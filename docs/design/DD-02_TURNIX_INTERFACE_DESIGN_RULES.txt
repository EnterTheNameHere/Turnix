===============================================================================
DESIGN DOCTRINE DD-02 - TURNIX INTERFACE DESIGN RULES
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines interface design rules for Turnix APIs, boundaries, semantic
structures, helper usage, and surfaced runtime outcomes.

Purpose:
--------
This document defines how Turnix interfaces communicate meaning, reduce
accidental misuse, preserve platform integrity, and avoid implicit inference
burdens without unnecessarily restricting creators.

It defines:
- interface responsibility
- misuse resistance
- execution containment boundaries
- failure translation
- surfaced failure structure
- semantic naming expectations
- canonical helper reuse
- validated semantic structures
- observed data and effective values
- incomplete and partial state handling
- explicit integration of fragmented interface meaning

It does NOT define:
- specific pack APIs
- specific capability schemas
- frontend protocol details
- exact error taxonomies
- tracing data structures
- concrete validation framework requirements
- concrete retry or recovery policies
- concrete rendering policies

Upstream Documents:
------------------
- CMR-01
- CMR-02
- CMR-03
- CMR-04
- CMR-05


===============================================================================
01. INTERFACE RESPONSIBILITY
===============================================================================

01.1. If a Turnix interface is likely to be used incorrectly by a competent
      creator, the interface design requires review.

01.2. Turnix interface design makes the intended path explicit.

01.3. Turnix interface design makes common failure modes visible.

01.4. Turnix interface design reduces accidental misuse where doing so does
      not compromise creator freedom.

01.5. Turnix does not assume that documentation alone compensates for a
      weak interface.

01.6. Documentation may explain constraints, but when misuse is probable
      and detectable, interface design and runtime structure both matter.

01.7. Interface design includes the shape of values, result objects,
      failure outcomes, helper usage, and validation placement exposed by
      the interface.

01.8. An interface that requires callers to repeatedly reconstruct the same
      semantic meaning from raw fields is incomplete unless that burden is
      intentional and justified.


===============================================================================
02. ADULT INTERFACE MODEL
===============================================================================

02.1. Incorrect use is not automatically forbidden.

02.2. Turnix interfaces do not attempt to block every incorrect action by
      default.

02.3. Creators remain free to do unusual, risky, or unconventional things.

02.4. Turnix interface design focuses on:
      - reducing accidental misuse where practical
      - detecting important misuse where practical
      - preserving platform integrity always

02.5. This model assumes competent adult creators and does not treat
      default prohibition as the starting point.

02.6. Adult interface design does not mean leaving preventable ambiguity in
      place merely because a competent creator could eventually infer the
      intended meaning.

02.7. Creator freedom is better served by clear interfaces than by unclear
      interfaces that require guesswork, convention mining, or assistant-
      inferred intent.


===============================================================================
03. DOCUMENTED FAILURE MODES AS DETECTION OPPORTUNITIES
===============================================================================

03.1. When documentation states that a certain failure mode exists and must
      be handled, that statement creates a potential runtime-detection
      opportunity.

03.2. Example:
      - a mod calls a capability
      - capability permission is rejected
      - the mod does not handle the failure
      - the error escapes the mod boundary

03.3. If Turnix can identify that pattern reliably, Turnix may record it,
      report it, or surface it in post-run diagnostics.

03.4. Turnix does not introduce broad detection logic from vague hints.

03.5. Detection logic enters the platform only when the pattern is clear,
      the signal is reliable, and the handling is worth the added
      complexity.

03.6. Documented failure modes distinguish:
      - invalid use
      - refused use
      - partial success
      - incomplete result
      - provider or transport failure
      - valid runtime outcome that is not useful to the caller

03.7. A valid but unusable outcome is not automatically the same category as
      an interface failure.


===============================================================================
04. EXECUTION CONTAINMENT BOUNDARIES
===============================================================================

04.1. Turnix defines containment boundaries for execution.

04.2. Typical containment boundaries include:
      - mod execution boundaries
      - capability execution boundaries
      - pipeline step boundaries
      - pack lifecycle boundaries

04.3. A boundary either contains failure correctly or it does not.

04.4. If failure crosses a boundary that Turnix defined as containing that
      class of failure, Turnix has a boundary defect.

04.5. Boundary behavior is part of interface design, not merely an
      implementation detail.

04.6. Same-language or same-process execution does not remove boundary
      responsibility.

04.7. In-process calls may be used as an implementation technique only when
      the interface still preserves boundary meaning, outcome meaning, and
      failure ownership.


===============================================================================
05. FAILURE TRANSLATION
===============================================================================

05.1. Raw failure at a boundary is translated into a structured runtime
      outcome.

05.2. Structured outcomes support:
      - tracing
      - diagnosis
      - creator feedback
      - safe continuation decisions
      - platform integrity review

05.3. A raw exception escaping without translation at a Turnix-defined
      containment edge indicates a likely containment defect.

05.4. Translation does not erase the original cause. Translation preserves
      the cause in a form suitable for runtime handling.

05.5. Translation distinguishes provider, transport, runtime, policy,
      validation, and domain outcomes when those distinctions affect safe
      handling or explanation.

05.6. Translation does not convert every undesirable result into an error.

05.7. If an operation completes successfully but reaches a limit, produces a
      partial result, or returns no usable payload, the translated outcome
      preserves that distinction.

05.8. Retry, recovery, fallback, or repair behavior is not implied merely
      because an outcome is classified. Such behavior requires explicit
      policy or explicit caller choice.


===============================================================================
06. SURFACED FAILURE AND OUTCOME STRUCTURE
===============================================================================

06.1. A surfaced Turnix failure is not presented as a bare message alone.

06.2. Surfaced failures preserve structured meaning sufficient for:
      - diagnosis
      - creator feedback
      - safe continuation decisions
      - platform integrity review

06.3. A surfaced failure includes or remains linkable to:
      - error code
      - human-readable message
      - reason
      - trace correlation evidence when available

06.4. Failure translation does not erase traceability.

06.5. When trace evidence is unavailable, incomplete, pruned, dropped,
      corrupt, or not yet initialized, that limitation remains explicit.

06.6. Interface surfaces do not fabricate explanation evidence merely to
      present a cleaner error.

06.7. Surfaced non-error outcomes may also require structured explanation
      when the outcome could reasonably surprise the user or creator.

06.8. A surfaced outcome that is incomplete, partial, limit-stopped, or
      otherwise uncertain keeps that limitation visible rather than hiding
      it behind a normal-looking success message.


===============================================================================
07. EXPLICIT SEMANTIC NAMING
===============================================================================

07.1. Turnix code favors explicit semantic naming.

07.2. Names communicate meaning at the point of use.

07.3. Short names that rely on easy local deduction are not preferred
      merely because they are conventional.

07.4. Examples of preferred semantic naming include names such as:
      - traceRecordId
      - sessionId
      - indexElement
      - wasErrorRaised

07.5. Semantic explicitness reduces ambiguity for both humans and language
      model assistants.

07.6. Incidental implementation detail does not belong in a name unless
      that detail matters semantically.

07.7. Type-encoding style inherited from older ecosystems is not a default
      Turnix naming strategy.

07.8. Domain meaning matters more than decorative type noise.

07.9. Names for result objects, validation helpers, and outcome categories
      describe Turnix-facing meaning rather than provider-specific
      transport detail.

07.10. Names make incomplete, partial, refused, failed, and successful
       outcomes distinguishable when those distinctions matter.


===============================================================================
08. CANONICAL HELPERS AND CONTRACT REUSE
===============================================================================

08.1. When a stable semantic check or contract already has a canonical
      helper, code uses that helper instead of re-expressing the same rule
      inline.

08.2. Inline duplication of stable logic increases drift risk.

08.3. Canonical helpers centralize contract meaning.

08.4. Canonical helpers make later tightening, auditing, and review easier.

08.5. A helper is introduced when it strengthens clarity, stability, or
      contract reuse without imposing more cost than the problem it solves.

08.6. Helper introduction is not automatic. It remains a design decision.

08.7. A canonical helper may validate, normalize, classify, or explain a
      value when that behavior belongs to a stable interface contract.

08.8. A caller does not manually duplicate a canonical validation or
      classification rule merely because raw fields are locally available.

08.9. If a canonical helper exists but usage sites repeatedly bypass it, the
      interface or helper placement requires review.

08.10. Helper reuse is not only a code-size concern. It preserves one
       semantic home for a rule that would otherwise drift across callers.


===============================================================================
09. VALIDATED SEMANTIC STRUCTURES
===============================================================================

09.1. When structured data crosses a Turnix boundary, Turnix prefers a
      validated semantic structure over a passive data bag when the data has
      stable domain meaning.

09.2. A validated semantic structure carries or exposes the interpretation
      needed to use the value safely.

09.3. A validated semantic structure may provide:
      - normalized fields
      - validation status
      - outcome classification
      - semantic helper properties
      - explanation data
      - safe inspection of incomplete or partial state

09.4. Callers ask semantic questions of the structure or its canonical
      helper instead of reconstructing the same meaning from raw fields at
      each usage site.

09.5. Example categories of semantic questions include:
      - whether an operation produced visible content
      - whether an operation reached a configured limit
      - whether an outcome is complete or partial
      - whether an object is safe to commit
      - whether a value is normalized for the next boundary

09.6. Validated structures do not need to enforce every possible invariant
      eagerly.

09.7. Validation may be automatic, constructor-based, helper-based, adapter-
      based, or explicitly invoked when that choice preserves clear failure
      explanation and interface meaning.

09.8. Automatic validation is acceptable when it makes invalid state harder
      to create without hiding why validation failed.

09.9. Automatic validation is not required merely because a language or
      framework supports it.

09.10. A structure that looks complete but contains unvalidated or
       semantically ambiguous fields increases misuse risk.

09.11. If a value is intentionally raw, provisional, unchecked, or provider-
       specific, its type, name, or boundary placement reflects that status.

09.12. Raw provider-specific structures are translated into Turnix-facing
       semantic structures before crossing into layers that should not know
       provider-specific response details.


===============================================================================
10. OBSERVED DATA AND EFFECTIVE VALUES
===============================================================================

10.1. Turnix preserves observed data at processing boundaries unless an
      interface explicitly defines a different value as the value being
      carried forward.

10.2. Observed data is data received from a user, provider, file, pack,
      adapter, runtime boundary, or other external or internal source.

10.3. Processing does not silently replace observed data with explanatory,
      normalized, fallback, rendered, or diagnostic data.

10.4. When processing discovers additional meaning, Turnix prefers adding
      structure around the observed value.

10.5. Added structure may include:
      - state
      - outcome classification
      - validation status
      - normalization status
      - diagnostic information
      - effective value
      - rendering guidance

10.6. A processing layer may define an effective value when consumers are
      expected to use a processed value instead of, or alongside, the
      observed value.

10.7. When both observed and effective values are exposed, naming makes the
      distinction explicit.

10.8. The "raw" prefix is used only when it distinguishes an observed value
      from an effective, normalized, rendered, or otherwise processed value.

10.9. A value is not given a "raw" prefix merely because it originated from
      a source boundary.

10.10. Shadowing observed data is allowed only when downstream consumers are
       not expected to benefit from knowing that shadowing occurred.

10.11. If a downstream consumer may need to know whether data was processed,
       normalized, replaced, rendered, or synthesized, the interface carries
       that information explicitly.

10.12. Rendering layers decide how to present observed data, effective data,
       state, and diagnostics to users.

10.13. Data processing layers decide how to validate, classify, normalize,
       or derive values, but they do not disguise those decisions as the
       original observed value when that distinction matters.

10.14. Diagnostic or explanatory text produced by Turnix is not stored or
       forwarded as if it were observed model, user, file, or provider data.

10.15. If a fallback value exists only for presentation, it remains a
       rendering concern or surfaced outcome detail.

10.16. If a fallback value is intended to become data for later consumers,
       the interface records that it is a fallback or effective value.


===============================================================================
11. INCOMPLETE AND PARTIAL STATES
===============================================================================

11.1. Some Turnix workflows may construct values gradually.

11.2. Gradual construction is acceptable when incomplete state is represented
      explicitly.

11.3. Incomplete, partial, provisional, or sentinel-backed state does not
      masquerade as complete state.

11.4. When incomplete state is valid to inspect, the interface provides safe
      inspection paths.

11.5. When incomplete state is invalid to use for a certain operation, the
      failure is clear, structured, and tied to the missing or invalid
      requirement.

11.6. A throwing sentinel may be used when misuse must fail loudly, but the
      sentinel does not hide that the object is incomplete.

11.7. A safely inspectable incomplete object is preferred over an object that
      silently appears complete until unrelated later code fails.

11.8. Incomplete state does not avoid making required decisions explicit.

11.9. If an object requires later completion before crossing a boundary,
      that boundary verifies or receives a verified complete form.

11.10. Partial runtime outcomes remain valid outcomes when they honestly
       represent what happened.

11.11. Partial outcomes are not silently promoted to complete outcomes for
       presentation convenience.


===============================================================================
12. EXPLICIT INTEGRATION OVER IMPLIED MEANING
===============================================================================

12.1. When a principle, intention, or concept is important to Turnix
      behavior, it is expressed where future readers and assistants can find
      the complete meaning without relying on scattered clues.

12.2. A partial principle that requires inference from several distant
      passages is a drift risk.

12.3. If the intended meaning is incomplete, fragmented, or ambiguous, a
      clearer rewrite is preferred over leaving the missing meaning
      implicit.

12.4. Rewriting a section to preserve full meaning is acceptable when local
      insertion would leave the document dependent on hidden context.

12.5. Limited duplication is acceptable when it removes ambiguity, preserves
      full meaning at the point of use, or prevents assistant-dependent
      inference.

12.6. Duplication is not acceptable when it creates competing authorities for
      the same rule.

12.7. The preferred form is:
      - one authoritative semantic home
      - enough local restatement to make nearby interface rules clear
      - no hidden dependence on unstated intent

12.8. A clearer rewrite is not automatically better. The rewrite is better
      only when it preserves or improves semantic accuracy, boundary
      placement, and future reviewability.

12.9. Interface doctrine does not rely on future assistants inferring the
      correct design direction from incomplete wording.

12.10. When important meaning is discovered during implementation, review, or
       audit, the relevant document is updated directly if the meaning is
       intended to persist.


===============================================================================
13. INTERFACE CLARITY OVER FALSE TIGHTNESS
===============================================================================

13.1. Turnix does not treat tighter code as an automatic virtue.

13.2. Interface clarity, stable meaning, and reviewability matter more than
      local cleverness.

13.3. A design that is less compact but much harder to misuse may be the
      better Turnix design.

13.4. Post-hoc tightening that changes scope, weakens clarity, or starts a
      second refactor cycle is not treated as an automatic improvement.

13.5. A compact interface that forces callers to infer hidden state,
      duplicate validation, or manually classify outcomes is not clearer
      merely because it is smaller.

13.6. A slightly larger structure that preserves semantic meaning, outcome
      classification, and future validation seams may be the clearer
      interface.


===============================================================================
14. SUMMARY
===============================================================================

14.1. Turnix interface design aims for explicit meaning, accidental-misuse
      resistance, creator freedom, and strong containment boundaries.

14.2. Interfaces are judged not only by elegance, but by whether they help
      preserve platform truth and reduce unnecessary ambiguity.

14.3. Surfaced failures remain structured, explainable, and linked to trace
      correlation evidence when such evidence is available.

14.4. Stable semantic checks, validations, and classifications belong in
      canonical helpers or validated semantic structures rather than being
      duplicated across callers.

14.5. Turnix preserves observed data by default and adds structure for
      validation, classification, effective values, and rendering guidance
      instead of silently replacing the observed value.

14.6. Incomplete, partial, and limit-stopped outcomes remain explicit.

14.7. Important interface meaning is rewritten into clear doctrine when
      needed rather than left for future readers or assistants to infer from
      fragmented context.
