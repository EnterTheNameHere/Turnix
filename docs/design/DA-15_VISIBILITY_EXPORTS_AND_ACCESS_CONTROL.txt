===============================================================================
DESIGN AREA DA-15 - VISIBILITY, EXPORTS & ACCESS CONTROL
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines permissioned reference reachability, export enforcement, and
access-control consequences across Pack hierarchy, dependency/source domains,
and SaveBundle-local retained or copied Pack material.

Visibility is enforced by Turnix.
Visibility is not negotiated at runtime by Packs.
Visibility violations are hard failures.

Purpose:
--------
This document defines the deterministic, policy-enforced reachability system
that constrains Pack-to-Pack referencing across Pack hierarchy,
dependency/source boundaries, and SaveBundle-local retained material.

It defines:
- the visibility question and its scope boundary
- canonical architecture names used by this document
- local and global visibility enforcement inputs
- manifest-level visibility fields and access-control consequences
- exportNestedPacks enforcement consequences
- importPacksFromParent enforcement consequences
- dependency/source isolation for visibility
- SaveBundle-local retained or copied Pack material visibility isolation
- capability, service, execution, and authority stop-lines
- failure behavior and error requirements

It does NOT define:
- Pack identity, hierarchy, or computed visibility ownership
- generic resolution ordering or selection criteria
- dependency semantics, dependency-source policy, or solver behavior
- importing, module loading, or code-boundary mechanics
- activation lifecycle, runtime execution, or adapter execution
- capability schemas, permission prompting, or grant persistence details
- Service registry shape or direct service-access surfaces
- ModCallContext facade shape, lifetime, or absent surfaces
- Application or ApplicationRun lifecycle semantics
- RuntimeHost command behavior or Workspace ownership
- PackManager catalog, graph-preparation, repair, or UI behavior
- SaveBundle storage format, ownership, loading, or graph evidence details
- exact UI phrasing, graph visualization, or final error subtype taxonomy

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines visibility, exports, and access-control
      boundaries within that shared interpretation model.

01.5. This document uses canonical architecture names.

01.6. SaveBundle is the durable persistence closure of an Application.

01.7. SaveBundle is not a Pack.

01.8. Application is one durable application individual.

01.9. ApplicationRun is one live execution period of an Application.

01.10. ModCallContext is the invocation-scoped Pack-facing gateway into
       Turnix.

01.11. SaveBundle-local Pack material means Pack material retained or copied
       inside a SaveBundle for use by its owning Application context.

01.12. Visibility does not grant authority merely because this document names
       another runtime domain.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. Visibility answers exactly one question:

          "Is Pack A permitted to reference Pack B?"

02.2. Visibility is permissioned reachability.

02.3. Visibility is about reference permission only.

02.4. Visibility is not activation.

02.5. Visibility is not code loading.

02.6. Visibility is not importing or module loading authority.

02.7. Visibility is not execution order.

02.8. Visibility is not dependency satisfaction.

02.9. Visibility is not version compatibility.

02.10. Visibility is not runtime capability access.

02.11. Visibility is not runtime service access.

02.12. Visibility is not ApplicationRun authority.

02.13. Visibility is not RuntimeHost authority.

02.14. Visibility is not adapter authority.

02.15. Visibility is not PackManager authority.

02.16. Visibility is not committed-state authority.

02.17. Visibility is not OrchestrationUnit mutation authority.

02.18. Visibility is not ModCallContext gateway authority.

02.19. This document defines visibility as a gate on permitted reference
       reachability.


===============================================================================
03. AUTHORITY STOP-LINES
===============================================================================

03.1. DA-15 owns visibility enforcement and access-control consequences.

03.2. DA-15 may name neighboring domains only to state that visibility does
      not grant authority in those domains.

03.3. Neighboring domains own their detailed behavior.

03.4. Neighboring domains include:
      - Pack identity and hierarchy
      - local and global visibility structure
      - generic resolution
      - dependency and dependency/source policy
      - importing and module loading
      - activation lifecycle
      - Services, Capabilities, and permissions
      - Application and ApplicationRun lifecycle
      - ExecutionAdapter and adapter lifecycle
      - RuntimeHost behavior
      - PackManager behavior
      - ModCallContext gateway behavior
      - SaveBundle persistence and retained material

03.5. This section is an authority stop-line.

03.6. This section does not create detailed DA-15 semantics for neighboring
      domains.


===============================================================================
04. VISIBILITY VS DEPENDENCY
===============================================================================

04.1. Dependency declaration expresses requirement.

04.2. Visibility expresses permission.

04.3. A Pack may depend on another Pack and still be forbidden from
      referencing it.

04.4. A dependency may fail because visibility forbids the dependency target.

04.5. Visibility failure during dependency resolution is a hard dependency
      failure.

04.6. Turnix does not silently bypass visibility when dependency resolution
      encounters a forbidden target.

04.7. Visibility is evaluated:
      - during dependency resolution
      - during resolvePack calls
      - during turnixImport resolution

04.8. Visibility is not bypassed or deferred.


===============================================================================
05. VISIBILITY DOMAINS
===============================================================================

05.1. Each Pack participates in two visibility domains:
      - local visibility
      - global visibility

05.2. Local visibility applies within a parent Pack tree.

05.3. Local visibility controls parent-child export gating inputs.

05.4. Global visibility determines whether a Pack is reachable from outside
      its parent chain.

05.5. DA-10 owns the structure and computation of local visibility and
      global visibility.

05.6. DA-15 owns the enforcement consequences of those visibility values.

05.7. Visibility values are computed statically and enforced dynamically.


===============================================================================
06. DECLARED VISIBILITY
===============================================================================

06.1. Manifest field:
      visibility: "public" | "private"

06.2. If declared, the declared value is used as-is.

06.3. If omitted, the default is derived from Pack kind:
      - ContentPack -> public
      - AppPack -> private
      - ViewPack -> private
      - ModPack -> private

06.4. Declared visibility expresses local visibility intent only.

06.5. Declared visibility does not directly grant global reachability.

06.6. SaveBundle does not use Pack manifest visibility as its own
      visibility identity.

06.7. SaveBundle-local retained or copied Pack material follows
      SaveBundle-local visibility isolation and the retained Pack material's
      own applicable Pack identity and visibility rules.


===============================================================================
07. EXPORTNESTEDPACKS
===============================================================================

07.1. Manifest field:
      exportNestedPacks

07.2. Allowed values are:
      - true
      - false
      - list of localId strings

07.3. exportNestedPacks controls which direct child Packs may become
      globally visible.

07.4. If exportNestedPacks is true, all direct child Packs may be exported.

07.5. If exportNestedPacks is false, no direct child Packs are exported.

07.6. If exportNestedPacks is a list, only listed direct child Packs may be
      exported.

07.7. Only direct child Packs may be listed.

07.8. Dotted identifiers are forbidden in exportNestedPacks lists.

07.9. A non-existent localId in an exportNestedPacks list is an error.

07.10. exportNestedPacks does not apply transitively.

07.11. exportNestedPacks does not grant capability access.

07.12. exportNestedPacks does not grant service access.

07.13. exportNestedPacks does not authorize activation, importing, module
       loading, adapter execution, or RuntimeHost command execution.

07.14. DA-15 uses exportNestedPacks as an access-control input.

07.15. DA-10 owns the identity and hierarchy structure behind
       exportNestedPacks.


===============================================================================
08. GLOBAL VISIBILITY ENFORCEMENT INPUT
===============================================================================

08.1. DA-10 defines and computes globalVisibility.

08.2. DA-15 consumes the DA-10-defined globalVisibility value as an
      enforcement input.

08.3. DA-15 does not define the full globalVisibility computation.

08.4. For DA-15 enforcement, globalVisibility determines whether the target
      Pack can pass the outside-parent-chain visibility gate.

08.5. A Pack whose DA-10-defined globalVisibility is public may pass the
      outside-parent-chain visibility gate when all other applicable gates
      also pass.

08.6. A Pack whose DA-10-defined globalVisibility is private does not pass
      the outside-parent-chain visibility gate by global visibility.

08.7. globalVisibility does not override the active dependency/source domain.

08.8. globalVisibility does not grant capability access.

08.9. globalVisibility does not grant service access.

08.10. globalVisibility does not authorize importing, activation, adapter
       execution, RuntimeHost command execution, or state mutation.

08.11. DA-15 treats globalVisibility immutability as a DA-10-owned input
       property.


===============================================================================
09. IMPORTPACKSFROMPARENT
===============================================================================

09.1. Manifest field:
      importPacksFromParent

09.2. importPacksFromParent controls which parent-side Packs are
      reference-visible to this Pack.

09.3. importPacksFromParent does not imply export.

09.4. importPacksFromParent does not imply capability access.

09.5. importPacksFromParent does not imply service access.

09.6. importPacksFromParent does not imply permission inheritance.

09.7. importPacksFromParent does not imply activation.

09.8. importPacksFromParent does not authorize adapter execution.

09.9. importPacksFromParent does not grant RuntimeHost authority.

09.10. Allowed values are:
       - false
       - true
       - list of selectors

09.11. If importPacksFromParent is false, no parent-side Packs are visible.

09.12. If importPacksFromParent is true, all globally visible parent-side
       Packs are visible.

09.13. If importPacksFromParent is a list, only explicitly listed
       parent-side Packs are visible.

09.14. Default importPacksFromParent values are:
       - ViewPack -> false
       - all other Pack kinds -> true

09.15. ViewPack isolation remains the default unless an owning View document
       changes it.


===============================================================================
10. IMPORTPACKSFROMPARENT LIST RESOLUTION
===============================================================================

10.1. Selectors in an importPacksFromParent list are resolved relative to
      the parent Pack.

10.2. Resolution rule:
      resolvedId = parent.packTreeId + "." + selector

10.3. Selectors refer only to descendants of the parent Pack.

10.4. Escaping the parent Pack tree is forbidden.

10.5. Invalid selector resolution is a hard error.

10.6. Visibility checks still apply after selector resolution.

10.7. List resolution does not grant a selector access to Packs outside the
      parent Pack tree.


===============================================================================
11. VISIBILITY AND DEPENDENCY/SOURCE DOMAINS
===============================================================================

11.1. Visibility evaluation occurs after dependency/source determination.

11.2. The dependency/source domain is determined before visibility
      evaluation.

11.3. Only Packs inside the active dependency/source domain are considered
      visible candidates.

11.4. Packs outside the active dependency/source domain are not visible
      candidates regardless of declared visibility or globalVisibility.

11.5. Visibility does not bridge dependency/source domains.

11.6. SaveBundle-local dependency/source resolution ignores ordinary global
      Packs unless a global source is explicitly selected.

11.7. Global dependency/source resolution ignores SaveBundle-local retained
      or copied Pack material unless a SaveBundle-local source is explicitly
      selected.

11.8. Dependency/source policy remains owned by DA-13.

11.9. DA-15 defines only the visibility consequence once the active
      dependency/source domain has been selected.


===============================================================================
12. SAVEBUNDLE-LOCAL PACK MATERIAL VISIBILITY
===============================================================================

12.1. SaveBundle is not ordinary globally visible Pack material.

12.2. SaveBundle-local retained or copied Pack material has a dedicated
      SaveBundle/Application visibility context.

12.3. SaveBundle-local retained or copied Pack material is visible only
      within its owning SaveBundle/Application context unless another owning
      document explicitly exposes it.

12.4. SaveBundle-local retained or copied Pack material is not visible
      globally by default.

12.5. SaveBundle-local retained or copied Pack material may shadow global
      Packs of the same identity inside its SaveBundle/Application context.

12.6. Shadowing behavior follows dependency/source and graph rules owned by
      their respective documents.

12.7. If a Pack is resolved from a SaveBundle-local source, global Packs with
      the same identity are not visible for that resolution path unless the
      active dependency/source policy explicitly selects a global source.

12.8. If a Pack is resolved from a SaveBundle-local source, the global
      registry is not consulted for that resolution path unless the active
      dependency/source policy explicitly selects a global source.

12.9. SaveBundle-local visibility isolation does not make SaveBundle a Pack.

12.10. SaveBundle-local visibility isolation does not define SaveBundle
       storage format, ownership, loading, or graph evidence details.


===============================================================================
13. VISIBILITY AND IMPORTING
===============================================================================

13.1. Visibility is evaluated during turnixImport resolution.

13.2. Visibility does not by itself load code.

13.3. Visibility does not authorize importing or module loading.

13.4. Importing and module loading remain owned by DA-12.

13.5. A visible Pack may still be unavailable for import or module loading
      when DA-12 boundaries, adapter support, activation state, or other owning
      rules forbid that access.

13.6. Native host-language mechanisms do not bypass Turnix visibility rules.

13.7. Direct implementation access across Pack boundaries is not created by
      visibility.


===============================================================================
14. VISIBILITY AND ACTIVATION
===============================================================================

14.1. Visibility does not activate Packs.

14.2. Visibility does not create Pack lifecycle participation.

14.3. Visibility does not define activation order.

14.4. Visibility does not satisfy activation prerequisites.

14.5. Activation lifecycle and execution guarantees remain owned by DA-14.

14.6. A Pack that is visible to another Pack may still be inactive.

14.7. A Pack that is visible to another Pack may still be unavailable for
      runtime execution.


===============================================================================
15. VISIBILITY AND CAPABILITIES
===============================================================================

15.1. Capabilities are not governed by visibility.

15.2. Visibility does not grant capabilities.

15.3. Capabilities are not inherited through visibility.

15.4. Capability access requires an explicit capability path defined by the
      owning capability and permission documents.

15.5. A visible Pack may still be unable to use another Pack's capabilities.

15.6. Visibility does not authorize capability invocation.

15.7. Services, Capabilities, permission semantics, and capability invocation
      remain owned by DA-16.


===============================================================================
16. VISIBILITY AND SERVICES
===============================================================================

16.1. Services are runtime/internal wiring owned by DA-16 and related
      runtime documents.

16.2. Visibility does not grant access to Services.

16.3. Visibility does not create direct Service object access.

16.4. Service access, if any, requires an explicitly defined runtime-owned or
      capability-mediated surface in an owning document.

16.5. Cross-Pack execution uses Capabilities rather than direct Service
      object lookup.

16.6. A visible Pack may still be unable to use a Service associated with
      another Pack.

16.7. DA-15 does not define Service registry shape.

16.8. DA-15 does not define Pack-facing Service access surfaces.


===============================================================================
17. VISIBILITY AND MODCALLCONTEXT
===============================================================================

17.1. ModCallContext is the Pack-facing invocation gateway into Turnix.

17.2. Visibility does not grant ModCallContext authority.

17.3. Visibility does not add ModCallContext facades.

17.4. Visibility does not make absent ModCallContext surfaces present.

17.5. Visibility does not allow Pack code to retain or fabricate a
      ModCallContext.

17.6. ModCallContext gateway semantics, facade shape, lifetime, and absent
      surfaces remain owned by DA-30.


===============================================================================
18. VISIBILITY AND RUNTIME AUTHORITY
===============================================================================

18.1. Visibility does not grant ApplicationRun authority.

18.2. Visibility does not grant RuntimeHost authority.

18.3. Visibility does not grant ExecutionAdapter authority.

18.4. Visibility does not grant adapter lifecycle authority.

18.5. Visibility does not grant OrchestrationUnit mutation authority.

18.6. Visibility does not grant committed-state authority.

18.7. Visibility does not grant persistence authority.

18.8. Visibility does not authorize RuntimeHost command execution.

18.9. Visibility does not authorize adapter execution.

18.10. Visibility does not authorize state mutation.

18.11. Runtime authority remains mediated by the owning runtime domains.


===============================================================================
19. PACKMANAGER PRESENTATION AND VISIBILITY
===============================================================================

19.1. PackManager may present, inspect, or prepare information related to
      Pack visibility.

19.2. PackManager presentation is not visibility authority.

19.3. PackManager graph preparation is not visibility authority.

19.4. PackManager repair suggestions do not silently override visibility
      rules.

19.5. PackManager repair suggestions do not silently expose forbidden Packs.

19.6. PackManager UI behavior remains owned by DA-29.

19.7. DA-15 defines the access-control consequence of visibility failure, not
      PackManager repair behavior.


===============================================================================
20. VISIBILITY EVALUATION TIMING
===============================================================================

20.1. Visibility checks occur:
      - during dependency resolution
      - during resolvePack calls
      - during turnixImport resolution

20.2. Visibility is evaluated dynamically between:
      - the requesting Pack
      - the target Pack

20.3. Visibility is not pre-expanded into a static graph.

20.4. Visibility evaluation uses the active dependency/source domain.

20.5. Visibility evaluation uses the applicable local visibility and global
      visibility values.

20.6. Visibility evaluation treats identifiers as case-sensitive and
      byte-exact.

20.7. Visibility evaluation is not runtime negotiation by Packs.


===============================================================================
21. FAILURE MODE
===============================================================================

21.1. If a visibility check fails, Turnix raises PermissionDeniedError unless
      an owning error-taxonomy document defines a more specific visibility
      denial subtype.

21.2. A visibility-denial error includes:
      - requesting Pack identity
      - target Pack identity
      - violated rule

21.3. Visibility failure during dependency resolution is a hard dependency
      failure.

21.4. Visibility failure during dependency resolution aborts resolution for
      that request.

21.5. Visibility failure permits no fallback.

21.6. Visibility failure permits no probing.

21.7. Visibility failure permits no runtime negotiation by Packs.

21.8. Turnix does not retry weaker visibility rules and present the result as
      if it answered the original request.

21.9. Exact final error subtype taxonomy remains outside this document unless
      an owning error document fixes it.


===============================================================================
22. CASE SENSITIVITY
===============================================================================

22.1. All identifiers used in visibility checks are case-sensitive.

22.2. All identifiers used in visibility checks are byte-exact.

22.3. Visibility evaluation performs no identifier normalization.

22.4. Visibility evaluation performs no case folding.


===============================================================================
23. EXPLICITLY OPEN QUESTIONS
===============================================================================

23.1. OPEN questions include:
      - tooling for visualizing visibility graphs
      - UI phrasing for visibility-denial explanations
      - final visibility-denial error subtype taxonomy

23.2. Explicit bilateral visibility agreements remain out of scope for this
      document unless an owning design document defines them.

23.3. PackManager repair behavior remains out of scope for this document.

23.4. SaveBundle storage format and graph-evidence layout remain out of scope
      for this document.

23.5. ModCallContext facade shape and absent surfaces remain out of scope for
      this document.


===============================================================================
24. SUMMARY
===============================================================================

24.1. Visibility is permissioned reference reachability.

24.2. Visibility is permission, not preference.

24.3. Dependency does not override visibility.

24.4. Visibility and exportNestedPacks constrain global reachability.

24.5. importPacksFromParent controls parent-to-child reference visibility.

24.6. Dependency/source domain selection restricts the visibility domain.

24.7. SaveBundle-local retained or copied Pack material is isolated from
      global visibility by default.

24.8. Visibility does not imply capability access.

24.9. Visibility does not imply service access.

24.10. Visibility does not authorize importing, module loading, activation,
       adapter execution, capability invocation, RuntimeHost command
       execution, OrchestrationUnit-backed mutation, committed-state
       authority, ApplicationRun authority, ModCallContext authority, or
       PackManager authority.

24.11. Visibility is evaluated dynamically with hard failure on violation.

24.12. Visibility failure permits no fallback, probing, silent bypass, or
       runtime negotiation by Packs.

24.13. Visibility-check identifiers are case-sensitive and byte-exact.

24.14. Remaining OPEN items are tooling, presentation, and error-taxonomy
       details only.
