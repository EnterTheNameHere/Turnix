===============================================================================
DESIGN AREA DA-05 - PAYLOAD IDENTITY, CHUNKS & VALUEREF REPRESENTATION
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the storage-neutral representation contract for committed values in
Turnix, including immutable payload identity, Chunk semantics, ChunkId
semantics, and ValueRef forms.

This document makes committed value representation stable across storage
backends without turning storage realization into platform truth.

Purpose:
--------
This document defines how authoritative committed values are represented in
Turnix independently of any specific storage backend, file layout, or database
implementation.

It defines:
- the storage-neutral payload model for committed values
- immutable payload identity through Chunk and ChunkId
- integrity requirements for committed payload material
- ValueRef as the committed value representation contract
- schemaless default and optional schema linkage for committed values
- payload sharing and reachability constraints across retained artifacts
- boundary rules between representation semantics and persistent I/O authority

It does NOT define:
- the general memory, transaction, and authoritative-state model (see DA-04)
- concrete persistent I/O authority, Readers, Writers, or filesystem rules
  (see DA-07)
- tracing structure, trace event schema, trace retention, trace pruning, trace
  loss, span mechanics, or trace storage semantics (see DA-03)
- configuration-specific scope, defaults, schema, or migration semantics
  (see DA-06)
- Window, ActiveWindow, SafePointWindow, AbortedWindow, Window sequence, or
  Window finalization semantics (see DA-08)
- WindowManifest, WindowExport, Minimal Audit Bundle, digest representation,
  partial export, missing material, export creation, or offline-inspection
  artifact semantics (see DA-25)
- equality modes, ComparisonResult, Replay, Resume, Retry, or audit workflow
  semantics (see DA-26)
- SaveBundle storage, compatibility, recovery, or durable persistence closure
  details owned by persistence documents
- concrete digest algorithms, canonical serialization formats, codec
  implementations, storage layouts, or garbage-collection algorithms beyond
  the semantic constraints stated here

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines committed value representation and payload
      identity semantics within that shared interpretation model.

01.05. This document uses SaveBundle to name the durable persistence closure
      of one Application.

01.06. SaveBundle semantics remain owned by their owning persistence
      documents.

01.07. This document uses ValueRef to name an immutable committed-value
      decoding contract.

01.08. This document uses Chunk to name an immutable byte payload.

01.09. This document uses ChunkId to name stable content-derived identity for a
      Chunk.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. This design area answers:

          "How are committed values represented so that they remain stable,
           inspectable, and independent of any one storage backend?"

02.02. Turnix does not treat committed state as live runtime object identity.

02.03. Turnix represents committed values through immutable payload references.

02.04. Runtime objects are decoded views of committed payload material.

02.05. Runtime residency is an implementation detail and does not change the
      meaning of a committed value.

02.06. Representation semantics remain storage-neutral.

02.07. Storage-neutral representation means that committed value meaning does
      not depend on:
      - filesystem path
      - database row identity
      - runtime pointer identity
      - machine-local layout accident

02.08. This document defines the representation contract only.

02.09. This document does not define who is allowed to persist payload
      material or how persistent I/O is performed.

02.10. Persistent I/O authority belongs to DA-07.

02.11. Turnix does not treat storage realization as the definition of
       committed truth.

02.12. Turnix does not allow backend convenience, location, or runtime
       identity to redefine committed value meaning.

02.13. Later sections of this document refine and apply these rules.
       They do not weaken them.

02.14. DA-05 defines representation semantics for committed values.

02.15. DA-05 does not grant transaction authority, persistence authority,
       trace authority, capability permission, Pack authority, Window
       finalization authority, export authority, comparison authority, Replay,
       Resume, or Retry authority.


===============================================================================
03. STORAGE-NEUTRAL PAYLOAD MODEL
===============================================================================

03.01. Authoritative committed state does not embed mutable runtime objects.

03.02. A committed value is representable as immutable payload material plus
      deterministic decoding information.

03.03. Committed state references immutable payload bytes rather than live
      runtime object identity.

03.04. Runtime objects are decoded views of immutable payload material.

03.05. This model supports:
      - deterministic restoration
      - backend-agnostic storage realization
      - offline inspection
      - safe payload sharing
      - stable artifact closure

03.06. A committed key in a committed layer or committed configuration is
      representable at the commit boundary as:

          key -> ValueRef

03.07. A ValueRef is immutable once created.

03.08. A ValueRef does not depend on:
      - transactional layers
      - journal completeness
      - trace completeness
      - hidden external side effects

03.09. If a committed value cannot be decoded from its retained authoritative
      representation, the failure is explicit.

03.10. A decode failure does not cause the value to be treated as valid
       authoritative content.

03.11. Turnix does not treat live object identity as part of committed value
       meaning.

03.12. Turnix does not allow mutable runtime structure to leak into the
       authoritative committed representation.

03.13. Committed value meaning remains stable even if the storage backend,
       retrieval path, or residency strategy changes.


===============================================================================
04. CORE TERMS
===============================================================================

04.01. A Chunk is an immutable byte sequence.

04.02. A ChunkId is the canonical identity of a Chunk.

04.03. A ValueRef is an immutable reference describing how to obtain and decode
      committed value payload material.

04.04. A codec is a deterministic decoding rule identified by codecId.

04.05. A schema is optional typing and version metadata that may participate in
      typed decode and compatibility handling.

04.06. A root manifest is an immutable manifest that enumerates referenced
      payload roots and defines a reachability root for retained artifact
      closure.

04.07. Specialized manifest kinds may satisfy the root-manifest role for
      particular retained artifact classes when their owning documents define
      that role.

04.08. This document defines the semantic meaning of these terms.

04.09. This document does not define their concrete on-disk realization.

04.10. These terms describe representation semantics. They do not by
       themselves define authority boundaries outside the committed-state model
       defined elsewhere.


===============================================================================
05. CHUNKS AND CHUNK IDENTITY
===============================================================================

05.01. A Chunk is immutable once created.

05.02. Chunk immutability is enforced by the storage implementation that
      realizes this contract.

05.03. A Chunk is addressable by a stable ChunkId.

05.04. A retained Chunk is retrievable by ChunkId unless it has been removed by
      explicit retention or garbage-collection policy compatible with
      authoritative reachability guarantees.

05.05. Two Chunks are the same Chunk if and only if their ChunkId is identical.

05.06. ChunkId is stable across:
      - export and import
      - copying between storage backends
      - SaveBundle packaging
      - SaveBundle persistence-closure movement
      - other storage relocation that preserves the same payload material

05.07. ChunkId does not depend on:
      - filesystem paths
      - database row identifiers
      - local timestamps
      - machine identity
      - wall-clock time

05.08. ChunkId is content-derived.

05.09. Content-derived means that ChunkId is computed from:
      - the payload byte sequence
      - the identity-relevant chunk metadata fields

05.10. ChunkId is not derived from values expected to differ across machines or
       runs.

05.11. ChunkId is representable in plain text.

05.12. ChunkId remains byte-for-byte stable across export and import.

05.13. The exact ChunkId encoding remains open within the constraints of this
       document.

05.14. Turnix does not treat location, transport, or storage-container identity
       as Chunk identity.

05.15. Chunk identity does not become backend-specific merely because a backend
       stores, packs, or indexes payloads differently.


===============================================================================
06. CHUNK HEADER AND INTEGRITY
===============================================================================

06.01. Each Chunk has an associated ChunkHeader.

06.02. ChunkHeader contains the identity-relevant header metadata for that
      Chunk.

06.03. ChunkHeader includes:
      - chunkId
      - chunkType
      - byteLength
      - hashAlgorithm
      - contentHash

06.04. byteLength equals the number of bytes in the payload.

06.05. contentHash is computed over the payload bytes.

06.06. hashAlgorithm names a deterministic hash function.

06.07. chunkType is a stable explicit identifier for the chunk's artifact role.

06.08. chunkType does not redefine Chunk identity semantics by itself.

06.09. Example chunkType values include:
      - stateLayerValues
      - configValues
      - revisionIndex
      - journalEntries
      - traceEvents
      - traceIndex
      - windowManifest
      - packManifest
      - blob

06.10. Example chunkType values are illustrative and do not lock the full
       future chunkType catalog.

06.11. Integrity verification is performed by recomputing contentHash from
       payload bytes and comparing it with the stored contentHash.

06.12. If integrity verification fails, retrieval of that retained chunk is
       treated as corrupt.

06.13. Corrupt payload material is not treated as authoritative.

06.14. Corruption detection creates a representation-domain trace emission
       obligation when detected in a running Turnix context.

06.15. Trace retention, trace pruning, trace loss, event structure, span
       mechanics, and trace storage semantics remain owned by DA-03.

06.16. ChunkId is verified against the identity-relevant header fields when
       integrity validation requires that check.

06.17. Turnix does not silently accept corrupt retained payload material as
       valid committed representation.

06.18. Turnix does not treat integrity failure as a tolerable variation in
       authoritative content.


===============================================================================
07. FORMAT AWARENESS AND IDENTITY STABILITY
===============================================================================

07.01. Chunk identity is format-aware.

07.02. Format-aware means that payloads representing the same semantic value in
      different encodings produce different ChunkIds unless some later
      authoritative rule explicitly defines a canonical equivalence model.

07.03. Any change to payload serialization format results in a different Chunk
      identity.

07.04. Identity does not collapse multiple encodings into one merely because
      their decoded semantic value could be judged similar.

07.05. Identity-relevant metadata may include format or schema-related markers
      when that metadata participates in identity.

07.06. Turnix does not silently treat representation variance as identity
      equivalence.

07.07. Turnix does not infer canonical sameness from semantic similarity unless
      a later authoritative rule defines that equivalence explicitly.


===============================================================================
08. VALUEREF
===============================================================================

08.01. VALUEREF CORE RULES
--------------------------

08.01.01. A ValueRef is an immutable reference to committed value payload
        material.

08.01.02. A ValueRef is not a pointer to live runtime memory.

08.01.03. A ValueRef is a deterministic decoding contract for one committed
        value payload.

08.01.04. A committed key in a committed layer or committed configuration is
        representable as key -> ValueRef at the commit boundary.

08.01.05. A ValueRef is immutable once created.

08.01.06. A ValueRef does not require:
        - transactional layers
        - journal completeness
        - trace completeness
        - hidden runtime side effects
        in order to decode successfully.

08.01.07. If a ValueRef cannot be decoded, the failure is explicit.

08.01.08. A committed value whose ValueRef cannot be decoded is not treated as
        valid authoritative content.

08.01.09. A ValueRef may be resolved eagerly or lazily.

08.01.10. Eager versus lazy resolution is an implementation choice and does not
         change ValueRef semantics.

08.01.11. Turnix does not treat residency strategy as part of committed value
         meaning.

08.01.12. Turnix does not allow decoding success to depend on hidden mutable
         runtime context.


08.02. VALUEREF FORMS
---------------------

08.02.01. A ValueRef is exactly one of the following forms:

        A) InlineValueRef
        B) ChunkValueRef

08.02.02. InlineValueRef stores payload bytes directly inside the ValueRef.

08.02.03. ChunkValueRef stores payload bytes in a Chunk and references them by
        ChunkId.

08.02.04. Both ValueRef forms include an explicit codec identifier.

08.02.05. ChunkValueRef includes integrity metadata sufficient to validate
        retrieved payload bytes.

08.02.06. InlineValueRef may include integrity metadata.

08.02.07. Arbitrary network references and arbitrary file-path references are not
        part of ValueRef under this document.

08.02.08. If a later authoritative document ever introduces external references,
        such references do not become valid for authoritative committed state
        unless deterministic retrieval is explicitly guaranteed.

08.02.09. Turnix does not silently widen ValueRef into an open-ended external
        reference model.

08.02.10. Turnix does not treat environment-dependent retrieval as valid
         authoritative committed representation.


08.03. VALUEREF REQUIRED FIELDS
-------------------------------

08.03.01. Every ValueRef includes:
        - codecId

08.03.02. codecId is a stable identifier describing how payload bytes decode into
        a runtime value.

08.03.03. Every ChunkValueRef includes:
        - chunkId
        - integrity metadata

08.03.04. chunkId identifies the immutable payload bytes.

08.03.05. integrity metadata is sufficient to validate the retrieved payload
        bytes used by that ChunkValueRef.

08.03.06. A ValueRef may additionally include:
        - contentType
        - schemaId
        - schemaVersion

08.03.07. Optional fields do not become required merely because some artifact
        classes use them.

08.03.08. Optional descriptive metadata does not redefine committed value
        identity unless this document or a later authoritative document says
        that it participates in identity.


===============================================================================
09. SCHEMALESS DEFAULT AND OPTIONAL SCHEMA LINKAGE
===============================================================================

09.01. Committed values are schemaless by default.

09.02. Schemaless default means that a ValueRef without schema linkage decodes
      into the generic runtime structure defined by its codec.

09.03. Generic runtime structure may include:
      - map
      - list
      - scalar
      - bytes

09.04. A ValueRef may include schema linkage through schemaId and, where
      required, schemaVersion.

09.05. If schema linkage is present, decoding may be schema-aware and may
      produce a typed runtime object or typed structured result.

09.06. Presence of schema linkage is not required for storing simple values.

09.07. If schema-aware decode fails, the failure is explicit unless some later
      authoritative policy explicitly permits fallback.

09.08. Any permitted fallback from schema-aware decode to schemaless decode
      creates a representation-domain trace emission obligation when it occurs
      in a running Turnix context.

09.09. Trace retention, trace pruning, trace loss, event structure, span
      mechanics, and trace storage semantics remain owned by DA-03.

09.10. This document defines schema linkage only as optional committed-value
       representation metadata.

09.11. This document does not define the full generalized schema system used by
       configuration or other structured domains.

09.12. Turnix does not silently require schema for ordinary committed value
       storage.

09.13. Turnix does not silently downgrade schema-aware failure into successful
       committed decode unless an explicit authoritative policy allows that
       behavior.


===============================================================================
10. VALUE ORIGIN AND STATIC DATA
===============================================================================

10.01. A ValueRef may reference payload bytes originating from static data.

10.02. Static origin does not exempt a committed value from the committed
      representation contract defined by this document.

10.03. If committed state stores a value derived from static data, that
      committed value remains representable as a ValueRef at the commit
      boundary.

10.04. Patch and Copy semantics apply at the level of committed value meaning
      rather than raw chunk storage identity.

10.05. Chunk reuse or duplication is an implementation detail when committed
      value meaning remains preserved.

10.06. Turnix does not let static origin bypass the normal committed
      representation contract.

10.07. Turnix does not treat raw storage reuse as semantic equivalence unless
      committed value meaning is actually preserved.


===============================================================================
11. PAYLOAD SHARING, ROOTS, AND REACHABILITY
===============================================================================

11.01. Payload chunks may be shared across retained artifacts.

11.02. The same ChunkId may be referenced by multiple retained artifacts
       such as:
      - committed state roots
      - Windows
      - Window manifests
      - traces
      - journals
      - exports
      - Minimal Audit Bundle manifests
      - SaveBundle manifests

11.03. Payload sharing does not change authority boundaries.

11.04. Payload sharing is safe only when reachability can be determined from
      explicit retained roots.

11.05. All retained chunk references use ChunkId.

11.06. Storage realization allows enumeration of chunk references from a root
      manifest sufficient to compute reachability.

11.07. Garbage collection may delete chunks unreachable from all retained roots
      according to explicit policy.

11.08. Garbage collection does not delete any chunk reachable from an
      authoritative retained root.

11.09. Garbage collection creates a representation-domain trace emission
      obligation when performed in a running Turnix context.

11.10. Trace retention, trace pruning, trace loss, event structure, span
       mechanics, and trace storage semantics remain owned by DA-03.

11.11. Example retained roots include:
       - SaveBundle manifests
       - pinned Window manifests
       - pinned Minimal Audit Bundle manifests
       - other explicitly designated policy roots

11.12. Example retained roots are illustrative and do not lock the full future
       root catalog.

11.13. Sharing does not promote non-authoritative artifacts into authority.

11.14. Reachability determines retention safety. It does not redefine what kind
       of artifact a root represents.

11.15. Turnix does not silently collect payload that authoritative retained
       roots still require.


===============================================================================
12. BOUNDARY TO PERSISTENT I/O AUTHORITY
===============================================================================

12.01. This document defines payload representation and identity semantics.

12.02. This document does not define who may read or write persistent payload
      material directly.

12.03. Persistent access required to resolve retained Chunk material or
      committed ValueRef payload routes through the centralized persistent I/O
      authority defined by DA-07.

12.04. Packs do not resolve chunk storage directly.

12.05. Packs do not write payload bytes referenced by authoritative committed
      ValueRefs directly.

12.06. Readers, Writers, codecs, and storage providers that realize this
      representation contract remain subordinate to DA-07 persistent I/O
      authority.

12.07. Representation semantics remain stable even if the persistent storage
      backend changes.

12.08. Persistent I/O authority controls access. It does not redefine the
      representation meaning defined by this document.

12.09. SaveBundle may physically retain payload material. That physical
      retention does not make SaveBundle a Pack and does not transfer
      persistent I/O authority to Pack code.

12.10. Turnix does not allow direct storage access to become a shadow authority
       path for committed value meaning.


===============================================================================
13. OPTIONAL CAPABILITIES AND OPEN ENCODING CHOICES
===============================================================================

13.01. Storage realizations may support optional capabilities such as:
      - compression
      - encryption at rest
      - chunk streaming
      - logical chunk packing into containers
      - partial retrieval through index chunks

13.02. Optional capabilities do not change Chunk or ValueRef identity semantics.

13.03. If storage transforms bytes for transport or persistence convenience,
      Chunk identity still follows the canonical payload rule defined by the
      storage realization that implements this contract.

13.04. Paging and partial retrieval are expressed through retained chunk or
      index-chunk structure rather than hidden references outside explicit
      reachability.

13.05. The exact ChunkId encoding remains open.

13.06. Concrete digest algorithms remain open.

13.07. Concrete canonical serialization rules remain open except where some
      later authoritative document defines them for a specific artifact class.

13.08. Concrete codec implementation remains open except where an owning
      implementation specification defines it.

13.09. Concrete storage layout remains open except where an owning
      implementation specification defines it.

13.10. Optional capability does not authorize hidden semantic drift.

13.11. Open encoding choice does not permit backend-specific weakening of the
       identity contract defined by this document.


===============================================================================
14. LOCKED SUMMARY
===============================================================================

14.01. LOCKED:
      - committed values are represented through immutable payload references
        rather than live runtime object identity
      - a committed key is representable as key -> ValueRef at the commit
        boundary
      - Chunk is immutable byte payload identified by stable ChunkId
      - ChunkId is content-derived and independent of path, machine, and
        wall-clock accident
      - Chunk identity is format-aware
      - integrity failure is explicit and corrupt payload is not treated as
        authoritative
      - decode failure is explicit and failed decode is not treated as valid
        authoritative content
      - ValueRef is immutable and decodes deterministically from retained
        authoritative payload material
      - ValueRef forms are InlineValueRef and ChunkValueRef
      - arbitrary file-path and arbitrary network references are not ValueRef
        forms
      - committed values are schemaless by default with optional schema linkage
      - static origin does not bypass committed representation
      - payload sharing across retained artifacts does not change authority
        boundaries
      - reachability is determined from explicit retained roots
      - garbage collection does not delete chunks reachable from authoritative
        retained roots
      - representation-domain trace wording means trace emission obligation,
        not trace persistence guarantee
      - trace substrate, retention, pruning, loss, event structure, span
        mechanics, and trace storage semantics remain owned by DA-03
      - committed-state authority and transaction semantics remain owned by
        DA-04
      - persistent I/O authority remains owned by DA-07
      - Window finalization remains owned by DA-08
      - artifact and export semantics remain owned by DA-25
      - comparison, Replay, Resume, Retry, and audit workflow semantics remain
        owned by DA-26
      - SaveBundle and persistence documents own durable persistence closure,
        retained material, storage, compatibility, and recovery semantics
      - representation semantics are separate from persistent I/O authority

14.02. OPEN:
      - exact ChunkId encoding
      - concrete digest algorithms
      - concrete canonical serialization rules
      - concrete codec implementation
      - concrete storage layout
      - optional storage capabilities within the constraints of this document
      - reachability graph storage and garbage-collection algorithm details
