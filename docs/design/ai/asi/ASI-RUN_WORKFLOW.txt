Turnix Assistant Semantic Index run workflow entrypoint
=======================================================

Purpose
-------
This file is the human-facing entrypoint for running or preparing Assistant
Semantic Index workflows.

This file is non-authoritative workflow guidance. It does not define Turnix
semantics.

Use this file when
------------------
Use this file when the user provides an ASI_WORKFLOW_CALL block or otherwise
asks to run, prepare, inspect, or dry-run an ASI workflow.

Do not use this file to answer ordinary Turnix semantic questions.

Do not use this file to ask ASI indexes what canonical material should be
loaded for a topic. Use ASI-ASK_INDEX_FOR_LOADS.txt for that.

Runner role
-----------
The workflow runner resolves workflow calls into bounded work.

The runner may:
- read ASI workflow registries
- read ASI load groups
- read ASI batch registry entries
- read ASI file index entries
- load the workflow prompt declared by the resolved workflow
- prepare a launch prompt for a fresh thread
- perform a dry-run plan
- run a workflow in the current thread when allowed by the workflow contract and
  explicit user instruction

The runner must not:
- invent workflow IDs
- silently fill missing required parameters
- treat ASI metadata as Turnix authority
- run generated-output workflows unless the workflow registry declares them
- write files outside the resolved workflow contract
- continue through workflow contract conflicts
- use repository search to replace required exact file loading

Required initial loads
----------------------
Before resolving an ASI_WORKFLOW_CALL, load and classify as COMPLETE:
- docs/AI_WORKFLOW_BOOTSTRAP.txt
- docs/design/ai/asi/ASI-RUN_WORKFLOW.txt
- docs/design/ai/asi/ASI-WORKFLOW_CALL_FORMAT.txt
- docs/design/ai/asi/registry/ASI-FILE_INDEX.txt
- docs/design/ai/asi/registry/ASI-WORKFLOW_REGISTRY.txt
- docs/design/ai/asi/registry/ASI-LOAD_GROUPS.txt

Load this when BATCH_ID is present or when the workflow registry declares a
batch-aware workflow:
- docs/design/ai/asi/registry/ASI-BATCH_REGISTRY.txt

Load this when PROGRESS_LOG is compact or structured:
- docs/design/ai/asi/ASI-PROGRESS_LOGGING.txt

Load CMR-04 when the workflow requires canonical DOC_ID resolution:
- docs/CMR-04_CANONICAL_INDEX_TURNIX_SPECIFICATION.txt

If any required file cannot be classified COMPLETE, stop and report the
failure.

Invocation format
-----------------
ASI_WORKFLOW_CALL syntax is defined in:

docs/design/ai/asi/ASI-WORKFLOW_CALL_FORMAT.txt

Example:

ASI_WORKFLOW_CALL
WORKFLOW_ID: asi.document.extract
BRANCH: CHATGPT_EXTRACT_INDEX
DOC_ID: DA-03
BATCH_ID: Batch 1 foundation
EXECUTION_TARGET: new_thread_launch_prompt
END_ASI_WORKFLOW_CALL

Branch fields
-------------
BRANCH is the normal user-facing shorthand for ordinary ASI workflows.

When BRANCH is supplied, the runner resolves:

READ_BRANCH: <BRANCH>
WRITE_BRANCH: <BRANCH>

READ_BRANCH is the repository branch used for repository file loads.

WRITE_BRANCH is the repository branch used for repository file writes when the
workflow writes.

Generated launch prompts must use READ_BRANCH and WRITE_BRANCH explicitly.
They must not rely on a bare BRANCH field for repository file loading.

For ordinary ASI workflows, READ_BRANCH and WRITE_BRANCH should match. If they
differ, the prompt must explicitly say the split read/write branch behavior is
intended.

For current_thread execution of any workflow that may write repository files,
WRITE_BRANCH is required.

For any workflow that reads repository files, READ_BRANCH is required.

For new_thread_launch_prompt and dry_run_plan, the runner may use an active task
branch as both READ_BRANCH and WRITE_BRANCH only when that branch is already
unambiguous in the current task.

If no BRANCH, READ_BRANCH, or WRITE_BRANCH is supplied and no active task branch
is unambiguous, the runner stops and asks for the missing branch information.

Repository load rule
--------------------
All repository file loads in generated launch prompts must name READ_BRANCH.

Required loads should use wording like:

From repository EnterTheNameHere/Turnix, branch <READ_BRANCH>, load and classify
COMPLETE:
- path: docs/AI_WORKFLOW_BOOTSTRAP.txt
  branch: <READ_BRANCH>

If READ_BRANCH is missing, stop before repository loading and report
MISSING_READ_BRANCH.

If a file was loaded from a branch other than READ_BRANCH, report
LOAD_BRANCH_VIOLATION.

Do not classify a file as missing based on a load from the wrong branch.

Repository write rule
---------------------
All repository writes in generated launch prompts must name WRITE_BRANCH.

If WRITE_BRANCH is missing for a write-capable workflow, stop before writing and
report MISSING_WRITE_BRANCH.

If a write would target a branch other than WRITE_BRANCH, stop and report
WRITE_BRANCH_VIOLATION.

Progress logging
----------------
PROGRESS_LOG controls optional user-visible progress callouts.

Accepted values:
- none
- compact
- structured

Default:

PROGRESS_LOG: none

When PROGRESS_LOG is compact or structured, load:

docs/design/ai/asi/ASI-PROGRESS_LOGGING.txt

Progress logging does not change required loads, read boundaries, write
boundaries, stopping conditions, or execution target behavior.

Progress logging must not add separate timing tool calls, Python calls, Bash
calls, or clock formatting.

Resolution steps
----------------
For each ASI_WORKFLOW_CALL:

1. Parse the invocation block.
2. Verify WORKFLOW_ID is present.
3. Resolve BRANCH shorthand into READ_BRANCH and WRITE_BRANCH when used.
4. Verify READ_BRANCH and WRITE_BRANCH are present as required by the workflow.
5. Resolve WORKFLOW_ID through ASI-WORKFLOW_REGISTRY.txt.
6. Verify required parameters are present.
7. Verify repeated fields only use registry-declared REPEATABLE_PARAM entries.
8. Apply explicit default values for omitted optional parameters.
9. Resolve and validate PROGRESS_LOG.
10. Load ASI-PROGRESS_LOGGING.txt when PROGRESS_LOG is compact or structured.
11. Resolve BATCH_ID through ASI-BATCH_REGISTRY.txt when required or supplied.
12. Resolve DOC_ID through CMR-04 when required.
13. Resolve ordinary LOAD_GROUP entries through ASI-LOAD_GROUPS.txt.
14. Record LOAD_GROUP_BEFORE_WRITE entries as deferred write-phase loads.
15. Load the workflow prompt declared by the registry entry.
16. Check for contract conflicts between the registry, load groups, and
    workflow prompt.
17. Apply the requested EXECUTION_TARGET.

Deferred write-phase load groups
--------------------------------
LOAD_GROUP entries are required before the workflow body starts.

LOAD_GROUP_BEFORE_WRITE entries are required only before the named write class
or write phase starts.

The runner does not treat LOAD_GROUP_BEFORE_WRITE entries as ordinary startup
LOAD_GROUP entries.

When EXECUTION_TARGET is dry_run_plan or new_thread_launch_prompt, the runner
reports deferred write-phase load groups but does not load them unless the
assignment explicitly asks for full write-readiness checking.

When EXECUTION_TARGET is current_thread and the workflow reaches the named write
phase, the runner loads each required LOAD_GROUP_BEFORE_WRITE group before that
write phase begins.

If a deferred write-phase load group cannot be classified COMPLETE, the runner
stops before the write phase.

Contract conflict rule
----------------------
If loaded workflow/control files disagree about required loads, allowed writes,
forbidden writes, role authority, generated-output boundaries, execution target
support, branch requirements, or required parameters, stop and report a workflow
contract conflict.

Do not silently choose the stricter or looser rule.

The assistant may describe the stricter behavior as the temporary safe
interpretation, but it must not execute the workflow until the conflict is
resolved by explicit user or supervisor instruction.

Execution targets
-----------------
current_thread:
Run the workflow in this conversation only if the workflow registry and workflow
prompt allow current-thread execution and the user clearly requested it.

new_thread_launch_prompt:
Prepare a copy-paste first message for a fresh thread.

The launch prompt must include repository identity, READ_BRANCH, WRITE_BRANCH,
required loads with branch visibility, role declaration, assigned parameters,
task statement, read boundary, write boundary, forbidden writes, stopping
conditions, execution-target context, and progress-log mode.

dry_run_plan:
Report resolved workflow ID, prompt file, required files, required parameters,
repository, READ_BRANCH, WRITE_BRANCH, read permissions, write permissions,
forbidden writes, expected outputs, and blocking issues. Do not run the workflow
body.

Launch prompt skeleton
----------------------
For new_thread_launch_prompt, print a complete launch prompt in this shape:

BEGIN ASI GENERATED LAUNCH PROMPT
WORKFLOW_ID:
ROLE:
REPOSITORY:
READ_BRANCH:
WRITE_BRANCH:
BRANCH_RULE:
READ_BRANCH_RULE:
WRITE_BRANCH_RULE:
EXECUTION_TARGET:
PROGRESS_LOG:
ASSIGNED_PARAMETERS:
REQUIRED_LOADS:
DEFERRED_WRITE_PHASE_LOADS:
TASK:
MAY_READ:
MAY_WRITE:
MUST_NOT_READ:
MUST_NOT_WRITE:
STOPPING_CONDITIONS:
FINAL_REPORT_REQUIREMENTS:
END ASI GENERATED LAUNCH PROMPT

The generated launch prompt may use plain prose inside each field, but it keeps
these field labels so another assistant can parse the launch context reliably.

Required loads in generated launch prompts must show the branch at the file level
when practical:

- path: docs/AI_WORKFLOW_BOOTSTRAP.txt
  branch: <READ_BRANCH>

Stopping conditions in generated launch prompts must include:
- Stop if READ_BRANCH is missing.
- Stop if WRITE_BRANCH is missing for a write-capable workflow.
- Stop if any repository file load is attempted without using READ_BRANCH.
- Report wrong-branch loads as LOAD_BRANCH_VIOLATION, not as MISSING,
  TRUNCATED, or NOT PROVEN COMPLETE.
- Stop if any repository write is attempted without using WRITE_BRANCH.
- Report wrong-branch writes as WRITE_BRANCH_VIOLATION.

When PROGRESS_LOG is compact or structured, the first progress callout should
include READ_BRANCH, for example:

Starting required-file access from READ_BRANCH: <READ_BRANCH>.

Write boundary
--------------
The runner itself does not create generated ASI output unless the resolved
workflow is explicitly an output-writing workflow and EXECUTION_TARGET is
current_thread.

When preparing a launch prompt, the runner writes no repository files.

When producing a dry-run plan, the runner writes no repository files.

When running a workflow in the current thread, writes are limited to the
MAY_WRITE entries declared by the resolved registry entry and any stricter
workflow prompt rule.

Repository write authority still requires complete source state and update SHA
handling as defined by AI_WORKFLOW_BOOTSTRAP.

Final report
------------
For dry-run or current-thread execution, report:
- WORKFLOW_ID
- resolved workflow prompt
- repository
- read branch used for repository loads
- write branch used for repository writes when applicable
- required parameters
- repeatable parameters used
- progress-log mode
- resolved DOC_ID and source path when applicable
- resolved BATCH_ID when applicable
- required load groups
- deferred write-phase load groups
- files loaded and retrieval classification
- allowed writes
- forbidden reads
- forbidden writes
- execution target
- blocked items or contract conflicts

For launch-prompt output, print the complete launch prompt in a text code block.

END
