SEMANTIC_ANCHORS
----------------
- UI is presentation and interaction, not authoritative state, capability
  authority, policy authority, or persistence authority by itself.
- A View is a kernel-recognized frontend runtime surface that receives state and
  sends interaction through Turnix-mediated channels.
- User interaction becomes meaningful only when the kernel accepts the
  corresponding command, decision, capability call, or RPC message.
- Frontend runtime code is adapter-executed frontend code under DA-23.
- Frontend adapter execution does not grant authority by itself.
- A View or frontend client may act as a RuntimeHost entry surface only when
  DA-28 and the relevant runtime workflow define that relationship.
- View identity, AppInstance identity, frontend client identity, user identity,
  frontend adapter identity, and RuntimeHost identity are distinct concepts.
- View creation does not activate packs by itself.
- View creation does not create an AppInstance by itself unless an explicit
  launcher or runtime workflow defines that behavior.
- View readiness does not imply AppInstance readiness, RuntimeHost readiness,
  pack activation success, or frontend adapter execution success beyond the View
  readiness condition itself.
- View disconnect is a frontend or transport condition and does not silently
  cancel Jobs, fail adapters, deactivate AppInstances, stop RuntimeHosts, or
  discard authoritative state.
- Frontend runtime code does not mutate files directly as a Turnix authority path
  and does not bypass adapter, RPC, capability, policy, transaction,
  persistence, or RuntimeHost boundaries.
- Presentation-local state does not become committed state unless a
  kernel-mediated mutation commits it under DA-04 and related documents.
- View packs remain subject to normal pack, import, adapter selection,
  execution authorization, activation, visibility, and capability rules.
- Frontend-side validation may improve user experience but does not replace
  kernel validation, capability permission, execution authorization, or policy
  evaluation.
- UI event order does not by itself define committed-state order or RuntimeHost
  operation order.
- Decision presentation is not decision ownership.
- The UI does not invent hidden defaults or auto-confirm decisions without policy
  authority.
- Debugger UI is a frontend surface for debugger behavior and does not own
  debugger semantics.
- Accessibility and presentation transforms do not mutate authoritative state or
  change capability, permission, decision, Job, adapter, RuntimeHost, or
  debugging semantics by themselves.
- UI-domain trace evidence does not replace RPC, adapter, decision,
  RuntimeHost, capability, Job, debugger, or AppInstance trace evidence.
- UI-domain trace reason identifiers describe UI/View behavior only.
- UIRuntimeHostCommandRequested does not define RuntimeHost command acceptance,
  RuntimeHost operation success, or RuntimeHost lifecycle outcome.

CONFUSABLE_TERMS

- UI vs authoritative state

        itself.

- View vs AppInstance
  CONFIDENCE: explicit
  NOTE: View identity is distinct from AppInstance identity; one AppInstance may
        have zero, one, or multiple Views.

- View vs frontend client
  CONFIDENCE: explicit
  NOTE: A frontend client is a concrete connected instance such as a browser tab;
        View is the kernel-recognized frontend surface.

- frontend client identity vs user identity
  CONFIDENCE: explicit
  NOTE: Frontend client identity is distinct from user identity.

- frontend adapter identity vs View identity
  CONFIDENCE: explicit
  NOTE: Frontend adapter identity is distinct from View identity and frontend
        client identity.

- View identity vs RuntimeHost identity
  CONFIDENCE: explicit
  NOTE: DA-22 explicitly separates these identities and routes RuntimeHost
        meaning to DA-28.

- frontend adapter execution authorization vs capability permission
  CONFIDENCE: explicit
  NOTE: Authorization to execute frontend adapter code is distinct from
