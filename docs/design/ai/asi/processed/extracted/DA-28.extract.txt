Semantic anchors
----------------
- RuntimeHost is the running Turnix host boundary; it is not Kernel.
- RuntimeHost binds a workspace or runtime scope and exposes controlled entry
  surfaces.
- Kernel owns authority; RuntimeHost coordinates access to Kernel-owned
  authority.
- Deployment shape, process location, command syntax, network exposure, and
  implementation framework do not grant authority.
- runtimeHostId is stable for one RuntimeHost lifetime and distinct from
  workspace, process, AppPack, SavePack, appInstanceId, viewId, adapter, RPC,
  channel, transport, capability, jobId, orchestrationUnitId, transaction, and
  decision identity.
- A writable workspace is owned by at most one RuntimeHost at a time unless a
  later authoritative multi-host design defines another mode.
- Second host behavior must not silently acquire ownership, discard evidence,
  supersede another host, detach work, or claim owned results.
- Startup modes are entry workflows over shared Kernel-mediated runtime
  operations, not separate runtime semantics.
- Entry surfaces and command surfaces are not authority by themselves.

- Local-first means user-controlled local infrastructure, not necessarily
  same-machine execution.

- RuntimeHost lifecycle does not by itself define AppInstance, View, adapter,
  RPC transport, Job, Orchestration Unit, Window, or committed-state outcomes.

Confusable terms
----------------
- RuntimeHost vs Kernel:
  RuntimeHost is the running host boundary; Kernel owns runtime authority.

- RuntimeHost vs AppInstance:
  RuntimeHost may load AppInstances, but runtimeHostId and appInstanceId remain
  distinct and lifecycle semantics are separate.

- RuntimeHost workspace ownership vs SavePack write authority:
  Workspace ownership does not make RuntimeHost or adapter-executed code the
  SavePack writer.

- Startup mode vs runtime semantics:
  Startup mode selects entry workflow; it does not create separate AppInstance,
  SavePack, adapter, RPC, capability, policy, persistence, Orchestration Unit,
  Job, View, or trace semantics.

- Entry surface vs authority:
  CLI, frontend, remote client, test surface, and launcher surface are ways in;
  they are not authority by themselves.

- Command receipt vs command acceptance vs command completion:
  These are separate command-surface states; completion is not automatically Job
  success.

- RuntimeHost operation vs Orchestration Unit:
  A RuntimeHost operation is a host-level requested action; an Orchestration
  Unit is the Kernel-tracked execution-authority unit for orchestrated mutation.

- RuntimeHost lifecycle vs Job, Window, adapter, AppInstance, View, RPC, and
  Orchestration Unit lifecycle:
  RuntimeHost stop, failure, or crash does not automatically define outcomes in
  those domains.

- Local-first vs same-machine:
  Local-first permits LAN/home-server/local-infrastructure forms and does not
  require same-machine execution.

- LAN access vs authority:
  LAN or remote access does not imply state authority, adapter execution
  authority, capability permission, or user identity.
