SEMANTIC_ANCHORS
----------------
- A dependency is a hard functional requirement: the pack cannot function correctly unless another pack satisfies the request.
- Dependencies are contracts, not preferences.
- Declaring a dependency does not load code, activate a pack, grant visibility, grant capabilities, or define activation order.
- Failure to satisfy a hard dependency is a hard failure unless accepted policy or user decision explicitly resolves it.
- Shared syntax does not imply shared semantics; packs, advisory fields, and role-related fields may reuse pack specifiers with different meanings.
- Fingerprint is an optional strengthening of an exact concrete pack form, not a vague compatibility hint.
- Every entry under packs is a hard dependency, and list order carries no semantic meaning by itself.
- A dependency is satisfied when at least one normalized accepted entry resolves successfully under the active dependency source and context.
- Multiple accepted entries express one-of semantics at the accepted-entry level.
- Fingerprint requires exact concrete version; name-plus-fingerprint without version and range-plus-fingerprint are invalid.
- Hard dependency failure does not cause automatic disabling, silent downgrade, implicit fallback, or best-effort substitution.
- Dependency resolution produces exactly one concrete target, one classified failure, or one classified ambiguity requiring external decision.
- SaveOnly, GlobalPinned, and GlobalNormal are mutually exclusive dependency-resolution sources.
- GlobalNormal selection is procedural and deterministic: version handling, author relationship, root precedence, then lexicographic tie-break.
- Silent substitution is forbidden.
- requiredRoles and providedRoles are separate from packs and do not force loader reordering or magical dependency-graph mutation.
- Advisory pack relations are hints for Pack Manager, UI, compatibility presentation, and load-list assembly; they are not dependency graph enforcement.
- Ambiguity pauses resolution and requires user decision or accepted policy input that is persisted by the surrounding consumer.
- Last-known-good fallback is used only after activation failure and is not consulted during dependency resolution.

CONFUSABLE_TERMS
----------------
- TERM: dependency vs preference
  DISTINCTION: Dependency is a hard functional requirement; advisory fields express compatibility or ecosystem hints.
- TERM: packs vs supportedPacks / conflictingPacks / recommendedPacks
  DISTINCTION: packs declares hard dependencies; advisory fields do not enforce dependency graph validity or activation blocking.
- TERM: shared pack-specifier syntax vs shared semantics
  DISTINCTION: The same specifier structure may be reused, but the surrounding field defines the meaning.
- TERM: PackRequest grammar vs dependency interpretation
  DISTINCTION: DA-11 owns PackRequest parsing and generic mechanics; DA-13 owns how dependency policy uses the request.
- TERM: fingerprint vs version compatibility
  DISTINCTION: Fingerprint is an exact-artifact lock and requires an exact concrete version.
- TERM: multiple accepted entries vs multiple dependencies
  DISTINCTION: Multiple accepted entries inside one dependency express one-of satisfaction; separate packs entries are separate hard dependencies.
- TERM: SaveOnly vs GlobalPinned vs GlobalNormal
  DISTINCTION: These are mutually exclusive dependency-resolution sources; the resolver does not mix or silently fall back between them.
- TERM: GlobalPinned vs saved copied pack
  DISTINCTION: GlobalPinned uses a pinned concrete identity in the global registry; SaveOnly uses copied packs inside a SavePack.
- TERM: provider-role requirement vs runtime capability call
  DISTINCTION: requiredRoles is a dependency/resolution-layer declaration, not a capability invocation or service lookup.
- TERM: dependency resolution vs activation
  DISTINCTION: Dependency resolution does not activate packs, load code, or grant runtime access.
- TERM: dependency failure vs last-known-good fallback
  DISTINCTION: Last-known-good fallback is not used during dependency resolution; it is only attempted after activation failure.
- TERM: deterministic selection vs scoring
  DISTINCTION: DA-13 defines procedural ordering for GlobalNormal; no scoring model exists in DA-13.
