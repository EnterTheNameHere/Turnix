Cross-document traps
--------------------
- TRAP: Discovery is not resolution, dependency satisfaction, importing, activation, or PackManager catalog reading.
  PRIMARY_DOCS: DA-09; DA-11; DA-13; DA-12; DA-14; DA-29
  NOTES: DA-09 owns root/category scanning, manifest discovery, PackDescriptor production, and rejected candidates. DA-11 selects from an already-built registry snapshot. DA-13 interprets dependency requests. DA-12 handles import/module loading boundaries. DA-29 consumes discovered/indexed descriptors for catalog and graph-preparation behavior.

- TRAP: Root/category precedence is not a universal winner-selection rule.
  PRIMARY_DOCS: DA-09; DA-11; DA-13
  NOTES: DA-09 records content-root precedence as a discovery/root input. DA-11 owns generic deterministic selection mechanics. DA-13 adds dependency-specific GlobalNormal ordering. Do not answer dependency or generic resolution questions from root precedence alone.

- TRAP: Pack identity, hierarchy, visibility, and access-control reachability must not be collapsed.
  PRIMARY_DOCS: DA-10; DA-15
  NOTES: DA-10 owns identity layers, hierarchy, declaredId, packTreeId, author/version inheritance, local visibility defaults, exportNestedPacks, importPacksFromParent, and computed global visibility in the identity/hierarchy context. DA-15 owns pack-to-pack reference permission, visibility failure behavior, reachability gates, source isolation, and PermissionDeniedError semantics.

- TRAP: Visibility is not dependency satisfaction, activation, service access, capability permission, or state mutation authority.
  PRIMARY_DOCS: DA-15; DA-13; DA-14; DA-16; ODA-E
  NOTES: A visible pack may still fail dependency resolution or activation. A dependency target may exist but be unreachable by visibility. Visibility does not grant capability/service authority. ODA-E is only an optional state-access authority model and should not be used to replace DA-15, DA-16, or higher-authority state documents.

- TRAP: PackRequest grammar is not dependency meaning and is not turnixImport selector syntax.
  PRIMARY_DOCS: DA-11; DA-13; DA-12
  NOTES: DA-11 owns PackRequest parsing grammar and generic resolution mechanics. DA-13 owns how PackRequest-like entries behave as hard dependencies and shared pack-specifier fields. DA-12 excludes semver-qualified selectors from turnixImport and requires import selectors to match already-resolved dependency identity.

- TRAP: Importing is not resolution, dependency declaration, activation, execution authorization, or capability permission.
  PRIMARY_DOCS: DA-12; DA-11; DA-13; DA-14; DA-16
  NOTES: DA-12 owns native import limits, turnixImport, default/sub-entry JavaScript import behavior, Python pack-code boundaries, and strict import errors. Resolution selects identity; dependency declaration states requirements; activation is a lifecycle step; capabilities and permissions remain separately mediated.

- TRAP: Module evaluation is not Turnix-recognized activation.
  PRIMARY_DOCS: DA-12; DA-14
  NOTES: DA-12 treats ESM module evaluation, immediate execution, IIFE patterns, top-level side effects, and background work outside Turnix orchestration as outside Turnix guarantees. DA-14 owns activation lifecycle and onLoad(ctx) behavior when activation is the question.

- TRAP: Dependencies are hard functional requirements, not advisory compatibility hints or PackManager presentation warnings.
  PRIMARY_DOCS: DA-13; DA-29; ODA-D
  NOTES: DA-13 owns packs as hard dependency semantics and separates hard dependencies from supportedPacks, conflictingPacks, recommendedPacks, and provider roles. DA-29 may present advisory relations during catalog/graph work. ODA-D's compatibility split is optional and subordinate to higher-authority dependency, activation, adapter, and AppInstance documents.

- TRAP: Dependency source models must not silently mix or fall back between SaveOnly, GlobalPinned, and GlobalNormal.
  PRIMARY_DOCS: DA-13; DA-09; DA-10; DA-11; DA-15
  NOTES: DA-13 owns mutually exclusive dependency-resolution sources and deterministic GlobalNormal ordering. DA-09 supplies save/global discovery context. DA-10 and DA-15 supply identity/visibility constraints. DA-11 supplies generic resolver mechanics. Do not convert source mismatch into automatic fallback.

- TRAP: SavePack behavior appears in multiple documents but each owns a different layer.
  PRIMARY_DOCS: DA-09; DA-10; DA-13; DA-15; DA-29; ODA-D; ODA-E
  NOTES: DA-09 owns SavePack discovery and default shallow scanning. DA-10 owns save-local visibility in identity/hierarchy framing. DA-15 owns SavePack visibility isolation and save-scoped reachability. DA-13 owns SaveOnly/copied and GlobalPinned dependency source semantics. DA-29 owns PackManager SavePack graph checks and presentation semantics. ODA-D offers optional exact-version pinning/update-safety framing. ODA-E offers optional state-access framing.

- TRAP: PackManager is official tooling, not authority bypass.
  PRIMARY_DOCS: DA-29; DA-09; DA-11; DA-13; DA-14; DA-16; DA-17
  NOTES: DA-29 owns PackManager semantic boundaries, catalog operations, selected graph intent, activation-plan preparation meaning, and PackManager trace reasons. It does not rescan by catalog reading, silently resolve ambiguity, import code, activate packs, grant capabilities, persist remembered decisions, or bypass Kernel-mediated boundaries.

- TRAP: Selected pack graph, activation plan, activation lifecycle, and last-known-good fallback are separate concepts.
  PRIMARY_DOCS: DA-29; DA-14; DA-13; ODA-D
  NOTES: DA-29 owns selected pack graph and activation-plan preparation meaning. DA-14 owns activation lifecycle and activation failure handling. DA-13 says last-known-good fallback is not part of dependency resolution. ODA-D discusses optional update-safety and rollback ideas only within its subordinate compatibility model.

- TRAP: Optional design areas must not be promoted above DA documents.
  PRIMARY_DOCS: ODA-D; ODA-E; DA-11; DA-13; DA-14; DA-20; DA-23; DA-04; DA-16
  NOTES: ODA-D and ODA-E are optional design areas. Use them for optional compatibility and state-access models, but route final authority to higher DA documents when the question asks for authoritative resolution, dependency, activation, adapter, AppInstance, persistence, capability, or permission semantics.

- TRAP: Candidate existence, catalog listing, visibility, selected graph membership, importability, activation state, and capability availability must stay distinct.
  PRIMARY_DOCS: DA-09; DA-10; DA-11; DA-12; DA-13; DA-15; DA-29; DA-16
  NOTES: Batch 3 repeatedly separates stages and authority layers. Index generation should avoid phrases that imply a listed or discovered pack is automatically visible, resolved, importable, active, dependency-satisfied, or capability-authorized.
