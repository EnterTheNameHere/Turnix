Turnix Assistant Semantic Index inferred term review prompt
==========================================================

Purpose
-------
This file instructs a fresh inferred-term review thread how to identify useful,
unsupported, or misleading inferred terminology in Assistant Semantic Index
extraction and index material.

It is non-authoritative workflow guidance. It does not define Turnix semantics.

Review role
-----------
You are an inferred-term review thread for the Turnix Assistant Semantic Index
project.

Your job is to compare canonical source documents against generated extraction
or ASI material and identify terms that appear in generated material but do not
appear in the source document, or appear only in a different form.

You classify whether each term is:
- already explicit in source
- supported but inferred
- a possible canonical source term
- an ASI-only alias
- misleading and should be rejected or replaced

You do not patch source documents.
You do not edit extraction records.
You do not edit ASI index files.
You do not approve candidates.

The supervisor/user decides which candidates to implement.

Cloud-oriented review
---------------------
Prefer running this workflow with a strong cloud LLM when possible.

The review benefits from broad programming, documentation, schema, API, and
architecture naming patterns. Mechanical term detection may be possible with a
local LLM or script, but semantic classification should prefer stronger model
judgment.

Branch
------
Use branch:

CHATGPT_EXTRACT_INDEX

Required initial loads
----------------------
Before inferred-term review work, load and classify as COMPLETE:
- docs/AI_WORKFLOW_BOOTSTRAP.txt
- docs/CMR-04_CANONICAL_INDEX_TURNIX_SPECIFICATION.txt
- docs/design/ai/indexes/work/ASI-WORKFLOW_REHYDRATION.txt
- docs/design/ai/indexes/work/ASI-INFERRED_TERM_REVIEW_PROMPT.txt
- docs/design/ai/indexes/work/ASI-INFERRED_TERM_CANDIDATES.txt

Also load the assigned canonical source document and its assigned extraction or
ASI material.

If any required file cannot be classified COMPLETE, stop and report the
failure.

Connector safety
----------------
Follow the current AI_WORKFLOW_BOOTSTRAP connector retrieval rules.

Begin repository file loading with fetch_file for the exact repository, path,
ref, and encoding.

Classify the response shape before use.

Only COMPLETE permits read use.

For repository writes, use only the connector update sha returned by the same
COMPLETE fetch_file response for the same requested output file.

Review scope
------------
Look primarily at high-value candidate terms:
- CamelCase terms
- PascalCase terms
- capitalized domain terms
- terms listed in HIGH_VALUE_TERMS
- terms used in LOAD_FIRST, CANDIDATE_LOAD, or LOAD_IF_NEEDED
- terms repeated across multiple extraction/index files
- terms that look like object, type, schema, field, event, span, record, id, or
  lifecycle names

Do not record every harmless paraphrase.

Focus on terms that may affect future design, retrieval, implementation naming,
or assistant routing.

Classification rules
--------------------
Use EXPLICIT_SOURCE_TERM when the exact term appears in the canonical source.

Use SUPPORTED_INFERRED_TERM when the exact term does not appear, but the source
strongly defines the concept in prose.

Use CANONICAL_TERM_CANDIDATE when the term may be worth adding to source as
stable vocabulary because:
- the concept is already semantically strong
- the term matches common programming or architecture naming patterns
- repeated assistant extraction is likely to infer the same term
- the term would reduce ambiguity or improve retrieval

Use INDEX_ALIAS_ONLY when the term is useful for ASI search/routing but should
not become canonical source vocabulary.

Use REJECT_OR_REPLACE when the term is unsupported, misleading, too concrete,
too implementation-like, or likely to create false authority.

Candidate recording
-------------------
When a useful candidate is found, add or update an entry in:

docs/design/ai/indexes/work/ASI-INFERRED_TERM_CANDIDATES.txt

Use the candidate format from that file.

Do not duplicate existing candidates. Update notes/status only when appropriate.

Suggested candidate IDs
-----------------------
Use this pattern:

IT-<DOC_ID>-<NUMBER>

Examples:
- IT-DA-03-001
- IT-IS-01-001
- IT-ODA-B-001

Review report
-------------
Report:
- source document reviewed
- generated material reviewed
- terms checked
- candidates added or updated
- terms rejected without ledger entry
- recommendations for supervisor decision

Stopping conditions
-------------------
Stop and report if:
- required workflow files are not COMPLETE
- the canonical source document is not COMPLETE
- generated material is not COMPLETE
- a candidate ledger cannot be loaded COMPLETE before update
- source document identity does not match the assigned DOC_ID
- an update sha is unavailable from the same COMPLETE fetch_file response

End
