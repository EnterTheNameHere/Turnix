Overall review
--------------
The Batch 1 extraction records are broadly good.

They preserve the main authority split:
- DA-01 owns foundational invariants and CT-D.
- DA-02 owns platform truth, contract boundaries, and implementation
  independence.
- DA-03 owns the trace substrate.
- DA-04 owns committed state, transactions, and authoritative mutation.
- DA-21 owns abstract RPC semantics and message-flow boundaries.
- IS-01 owns concrete RPC message-envelope schema.
- ODA-B owns optional developer diagnostics and tooling presentation that
  consume evidence.

The main weakness is not factual correctness. The main weakness is
cross-document retrieval sharpness. Several documents intentionally overlap in
terms such as trace, state, RPC, authority, diagnostics, correlation, evidence,
lifecycle, success, timeout, and disconnect. The extraction records should make
those boundaries more visible to fresh assistant threads.

Recommended batch-level improvement
-----------------------------------
Create a shared authority-boundary cluster for the final index layer.

Suggested cluster:

- valid envelope != successful work
- acknowledgement != request success
- acknowledgement != Job success
- trace evidence != committed state
- diagnostic presentation != authority
- persistence != truth
- runtime memory != committed state
- RPC stateUpdate != committed authoritative state mutation
- transport timeout != Job timeout
- transport disconnect != Job cancellation
- transport disconnect != adapter failure
- transport disconnect != RuntimeHost failure

Suggested authority ladder:

- DA-01: project invariant anchor
- DA-02: architectural contract-boundary anchor
- DA-03: trace evidence substrate
- DA-04: authoritative committed-state boundary
- DA-21: abstract RPC and message-flow boundary
- IS-01: concrete RPC envelope schema
- ODA-B: optional tooling presentation and diagnostics consumer

Suggested cross-layer routing rule:

When a question combines RPC, trace evidence, state, and success/failure,
resolve the layer first:
- DA-21 for abstract RPC delivery, acknowledgement, request acceptance,
  routing, subscription, cancellation, timeout, and disconnect meaning.
- IS-01 for concrete envelope fields, message type names, serialization,
  isComplete, final, origin, route, lane, payload, and job metadata carriage.
- DA-03 for trace semantics, retained evidence, causal links, trace loss, and
  correlation meaning.
- DA-04 for whether anything became committed authoritative state.
- DA-19 for Job lifecycle and terminal outcomes once Job-backed work exists.
- DA-23 for adapter lifecycle and execution-boundary outcomes.
- DA-28 for RuntimeHost lifecycle, command-surface, entry-surface, workspace,
  startup, LAN, and host-operation outcomes.
- ODA-B for how optional developer tooling should display, report, filter, or
  explain retained evidence.

Common retrieval traps
----------------------
Add explicit do-not-answer-from-this-document-alone guidance for common trap
questions.

Question: Did this RPC succeed?
Recommended load:
- DA-21 first.
- IS-01 if envelope fields or message type names matter.
- DA-19 if the work is Job-backed.
- DA-23 if the work is adapter-mediated.
- DA-28 if the work is a RuntimeHost operation.
Do not answer from IS-01 alone.

Question: Is this state authoritative?
Recommended load:
- DA-04 first.
- DA-03 only if trace/evidence/correlation is involved.
- ODA-B only if diagnostic presentation is involved.
Do not answer from DA-03 or ODA-B alone.

Question: What does this trace prove?
Recommended load:
- DA-03 first.
- DA-04 if the question asks whether trace evidence proves committed state.
- ODA-B if the question asks how tooling should display it.

Question: Does stateUpdate mean committed state changed?
Recommended load:
- IS-01 for the concrete stateUpdate message type.
- DA-21 for abstract update/subscription flow.
- DA-04 for authoritative committed-state mutation.
Do not infer committed-state mutation from the message name.

Question: Does isComplete mean the operation completed?
Recommended load:
- IS-01 for isComplete as envelope completion marker.
- DA-21 for message handling, request acceptance, and final work outcome
  distinctions.
- Owning lifecycle document if the operation is Job-backed, adapter-mediated,
  or RuntimeHost-owned.
