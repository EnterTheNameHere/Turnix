PRIMARY_DOMAINS
---------------
- Abstract RPC communication semantics.
- Transport-neutral channel boundaries.
- Logical request, reply, emit, subscribe, cancel, error, update, and acknowledgement flow.
- Distinction between message delivery, acknowledgement, request acceptance, handler execution, Job creation,
  lifecycle ownership, and final work outcome.
- Routing boundaries for object, capability, adapter-facing, control, and subscription messages.
- Transport timeout, disconnect, and cancellation semantics at the RPC layer.
- RPC correlation and trace-observability obligations.
- Relationship between DA-level RPC semantics and concrete implementation specifications.

OWNERSHIP_HINTS
---------------
- Owns RPC as a logical communication boundary.
- Owns RPCChannel as the abstract transport-neutral interface.
- Owns transport/channel separation at the DA level.
- Owns abstract RPC message categories and their high-level meanings.
- Owns abstract request acceptance, acknowledgement, routing, subscribe, unsubscribe, cancellation, timeout, and disconnect distinctions.
- Owns RPC acceptance/correlation relationships for Job-backed, adapter-mediated, and RuntimeHost-owned work without owning those lifecycle domains.
- Owns the boundary that transport delivery, acknowledgement, request acceptance, handler execution, Job creation, and final work outcome are distinct.

SEMANTIC_ANCHORS
----------------
- RPC is a logical boundary, not WebSocket, JSON, a transport, capability authority, adapter authority, RuntimeHost authority, or Job lifecycle.
- Transport carries RPC messages but does not define RPC semantics.
- RPCChannel is the transport-neutral surface consumed by the RPC host or equivalent runtime owner.
- Message delivery, acknowledgement, request acceptance, handler execution, Job creation, and Job terminal outcome are distinct events.
- Acknowledgement means receipt or transport/RPC handling only, not request success, capability execution, adapter execution, RuntimeHost operation completion, Job creation, or Job success.
- Request acceptance is distinct from final operation success unless an operation contract explicitly defines acceptance as the result.
- Routing identifies a logical target but does not grant permission, activate packs, select adapters, authorize adapters, or bypass capability mediation.
- State or update delivery and concrete stateUpdate messages do not by themselves define committed authoritative state mutation; DA-04 owns committed-state authority.
- Job-backed work, adapter-mediated work, and RuntimeHost operations use DA-21 for RPC acceptance/correlation only; lifecycle and terminal outcome semantics remain with their owning documents.
- Transport timeout and disconnect are RPC/channel/transport concerns, not Job, adapter, or RuntimeHost terminal outcomes by themselves.
- RPC cancellation is a request, not a direct execution kill.
- Subscription delivery may carry progress or state, but the meaning of Job, adapter, RuntimeHost, View, or committed-state evidence remains owned by the corresponding domain.
- RPC trace evidence preserves correlation between messages and higher-domain events where those events exist.
- Concrete envelope construction details, including IS-01 isComplete, remain schema concerns and must not be read as semantic work completion.

  TERM_B: execution adapter
  DISTINCTION: Transport adapters translate concrete transport events into RPCChannel events; execution adapter boundary semantics belong to DA-23.

- TERM_A: acknowledgement
  TERM_B: request success
  DISTINCTION: Acknowledgement confirms receipt or transport/RPC handling only; request success depends on the operation contract.

- TERM_A: acknowledgement
  TERM_B: Job success
  DISTINCTION: Acknowledgement does not imply Job creation or Job terminal success.

- TERM_A: request acceptance
  TERM_B: final operation success
  DISTINCTION: Acceptance means crossing the RPC dispatch boundary and target acceptance, not final success unless the operation contract defines that result.

- TERM_A: request completion / work completion
  TERM_B: IS-01 isComplete
  DISTINCTION: isComplete marks complete envelope construction; DA-21 separates message handling, request acceptance, and final work outcome.

- TERM_A: state or update messages / stateUpdate
  TERM_B: committed state mutation
  DISTINCTION: State/update delivery through RPC does not by itself define authoritative committed-state mutation; load IS-01 for concrete stateUpdate fields, DA-21 for delivery flow, and DA-04 for committed-state authority.

- TERM_A: transport timeout
  TERM_B: Job timeout
  DISTINCTION: Transport timeout is an RPC/channel/transport concern; Job timeout is a Job lifecycle concern owned by DA-19.

- TERM_A: transport disconnect
  TERM_B: Job cancellation
  DISTINCTION: Disconnect does not automatically cancel, supersede, discard, or fail Job-backed work.

- TERM_A: transport disconnect
  TERM_B: adapter failure / RuntimeHost failure
  DISTINCTION: Disconnect does not automatically fail an adapter or stop/fail a RuntimeHost; DA-23 or DA-28 owns those lifecycle outcomes.

- TERM_A: unsubscribe
  TERM_B: cancellation of underlying work
  DISTINCTION: Unsubscribe withdraws delivery interest; it cancels underlying work only if operation contract or policy explicitly connects them.
