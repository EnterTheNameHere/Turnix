OWNERSHIP_HINTS
---------------
- Owns the concrete RPCMessage wire envelope used between runtime participants.
- Owns Gen, Route, and RPCMessage as core RPC wire models.
- Owns top-level RPC envelope field meanings and per-message-type field expectations.
- Owns helper-constructor expectations for validated envelope construction.
- Owns canonical serializer field-order expectations for isComplete as tail sentinel.
- Owns receiver-side incomplete-envelope rejection before routing.
- Owns schema-level carriage of adapter, AppInstance, View, trace, and Job correlation metadata.

NON_OWNERSHIP_HINTS
-------------------
- Does not define abstract RPC, channel, or transport semantics; load DA-21.
- Does not define permission, policy, or capability authority; load DA-16 and DA-17.
- Does not define Job lifecycle semantics; load DA-19.
- Does not define AppInstance lifecycle or runtime identity; load DA-20.
- Does not define View or frontend runtime semantics; load DA-22.
- Does not define execution adapter boundary semantics; load DA-23.
- Does not define trace semantics beyond carrying correlation metadata; load DA-03.
- Does not define higher-level routing, visibility, activation, or capability semantics.
- Does not make valid serialization evidence of successful work or authority.

SEMANTIC_ANCHORS
----------------
- concrete wire structure, not authority semantics
- envelope validity precedes routing
- isComplete is envelope construction completion, not semantic correctness
- correlation metadata is evidence only, not authority
- message id is distinct from appInstanceId, jobId, viewId, and adapter identity
- lane and route support routing but do not grant permission
- final marks a streamed or ordered series, not single-envelope completion
- job metadata is not final Job success

CONFUSABLE_TERMS
----------------
- TERM_A: isComplete
  TERM_B: final
  DISTINCTION: isComplete marks intentional completion of one top-level RPC envelope; final marks the final item in a streamed or ordered message series.

- TERM_A: isComplete
  TERM_B: semantic correctness
  DISTINCTION: isComplete proves neither correctness nor authority; it only marks complete envelope construction after parsing and validation.

- TERM_A: ack / acknowledgement metadata
  TERM_B: Job success
  DISTINCTION: acknowledgement confirms receipt or transport-level handling only; Job lifecycle and outcome belong to DA-19.

- TERM_A: route / lane
  TERM_B: permission or execution authority
  DISTINCTION: route and lane support delivery and selection; permission and authority are defined by higher DA documents.

- TERM_A: origin metadata
  TERM_B: authority grant
  DISTINCTION: origin carries opaque correlation evidence and does not grant permission, activation, adapter execution, or state mutation.

- TERM_A: seq
  TERM_B: committed-state revision
  DISTINCTION: seq orders messages within a lane; it is not a committed-state revision.

- TERM_A: correlatesTo
  TERM_B: jobId / adapter identity
  DISTINCTION: correlatesTo links messages to parent messages; Job and adapter identities are separate metadata concepts.

- TERM_A: valid serialization
  TERM_B: successful work
  DISTINCTION: valid serialization only means the envelope can be interpreted; it does not mean the operation succeeded.

----------------

- Do not auto-load IS-01 merely because a task mentions permissions; prefer DA-16 and DA-17 first.
- Do not auto-load IS-01 merely because a task mentions Jobs; prefer DA-19 unless RPC-carried Job metadata is in scope.
- Do not auto-load IS-01 merely because a task mentions AppInstance, View, adapter, or trace semantics without envelope-field questions.
