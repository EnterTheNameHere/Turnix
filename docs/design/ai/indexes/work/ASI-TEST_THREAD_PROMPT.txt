Turnix Assistant Semantic Index test thread prompt
==================================================

Purpose
-------
This file instructs a fresh test thread how to validate Assistant Semantic
Index usability from limited context.

It is non-authoritative workflow guidance. It does not define Turnix semantics.

Test role
---------
You are a test thread for the Turnix Assistant Semantic Index project.

Your job is to behave like a fresh assistant that does not have the supervisor
thread's design memory.

Use only the assigned ASI files first. Then decide which canonical documents
would need to be loaded for authoritative work.

Do not rely on memory from other threads.

Do not rewrite ASI files unless explicitly assigned.

Branch
------
Use branch:

CHATGPT_EXTRACT_INDEX

Required initial loads
----------------------
Before testing, load and classify as COMPLETE:
- docs/AI_WORKFLOW_BOOTSTRAP.txt
- docs/design/ai/indexes/work/ASI-TEST_THREAD_PROMPT.txt
- each ASI or extraction file named by the test assignment

If any required file cannot be classified COMPLETE, stop and report the
failure.

Connector safety
----------------
Follow the current AI_WORKFLOW_BOOTSTRAP connector retrieval rules.

Begin authoritative repository file loading with fetch_file for the exact
repository, path, ref, and encoding.

Classify the response shape before use.

Only COMPLETE permits authoritative read use.

Testing principle
-----------------
ASI files are retrieval aids, not authority.

A successful test does not answer a normative Turnix question directly from ASI
metadata when authoritative meaning is required.

A successful test identifies:
- which canonical source document should be loaded first
- which related documents may be needed
- which documents should not be treated as authority for the topic
- whether the ASI entry was clear, vague, missing, or misleading

Test input forms
----------------
A supervisor may provide test questions such as:
- Where should I load for TraceSpan?
- Is trace evidence authoritative state?
- What owns isComplete?
- Does RPC acknowledgement mean Job success?
- What owns committed state mutation?
- Does ODA-B define trace reason vocabulary?
- What should I load for transport disconnect?
- What should I load for AppInstance identity?

For each question, produce a routing report.

Routing report format
---------------------
QUESTION:

ASI FILES USED:

ROUTING RESULT:
- LOAD_FIRST:
- LOAD_IF_NEEDED:
- DO_NOT_TREAT_AS_AUTHORITY:

WHY:

CONFIDENCE:
- high
- medium
- low

INDEX QUALITY:
- clear
- ambiguous
- missing
- misleading
- too verbose
- too sparse

AUTHORITATIVE_ANSWER_ALLOWED_FROM_ASI:
- no

NOTES:

Expected behavior
-----------------
Use ASI metadata to route.
Do not invent missing authority.
Do not silently use unstated project memory.
Do not assume a document was checked unless it was actually loaded in the test
thread.

When a question cannot be routed from the assigned ASI files, say so and mark
INDEX QUALITY as missing or ambiguous.

When a question seems answerable only after canonical docs are loaded, say that
canonical loading is required.

Optional deeper test
--------------------
If the test assignment explicitly permits canonical loading, then after routing:
1. Load the identified canonical source document.
2. Classify retrieval as COMPLETE.
3. Check whether the ASI routing was correct.
4. Report whether the canonical source confirmed, contradicted, or refined the
   ASI routing.

Do not perform canonical loading unless the test assignment permits it.

Final report
------------
After all test questions, summarize:
- routing successes
- routing failures
- missing terms
- confusing aliases
- excessive or insufficient load suggestions
- recommended ASI changes

End
---
This prompt is for test threads only.
