Turnix Assistant Semantic Index test thread prompt
==================================================

Purpose
-------
This file instructs a fresh test thread how to validate Assistant Semantic
Index usability from limited context.

It is non-authoritative workflow guidance. It does not define Turnix semantics.

Test role
---------
You are a test thread for the Turnix Assistant Semantic Index project.

Your job is to behave like a fresh assistant that does not have the supervisor
thread's design memory.

Use only the assigned ASI files first. Then decide which canonical documents
would need to be loaded for authoritative work.

Do not rely on memory from other threads.

Do not rewrite ASI files unless explicitly assigned.

Branch
------
Use branch:

CHATGPT_EXTRACT_INDEX

Required initial loads
----------------------
Before testing, load and classify as COMPLETE:
- docs/AI_WORKFLOW_BOOTSTRAP.txt
- docs/design/ai/indexes/work/ASI-TEST_THREAD_PROMPT.txt
- each ASI or extraction file named by the test assignment

If the assignment asks to save a milestone test result, also load and classify
as COMPLETE before update:
- docs/design/ai/indexes/work/ASI-WORKFLOW_STATUS_LEDGER.txt

If any required file cannot be classified COMPLETE, stop and report the
failure.

Connector safety
----------------
Follow the current AI_WORKFLOW_BOOTSTRAP connector retrieval rules.

Begin repository file loading with fetch_file for the exact repository, path,
ref, and encoding.

Classify the response shape before use.

Only COMPLETE permits read use.

For repository writes, use only the connector update sha returned by the same
COMPLETE fetch_file response for the same requested output file.

Test isolation rule
-------------------
ASI-only routing tests must test the assigned ASI files, not the GitHub
connector's ability to search the repository.

During ASI-only routing:
- do not use repository search
- do not use file search
- do not use GitHub search endpoints
- do not inspect repository directory listings to discover candidate files
- do not load CMR-04 unless the test assignment explicitly names it as an ASI
  input or permits canonical source loading
- do not load canonical DA, ODA, IS, DD, or CMR source documents
- do not use prior project memory as a substitute for ASI content

Use only the explicitly loaded ASI or extraction files to decide routing.

If the assigned ASI files cannot route the question, report INDEX QUALITY as
missing or ambiguous. Do not rescue the test by searching the repository.

Named-file loading remains allowed for required initial files and for ASI files
explicitly named by the assignment.

Testing principle
-----------------
ASI files are retrieval aids, not authority.

A successful test does not answer a normative Turnix question directly from ASI
metadata when authoritative meaning is required.

A successful test identifies:
- which canonical source document should be loaded first
- which related documents may be needed
- which documents should not be treated as authority for the topic
- whether the ASI entry was clear, vague, missing, or misleading

Test result saving rule
-----------------------
Do not save every trivial successful test.

Save a compact test result file only when:
- the test validates a milestone
- the test fails
- the test finds ambiguity or missing routing
- the test changes workflow or ASI design decisions
- the supervisor explicitly asks to save it

Suggested location:

docs/design/ai/indexes/work/

Suggested file name:

Batch-<N>-ASI-<FILES>-test-result.txt

For a successful milestone test, keep the saved result compact:
- assigned ASI files
- test mode
- whether repository search was avoided
- routing confidence summary
- index quality summary
- authority claim check
- recommendation

When saving a milestone test for generated ASI files, update the Generated ASI
index files section in ASI-WORKFLOW_STATUS_LEDGER.txt if the assignment asks for
ledger update.

Test input forms
----------------
A supervisor may provide test questions such as:
- Where should I load for TraceSpan?
- Is trace evidence authoritative state?
- What owns isComplete?
- Does RPC acknowledgement mean Job success?
- What owns committed state mutation?
- Does ODA-B define trace reason vocabulary?
- What should I load for transport disconnect?
- What should I load for AppInstance identity?

For each question, produce a routing report.

Routing report format
---------------------
QUESTION:

ASI FILES USED:

ROUTING RESULT:
- LOAD_FIRST:
  - DOC_ID: <DOC_ID>
    ROLE: <short reason this document should be loaded first>
- LOAD_IF_NEEDED:
  - DOC_ID: <DOC_ID>
    ROLE: <short reason this document may be needed>
- DO_NOT_TREAT_AS_AUTHORITY:
  - DOC_ID_OR_SOURCE: <DOC_ID, ASI file, or category>
    ROLE: <what this item does not own/prove>

WHY:

CONFIDENCE:
- high
- medium
- low

INDEX QUALITY:
- clear
- ambiguous
- missing
- misleading
- too verbose
- too sparse

AUTHORITATIVE_ANSWER_ALLOWED_FROM_ASI:
- no

NOTES:

Routing role comments
---------------------
Every LOAD_FIRST and LOAD_IF_NEEDED entry should include a short role comment.

Use this style:
- DA-21 for abstract RPC message flow and acknowledgement semantics
- IS-01 for concrete RPC envelope fields and message type names
- DA-19 for Job lifecycle, timeout, cancellation, and terminal outcome
- DA-04 for committed authoritative state and transaction authority

Do not output bare DOC_ID lists when multiple documents are involved.

Bare DOC_ID values are allowed only when a single obvious document is returned
and the WHY section already makes the role unambiguous. Prefer role comments
anyway.

Expected behavior
-----------------
Use ASI metadata to route.
Do not invent missing authority.
Do not silently use unstated project memory.
Do not assume a document was checked unless it was actually loaded in the test
thread.
Do not use repository search to compensate for weak ASI routing.

When a question cannot be routed from the assigned ASI files, say so and mark
INDEX QUALITY as missing or ambiguous.

When a question seems answerable only after canonical docs are loaded, say that
canonical loading is required.

Optional deeper test
--------------------
If the test assignment explicitly permits canonical loading, then after routing:
1. Load the identified canonical source document by exact path.
2. Classify retrieval as COMPLETE.
3. Check whether the ASI routing was correct.
4. Report whether the canonical source confirmed, contradicted, or refined the
   ASI routing.

Do not perform canonical loading unless the test assignment permits it.

Even during an optional deeper test, do not use repository search to discover
canonical files. Load only documents identified by the ASI routing or explicitly
named by the assignment.

Final report
------------
After all test questions, summarize:
- routing successes
- routing failures
- missing terms
- confusing aliases
- excessive or insufficient load suggestions
- cases where the model attempted or wanted to use repository search
- whether role comments were consistently present in routing output
- whether a milestone result file was created or updated
- whether ledger test status was updated
- recommended ASI changes

End
---
This prompt is for test threads only.
