===============================================================================
DESIGN AREA DA-19 - JOBS, LONG-RUNNING WORK & CANCELLATION
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines Job identity, Job lifecycle states, terminal outcomes, cancellation,
timeout, supersession, progress, safe-point pause, execution-stop behavior,
and Job-owned trace reason identifiers for observable work.

Purpose:
--------
This document defines the Turnix Job lifecycle and identity model.

It defines:
- Job as an explicit observable lifecycle object for requested work
- Job identity and owner correlation
- the relationship between Jobs and OrchestrationUnits
- the distinction between Job lifecycle and underlying execution
- Job lifecycle states and terminal outcomes
- result, error, cancellation, timeout, and supersession ownership
- progress semantics
- cancellation and execution-stop behavior
- timeout behavior
- supersession as a first-class non-error terminal outcome
- late completion handling after terminal outcome
- safe-point pause behavior
- Job-domain trace reason identifiers
- minimum trace evidence for Job lifecycle events

It does NOT define:
- trace event structure, trace DAG semantics, or span mechanics (see DA-03)
- authoritative committed state or transaction semantics (see DA-04)
- Window, SafePointWindow, or AbortedWindow semantics (see DA-08)
- pack activation lifecycle semantics (see DA-14)
- service, capability, or permission semantics (see DA-16)
- user decision and remembered policy semantics (see DA-17)
- debugger UI layout, breakpoint, or execution-control behavior (see DA-18)
- Application or ApplicationRun lifecycle semantics (see DA-20)
- RPC lifecycle, channels, or transport semantics (see DA-21)
- abstract ExecutionAdapter boundary semantics (see DA-23)
- OrchestrationUnit lifecycle or mutation-authority semantics (see DA-24)
- Window artifact, export, or bundle semantics (see DA-25)
- comparison, Replay, Resume, Retry, or audit workflow semantics (see DA-26)
- adapter lifecycle, trust, isolation, or failure semantics (see DA-27)
- RuntimeHost command-surface or host-boundary semantics (see DA-28)
- PackManager graph-management semantics (see DA-29)
- ModCallContext gateway semantics or absent surfaces (see DA-30)
- concrete RPC message schemas or transport behavior (see IS-01 and IS-02)

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines Job lifecycle, identity, cancellation, timeout,
      supersession, and execution-stop semantics within that shared
      interpretation model.

01.05. This document uses canonical architecture names for runtime concepts.

01.06. Job means an observable lifecycle handle for requested work.

01.07. OrchestrationUnit means a bounded work and mutation-authority context.

01.08. ApplicationRun means one live execution period of an Application.

01.09. ModCallContext means the invocation-scoped Pack-facing gateway into
      Turnix.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. A Job answers:

          "What requested work is waiting, running, succeeded, failed,
           cancelled, timed out, superseded, or paused at a safe point?"

02.02. A Job is an explicit lifecycle object representing requested work.

02.03. A Job is an observable request/work handle.

02.04. A Job may represent short work or long-running work.

02.05. A Job has identity independent of any one RPC message, UI request,
      transport event, capability call, OrchestrationUnit, or runtime task.

02.06. A Job provides a stable handle for:
      - completion signaling
      - progress reporting
      - failure reporting
      - cancellation request
      - timeout handling
      - supersession reporting
      - safe-point pause interaction when supported

02.07. A Job is not merely a Promise, coroutine, callback, thread, task,
      process, model request, or transport message.

02.08. A Job may be implemented using runtime primitives, but those runtime
      primitives do not define the Job lifecycle semantics.

02.09. A Job does not become authoritative committed state merely because it
      exists, runs, or reaches a terminal outcome.

02.10. Job effects become authoritative only through the state,
       transaction, Window, capability, and persistence rules owned by the
       documents that govern those effects.

02.11. A Job may exist before any underlying execution mechanism exists.

02.12. A Job lifecycle and the lifecycle of the underlying execution
       mechanism remain distinct.

02.13. A Job terminal outcome closes the Job lifecycle.

02.14. A closed Job is not restarted.

02.15. Job lifecycle state does not directly define:
       - underlying execution state
       - OrchestrationUnit outcome
       - transaction commit or abort
       - committed-state truth
       - Window finalization
       - ApplicationRun lifecycle
       - adapter lifecycle
       - RuntimeHost lifecycle
       - PackManager operation outcome
       - RPC request outcome
       - transport outcome
       - artifact or export authority
       - comparison outcome
       - Replay outcome
       - Resume outcome
       - Retry outcome
       - audit workflow outcome

02.16. If a Job outcome affects another domain, that domain defines the
       resulting consequence.

02.17. Correlation between a Job and another domain outcome is explicit.


===============================================================================
03. JOB IDENTITY
===============================================================================

03.01. A jobId identifies one Job.

03.02. jobId is stable for the lifetime of that Job.

03.03. jobId is not reused for a different Job during the same ApplicationRun
      active region.

03.04. jobId is the correlation identity used by Job-owned trace evidence.

03.05. jobId does not identify the result payload by itself.

03.06. jobId does not identify an OrchestrationUnit by itself.

03.07. jobId does not identify an RPC request by itself.

03.08. jobId does not identify the underlying execution mechanism by itself.

03.09. jobId does not identify an Application by itself.

03.10. jobId does not identify an ApplicationRun by itself.

03.11. jobId does not identify an ExecutionAdapter by itself.

03.12. jobId does not identify a RuntimeHost by itself.

03.13. jobId does not identify a Window by itself.

03.14. jobId does not identify a Window artifact or export by itself.

03.15. jobId does not identify a Replay, Resume, Retry, or
       comparison workflow by itself.

03.16. jobId does not identify a PackManager operation by itself.

03.17. If a broader Turnix identifier document later defines a canonical Job
       identifier encoding, DA-19 remains subordinate to that identifier
       document for concrete encoding.

03.18. The exact jobId representation remains OPEN.


===============================================================================
04. JOB OWNERSHIP AND CORRELATION
===============================================================================

04.01. A Job has an owning scope.

04.02. The owning scope may include:
      - applicationId
      - applicationRunId
      - orchestrationUnitId
      - caller pack identity
      - capability identifier
      - RPC request identity
      - debugger request identity
      - user decision identity
      - scheduler identity

04.03. Identifier presence varies by Job origin.

04.04. Missing optional correlation identifiers do not invalidate the Job.

04.05. Required correlation identifiers for a concrete Job class are defined
      by the document or implementation specification that creates that Job
      class.

04.06. This document defines the shared Job identity and lifecycle boundary.

04.07. This document does not define every possible Job origin.

04.08. A Job origin does not gain authority merely because it created a Job.


===============================================================================
05. RELATION TO ORCHESTRATIONUNITS
===============================================================================

05.01. A Job is an observable lifecycle handle.

05.02. An OrchestrationUnit is an execution-authority unit.

05.03. A transaction is a mutation staging and commit boundary.

05.04. These concepts are related but distinct.

05.05. A Job may be backed by one OrchestrationUnit.

05.06. A Job may coordinate multiple OrchestrationUnits when a later document
      explicitly defines that behavior.

05.07. An OrchestrationUnit may be associated with a Job when the unit is
      performing requested work that requires Job lifecycle visibility.

05.08. Not every OrchestrationUnit is necessarily a Job.

05.09. Not every Job detail is necessarily represented by an
      OrchestrationUnit.

05.10. Job lifecycle identity and OrchestrationUnit mutation authority remain
       distinct concepts.

05.11. State mutation authority remains constrained by DA-04 even when work
       is represented as a Job.

05.12. A Job terminal outcome does not automatically complete, fail, commit,
       abort, or roll back an OrchestrationUnit or a transaction.

05.13. OrchestrationUnit lifecycle and outcome semantics remain owned by
       DA-24.

05.14. Transaction commit, abort, rollback, and committed-state truth remain
       owned by DA-04.

05.15. Window finalization remains owned by DA-08.


===============================================================================
06. JOB LIFECYCLE STATE MODEL
===============================================================================

06.01. A Job lifecycle has explicit observable states and outcomes.

06.02. The primary Job states are:
      - Pending
      - Running
      - Succeeded
      - Failed
      - Cancelled
      - TimedOut
      - Superseded

06.03. Pending means the Job exists but its underlying execution mechanism has
      not started.

06.04. Running means the Job's underlying execution mechanism has started and
      the Job has not reached a terminal outcome.

06.05. Succeeded means the Job reached a successful terminal outcome.

06.06. Failed means the Job reached a failure terminal outcome.

06.07. Cancelled means the Job reached an intentional cancellation terminal
      outcome.

06.08. TimedOut means the Job reached a timeout terminal outcome.

06.09. Superseded means the Job reached a terminal outcome because newer
      accepted input, newer work, or higher-priority work replaced it.

06.10. Terminal states are:
       - Succeeded
       - Failed
       - Cancelled
       - TimedOut
       - Superseded

06.11. A Job reaches exactly one terminal state.

06.12. A terminal state is final.

06.13. A terminal Job does not later become Pending or Running again.

06.14. Retry is new work.

06.15. Retry does not reuse the previous jobId.

06.16. A Retry workflow may reference earlier Job evidence to explain why the
       later attempt exists.

06.17. A Retry workflow does not reopen, continue, or restart the earlier
       Job lifecycle.

06.18. DA-26 owns Retry workflow semantics.

06.19. Created, queued, cancellation requested, pause requested, paused at a
       safe point, continued from pause, and progress updated are lifecycle
       events, phases, or control conditions rather than primary Job states.

06.20. Queued means a Pending Job is accepted but not yet running.

06.21. A queued Job remains Pending until execution begins.

06.22. A paused-at-safe-point Job remains non-terminal.

06.23. Pause-at-safe-point does not create a terminal outcome.

06.24. Job continuation from pause is not DA-26 Resume after
       SafePointWindow restoration.

06.25. A Job may report progress while it is non-terminal.

06.26. Progress reporting does not by itself imply committed state mutation.

06.27. A Job terminal outcome reports the Job's lifecycle result.

06.28. A Job terminal outcome does not by itself define whether any side
       effect became authoritative.


===============================================================================
07. RESULT AND ERROR OWNERSHIP
===============================================================================

07.01. A Job result exists only for Succeeded.

07.02. A Job result is absent for Failed, Cancelled, TimedOut, and
      Superseded.

07.03. A failure error exists for Failed.

07.04. Timeout metadata may exist for TimedOut.

07.05. Cancellation metadata may exist for Cancelled.

07.06. Supersession metadata may exist for Superseded.

07.07. Cancelled is not represented as an ordinary failure error.

07.08. TimedOut is not represented as an ordinary failure error unless a
      concrete API explicitly maps timeout into a failure envelope while
      preserving the TimedOut lifecycle outcome.

07.09. Superseded is not represented as an ordinary failure error.

07.10. A Job result envelope does not become authoritative committed state
       merely because the Job succeeded.

07.11. Failure, cancellation, timeout, supersession, diagnostic, partial,
       workflow, artifact, comparison, Replay, Resume, and Retry data
       are not Job result data.

07.12. Such non-result data is represented by separate metadata, events,
       diagnostics, or owning-domain structures.

07.13. The exact Job result envelope remains OPEN.

07.14. The exact Job error envelope remains OPEN.


===============================================================================
08. PROGRESS
===============================================================================

08.01. A Job may report progress.

08.02. Progress is observational lifecycle evidence.

08.03. Progress is not authoritative mutation.

08.04. Progress may include:
      - current phase
      - percent or unit progress when meaningful
      - human-readable status
      - last progress timestamp
      - last progress reason
      - current owner or active OrchestrationUnit when available

08.05. Progress updates are trace-visible when meaningful.

08.06. Progress updates do not commit authoritative state by themselves.

08.07. Progress does not prove eventual success.

08.08. The exact progress payload remains OPEN.


===============================================================================
09. CANCELLATION AND EXECUTION STOPPING
===============================================================================

09.01. Cancellation is explicit.

09.02. Cancellation is intentional.

09.03. Cancellation is not failure.

09.04. Cancellation request and cancellation outcome are distinct lifecycle
      events.

09.05. A cancellation request does not guarantee immediate cancellation.

09.06. A Job may be cancelled before execution begins.

09.07. If a Job is cancelled before execution begins, Turnix removes or
      invalidates the scheduled execution when possible and transitions the
      Job to Cancelled.

09.08. Cancelling a Job before execution begins does not require an
      execution-stop attempt because no underlying execution mechanism has
      started.

09.09. If a Job is cancelled after execution begins, Turnix may attempt to
      stop the underlying execution mechanism.

09.10. The Job cancellation outcome and the underlying execution-stop
       outcome remain distinct.

09.11. A Job may refuse or defer cancellation only through explicit policy
       or explicit lifecycle semantics defined by the Job owner.

09.12. Cancelling a Job discards the Job's uncommitted work from the
       perspective of the Job result.

09.13. Cancellation does not silently roll back committed state.

09.14. Committed state produced before cancellation remains governed by the
       state and Window documents that own committed-state meaning.

09.15. If cancellation affects uncommitted transactional staging, DA-04 owns
       whether that staging is aborted, discarded, or otherwise resolved.

09.16. Cancellation sources may include:
       - user action
       - frontend disconnect policy
       - RPC cancel message
       - timeout handling
       - scheduler policy
       - debugger action
       - system shutdown
       - higher-priority orchestration policy

09.17. Cancellation remains trace-visible.

09.18. Execution-stop attempts remain trace-visible when an execution-stop
       attempt exists.


===============================================================================
10. TIMEOUT
===============================================================================

10.01. Timeout is explicit.

10.02. Job timeout is a Job lifecycle concern.

10.03. Job timeout is not RPC transport timeout.

10.04. RPC transport timeout is not Job timeout.

10.05. Job timeout applies after a Job has been accepted.

10.06. A Job timeout uses a monotonic clock.

10.07. The timeout policy source is explicit.

10.08. If the timeout deadline is reached before terminal completion, the Job
      transitions to TimedOut.

10.09. When a Running Job times out, Turnix may attempt to stop the
      underlying execution mechanism.

10.10. When a Pending Job times out, Turnix removes or invalidates the
       scheduled execution when possible.

10.11. Timeout does not silently convert into cancellation.

10.12. TimedOut is distinct from Cancelled.

10.13. TimedOut is distinct from Failed.

10.14. A later worker completion after TimedOut does not change the Job
       terminal state.

10.15. Timeout remains trace-visible.

10.16. Timeout trace evidence records enough context to explain:
       - jobId
       - timeout policy source
       - deadline or timeout duration
       - monotonic elapsed time
       - last known progress phase
       - active OrchestrationUnit when available
       - execution-stop result when an execution-stop attempt exists


===============================================================================
11. SUPERSESSION
===============================================================================

11.01. Supersession is explicit.

11.02. Supersession is intentional.

11.03. Supersession is not failure.

11.04. Supersession is not timeout.

11.05. Supersession is not ordinary user cancellation, although user action may
      cause supersession.

11.06. Superseded is a first-class terminal non-error outcome.

11.07. Superseded means the Job ended because newer accepted input, newer
      work, or higher-priority work made the old Job no longer relevant.

11.08. Superseded closes the Job lifecycle.

11.09. A Superseded Job is not restartable.

11.10. A Superseded Job produces no Job result.

11.11. A Superseded Job records the superseding cause when known.

11.12. Superseded does not roll back authoritative state that was already
       committed.

11.13. Superseded does not make new authoritative mutation from the
       superseded Job after the terminal transition.

11.14. If a parent workflow, transaction policy, Window policy, or
       compensation mechanism discards, masks, reverts, or supersedes already
       committed effects, that behavior is owned by that parent mechanism.

11.15. If a Superseded Job has open transactional staging, DA-04 owns whether
       that staging is aborted, discarded, or otherwise resolved.

11.16. Supersession metadata may include:
       - supersededByJobId
       - supersededByRequestId
       - supersededByInputId
       - supersessionPolicy
       - supersessionReason
       - replacedSemanticTarget

11.17. Supersession remains trace-visible.

11.18. User-facing diagnostics do not present Superseded as failure.

11.19. User-facing diagnostics may describe Superseded as:
       - replaced by newer request
       - replaced by newer input
       - stopped because newer work took precedence


===============================================================================
12. LATE COMPLETION AFTER TERMINAL OUTCOME
===============================================================================

12.01. Late completion occurs when an underlying execution mechanism reports
      completion after the Job has already reached a terminal state.

12.02. Late completion does not change the Job terminal state.

12.03. Late completion does not produce a Job result.

12.04. Late completion does not deliver a reply or result from the late
      completion.

12.05. Late completion may be traced as diagnostic evidence.

12.06. No new authoritative mutation may be committed from late completion
      after the Job terminal transition.

12.07. Authoritative mutation that committed before the Job terminal
      transition remains governed by the state and Window documents that own
      committed-state meaning.

12.08. Late completion handling prevents cancelled, timed-out, or superseded
      work from appearing to succeed later.


===============================================================================
13. SAFE-POINT PAUSE AND DEBUGGER INTERACTION
===============================================================================

13.01. A Job may support pause-at-safe-point behavior.

13.02. Pause-at-safe-point is explicit.

13.03. Pause request and pause achievement are distinct lifecycle events.

13.04. A Job that cannot reach a safe point reports that limitation
      explicitly.

13.05. Safe-point pause does not silently cancel the Job.

13.06. Safe-point pause does not silently supersede the Job.

13.07. A paused-at-safe-point Job remains non-terminal.

13.08. A paused-at-safe-point Job may later continue from that pause.

13.09. Continuing from pause continues the same Job lifecycle.

13.10. Continuing from pause is not DA-26 Resume after SafePointWindow
       restoration.

13.11. A paused-at-safe-point Job may later reach any valid terminal outcome.

13.12. Debugger breakpoint and inspection behavior remains constrained by
       DA-18.

13.13. Window creation waiting and safe-point policy remain constrained by
       DA-08.


===============================================================================
14. JOB TRACE REASON IDENTIFIERS
===============================================================================

14.01. DA-19 owns the Job-domain trace reason identifiers used for Job
      lifecycle, progress, cancellation, timeout, supersession, execution
      stopping, late completion, and safe-point pause events.

14.02. The following Job-domain trace reasons are defined:

      - JobCreated
      - JobQueued
      - JobStarted
      - JobProgressUpdated
      - JobSucceeded
      - JobFailed
      - JobCancellationRequested
      - JobCancelled
      - JobTimeoutScheduled
      - JobTimedOut
      - JobSuperseded
      - JobLateCompletionIgnored
      - JobExecutionStopRequested
      - JobExecutionStopSucceeded
      - JobExecutionStopFailed
      - JobPauseAtSafePointRequested
      - JobPausedAtSafePoint
      - JobPauseDeferred
      - JobContinued

14.03. JobCreated is emitted when a Job lifecycle object is created.

14.04. JobQueued is emitted when a Pending Job is accepted but not yet
      running.

14.05. JobStarted is emitted when Job execution begins.

14.06. JobProgressUpdated is emitted when a Job reports progress.

14.07. JobSucceeded is emitted when a Job reaches the Succeeded terminal
      state.

14.08. JobFailed is emitted when a Job reaches the Failed terminal state.

14.09. JobCancellationRequested is emitted when cancellation is requested for
      a Job.

14.10. JobCancelled is emitted when a Job reaches the Cancelled terminal
       state.

14.11. JobTimeoutScheduled is emitted when a timeout policy is attached to a
       Job or when the Job timeout deadline becomes known.

14.12. JobTimedOut is emitted when a Job reaches the TimedOut terminal
       state.

14.13. JobSuperseded is emitted when a Job reaches the Superseded terminal
       state.

14.14. JobLateCompletionIgnored is emitted when an underlying execution
       mechanism reports completion after the Job is already terminal and the
       late completion is ignored.

14.15. JobExecutionStopRequested is emitted when Turnix attempts to stop the
       underlying execution mechanism for a Job.

14.16. JobExecutionStopSucceeded is emitted when the underlying execution
       mechanism reports or is known to have stopped in response to a stop
       attempt.

14.17. JobExecutionStopFailed is emitted when Turnix attempts to stop the
       underlying execution mechanism and the stop attempt fails, is refused,
       is unsupported, or cannot be confirmed.

14.18. JobPauseAtSafePointRequested is emitted when pause-at-safe-point is
       requested for a Job.

14.19. JobPausedAtSafePoint is emitted when a Job reaches and applies a
       safe-point pause.

14.20. JobPauseDeferred is emitted when a Job cannot pause immediately but
       the pause request remains pending or deferred by policy.

14.21. JobContinued is emitted when a paused Job continues from pause.

14.22. Job lifecycle trace evidence records enough context to explain:
       - jobId
       - Job state
       - Job terminal outcome when the Job reaches one
       - applicationId when applicable
       - applicationRunId when applicable
       - orchestrationUnitId when applicable
       - caller pack identity when applicable
       - capability identifier when applicable
       - RPC request identity when applicable
       - debugger request identity when applicable
       - scheduler identity when applicable
       - timeout policy when applicable
       - cancellation source when applicable
       - supersession source when applicable
       - failureReasonCategory when the Job fails
       - cancelReasonCategory when cancellation completes
       - supersessionReason when the Job is superseded
       - safePointDescriptor when a safe point is reached
       - execution-stop result when an execution-stop attempt exists

14.23. Job trace evidence links causally to the owner or trigger when that
       owner or trigger exists and is known.

14.24. Possible causal owners or triggers include:
       - RPC request that created or accepted the Job
       - capability call that created or used the Job
       - OrchestrationUnit that executed the work
       - transaction commit or abort caused by the work
       - decision point that paused or influenced the work
       - scheduler decision that queued, cancelled, or superseded the Job

14.25. Job-domain trace evidence is required as an emission obligation where
       Job lifecycle events occur.

14.26. DA-03 defines the trace substrate used to represent Job lifecycle
       trace evidence.

14.27. Trace representation, retention, pruning, and loss remain governed by
       DA-03.

14.28. Trace evidence does not become committed state, Job result, Window
       finalization, artifact/export authority, comparison outcome, Replay
       outcome, Resume outcome, Retry outcome, or audit workflow outcome by
       itself.

14.29. DA-19 defines only the Job-domain ownership of these trace reasons and
       required correlation evidence.


===============================================================================
15. RELATION TO RPC AND TRANSPORT
===============================================================================

15.01. Job lifecycle is distinct from RPC transport lifecycle.

15.02. A transport acknowledgement does not prove that a Job exists.

15.03. A Job may exist even if the transport that caused it later
      disconnects.

15.04. A transport timeout does not automatically imply Job timeout.

15.05. A Job timeout does not automatically imply transport timeout.

15.06. A request may be rejected before a Job exists.

15.07. A request may be accepted as a Job.

15.08. A request accepted as a Job creates Job lifecycle evidence.

15.09. Request acceptance is not final Job success.

15.10. DA-21 owns RPC lifecycle, channel, transport, timeout, disconnect, and
       logical communication semantics.

15.11. IS-01 owns concrete RPC message envelope structure.

15.12. IS-02 owns concrete WebSocket RPC transport flow.

15.13. DA-19 owns Job lifecycle semantics after accepted work exists.


===============================================================================
16. RELATION TO CAPABILITIES
===============================================================================

16.01. Capability invocation may complete without creating a Job.

16.02. Long-running, cancellable, progress-reporting, timeout-managed, or
      observable capability execution may create or attach to a Job.

16.03. A Job handle is a lifecycle handle.

16.04. A Job handle is not a raw service object.

16.05. A Job handle is not a direct reference to implementation internals.

16.06. Job-backed capability execution remains capability-mediated.

16.07. DA-16 owns service, capability, and permission semantics.

16.08. DA-19 owns Job lifecycle semantics when a capability creates or attaches
      to a Job.


===============================================================================
17. RELATION TO ARTIFACTS AND WORKFLOWS
===============================================================================

17.01. Job lifecycle evidence may appear in retained evidence, Window-related
      artifacts, exports, bundles, offline inspections, comparisons, Replay,
      Resume, Retry, or audit workflows.

17.02. Appearance of Job evidence in another artifact or workflow does not
      make the Job the owner of that artifact or workflow.

17.03. DA-25 owns Window artifacts, WindowManifests, WindowExports, bundle
      representation, optional digest representation, partial export, missing
      material, and offline inspection artifact semantics.

17.04. DA-26 owns ComparisonResult, equality modes, Replay, Resume, Retry, and
      audit workflow semantics.

17.05. A ComparisonResult does not change a Job terminal outcome.

17.06. Replay does not reopen, continue, or restart a closed Job.

17.07. Resume after SafePointWindow restoration is new workflow activity.

17.08. Resume after SafePointWindow restoration does not reuse a closed Job
      lifecycle.

17.09. Retry is new work and does not reuse the previous jobId.

17.10. Audit workflow evidence does not change a Job terminal outcome.

17.11. Audit workflow evidence does not create a Job result.

18.02. These questions remain open because this document defines Job

      - Job primary states are Pending, Running, Succeeded, Failed,
        Cancelled, TimedOut, and Superseded
      - Succeeded, Failed, Cancelled, TimedOut, and Superseded are terminal
      - terminal state is final
      - closed Jobs are not restarted
      - Retry is new work
      - Retry does not reuse the previous jobId
      - Job continuation from pause is not DA-26 Resume workflow
      - Queued is a Pending phase or event, not a terminal state
      - result exists only for Succeeded
      - Cancelled is intentional and not failure
      - TimedOut is explicit and distinct from Cancelled and Failed
      - Superseded is a first-class non-error terminal outcome
      - Superseded does not roll back already committed state
      - cancellation request and cancellation outcome are distinct
      - cancellation before execution does not require execution-stop
      - Job terminal outcome and execution-stop outcome remain distinct
      - late completion after terminal outcome is ignored
      - progress is observational and not authoritative mutation
      - safe-point pause is explicit and non-terminal
      - Job-domain trace reason identifiers are owned by DA-19
      - DA-03 owns the trace substrate, not Job lifecycle semantics
      - DA-04 owns transaction and committed-state truth semantics
      - DA-24 owns OrchestrationUnit lifecycle and outcome semantics
      - DA-25 owns artifact and export semantics
      - DA-26 owns comparison, Replay, Resume, Retry, and audit workflows

19.02. OPEN:
      - concrete result, error, progress, RPC, capability, retry, and
        retained-result envelopes
