===============================================================================
DESIGN AREA DA-11 - GENERIC RESOLUTION SEMANTICS
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the generic, dependency-agnostic resolution machinery used by Turnix
to interpret PackRequests, enumerate candidates, apply constraints, compare
candidate identity, and produce deterministic outcomes.

This document defines resolution mechanics only.

This area strictly separates:
- request parsing
- candidate enumeration
- whole-candidate comparison
- constraint application
- deterministic selection
- ambiguity and failure signaling
- resolution-domain observability

Nothing in this area implies discovery, indexing, importing, activation,
execution order, runtime access, capability permission, user-decision policy,
PackManager repair, Application lifecycle, ApplicationRun lifecycle,
SaveBundle behavior, or committed-state authority.

Purpose:
--------
This document defines the generic, side-effect-free resolution engine that
higher-level consumers invoke with their own explicit context, policy, and
ordering criteria.

It defines:
- PackRequest grammar
- PackRequest parsing and internal representation
- candidate enumeration phases
- whole-candidate resolution boundary inherited from discovery
- candidate equivalence and non-equivalence handling
- hard and soft constraint handling
- deterministic selection contract
- ambiguity and failure signaling
- resolution observability requirements
- resolution-domain trace reason identifiers
- separation between resolution mechanics and consumer policy

It does NOT define:
- discovery, indexing, or candidate production (see DA-09)
- pack identity, hierarchy, or visibility semantics (see DA-10)
- importing or module-loading behavior (see DA-12)
- dependency meaning, dependency strength, or graph intent (see DA-13)
- activation lifecycle, activation phases, or cycle handling (see DA-14)
- service, capability, or permission authority (see DA-16)
- warning, allow, deny, remember, or user-decision behavior (see DA-17)
- Job lifecycle or terminal outcomes (see DA-19)
- Application or ApplicationRun lifecycle semantics (see DA-20)
- RPC, channel, transport, or message-flow semantics (see DA-21)
- execution adapter boundary, lifecycle, trust, or isolation semantics
  (see DA-23 and DA-27)
- OrchestrationUnit lifecycle or mutation authority (see DA-24)
- RuntimeHost workspace ownership or command surfaces (see DA-28)
- PackManager catalog, graph-preparation, repair, View, or write semantics
  (see DA-29)
- SaveBundle runtime behavior
- committed-state authority

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines generic resolution mechanics within that shared
      interpretation model.


===============================================================================
02. CORE CONCEPT AND BOUNDARY
===============================================================================

LOCKED:

02.1. Resolution answers:

          "Which concrete pack identity satisfies this PackRequest
           inside the current resolution context?"

02.2. Resolution is side-effect-free deterministic selection from an
      already-built snapshot of discovered and indexed pack descriptors.

02.3. Resolution consumes:
      - one PackRequest
      - one registry snapshot
      - one explicit consumer-supplied resolution context

02.4. Resolution produces exactly one of:
      - one resolved concrete pack identity
      - one classified resolution failure
      - one classified ambiguity requiring external decision handling

02.5. Resolution does not:
      - discover candidate roots
      - index packs
      - rescan the filesystem
      - read manifests lazily
      - merge manifest fragments
      - compose synthetic candidates from partial candidates
      - switch resolution context
      - guess policy
      - persist ambiguity decisions
      - activate packs
      - import code
      - load runtimes
      - grant runtime access
      - grant capability permission
      - define user-decision policy
      - define runtime lifecycle outcomes

02.6. Discovery builds the candidate universe.

02.7. Resolution selects from that already-built universe.

02.8. Resolution works on whole discovered candidate artifacts produced by
      DA-09 discovery.

02.9. Resolution remains strictly separate from activation and runtime use.

02.10. This document defines generic mechanics, not consumer-specific
       strategy.


===============================================================================
03. PACKREQUEST REFERENCE GRAMMAR
===============================================================================

LOCKED:

03.1. Canonical grammar:
      [<author>@]<packTreeId>[@<semverRequirement>]

03.2. Grammar rules:
      - case-sensitive
      - exactly zero, one, or two "@" characters
      - no filesystem paths
      - no slashes
      - dots are allowed only for pack hierarchy
      - no implicit defaults inside the raw reference string

03.3. Valid examples:
      - "ui"
      - "ui.controls"
      - "Turnix@ui.controls"
      - "ui.controls@^2.0"
      - "Turnix@ui.controls@~1.4"

03.4. Invalid examples:
      - "@ui"
      - "ui/controls"
      - "ui.controls:1.0"

03.5. PackRequest syntax is identity and request syntax.

03.6. PackRequest syntax is not filesystem syntax.


===============================================================================
04. SINGLE-AT DISAMBIGUATION RULE
===============================================================================

LOCKED:

04.1. If a PackRequest contains exactly one "@", the resolver first attempts
      to parse the suffix as a semantic version requirement.

04.2. If semantic-version parsing succeeds, the suffix is treated as
      semverRequirement.

04.3. If semantic-version parsing fails, the suffix is treated as author.

04.4. Examples:
      - "foo@1.2" -> packTreeId = "foo", semverRequirement = "1.2"
      - "foo@bar" -> author = "foo", packTreeId = "bar"

04.5. Failure to parse semantic version in this case is not itself an error.

04.6. That failure is part of the intentional disambiguation rule.


===============================================================================
05. PACKREQUEST INTERNAL REPRESENTATION
===============================================================================

LOCKED:

05.1. PackRequest is the parsed internal representation used by the generic
      resolver.

05.2. PackRequest structure:
      - author: str | None
      - packTreeId: str
      - semverRequirement: SemVerPackRequirement | None
      - kind: PackKind | None

05.3. PackRequest is created before generic resolution begins.

05.4. PackRequest remains immutable after creation.

05.5. PackRequest carries only normalized request identity and request
      constraints.

05.6. PackRequest does not carry higher-level resolution policy.

05.7. Higher-level policy includes optionality, source preference,
      prerelease allowance, and persisted ambiguity decisions.

05.8. kind may be injected by the surrounding resolution context when that
      context requires kind restriction.


===============================================================================
06. RESOLUTION ATTEMPT
===============================================================================

LOCKED:

06.1. A resolution attempt is deterministic.

06.2. A resolution attempt is side-effect free.

06.3. Given the same PackRequest, registry snapshot, and resolution context,
      the outcome is identical.

06.4. The resolver does not mutate the registry snapshot.

06.5. The resolver does not trigger discovery.

06.6. The resolver does not trigger indexing.

06.7. The resolver does not combine partial candidate data into a new
      candidate.

06.8. The resolver does not create persistent policy state.

06.9. The resolver does not change Application state, ApplicationRun state,
      SaveBundle material, committed state, or configuration state.


===============================================================================
07. CANDIDATE ENUMERATION
===============================================================================

LOCKED:

07.1. Candidate enumeration identifies packs that are structurally compatible
      with a PackRequest.

07.2. Candidate enumeration occurs over the already-built registry snapshot.

07.3. Enumeration steps:
      1) match packTreeId
      2) apply author constraint if present
      3) apply kind constraint if present
      4) collect remaining candidates

07.4. Candidate enumeration does not:
      - order candidates
      - select a winner
      - apply consumer preference
      - perform fallback
      - interpret optionality
      - merge candidates
      - repair missing candidates
      - alter graph intent

07.5. This phase answers only:
      "Which candidates could structurally satisfy this request?"


===============================================================================
08. WHOLE-CANDIDATE BOUNDARY
===============================================================================

LOCKED:

08.1. Resolution operates on whole discovered candidate artifacts supplied by
      the registry snapshot.

08.2. The candidate universe is produced by discovery and indexing.

08.3. Manifest candidates are selected as whole definitions during the
      discovery and indexing pipeline described by DA-09.

08.4. Resolution does not merge duplicate manifests.

08.5. Resolution does not stack manifest fields.

08.6. Resolution does not compose a synthetic candidate from several shadowed
      candidates.

08.7. If several discovered candidates exist for the same apparent pack,
      resolution compares those candidates as whole candidates.

08.8. This boundary prevents resolution from becoming a hidden manifest merge
      stage.

08.9. SaveBundle-local retained Pack material may be part of the candidate
      population only when the surrounding consumer supplies that population
      or context explicitly.

08.10. DA-11 does not define SaveBundle-local material selection policy.


===============================================================================
09. CANDIDATE EQUIVALENCE AND FINGERPRINTS
===============================================================================

LOCKED:

09.1. Candidate equivalence means two or more candidates represent the same
      concrete pack content for the current comparison purpose.

09.2. When pack fingerprints are available and relevant to the current
      comparison, equality of the full fingerprint string establishes
      fingerprint equivalence for that comparison.

09.3. The full fingerprint string is compared as a whole.

09.4. Fingerprint equivalence is comparison equivalence for the current
      resolution purpose.

09.5. Fingerprint equivalence is not authenticity proof.

09.6. Candidate origin may be surfaced as explanation context.

09.7. Candidate origin alone does not prove authenticity.

09.8. If two candidates are fingerprint-equivalent, they are treated as
      equivalent candidates for selection.

09.9. Equivalent candidates do not all load.

09.10. Equivalent candidates do not all become winners.

09.11. The first equivalent candidate in deterministic order wins.

09.12. Later equivalent candidates remain separate shadowed-equivalent
       entries for diagnostics, provenance, and explanation.

09.13. Shadowed-equivalent candidates remain observable.

09.14. If candidates share the same canonicalPackId and packVersion but have
       different fingerprints, they are not equivalent.

09.15. A same-identity same-version fingerprint difference is candidate
       divergence.

09.16. Warning, allow, deny, remember, or user-decision behavior for
       candidate divergence belongs to DA-17 and the surrounding consumer.


===============================================================================
10. CONSTRAINT APPLICATION
===============================================================================

LOCKED:

10.1. Constraint application removes or restricts candidates after structural
      enumeration and whole-candidate comparison.

10.2. Constraint classes are:
      - hard constraints
      - soft constraints

10.3 Hard constraints
---------------------

10.3.1. Hard constraints permanently exclude candidates.

10.3.2. Examples include:
        - packTreeId mismatch
        - required author mismatch
        - kind mismatch
        - visibility violation
        - forbidden root or source within the current resolution context
        - concrete version mismatch
        - fingerprint mismatch when an exact fingerprint expectation is
          supplied by the current consumer context

10.3.3. A candidate that fails a hard constraint is not selectable.

10.3.4. A candidate that fails a hard constraint is not offered as a valid
        outcome.

10.3.5. Hard-constraint failure remains observable through resolution-domain
        observability and tracing.

10.4 Soft constraints
---------------------

10.4.1. Soft constraints discourage selection without erasing candidate
        identity.

10.4.2. Examples include:
        - prerelease discouraged by policy
        - deprecated pack
        - policy-based discouragement

10.4.3. Soft-constrained candidates remain known to the resolver.

10.4.4. Soft-constrained candidates are not selected unless the surrounding
        consumer context explicitly allows them.

10.4.5. Soft constraints apply to candidates rather than to request strength
        or optionality.

10.4.6. Request strength or optionality is defined outside this document.

10.4.7. If soft-constrained candidates become allowed, they remain subject
        to deterministic ordering.


===============================================================================
11. RESOLUTION CONTEXT AND CONSUMER POLICY
===============================================================================

LOCKED:

11.1. Resolution always occurs inside one explicit resolution context.

11.2. A resolution attempt has exactly one active resolution context.

11.3. The surrounding consumer supplies the resolution context.

11.4. The resolution context determines:
      - which candidate population is visible to the resolver
      - which source boundaries are legal
      - which policy constraints are in force
      - which ordering criteria will later be applied
      - whether an exact fingerprint expectation is being enforced

11.5. The generic resolver does not create a resolution context.

11.6. The generic resolver does not infer a resolution context.

11.7. The generic resolver does not switch a resolution context.

11.8. The generic resolver does not mix resolution contexts silently.

11.9. The generic resolver does not persist a resolution context.

11.10. If the surrounding consumer violates context assumptions, resolution
       fails explicitly.

11.11. If a consumer wants source preference, prerelease rules,
       SaveBundle-local graph intent, selected graph restoration, pinned
       graph evidence, or user-selected override behavior, that consumer
       supplies those semantics explicitly in its context or pre-resolution
       candidate population.

11.12. DA-11 does not define those consumer policies.

11.13. DA-13 owns dependency meaning, dependency strength, provider-role,
       pinned, copied, source-specific dependency policy, advisory relation
       semantics, and graph intent.

11.14. DA-11 may be invoked by dependency or graph-building consumers to
       resolve a PackRequest.

11.15. Invocation by such a consumer does not transfer dependency meaning,
       graph intent, or graph-preparation authority to DA-11.


===============================================================================
12. DETERMINISTIC SELECTION
===============================================================================

LOCKED:

12.1. After constraints are applied, the resolver imposes a total,
      deterministic ordering on the remaining selectable candidates.

12.2. The resolver selects the first candidate in that ordering.

12.3. Ordering is:
      - stable
      - reproducible
      - independent of incidental iteration order
      - free of randomness
      - total over the selectable candidate set

12.4. The exact ordering criteria are supplied by the surrounding consumer.

12.5. DA-11 defines the requirement that selection order be total and
      deterministic.

12.6. DA-11 does not define every consumer's ordering policy.

12.7. Root precedence may be one consumer-provided ordering input.

12.8. Root precedence does not silently override SaveBundle-local material,
      selected graph intent, pinned graph evidence, explicit user choice,
      Application semantics, ApplicationRun semantics, or consumer-specific
      source policy unless an owning document defines that behavior.

12.9. Silent substitution is forbidden.

12.10. Equivalent candidates follow the same deterministic ordering rule.

12.11. The first equivalent candidate wins.

12.12. Later equivalent candidates remain shadowed-equivalent rather than
       loaded as additional winners.


===============================================================================
13. AMBIGUITY HANDLING
===============================================================================

LOCKED:

13.1. If deterministic ordering cannot reduce the selectable candidates to
      one unambiguous result, resolution pauses.

13.2. Ambiguity is classified explicitly.

13.3. External consumer policy or DA-17-mediated user decision handling is
      then required.

13.4. The generic resolver does not guess.

13.5. The generic resolver does not auto-persist decisions.

13.6. Once an external decision is made, any persistence of that decision is
      owned by the consumer, DA-17 decision handling, or the policy-storage
      boundary defined outside DA-11.

13.7. Fingerprint divergence, when not treated as a hard constraint by the
      current context, may be surfaced to the surrounding consumer as an
      ambiguity or warning-class condition.

13.8. DA-17 defines user-facing warning, allow, deny, remember, and
      remembered-decision behavior.


===============================================================================
14. FAILURE CONDITIONS
===============================================================================

LOCKED:

14.1. Resolution fails explicitly if:
      - no candidates exist after hard constraints
      - no candidates are selectable under the supplied context
      - context rules are violated
      - ambiguity requires decision and no decision path is available

14.2. Resolution failure is:
      - explicit
      - classified
      - observable

14.3. Resolution failure never falls back silently.

14.4. Resolution failure does not trigger PackManager repair.

14.5. Resolution failure does not trigger discovery, indexing, importing,
      activation, runtime loading, capability permission, or state mutation.


===============================================================================
15. RESOLUTION OBSERVABILITY
===============================================================================

15.1. Resolution outcomes remain observable.

15.2. Observability covers successful resolution paths as well as failures.

15.3. A successful resolution outcome remains explainable after the fact.

15.4. Resolution observability supports explanation of:
      - which candidates were enumerated
      - which filters or constraints were applied
      - which candidates were softly constrained
      - which candidates were hard-rejected
      - why the selected candidate won
      - why another candidate did not win
      - why a candidate was shadowed as equivalent
      - why the active resolution context permitted this outcome

15.5. Ambiguity detection remains trace-visible.

15.6. User decision points produced by resolution remain trace-linked to the
      resolution context that required the decision.

15.7. Resolution trace obligations are resolution-domain emission
      obligations.

15.8. DA-11 owns the resolution-domain reason identifiers needed to explain
      PackRequest parsing, candidate enumeration, filtering, constraint
      rejection, soft discouragement, selection, shadowed equivalence,
      ambiguity, and failure.

15.9. DA-03 owns trace substrate, trace retention, trace loss, trace DAG,
      event structure, and span semantics.

15.10. Trace evidence does not become committed state.

15.11. Trace evidence is not resolution truth beyond retained evidence.

15.12. The following resolution-domain trace reasons are defined:

       - PackRequestParseFailed
       - SemVerParseError
       - CandidateEnumerated
       - CandidateHardRejected
       - CandidateSoftConstrained
       - CandidateSelected
       - AmbiguityDetected
       - ResolutionPermissionDenied
       - ResolutionFailed

15.13. PackRequestParseFailed is emitted when a PackRequest cannot be parsed
       into the internal representation required by this document.

15.14. SemVerParseError is emitted when semantic-version parsing fails in a
       context where a semantic-version requirement is required rather than
       disambiguated as author syntax.

15.15. CandidateEnumerated is emitted when a candidate enters the
       structurally compatible candidate set.

15.16. CandidateHardRejected is emitted when a candidate is excluded by a
       hard constraint.

15.17. CandidateSoftConstrained is emitted when a candidate remains known
       but is discouraged or unavailable unless the surrounding consumer
       context permits it.

15.18. CandidateSelected is emitted when deterministic ordering selects the
       resolved candidate.

15.19. AmbiguityDetected is emitted when resolution cannot select one
       unambiguous result without external decision handling.

15.20. ResolutionPermissionDenied is emitted when resolution refuses a
       candidate or outcome because the active resolution context or
       authority boundary does not permit it.

15.21. ResolutionFailed is emitted when resolution ends in a classified
       failure rather than a selected candidate or ambiguity decision.

15.22. If a resolution path cannot be explained after the fact, that is a
       resolution observability failure.

===============================================================================
17. ERROR MODEL
===============================================================================

LOCKED:

17.1. Resolution errors include examples such as:
      - NotFoundError
      - VersionMismatchError
      - AmbiguousResolutionError
      - PermissionDeniedError

17.2. Resolution errors use the standard error envelope.

17.3. Resolution errors include:
      - PackRequest context
      - resolution context
      - reason classification

17.4. This document does not lock the final full error taxonomy beyond the
      requirement that classification remains explicit.

17.5. Error classification does not create fallback behavior.

17.6. Error classification does not create PackManager repair authority.


===============================================================================
18. LOCKED SUMMARY
===============================================================================

18.1. LOCKED:
      - PackRequest grammar and disambiguation rules
      - immutable PackRequest internal representation
      - side-effect-free resolution
      - resolution over one already-built registry snapshot
      - one explicit consumer-supplied resolution context per attempt
      - no lazy discovery during resolution
      - no indexing during resolution
      - no manifest merging during resolution
      - whole-candidate boundary inherited from DA-09 discovery
      - fingerprint-equivalent candidates select only the first winner
      - shadowed-equivalent candidates remain observable
      - same canonicalPackId and packVersion with different fingerprints are
        non-equivalent candidates
      - candidate origin is explanation context, not authenticity proof
      - phase-A candidate enumeration
      - phase-B hard and soft constraint handling
      - deterministic ordering and winner selection contract
      - deterministic ordering criteria are consumer-supplied
      - concrete version mismatch is a hard exclusion
      - exact fingerprint mismatch is a hard exclusion when such an
        expectation is supplied by context
      - successful and failed resolution outcomes remain observable
      - explicit ambiguity signaling
      - no silent substitution
      - no silent fallback
      - no resolver-owned persistence of ambiguity decisions
      - resolution remains separate from activation, importing, runtime
        loading, capability permission, policy, lifecycle, and state authority
      - resolution-domain trace reason identifiers are owned by DA-11
      - DA-03 remains trace-substrate owner

18.2. DEFERRED:
      - dependency semantics
      - dependency strength
      - graph intent
      - SaveBundle-specific override policy
      - pinning and copying rules
      - activation and lifecycle behavior
      - importing and module-loading behavior
      - consumer-specific ordering criteria
      - user-facing warning and remembered-decision behavior
      - PackManager repair behavior
      - Application and ApplicationRun lifecycle behavior
      - SaveBundle runtime behavior
      - committed-state authority
