===============================================================================
DESIGN AREA DA-22 - UI, VIEWS & FRONTEND RUNTIME
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines Turnix UI and View semantics as presentation, interaction, and
frontend runtime surfaces that remain subordinate to Kernel authority,
execution adapter boundaries, RPC/channel boundaries, capability mediation,
decision handling, RuntimeHost entry-surface boundaries, and committed-state
rules.

This document owns the abstract UI/View model. Concrete browser assets,
component layouts, JavaScript framework choices, and WebSocket frame flow
remain implementation details or implementation specifications.

Purpose:
--------
This document defines how Turnix presents runtime state, receives user input,
loads frontend View code, and connects frontend surfaces to the Kernel without
turning UI behavior into hidden authority.

It defines:
- UI as a presentation and interaction surface
- View as a Kernel-bound frontend runtime surface
- View identity and lifecycle boundaries
- relationship between Views, Applications, ApplicationRuns, and frontend
  clients
- frontend runtime authority boundaries
- frontend runtime as a frontend adapter family under DA-23
- UI pack and View pack participation boundaries
- UI state, presentation state, and authoritative state separation
- frontend event and command flow through RPC
- decision presentation responsibilities
- debugger UI boundaries
- accessibility and presentation transforms
- reconnect and multi-client boundaries
- UI trace and observability obligations

It does NOT define:
- concrete RPC envelope fields (see IS-01)
- concrete WebSocket flow (see IS-02)
- abstract RPC, channel, and transport semantics (see DA-21)
- execution adapter boundary semantics (see DA-23)
- adapter lifecycle semantics or lifecycle classification (see DA-27)
- RuntimeHost identity, workspace ownership, startup modes, entry surfaces, or
  command-surface semantics (see DA-28)
- trace event structure, trace DAG semantics, span mechanics, trace retention,
  trace pruning, or trace storage semantics (see DA-03)
- authoritative committed state or transaction semantics (see DA-04)
- committed-value representation, ValueRef, Chunk, decode, or integrity
  semantics (see DA-05)
- configuration semantics, configuration storage layout, or configuration
  persistence semantics (see DA-06)
- persistent-I/O authority, filesystem authority, Reader/Writer provider, or
  storage-root semantics (see DA-07)
- importing and module-loading boundaries (see DA-12)
- activation lifecycle semantics (see DA-14)
- service, capability, or permission semantics (see DA-16)
- user decision and remembered policy semantics (see DA-17)
- debugging, inspection, and breakpoint semantics (see DA-18)
- Job lifecycle or long-running work semantics (see DA-19)
- Application/ApplicationRun lifecycle or runtime identity semantics
  (see DA-20)
- OrchestrationUnit lifecycle or mutation-authority semantics (see DA-24)
- Window artifact, export, Minimal Audit Bundle, digest, or offline inspection
  artifact semantics (see DA-25)
- comparison, Replay, Resume, Retry, or audit workflow semantics (see DA-26)
- ModCallContext invocation gateway semantics (see DA-30)

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines UI, View, frontend runtime, presentation, and
      interaction semantics within that shared interpretation model.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. UI answers:

          "How does Turnix present state and decisions to users, receive
           interaction, and connect frontend surfaces to Kernel-mediated
           behavior without granting the frontend hidden authority?"

02.2. UI is a presentation and interaction surface.

02.3. UI is not authoritative state by itself.

02.4. UI is not capability authority by itself.

02.5. UI is not policy authority by itself.

02.6. UI is not persistence authority by itself.

02.7. A View is a Kernel-bound frontend runtime surface.

02.8. A View may present one ApplicationRun, one Application, one tool
      surface, one debugger surface, one management surface, or another
      Kernel-recognized surface class.

02.9. A View receives state and sends interaction through Turnix-mediated
      channels.

02.10. A View does not become authoritative merely because the user can see
       or interact with it.

02.11. User interaction becomes meaningful only when the Kernel accepts the
       corresponding command, decision, capability call, or RPC message.

02.12. Frontend runtime code is adapter-executed frontend code under DA-23.

02.13. Frontend adapter execution does not grant authority by itself.

02.14. A View or frontend client may act as a RuntimeHost entry surface only
       when DA-28 and the relevant runtime workflow define that relationship.

02.15. RuntimeHost entry-surface participation does not make UI, View, or
       frontend client behavior RuntimeHost authority by itself.

02.16. UI presentation of state, configuration, payload material, or stored
       material does not define DA-04 committed-state authority, DA-05
       payload representation, DA-06 configuration semantics, or DA-07
       persistent-I/O authority.

02.17. UI, View, audit viewer, reconnect, retained-update, and result
       retrieval wording does not define artifact export, comparison, Replay,
       Resume, Retry, or audit workflow semantics unless routed through DA-25
       or DA-26.


===============================================================================
03. UI, VIEW, AND FRONTEND CLIENT TERMS
===============================================================================

03.1. UI means the user-facing presentation and interaction layer.

03.2. View means a Kernel-recognized frontend surface with identity,
      lifecycle, state delivery, and interaction routing.

03.3. Frontend client means one concrete connected frontend participant, such
      as a browser tab, embedded frontend, developer tool, remote frontend, or
      future frontend host.

03.4. Frontend runtime means the client-side execution environment that
      presents a View and processes frontend interaction.

03.5. Frontend adapter means a frontend-role ExecutionAdapter under DA-23
      whose purpose is presentation, interaction, or frontend runtime
      participation.

03.6. Browser JavaScript frontend runtime is one frontend adapter family.

03.7. One frontend client may bind to one View.

03.8. Multiple frontend clients may bind to one View only when the View
      binding model and policy permit that behavior.

03.9. One ApplicationRun may have zero, one, or multiple Views depending on
      the runtime and policy model.

03.10. A View may present one durable Application without presenting a live
       ApplicationRun only when the surface class defines that behavior.

03.11. A View may exist for a non-ApplicationRun surface such as:
       - launcher
       - pack manager
       - configuration editor
       - debugger
       - artifact viewer
       - audit viewer
       - future management surface

03.12. View identity is distinct from Application identity.

03.13. View identity is distinct from ApplicationRun identity.

03.14. View identity is distinct from frontend client identity.

03.15. Frontend client identity is distinct from user identity.

03.16. Frontend adapter identity is distinct from View identity and frontend
       client identity.

03.17. View identity is distinct from RuntimeHost identity under DA-28.

03.18. Frontend client identity is distinct from RuntimeHost identity under
       DA-28.

03.19. View identity is distinct from Window identity.

03.20. View identity is distinct from artifact or export identity.

03.21. View identity is distinct from comparison, Replay, Resume, Retry, or
       audit workflow identity.

03.22. A launcher, pack manager, configuration editor, artifact viewer, audit
       viewer, or management View may be a RuntimeHost entry surface, but
       DA-28 owns the runtime-host meaning of that entry surface.

03.23. Concrete cookie, token, and bootstrap details belong to implementation
       specifications.

03.24. Client instance wording is not a canonical DA-22 term by itself. When
       used informally, it describes a concrete connected participant whose
       owning concept remains frontend client, remote client, command surface,
       entry surface, transport endpoint, or another term defined by the
       owning document.


===============================================================================
04. VIEW LIFECYCLE
===============================================================================

04.1. A View lifecycle has explicit observable phases.

04.2. View lifecycle phases may include:
      - created
      - bound to frontend client
      - initialized
      - ready
      - disconnected
      - reconnected
      - closed

04.3. View creation does not activate packs by itself.

04.4. View creation does not create an ApplicationRun by itself unless an
      explicit launcher or runtime workflow defines that behavior.

04.5. RuntimeHost startup modes and entry-surface workflows are defined by
      DA-28.

04.6. When a View participates in a launcher or RuntimeHost entry-surface
      workflow, the View lifecycle remains distinct from RuntimeHost
      lifecycle.

04.7. View binding associates a frontend client with a Kernel-recognized
      View identity.

04.8. View readiness means the frontend can receive and process the View's
      expected runtime messages.

04.9. View readiness does not imply ApplicationRun readiness.

04.10. View readiness does not imply RuntimeHost readiness.

04.11. View readiness does not imply pack activation success.

04.12. View readiness does not imply frontend adapter execution success
       beyond the View readiness condition itself.

04.13. View disconnect is a frontend or transport condition.

04.14. View disconnect does not automatically cancel Jobs.

04.15. View disconnect does not automatically fail a frontend adapter.

04.16. View disconnect does not automatically deactivate an ApplicationRun.

04.17. View disconnect does not automatically stop, fail, or close a
       RuntimeHost.

04.18. View disconnect does not automatically discard authoritative state.

04.19. View disconnect does not define Window finalization.

04.20. View disconnect does not define artifact or export creation.

04.21. View disconnect does not define comparison, Replay, Resume, Retry, or
       audit workflow outcomes.

04.22. If View disconnect affects accepted or in-flight work, DA-17 and
       DA-19 govern policy and Job lifecycle outcomes.

04.23. If View disconnect affects frontend adapter lifecycle, DA-23 and
       DA-27 govern adapter boundary and adapter lifecycle classification.

04.24. If View disconnect affects RuntimeHost entry-surface behavior, DA-28
       governs RuntimeHost lifecycle or host-operation classification.

04.25. View closure releases the View runtime surface.

04.26. View closure does not by itself define whether ApplicationRun work
       committed, aborted, continued, detached, requested DA-26 Retry,
       requested DA-26 Resume, finalized a Window, created an artifact or
       export, or completed an audit workflow.

04.27. View closure does not by itself define RuntimeHost stop, failure, or
       command-surface outcome.


===============================================================================
05. FRONTEND RUNTIME AUTHORITY BOUNDARY
===============================================================================

05.1. Frontend runtime code executes as presentation and interaction logic.

05.2. Frontend runtime code is adapter-executed code under DA-23.

05.3. Frontend runtime code does not gain direct authority over committed
      state.

05.4. Frontend runtime code does not mutate files directly as a Turnix
      authority path.

05.5. Frontend runtime code does not bypass execution adapter, RPC,
      capability, policy, transaction, or persistence boundaries.

05.6. Frontend runtime code does not bypass RuntimeHost workspace ownership,
      startup-mode, entry-surface, or command-surface boundaries under DA-28.

05.7. Frontend runtime code sends requests, emits events, subscribes to
      updates, and presents received state through DA-21 RPC semantics.

05.8. Kernel-side handlers decide whether a frontend request is valid.

05.9. Kernel-side handlers decide whether a frontend request crosses a
      capability, policy, persistence, adapter, RuntimeHost, or mutation
      boundary.

05.10. A frontend command is not authoritative merely because the user
       clicked, typed, dragged, confirmed, or otherwise interacted with the
       UI.

05.11. A frontend command that targets RuntimeHost control behavior remains
       subject to DA-28.

05.12. Frontend code may hold presentation-local state.

05.13. Presentation-local state does not become committed state unless a
       Kernel-mediated mutation commits it under DA-04 and related documents.

05.14. Frontend adapter execution authorization is distinct from capability
       permission for frontend-originated requests.

05.15. Frontend adapter execution authorization is distinct from DA-27
       adapter lifecycle outcome.

05.16. Frontend-originated persistence requests remain mediated by Kernel and
       IoManager authority paths.

05.17. Frontend-originated configuration changes remain mediated by
       configuration and policy authority paths.


===============================================================================
06. VIEW PACKS AND UI PACK PARTICIPATION
===============================================================================

06.1. View packs and UI-related packs may provide frontend modules,
      components, layouts, or interaction behavior.

06.2. View packs remain packs.

06.3. View packs remain subject to discovery, identity, resolution,
      dependency, import, adapter selection, execution authorization,
      activation, visibility, and capability rules.

06.4. A View pack does not gain authority merely because it renders visible
      UI.

06.5. A View pack does not bypass turnixImport or other code-boundary rules.

06.6. JavaScript frontend code loaded for a View remains constrained by
      DA-12 import and module-loading rules.

06.7. View pack activation remains constrained by DA-14.

06.8. View pack invocation surfaces remain constrained by DA-30 when
      ModCallContext gateway semantics apply.

06.9. View pack execution remains constrained by DA-23.

06.10. View pack lifecycle outcome remains constrained by DA-27 when adapter
       lifecycle classification applies.

06.11. View pack interaction with backend behavior remains mediated through
       RPC, services, capabilities, or other Turnix-defined surfaces.

06.12. View pack interaction with RuntimeHost control behavior remains
       mediated through DA-28-constrained entry-surface and command-surface
       rules.

06.13. View pack code must not assume another pack is activated merely
       because that pack appears in the UI.

06.14. UI extension points are explicit.

06.15. UI extension points do not imply arbitrary mutation authority.

06.16. UI extension points do not imply RuntimeHost control authority.

06.17. UI extension points do not imply artifact/export authority or DA-26
       workflow outcome authority.


===============================================================================
07. UI STATE, PRESENTATION STATE, AND AUTHORITATIVE STATE
===============================================================================

07.1. UI may present state snapshots, deltas, computed projections,
      validation results, progress, diagnostics, and decision prompts.

07.2. UI may present payload, configuration, persistence, artifact, export,
      comparison, workflow, or retained-evidence material when another owning
      domain supplies or authorizes that material.

07.3. Presented state is not authoritative merely because it is presented.

07.4. Presentation state may include:
      - selected tab
      - scroll position
      - expanded tree node
      - local filter
      - temporary draft input
      - layout size
      - frontend-only cache

07.5. Presentation state is non-authoritative unless explicitly persisted
      through Turnix-managed state or configuration.

07.6. UI projections may simplify or summarize authoritative state.

07.7. UI projections do not replace the authoritative source of truth.

07.8. If a UI projection omits, filters, groups, rounds, truncates, or
      summarizes state, the projection remains presentation-only.

07.9. If a presented value can become stale, the UI does not present stale
      data as confirmed current truth.

07.10. The Kernel remains responsible for authoritative mutation and
       validation of submitted changes.

07.11. Frontend-side validation may improve user experience.

07.12. Frontend-side validation does not replace Kernel validation.

07.13. Frontend-side validation does not replace capability permission,
       execution authorization, policy evaluation, or persistence authority.

07.14. Frontend-side validation does not replace DA-05 payload decode or
       integrity semantics.

07.15. Frontend-side validation does not replace DA-06 configuration
       validation, storage layout, migration, or materialization semantics.

07.16. Frontend-side validation does not replace DA-07 persistent-I/O
       authority or storage safety.

07.17. A UI draft becomes authoritative only through an accepted
       Kernel-mediated mutation that reaches the owning commit boundary.


===============================================================================
08. FRONTEND EVENT AND COMMAND FLOW
===============================================================================

08.1. Frontend interactions become Turnix-visible only when sent through a
      Turnix-mediated channel.

08.2. Frontend interactions may produce:
      - RPC request
      - RPC emit
      - capability-routed request
      - decision response
      - subscription request
      - cancellation request
      - debugger command
      - configuration or management command
      - artifact or export command
      - comparison or workflow command
      - RuntimeHost entry-surface command

08.3. The Kernel classifies the received interaction.

08.4. The Kernel routes the interaction through the appropriate authority
      surface.

08.5. If the interaction invokes a capability, DA-16 governs capability
      mediation and permission semantics.

08.6. If the interaction crosses an adapter boundary, DA-23 governs adapter
      boundary semantics.

08.7. If the interaction affects adapter lifecycle classification, DA-27
      governs adapter lifecycle semantics.

08.8. If the interaction answers a decision point, DA-17 governs decision
      handling.

08.9. If the interaction controls a Job, DA-19 governs Job lifecycle
      semantics.

08.10. If the interaction controls debugger behavior, DA-18 governs debugger
       semantics.

08.11. If the interaction controls RuntimeHost behavior, DA-28 governs
       RuntimeHost lifecycle, command-surface, entry-surface, and host-
       operation semantics.

08.12. If the interaction mutates committed state, DA-04 governs commit
       semantics.

08.13. If the interaction persists or inspects committed payload material,
       DA-05 and DA-07 govern representation and persistent-I/O boundaries.

08.14. If the interaction persists configuration or policy material, DA-06
       and DA-17 govern configuration and policy scope behavior.

08.15. If the interaction creates, inspects, imports, or exports Window
       artifacts, DA-25 governs artifact/export semantics.

08.16. If the interaction requests comparison, Replay, Resume, Retry, or
       audit workflow behavior, DA-26 governs the workflow semantics.

08.17. UI event order does not by itself define committed-state order.

08.18. UI event order does not by itself define RuntimeHost operation order.

08.19. UI event order does not by itself define artifact/export order.

08.20. UI event order does not by itself define comparison, Replay, Resume,
       Retry, or audit workflow order.

08.21. Committed-state order is defined by the relevant Kernel-owned commit
       and orchestration boundaries.

08.22. RuntimeHost operation order is defined by RuntimeHost and owning
       runtime-operation rules under DA-28 and related documents.


===============================================================================
09. DECISION PRESENTATION RESPONSIBILITIES
===============================================================================

09.1. UI may present Kernel-originated decision points.

09.2. Decision presentation is not decision ownership.

09.3. DA-17 owns decision and policy semantics.

09.4. The UI presents only valid options supplied or authorized by the
      Kernel.

09.5. The UI does not invent hidden defaults.

09.6. The UI does not auto-confirm decisions without policy authority.

09.7. The UI presents consequences, scope, and persistence effect when such
      information is available.

09.8. The UI preserves distinctions between:
      - allow and deny
      - for-this-run and remember
      - soft and hard decisions
      - execution authorization and capability permission
      - capability permission decisions and work-lifecycle policy decisions
      - transport timeout and Job timeout
      - transport disconnect and adapter failure
      - View disconnect and RuntimeHost stop
      - frontend command receipt and RuntimeHost command acceptance
      - cancellation and supersession
      - failure and Superseded
      - debugger resume / continue and DA-26 Resume
      - local UI retry affordance and DA-26 Retry
      - artifact presentation and artifact/export authority
      - result presentation and comparison/workflow outcome authority

09.9. If multiple frontend clients present the same decision point, the
      Kernel remains the single arbiter of the accepted response.

09.10. A stale or already-resolved decision presentation is dismissed or
       marked inactive rather than accepted again.


===============================================================================
10. DEBUGGER AND TOOLING UI BOUNDARIES
===============================================================================

10.1. Debugger UI is a frontend surface for debugger behavior.

10.2. Debugger UI does not own debugger semantics.

10.3. DA-18 owns debugger inspection, breakpoint, pause, mutation,
      disconnect, and Job-control semantics.

10.4. Debugger UI may request inspection, pause, debugger resume / continue
      from debugger pause, mutation, cancellation, supersession, or
      safe-point behavior only through Turnix-mediated channels.

10.5. Debugger UI resume / continue from debugger pause is debugger-control
      behavior under DA-18.

10.6. Debugger UI resume / continue from debugger pause does not mean DA-26
      Resume after SafePointWindow restoration.

10.7. Debugger UI does not directly write committed state.

10.8. Debugger UI does not directly write Job terminal state.

10.9. Debugger UI does not bypass policy decisions when policy is required.

10.10. Debugger UI does not bypass adapter boundaries when debugger UI code
       is frontend adapter code.

10.11. Debugger UI distinguishes staged, committed, unavailable, and
       unresolved state when those distinctions are surfaced.

10.12. Debugger UI does not present paused-at-safe-point Jobs as terminal.

10.13. Debugger UI does not present Superseded as failure.


===============================================================================
11. ACCESSIBILITY AND PRESENTATION TRANSFORMS
===============================================================================

11.1. UI may apply presentation transforms for accessibility, readability,
      localization, scaling, filtering, grouping, or layout.

11.2. Presentation transforms are runtime presentation behavior.

11.3. Presentation transforms do not mutate authoritative state by
      themselves.

11.4. Presentation transforms do not change capability, permission,
      decision, Job, adapter, RuntimeHost, debugging, artifact/export, or
      DA-26 workflow semantics.

11.5. If a presentation transform is persisted as user preference, that
      persistence follows configuration and policy rules defined elsewhere.

11.6. Computed-only presentation transforms are not persisted merely because
      they are visible.

11.7. UI does not silently persist computed-only presentation effects as
      configuration or committed state.


===============================================================================
12. VIEW DISCONNECT, RECONNECT, AND MULTI-CLIENT BEHAVIOR
===============================================================================

12.1. A frontend client may disconnect while a View remains meaningful.

12.2. A View may reconnect when the connection model permits reconnection.

12.3. Reconnect does not imply re-emission of all missed frontend-local
      events.

12.4. Reconnect does not mean DA-26 Replay.

12.5. Reconnect may receive a fresh snapshot, generation update, retained
      update state, or another implementation-defined recovery surface.

12.6. Reconnect delivery does not define artifact/export authority or DA-26
      workflow outcome.

12.7. Concrete reconnect flow belongs to implementation specifications.

12.8. Multi-client View behavior is explicit.

12.9. Multiple frontend clients do not create multiple authoritative truths
      for the same View.

12.10. If concurrent frontend interactions conflict, the Kernel resolves the
       conflict through normal authority, ordering, policy, and commit rules.

12.11. View disconnect does not silently cancel, supersede, detach, retain,
       or discard accepted work.

12.12. View disconnect does not silently fail frontend adapter execution.

12.13. View disconnect does not silently stop, fail, or close RuntimeHost
       execution.

12.14. View disconnect does not silently finalize a Window.

12.15. View disconnect does not silently create an artifact or export.

12.16. View disconnect does not silently complete comparison, Replay, Resume,
       Retry, or audit workflow behavior.

12.17. Those outcomes require policy or lifecycle authority defined in the
       owning documents.


===============================================================================
13. UI TRACE AND OBSERVABILITY
===============================================================================

13.1. DA-22 defines UI-domain trace emission obligations.

13.2. DA-03 owns trace event structure, trace DAG semantics, span mechanics,
      trace retention, trace pruning, trace loss, and trace storage semantics.

13.3. UI and View lifecycle behavior remains trace-visible where trace
      evidence exists.

13.4. UI trace evidence distinguishes:
      - View created
      - frontend client bound
      - View initialized
      - View ready
      - View disconnected
      - View reconnected
      - View closed
      - frontend command received
      - decision presented
      - decision response submitted
      - UI-originated cancellation requested
      - UI-originated debugger command requested
      - UI-originated RuntimeHost command requested

13.5. UI trace evidence records enough context, when available, to explain:
      - viewId
      - frontend client identity
      - frontend adapter identity when applicable
      - runtimeHostId when applicable
      - RuntimeHost operation identity when applicable
      - applicationId when applicable
      - applicationRunId when applicable
      - active pack identity when applicable
      - SaveBundle identity when applicable
      - RPC message identity when applicable
      - decision identity when applicable
      - jobId when applicable
      - debugger request identity when applicable
      - command kind
      - disconnect or reconnect reason category when applicable

13.6. UI trace evidence does not replace RPC trace evidence.

13.7. UI trace evidence does not replace adapter trace evidence.

13.8. UI trace evidence does not replace decision trace evidence.

13.9. UI trace evidence does not replace RuntimeHost trace evidence.

13.10. UI trace evidence does not replace capability, Job, debugger,
       Application, or ApplicationRun trace evidence.

13.11. UI trace evidence does not replace Window trace evidence.

13.12. UI trace evidence does not replace artifact/export trace evidence.

13.13. UI trace evidence does not replace comparison, Replay, Resume, Retry,
       or audit workflow trace evidence.

13.14. UI trace evidence does not replace committed-state trace evidence.

13.15. UI trace evidence does not imply that trace evidence is committed
       state.

13.16. UI trace evidence does not imply that trace persistence is guaranteed
       forever.

13.17. DA-21 defines RPC trace correlation semantics.

13.18. DA-23 defines adapter-boundary trace obligations.

13.19. DA-27 defines adapter lifecycle trace obligations.

13.20. DA-17 defines decision trace obligations.

13.21. DA-18 defines debugger trace obligations.

13.22. DA-19 defines Job lifecycle trace obligations.

13.23. DA-20 defines Application/ApplicationRun trace obligations.

13.24. DA-25 defines artifact/export trace obligations where artifact or
       export creation occurs.

13.25. DA-26 defines workflow trace obligations for comparison, Replay,
       Resume, Retry, and audit workflows.

13.26. DA-28 defines RuntimeHost-domain trace obligations.


===============================================================================
14. UI DOMAIN TRACE REASON IDENTIFIERS
===============================================================================

14.1. DA-22 owns the UI-domain trace reason identifiers used for View
      lifecycle, frontend binding, frontend command receipt, decision
      presentation, and UI-originated control requests.

14.2. The following UI-domain trace reasons are defined:

      - ViewCreated
      - ViewFrontendBound
      - ViewInitialized
      - ViewReady
      - ViewDisconnected
      - ViewReconnected
      - ViewClosed
      - UICommandReceived
      - UIDecisionPresented
      - UIDecisionResponseSubmitted
      - UICancelRequested
      - UIDebuggerCommandRequested
      - UIRuntimeHostCommandRequested

14.3. ViewCreated is emitted when a View identity is created by the Kernel.

14.4. ViewFrontendBound is emitted when a frontend client is bound to a
      View.

14.5. ViewInitialized is emitted when the View initialization path begins or
      completes according to the concrete implementation contract.

14.6. ViewReady is emitted when the frontend reports or reaches the ready
      condition for the View.

14.7. ViewDisconnected is emitted when the frontend client or View
      connection disconnects.

14.8. ViewReconnected is emitted when a frontend client reconnects to an
      existing View identity under valid reconnection rules.

14.9. ViewClosed is emitted when the View is closed or released by the
      Kernel.

14.10. UICommandReceived is emitted when a frontend command is received and
       accepted for classification by the Kernel.

14.11. UIDecisionPresented is emitted when a decision point is presented to
       a frontend client.

14.12. UIDecisionResponseSubmitted is emitted when a frontend client submits
       a decision response.

14.13. UICancelRequested is emitted when a frontend interaction requests
       cancellation or withdrawal of interest.

14.14. UIDebuggerCommandRequested is emitted when debugger UI requests a
       debugger action.

14.15. UIRuntimeHostCommandRequested is emitted when frontend interaction
       requests RuntimeHost control behavior.

14.16. UIRuntimeHostCommandRequested does not define RuntimeHost command
       acceptance, RuntimeHost operation success, or RuntimeHost lifecycle
       outcome.

14.17. UI-domain trace reasons describe UI/View behavior only.

14.18. UI-domain trace reasons do not define capability outcome, Job
       terminal outcome, decision outcome, debugger outcome, adapter outcome,
       RuntimeHost outcome, Window outcome, artifact/export outcome,
       committed-state mutation outcome, or DA-26 workflow outcome.


===============================================================================
15. RELATION TO IMPLEMENTATION SPECIFICATIONS
===============================================================================

15.1. Implementation specifications may define:
       - concrete browser bootstrap flow
       - concrete View registry behavior
       - concrete frontend adapter binding
       - concrete frontend asset loading
       - concrete component mounting
       - concrete frontend state synchronization
       - concrete reconnect behavior
       - concrete multi-client behavior
       - concrete UI event payloads
       - concrete artifact or audit viewer UI behavior
       - concrete RuntimeHost frontend entry-surface payloads when constrained
         by DA-28
       - concrete CSS, layout, or component conventions
       - concrete cookie or token format

15.2. Implementation specifications do not redefine:
       - UI as non-authoritative presentation
       - frontend runtime as adapter-executed frontend code
       - View identity and lifecycle meaning
       - Kernel ownership of decisions
       - frontend client as a concrete connected frontend participant
       - client instance wording as a canonical DA-22 term
       - RPC, adapter, capability, Job, debugger, RuntimeHost, Window,
         artifact/export, DA-26 workflow, and committed-state boundaries

15.3. If a frontend implementation requires a semantic rule not defined
      here, this document is updated first or alongside that implementation
      specification.


===============================================================================
16. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

16.1. The following are not supported:
      - frontend-only authoritative mutation
      - frontend adapter execution treated as authority by itself
      - UI-controlled bypass of execution adapter boundaries
      - UI-controlled bypass of capability mediation
      - UI-controlled bypass of decision handling
      - UI-controlled bypass of RuntimeHost workspace ownership or command-
        surface semantics
      - UI-controlled bypass of persistence authority
      - UI-controlled direct filesystem access as a Turnix authority path
      - UI-created hidden policy defaults
      - UI-created hidden activation or pack-loading behavior
      - UI-created hidden RuntimeHost startup behavior
      - UI-created hidden RuntimeHost command acceptance
      - UI-created hidden Window finalization
      - UI-created hidden artifact or export authority
      - UI-created hidden comparison, Replay, Resume, Retry, or audit workflow
        outcome
      - presenting transport timeout as Job timeout
      - presenting Job timeout as transport timeout
      - presenting transport disconnect as adapter failure
      - presenting adapter failure as transport disconnect
      - presenting View disconnect as RuntimeHost stop
      - presenting RuntimeHost stop as View disconnect
      - presenting Superseded as failure
      - presenting debugger resume / continue from pause as DA-26 Resume
      - presenting a UI retry affordance as DA-26 Retry outcome by itself
      - treating visible state as authoritative merely because it is visible
      - treating visible RuntimeHost control UI as RuntimeHost authority by
        itself
      - treating visible artifact/export UI as artifact/export authority by
        itself
      - treating visible comparison/workflow UI as DA-26 workflow authority by
        itself
      - treating frontend client identity as View identity
      - treating frontend client identity as RuntimeHost identity
      - treating client instance wording as a canonical DA-22 concept by itself

18. LOCKED SUMMARY
===============================================================================

18.1. LOCKED:
      - UI is presentation and interaction, not authority by itself
      - View is a Kernel-bound frontend runtime surface
      - frontend client is one concrete connected frontend participant
      - client instance wording is not a canonical DA-22 concept by itself
      - frontend runtime code is adapter-executed frontend code under DA-23
      - frontend adapter is a frontend-role ExecutionAdapter family
      - View identity is distinct from Application identity
      - View identity is distinct from ApplicationRun identity
      - View identity is distinct from frontend client identity
      - frontend client identity is distinct from user identity
      - frontend client identity is distinct from RuntimeHost identity
      - View identity is distinct from RuntimeHost identity
      - View identity is distinct from Window, artifact/export, and DA-26
        workflow identity
      - frontend adapter identity is distinct from View identity and frontend
        client identity
      - frontend runtime code does not directly mutate committed state
      - frontend runtime code does not bypass execution adapter, RPC,
        capability, policy, transaction, persistence, or RuntimeHost
        boundaries
      - View packs remain subject to normal pack, import, adapter selection,
        execution authorization, activation, visibility, and capability rules
      - presentation state is non-authoritative unless explicitly persisted
        through Turnix-managed state or configuration
      - frontend-side validation does not replace Kernel validation
      - frontend-side validation does not replace execution authorization,
        capability permission, policy evaluation, persistence authority,
        payload integrity, or configuration validation
      - decision presentation is not decision ownership
      - debugger UI does not own debugger semantics
      - debugger resume / continue from pause is not DA-26 Resume
      - accessibility and presentation transforms do not mutate
        authoritative state by themselves
      - View disconnect does not silently cancel, supersede, detach, retain,
        discard accepted work, fail frontend adapter execution, stop/fail
        RuntimeHost execution, finalize a Window, create an artifact/export,
        or complete DA-26 workflow behavior
      - UI-domain trace reason identifiers are owned by DA-22
      - RuntimeHost-domain trace reason identifiers are owned by DA-28
      - UI trace evidence does not replace RPC, adapter, decision,
        capability, Job, debugger, RuntimeHost, Application/ApplicationRun,
        Window, artifact/export, committed-state, or DA-26 workflow trace
        evidence

18.2. OPEN:
      - concrete View registry, frontend bootstrap, frontend adapter binding,
        state sync, UI extension, reconnect, multi-client, artifact/audit
        viewer, and component implementation details
