===============================================================================
OPTIONAL DESIGN AREA ODA-D - MINIMAL PACK / MOD CONTRACT
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines an optional minimal contract model for Pack and mod compatibility,
version and fingerprint binding, adapter requirements, and update safety.

This area is pragmatic and subordinate. It does not replace the Turnix
DESIGN AREA documents that define runtime authority, state, persistence,
resolution, activation, adapter, capability, or policy semantics.

Purpose:
--------
This document records a minimal compatibility and update-safety model aimed
at low author burden, reproducibility, reversibility, and explicit
uncertainty.

It defines:
- a pragmatic ownership model
- a three-part compatibility split
- adapter and runtime requirement compatibility as optional diagnostics
- SaveBundle published-generation Pack binding for restoration
- safe-default update behavior
- storage and cleanup expectations for retained Pack material

It does NOT define:
- authoritative dependency semantics
- authoritative generic resolution behavior
- authoritative activation rules
- authoritative visibility or import rules
- authoritative execution adapter semantics
- authoritative capability or permission semantics
- authoritative persistence, state, or SaveBundle semantics
- authoritative Application or ApplicationRun lifecycle semantics
- final manifest field shapes or schema details
- any guarantee that compatibility can be proven in advance

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines an optional minimal Pack and mod contract model
      within that shared interpretation model.

01.05. This document is subordinate to DESIGN AREA documents that own the
      affected runtime, persistence, graph, activation, adapter, and
      permission domains.


===============================================================================
02. CORE ASSUMPTION
===============================================================================

02.01. Turnix does not guarantee compatibility correctness in advance.

02.02. This model instead prioritizes:
      - reproducibility
      - reversibility
      - explicit uncertainty

02.03. This document treats those three properties as the practical baseline
      for a low-burden compatibility contract.

02.04. This document does not claim that broad compatibility guarantees can
      be made reliable merely through author declarations.

02.05. Adapter compatibility declarations improve diagnostics but do not
      prove safe execution.

02.06. Capability compatibility declarations improve diagnostics but do not
      grant capability permission.

02.07. Version and fingerprint binding improve restoration reliability but
      do not replace the owning domains that define state truth, Pack graph
      truth, activation truth, or persistence truth.


===============================================================================
03. OWNERSHIP MODEL
===============================================================================

03.01. In this model, Turnix owning domains own:
      - stability enforcement at their own boundaries
      - version and fingerprint binding behavior
      - rollback and restoration support where their domains provide it
      - enforcement of hard rules that belong to their domains

03.02. In this model, the Pack author owns:
      - intent
      - declaration of minimum requirements
      - declaration of runtime requirements where applicable
      - declaration of adapter requirements where applicable
      - declaration of capability reliance where applicable

03.03. In this model, the Pack author does not guarantee broad
      compatibility.

03.04. In this model, the user owns decisions only after consequences are
      made explicit.

03.05. This ownership split exists so that no party is assigned a burden it
      cannot realistically satisfy.

03.06. The term "Turnix owning domains" does not mean one monolithic
      system object.

03.07. The owning domain for a compatibility question is the domain that
      owns the affected authority boundary.


===============================================================================
04. THREE KINDS OF COMPATIBILITY
===============================================================================

04.01. This model separates:
      - hard compatibility
      - soft compatibility
      - capability compatibility


04.01 Hard compatibility
-----------------------

04.01.01. Hard compatibility is non-negotiable in this model.

04.01.02. Hard compatibility is declared by the Pack author and enforced by
        the Turnix owning domain at the affected boundary.

04.01.03. If hard compatibility fails, the failure blocks the operation whose
        boundary detected the failure.

04.01.04. A hard compatibility failure may block:
        - inclusion in an accepted runtime graph
        - adapter binding
        - activation-entry loading
        - Pack activation
        - another owning-domain operation that depends on the failed rule

04.01.05. A hard compatibility failure does not need to block discovery when
        discovery can still classify the candidate safely.

04.01.06. This model does not allow ordinary override or "try anyway"
        behavior for hard compatibility failure.

04.01.07. Example:
        turnixApi: ">=1.6 <2.0"

04.01.08. Typical hard-compatibility content may include:
        - required Turnix API range
        - required runtime such as JavaScript, Python, or a VM
        - required ExecutionAdapter kind
        - required adapter isolation property where the owning adapter
          contract defines such a property
        - required execution model such as ESM versus CJS or sync versus
          async

04.01.09. If hard compatibility mismatches:
        - the relevant owning-domain operation is blocked
        - the error is explicit and final for that operation

04.01.10. The purpose of hard compatibility is to protect Turnix authority
         boundaries and prevent undefined participation.

04.01.11. Hard compatibility does not bypass execution adapter authorization.

04.01.12. Hard compatibility does not grant dependency satisfaction,
         visibility, import permission, capability permission, or lifecycle
         authority by itself.


04.02 Soft compatibility
-----------------------

04.02.01. Soft compatibility is informational in this model.

04.02.02. Soft compatibility means:
        - the Pack may work
        - the Pack is not proven compatible by this declaration alone

04.02.03. Soft compatibility is optional for Pack authors to declare.

04.02.04. Example:
        testedWith:
        - turnix@1.6.0
        - turnix@1.6.1

04.02.05. If the current Turnix version is outside testedWith:
        - the Pack may still remain eligible where hard rules pass
        - the Pack is marked as unverified for that version
        - Turnix emits an informational warning

04.02.06. Warnings in this model are consequence-based rather than
        moralized.

04.02.07. Good warning example:
        "This Pack has not been tested with Turnix 1.6.2.
         Last known tested version: 1.6.0."

04.02.08. This model avoids yes-or-no prompting based only on soft
        compatibility.

04.02.09. Soft adapter compatibility warning does not imply adapter execution
        authorization.

04.02.10. Soft compatibility information may feed diagnostics, user decision
         surfaces, or policy surfaces only where the owning documents allow
         that use.


04.03 Capability compatibility
-----------------------------

04.03.01. Capability compatibility is fine-grained in this model.

04.03.02. Packs may declare which Turnix capabilities they rely on.

04.03.03. Example:
        capabilities:
        - worldState.write
        - ui.inject
        - asset.pipeline@1

04.03.04. If Turnix tracks capability changes between versions, a Pack may be
        flagged as potentially affected when one of those capabilities
        changes.

04.03.05. Example:
        "Capability 'ui.inject' changed behavior in Turnix 1.6.2."

04.03.06. The purpose of capability compatibility is to improve diagnostics
        without forcing authors to re-release merely to update version tags.

04.03.07. Capability compatibility does not grant capability permission.

04.03.08. Capability compatibility does not grant service-object access.

04.03.09. Capability compatibility does not make a capability invocation
        valid when permission, policy, visibility, activation, or runtime
        state would reject the invocation.


===============================================================================
05. COMPATIBILITY DECLARATION AUTHORITY BOUNDARIES
===============================================================================

05.01. Compatibility declarations are inputs to validation, diagnostics,
      graph preparation, and policy or user decision surfaces where owning
      documents allow them.

05.02. Compatibility declarations do not define dependency semantics.

05.03. Compatibility declarations do not define resolution semantics.

05.04. Compatibility declarations do not define activation semantics.

05.05. Compatibility declarations do not define import or module-loading
      semantics.

05.06. Compatibility declarations do not grant Pack visibility.

05.07. Compatibility declarations do not satisfy dependencies by
      themselves.

05.08. Compatibility declarations do not grant adapter execution
      authorization.

05.09. Compatibility declarations do not grant capability permission.

05.10. Compatibility declarations do not grant persistence authority.

05.11. Compatibility declarations do not grant lifecycle authority.

05.12. A compatibility declaration may be used only within the authority
       boundary of the domain consuming it.

05.13. A compatibility declaration remains evidence or constraint input.

05.14. A compatibility declaration does not become Kernel authority,
       RuntimeHost authority, PackManager authority, resolver authority,
       activator authority, adapter authority, or permission authority.


===============================================================================
06. SAVEBUNDLE GENERATION PACK BINDING
===============================================================================

06.01. In this model, a SaveBundle generation records exact Pack bindings
      used for restoration.

06.02. Recorded Pack bindings may include:
      - accepted Pack identity
      - exact Pack version
      - Pack fingerprint or content identity
      - copied Pack binding
      - pinned external Pack binding
      - compatibility evidence used when the generation was published

06.03. Example:
      saveBundleGeneration:
        applicationId: example-application
        generationId: 43
        packs:
        - packId: example.mod
          version: 2.3.1
          fingerprint: abcdef123456

06.04. Model rules:
      - updates do not overwrite a published SaveBundle generation
      - loading a SaveBundle uses a published generation
      - loading a SaveBundle creates another ApplicationRun of the same
        Application
      - future updates create future graph selections or future generations

06.05. The intended result is:
      - deterministic restoration
      - no silent breakage from updates
      - straightforward rollback to retained published generations

06.06. SaveBundle generations preserve restoration evidence and accepted
      graph bindings.

06.07. SaveBundle generations do not replace semantic ownership of state,
      policy, configuration, trace, resolution, activation, adapter,
      capability, permission, or lifecycle domains.

06.08. SaveBundle generation binding does not make SaveBundle identity the
      same as Application identity.

06.09. SaveBundle generation binding does not make SaveBundle identity the
      same as ApplicationRun identity.

06.10. SaveBundle generation binding does not authorize multi-writer
       SaveBundle mutation.

06.11. SaveBundle generation binding is subordinate to higher-authority
       persistence, Application, ApplicationRun, state, and Pack graph
       documents.


===============================================================================
07. UPDATE POLICY
===============================================================================

07.01. In this model, updates do not silently alter retained published
      SaveBundle generations.

07.02. In this model, updates do not silently alter an active
      ApplicationRun.

07.03. Safe-default behavior treats follow-up updates as future-selection
      inputs rather than mutations of already accepted runtime material.

07.04. Example per-Application or per-SaveBundle setting:
      - followUpdates = false as default
      - followUpdates = true only by explicit opt-in

07.05. Rolling-profile behavior may exist in this model.

07.06. Rolling-profile behavior may affect future graph preparation.

07.07. Rolling-profile behavior may affect future SaveBundle generations.

07.08. Rolling-profile behavior does not change already published
      SaveBundle generations.

07.09. Rolling-profile behavior does not silently change an active
      ApplicationRun.

07.10. Updating a Pack does not silently change the accepted Pack graph of
       an already published SaveBundle generation.

07.11. Updating a Pack does not silently change an already running
       ApplicationRun.


===============================================================================
08. STORAGE AND CLEANUP
===============================================================================

08.01. In this model, Turnix may keep multiple versions of the same Pack.

08.02. Pack material referenced by retained published SaveBundle
      generations is not deleted by ordinary cleanup.

08.03. Pack material referenced by explicit pins is not deleted by ordinary
      cleanup.

08.04. Pack material referenced by accepted graph evidence is not deleted by
      ordinary cleanup.

08.05. Pack material referenced by copied or pinned bindings is not deleted
      by ordinary cleanup.

08.06. Pack material required by retained compatibility policy is not
      deleted by ordinary cleanup.

08.07. Unreferenced Pack versions may be deleted by policy.

08.08. Example deletion policies may include:
      - age-based cleanup
      - disk quota cleanup
      - explicit user cleanup

08.09. Users may pin Pack versions manually to prevent deletion.

08.10. Storage cleanup does not remove material required by retained
       authoritative state.

08.11. Storage cleanup does not remove material required by owning-domain
       retention rules.

08.12. Cleanup policy does not define Pack graph truth.

08.13. Cleanup policy does not define persistence truth.


===============================================================================
09. WHAT THIS CONTRACT DOES NOT REQUIRE
===============================================================================

09.01. This model does not require Pack authors to:
      - maintain parallel branches
      - publish exact works-with-every-version claims
      - update only to silence warnings

09.02. This model does not require users to:
      - understand dependency graphs
      - manage version pinning manually in normal use
      - reason about adapter authority boundaries directly

09.03. This model does not pretend that compatibility can be guaranteed in
      advance.

09.04. This model does not require every compatibility warning to become a
      decision prompt.

09.05. This model does not require Turnix to retain unbounded Pack material
      when no retained generation, pin, evidence, or policy requires it.


===============================================================================
10. WHAT THIS CONTRACT GUARANTEES
===============================================================================

10.01. Within the scope of this model:
      - a build that worked once can be restored when required retained
        material is still available
      - updates remain reversible within retained generation and rollback
        boundaries
      - responsibility remains explicit
      - uncertainty remains visible rather than hidden
      - stability remains system-owned rather than outsourced to authors

10.02. These practical guarantees remain subordinate to higher-authority
      state, Application, ApplicationRun, persistence, adapter, permission,
      resolution, activation, and Pack graph documents.

10.03. This document does not guarantee that every retained build remains
      executable forever when required external runtime conditions are no
      longer available.

10.04. This document does not guarantee that compatibility declarations can
      prove behavioral correctness.


===============================================================================
11. RELATION TO HIGHER DOCUMENTS
===============================================================================

11.01. This document is optional and subordinate.

11.02. If this document conflicts with higher-authority DESIGN AREA
      documents, the higher-authority documents win.

11.03. This document is useful only to the extent that it remains aligned
      with the higher Turnix design.

11.04. The lifecycle and runtime-identity design owns Application and
      ApplicationRun identity.

11.05. The persistence design owns SaveBundle persistence and generation
      publication semantics.

11.06. The Pack graph, dependency, and resolution designs own accepted graph
      selection semantics.

11.07. The activation design owns Pack activation semantics.

11.08. The execution adapter design owns adapter boundary semantics.

11.09. The capability and permission designs own capability invocation and
      permission semantics.

11.10. This document may describe compatibility inputs to those domains.

11.11. This document does not absorb authority from those domains.


===============================================================================
12. LOCKED AND OPEN
===============================================================================

12.01. LOCKED:
      - the hard, soft, and capability compatibility split
      - low-burden authoring intent
      - reproducibility, reversibility, and explicit uncertainty as the
        practical foundation of this model
      - adapter compatibility declarations do not grant adapter authority
      - capability compatibility declarations do not grant capability
        permission
      - SaveBundle published generations are not silently changed by Pack
        updates
      - active ApplicationRuns are not silently changed by Pack updates

12.02. OPEN:
      - exact field shapes and final schema details
      - exact adapter requirement declaration shape
      - exact fingerprint and content-identity field names
      - exact compatibility evidence retention shape
      - exact user-facing warning presentation
      - exact relationship between rolling profiles and Pack graph selection
