===============================================================================
DESIGN AREA DA-21 - RPC, CHANNELS, TRANSPORTS & MESSAGE FLOW
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines Turnix RPC as a transport-independent communication boundary, defines
RPC channels and transports, and separates logical message flow from concrete
wire schemas such as JSON envelopes and WebSocket frames.

This document owns abstract RPC semantics. Concrete message schema and
concrete WebSocket flow remain implementation specifications.

Purpose:
--------
This document defines the Turnix model for RPC communication between runtime
participants, execution adapters, frontend surfaces, tools, and
kernel-mediated execution paths.

It defines:
- RPC as a logical communication boundary
- RPC message-flow categories
- RPCChannel as the transport-neutral communication interface
- transport as an interchangeable carrier of RPC messages
- peer identity and connection context
- request, emit, subscribe, cancel, reply, error, and acknowledgement
  meaning
- routing boundaries for object and capability messages
- relationship between RPC and ExecutionAdapters
- separation between RPC transport lifecycle and Job lifecycle
- relationship between RPC requests and Job-backed work
- relationship between RPC messages and adapter-mediated work
- relationship between RPC messages and RuntimeHost operations
- transport timeout and disconnect semantics at the abstract level
- message correlation and RPC-domain trace obligations
- relation between DA-level RPC semantics and implementation specifications

It does NOT define:
- concrete JSON envelope fields (see IS-01)
- concrete WebSocket handshake and frame flow (see IS-02)
- trace event structure, trace DAG semantics, span mechanics, retention,
  pruning, loss, or trace storage semantics (see DA-03)
- payload identity, ValueRef, Chunk, retained value representation, decode,
  or integrity semantics (see DA-05)
- persistent-I/O authority, storage roots, Reader/Writer providers, backup,
  snapshot, or streaming I/O semantics (see DA-07)
- Window kind, Window ordering, finalized runtime history, or Window
  finalization semantics (see DA-08)
- capability permission semantics (see DA-16)
- user decision and remembered policy semantics (see DA-17)
- Job lifecycle, Job terminal outcomes, or Job result semantics (see DA-19)
- Application/ApplicationRun lifecycle or runtime identity semantics
  (see DA-20)
- execution adapter boundary semantics (see DA-23)
- OrchestrationUnit lifecycle or mutation-authority semantics (see DA-24)
- artifact, export, bundle, digest, partial export, missing-material, or
  offline inspection artifact semantics (see DA-25)
- comparison, Replay, Resume, Retry, or audit workflow semantics (see DA-26)
- adapter lifecycle, trust, isolation, failure, disconnect, or adapter-domain
  trace semantics (see DA-27)
- frontend UI layout or presentation behavior (see DA-22)
- RuntimeHost identity, workspace ownership, startup modes, entry surfaces,
  command-surface semantics, or host lifecycle semantics (see DA-28)
- PackManager catalog, graph-preparation, repair, write, or operation
  semantics (see DA-29)

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines RPC, channel, transport, routing, and abstract
      message-flow semantics within that shared interpretation model.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. RPC answers:

          "How do Turnix participants communicate across a boundary without
           confusing transport delivery, permission authority, execution
           lifecycle, and final work outcome?"

02.2. RPC is a logical communication boundary.

02.3. RPC is not a transport.

02.4. RPC is not WebSocket.

02.5. RPC is not JSON.

02.6. RPC is not capability authority by itself.

02.7. RPC is not adapter authority by itself.

02.8. RPC is not RuntimeHost authority by itself.

02.9. RPC is not Job lifecycle by itself.

02.10. RPC is not OrchestrationUnit lifecycle by itself.

02.11. RPC is not artifact, export, comparison, Replay, Resume, Retry, or
       audit workflow authority by itself.

02.12. A transport carries RPC messages.

02.13. A channel provides the transport-neutral interface through which RPC
       messages are received and sent.

02.14. Message delivery, message acknowledgement, request acceptance,
       handler execution, Job creation, OrchestrationUnit creation,
       adapter-mediated work, RuntimeHost operation acceptance, Window
       finalization, artifact/export operation, workflow operation, and
       final outcome are distinct concepts.

02.15. Turnix does not treat successful message delivery as successful work
       completion.

02.16. Turnix does not treat transport failure as Job failure.

02.17. Adapter-executed code may communicate through RPC-shaped boundaries
       under DA-23.

02.18. RPC carries adapter-originated or adapter-targeted messages without
       making the transport or channel an authority owner.

02.19. RuntimeHost entry surfaces and command surfaces may use RPC to
       communicate with Kernel-mediated runtime paths.

02.20. RPC use by a RuntimeHost entry surface does not make RPC the
       RuntimeHost authority owner.

02.21. RuntimeHost entry-surface, command-surface, startup-mode, workspace
       ownership, and host lifecycle semantics remain owned by DA-28.

02.22. Trace-visible RPC flow means an RPC-domain trace emission obligation
       where applicable.

02.23. Trace retention, trace pruning, trace loss, and trace storage
       semantics remain governed by DA-03.

02.24. RPC outcome wording does not define Job outcome, ApplicationRun
       outcome, OrchestrationUnit outcome, Window finalization, artifact
       export, retained-result authority, comparison, Replay, Resume,
       Retry, or audit workflow outcome.


===============================================================================
03. RPC, CHANNEL, AND TRANSPORT TERMS
===============================================================================

03.1. RPC means the logical request, reply, event, subscription,
      cancellation, and error flow between Turnix participants.

03.2. RPCChannel is the transport-neutral interface consumed by the RPC host
      or equivalent runtime owner.

03.3. Transport is the concrete carrier that moves bytes, text, frames,
      streams, or messages.

03.4. Example transports may include:
      - WebSocket
      - local in-process channel
      - testing channel
      - future inter-process communication transport
      - future stdio transport

03.5. A transport may disconnect.

03.6. A channel may become unavailable.

03.7. RPC semantics remain defined independently of any one transport.

03.8. Transport-specific framing, handshake, encoding, buffering, and
      reconnection rules belong to implementation specifications.

03.9. A transport adapter translates concrete transport events into
      RPCChannel events.

03.10. A transport adapter does not gain authority merely because it carries
       RPC messages.

03.11. A transport adapter does not smuggle transport-specific authority,
       fallback, or policy into RPC semantics.

03.12. A transport adapter is distinct from an ExecutionAdapter under
       DA-23, even when one implementation object performs both roles.

03.13. A transport adapter is distinct from a RuntimeHost entry surface under
       DA-28, even when one implementation object participates in both roles.


===============================================================================
04. RPC MESSAGE CATEGORIES
===============================================================================

04.1. RPC message categories include:
      - control messages
      - request messages
      - emit messages
      - reply messages
      - error messages
      - subscription messages
      - cancellation messages
      - state or update messages
      - acknowledgement messages

04.2. Control messages establish or maintain communication state.

04.3. Request messages ask for a correlated result, acceptance, or error.

04.4. Emit messages report or trigger one-way behavior where no final result
      is expected by the caller.

04.5. Reply messages carry successful immediate results or accepted-work
      responses according to operation contract.

04.6. Error messages carry structured failure information.

04.7. Subscription messages establish continuing delivery of updates.

04.8. Cancellation messages request cancellation or withdrawal of interest.

04.9. State or update messages carry state snapshots, state deltas, progress
      updates, or other subscribed update material according to operation
      contract.

04.10. Acknowledgement messages confirm message receipt or transport-level
       handling only.

04.11. Acknowledgement does not imply request success.

04.12. Acknowledgement does not imply capability execution.

04.13. Acknowledgement does not imply adapter execution.

04.14. Acknowledgement does not imply Job creation.

04.15. Acknowledgement does not imply Job success.

04.16. Acknowledgement does not imply OrchestrationUnit creation.

04.17. Acknowledgement does not imply RuntimeHost operation completion.

04.18. Acknowledgement does not imply artifact/export operation completion.

04.19. Acknowledgement does not imply comparison, Replay, Resume, Retry, or
       audit workflow completion.

04.20. Concrete message type names and concrete field layout belong to
       IS-01 or another implementation specification.


===============================================================================
05. ROUTING MODEL
===============================================================================

05.1. RPC routing identifies the logical target of a message.

05.2. RPC routes may target:
      - objects
      - capabilities
      - adapter-facing endpoints
      - control endpoints
      - subscription endpoints
      - artifact or retained-result endpoints
      - workflow endpoints
      - PackManager-facing endpoints

05.3. RPC routing does not grant permission.

05.4. RPC routing does not activate packs.

05.5. RPC routing does not select or authorize an execution adapter.

05.6. RPC routing does not bypass capability mediation.

05.7. RPC routing does not grant RuntimeHost authority.

05.8. RPC routing does not grant workspace ownership.

05.9. RPC routing does not accept a RuntimeHost command by itself.

05.10. RPC routing does not create an ApplicationRun by itself.

05.11. RPC routing does not create an OrchestrationUnit by itself.

05.12. RPC routing does not finalize a Window.

05.13. RPC routing does not define artifact/export authority.

05.14. RPC routing does not define ComparisonResult, Replay, Resume, Retry,
       or audit workflow authority.

05.15. A capability-routed RPC message remains subject to DA-16.

05.16. An adapter-facing RPC message remains subject to DA-23 and DA-27 as
       appropriate.

05.17. A RuntimeHost control-surface RPC message remains subject to DA-28.

05.18. A PackManager-facing RPC message remains subject to DA-29.

05.19. If routing fails before capability execution, adapter execution,
       RuntimeHost command acceptance, Job creation, OrchestrationUnit
       creation, artifact/export-owned work acceptance, or workflow-owned
       work acceptance, the failure remains an RPC routing or dispatch
       failure rather than an owning-domain terminal outcome.

05.20. If routing succeeds and a capability accepts Job-backed work, later
       Job lifecycle semantics are owned by DA-19.

05.21. If routing succeeds and an operation creates an OrchestrationUnit,
       later OrchestrationUnit lifecycle and mutation-authority semantics are
       owned by DA-24.

05.22. If routing succeeds and a request is accepted for artifact/export-owned
       work, later artifact/export semantics are owned by DA-25.

05.23. If routing succeeds and a request is accepted for workflow-owned work,
       later comparison, Replay, Resume, Retry, or audit workflow semantics
       are owned by DA-26.


===============================================================================
06. REQUEST, ACCEPTANCE, AND JOB-BACKED WORK
===============================================================================

06.1. An RPC request may end in:
      - immediate reply
      - structured error
      - accepted Job-backed work
      - accepted OrchestrationUnit-backed work
      - accepted adapter-mediated work
      - accepted RuntimeHost operation
      - accepted communication request for artifact/export-owned work
      - accepted communication request for workflow-owned work
      - rejected-before-domain-object outcome

06.2. Request acceptance means the request crossed the RPC dispatch boundary
      and was accepted by the target operation.

06.3. Request acceptance is not final operation success unless the operation
      contract explicitly defines successful acceptance as the result.

06.4. A request accepted as Job-backed work creates or exposes Job lifecycle
      correlation.

06.5. A request accepted as OrchestrationUnit-backed work creates or exposes
      OrchestrationUnit lifecycle correlation.

06.6. A request accepted as adapter-mediated work may create or expose
      adapter lifecycle correlation.

06.7. A request accepted as RuntimeHost operation may create or expose
      runtime-host operation correlation.

06.8. A request accepted for artifact/export-owned work may create or expose
      artifact/export communication correlation.

06.9. A request accepted for workflow-owned work may create or expose
      workflow communication correlation.

06.10. ExecutionAdapter boundary semantics remain owned by DA-23.

06.11. Adapter lifecycle, failure, disconnect, and lifecycle classification
       semantics remain owned by DA-27.

06.12. RuntimeHost operation, command-surface, and entry-surface semantics
       remain owned by DA-28.

06.13. Once Job-backed work exists, DA-19 owns Job lifecycle semantics.

06.14. Once OrchestrationUnit-backed work exists, DA-24 owns
       OrchestrationUnit lifecycle and mutation-authority semantics.

06.15. Once artifact/export-owned work exists, DA-25 owns artifact/export
       semantics.

06.16. Once workflow-owned work exists, DA-26 owns comparison, Replay,
       Resume, Retry, and audit workflow semantics.

06.17. A request rejected before Job-backed work exists does not produce a
       Job terminal outcome.

06.18. A request rejected before OrchestrationUnit-backed work exists does
       not produce an OrchestrationUnit terminal outcome.

06.19. A request rejected before adapter-mediated work exists does not
       produce adapter lifecycle or failure outcome unless DA-23, DA-27, or
       adapter-owning documents classify that relationship explicitly.

06.20. A request rejected before RuntimeHost command acceptance does not
       produce RuntimeHost operation completion or failure unless DA-28
       classifies that relationship explicitly.

06.21. A request rejected before artifact/export-owned work exists does not
       produce artifact/export outcome unless DA-25 classifies that
       relationship explicitly.

06.22. A request rejected before workflow-owned work exists does not produce
       workflow outcome unless DA-26 classifies that relationship explicitly.

06.23. A request rejected before owning-domain work exists may still produce
       RPC trace evidence and a structured error envelope.

06.24. RPC request identity and jobId remain distinct.

06.25. RPC request identity and orchestrationUnitId remain distinct.

06.26. RPC request identity and adapter instance identity remain distinct.

06.27. RPC request identity and runtimeHostId remain distinct.

06.28. RPC request identity and RuntimeHost operation identity remain
       distinct.

06.29. RPC request identity and Window identity remain distinct.

06.30. RPC request identity and artifact/export identity remain distinct.

06.31. RPC request identity and workflow identity remain distinct.

06.32. RPC correlation may link request identity to jobId when a Job exists.

06.33. RPC correlation may link request identity to orchestrationUnitId when
       an OrchestrationUnit exists.

06.34. RPC correlation may link request identity to adapter identity when
       adapter-mediated work exists.

06.35. RPC correlation may link request identity to runtimeHostId and
       RuntimeHost operation identity when host-level work exists.

06.36. RPC correlation may link request identity to artifact/export identity
       when artifact/export-owned work exists.

06.37. RPC correlation may link request identity to workflow identity when
       workflow-owned work exists.

06.38. A request accepted as Job-backed work may return a Job handle,
       immediate accepted-work response, subscription relationship, or other
       operation-defined lifecycle surface.

06.39. A request accepted as OrchestrationUnit-backed work may return an
       operation-defined accepted-work response, subscription relationship,
       correlation identity, or other surface defined by the owning operation
       contract and constrained by DA-24.

06.40. A request accepted for artifact/export-owned work or workflow-owned
       work may return an operation-defined response, subscription
       relationship, correlation identity, or other communication surface
       constrained by the owning document.

06.41. The exact concrete envelope shape for Job-backed request acceptance
       remains owned by IS-01, IS-02, or a future implementation
       specification constrained by DA-19.

06.42. The exact concrete envelope shape for OrchestrationUnit-backed request
       acceptance remains owned by IS-01, IS-02, or a future implementation
       specification constrained by DA-24.

06.43. The exact concrete envelope shape for RuntimeHost-operation acceptance
       remains owned by IS-01, IS-02, or a future implementation
       specification constrained by DA-28.

06.44. The exact concrete envelope shape for communication requests accepted
       for artifact/export-owned work or workflow-owned work remains owned by
       IS-01, IS-02, or a future implementation specification constrained by
       DA-25 or DA-26.


===============================================================================
07. EMIT, SUBSCRIBE, AND UPDATE FLOW
===============================================================================

07.1. Emit flow represents one-way communication where the sender does not
      expect a final correlated result.

07.2. Emit flow may still be acknowledged at the transport or RPC handling
      level.

07.3. Emit acknowledgement does not imply that downstream work completed.

07.4. Subscribe flow establishes continuing delivery of updates until the
      subscription ends, fails, disconnects, or is cancelled.

07.5. Subscription delivery may carry state updates, event updates, Job
      progress, OrchestrationUnit progress, adapter lifecycle updates,
      RuntimeHost operation updates, artifact/export updates, retained-result
      retrieval updates, comparison updates, Replay updates, Resume updates,
      Retry updates, audit workflow updates, PackManager operation updates, or
      other operation-defined update material.

07.6. Subscription delivery does not by itself define Job lifecycle state.

07.7. Subscription delivery does not by itself define OrchestrationUnit
      lifecycle state.

07.8. Subscription delivery does not by itself define adapter lifecycle state
      unless it carries adapter-domain evidence owned by DA-27.

07.9. Subscription delivery does not by itself define RuntimeHost lifecycle or
      command outcome unless it carries RuntimeHost-domain evidence owned by
      DA-28.

07.10. Subscription delivery does not by itself define artifact/export
       authority, retained-result authority, comparison outcome, Replay
       outcome, Resume outcome, Retry outcome, or audit workflow outcome.

07.11. If subscription delivery reports Job progress or terminal outcome,
       the reported Job meaning remains owned by DA-19.

07.12. If subscription delivery reports OrchestrationUnit progress or terminal
       outcome, the reported OrchestrationUnit meaning remains owned by DA-24.

07.13. If subscription delivery reports adapter lifecycle state, the reported
       adapter meaning remains owned by DA-27.

07.14. If subscription delivery reports RuntimeHost lifecycle or operation
       state, the reported RuntimeHost meaning remains owned by DA-28.

07.15. If subscription delivery reports artifact/export state, the reported
       artifact/export meaning remains owned by DA-25.

07.16. If subscription delivery reports comparison, Replay, Resume, Retry, or
       audit workflow state, the reported workflow meaning remains owned by
       DA-26.

07.17. If subscription delivery reports PackManager operation state, the
       reported PackManager meaning remains owned by DA-29.

07.18. Unsubscribe withdraws interest in future subscription delivery.

07.19. Unsubscribe does not by itself cancel the underlying work unless the
       operation contract or policy explicitly connects unsubscribe to
       cancellation.


===============================================================================
08. TRANSPORT TIMEOUT, DISCONNECT, AND CANCELLATION
===============================================================================

08.1. Transport timeout is an RPC, channel, or transport concern.

08.2. Job timeout is a Job lifecycle concern.

08.3. OrchestrationUnit timeout is an OrchestrationUnit lifecycle concern.

08.4. Adapter timeout, if defined, is an adapter lifecycle concern.

08.5. RuntimeHost timeout, if defined, is a RuntimeHost lifecycle or operation
      concern under DA-28.

08.6. Workflow timeout, if defined, is a workflow concern under DA-26.

08.7. Transport timeout does not automatically transition a Job to TimedOut.

08.8. Transport timeout does not automatically transition an
      OrchestrationUnit to a terminal state.

08.9. Transport timeout does not automatically fail an adapter instance.

08.10. Transport timeout does not automatically fail a RuntimeHost.

08.11. Transport timeout does not automatically fail artifact/export work.

08.12. Transport timeout does not automatically fail comparison, Replay,
       Resume, Retry, or audit workflow work.

08.13. Job timeout does not mean the transport failed.

08.14. OrchestrationUnit timeout does not mean the transport failed.

08.15. Adapter failure does not mean the transport failed.

08.16. RuntimeHost failure does not mean the transport failed.

08.17. Workflow failure does not mean the transport failed.

08.18. Transport disconnect means the communication carrier became
       unavailable or closed.

08.19. Transport disconnect does not automatically cancel a Job.

08.20. Transport disconnect does not automatically supersede a Job.

08.21. Transport disconnect does not automatically discard a Job result.

08.22. Transport disconnect does not automatically cancel an
       OrchestrationUnit.

08.23. Transport disconnect does not automatically finalize a Window.

08.24. Transport disconnect does not automatically close or fail an
       ExecutionAdapter.

08.25. Transport disconnect does not automatically stop, fail, or close a
       RuntimeHost.

08.26. Transport disconnect does not automatically fail artifact/export work.

08.27. Transport disconnect does not automatically fail comparison, Replay,
       Resume, Retry, or audit workflow work.

08.28. Transport disconnect does not automatically mutate committed state.

08.29. If accepted or in-flight work exists when transport disconnect occurs,
       policy may decide whether work continues, cancels, supersedes,
       detaches, retains result, or discards result.

08.30. DA-17 owns decision and policy handling.

08.31. DA-19 owns Job terminal outcomes when a policy outcome affects a Job.

08.32. DA-24 owns OrchestrationUnit terminal outcomes when a policy outcome
       affects an OrchestrationUnit.

08.33. DA-23 owns ExecutionAdapter boundary outcomes when a policy outcome
       affects execution-adapter boundary handling.

08.34. DA-27 owns adapter lifecycle outcomes when a policy outcome affects
       adapter execution or adapter lifecycle.

08.35. DA-28 owns RuntimeHost lifecycle or host-operation outcomes when a
       policy outcome affects RuntimeHost behavior.

08.36. DA-25 owns artifact/export outcomes when a policy outcome affects
       artifact/export work.

08.37. DA-26 owns comparison, Replay, Resume, Retry, or audit workflow
       outcomes when a policy outcome affects those workflows.

08.38. RPC cancellation messages are requests.

08.39. RPC cancellation messages do not directly kill arbitrary execution.

08.40. When cancellation targets Job-backed work, the cancellation request is
       translated into Job lifecycle handling under DA-19.

08.41. When cancellation targets OrchestrationUnit-backed work, the
       cancellation request is translated into OrchestrationUnit lifecycle
       handling under DA-24.

08.42. When cancellation targets adapter-mediated work, the cancellation
       request is translated into execution-adapter boundary handling under
       DA-23 and adapter lifecycle handling under DA-27.

08.43. When cancellation targets a RuntimeHost operation, the cancellation
       request is translated into RuntimeHost operation handling under DA-28
       and owning workflow documents.

08.44. When cancellation targets artifact/export work, the cancellation
       request is translated into artifact/export handling under DA-25.

08.45. When cancellation targets comparison, Replay, Resume, Retry, or audit
       workflow work, the cancellation request is translated into workflow
       handling under DA-26.

08.46. When cancellation targets a subscription, cancellation may withdraw
       delivery interest without ending the underlying work.

08.47. When cancellation targets transport-local pending work, cancellation
       may resolve or reject local waiting state without defining a Job,
       OrchestrationUnit, adapter, RuntimeHost, artifact/export, or workflow
       outcome.


===============================================================================
09. RPCCHANNEL CONTRACT
===============================================================================

09.1. RPCChannel is the abstract communication surface used by the RPC host
      or equivalent runtime owner.

09.2. RPCChannel exposes peer context.

09.3. RPCChannel exposes connection state.

09.4. RPCChannel receives incoming transport events.

09.5. RPCChannel sends outgoing RPC payloads through the active transport.

09.6. RPCChannel may report:
      - text payload
      - binary payload
      - disconnect
      - transport-specific event classified as other

09.7. RPCChannel does not define message schema.

09.8. RPCChannel does not define WebSocket behavior.

09.9. RPCChannel does not define Job semantics.

09.10. RPCChannel does not define OrchestrationUnit semantics.

09.11. RPCChannel does not define ExecutionAdapter boundary semantics.

09.12. RPCChannel does not define adapter lifecycle semantics.

09.13. RPCChannel does not define RuntimeHost lifecycle or command-surface
       semantics.

09.14. RPCChannel does not define Window finalization semantics.

09.15. RPCChannel does not define artifact/export semantics.

09.16. RPCChannel does not define comparison, Replay, Resume, Retry, or audit
       workflow semantics.

09.17. Concrete channel implementations adapt concrete transports into this
       abstract interface.

09.18. A channel implementation preserves peer identity and connection
       context when the transport provides them.

09.19. A channel implementation reports loss of connection explicitly.

09.20. A channel implementation does not silently transform disconnect into
       work cancellation.

09.21. A channel implementation does not silently transform disconnect into
       adapter failure.

09.22. A channel implementation does not silently transform disconnect into
       RuntimeHost stop, failure, or command cancellation.

09.23. A channel implementation does not silently transform disconnect into
       Window finalization, artifact/export failure, workflow failure, or
       committed-state mutation.

10. TRACE AND OBSERVABILITY
===============================================================================

10.1. RPC message flow remains trace-visible where trace evidence exists.

10.2. RPC trace evidence distinguishes:
      - message receipt
      - message acknowledgement
      - routing or dispatch
      - rejection before accepted work exists
      - request accepted as Job-backed work
      - request accepted as OrchestrationUnit-backed work
      - request accepted as adapter-mediated work
      - request accepted as RuntimeHost operation
      - request accepted for artifact/export-owned work
      - request accepted for workflow-owned work
      - reply sent
      - delivery failure
      - cancellation requested
      - transport timeout
      - generation or client-binding mismatch
      - channel disconnect
      - disconnect policy application
      - incomplete or malformed envelope rejection

10.3. RPC trace evidence records enough context, when available, to explain:
      - message identity
      - correlation identity
      - route
      - lane or logical stream
      - peer identity
      - channel identity
      - transport kind
      - runtimeHostId when applicable
      - RuntimeHost operation identity when applicable
      - applicationId when applicable
      - applicationRunId when applicable
      - orchestrationUnitId when applicable
      - adapter kind when applicable
      - adapter instance identity when applicable
      - capability identifier when applicable
      - jobId when applicable
      - Window identity when applicable
      - artifact/export identity when applicable
      - workflow identity when applicable
      - PackManager operation identity when applicable
      - timeout category when applicable
      - disconnect category when applicable

10.4. RPC-domain trace emission does not guarantee trace retention.

10.5. RPC-domain trace emission does not make RPC trace evidence committed
      state.

10.6. DA-03 defines the tracing substrate, trace structure, trace retention,
      trace pruning, trace loss, and trace storage semantics.

10.7. DA-16 owns capability-domain trace reasons.

10.8. DA-17 owns decision-domain trace reasons.

10.9. DA-19 owns Job-domain trace reasons.

10.10. DA-20 owns Application/ApplicationRun-domain trace reasons.

10.11. DA-24 owns OrchestrationUnit-domain trace reasons.

10.12. DA-25 owns artifact/export trace obligations where artifact/export
       work occurs.

10.13. DA-26 owns comparison, Replay, Resume, Retry, and audit workflow trace
       obligations where those workflows occur.

10.14. DA-27 owns adapter-domain trace reasons.

10.15. DA-28 owns RuntimeHost-domain trace reasons.

10.16. DA-29 owns PackManager-domain trace reasons.

10.17. IS-02 owns concrete WebSocket RPC transport trace reasons unless this
       document later promotes those reason identifiers into the abstract RPC
       domain.

10.18. RPC observability does not replace trace evidence owned by capability,
       decision, Job, Application/ApplicationRun, OrchestrationUnit, adapter,
       RuntimeHost, Window, artifact/export, workflow, PackManager, or
       committed-state documents.

10.19. RPC observability preserves causal links between RPC messages and
       higher-domain events when those events exist.


===============================================================================
11. RETAINED RESULTS, ARTIFACTS, AND WORKFLOW MESSAGES
===============================================================================

11.1. RPC may carry, route, acknowledge, subscribe to, or deliver messages
      related to retained results.

11.2. RPC may carry, route, acknowledge, subscribe to, or deliver messages
      related to Window artifacts, exports, bundles, digests, or offline
      inspection artifacts.

11.3. RPC may carry, route, acknowledge, subscribe to, or deliver messages
      related to comparison, Replay, Resume, Retry, or audit workflows.

11.4. Carrying, acknowledging, routing, subscribing to, or delivering those
      messages does not define retained-result meaning.

11.5. Carrying, acknowledging, routing, subscribing to, or delivering those
      messages does not define artifact/export authority.

11.6. Carrying, acknowledging, routing, subscribing to, or delivering those
      messages does not define ComparisonResult, Replay outcome, Resume
      outcome, Retry outcome, or audit workflow outcome.

11.7. DA-19 owns Job result semantics.

11.8. DA-25 owns artifact/export semantics.

11.9. DA-26 owns comparison, Replay, Resume, Retry, and audit workflow
      semantics.

11.10. DA-05 owns retained value representation.

11.11. DA-07 owns persistent-I/O authority.

11.12. This document may define or constrain the RPC flow used to request or
       deliver a retained result.

11.13. This document does not define whether retained material is
       authoritative state, artifact material, Job result material, Replay
       material, Resume material, Retry material, or workflow material.


===============================================================================
12. RELATION TO IMPLEMENTATION SPECIFICATIONS
===============================================================================

12.1. IS-01 defines the concrete RPC message envelope schema.

12.2. IS-02 defines the concrete WebSocket RPC flow.

12.3. IS documents may define:
       - concrete field names
       - JSON representation
       - WebSocket frame flow
       - handshake sequence
       - serialization checks
       - concrete transport reason identifiers
       - concrete adapter metadata fields when constrained by DA-23 and DA-27
       - concrete RuntimeHost metadata fields when constrained by DA-28
       - concrete OrchestrationUnit metadata fields when constrained by DA-24
       - concrete artifact or workflow metadata fields when constrained by
         DA-25 or DA-26

12.4. IS documents do not redefine:
       - RPC as a logical boundary
       - channel and transport separation
       - capability authority
       - adapter authority
       - RuntimeHost authority boundaries
       - Job lifecycle
       - OrchestrationUnit lifecycle
       - artifact/export authority
       - comparison, Replay, Resume, Retry, or audit workflow semantics
       - decision and policy semantics

12.5. If an IS document needs a semantic rule not defined here, the DA is
      updated first or alongside the IS document.

12.6. A future non-WebSocket transport specification remains constrained by
      this document.

12.7. A future RPC schema revision remains constrained by this document.

12.8. A future adapter transport specification remains constrained by this
      document, DA-23, and DA-27.

12.9. A future RuntimeHost control-surface or LAN-client transport
      specification remains constrained by this document and DA-28.

===============================================================================
14. LOCKED SUMMARY
===============================================================================

14.1. LOCKED:
      - RPC is a logical communication boundary, not a transport
      - transport carries RPC messages but does not define RPC semantics
      - RPCChannel is the transport-neutral interface
      - WebSocket is one concrete transport, not the RPC model itself
      - JSON envelope shape belongs to IS-01
      - concrete WebSocket flow belongs to IS-02
      - acknowledgement means transport or message handling, not work
        success
      - acknowledgement does not imply request success, capability execution,
        adapter execution, Job creation, Job success, RuntimeHost operation
        completion, or downstream domain outcome
      - request acceptance is distinct from final result
      - request accepted as Job-backed work is distinct from Job success
      - request accepted as adapter-mediated work is distinct from adapter
        success
      - request accepted as RuntimeHost operation is distinct from
        RuntimeHost operation success
      - carried, routed, acknowledged, subscribed, or delivered domain messages
        do not make RPC the owner of the carried domain outcome
      - rejected-before-domain-object RPC failures do not produce owning-domain
        terminal outcomes by themselves
      - emit acknowledgement does not imply downstream work completion
      - subscription delivery is not domain truth
      - unsubscribe does not by itself cancel underlying work
      - transport timeout is a communication concern, not Job timeout, adapter
        timeout, RuntimeHost timeout, or downstream domain timeout
      - transport disconnect is a communication concern, not Job cancellation,
        adapter failure, RuntimeHost stop or failure, or downstream domain
        failure
      - RPC cancellation is a request, not direct execution kill
      - capability-routed RPC remains capability-mediated under DA-16
      - adapter-facing RPC remains adapter-mediated under DA-23 and DA-27
      - RuntimeHost control-surface RPC remains constrained by DA-28
      - Job lifecycle remains owned by DA-19
      - ExecutionAdapter boundary semantics remain owned by DA-23
      - adapter lifecycle semantics remain owned by DA-27
      - RuntimeHost lifecycle and command-surface semantics remain owned by
        DA-28
      - policy handling remains owned by DA-17
      - other carried or reportable domain outcomes remain owned by their
        subject documents
      - RPC trace evidence preserves correlation across message and
        owning-domain identities where available
      - RPC trace evidence does not replace owning-domain trace evidence
      - trace retention and trace loss remain owned by DA-03

14.2. OPEN:
      - trace reason ownership refinement
      - transport implementation expansion
      - subscription, retained-result retrieval, RuntimeHost metadata,
        OrchestrationUnit metadata, artifact/export metadata, workflow
        metadata, and adapter metadata details
