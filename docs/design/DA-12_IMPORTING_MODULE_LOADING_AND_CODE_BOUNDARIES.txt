===============================================================================
DESIGN AREA DA-12 - IMPORTING, MODULE LOADING & CODE BOUNDARIES
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines how code is referenced, loaded, and made available across supported
languages, and where strict boundaries exist between resolution, importing,
module loading, adapter selection, execution authorization, activation-plan
preparation, activation, and execution.

This area is intentionally strict.

Importing is not resolution.
Importing is not activation.
Importing is not dependency declaration.
Importing is not activation-plan preparation.
Importing is not adapter execution authority.
Importing does not imply permission to execute.

Purpose:
--------
This document defines how Turnix prevents native language import systems and
module-loading mechanisms from bypassing Turnix semantics such as Pack
resolution, visibility, SaveBundle/Application scoping, adapter selection,
execution authorization, activation-plan preparation, activation order, and
execution authority.

It defines:
- language-level import boundaries
- Pack-local private module boundaries
- Turnix-mediated cross-Pack code access mechanisms
- JavaScript turnixImport selector rules and loading behavior
- dependency consistency requirements during imports
- the distinction between module loading and activation participation
- the distinction between activation entries, private implementation modules,
  and exported module surfaces
- the separation between module evaluation and Turnix-recognized execution
- relationship between importing and ExecutionAdapter boundaries
- relationship between importing and activation-plan boundaries
- Python Pack-code import limits under the adapter model

It does NOT define:
- generic resolution semantics (see DA-11)
- dependency semantics and solver behavior (see DA-13)
- complete activation lifecycle, phase barriers, cyclic activation,
  registration publication, final Activated state, or activation failure
  semantics (see DA-14)
- capability schemas, capability permission, Service internals, or permission
  prompting details (see DA-16)
- user decision and remembered policy handling (see DA-17)
- ExecutionAdapter runtime semantics (see DA-23)
- adapter lifecycle, trust, or traceability semantics (see DA-27)
- PackManager graph-preparation or activation-plan preparation semantics
  (see DA-29)
- ModCallContext facade shape, absent surfaces, or invocation lifetime
  semantics (see DA-30)
- concrete served artifact URLs, cache strategy, bundling strategy,
  TypeScript artifact naming, or RPC field layout

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines importing, module-loading, and code-boundary rules
      within that shared interpretation model.

01.5. "Activation entry" is the canonical lifecycle-participation term used by
      this document.

01.6. "Adapter entry" is not a separate platform concept in this document.

01.7. When "adapter entry" appears informally, it means the activation entry
      for one declared adapter/runtime participation.

01.8. "Pack entry" is not a canonical lifecycle term in this document.

01.9. "Mechanical loading" means loading or evaluating a requested artifact,
      module, or activation entry through an applicable adapter or loader
      path.

01.10. Mechanical loading does not imply graph preparation, activation-plan
       preparation, dependency readiness, cyclic activation admission, or final
       Activated state.


===============================================================================
02. CANONICAL TERMS AND OWNERSHIP BOUNDARIES
===============================================================================

02.1. This document uses canonical architecture type names when those names
      are needed to state import and module-loading boundaries.

02.2. ModCallContext is the invocation-scoped, Pack-facing gateway through
      which adapter-executed Pack code interacts with Turnix.

02.3. DA-30 owns ModCallContext facade shape, absent surfaces, and
      invocation-scoped lifetime semantics.

02.4. DA-12 names ModCallContext only to prevent native imports or module
      loading from becoming a gateway bypass.

02.5. ApplicationRun is one live execution period of an Application.

02.6. Application is the durable application identity.

02.7. SaveBundle is the durable persistence closure of an Application.

02.8. ExecutionAdapter is the adapter boundary that loads or runs external or
      adapter-mediated Pack code.

02.9. DA-23 and DA-27 own concrete ExecutionAdapter semantics and adapter
      lifecycle boundaries.

02.10. DA-14 owns activation lifecycle semantics.

02.11. DA-16 owns capability and Service semantics.

02.12. DA-29 owns PackManager graph-preparation and activation-plan
       preparation semantics.

02.13. Importing and module loading do not grant Kernel authority.

02.14. Importing and module loading do not grant ModCallContext gateway
       authority.

02.15. Importing and module loading do not grant PackManager authority.

02.16. Importing and module loading do not grant activation authority.

02.17. Importing and module loading do not grant capability permission.


===============================================================================
03. CORE PROBLEM STATEMENT
===============================================================================

03.1. Native language import systems do not understand Turnix Pack resolution,
      visibility, SaveBundle/Application scoping, adapter selection, execution
      authorization, activation-plan boundaries, activation boundaries, or
      execution authority.

03.2. Turnix therefore does not allow arbitrary language-native importing
      across Packs.

03.3. Cross-Pack code access routes only through Turnix-defined mechanisms.

03.4. Native imports remain allowed only for:
      - language internals
      - Pack-local private implementation modules under adapter-supported
        local language rules
      - explicitly allowed Turnix platform surfaces where such access is part
        of the supported execution model

03.5. A Pack-local native import remains inside the importing Pack's local
      module boundary.

03.6. A child directory containing another Pack manifest starts another Pack
      boundary.

03.7. The parent Pack's private module space stops at the child Pack boundary.

03.8. Native language behavior does not override Pack visibility, dependency,
      activation-plan, activation, adapter, permission, or policy boundaries.

03.9. Same host language does not imply same authority.

03.10. Python Pack code remains adapter-executed Pack code.

03.11. Python Pack code does not become backend implementation code through
       Python import behavior.

03.12. A native import succeeding does not prove Turnix graph readiness.

03.13. A native import succeeding does not prove activation readiness.

04.19. Importing is not committed-state mutation.

04.20. Importing is not persistent I/O outcome.

04.23. Module loading is not activation-plan preparation.

04.24. Module loading is not dependency ordering.

04.25. Module loading is not activation ordering.

04.26. Module loading is not cyclic activation group admission.

04.27. Resolution answers which Pack identity satisfies a request.

04.28. PackManager graph preparation answers which selected graph and
       activation plan Turnix will attempt to use.

04.29. Adapter selection answers which adapter kind or concrete adapter
       provider is eligible for a declared executable artifact.

04.30. Execution authorization answers whether a declared executable artifact
       may be loaded or executed in the current Pack, ApplicationRun,
       SaveBundle/Application context, adapter, policy, and trust context.

04.31. Importing answers how a permitted code artifact is obtained and made
       available.

04.32. Activation answers when Turnix intentionally brings a Pack into
       recognized executable participation.

04.33. Execution authority answers whether code may perform meaningful
       Turnix-recognized work.

04.34. Capability permission answers whether a capability invocation is
       allowed under the capability, policy, and decision model.

04.35. If imported code later participates in another domain, that domain
       defines the resulting domain outcome.

04.36. This document keeps these boundaries explicit because native language
       import systems would otherwise collapse them into one accidental path.


===============================================================================
05. EXECUTABLE PACK MATERIAL ROLES
===============================================================================

05.1. Executable Pack material has three distinct module-loading roles.

05.2. An activation entry is declared executable Pack material loaded by
      Turnix through one ExecutionAdapter for lifecycle participation defined
      by DA-14.

05.3. A private implementation module is loaded by Pack code as ordinary
      implementation material owned by the same Pack.

05.4. A private implementation module is not externally addressable through
      Turnix by default.

05.5. A private implementation module does not participate in Pack lifecycle
      merely because it exists.

05.6. A private implementation module does not participate in Pack lifecycle
      merely because Pack code imports it.

05.7. An exported module surface is publicly addressable only through an
      explicitly supported mediated module-loading mechanism.

05.8. An exported module surface is loaded on demand.

05.9. An exported module surface does not receive lifecycle callbacks merely
      because it is exported.

05.10. Turnix does not automatically treat every code file as an activation
       entry.

05.11. Turnix does not automatically call lifecycle hooks on every code file
       found in a directory.

05.12. A plural module mapping used for mediated imports is not an automatic
       preload list.

05.13. Loading a module may execute host-runtime top-level code.

05.14. Preloading executable files is therefore behavior, not metadata.

05.15. Importing a private implementation module does not make that module an
       activation entry.

05.16. Importing an exported module surface does not make that surface an
       activation entry.

05.17. Loading an activation entry and loading a private implementation module
       are distinct acts even when the same adapter can load both.

05.18. Module role is not inferred from filename alone.

06. NATIVE LANGUAGE IMPORT BOUNDARY
===============================================================================

06.1. Native language imports remain local mechanisms.

06.2. Native language imports do not resolve Pack selectors.

06.3. Native language imports do not inspect Turnix visibility.

06.4. Native language imports do not choose resolved dependency identity.

06.5. Native language imports do not choose ExecutionAdapters.

06.6. Native language imports do not authorize execution.

06.7. Native language imports do not prepare activation plans.

06.8. Native language imports do not activate Packs.

06.9. Native language imports do not grant capability permission.

06.10. Native language imports do not grant access to trusted backend
       internals.

06.11. Native language imports do not establish dependency readiness.

06.12. Native language imports do not establish activation readiness.

06.13. Native language imports do not admit cyclic activation groups.

06.14. Native language imports do not prove activation-plan correctness.

06.15. Cross-Pack native imports are unsupported unless a later document
       explicitly defines a mediated cross-Pack native import mechanism.

06.16. Physical possibility in a host language does not create a Turnix
       guarantee.

06.17. Physical possibility in a host language does not grant Kernel
       authority.

06.18. Physical possibility in a host language does not make direct backend
       access a supported contract.


===============================================================================
07. PYTHON IMPORT RULES
===============================================================================

07.1. Python Pack code may use native Python imports for language internals.

07.2. Python Pack code may use native Python imports for Pack-local private
      implementation modules under the supported local module rules of the
      Python ExecutionAdapter.

07.3. Python Pack code may use explicitly allowed Turnix platform-surface
      imports when such imports are part of a supported adapter-facing
      execution model.

07.4. Local Python imports include examples such as:
      - from .llamacpp_client import LlamaCppClient
      - from .config import loadConfig

07.5. Explicitly allowed Turnix platform-surface imports include only the
      whitelisted supported surface.

07.6. Explicitly allowed Turnix platform-surface imports do not include raw
      backend internals merely because the Pack code is Python.

07.7. Cross-Pack native Python imports are not allowed.

07.8. Disallowed examples include:
      - from ui.controls import Button
      - from Turnix.ui.controls import Button
      - from first_party.mods.foo import bar
      - from backend.core.kernel import Kernel
      - from backend.persistence.io import IoManager

07.9. Python import machinery has no awareness of Pack resolution.

07.10. Python import machinery has no awareness of visibility.

07.11. Python import machinery has no awareness of SaveBundle/Application
       scoping.

07.12. Python import machinery has no awareness of adapter selection.

07.13. Python import machinery has no awareness of execution authorization.

07.14. Python import machinery has no awareness of activation-plan boundaries.

07.15. Python import machinery has no awareness of activation boundaries.

07.16. Python import machinery has no awareness of capability permission.

07.17. Allowing native cross-Pack Python imports would bypass Turnix
       guarantees.

07.18. Allowing Python Pack code to import backend internals as authority would
       bypass the ExecutionAdapter boundary.

07.19. Python import success does not establish dependency readiness.

07.20. Python import success does not establish activation readiness.

07.21. Python import success does not establish activation-plan correctness.


===============================================================================
08. PYTHON CROSS-PACK ACCESS
===============================================================================

08.1. Python Pack code interacts with other Packs only through
      Turnix-mediated surfaces.

08.2. Cross-Pack execution goes through Capabilities where the owning
      documents expose capability invocation.

08.3. Python Pack code may use metadata or identity queries where the owning
      documents expose those queries.

08.4. Python Pack code may use activation-control requests where the owning
      documents expose those requests.

08.5. Python Pack code may use ModCallContext-mediated surfaces explicitly
      exposed by DA-30 and the owning domain documents.

08.6. Internal runtime Services may back capability implementations or other
      runtime wiring.

08.7. Ordinary Pack code does not receive raw Service objects as a cross-Pack
      interaction shortcut.

08.8. There is no Python equivalent of turnixImport as a cross-Pack native
      symbol or executable-code import mechanism.

08.9. Python code does not receive executable code objects or symbols from
      other Packs through native import bypass.

08.10. Python Pack code may still receive Turnix-created context, capability,
       metadata, and activation-control surfaces when those surfaces are
       granted by the owning documents.

08.11. In-process Python access remains mediated by DA-23, DA-14, DA-16, and
       DA-30.

08.12. In-process Python access does not become backend authority merely
       because it uses function calls instead of network transport.

08.13. In-process Python access does not become PackManager graph-preparation
       authority.

08.14. In-process Python access does not become activation-plan preparation.


===============================================================================
09. JAVASCRIPT IMPORT MODEL
===============================================================================

09.1. Browser-side JavaScript Pack code does not assume Node.js runtime
      behavior.

09.2. Browser-side JavaScript Pack code does not receive filesystem access.

09.3. Browser-side JavaScript Pack code does not receive per-Pack native
      import maps as a cross-Pack loading path.

09.4. Browser-side JavaScript Pack code does not use native cross-Pack imports.

09.5. Dynamic cross-Pack JavaScript loading routes through:
      turnixImport(selector)

09.6. turnixImport is a Turnix-defined mediated loader.

09.7. turnixImport is not equivalent to native import().

09.8. Browser-side JavaScript code remains adapter-executed frontend code under
      DA-23 and DA-22.

09.9. Browser-side JavaScript module loading does not prepare activation
      plans.

09.10. Browser-side JavaScript module loading does not establish dependency
       readiness.


===============================================================================
10. TURNIXIMPORT - WHAT IT IS
===============================================================================

10.1. turnixImport(selector: string) is:
      - a Turnix-aware resolver front-end
      - a controlled loader
      - a mediated ESM importer

10.2. turnixImport behavior includes:
      - parsing a Turnix selector
      - asking Turnix to resolve Pack identity and load target
      - applying visibility and policy checks through owning domains
      - fetching the permitted JavaScript artifact
      - performing dynamic ESM import of that permitted artifact

10.3. turnixImport does not create a second independent resolution system.

10.4. turnixImport depends on Turnix resolution and boundary checks already
      defined elsewhere.

10.5. turnixImport participates in adapter loading semantics.

10.6. turnixImport does not become activation or execution authorization by
      itself.

10.7. turnixImport does not become activation-plan preparation by itself.

10.8. turnixImport does not become dependency ordering by itself.

10.9. turnixImport does not become activation ordering by itself.

10.10. turnixImport does not become cyclic activation group admission by
       itself.


===============================================================================
11. TURNIXIMPORT - WHAT IT IS NOT
===============================================================================

11.1. turnixImport is not:
      - a dependency declaration
      - an adapter selection request
      - an execution authorization request
      - an activation-plan preparation request
      - an activation request
      - a capability permission request
      - a visibility override
      - a permissive or best-effort loader
      - a version selector
      - a filesystem lookup
      - a URI loader
      - a lifecycle callback trigger
      - a registration publication mechanism
      - a cyclic activation group admission mechanism

11.2. If importing fails, the failure is explicit.

11.3. turnixImport does not silently guess or broaden the requested target.

11.4. turnixImport does not grant Kernel authority to imported module code.

11.5. turnixImport does not grant ModCallContext gateway authority to imported
      module code.

11.6. turnixImport does not prove activation-plan correctness.

11.7. turnixImport does not prove dependency readiness.

11.8. turnixImport does not prove activation readiness.


===============================================================================
12. TURNIXIMPORT SELECTOR FORMS
===============================================================================

12.1. A turnixImport selector is not:
      - a filesystem path
      - a URI
      - a semver-qualified reference

12.2. A turnixImport selector is an identity-based Turnix selector within the
      importing rules of this document.

12.3. Supported conceptual forms are:

      A) Explicitly exposed Turnix platform module
         "core/rpc.js"
         "core/layout.js"

      B) Pack default exported module surface
         "ui.controls"

      C) Pack sub-entry or exported module surface
         "ui.controls/Button"

12.4. Pack default exported module selectors require the corresponding
      declared dependency relationship already to exist where dependency rules
      require it.

12.5. Pack sub-entry selectors resolve against declared JavaScript exported
      module mappings rather than filesystem guessing.

12.6. Disallowed selector forms include:
      - "../"
      - absolute paths
      - filesystem guessing
      - semver in selector
      - author mismatch against the already-resolved dependency identity


===============================================================================
13. DEPENDENCY CONSISTENCY DURING IMPORT
===============================================================================

13.1. Importing respects the concrete identity already chosen during
      dependency resolution.

13.2. If a Pack declares a dependency that resolves to one concrete Pack
      identity, importing remains consistent with that chosen identity.

13.3. Allowed imports refer to the already-resolved identity.

13.4. Disallowed imports include attempts to:
      - switch author identity
      - restate semver in the selector
      - bypass the already-resolved dependency choice

13.5. Example:

      If a Pack declares dependency:
          "packs": ["Turnix@ui.controls@^1.2"]

      Allowed imports:
          turnixImport("ui.controls")
          turnixImport("ui.controls/Button")

      Disallowed imports:
          turnixImport("Other@ui.controls")
          turnixImport("ui.controls@2.0")

13.6. Violations are hard errors.

13.7. Importing does not reopen dependency resolution.

13.8. Importing does not prove that the dependency is Activated.

13.9. Importing does not prove that dependency-provided runtime surfaces are
      available.

13.10. Importing does not repair a missing or invalid dependency relationship.

13.11. Importing does not convert an advisory relationship into a dependency.


===============================================================================
14. SEMVER IN IMPORTS
===============================================================================

14.1. Semver is not allowed in turnixImport selectors.

14.2. Semver belongs to:
      - manifests
      - dependency resolution
      - policy decisions

14.3. Importing is identity-based rather than version-selection-based.


===============================================================================
15. FILE MATCHING RULES
===============================================================================

15.1. For sub-entry imports such as:
      turnixImport("ui.controls/Button")

      Turnix resolves against declared JavaScript exported module mappings.

15.2. Matching logic uses exact declared mapping identity.

15.3. If an owning manifest rule defines extension matching for an exported
      JavaScript module surface, that rule applies before artifact serving.

15.4. Ambiguous matches are errors.

15.5. Missing matches are errors.

15.6. There is no fallback from sub-entry import to default exported module
      surface.

15.7. There is no filesystem guessing.

15.8. File matching does not infer activation-entry status.

15.9. File matching does not infer lifecycle participation.

15.10. File matching does not infer dependency readiness.


===============================================================================
16. DEFAULT EXPORTED MODULE SURFACE BEHAVIOR
===============================================================================

16.1. If a selector has no sub-path, Turnix loads the declared default
      JavaScript exported module surface for that Pack.

16.1.1. Example:
          turnixImport("ui.controls")

16.2. The Pack declares which JavaScript module surface is the default import
      surface.

16.3. That declared module surface is loaded.

16.4. Module exports are then returned.

16.5. There is no implicit index.js, filename guessing, or directory guessing.

16.6. The default exported module surface is not an activation entry merely
      because turnixImport can load it.

16.7. The default exported module surface is not Activated merely because
      turnixImport can load it.

16.8. The default exported module surface does not become lifecycle authority
      merely because turnixImport can load it.


===============================================================================
17. IMPORTING VS ACTIVATION PLAN
===============================================================================

17.1. Activation-plan preparation is owned by DA-29.

17.2. An activation plan is selected graph intent refined for activation order
      and activation readiness.

17.3. Importing does not prepare selected pack graphs.

17.4. Importing does not prepare activation plans.

17.5. Importing does not decide dependency order.

17.6. Importing does not decide activation order.

17.7. Importing does not admit cyclic activation groups.

17.8. Importing does not reject cyclic activation groups.

17.9. Importing does not prove activation-plan correctness.

17.10. Importing does not repair activation-plan defects.

17.11. Importing does not replace PackManager diagnostics.

17.12. Import failure is import-domain evidence.

17.13. Activation-plan failure is graph-preparation or activation-domain
       evidence according to the owning failure context.

17.14. Importing preserves the boundary between code access and graph intent.


===============================================================================
18. IMPORTING VS ACTIVATION
===============================================================================

18.1. turnixImport loads a permitted JavaScript module and may trigger normal
      ESM evaluation by the JavaScript runtime.

18.2. That ESM module evaluation is not Turnix-recognized activation.

18.3. Loading or evaluating a module through turnixImport does not make the
      imported module an activation entry.

18.4. Loading or evaluating a module through turnixImport does not call
      lifecycle callbacks.

18.5. Loading or evaluating a module through turnixImport does not create
      final Activated state.

18.6. Loading or evaluating a module through turnixImport does not publish
      registrations.

18.7. turnixImport does not:
      - activate the Pack
      - grant execution authority
      - grant capability permission
      - imply lifecycle participation

18.8. Activation remains a separate Turnix-controlled action handled through
      DA-14-owned activation mechanisms.

18.9. If an exported module surface needs Pack lifecycle setup, the owning
      Pack's activation lifecycle establishes that setup through DA-14-owned
      semantics.

18.10. Module evaluation that occurs merely because the JavaScript runtime
       evaluated an imported module is not treated as Turnix-recognized Pack
       execution by itself.

18.11. Adapter loading or module evaluation is not activation under DA-23 and
       DA-14.

18.12. DA-12 does not define the complete activation-entry protocol.

18.13. DA-12 refers to declared activation entries only to distinguish them
       from private implementation modules, exported module surfaces, and
       modules loaded by turnixImport.

18.14. Importing does not establish that a dependency has completed Phase 1.

18.15. Importing does not establish that a dependency has completed Phase 2.

18.16. Importing does not establish that a dependency has completed Phase 3.

18.17. Importing does not establish that a dependency is Activated.

18.18. Importing does not make an intra-cycle surface available for cyclic
       activation.


===============================================================================
19. RESOLVEPACK VS ENSUREACTIVATED
===============================================================================

19.1. resolvePack(selector) resolves metadata only.

19.2. resolvePack(selector) performs visibility checks.

19.3. resolvePack(selector) does not load code.

19.4. resolvePack(selector) does not select an adapter for execution.

19.5. resolvePack(selector) does not authorize execution.

19.6. resolvePack(selector) does not prepare activation plans.

19.7. resolvePack(selector) does not activate a Pack.

19.8. ensureActivated(selector) requests or ensures Pack activation through the
      activation domain.

19.9. ensureActivated(selector) may trigger activation when activation rules
      allow it.

19.10. ensureActivated(selector) does not return exports or symbols.

19.11. ensureActivated(selector) may return activation diagnostics or a
       structured activation failure.

19.12. Activation-control failure indicates orchestration or activation
       failure rather than native import failure.

19.13. Activation-control failure surfaces to the user or caller according to
       the owning failure-surfacing rules.

19.14. ensureActivated(selector) may consume an accepted activation plan when
       the owning activation documents define that path.

19.15. ensureActivated(selector) does not prepare a replacement activation plan
       by itself.


===============================================================================
20. IMMEDIATE EXECUTION AND SIDE EFFECTS
===============================================================================

20.1. Some languages permit immediate execution constructs such as:
      - module-level statements
      - IIFE-style patterns
      - top-level side effects

20.2. Turnix does not coordinate, track, or rely on immediate execution as an
      importing guarantee.

20.3. Immediate execution is discouraged in Pack code.

20.4. Import-time execution is not an activation mechanism.

20.5. Importing a module does not imply permission to execute meaningful
      Turnix-recognized logic.

20.6. Code that executes immediately:
      - runs outside Turnix orchestration
      - runs without ModCallContext gateway authority
      - is outside Turnix guarantees
      - is not considered activated even if it appears to work

20.7. Meaningful Turnix-recognized execution waits for a supported DA-14-owned
      activation or orchestration path.

20.8. Adapter execution that occurs outside Turnix-recognized activation or
      orchestration remains unsupported by Turnix guarantees.

20.9. Import-time execution does not establish dependency readiness.

20.10. Import-time execution does not establish activation readiness.

20.11. Import-time execution does not repair activation-plan ordering.

20.12. Import-time execution does not admit cyclic activation groups.


===============================================================================
21. BACKGROUND WORK GUARANTEE
===============================================================================

21.1. Turnix does not guarantee behavior for background work started outside
      Turnix orchestration.

21.2. Only work triggered by supported Turnix-defined activation or
      orchestration pathways is supported by Turnix guarantees.

21.3. Such pathways may include:
      - activation lifecycle callbacks defined by DA-14
      - capability calls defined by DA-16
      - other Turnix-defined orchestrated execution pathways

21.4. Background work started otherwise:
      - may execute
      - remains unsupported
      - remains untracked
      - is not abortable by Turnix guarantees
      - is not cleaned up by Turnix guarantees

21.5. Adapter implementation details do not convert unsupported background
      work into supported Turnix execution.

21.6. Background work does not become supported merely because a module import
      started it.

21.7. Background work does not make the originating Pack Activated.


===============================================================================
22. ERROR PHILOSOPHY
===============================================================================

22.1. Import errors are hard errors.

22.2. Importing implies certainty.

22.3. Permissive loading creates nondeterminism.

22.4. Failures remain visible and explainable.

22.5. Import-related errors use a structured Turnix failure surface.

22.6. Import-related errors include requesting Pack identity when available.

22.7. Import-related errors include target identity when available.

22.8. Import-related errors include reason classification when available.

22.9. Import-related errors do not become capability permission failures merely
      because later execution might have used capabilities.

22.10. Import-related errors do not become Job terminal outcomes merely
       because later execution might have used Jobs.

22.11. Import-related errors do not become activation-plan failures merely
       because activation later could have consumed an activation plan.

22.12. Import-related errors do not become activation failures merely because
       activation later could have run.

22.13. Exact error envelope fields belong to the owning implementation or
       interface specification.


===============================================================================
23. EXPLICITLY OPEN QUESTIONS
===============================================================================

23.1. OPEN questions include:
      - possible rename of turnixImport
      - whether turnixImport remains strictly internal to Turnix, with Pack
        code using mediated metadata or activation-control surfaces instead
      - tooling for authoring exported module mappings
      - documentation wording that avoids Python-import confusion
      - final manifest field names for JavaScript exported module surfaces
      - final served artifact URL structure and cache strategy
      - final TypeScript compilation and artifact naming rules
      - final dynamic import bundling strategy

23.2. Activation-plan schema and graph-preparation open questions are owned by
      DA-29.

23.3. Activation phase, barrier, and cyclic activation open questions are
      owned by DA-14.

23.4. ExecutionAdapter runtime and mechanical loading open questions are owned
      by DA-23 and DA-27.


===============================================================================
24. SUMMARY
===============================================================================

24.1. Native language imports do not bypass Turnix semantics.

24.2. Cross-Pack native imports are not supported.

24.3. Python Pack code is not backend implementation code.

24.4. Browser-side JavaScript cross-Pack loading routes through turnixImport.

24.5. turnixImport is mediated loading, not authority.

24.6. turnixImport selectors are identity-based, not path-based, URI-based, or
      version-selection-based.

24.7. Importing respects the already-resolved dependency identity.

24.8. File matching is exact and non-heuristic.

24.9. Ambiguous imports and missing imports are errors.

24.10. There is no implicit index.js, filename guessing, or directory
       guessing.

24.11. Importing and module loading are not activation.

24.12. Importing and module loading are not activation-plan preparation.

24.13. Importing and module loading do not establish dependency readiness.

24.14. Importing and module loading do not admit cyclic activation groups.

24.15. Module evaluation is not Turnix-recognized execution by itself.

24.16. Import-time side effects and unsupported background work remain outside
       Turnix guarantees.

24.17. Activation entries, private implementation modules, and exported module
       surfaces remain distinct roles.

24.18. Import errors are strict, visible, classified, and explainable.

24.19. DA-12 remains the importing, module-loading, and code-boundary document.
