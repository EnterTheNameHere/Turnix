===============================================================================
DESIGN AREA DA-10 - PACK IDENTITY, HIERARCHY & VISIBILITY
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines Pack identity layers, hierarchical relationships, and visibility
boundaries.

This area directly affects resolution, imports, activation ordering,
retained Pack material inside durable application persistence, and the mental
model for Pack authors.

Purpose:
--------
This document defines how Turnix identifies Packs, how Pack hierarchy is
formed, and how visibility is computed without conflating visibility with
resolution, activation, import authority, capability authority, or permission
authority.

It defines:
- Pack as the general container concept
- canonical terminology used by this document
- Pack identity layers
- hierarchical identity construction
- author and version identity treatment
- visibility declarations and computed visibility
- parent-import visibility rules
- separation between visibility and capability or service authority
- SaveBundle-local visibility constraints for retained or copied Pack material

It does NOT define:
- root discovery boundaries (see DA-09)
- resolution winner selection or source selection (see DA-11)
- importing, module loading, or native/runtime import authority (see DA-12)
- dependency-source policy or PackRequest interpretation (see DA-13)
- activation order or runtime lifecycle (see DA-14)
- visibility enforcement or access-control consequences (see DA-15)
- capability schema, permission prompts, or enforcement mechanics (see DA-16)
- Application or ApplicationRun lifecycle identity (see DA-20)
- PackManager inspection, graph preparation, repair, or UI behavior (see DA-29)
- SaveBundle storage format, recovery details, or graph evidence format
- Pack addressing syntax beyond identity and hierarchy concepts

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines Pack identity, hierarchy, and visibility within
      that shared interpretation model.

01.5. This document uses canonical architecture terminology.

01.6. Pack means the general container concept for Pack material.

01.7. SaveBundle means the durable persistence closure of one Application.

01.8. Application means one durable application individual.

01.9. ApplicationRun means one live execution period of one Application.

01.10. SaveBundle is not a Pack.

01.11. Application is not a Pack.

01.12. ApplicationRun is not a Pack.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. Pack is the general container concept in Turnix.

02.2. AppPack, ModPack, ViewPack, and ContentPack are Pack kinds.

02.3. Additional Pack kinds exist only when an owning document explicitly
      defines them.

02.4. A Pack root is identified by its Pack manifest.

02.5. Packs may contain Packs.

02.6. Pack hierarchy is a structural relationship between Pack containers
      rather than a statement about runtime activation order.

02.7. A SaveBundle may retain, copy, or physically contain Pack material.

02.8. Retained or copied Pack material inside a SaveBundle does not make the
      SaveBundle itself a Pack.

02.9. Identity answers:
      - what this Pack is
      - where it sits in the Pack hierarchy
      - which author scope it belongs to
      - which version identity applies

02.10. Visibility answers whether one Pack is eligible to be seen from
       another Pack context.

02.11. Visibility does not decide:
       - resolution winners
       - dependency satisfaction
       - activation order
       - native import authority
       - runtime import authority
       - capability authority
       - service access
       - permission grants
       - runtime execution order


===============================================================================
03. PACK IDENTITY MODEL
===============================================================================

03.1. Pack identity uses distinct identity layers.

03.2. These identity layers are not conflated.

03.3. The identity layers defined by this document are:
      - declaredId
      - packTreeId
      - author
      - version


03.4 declaredId
---------------

03.4.1. declaredId is the manifest-level local identifier.

03.4.2. declaredId comes from manifest field:
        id

03.4.3. declaredId rules:
        - string
        - no dots
        - no "@"
        - no embedded version
        - local to its parent Pack context

03.4.4. declaredId is not globally unique.

03.4.5. Examples:
        - ui
        - button
        - llamacpp


03.5 packTreeId
---------------

03.5.1. packTreeId is computed from Pack hierarchy.

03.5.2. packTreeId construction rule:
        - root Pack:
          packTreeId = declaredId
        - child Pack:
          packTreeId = parent.packTreeId + "." + declaredId

03.5.3. Examples:
        - ui
        - ui.controls
        - ui.controls.button
        - main-menu.ui
        - main-menu.ui.button

03.5.4. packTreeId properties:
        - case-sensitive
        - hierarchical
        - not filesystem-based
        - unique only within the relevant author and version scope

03.5.5. packTreeId is not an activation path.

03.5.6. packTreeId is not a filesystem path.

03.5.7. packTreeId is not a capability address.


03.6 Author identity
--------------------

03.6.1. declaredAuthor is the manifest-level author value or None.

03.6.2. author is the effective author identity.

03.6.3. author is computed as:
        - declaredAuthor
        - or inherited from parent

03.6.4. author is part of identity rather than decoration.

03.6.5. Turnix does not use an engine-defined fallback author identity as a
        normal Pack-identity outcome.

03.6.6. If author cannot be resolved through declaration or inheritance, the
        Pack is invalid.

03.6.7. Author resolution failure is explicit.

03.6.8. Author resolution failure is not repaired through silent
        substitution.

03.6.9. This rule preserves stable Pack identity, persistent ownership
        identity, and deterministic discoverability.


===============================================================================
04. VERSION IDENTITY
===============================================================================

04.1. declaredVersion is the raw manifest version value or None.

04.2. version is the parsed version identity used by later resolution.

04.3. Parsing occurs after discovery.

04.4. Invalid version syntax causes Pack rejection.

04.5. This document does not use "effectiveVersion" naming.

04.6. Version inheritance rules:
      - if version is missing, inherit from parent
      - if a root Pack has no version, use engine-defined default behavior

04.7. Version affects Pack identity and later resolution compatibility.

04.8. Version inheritance exists to keep Pack trees coherent unless an
      owning document explicitly defines a different rule.

04.9. This document does not define version compatibility policy.

04.10. This document does not define resolution winner selection.


===============================================================================
05. HIERARCHY AND CONTAINMENT
===============================================================================

05.1. Pack hierarchy is a containment relationship.

05.2. A child Pack belongs to the Pack tree of its parent.

05.3. Parent-child hierarchy contributes to packTreeId construction.

05.4. Parent-child hierarchy does not by itself grant:
      - visibility
      - capability authority
      - service access
      - activation
      - permission
      - runtime execution order

05.5. A Pack tree is structural first.

05.6. Later areas define runtime behavior over that structure.

05.7. A child directory containing another Pack manifest defines a child Pack
      root.

05.8. Pack-local module space stops at child Pack-root boundaries.

05.9. Physical nesting does not grant direct implementation access across
      Pack boundaries.

05.10. Cross-Pack access remains subject to visibility, explicit public
       surfaces, mediated resolution and loading, capability or service
       boundaries, adapter support, and policy boundaries where applicable.


===============================================================================
06. VISIBILITY MODEL
===============================================================================

06.1. Visibility answers whether a Pack is eligible to be seen from another
      Pack context.

06.2. Visibility is not the same as:
      - dependency declaration
      - dependency satisfaction
      - import use
      - activation order
      - capability authority
      - service access
      - permission grant
      - runtime execution order

06.3. Visibility is one input to later contextual behavior.

06.4. Visibility is not the later contextual behavior itself.


06.5 Local visibility
---------------------

06.5.1. Each Pack has local visibility:
        - public
        - private

06.5.2. Local visibility is declared explicitly or obtained from per-kind
        defaulting rules.

06.5.3. Current default rules are:
        - ContentPack -> public
        - AppPack -> private
        - ViewPack -> private
        - ModPack -> private

06.5.4. SaveBundle is not assigned ordinary Pack-kind local visibility
        because SaveBundle is not a Pack.

06.5.5. Local visibility is only one input to broader visibility outcome.


06.6 exportNestedPacks
----------------------

06.6.1. exportNestedPacks controls whether a Pack's direct children become
        externally visible beyond the local parent context.

06.6.2. Allowed forms:
        - false
        - true
        - list of declaredId values

06.6.3. Semantics:
        - false -> no direct children exported
        - true  -> all direct children exported
        - list  -> only listed direct children exported

06.6.4. List entries are direct-child declaredId values only.

06.6.5. Dotted hierarchical ids are not valid inside exportNestedPacks.

06.6.6. exportNestedPacks applies only to direct children.

06.6.7. exportNestedPacks does not define deep export semantics.


06.7 Computed global visibility
-------------------------------

06.7.1. Computed visibility is derived after hierarchy is known.

06.7.2. For a root Pack:
        globalVisibility = visibility

06.7.3. For a non-root Pack:
        - if visibility is private:
          globalVisibility = private
        - else if parent.exportNestedPacks is false:
          globalVisibility = private
        - else if parent.exportNestedPacks is true:
          globalVisibility = public
        - else if parent.exportNestedPacks is a list:
          globalVisibility = public if declaredId is listed
                             else private

06.7.4. Computed visibility is static relative to the discovered/indexed
        Pack tree.

06.7.5. Computed visibility is not runtime-loaded state.

06.7.6. Computed visibility is not a runtime resolution outcome.

06.7.7. DA-15 owns enforcement of visibility at use points.


===============================================================================
07. IMPORTPACKSFROMPARENT
===============================================================================

07.1. importPacksFromParent controls which parent-context Packs are
      import-visible to a child Pack.

07.2. importPacksFromParent does not imply:
      - export
      - capability inheritance
      - permission inheritance
      - native import authority
      - runtime import authority
      - activation authority
      - service access
      - capability invocation

07.3. The locked name is:
      importPacksFromParent


07.4 Allowed forms
------------------

07.4.1. Allowed forms:
        - false
        - true
        - list of declaredId values or relative packTreeId fragments

07.4.2. Semantics:
        - false -> no parent-context Packs imported
        - true  -> all visible parent-context Packs imported
        - list  -> explicit whitelist

07.4.3. Example:
        importPacksFromParent = ["ui.button", "service"]

07.4.4. Resolution of listed entries is relative to the immediate parent
        context and remains subject to visibility rules.

07.4.5. This document does not define native import behavior.

07.4.6. This document does not define turnixImport implementation behavior.


07.5 Default behavior
---------------------

07.5.1. Current defaults are:
        - ViewPack -> false
        - all other Pack kinds -> true

07.5.2. The rationale is:
        - views do not automatically inherit parent UI mods
        - view isolation is preserved
        - unintended UI contamination is reduced


===============================================================================
08. VISIBILITY VS RESOLUTION
===============================================================================

08.1. Visibility is static and computed from structure plus visibility
      declarations.

08.2. Resolution is contextual.

08.3. A Pack may exist but be invisible.

08.4. A visible Pack may still fail resolution.

08.5. Visibility is not dependency satisfaction.

08.6. This document defines eligibility to be seen.

08.7. This document does not define selection of a winner.

08.8. DA-09 owns discovery and discovered candidate production.

08.9. DA-11 owns resolution winner selection, source selection, selector
      resolution, and deterministic resolution semantics.

08.10. DA-13 owns dependency-source policy and PackRequest dependency
       interpretation.


===============================================================================
09. CAPABILITIES AND SERVICES ARE NOT VISIBILITY
===============================================================================

09.1. Capability exports are not inherited through visibility alone.

09.2. Capability imports remain explicit.

09.3. Parent visibility does not grant capability authority.

09.4. Parent visibility does not grant service access.

09.5. Visibility does not grant permission.

09.6. Capabilities and services are behavioral power.

09.7. DA-16 owns capability schema, permission prompts, enforcement
      mechanics, service access rules, and capability authority.

09.8. This separation prevents accidental privilege escalation through
      structural visibility alone.


===============================================================================
10. SAVEBUNDLE-LOCAL PACK MATERIAL VISIBILITY
===============================================================================

10.1. SaveBundle is not a Pack.

10.2. SaveBundle is not ordinary globally visible Pack material.

10.3. SaveBundle-local retained or copied Pack material remains local to the
      relevant SaveBundle/Application context unless an owning document
      explicitly exposes it.

10.4. SaveBundle-local retained or copied Pack material does not leak into
      global visibility merely because it exists inside a SaveBundle.

10.5. SaveBundle-local retained or copied Pack material may shadow or
      override external or global candidates only within the relevant
      SaveBundle/Application context.

10.6. Shadowing or override behavior for SaveBundle-local retained or copied
      Pack material follows DA-13 dependency-source and selected-graph rules.

10.7. Ordinary global content-root precedence does not override
      SaveBundle-local retained or copied Pack material by default.

10.8. Tooling or PackManager UI presentation of SaveBundle-local retained or
      copied Pack material does not grant global visibility.

10.9. Tooling or PackManager UI presentation of SaveBundle-local retained or
      copied Pack material does not grant runtime authority.

10.10. SaveBundle storage format, retained-material layout, copied-material
       layout, graph evidence, persistence compatibility, and recovery
       details are outside this document's authority.

OPEN:

10.11. Exact internal visibility rules for SaveBundle-local retained or
       copied Pack material remain open.

10.12. Interaction between exportNestedPacks and SaveBundle/Application
       context remains open.

10.13. Tooling and UI representation of SaveBundle-local visibility graphs
       remains open.


===============================================================================
11. ENFORCEMENT AND PRESENTATION BOUNDARIES
===============================================================================

11.1. DA-10 defines visibility meaning and computed visibility mechanics.

11.2. DA-15 owns visibility enforcement and access-control consequences.

11.3. DA-15 owns reference permission failure and source-domain isolation at
      use points.

11.4. DA-15 owns visibility as applied during dependency resolution,
      resolvePack, and turnixImport.

11.5. DA-10 does not define enforcement mechanics.

11.6. DA-10 does not define PermissionDeniedError taxonomy.

11.7. DA-10 does not define runtime reference-check behavior.

11.8. DA-10 does not define dependency-resolution failure behavior.

11.9. DA-29 owns PackManager inspection, UI presentation, graph preparation,
      repair, and PackManager-domain trace semantics.

11.10. PackManager presentation does not grant visibility authority.

11.11. PackManager presentation does not grant runtime authority.


===============================================================================
12. WHY THIS AREA IS HARD
===============================================================================

12.1. This area balances:
      - expressiveness
      - safety
      - predictability
      - creator intuition

12.2. Too much permissiveness creates chaos.

12.3. Too much strictness creates an unusable ecosystem.

12.4. The current design favors:
      - explicitness
      - deferred contextual checks where appropriate
      - structural clarity over static can-see matrices

13. SUMMARY
===============================================================================

LOCKED:

13.1. Pack is the general container concept.

13.2. AppPack, ModPack, ViewPack, and ContentPack are Pack kinds.

13.3. declaredId, packTreeId, author, and version remain distinct identity
      layers.

13.4. declaredId is local to its parent Pack context.

13.5. declaredId is not globally unique.

13.6. packTreeId is case-sensitive, hierarchical, and not filesystem-based.

13.7. packTreeId is unique only within the relevant author and version scope.

13.8. author must resolve through declaration or inheritance.

13.9. A Pack without resolvable author is invalid.

13.10. Author resolution failure is explicit.

13.11. Turnix does not use an engine-defined fallback author identity for
       normal Pack identity.

13.12. This document does not use "effectiveVersion" naming.

13.13. Hierarchy is containment, not authority.

13.14. Visibility is eligibility to be seen.

13.15. Visibility does not decide resolution, dependency satisfaction,
       activation, import authority, capability authority, service access,
       permission grants, or runtime execution order.

13.16. Local visibility values are public and private.

13.17. ContentPack defaults public.

13.18. AppPack, ViewPack, and ModPack default private.

13.19. SaveBundle is not a Pack.

13.20. SaveBundle is not assigned ordinary Pack-kind local visibility.

13.21. exportNestedPacks controls direct-child export only.

13.22. importPacksFromParent is import-visibility, not authority.

13.23. Capabilities and services are not inherited through visibility alone.

13.24. SaveBundle-local retained or copied Pack material does not leak into
       global visibility by default.

13.25. Ordinary global content-root precedence does not override
       SaveBundle-local retained or copied Pack material by default.

13.26. PackManager presentation does not grant global visibility or runtime
       authority.

OPEN:

13.27. Exact internal visibility rules for SaveBundle-local retained or
       copied Pack material remain open.

       remains open.
