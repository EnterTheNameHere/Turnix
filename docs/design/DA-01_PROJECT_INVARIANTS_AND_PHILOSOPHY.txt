===============================================================================
DESIGN AREA DA-01 - PROJECT INVARIANTS AND PHILOSOPHY
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Foundational principles that constrain all other Turnix design areas.

Changes here have cascading impact and remain rare, explicit, and reviewed.

Purpose:
--------
This document defines the project-level invariants and design philosophy that
guide Turnix architecture.

It defines:
- Turnix core identity
- platform truth
- the Core Truth Doctrine
- locked project invariants
- highest-level authority boundaries
- local-first philosophy
- design attitudes
- explicitly open philosophical questions

It does NOT define:
- concrete pack formats
- AppDefinition or AppPack schema
- Application or ApplicationRun lifecycle details
- SaveBundle storage layout
- pack discovery, identity, visibility, resolution, or activation mechanics
- importing or module-loading mechanics
- service, capability, permission, or policy schemas
- ModCallContext facade details
- transaction, commit, payload, configuration, or persistence mechanics
- RPC schemas or transport behavior
- View, frontend, debugger, or tooling implementation details
- artifact, export, comparison, Replay, Resume, Retry, or audit workflows
- concrete RuntimeHost, Workspace, command-surface, or LAN behavior

Upstream Documents:
-------------------
- CMR-01
- CMR-02
- CMR-03
- CMR-04
- CMR-05


===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines project-level invariants and design attitudes
      within that shared interpretation model.

01.5. Detailed subsystem documents may specialize behavior inside their own
      authority domains.

01.6. Detailed subsystem documents may not weaken the project-level
      invariants defined here.


===============================================================================
02. ROLE OF THIS DOCUMENT
===============================================================================

02.1. DA-01 is the project-level philosophy and invariant anchor.

02.2. DA-01 is not the full Turnix architecture specification.

02.3. DA-01 names high-level authority boundaries only where the boundary is
      needed to prevent later architectural drift.

02.4. DA-01 does not replace the design area that owns a detailed concept.

02.5. A later document may define the mechanism for a concept named here.

02.6. A later document may not convert a mechanism into project identity
      unless DA-01 is explicitly revised.

02.7. A later document may not use implementation convenience to bypass the
      invariants in this document.


===============================================================================
03. CORE IDENTITY
===============================================================================

03.1. Turnix is a standalone runtime platform.

03.2. Turnix provides controlled runtime authority, deterministic
      boundaries, persistent continuity, explicit orchestration, and
      explainable state transitions.

03.3. Turnix is not defined by:
      - one programming language
      - one frontend technology
      - one transport
      - one launch mode
      - one Pack layout
      - one model provider
      - one operating-system process shape
      - one browser tab
      - one application
      - one Workspace
      - one current implementation

03.4. Turnix is not:
      - a plugin loader
      - a dynamic script runner
      - a web app framework
      - a convenience-first modding system
      - a pack-only application launcher
      - a PackManager
      - a catalog system
      - a graph-preparation tool
      - a root-discovery system
      - a pack-discovery system
      - a storage backend
      - a configuration file format
      - a UI framework
      - a debugger
      - an export format
      - a Replay tool

03.5. Turnix is:
      - a runtime continuity engine
      - a deterministic resolver
      - a policy-driven orchestrator
      - an explainable system
      - a controlled execution boundary
      - a controlled state boundary

03.6. Modular Packs are first-class Turnix mechanisms for describing,
      distributing, composing, extending, and persisting runtime behavior.

03.7. Packs do not define the whole identity of Turnix.

03.8. AppDefinition and AppPack material may define or contribute to
      Application creation where the owning creation model says so.

03.9. AppDefinition and AppPack material is not Turnix platform identity.

03.10. Application binds durable application identity.

03.11. ApplicationRun binds one live execution period of an Application.

03.12. Durable save persistence stores accepted Application state and
       associated persistence material under SaveBundle and persistence-domain
       rules.

03.13. Application, ApplicationRun, AppDefinition, AppPack, and SaveBundle
       details are owned by their detailed documents.

03.14. This document does not decide that every possible ApplicationRun is
       backed by one AppDefinition or AppPack.


===============================================================================
04. PLATFORM TRUTH
===============================================================================

04.1. Turnix platform truth is contractual.

04.2. Platform truth is defined by:
      - contracts
      - guarantees
      - authority boundaries
      - orchestration semantics
      - continuity behavior
      - retained state semantics
      - explainability requirements

04.3. Platform truth is not defined by:
      - current source layout
      - backend language
      - frontend technology
      - adapter implementation
      - transport implementation
      - launcher implementation
      - command-line entry shape
      - browser behavior
      - operating-system process topology
      - local optimization
      - direct-call convenience

04.4. Implementation choices are pragmatic and may change.

04.5. Platform contracts and guarantees remain valid across implementation
      replacement.

04.6. A useful implementation path does not become an authority boundary merely
      because it works.

04.7. A first-party implementation surface does not become project identity
      merely because it is official.

04.8. A first-party tool does not become authority merely because it is useful.


===============================================================================
05. HIGHEST-LEVEL AUTHORITY BOUNDARIES
===============================================================================

05.1. Kernel owns runtime authority.

05.2. RuntimeHost exposes controlled entry surfaces and command surfaces.

05.3. RuntimeHost is not Kernel authority.

05.4. ExecutionAdapters run adapter-mediated Pack code.

05.5. ExecutionAdapters are not Kernel authority.

05.6. Transports carry messages.

05.7. Transport behavior does not define authority.

05.8. RPC is the logical communication boundary.

05.9. RPC is not the transport.

05.10. Capabilities define explicit mediated operations.

05.11. Capability access is not granted by visibility, import, service access,
       same-language execution, or same-process execution.

05.12. Memory owns authoritative state semantics.

05.13. Transaction owns staged mutation before commit.

05.14. Committed state becomes authoritative only through the owning committed
       state and transaction model.

05.15. Application owns durable application identity.

05.16. ApplicationRun owns one live execution period.

05.17. SaveBundle carries durable persistence material without becoming the
       semantic owner of every retained domain.

05.18. ModCallContext is the invocation-scoped Pack-bound gateway through
       which adapter-executed Pack code interacts with Turnix.

05.19. ModCallContext is not Kernel authority.

05.20. Pack code interacts with Turnix only through supported mediated
       surfaces.

05.21. Direct access to trusted backend internals is unsupported.

05.22. Same host language does not imply same authority.

05.23. Same operating-system process does not imply same authority.

05.24. Pack-provided code is not backend implementation code merely because it
       runs in the same language or process as backend implementation code.

05.25. Direct-call optimization may optimize dispatch.

05.26. Direct-call optimization does not bypass authority boundaries.

05.27. Runtime authority ordering is architectural, not implementation-specific.

05.28. CLI, browser frontend, launcher surfaces, LAN clients, FastAPI,
       WebSocket, browser JavaScript, Python, local sockets, subprocesses,
       containers, or other implementation vehicles do not redefine this
       ordering.


===============================================================================
06. CORE TRUTH DOCTRINE
===============================================================================

06.1. Turnix does not guarantee correctness.

06.2. Turnix guarantees:
      - reproducibility
      - reversibility
      - explicit uncertainty

06.3. Reproducibility means that Turnix-owned choices and state transitions
      remain deterministic for the same retained state, filesystem material,
      configuration, accepted graph, inputs, policies, and user decisions.

06.4. Reproducibility excludes silent substitution.

06.5. Reproducibility excludes implicit best-guess resolution.

06.6. Reproducibility does not mean that external systems become
      deterministic merely because Turnix calls them.

06.7. Reversibility means that state changes do not silently destroy prior
      valid states.

06.8. Reversibility means that accepted decisions and mutation boundaries
      remain explainable after the fact within retained evidence.

06.9. Reversibility does not require infinite retention.

06.10. Reversibility requires honest representation of retained gaps when
       retained material is incomplete.

06.11. Explicit uncertainty means that ambiguity is classified, surfaced, and
       explainable.

06.12. Explicit uncertainty means that Turnix does not pretend to know what it
       did not determine.

06.13. Silent assumptions, guesses, hidden defaults, and hidden fallbacks
       violate explicit uncertainty when they decide meaningful behavior.

06.14. Any mechanism that hides uncertainty, makes silent decisions, or
       prevents later explanation violates the Core Truth Doctrine.


===============================================================================
07. LOCKED INVARIANTS
===============================================================================

07.1. The principles in this section are LOCKED and apply across Turnix unless
      an explicit accepted revision changes them.

07.2. Determinism is preferred over convenience.

07.3. Given the same retained state, filesystem material, configuration,
      accepted graph, inputs, policies, and user decisions, Turnix makes the
      same Turnix-owned choices every time.

07.4. Turnix does not perform silent substitution.

07.5. Turnix does not perform implicit best-guess resolution.

07.6. If ambiguity exists, Turnix classifies it.

07.7. If ambiguity blocks safe progress, Turnix resolves it through policy or
      user decision.

07.8. A policy or user decision that resolves ambiguity is persisted when the
      owning policy or state model requires persistence.

07.9. Continuity is preferred over performance.

07.10. Persistence failures for identity-bearing or authoritative material are
       not cosmetic.

07.11. Partial writes to required authoritative state do not occur.

07.12. Quarantine is preferred over overwrite when state integrity is at risk.

07.13. Best-effort behavior is acceptable only for explicitly optional
       non-authoritative material.

07.14. Explicitly optional non-authoritative material may include:
       - diagnostic logs
       - verbose diagnostic traces
       - analytics
       - caches
       - previews

07.15. Domain-required trace emission is not optional merely because retained
       trace evidence is non-authoritative.

07.16. Explicitness is preferred over magic.

07.17. Hidden imports, invisible dependency resolution, and behavior that
       cannot be explained after the fact do not belong in Turnix.

07.18. If something works, Turnix can explain why within the owning evidence
       and retention boundaries.

07.19. If something fails, Turnix can explain why within the owning evidence
       and retention boundaries.

07.20. User-visible decisions are surfaced.

07.21. A decision that can reasonably surprise a user is surfaced.

07.22. Silent retries do not occur unless explicit policy governs them.

07.23. Silent fallbacks do not occur unless explicit policy governs them.

07.24. Platform truth is implementation-independent.

07.25. Backend language, frontend technology, adapter strategy, transport
       strategy, or other current implementation choices do not define Turnix
       platform truth.

07.26. Platform contracts and guarantees remain valid across implementation
       replacement.

07.27. No guarantees exist outside Turnix orchestration.

07.28. Mutation outside Turnix orchestration does not acquire Turnix guarantees
       by implication.

07.29. Work started outside Turnix entrypoints, RuntimeHost operations,
       OrchestrationUnits, Jobs, capability calls, timers, event delivery,
       processing hooks, lifecycle callbacks, or other mediated authority paths
       is not guaranteed by Turnix merely because it runs nearby.

07.30. This limitation applies to:
       - timers not registered through Turnix
       - background threads
       - ad-hoc async tasks
       - detached work
       - side-effect-only module execution
       - native host-language imports outside Turnix mediation
       - direct unsupported backend access

07.31. If Pack code starts such work anyway, the resulting consequences belong
       to the Pack author unless Turnix explicitly guaranteed otherwise.

07.32. Runtime authority ordering remains explicit.

07.33. RuntimeHost, ExecutionAdapters, transports, frontends, tooling
       surfaces, command surfaces, LAN clients, and host-language runtimes do
       not acquire Kernel authority through implementation proximity,
       deployment topology, or host-language convenience.

07.34. Official tooling is not authority by default.

07.35. PackManager can prepare and explain graph intent.

07.36. PackManager does not silently activate, import, load, execute, mutate
       SaveBundle state, mutate active ApplicationRun graph state, remember
       decisions, broaden policy, grant capability permission, or bypass
       Kernel-mediated operation paths.

07.37. UI, debugger tooling, persistence helpers, artifact export tools,
       comparison tools, Replay, Resume, Retry, and audit workflows do not
       acquire authority merely because they exist near the runtime.


===============================================================================
08. LOCAL-FIRST INVARIANT
===============================================================================

08.1. Turnix is local-first.

08.2. Local-first means user-controlled local infrastructure is the default
      authority environment.

08.3. Local-first does not mean same-machine-only.

08.4. Local-first does not require every ExecutionAdapter, frontend client,
      model provider, storage device, or presentation surface to run in one
      process or on one machine.

08.5. Local-first permits explicit remote, LAN, server, or multi-client
      participation when Turnix authority and user control remain intact.

08.6. Remote or LAN access does not imply remote state authority.

08.7. Remote or LAN access does not imply adapter execution authority.

08.8. Remote or LAN access does not imply persistence authority.

08.9. Turnix assumes:
      - local filesystem ownership
      - limited hardware
      - limited context window
      - explicit recovery surfaces
      - user-controlled authority boundaries

08.10. Server-scale patterns are rejected by default.

08.11. Rejected server-scale patterns include:
       - lazy global registries
       - infinite retries
       - implicit availability
       - silent federation
       - hidden remote authority
       - background repair without explicit policy

08.12. A later document may define explicit remote or LAN behavior.

08.13. A later remote or LAN model may not replace local-first as the baseline
       authority, persistence, failure, recovery, or ownership model unless
       DA-01 is explicitly revised.


===============================================================================
09. TRACE, EVIDENCE, AND COMMITTED TRUTH
===============================================================================

09.1. Trace is structured runtime evidence.

09.2. Trace is not committed state.

09.3. Trace is not merely diagnostic logging.

09.4. Trace answers what Turnix observed, caused, attempted, accepted,
      rejected, failed, or completed within retained evidence.

09.5. A domain-owning document may require trace emission for meaningful
      actions in that domain.

09.6. Required trace emission is an emission obligation.

09.7. Trace persistence and retention are policy-governed.

09.8. Retained trace evidence may be bounded, rotated, pruned, or lossy when
      loss is represented honestly.

09.9. Trace loss weakens evidential completeness.

09.10. Trace loss does not by itself change committed-state correctness.

09.11. Committed-state truth is governed by the authoritative commit model,
       not by trace completeness.

09.12. Retained trace evidence does not become as authoritative as committed
       state merely because it explains committed state.

09.13. If an action is absent from retained trace evidence, trace cannot prove
       that the action happened.

09.14. Absence from retained trace evidence does not by itself prove that the
       action did not happen.

09.15. DA-03 owns trace substrate, trace retention, trace loss, trace event
       structure, and span semantics.

09.16. DA-04 owns authoritative committed state, transactions, and commit
       boundaries.

===============================================================================

10.1. DA-01 may name core runtime domains at philosophy level.

10.2. DA-01 does not define detailed subsystem behavior.

10.3. Trace details are not owned by DA-01.

10.5. Payload identity, Chunk, ChunkId, ValueRef, decode, integrity, and

10.7. IoManager and persistent-I/O authority details are not owned by DA-01.

10.8. Window, SafePointWindow, ActiveWindow, AbortedWindow, and finalized

10.9. Window artifact, WindowExport, Minimal Audit Bundle, optional digest,

10.10. Comparison, ComparisonResult, Replay, Resume, Retry, and audit workflow

10.11. Root discovery, Pack discovery, Pack identity, hierarchy, visibility,

10.12. Service, Capability, Permission, decision, and remembered-policy details

10.13. Job lifecycle and terminal outcome details are not owned by DA-01.

10.14. Application, ApplicationRun, AppDefinition, AppPack backing, and runtime

10.15. RPC, channel, and transport details are not owned by DA-01.

10.16. UI, View, frontend runtime, and frontend presentation details are not

10.23. DA-01 does not duplicate their mechanisms.


===============================================================================
11. ADJUSTABLE DESIGN ATTITUDE
===============================================================================

11.1. The principles in this section are strong design preferences rather than
      locked invariants.

11.2. These preferences may evolve with experience when locked invariants
      remain preserved.

11.3. Explainability is preferred over elegance when the more elegant design
      weakens clarity, traceability, or diagnosis.

11.4. A slightly verbose system that can explain itself is preferred over a
      clever system that only appears to work.

11.5. Policy is preferred over blanket prohibition when policy preserves
      authority boundaries and makes the governing rule visible.

11.6. When practical, Turnix classifies behavior, gates it by policy, and keeps
      defaults conservative.

11.7. Tooling friendliness matters.

11.8. Design supports:
      - trace inspection
      - PackManager UI
      - conflict explanation
      - audit and explanation of retained decision evidence

11.9. These tooling-oriented expectations remain relevant even when the
      tooling itself is not implemented yet.

11.10. Developer ergonomics matter when ergonomics do not create hidden magic.

11.11. Stable conventions are allowed when they are documented, deterministic,
       inspectable, and non-ambiguous.

11.12. Conventions do not override explicit declarations.

11.13. Conventions do not silently merge conflicting authority sources.

11.14. Conservative defaults are preferred when a choice affects authority,
       persistence, visibility, execution, or user control.


===============================================================================
12. EXPLICITLY OPEN QUESTIONS
===============================================================================

12.1. The questions in this section are intentionally OPEN.

12.2. Pack autonomy remains OPEN.

12.3. Current OPEN questions include:
      - whether Packs may ever declare always-allow permissions
      - whether Packs may auto-activate toolchains
      - which trust scopes can be remembered safely

12.4. AI-assisted recovery remains OPEN.

12.5. Current OPEN questions include:
      - whether LLM-assisted error recovery may exist
      - at which lifecycle phase it may exist
      - whether it would be optional, policy-gated, or first-class
      - which domains may accept AI-assisted suggestions
      - which domains require deterministic non-AI recovery

12.6. The long-term strictness of local-first assumptions remains OPEN.

12.7. Current OPEN questions include:
      - remote assets
      - remote compilers
      - federated pack indexes
      - remote processors
      - remote RuntimeHost coordination
      - cross-runtime coordination

12.8. Application creation source strictness remains OPEN.

12.9. Current OPEN questions include:
      - final AppDefinition terminology
      - final AppPack backing requirements
      - synthetic application-definition rules
      - direct-local application-definition rules
      - test and script creation surfaces

12.10. These questions are currently out of scope.

12.11. These questions are not philosophically banned.

12.12. An open question does not authorize hidden behavior before the owning
       document defines it.


===============================================================================
13. WHY THIS AREA EXISTS
===============================================================================

13.1. This area exists to prevent later specifications from drifting into:
      - convenience-driven shortcuts
      - accidental server assumptions
      - silent failure tolerance
      - hidden authority transfer
      - implementation-defined platform truth
      - deferred "fix it later" logic

13.2. Without this area, later specifications are more likely to weaken
      determinism, continuity, explainability, local control, or orchestration
      truth in exchange for local convenience.

13.3. This document is the anchor that prevents that drift.

13.4. A later document may be more detailed than DA-01.

13.5. A later document may not use detail to erase the principles defined by
      DA-01.
