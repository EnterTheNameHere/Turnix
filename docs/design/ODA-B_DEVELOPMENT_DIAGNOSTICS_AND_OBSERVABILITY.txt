===============================================================================
OPTIONAL DESIGN AREA ODA-B - DEVELOPMENT, DIAGNOSTICS & OBSERVABILITY
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines optional developer-facing diagnostics, reporting, and observability
surfaces that consume Turnix trace evidence and related system evidence.

This area improves trust, explainability, and maintainability without
introducing new runtime correctness semantics.

Purpose:
--------
This document defines optional but strongly useful development,
diagnostics, and observability expectations for Turnix tooling.

It defines:
- observability principles for developer experience
- tooling expectations for trace viewing and reporting
- activation and resolution explanation expectations as surfaced in tooling
- adapter, RPC, capability, Application, and ApplicationRun diagnostics
- development-versus-production diagnostics behavior
- diagnostic snapshot expectations for bug reports and regression testing
- post-mortem and diagnostic re-run boundary expectations

It does NOT define:
- trace event schemas, trace reasons, or trace retention semantics
  (see DA-03)
- debugger semantics, pause rules, or mutation safety (see DA-18)
- authoritative state or transactions (see DA-04)
- window semantics (see DA-08)
- execution adapter semantics (see DA-23)
- RPC, channel, and transport semantics (see DA-21)
- Application or ApplicationRun lifecycle semantics (see DA-20)
- deterministic Replay, Resume, or Retry semantics (see DA-26)
- new runtime correctness guarantees or authority boundaries

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines optional development, diagnostics, and
      observability tooling expectations within that shared interpretation
      model.


===============================================================================
02. CORE PROBLEM
===============================================================================

02.1. Turnix is:
      - modular
      - dynamic
      - policy-driven
      - runtime-activated
      - adapter-mediated
      - partially user-governed

02.2. Without strong diagnostics, failures may become:
      - non-reproducible
      - misattributed
      - silently masked
      - explained away as "magic"

02.3. This area exists to improve:
      - explainability
      - inspectability
      - debuggability
      - reviewability

02.4. This area remains optional in tier, but it is strategically useful for
      development and operational trust.

02.5. Diagnostic tooling consumes trace evidence, retained system evidence,
      and authorized read-only views of relevant authoritative state where
      such access is available.

02.6. Diagnostic tooling does not become authority by presenting that
      material.


===============================================================================
03. OBSERVABILITY PRINCIPLE
===============================================================================

LOCKED:

03.1. Meaningful decisions remain explainable where the owning domain and
      retained evidence support explanation.

03.2. Meaningful decisions emit or retain enough structured evidence to be:
      - traceable where the owning domain requires trace emission
      - attributable where retained evidence identifies the acting source
      - reproducible only where retained evidence and workflow semantics
        support reproduction

03.3. If something happened, tooling attempts to answer:
      - what happened
      - why it happened
      - who or what decided it
      - what alternatives existed when such alternatives were part of the
        decision context

03.4. ODA-B does not define the trace model itself.

03.5. DA-03 defines the trace model.

03.6. ODA-B defines how tooling consumes trace evidence.

03.7. Tooling distinguishes missing evidence from evidence of absence.

03.8. Tooling does not claim reproducibility from missing, pruned, dropped,
      corrupt, partial, or non-retained evidence.


===============================================================================
04. TRACE SYSTEM FOUNDATION
===============================================================================

LOCKED:

04.1. Turnix uses the structured tracing system defined in DA-03.

04.2. This document does not define:
      - trace event schemas
      - trace reason vocabularies
      - trace span rules
      - trace retention, pruning, or loss-evidence rules

04.3. This document defines:
      - developer-facing tooling expectations
      - diagnostics workflows and reports
      - optional user-interface surfaces that consume trace data
      - development-mode enhancements that do not change runtime behavior

04.4. Domain-specific trace reason ownership remains with the owning DA
      document.

04.5. ODA-B tooling does not turn trace evidence into committed state,
      persistence authority, Kernel authority, or runtime correctness.


===============================================================================
05. TRACE DOMAINS
===============================================================================

LOCKED:

05.1. Important trace domains may include:
      - discovery
      - indexing
      - resolution
      - activation
      - permissions
      - capabilities
      - io
      - persistence
      - Application and ApplicationRun lifecycle
      - RPC and transport flow
      - frontend UI and View lifecycle
      - execution adapter lifecycle
      - Job and OrchestrationUnit lifecycle
      - runtime errors

05.2. Trace domains are additive rather than exclusive.

05.3. ODA-B tooling does not invent trace-domain authority merely by showing
      a domain filter.

05.4. A displayed domain filter is a presentation and search aid.

05.5. A displayed domain filter is not an authority boundary by itself.


===============================================================================
06. TRACE VISIBILITY
===============================================================================

LOCKED:

06.1. Trace events remain recordable even when no user interface is present.

06.2. Retained trace evidence remains queryable later through structured
      access where the relevant retention policy preserved it.

06.3. Trace persistence remains policy-driven under DA-03.

06.4. ODA-B tooling treats trace evidence as potentially incomplete.

06.5. If trace evidence is incomplete because of pruning, dropping,
      corruption, non-retention, or partial export, tooling surfaces that
      incompleteness explicitly and does not guess.

06.6. Trace event levels and trace domains are defined by DA-03.

06.7. ODA-B tooling uses the DA-03 definitions rather than inventing new
      local ones.

06.8. Adapter, RPC, UI, Application, ApplicationRun, capability, Job, and
      OrchestrationUnit evidence may be correlated by tooling only where
      retained trace evidence supports that correlation.


===============================================================================
07. TRACE VIEWER
===============================================================================

07.1. A trace-viewer surface may exist to:
      - inspect trace DAGs and spans
      - filter by domain, reason, and scope identifiers
      - collapse or expand causal branches
      - jump to related entities such as packs, links, memory, Jobs,
        Applications, ApplicationRuns, Views, RPC messages, and adapter
        instances

07.2. The trace-viewer user interface is optional.

07.3. The trace data model and reason vocabulary remain defined by DA-03 and
      the owning domain documents.

07.4. Viewer rules:
      - the viewer does not fabricate reasons
      - the viewer does not fabricate causal links
      - if evidence incompleteness is declared under DA-03, the viewer
        surfaces that incompleteness explicitly
      - the viewer distinguishes transport, adapter, capability, Job, View,
        Application, and ApplicationRun outcomes where evidence supports
        those distinctions

07.5. The viewer does not make frontend presentation authoritative.

07.6. The viewer does not make retained non-authoritative evidence
      authoritative.


===============================================================================
08. PACK RESOLUTION EXPLANATIONS
===============================================================================

LOCKED:

08.1. When a pack is:
      - selected
      - rejected
      - overridden
      - downgraded

      the resolver trace remains sufficient, under DA-03 and DA-11, to
      explain:
      - candidate set
      - applied filters
      - scoring or ordering inputs
      - tie-breakers
      - final choice

08.2. This explanatory requirement is defined by DA-03 and DA-11 rather
      than by ODA-B.

08.3. ODA-B adds the following tooling expectations:
      - development tooling may provide "why not chosen" views when
        evidence is available
      - if available trace evidence is not sufficient to explain why a
        candidate was not chosen, tooling states that limitation explicitly
        and does not guess

08.4. Resolution explanations do not change resolver outcome.

08.5. Resolution explanations do not create alternate resolution semantics.


===============================================================================
09. CAPABILITY USAGE REPORTING
===============================================================================

LOCKED:

09.1. In development mode, Turnix may produce capability-usage reports.

09.2. Reports may be produced per:
      - KernelRunSpan
      - selected ApplicationRun span
      - selected window
      - selected adapter instance
      - selected RPC correlation
      - selected time range

09.3. Any such report is derived from retained trace evidence and registry
      state available to the reporting tool.

09.4. Reports distinguish:
      - not used
      from
      - not provable because of missing trace evidence

09.5. Adapter-originated capability reports do not imply that the adapter
      owned capability authority.

09.6. Capability reports do not grant capability permission.

09.7. Capability reports do not redefine service access, capability access,
      or permission outcome semantics.


===============================================================================
10. ACTIVATION ORDER DIAGNOSTICS
===============================================================================

LOCKED:

10.1. Tooling may explain:
      - activation order
      - why pack X ran before pack Y
      - why reordering was impossible
      - where user intervention occurred
      - which adapter participated in activation when applicable
      - which lifecycle phase or barrier was relevant when evidence exists

10.2. These explanations remain trace-backed as defined by DA-03 and
      constrained by DA-14.

10.3. Reordering failures remain visible.

10.4. If evidence is incomplete, tooling surfaces that incompleteness
      explicitly.

10.5. Adapter loading or readiness is not presented as activation unless
      activation evidence supports that conclusion.

10.6. Activation diagnostics do not define activation ordering.

10.7. Activation diagnostics do not retry, repair, or reinterpret dependency
      cycles by themselves.


===============================================================================
11. RUNTIME SAFETY WARNINGS
===============================================================================

11.1. Optional diagnostics may warn about patterns such as:
      - background tasks outside Turnix orchestration
      - timers outside Turnix-controlled scheduling
      - untracked async loops
      - direct filesystem access attempts
      - native imports attempting to bypass code boundaries
      - in-process calls attempting to bypass capability mediation
      - frontend state presented as authoritative state

11.2. These are warnings rather than correctness errors unless an owning
      document explicitly classifies the situation otherwise.

11.3. Tooling warnings do not grant execution authorization, capability
      permission, or persistence authority.

11.4. Tooling warnings do not make the diagnostic subsystem responsible for
      enforcing every warned pattern.

11.5. A warning may identify a risk without proving that platform
      correctness was violated.


===============================================================================
12. DEVELOPMENT-MODE BEHAVIOR
===============================================================================

LOCKED:

12.1. In development mode:
      - warnings may be more verbose
      - unused declarations may be reported
      - trace verbosity may be higher
      - stricter diagnostics may be enabled

12.2. Development-mode enhancements do not change runtime correctness
      semantics.

12.2.1. Development-mode versus production-mode diagnostics do not weaken
        tracing requirements defined elsewhere.

12.2.2. If tracing is required by DA-03 or another authoritative document,
        that tracing remains required regardless of mode.

12.3. In production mode:
      - warnings are quieter
      - traces may still be recorded according to DA-03 policy
      - user-facing diagnostic noise is reduced

12.4. Development-mode adapter diagnostics do not weaken adapter authority
      boundaries.

12.5. Production-mode quietness does not convert missing evidence into
      evidence of absence.


===============================================================================
13. ERROR, WARNING, AND INFO LEVELS
===============================================================================

LOCKED:

13.1. ODA-B tooling may classify surfaced diagnostics using the levels:
      - ERROR
      - WARNING
      - INFO

13.2. In ODA-B tooling, ERROR is used for presentation of:
      - a blocking failure
      - an owning-domain-classified correctness violation
      - a diagnostic condition mapped from owning-domain evidence

13.3. In ODA-B tooling, WARNING is used for presentation of a policy,
      hygiene, or diagnostics concern without the same blocking
      implication.

13.4. In ODA-B tooling, INFO is used for presentation of expected behavior
      or informational outcome.

13.5. ODA-B diagnostic levels classify how tooling presents evidence.

13.6. ODA-B diagnostic levels do not define the underlying domain outcome,
      authority violation, Job result, adapter failure, RPC failure, or
      committed-state correctness.

13.7. Correctness errors are not silently downgraded by tooling.

13.8. Tooling does not treat transport timeout, adapter failure, Job
      timeout, and ApplicationRun failure as interchangeable diagnostic
      categories.


===============================================================================
14. DIAGNOSTIC SNAPSHOTS
===============================================================================

14.1. Optional tooling may snapshot read-only diagnostic views or retained
      evidence for:
      - pack registry
      - dependency graph
      - activation state
      - Memory contexts and transaction layers
      - committed state views where authorized
      - Application identity evidence
      - ApplicationRun lifecycle evidence
      - SaveBundle generation evidence where relevant
      - View and frontend client evidence
      - adapter lifecycle evidence
      - RPC correlation evidence

14.2. Snapshot tooling may be used for:
      - bug reports
      - reproducibility work
      - regression testing

14.3. Snapshot tooling does not create new authority semantics by itself.

14.4. Snapshot tooling distinguishes authoritative state from
      non-authoritative evidence.

14.5. Snapshot packaging does not make staged, diagnostic, exported,
      retained, or presentation material authoritative.

14.6. Authoritative state remains authoritative only through the owning
      state and commit model.

14.7. A diagnostic snapshot is not a live process snapshot.

14.8. A diagnostic snapshot is not a SaveBundle generation unless the
      owning persistence and state documents define it as such.


===============================================================================
15. DIAGNOSTIC RE-RUN AND POST-MORTEM
===============================================================================

OPEN:

15.1. Future tooling may support:
      - diagnostic re-run using retained inputs and evidence
      - simulation using controlled inputs
      - inspecting divergence
      - comparing traces
      - post-mortem inspection of adapter, RPC, Application, and
        ApplicationRun correlation across a failure

15.2. This area remains OPEN and is not locked by this document.

15.3. Diagnostic re-run, simulation, comparison, and post-mortem inspection
      are not DA-26 Replay unless the workflow satisfies DA-26 Replay
      semantics.

15.4. Diagnostic re-run and simulation are new work.

15.5. Diagnostic re-run and simulation do not imply deterministic
      restoration, resumed work, re-run external effects, or authority over
      activation outcomes.

15.6. ODA-B does not define Replay, Resume, Retry, comparison, or retained
      artifact authority semantics.


===============================================================================
16. WHAT THIS AREA DOES NOT DO
===============================================================================

16.1. This area does not define:
      - automatic fixing
      - AI-driven debugging as a required feature
      - speculative corrections
      - hiding errors
      - trace schema authority
      - trace retention authority
      - committed-state authority
      - adapter authority
      - RPC authority
      - capability permission authority
      - persistence authority
      - Kernel authority
      - Application lifecycle authority
      - ApplicationRun lifecycle authority
      - Replay, Resume, or Retry authority

16.2. ODA-B diagnostics may reveal an issue.

16.3. ODA-B diagnostics do not own the domain rule that made the issue
      important.

16.4. ODA-B diagnostics may guide a human or tool toward a fix.

16.5. ODA-B diagnostics do not apply fixes unless another owning domain
      grants an explicit, mediated action path.


===============================================================================
17. SUMMARY
===============================================================================

LOCKED:

17.1. Observability remains a first-class development concern.

17.2. Tooling consumes DA-03 trace evidence without redefining it.

17.3. Domain-specific trace reason ownership remains with owning documents.

17.4. Retained evidence remains distinct from committed-state authority.

17.5. Resolver explanations remain trace-backed.

17.6. Capability-usage reporting distinguishes absence from missing proof.

17.7. Activation diagnostics remain trace-backed.

17.8. Adapter, RPC, Application, and ApplicationRun diagnostics consume
      evidence without creating authority.

17.9. Development and production diagnostics remain distinct.

17.10. Diagnostic levels classify presentation rather than owning domain
       outcomes.

17.11. Diagnostic snapshots do not create authority.

OPEN:

17.12. Trace-viewer UI remains optional.

17.13. Diagnostic snapshots remain optional.

17.14. Diagnostic re-run, simulation, comparison, and post-mortem tooling
       remain open.
