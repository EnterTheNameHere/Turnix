==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. Correct implementation-specification scope.

    IS-01 clearly states that it defines the concrete RPC message envelope,
    fields, helper construction expectations, serialization responsibilities,
    routing expectations, and completion-marker behavior.

    It also clearly says that it does not introduce new runtime authority,
    permission, policy, lifecycle, adapter, View, Job, or transport semantics.

2. Correct RPC / transport boundary.

    The document treats the schema as a concrete envelope usable by WebSocket,
    in-process, testing, or future transport implementations when they carry the
    same RPCMessage envelope.

    This preserves the higher DA boundary that RPC is the logical communication
    boundary while transport is only the carrier.

3. Good per-field authority stop-lines.

    The document repeatedly prevents field metadata from becoming authority:

        - id is distinct from runtime and lifecycle identities.
        - Route does not grant permission, activate packs, or authorize adapter
          execution.
        - lane selection does not grant permission or execution authority.
        - budgetMs does not define Job timeout unless explicitly mapped by a
          higher-level operation.
        - acknowledgement metadata confirms message receipt or transport-level
          handling only.
        - job metadata does not define Job lifecycle semantics.
        - idempotencyKey does not bypass permission, adapter authorization, or
          capability mediation.
        - origin metadata is correlation evidence only.
        - final is a series-level marker, not a single-envelope completion
          marker or Job terminal outcome.
        - payload content does not gain authority merely because the envelope is
          valid.

4. Good isComplete boundary.

    isComplete is correctly scoped as a top-level wire-envelope completion
    marker. The document correctly says it does not prove content correctness,
    does not replace parsing or schema validation, and does not imply capability
    permission, Job success, adapter readiness, Application readiness, or
    committed-state mutation.

5. Good helper-constructor model.

    The helper-constructor section usefully prevents ad-hoc envelope creation.
    It keeps completion marking, required fields, idempotency key copying,
    correlation preservation, lane inference, and serialization expectations in
    one place.

6. Good relation-to-higher-documents section.

    The final section explicitly says that routing, visibility, activation,
    capability, permission, decision-handling, runtime lifecycle, View lifecycle,
    execution adapter semantics, transport semantics, and Job lifecycle semantics
    remain governed by higher documents.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. AppInstance terminology is superseded by the current Application /
   ApplicationRun model.

    IS-01 still uses AppInstance in scope text, field descriptions, origin
    metadata, relation-to-higher-documents text, and isComplete stop-lines.

    Current source-stack correction:
        Proposal P02 replaces the older combined AppInstance layer with:

            Application
                durable application individual

            ApplicationRun
                one live execution period of that Application

            SaveBundle
                durable persistence closure of the Application

    Required consequence for IS-01:
        Replace AppInstance terminology with Application and/or ApplicationRun,
        depending on the field meaning.

        For RPC correlation metadata, the envelope should generally distinguish:

            applicationId
                durable Application identity, when available

            applicationRunId
                live run identity, when available

        Avoid treating one appInstanceId as the current universal runtime
        identity.

2. Session wording risks reintroducing a removed core concept.

    The Gen section says Gen is used to detect stale traffic from previous
    sessions and is embedded where session continuity validation is required.

    Current source-stack correction:
        Session is removed from the Turnix core model. RPC routing must not
        become Session-based.

    Required consequence for IS-01:
        Replace session wording with connection-generation or transport-
        continuity wording.

        Use wording such as:

            Gen wraps the connection generation assigned by the runtime side.

            Gen contains generation components used to detect stale traffic from
            previous connection generations.

            Gen is embedded in RPC envelopes where connection-generation
            continuity validation is required.

        Do not use Session, MainSession, HiddenSession, TemporarySession,
        SessionRegistry, or Session-based RPC routing terminology.

3. origin calling-context wording could be mistaken for retained
   ModCallContext.

    IS-01 says origin may include "calling context".

    Current source-stack correction:
        Proposal P02 replaces PackContext with ModCallContext. ModCallContext is
        invocation-scoped, Pack-bound, fresh per callback, and must not be
        retained after callback completion.

    Required consequence for IS-01:
        origin may carry serializable cause/correlation descriptors, but it must
        not carry or imply a live ModCallContext, PackContext, transaction,
        service object, raw backend object, or reusable authority context.

        Replace "calling context" with wording such as:

            cause/correlation descriptor
            invocation correlation identifiers
            serialized caller descriptor

        Add a compact stop-line:

            origin never carries a live ModCallContext and never preserves
            invocation authority across messages.

4. Route object wording is under-specified.

    Route points to either a capability or an object. The document already says
    route does not grant permission or authority, but "object" is still broad
    enough to be misread as a raw backend object, service object, application
    object, or direct object authority.

    Required consequence for IS-01:
        Keep object routing only if the rewritten document defines it as an RPC
        routing endpoint identity or handler target known to the routing layer.

        Add a compact stop-line:

            An object route is not raw backend-object access, Service-object
            access, filesystem access, committed-state authority, or capability
            permission by itself.

5. idempotencyKey wording risks blurring RPC deduplication with Retry semantics.

    IS-01 says retries using the same effective idempotencyKey are naturally
    deduplicated by the backend when that behavior is enabled.

    Current source-stack correction:
        Replay, Resume, and Retry semantics are owned by higher workflow
        documents. Retry is new work and does not reuse previous Job,
        OrchestrationUnit, adapter execution, or ProcessingRun identity unless a
        specific owner defines a narrower relationship.

    Required consequence for IS-01:
        Clarify that idempotencyKey deduplication is request/message handling
        behavior only.

        It is not DA-level Retry semantics, not replay, not resume, not Job
        identity reuse, not OrchestrationUnit identity reuse, and not
        ProcessingRun identity reuse.

6. cancel message semantics need one additional stop-line.

    IS-01 includes cancel as a message type and says correlatesTo may be used for
    cancels. The document already prevents type and metadata from defining Job
    outcomes, but cancel is common enough to deserve an explicit local guardrail.

    Required consequence for IS-01:
        Add a compact rule:

            A cancel message is a cancellation request or signal carried by RPC.
            It does not by itself make a Job Cancelled, abort an
            OrchestrationUnit, close an ApplicationRun, fail an ExecutionAdapter,
            or finalize runtime history.

7. stateUpdate payload wording should not imply committed-state mutation.

    IS-01 says stateUpdate carries state-update payload / state deltas. That is
    acceptable as wire-schema language, but the final document should not allow
    a reader to infer that receiving or routing stateUpdate mutates authoritative
    Application state.

    Required consequence for IS-01:
        Add a compact stop-line:

            stateUpdate is an RPC payload category. It does not mutate committed
            Application state, configuration, retained history, or SaveBundle
            material merely by being received or routed.

8. Backend/frontend wording should remain concrete implementation shape, not
   platform identity.

    IS-01 currently names backend helper functions, frontend mirrors, and
    RpcClient behavior. This is acceptable for an implementation specification as
    long as it does not imply that Turnix is fundamentally a frontend/backend
    template or that only one frontend technology or transport can use the
    schema.

    Required consequence for IS-01:
        Keep backend/frontend references where they identify current concrete
        model locations or mirrored helpers, but preserve the existing
        transport-agnostic statement that any transport may carry the same
        RPCMessage envelope.

9. Code-location canonicality should not make code silently override the spec.

    IS-01 says the canonical backend RPC message model lives in
    backend/rpc/models.py and that the frontend mirrors it.

    This is acceptable for an implementation specification, but avoid implying
    that undocumented code drift becomes architecture truth.

    Required consequence for IS-01:
        Preserve the existing rule that code and specification are updated
        together. Do not rewrite the file so that implementation accident becomes
        semantic authority.

==============================================================================
OBSOLETE-PRESERVATION RISKS
==============================================================================

1. Do not preserve AppInstance as current terminology.

    Translate AppInstance to Application / ApplicationRun according to meaning.

    Use Application when the identity is durable across loads.

    Use ApplicationRun when the identity is live, connection/run-scoped, or
    relevant to open RPC channels, live adapters, live Views, live Jobs, and
    current runtime contexts.

2. Do not preserve Session wording as harmless prose.

    In IS-01, "session" appears in the Gen/continuity context. Even if the
    intended meaning is connection session, the current source stack removes
    Session from core architecture. Use connection-generation wording instead.

3. Do not preserve PackContext if adding clarification.

    IS-01 does not currently expose PackContext directly, but any clarification
    around origin/calling context must use ModCallContext and must state that
    live contexts are not carried in RPC envelopes.

4. Do not preserve older retry wording if it implies old work identity reuse.

    RPC idempotency deduplication is not the same as architectural Retry.

No major process-metadata leakage was found in the target IS text.

REQUIRED FIXES

    Replace examples:

        adapter and AppInstance correlation metadata carried by the envelope

    with:

        adapter, Application, and ApplicationRun correlation metadata carried by
        the envelope

    Replace:

        appInstanceId

    with one or both of:

        applicationId
        applicationRunId

    depending on whether the field is durable-identity or live-run correlation.

    Replace:

        AppInstance lifecycle semantics
        AppInstance lifecycle
        AppInstance readiness

    with Application / ApplicationRun wording.

2. Replace Session continuity wording.

    Replace:

        reject frames from previous sessions
        session continuity validation
        session or transport continuity evidence

    with connection-generation and stale-traffic wording.

3. Clarify origin metadata.

    Replace "calling context" in origin examples with serializable
    cause/correlation wording.

    Add the stop-line that origin never carries live ModCallContext and never
    preserves invocation authority across messages.

4. Clarify object routes.

    Define object route as an RPC routing target identity / handler target known
    to the routing layer.

    Add the stop-line that object route is not raw backend object access,
    Service-object access, filesystem access, committed-state authority, or
    capability permission by itself.

5. Clarify idempotencyKey.

    Reword retry/deduplication text so it does not claim DA-level Retry
    semantics.

    Use "repeated messages" or "repeated requests" unless specifically talking
    about a higher-level Retry workflow.

6. Clarify cancel.

    Add a cancel stop-line saying cancel messages do not by themselves produce
    Job, OrchestrationUnit, ApplicationRun, ExecutionAdapter, transport, or
    history finalization outcomes.

7. Clarify stateUpdate.

    Add a stateUpdate stop-line saying stateUpdate payloads do not mutate
    committed Application state, configuration, retained history, or SaveBundle
    material merely by being received or routed.

8. Preserve isComplete as wire-envelope marker only.

    Keep the existing isComplete section substantially intact.

    Do not expand isComplete into authority, correctness, permission, lifecycle,
    Job, trace, payload, or committed-state semantics.

9. Preserve transport-agnostic schema scope.

    Keep the rule that the schema may be used by WebSocket, in-process, testing,
    or future transport implementations when those implementations carry the same
    concrete RPCMessage envelope.

10. Keep implementation references scoped.

    It is acceptable for this IS to name backend/rpc/models.py,
    frontend/assets/types.d.ts, and RpcClient helper utilities as concrete
    implementation locations.

    Do not make those implementation locations broader architecture authority.

ACCEPTANCE CONDITIONS FOR FINAL REWRITTEN IS-01
==============================================================================

Accept the rewritten IS-01 only if all of the following are true:

1. It defines only the concrete RPCMessage wire-envelope schema and helper /
   serialization expectations.

2. It does not introduce new authority, policy, permission, lifecycle, transport,
   adapter, View, Job, Application, ApplicationRun, SaveBundle, trace-retention,
   or committed-state semantics.

3. All AppInstance terminology has been translated to Application and/or
   ApplicationRun according to current meaning.

4. Session wording has been removed from Gen / continuity text and replaced with
   connection-generation or transport-continuity wording.

5. origin metadata is described as serializable correlation / cause descriptors,
   not a live ModCallContext, PackContext, transaction, service object, or
   reusable authority context.

6. Route object wording cannot be read as raw backend object access or Service
   object exposure.

7. ack, correlatesTo, lane, budgetMs, job metadata, idempotencyKey, cancel,
   final, payload, stateUpdate, and isComplete each remain non-authoritative
   unless a higher owner accepts the corresponding operation through the proper
   boundary.

8. idempotencyKey deduplication is not confused with architectural Retry,
   Replay, Resume, Job identity reuse, OrchestrationUnit identity reuse, or
   ProcessingRun identity reuse.

9. stateUpdate is clearly an RPC payload category and not a committed-state
   mutation mechanism by itself.

10. isComplete remains a wire-envelope completion marker only and is not treated
    as semantic correctness, lifecycle success, permission, authority, trace
    proof, or committed-state mutation.

11. Backend/frontend implementation references remain scoped to concrete schema
    mirrors and helper locations. They do not redefine Turnix as a
    frontend/backend template.

12. The document keeps its transport-agnostic statement that WebSocket is only
    one possible transport for the same concrete RPCMessage envelope.
