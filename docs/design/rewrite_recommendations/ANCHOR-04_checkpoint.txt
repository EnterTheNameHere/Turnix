CURRENT DV3 THESIS
==================

Turnix is a reusable runtime for persistent, local-first, traceable, stateful,
orchestrated AI applications and adjacent runtime systems.

Turnix is not primarily:

    - a launcher
    - an AppPack runner
    - a pack format
    - a pack manager
    - a catalog system
    - a graph-preparation tool
    - a frontend/backend template
    - a plugin loader
    - a dynamic script runner
    - a web app framework
    - a convenience-first modding system

Turnix is primarily:

    - a runtime continuity engine
    - a deterministic resolver
    - a policy-driven orchestrator
    - an explainable system
    - a controlled execution and state boundary
    - a host for AppInstances and other runtime-managed work

Core Dv3 correction:

    Turnix does not merely run AppPacks.

    Turnix runs AppInstances.

    AppPack is one declarative way to create an AppInstance.

Packs remain first-class, but packs do not define the whole identity of Turnix.

PackManager is an official Turnix management domain, but PackManager also does
not define the whole identity of Turnix.


HIGH-LEVEL RUNTIME MODEL
========================

Turnix Runtime contains or composes:

    - Kernel
    - RuntimeHost
    - Trace substrate
    - Memory / committed state model
    - IO / persistence protection
    - Service system
    - Permission system
    - Capability system
    - Job system
    - OrchestrationUnit system
    - RPC / interoperability boundary
    - transport implementations
    - ExecutionAdapters
    - PackManager
    - AppInstance system
    - SavePack / durable AppInstance state system
    - pack discovery and resolution
    - pack identity and visibility
    - pack dependency and activation systems
    - importing / module-loading boundary
    - LLM pipeline / LLM driver systems
    - debugger / diagnostic surfaces

Most subsystems should be independently useful where possible.

Examples:

    Memory can be useful without LLMs.
    Trace can be useful without a frontend.
    LLMDriver can be replaceable.
    RPC should be transport-agnostic.
    ExecutionAdapters should be replaceable.
    Pack system should be first-class but not mandatory for every embedded use.
    PackManager can help manage pack graph intent without owning activation,
    importing, persistence, policy, or Kernel authority.

However, once these parts need to work together as one runtime, Kernel and
RuntimeHost compose them under Turnix-owned lifecycle, authority, policy,
orchestration, and state boundaries.


AUTHORITY GUARDRAILS
====================

Preserve authority boundaries.

Do not let convenience, implementation proximity, same-language execution,
same-process execution, direct-call optimization, first-party tooling, or
RuntimeHost command surfaces collapse authority boundaries.

Kernel owns runtime authority.

RuntimeHost exposes controlled entry surfaces but is not Kernel authority.

ExecutionAdapter runs external or adapter-mediated code but is not Kernel
authority.

RPC is the logical communication boundary, not a transport.

Transport carries messages but does not define authority.

Capability invocation is not automatically Job.

Service object access is not capability permission.

PackContext is scoped participation, not backend internals access.

Discovery is candidate production, not visibility, resolution, activation,
import, runtime loading, or runtime identity.

Visibility is eligibility-to-be-seen, not resolution, dependency satisfaction,
activation, import, permission, or capability authority.

Resolution is deterministic selection under one explicit context, not
discovery, activation, import, PackManager repair, policy guessing, or source
mixing.

Importing/module loading is not activation.

Activation is controlled executable participation, not import.

Dependencies are hard contracts, not preferences, activation, import,
capability permission, or advisory metadata.

Advisory pack relations are metadata for PackManager/UI presentation, not hard
dependencies, hard activation blockers, resolution constraints, or loader rules
by themselves.

PackManager is first-party management/tooling domain, not Kernel, RuntimeHost
authority, resolver, loader, activator, policy owner, persistence authority, or
Turnix identity.


KERNEL
======

Kernel is the runtime authority root.

Kernel should remain intentionally small and should not become a god object.

Kernel owns or coordinates:

    - runtime authority
    - root runtime context
    - service registries
    - AppInstance management
    - Job management
    - Capability registry
    - Permission manager
    - TraceHub / trace substrate access
    - IOManager / persistence access
    - adapter manager
    - RuntimeHost connection points
    - approved internal routing paths

Kernel is not:

    - Memory
    - LLMPipeline
    - LLMDriver
    - IOManager
    - PackResolver
    - PackManager
    - RuntimeHost
    - AppInstance
    - frontend
    - adapter
    - application logic
    - mod logic
    - storage logic
    - prompt logic

Kernel rule:

    If a subsystem can work without Kernel, it should be allowed to.

    If multiple subsystems need to work together as one runtime, Kernel composes
    them and enforces the contract boundaries between them.

Kernel should be small, boring, and hard to abuse.


RUNTIMEHOST
===========

RuntimeHost is the running host boundary.

RuntimeHost is not Kernel authority.

RuntimeHost owns the running host boundary through which Kernel-owned authority
is started, exposed, coordinated, and closed.

RuntimeHost is not:

    - Kernel
    - AppInstance
    - SavePack
    - CLI
    - ExecutionAdapter
    - transport
    - Job
    - OrchestrationUnit
    - PackManager
    - Turnix identity
    - launcher identity

RuntimeHost may expose controlled entry surfaces.

Entry surfaces and command surfaces can request, observe, or control runtime
operations only through mediated paths.

They do not become authority themselves.

Startup modes are entry workflows, not separate runtime semantics.

Examples:

    interactive host mode
    one-shot command mode
    serve mode
    connect mode
    test mode
    launcher mode

These are different ways to enter Turnix, not different Turnixes.


LOCAL-FIRST
===========

Turnix is local-first, not local-only.

Local-first does not require same-machine execution.

Local-first means authoritative runtime and state remain under user-controlled
local infrastructure.

This can include:

    - RuntimeHost and frontend on the same machine
    - RuntimeHost on one LAN machine and frontend on another
    - home server RuntimeHost with local SavePack/state ownership
    - powerful local AI machine hosting execution while lighter clients present UI

Local-first does not prohibit explicit, policy-governed:

    - LAN mode
    - server hosting
    - remote-resource mode
    - federated discovery
    - remote clients

But those modes must not replace local-first as the baseline authority,
persistence model, failure model, and recovery model.


TRACE
=====

Corrected trace model after DA-03 and DA-04:

    Trace is structured evidence.

    Trace is not committed state.

    Trace is not logging.

    Trace is not memory.

    Trace is not persistence truth.

Trace answers:

    What happened?
    What caused what?
    Why?

Trace evidence is proof only within retained trace evidence.

If an action is not present in retained trace evidence, trace cannot prove that
it happened.

If trace evidence was lost, the loss itself must be represented honestly when
possible.

Important distinction:

    Domain-required trace emission
        A subject-owning document may require that a domain attempt to emit
        trace evidence for meaningful actions.

        This is an emission obligation.

    Trace persistence / retention
        Trace persistence is policy-governed.

        Retained trace evidence may be bounded, rotated, or lossy when loss is
        represented honestly.

    Optional diagnostic / verbose trace
        Development-mode or diagnostic enrichment that is best-effort and
        non-authoritative.

Trace loss weakens evidential completeness.

Trace loss does not by itself change committed-state correctness.

Committed-state truth is governed by DA-04's authoritative commit model, not by
trace completeness.

Corrected mantra:

    If not traced, trace cannot prove it happened.

Not:

    If trace persistence failed, committed state is invalid.

Trace reason ownership is domain-specific:

    DA-03 = trace substrate
    DA-04 = state / transaction trace obligations
    DA-09 = discovery trace reasons
    DA-11 = resolution trace reasons
    DA-14 = activation trace reasons
    DA-16 = capability trace reasons
    DA-19 = Job trace reasons
    DA-21 = RPC trace evidence and message-flow observability
    DA-24 = OrchestrationUnit trace reasons
    DA-28 = RuntimeHost trace reasons
    DA-29 = PackManager trace reasons

DA-03 should not become the catalog of every domain trace reason.

Cross-document trace wording rule:

    When a document says trace-visible or requires trace evidence, treat that
    as a domain trace emission obligation unless the document explicitly
    defines stronger persistence semantics under DA-03.

    Do not let trace wording imply that retained trace evidence is committed
    state, that trace persistence is guaranteed forever, or that trace loss
    invalidates committed-state truth.


MEMORY AND COMMITTED STATE
==========================

Memory is not merely chat history.

Memory is not merely prompt context.

Memory is not authoritative merely because it is:

    - resident
    - visible
    - active
    - currently in use

Committed state becomes authoritative only after crossing the DA-04 commit
boundary.

Correct state model:

    memory = runtime representation
    state = committed authority
    trace = evidence / observation
    persistence = protection

DA-04 uses exactly two authority classes:

    Authoritative
    Non-authoritative

Avoid introducing semi-authoritative state categories.

A thing may be important, required to attempt, useful for explanation, or
policy-required, but for committed-state truth it is either authoritative or
non-authoritative.


MEMORY LAYERS
=============

Memory is layered by:

    - authority
    - scope
    - lifetime
    - rollback boundary

There is no single global memory object.

Reads resolve according to the active layer stack for the requesting scope.

Example layer kinds may include:

    - kernel-global layer
    - AppInstance layer
    - session layer
    - view layer
    - transactional layer
    - override layer
    - mod-provided layer

The example layer list is not a closed taxonomy.

Concrete layer catalogs should be defined in implementation/spec documents.


TRANSACTIONS AND COMMIT
=======================

A transaction is a temporary staging overlay.

Staged mutation is not authoritative.

A transaction resolves only by:

    - commit
    - abort

Commit and abort are atomic.

Partial propagation does not occur.

A transaction does not remain half-committed.

Nested transaction model:

    Child transaction commits propagate into parent transactions, not directly
    into committed layers while an enclosing transaction exists.

    Only the outermost transaction commit mutates committed layers.

Conflict detection:

    A transaction records the base committed revision visible when a key was
    first touched.

    Commit conflicts occur when committed existence or committed revision
    changed.

    Conflicting commit fails deterministically.

Turnix does not silently use:

    - merge
    - last-write-wins
    - heuristic reconciliation

Any override requires explicit user decision or explicit policy elsewhere.


PERSISTENCE
===========

Persistence protects committed state against loss.

Persistence does not define what state truth is.

Committed state truth is determined by the commit model.

Persistence failure does not silently redefine committed-state truth.

Clean stack:

    Commit model decides truth.
    Persistence protects truth.
    Trace explains or reports what happened.

Committed state restoration:

    Turnix supports deterministic restoration of committed state from retained
    authoritative material.

This does not imply:

    - deterministic reconstruction of in-flight activity
    - deterministic replay of external side effects
    - reproducibility of uncommitted activity


LATEST STATE
============

Latest committed state must remain restorable from retained authoritative
material.

History may be bounded.

Older revisions may be removed by retention/garbage-collection policy.

Garbage collection must not remove data required to reconstruct latest committed
state for each committed key.

Current committed truth cannot be silently rewritten by retention policy.


PACK DISCOVERY
==============

Discovery is candidate/root production.

Discovery is not:

    - visibility
    - enablement
    - selector resolution
    - dependency satisfaction
    - activation
    - import
    - runtime loading
    - capability authority
    - broader policy authority

Discovery is intentionally strict, boring, predictable, and side-effect free.

Discovery identifies candidate pack entities inside allowed roots and classifies
them into discovered or rejected outcomes.

Discovery also establishes candidate roots for non-pack categories such as
userdata and saves.

Discovery output is an input to later indexing, visibility, and resolution.

Discovery output is not a runtime-loaded result.

Root categories:

    - custom/
    - first-party/
    - third-party/
    - userdata/
    - saves/

userdata/ and saves/ are not content categories.

SavePacks are discoverable as save entities.

SavePacks are not eligible for import as normal content-root packs.

Packs copied into a SavePack remain context-bound to that SavePack unless a
later authoritative document explicitly states otherwise.

Save-local pack material is a distinct nearer source context and precedes
ordinary content-root precedence.

custom does not override save-local pack material by default.

Content-root precedence:

    custom
    first-party
    third-party

Watch item:

    This precedence should remain ordinary content-root precedence.

    It must not override SaveOnly, GlobalPinned, save-local copied material,
    selected graph intent, pinned SavePack graph evidence, or explicit
    AppInstance/SavePack semantics unless a later authoritative document
    explicitly says so.

PackManager and UI may be more helpful and exploratory, but that helpfulness
must not silently migrate into discovery itself.


PACK IDENTITY AND VISIBILITY
============================

Pack is the general container concept.

Specific pack kinds include:

    - AppPack
    - ModPack
    - ViewPack
    - ContentPack
    - SavePack

Pack identity layers are distinct:

    - declaredId
    - packTreeId
    - author
    - version

declaredId is manifest-local to its parent pack context.

packTreeId is computed from hierarchy and is not filesystem-based.

author is part of identity, not decoration.

If author cannot be resolved through declaration or inheritance, the pack is
invalid.

Visibility answers whether one pack is eligible to be seen from another
context.

Visibility is not:

    - dependency declaration
    - dependency satisfaction
    - import use
    - activation order
    - capability authority
    - permission
    - resolution winner selection

Local visibility values:

    - public
    - private

Default local visibility:

    - ContentPack -> public
    - AppPack -> private
    - ViewPack -> private
    - ModPack -> private
    - SavePack -> private

exportNestedPacks controls whether direct children become externally visible
beyond the local parent context.

importPacksFromParent controls which parent-context packs are import-visible to
a child pack.

importPacksFromParent does not imply:

    - export
    - capability inheritance
    - permission inheritance

SavePack visibility remains save-local.

Packs copied into a SavePack do not leak into global visibility merely because
they exist inside that SavePack.

Save-local copied packs may override external candidates within that SavePack
context.

Open watch item:

    Exact internal visibility rules inside one SavePack remain to be defined.


GENERIC RESOLUTION
==================

Resolution answers:

    Which concrete pack identity satisfies this PackRequest inside the current
    resolution context?

Resolution is deterministic and side-effect free.

Resolution consumes:

    - one PackRequest
    - one registry snapshot
    - one externally supplied resolution context

Resolution outputs exactly one of:

    - one resolved concrete pack identity
    - one classified resolution failure
    - one classified ambiguity requiring external decision

Resolution does not:

    - rescan the filesystem
    - read manifests lazily
    - merge manifest fragments
    - activate packs
    - load runtimes
    - guess policy
    - mutate the registry snapshot
    - trigger new discovery
    - combine partial candidate data into a synthetic candidate

Discovery builds the candidate universe.

Resolution selects from that already-built universe.

Resolution works on whole discovered candidate artifacts.

Resolution does not merge duplicate manifests, stack manifest fields, or compose
synthetic candidates from several shadowed candidates.

Resolution always occurs inside one explicit resolution context.

The generic resolver does not invent, switch, or silently mix resolution
contexts.

If the surrounding consumer violates context assumptions, resolution fails
explicitly.

Silent substitution is forbidden.

Ambiguity requires external policy or user decision.

The generic resolver does not guess.

Watch item:

    Later consumer documents must explicitly define the resolution context and
    ordering criteria they supply.

    Consumer ordering must not smuggle hidden policy, source switching, silent
    repair, remembered decisions, or PackManager repair into generic resolution.


IMPORTING AND MODULE LOADING
============================

Importing is not:

    - dependency declaration
    - resolution
    - adapter selection
    - execution authorization
    - activation
    - execution authority
    - capability permission

Native language import systems do not understand Turnix pack resolution,
visibility, save scoping, adapter selection, execution authorization,
activation boundaries, or execution authority.

Turnix does not allow arbitrary language-native importing across packs.

Cross-pack code access routes only through Turnix-defined mechanisms.

Same host language does not imply same authority.

Python pack code remains adapter-executed pack code and does not become backend
implementation code through Python import behavior.

Python pack code may use native Python imports only for local code under the
same-file or same-directory rule and for explicitly allowed Turnix platform
surfaces.

Cross-pack native Python imports are not allowed.

Python pack code interacts with other packs only through Turnix-mediated APIs.

There is no Python equivalent of turnixImport as a cross-pack native symbol or
executable-code import mechanism.

JavaScript cross-pack loading routes through:

    turnixImport(selector)

turnixImport is a Turnix-defined mediated loader.

turnixImport is not native import().

turnixImport is not:

    - dependency declaration
    - adapter selection request
    - execution authorization request
    - activation request
    - capability permission request
    - visibility override
    - permissive or best-effort loader
    - version selector
    - Kernel authority grant

turnixImport does not create a second independent resolution system.

turnixImport depends on Turnix resolution and boundary checks.

Importing respects the concrete identity already chosen during dependency
resolution.

Importing does not reopen dependency resolution.

Semver is not allowed in turnixImport selectors.

Importing is identity-based rather than version-selection-based.

Module evaluation caused by JavaScript ESM import is not Turnix-recognized
activation.

Import-time execution is not an activation mechanism.

Background work started outside Turnix orchestration is unsupported by Turnix
guarantees.

Watch item:

    Core/internal runtime file selectors must remain whitelisted Turnix platform
    surfaces, not a general filesystem path namespace.


DEPENDENCIES AND PACK REQUESTS
==============================

Dependencies are hard functional contracts.

Dependency meaning:

    This pack cannot function correctly unless another pack exists that
    satisfies this request.

Dependencies are not preferences.

Declaring a dependency does not:

    - load code
    - activate a pack
    - grant visibility
    - grant capabilities
    - define activation order

Failure to satisfy a hard dependency is a hard failure unless some other
accepted policy or user decision explicitly resolves it.

Manifest field:

    packs

Rules:

    - absence of "packs" means no hard dependencies
    - an empty list means explicitly no hard dependencies
    - every entry under "packs" is a hard dependency meaning
    - list order carries no semantic meaning by itself

Dependency resolution source model:

    - SaveOnly
    - GlobalPinned
    - GlobalNormal

Every hard dependency is resolved from exactly one dependency-resolution source.

Sources are mutually exclusive.

The resolver does not silently mix or fall back between these sources.

SaveOnly:

    - applies when dependency packTreeId is listed in SavePack metadata as copied
    - only copied packs inside that SavePack are eligible
    - global registry is not consulted
    - absence of the copied pack is a hard error

GlobalPinned:

    - applies when dependency is bound to a pin in SavePack metadata
    - only the pinned concrete identity is eligible
    - resolution occurs in the global registry only
    - a missing pinned identity is a hard error
    - the pin does not imply copying or saving

GlobalNormal:

    - applies in all other dependency cases
    - resolution occurs in the global registry only
    - SavePack content is not consulted
    - selection follows deterministic GlobalNormal procedure

GlobalNormal selection procedure:

    1) version handling
    2) author relationship ordering
    3) root precedence: custom, first-party, third-party
    4) final lexicographic tie-break

Fingerprint requires exact concrete version.

Fingerprint is an exact artifact lock, not a vague compatibility hint.

Advisory pack relations:

    - supportedPacks
    - conflictingPacks
    - recommendedPacks

Advisory relations are not:

    - hard dependencies
    - hard activation blockers
    - generic resolution constraints
    - loader/runtime warning rules by themselves

Advisory relations are for PackManager, UI, compatibility presentation, and
helping the user assemble a load list.

Required roles / provided roles:

    requiredRoles and providedRoles are dependency/resolution-layer semantics.

    They are not runtime capability invocation semantics.

Watch item:

    Provider registration and provider selection need later audit.

    "First registered provider wins" is safe only if registration order itself
    is deterministic, scoped, trace-visible, and authority-safe.


ACTIVATION
==========

Activation is the controlled boundary between inert metadata and
Turnix-recognized executable participation.

Activation answers:

    Has Turnix intentionally brought this pack into recognized executable
    participation under Turnix orchestration?

Activation is a controlled, explicit, one-time state transition.

Before activation:

    - a pack exists only as metadata
    - its code has no execution authority under Turnix
    - adapter loading or native module evaluation does not make it active

After activation:

    - the pack may participate in runtime behavior
    - execution is allowed only through Turnix-controlled orchestration pathways
    - PackContext defines the pack-facing authority context

Activation is not:

    - discovery
    - indexing
    - dependency resolution
    - importing
    - adapter selection
    - execution authorization
    - adapter loading
    - visibility granting
    - capability permission

Activation is the first moment Turnix may intentionally execute pack code with
PackContext authority.

Activation applies to the pack as a whole.

Activation does not apply to:

    - individual files
    - individual modules
    - individual imports
    - individual capabilities
    - individual adapter-loaded artifacts

Current activation entrypoint:

    onLoad(ctx)

Rules:

    - onLoad(ctx) is called exactly once per pack instance
    - onLoad(ctx) is called only by Turnix
    - ctx is always provided by Turnix
    - failure aborts activation of that pack

Future activation entrypoints, if introduced, must follow the same rules and be
explicitly defined by Turnix.

Activation and execution are distinct.

Execution occurs only after activation when Turnix-recognized.

Execution may happen multiple times.

Execution occurs only when invoked by Turnix orchestration.

Adapter loading does not create partial activation.

Immediate execution, IIFE-style patterns, module-level statements, and top-level
side effects are unsupported by Turnix guarantees.

Activation-independent library code may accept a PackContext explicitly as a
parameter.

In that case:

    - the caller pack owns responsibility
    - the authority is that of the caller, not the provider
    - the provider pack's activation state does not change

Activation order is affected by PackManager, resolved dependencies, visibility
constraints, user policy, and future category-based ordering if accepted.

Watch item:

    PackManager may prepare or propose activation graph/load order, but
    activation itself remains Turnix-controlled and constrained by Kernel,
    policy, capability, adapter, trace, and lifecycle boundaries.

Last-known-good fallback:

    DA-13 says last-known-good fallback is used only after activation failure.

    It is not consulted during dependency resolution.

    Any later fallback behavior must remain explicit, trace-visible,
    policy-bound, and must not become silent dependency-resolution success.


SERVICES
========

Service = runtime wiring object.

A Service is not a permission layer.

A Service is not capability authority.

A Service is not adapter authority.

A Service is not PackContext authority.

A Service is not a backend-internal exposure path to adapter-executed code.

A Service is not a cross-pack execution shortcut.

A Service is not an in-process adapter bypass.

Services must not bypass:

    - configuration schemas
    - persistence rules
    - execution authorization
    - permission checks
    - capability mediation
    - adapter boundaries
    - Job lifecycle boundaries

Correct model:

    Services are runtime wiring.

    Capabilities are mediated execution boundaries.


CAPABILITIES
============

Capability = named, permissioned, Turnix-mediated operation.

Capability is not:

    - permission itself
    - Service
    - Job
    - OrchestrationUnit
    - RPC message
    - direct service object
    - committed-state authority
    - PackManager authority
    - adapter authority
    - execution authorization
    - persistence authority

Capability export happens at runtime through explicit capability registration.

Manifest capability declarations may support tooling, diagnostics, and user
experience, but manifest intent does not override runtime reality.

Capability invocation may complete without creating a Job.

Long-running, cancellable, progress-reporting, timeout-managed, or observable
capability execution may create or attach to a Job.

A Job handle is a lifecycle handle, not a raw service object or direct
implementation-internal reference.

Job-backed capability execution remains capability-mediated.

Job-backed execution does not expose service internals, raw implementation
objects, or the underlying execution mechanism.

Capability permission is distinct from adapter execution authorization.

A code artifact may be allowed to run while a specific capability invocation is
still denied.

Same process, same runtime, or same language does not bypass capability
mediation.


PERMISSIONS
===========

Permission classes currently audited in DA-16:

    - none
    - soft
    - hard

Permission class is immutable per major version.

Permission classification is capability-defined and is not negotiated by
callers.

Remembered capability permission matching uses the exact versioned capability
identifier.

Wildcard, prefix, family, or versionless fallback matching for remembered
capability decisions is not introduced by DA-16.

DA-17 remains load-bearing for remembered-decision semantics.


ORCHESTRATIONUNIT
=================

OrchestrationUnit is a kernel-tracked execution-authority unit.

Better wording:

    OrchestrationUnit authorizes and coordinates mutation flow.

Not:

    OrchestrationUnit is committed state authority.

Not:

    Anything inside the OrchestrationUnit gets direct authority.

OrchestrationUnit is distinct from:

    - AppInstance
    - Job
    - transaction
    - View
    - ExecutionAdapter
    - RuntimeHost
    - RPC message
    - capability
    - transport message

Correct split:

    OrchestrationUnit coordinates mutation authority.
    DA-04 still owns committed-state truth.

Mutation through OrchestrationUnit still crosses:

    - policy
    - capability
    - transaction
    - commit
    - persistence
    - trace boundaries

Mutation outside orchestration does not acquire Turnix guarantees by implication.

Same-language or same-process execution does not bypass committed-state
authority.

RuntimeHost implementation code does not directly mutate committed state outside
Kernel-owned orchestration paths.

Adapter-executed code does not directly mutate committed state.


SINGLE-LANE APPINSTANCE ORCHESTRATION
=====================================

Default model:

    Turnix uses deterministic single-lane orchestration within one AppInstance
    unless an explicit concurrency mode is defined elsewhere.

Turnix does not execute multiple OrchestrationUnits concurrently when those
units may mutate the same AppInstance state.

Awaited model calls, adapter calls, transport calls, RuntimeHost calls, or other
I/O may suspend the current unit.

Suspension does not authorize another state-mutating unit to run concurrently
inside the same AppInstance unless explicit concurrency mode permits it.

This prevents async/suspension from accidentally becoming concurrency authority.


JOB
===

Corrected DA-19 model:

    Job = observable lifecycle handle for requested work.

Job is not:

    - Promise
    - coroutine
    - callback
    - thread
    - task
    - process
    - model request
    - transport message
    - RPC request
    - capability
    - OrchestrationUnit
    - transaction
    - committed state
    - execution mechanism
    - result payload

Runtime primitives may implement Jobs, but those primitives do not define Job
lifecycle semantics.

Core triad:

    Job answers:
        What requested work is waiting, running, succeeded, failed, cancelled,
        timed out, superseded, or paused?

    OrchestrationUnit answers:
        What owns or coordinates execution authority?

    Transaction answers:
        What staged mutation may become committed truth?

Job states:

    - Pending
    - Running
    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

Terminal states:

    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

A Job reaches exactly one terminal state.

Terminal state is final.

Closed Jobs are not restarted.

Retry is new work unless a later document explicitly defines a retry
relationship.

Retry does not reuse the previous jobId.


JOB RESULT, PROGRESS, AND STATE
===============================

A Job result exists only for Succeeded.

Failed has failure error.

Cancelled, TimedOut, and Superseded may have metadata, but they should not
smuggle successful result semantics into their terminal state.

Progress is observational lifecycle evidence.

Progress is not authoritative mutation.

Progress updates do not commit authoritative state.

Progress does not prove eventual success.

A Job does not become committed state merely because it exists, runs, or reaches
terminal outcome.

A Job result envelope does not become authoritative committed state merely
because the Job succeeded.

Job effects become authoritative only through the documents that own those
effects:

    - state
    - transaction
    - Window
    - capability
    - persistence


CANCELLATION, TIMEOUT, SUPERSESSION
===================================

Cancellation:

    Cancellation is explicit.
    Cancellation is intentional.
    Cancellation is not failure.

Cancellation request, cancellation outcome, execution-stop attempt, and
execution-stop result are distinct.

A cancellation request does not guarantee immediate cancellation.

Cancelling before execution begins does not require execution-stop because no
underlying execution exists yet.

Cancelling after execution begins may attempt to stop the underlying execution
mechanism, but Job cancellation outcome and execution-stop outcome remain
distinct.

Timeout:

    Job timeout is a Job lifecycle concern.
    Job timeout is not RPC transport timeout.
    RPC transport timeout is not Job timeout.
    Timeout uses a monotonic clock.
    Timeout policy source is explicit.
    TimedOut is distinct from Cancelled and Failed.

Supersession:

    Superseded is a first-class terminal non-error outcome.

    Supersession is explicit, intentional, not failure, not timeout, and not
    ordinary user cancellation.

    Superseded means newer accepted input, newer work, or higher-priority work
    made the old Job no longer relevant.

    Superseded does not roll back authoritative state already committed.

    Superseded does not allow new authoritative mutation from the superseded Job
    after terminal transition.

Late completion after terminal outcome:

    - does not change the Job terminal state
    - does not produce a Job result
    - does not deliver a reply/result
    - may be traced as diagnostic evidence
    - may not commit new authoritative mutation after the terminal transition


RPC AND TRANSPORT
=================

RPC is the logical communication boundary.

Transport is the concrete carrier.

WebSocket is one possible transport, not the definition of RPC.

RPC / transport must not be confused with Job lifecycle or OrchestrationUnit
outcome.

Important rules:

    A transport acknowledgement does not prove that a Job exists.

    A Job may exist even if the creating transport later disconnects.

    A transport timeout does not imply Job timeout.

    Job timeout does not imply transport timeout.

    A request may be rejected before a Job exists.

    A request may be accepted as a Job.

RPC message flow stages are distinct:

    - transport delivery
    - decoding / validation
    - routing
    - acceptance
    - handler execution
    - optional Job creation
    - response / update emission
    - terminal Job outcome when a Job exists

Transport failure does not by itself define Job failure, adapter failure,
activation failure, or RuntimeHost failure.

Everything outside trusted backend internals should communicate with backend
internals through controlled boundaries:

    external caller
        -> ExecutionAdapter / entry surface
        -> RPC / interoperability boundary
        -> permission check
        -> capability / orchestration / job
        -> internal service


EXECUTIONADAPTER
================

ExecutionAdapter is the selected Dv3 umbrella term.

The older general term FrontendAdapter is too narrow.

Frontend/browser adapter may remain only as a specific UI-facing adapter
realization or subtype.

ExecutionAdapter runs code or surfaces outside trusted Turnix internals.

Examples:

    - Browser/Electron adapter
    - Python adapter
    - Unity/C# adapter
    - Lua adapter
    - C++ adapter
    - remote process adapter
    - test adapter

Important Python distinction:

    Internal Turnix Python is trusted backend implementation.

    Pack-provided Python is external code.

Pack-provided Python should not call backend internals directly merely because
Turnix backend is written in Python.

Same-language or same-process execution does not erase a contract boundary.

Adapter-executed mutation seeking Turnix guarantees must re-enter through:

    - orchestration
    - capability
    - transaction
    - commit boundaries

Direct-call optimization may implement a transport or dispatch optimization.

Direct calls do not bypass:

    - RPC-shaped authority boundary
    - route or capability target identity
    - permission checks
    - lifecycle ownership
    - trace correlation
    - structured result and error handling
    - OrchestrationUnit boundaries
    - transaction and commit boundaries
    - AppInstance and SavePack state authority
    - RuntimeHost authority boundaries


PACKMANAGER
===========

PackManager is the official Turnix pack-management and graph-preparation
domain.

PackManager helps inspect, explain, prepare, validate, repair, and manage pack
graph intent.

PackManager is not:

    - Kernel
    - discovery
    - generic resolution
    - importing
    - activation
    - ExecutionAdapter
    - mechanical loader
    - capability permission
    - persistence authority
    - View authority
    - policy owner
    - AppInstance lifecycle owner
    - SavePack authority
    - RuntimeHost
    - Turnix identity

PackManager helps choose and explain what Turnix will try.

Turnix still performs only accepted graph, activation plan, policy, and
operation through Kernel-mediated boundaries.

PackManager may prepare an activation plan.

PackManager does not activate packs by preparing an activation plan.

PackManager does not execute pack code by preparing selected graph intent.

PackManager does not import code by preparing selected graph intent.

PackManager does not grant PackContext authority by preparing selected graph
intent.

PackManager operations may be exposed through RuntimeHost commands,
capabilities, RPC, Views, or test surfaces, but those surfaces remain mediated
request surfaces.

PackManager Views are presentation and interaction surfaces.

Displaying a PackManager View does not grant pack-management authority to the
displaying surface.

PackManager UI does not own the semantics it presents.

PackManager writes occur only through Kernel-mediated persistence,
configuration, transaction, and policy boundaries.

PackManager does not silently mutate active AppInstance graph state.

PackManager does not silently update packs active in a running AppInstance.

PackManager does not silently make changes to a SavePack-owned copied pack
graph.

PackManager graph changes affecting a running AppInstance require explicit
lifecycle, policy, and trace handling.


PACKMANAGER REPAIR
==================

Repair means:

    explicit, scoped, policy/user-mediated graph-preparation repair

Repair does not mean:

    automatic hidden correction

Repair must not silently:

    - resolve ambiguity
    - accept risky graphs
    - broaden remembered decisions
    - rewrite manifests
    - bypass visibility
    - satisfy hard dependencies
    - update active AppInstance packs
    - mutate SavePack-owned copied pack graph
    - write roots/config/state/policy decisions


PACKS
=====

Pack is the general distributable unit.

Packs are first-class but not identity-defining.

Pack may contain:

    - manifest
    - metadata
    - code
    - assets
    - data
    - schemas
    - prompt fragments
    - adapter entrypoints
    - requirements
    - requested permissions
    - provided capabilities
    - dependencies

Pack types may include:

    - AppPack
    - ModPack
    - ContentPack
    - SavePack
    - ViewPack
    - possibly RuntimePack or ProviderPack later


APPPACK
=======

AppPack is an application definition or launch recipe.

AppPack describes how to create an AppInstance.

AppPack does not define Turnix identity.

AppPack may specify:

    - application identity
    - entrypoints
    - required packs
    - required adapters
    - required capabilities
    - required models/providers
    - initial orchestration units
    - initial memory templates
    - UI surfaces
    - assets
    - default settings
    - permission requirements

Important Dv3 correction:

    Turnix runs AppInstances.

    AppPack describes one declarative way to create an AppInstance.

An AppPack may be absent in embedded/scripted/test usage.

Pack-based usage remains first-class for product/user-facing applications.


MODPACK
=======

ModPack provides additional behavior, content, UI, orchestration hooks, or
capabilities.

ModPack code is external to trusted backend internals.

Therefore ModPack code should run through ExecutionAdapters and communicate
through RPC/capabilities/events.

ModPack should not mutate backend internals directly.

ModPack may register or request participation in orchestration only through
explicit contracts.


SAVEPACK
========

SavePack likely represents persisted state for a concrete AppInstance.

    SavePack stores durable executed state.

Likely improved wording, pending SavePack/AppInstance audit:

    SavePack stores durable AppInstance state.

SavePack should not be treated as merely a folder of files.

Likely SavePack contents may include:

    - AppInstance identity
    - selected AppPack identity/version
    - resolved dependency information
    - copied pack material
    - pinned global dependency identities
    - selected graph records or graph evidence
    - settings
    - latest committed memory/state
    - memory history, if retained
    - runtime state
    - user data
    - trace references or trace snapshots, if retained by policy
    - adapter state
    - orchestration state

This remains pending until SavePack/AppInstance documents are audited.


APPINSTANCE
===========

AppInstance is the live runtime realization of an application.

It may be created from an AppPack, with or without an existing SavePack.

AppInstance is not RuntimeHost.

RuntimeHost may host zero, one, or multiple AppInstances.

Likely AppInstance references:

    - resolved pack graph
    - active activation graph
    - memory root
    - active OrchestrationUnits
    - active Jobs
    - active adapters
    - permission context
    - trace context
    - IO context
    - runtime settings
    - lifecycle state

This remains pending until AppInstance documents are audited.


LLMPIPELINE
===========

LLMPipeline is likely an OrchestrationUnit type.

It is not the whole application.

It should own the lifecycle of an LLM run, not provider-specific model
communication.

Likely minimal stages:

    - receive input
    - prepare input
    - build query items
    - filter query items
    - build prompt
    - call LLMDriver
    - receive streamed response
    - receive final response
    - parse streamed response
    - parse final response
    - update query items / staged state
    - finalize

LLMPipeline should not bypass DA-04 commit rules.

LLMPipeline should not know provider-specific details.

LLMPipeline should probably run inside OrchestrationUnit / Job / transaction
boundaries when it mutates Turnix state.

This remains pending until LLMPipeline documents are audited.


LLMDRIVER
=========

LLMDriver is the provider-specific bridge to a model backend.

LLMDriver receives normalized model requests and returns stream/final response
events.

Possible drivers:

    - llama.cpp
    - Ollama
    - OpenAI-compatible API
    - local mock
    - replay driver

LLMDriver should not own application orchestration.

LLMDriver should not decide what memory means.

LLMDriver should not directly mutate AppInstance state.

LLMDriver should not replace LLMPipeline.

This remains pending until LLM driver/pipeline documents are audited.


DEBUGGER / TOOLING
==================

Tooling can inspect through controlled surfaces.

Tooling-initiated mutation must occur inside a transaction and follow the same
commit/abort rules as runtime mutation.

Tooling does not bypass authority boundaries merely because it is privileged
tooling.

The debugger/memory viewer must not become a separate state authority path.

PackManager tooling also does not become authority merely because it is official
tooling.

DA-18 and DA-08 remain to be audited for debugger pause/window/safe-point
behavior.

No guarantees outside orchestration.

Mutation outside orchestration does not acquire Turnix guarantees by implication.

Same-language or same-process implementation does not erase contract boundaries.

Pack-provided Python is external code.

Discovery is not resolution.

Importing is not activation.

AppPack is not Turnix identity.

CURRENT ONE-PARAGRAPH REHYDRATION
=================================

Turnix Dv3 is a runtime-domain architecture for persistent, local-first,
traceable, stateful, orchestrated AI applications. It is not merely an AppPack
runner, launcher, pack manager, catalog, or frontend/backend template. Turnix
runs AppInstances; AppPack is one declarative way to create one. Kernel owns
runtime authority, while RuntimeHost is only the running host boundary. Trace
is structured evidence, not committed state. Memory/DA-04 owns authoritative
committed-state truth through explicit transaction and commit boundaries.
Persistence protects committed state; it does not define truth. Discovery finds
candidate pack/root material but does not define visibility, resolution,
activation, import, or runtime loading. Visibility is eligibility-to-be-seen,
not resolution or permission. Resolution is deterministic snapshot selection
under one explicit context, not policy guessing or source mixing. Importing is
not activation. Dependencies are hard contracts, not activation or advisory
metadata. Activation is explicit pack-level executable participation with
PackContext authority and Turnix orchestration. OrchestrationUnit coordinates
mutation flow but cannot bypass the commit model. Job is an observable lifecycle
handle for requested work, not an OrchestrationUnit, transaction, RPC request,
capability, execution primitive, or committed state. Service is runtime wiring;
Capability is a named, permissioned, Turnix-mediated operation. ExecutionAdapter
is the general adapter category; same-language or same-process execution does
not erase boundaries. Pack-provided Python is external code. RPC is the logical
communication boundary; transport is only the carrier. PackManager is the
official pack-management and graph-preparation domain, but it does not become
Kernel, resolver, activator, importer, loader, capability permission,
persistence, View, AppInstance, SavePack, RuntimeHost, policy, or Turnix
identity. Turnix guarantees apply only inside Turnix-owned orchestration,
transaction, capability, persistence, policy, trace, and authority boundaries.
