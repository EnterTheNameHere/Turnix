==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Superseded by Proposal P02 in its SavePack/AppInstance/PackContext vocabulary;
    useful only as translated boundary-preservation guidance.

    Do not keep the recommendation as an obsolete historical artifact. Use it to
    preserve strict discovery boundaries, root-origin/category separation,
    manifest-based deterministic scanning, save-root discovery limits, PackManager
    separation, and DA-03-compatible trace wording after translating SavePack,
    AppInstance, and PackContext into canonical architecture terms.

Document verdict:
    Keep with targeted terminology and boundary fixes.

DA-09 is architecturally strong. It correctly owns root origins, root categories,
candidate-root formation, bootstrap path behavior, content-root aggregation,
discovery entrypoint rules, directory scanning constraints, discovery output,
save discovery policy, discovery guarantees, and discovery-domain trace
obligations.

No heavy conceptual rewrite is recommended.

The main required fix is terminology and SaveBundle alignment:

    - DA-09 currently treats SavePack as a specialized Pack kind.
    - Proposal P02 makes SaveBundle the durable persistence closure.
    - SaveBundle is not a Pack.
    - SaveBundle-related discovery/listing should not be described as ordinary
      Pack discovery or ListPacks filtered by SavePack kind.

DA-09 should preserve its strict discovery model, but rewrite save-related
vocabulary around SaveBundle and retained/copied Pack material inside or
associated with a SaveBundle.

Primary conclusion:
    Keep DA-09 as the root-system and discovery-boundary document. Perform a
    targeted terminology rewrite so SaveBundle is not fossilized as SavePack, and
    so discovery remains candidate production rather than runtime identity,
    activation, import, resolution, PackManager repair, or persistence authority.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-09 should not keep older terminology as a historical artifact.

Specifically, the rewrite should not preserve:

    - SavePack as a Pack kind
    - SavePack as ordinary importable content-root Pack material
    - SavePack directory deep scanning as ordinary Pack discovery
    - SavePack context where SaveBundle context or SaveBundle-local retained Pack
      material is meant
    - AppInstance context where Application / ApplicationRun context is meant
    - PackContext where ModCallContext is meant
    - old trace names or old context names merely for continuity if there is no
      compatibility reason

If a legacy alias is intentionally retained, DA-09 should say so explicitly and
should still state the canonical architecture term as primary.

Otherwise, the old names should be removed or translated.

The useful part of the old recommendation is not the old terminology. The useful
part is the discovery boundary:

    Discovery identifies and classifies candidate pack entities inside allowed
    roots. It also establishes candidate roots for non-pack categories such as
    userdata and saves. It does not grant runtime meaning, activation,
    importability, capability authority, PackManager repair authority, or
    persistence authority.

==============================================================================
01B. DOCUMENT-METADATA LEAKAGE CHECK
==============================================================================

The final DA-09 document should read as architecture documentation, not as audit,
version, or rewrite-process metadata.

Do not include statements such as:

    - This is V3 design.
    - In V3, SaveBundle replaces SavePack.
    - The new design uses Proposal P02.
    - This rewrite changed save discovery terminology.
    - Unlike V2, DA-09 now uses SaveBundle.
    - Codex kept SavePack wording.
    - This audit decided to use SaveBundle.
    - DA-09 was rewritten because of the audit.

Those facts may be useful in audit files, branch notes, migration notes,
compatibility notes, changelogs, or editor instructions. They do not belong in
the architecture document itself.

The final DA-09 should simply define roots, root categories, candidate roots,
bootstrap behavior, discovery rules, SaveBundle-related discovery boundaries,
side-effect-free discovery guarantees, and discovery-domain trace obligations.

==============================================================================
02. WHAT DA-09 GETS RIGHT
==============================================================================

02.1. Discovery is strict candidate production
----------------------------------------------

DA-09 correctly states that discovery identifies candidate pack entities inside
allowed roots and classifies them into discovered or rejected outcomes.

It also correctly says discovery establishes candidate roots for non-pack
categories such as userdata and saves, but does not grant runtime meaning beyond
the root/bootstrap model defined in DA-09.

Preserve this.

02.2. Discovery is not authority
--------------------------------

DA-09 correctly says discovery does not decide:

    - visibility
    - enablement
    - selector resolution
    - dependency satisfaction
    - activation
    - runtime loading
    - capability authority
    - policy outcomes beyond the root/bootstrap model

Preserve this and add import behavior explicitly where useful.

02.3. Root origin and root category are separate
------------------------------------------------

DA-09 correctly distinguishes root origin kind from root category.

Root origin kind describes where a root came from. It does not by itself decide
later resolution winner.

Root categories carry distinct meanings:

    - custom/
    - first-party/
    - third-party/
    - userdata/
    - saves/

Preserve this.

02.4. Externally-managed content-root rule is scoped correctly
-------------------------------------------------------------

DA-09 correctly says externally-managed content roots are content-only roots by
semantics and that this is a provenance/safety-hygiene rule, not a hard
adversarial-security guarantee.

Preserve this careful scope.

02.5. Userdata and saves root behavior is strong
------------------------------------------------

DA-09 correctly distinguishes candidate, selected, and preferred roots.

It correctly says selected roots are stronger than preferred roots for userdata
and saves, selected roots express explicit user choice, and mismatches caused by
controlled recovery must be surfaced rather than hidden.

It correctly says userdata has exactly one active root and saves has exactly one
active writable root.

It correctly keeps userdata redirect semantics separate from saves semantics.

Preserve this.

02.6. Content-root precedence is useful but scoped
-------------------------------------------------

DA-09 correctly defines ordinary content-root precedence:

    custom
    first-party
    third-party

This should remain as discovery/root input for later deterministic resolution and
tie-breaking, not as universal runtime authority.

Preserve the precedence but strengthen the stop-line that it does not override
SaveBundle-local retained Pack material, pinned/accepted graph evidence, explicit
user choice, or policy-owned graph choices.

02.7. Roots are namespaces, not packs
-------------------------------------

DA-09 correctly says root directories are namespaces rather than Packs and that a
manifest directly in a category root is ignored, not treated as a fatal error.

Preserve this.

02.8. Manifest-based deterministic scanning is strong
-----------------------------------------------------

DA-09 correctly defines discovery depth by manifest nesting rather than raw
filesystem nesting.

It correctly defines totalDepth behavior, default totalDepth, non-fatal depth
limit stopping, and default symlink refusal.

Preserve this.

02.9. Discovery output contract is strong
-----------------------------------------

DA-09 correctly says discovery produces PackDescriptor objects in Discovered
state, classifies candidates into discovered/rejected outcomes, preserves raw
manifest data, and preserves multiple distinct discovered candidates even when
later stages may decide equivalence.

Preserve this.

02.10. Manifest whole-artifact rule is strong
---------------------------------------------

DA-09 correctly says manifests are whole-definition artifacts, duplicate manifest
candidates are selected/shadowed rather than merged/stacked, and no additive
field composition across duplicate manifests occurs.

Preserve this.

02.11. Discovery remains side-effect-free
-----------------------------------------

DA-09 correctly says discovery is fast, side-effect-free, independent from Pack
activation, and does not require Pack-provided Readers, Writers, compilers, or
runtime providers.

Preserve this strongly.

02.12. PackManager helpfulness stays outside discovery
------------------------------------------------------

DA-09 correctly says PackManager and UI may be more helpful and exploratory, but
that helpfulness must not silently migrate into discovery itself.

Preserve this and align the name to PackManager where used as the domain/type.

==============================================================================
03. MAJOR REQUIRED FIX: SAVEBUNDLE AND SAVE-LOCAL TERMINOLOGY
==============================================================================

The current DA-09 and the recommendation still use SavePack as if it were a
specialized Pack kind.

Proposal P02 changes the durable persistence identity to SaveBundle. SaveBundle
is a durable persistence closure of an Application. SaveBundle is not a Pack.

DA-09 should be revised so saves/ remains a root category for durable save
material, but discovery does not classify SaveBundle itself as an ordinary Pack.

03.1. Replace SavePack as Pack kind
-----------------------------------

Current risky wording includes:

    Specialized pack kinds such as AppPack, ModPack, ContentPack, and SavePack
    remain specific uses of that broader container concept.

This should be rewritten.

Recommended direction:

    Pack is the general reusable content/application/mod/module container
    concept.

    Specialized Pack kinds include AppPack, ModPack, ContentPack, and other
    Pack-defined forms.

    SaveBundle is not a Pack. It is a durable Application persistence closure
    that may retain, copy, pin, or reference Pack material according to
    SaveBundle and Pack graph rules.

    DA-09 uses SaveBundle where durable Application persistence closure is meant.

Do not list SaveBundle as a Pack kind.

03.2. Replace saves/ category meaning
-------------------------------------

Current DA-09 says:

    saves/ contains SavePacks and related save-context state.

Replace with:

    saves/ contains SaveBundles and related durable Application persistence
    material.

    A SaveBundle may contain retained or copied Pack material, pinned Pack graph
    evidence, compatibility evidence, and SaveBundle-local material according to
    owning SaveBundle and graph documents.

    The SaveBundle itself is not an ordinary importable Pack.

03.3. Replace SavePack discovery policy
---------------------------------------

Current DA-09 says:

    By default, Turnix does not recurse into SavePack directories.

    By default, Turnix does not discover copied packs inside SavePacks eagerly.

    Deep scanning of SavePack contents occurs only when a SavePack is explicitly
    loaded, a management surface inspects a SavePack, or configuration explicitly
    enables deep save scanning.

Translate this to SaveBundle terminology.

Recommended model:

    By default, Turnix discovers SaveBundle candidates at the defined saves-root
    depth.

    By default, Turnix does not recurse deeply into SaveBundle-local retained or
    copied Pack material.

    Deep scanning of SaveBundle-local Pack material occurs only when:

        - a SaveBundle is explicitly loaded
        - a management surface inspects a SaveBundle
        - configuration explicitly enables deep save scanning

    At that point, copied or retained Pack material may be discovered for
    SaveBundle-local context, but visibility remains limited to that SaveBundle or
    the owning graph context unless another authoritative document states
    otherwise.

03.4. Replace save-local context wording
----------------------------------------

Current DA-09 says save-local pack material is a distinct nearer source context
and precedes ordinary content-root precedence.

The boundary is still important.

Translate it as:

    SaveBundle-local retained or copied Pack material is a distinct nearer source
    context for that SaveBundle/Application context.

    Ordinary content-root precedence does not override SaveBundle-local retained
    or copied Pack material by default.

This preserves the core boundary without treating SaveBundle as a Pack kind.

03.5. SaveBundle listing is not ListPacks filtered by Pack kind
---------------------------------------------------------------

If DA-09 or nearby documents imply SavePack listing is a ListPacks filter, remove
that implication.

Correct model:

    Pack listing remains about Packs.

    SaveBundle listing remains about durable Application persistence closures.

    A SaveBundle-related catalog operation may expose retained/copy/pinned Pack
    material associated with SaveBundles, but the SaveBundle itself is not a Pack
    discovered through ordinary Pack discovery.

==============================================================================
04. MAJOR REQUIRED FIX: OWNER STOP-LINES
==============================================================================

DA-09 should stay the root system and discovery-boundary document.

It may name other domains to preserve stop-lines, but it should not define their
detailed behavior.

04.1. Add or preserve owner mapping
-----------------------------------

Recommended stop-line mapping:

    DA-03 owns trace substrate, trace DAG semantics, trace storage, trace
    retention, and trace loss.

    DA-06 owns configuration semantics and path-config persistence.

    DA-07 owns early-phase I/O limits and built-in-reader-only behavior.

    DA-10 owns Pack identity, hierarchy, indexing, visibility, and visibility
    semantics for retained Pack material.

    DA-11 owns generic PackRequest resolution mechanics, selector resolution, and
    deterministic selection.

    DA-12 owns importing, module loading, and code-boundary rules.

    DA-13 owns dependency semantics, advisory relation semantics, pinned/copied
    field semantics, and provider-role semantics.

    DA-14 owns activation lifecycle and final Activated state.

    DA-16 owns service, capability, permission, and Job-backed capability
    semantics.

    DA-17 owns user decision and remembered policy semantics outside DA-09's
    root/bootstrap model.

    DA-20 owns Application/ApplicationRun lifecycle and runtime identity.

    DA-21 owns RPC, channel, and transport semantics.

    DA-23 owns ExecutionAdapter boundary semantics.

    DA-24 owns OrchestrationUnit and mutation-authority semantics.

    DA-28 owns RuntimeHost workspace ownership and command-surface semantics.

    DA-29 owns PackManager inspection, explanation, graph preparation, validation,
    repair, selected graph management, and PackManager-domain trace semantics.

    DA-30 owns ModCallContext invocation gateway semantics.

    SaveBundle and persistence documents own SaveBundle storage format,
    compatibility, generation, retained material, ownership, and loading details.

04.2. Discovery trace wording
-----------------------------

DA-09 should continue to own discovery-domain trace reason identifiers and trace
emission obligations.

It should not imply DA-09 owns trace schema, trace storage, trace retention, or
trace loss.

Add/keep:

    Discovery trace evidence does not define resolution, visibility, activation,
    import, runtime loading, capability availability, committed state, SaveBundle
    truth, or runtime meaning.

==============================================================================
05. SECONDARY FIXES
==============================================================================

05.1. Pack Manager -> PackManager
---------------------------------

The current document sometimes uses Pack Manager with a space.

Use PackManager when referring to the architecture domain/type, unless the project
explicitly keeps Pack Manager as display wording.

05.2. Import behavior stop-line
-------------------------------

The core concept lists discovery as not deciding runtime loading and capability
authority. It should also consistently include import behavior / module loading.

Discovery does not decide:

    - import behavior
    - module loading

DA-12 owns those.

05.3. Runtime loading wording
-----------------------------

Discovery should not "load runtimes". Prefer:

    Discovery does not activate Packs, import code, run Pack code, select
    ExecutionAdapters, or create ApplicationRuns.

The exact wording depends on local section.

05.4. Trace reason identifiers may remain if stable
---------------------------------------------------

DA-09 defines trace reasons:

    ManifestInRootLayerDir
    SymlinkForbidden
    ScanDepthLimitReached

These do not conflict with P02 and can remain.

If future trace reasons mention SavePack, prefer SaveBundle unless there is a
compatibility reason to keep the old event name.

==============================================================================
06. WHAT TO PRESERVE FROM CURRENT DA-09
==============================================================================

Preserve these boundaries, but rewrite SavePack/AppInstance/PackContext-era terms
where present:

    - Discovery is strict candidate production.
    - Discovery is side-effect-free.
    - Discovery does not decide visibility, enablement, selector resolution,
      dependency satisfaction, activation, import behavior, runtime loading,
      capability authority, PackManager repair, committed-state authority, or
      policy outcomes beyond the root/bootstrap model.
    - Root origin kind describes where a root came from.
    - Root origin kind does not decide later resolution winner by itself.
    - Root categories have separate meanings.
    - custom/first-party/third-party are content categories.
    - userdata/ and saves/ are not content categories.
    - Externally-managed content roots contribute only third-party content unless
      another authoritative document explicitly changes that rule.
    - Externally-managed content-root constraints are provenance and
      safety-hygiene constraints, not a hard adversarial-security guarantee.
    - Candidate, selected, and preferred roots are distinct.
    - Selected roots express explicit user choice for active state categories.
    - Preferred roots are last-used usable operational targets.
    - Selected/preferred mismatches caused by controlled recovery are surfaced to
      the user.
    - userdata has exactly one active root.
    - saves has exactly one active writable root.
    - userdata redirect applies only to userdata and may be followed once.
    - saves does not use redirect semantics.
    - selectedSaves is explicit selected saves root.
    - savesDirectoryRoots are extra candidate hints, not silent jumps.
    - No silent fallthrough if selected saves becomes unusable.
    - Readable old saves may remain visible for loading where possible while new
      writable saves go to the writable root.
    - Root directories are namespaces, not Packs.
    - Manifests directly in category roots are ignored, not fatal.
    - Discovery scanning is manifest-based and deterministic.
    - totalDepth behavior remains as defined.
    - Symlinks are forbidden by default.
    - Discovery produces PackDescriptor objects for discovered Pack candidates.
    - Discovery preserves raw manifest data and provenance.
    - Manifests are whole artifacts; duplicates are selected/shadowed, not merged
      or stacked.
    - Discovery failures are classified and local unless core prerequisites are
      unavailable.
    - Discovery remains compatible with DA-07 early-phase I/O and DA-03 trace
      substrate requirements.
    - PackManager helpfulness must not silently migrate into ordinary discovery.

==============================================================================
07. WHAT TO ADD OR CHANGE IN THE REVISED DA-09
==============================================================================

07.1. Add canonical terminology note
------------------------------------

Add a compact note near the concept or category section:

    DA-09 uses canonical architecture names:

        SaveBundle:
            durable persistence closure of an Application

        Application:
            durable application individual

        ApplicationRun:
            one live execution period of an Application

        ModCallContext:
            invocation-scoped Pack-facing gateway into Turnix

    Older notes may use SavePack, AppInstance, or PackContext. DA-09 does not use
    those names as primary architecture terms unless a compatibility note
    explicitly says so.

Do not write this as "V3 names", "new names", or "after the rewrite".

07.2. Rewrite SavePack-related core concept
-------------------------------------------

Replace the current Pack/SavePack explanation with a SaveBundle-aware split.

Recommended direction:

    Pack remains the general reusable pack/content/application/mod container
    concept.

    SaveBundle is not a Pack. It is the durable persistence closure of an
    Application.

    SaveBundle may retain or copy Pack material and graph evidence, but that
    retained material is SaveBundle-local unless another owning document makes it
    visible elsewhere.

07.3. Rewrite saves/ category meaning
-------------------------------------

Replace:

    saves/ contains SavePacks and related save-context state.

with:

    saves/ contains SaveBundles and related durable Application persistence
    material.

Then define that SaveBundle-local retained Pack material is context-bound.

07.4. Rewrite save discovery policy
-----------------------------------

Translate default and deep scanning sections from SavePack to SaveBundle.

Preserve the lazy behavior:

    - ordinary discovery identifies SaveBundle candidates at the defined saves
      scanning depth
    - ordinary discovery does not eagerly recurse into SaveBundle-local retained
      Pack material
    - deep scanning is explicit through SaveBundle load, PackManager inspection,
      or configuration

07.5. Add DA-20 / DA-29 / DA-30 stop-lines
------------------------------------------

Add DA-20, DA-29, and DA-30 to downstream or stop-line references where useful:

    - DA-20 owns Application/ApplicationRun identity.
    - DA-29 owns PackManager graph preparation and repair.
    - DA-30 owns ModCallContext gateway semantics.

DA-09 should not define those details.

07.6. Keep implementation details open
--------------------------------------

Do not turn DA-09 into:

    - a concrete filesystem watcher spec
    - a concrete path-config persistence spec
    - a concrete SaveBundle format spec
    - a PackManager repair spec
    - a deterministic resolution selector spec
    - an import/module-loading spec
    - an activation spec
    - a capability/permission spec
    - a trace schema/storage spec

==============================================================================
08. SPECIFIC PHRASE REPLACEMENTS
==============================================================================

Use these as a starting pass. Context still matters.

    SavePack
        -> SaveBundle where durable Application persistence closure is meant
        -> SaveBundle-local retained Pack material where copied Pack material is
           meant

    SavePacks are discoverable as save entities
        -> SaveBundles are discoverable as durable Application persistence
           entities

    SavePacks are not eligible for import as normal content-root packs
        -> SaveBundles are not ordinary importable content-root Packs

    Packs copied into a SavePack remain context-bound to that SavePack
        -> Pack material retained or copied into a SaveBundle remains
           SaveBundle-local/context-bound unless another authoritative document
           explicitly states otherwise

    Save-local pack material
        -> SaveBundle-local retained or copied Pack material

    save context
        -> SaveBundle context / SaveBundle binding, depending on exact meaning

    SavePack directories
        -> SaveBundle directories / SaveBundle-local material, depending on exact
           meaning

    copied packs inside SavePacks
        -> retained or copied Pack material inside SaveBundles

    SavePack contents
        -> SaveBundle-local retained/copied material

    SavePack context
        -> SaveBundle/Application context

    SavePack/AppInstance context
        -> SaveBundle/Application context, or ApplicationRun context if live run is
           meant

    PackContext authority
        -> ModCallContext gateway authority

    Pack Manager
        -> PackManager when used as the architecture domain/type name

    Any final-document wording like "In V3, SaveBundle..."
        -> replace with direct architecture language such as "SaveBundle..."

==============================================================================
09. ACCEPTANCE CONDITIONS FOR THE REVISED DA-09
==============================================================================

A revised DA-09 is acceptable when all of the following are true:

    - It preserves discovery as strict, deterministic, side-effect-free candidate
      production.

    - It preserves discovery output as input, not runtime result.

    - It preserves root origin and root category separation.

    - It preserves custom / first-party / third-party / userdata / saves category
      meanings.

    - It preserves selected/preferred/candidate root distinctions.

    - It preserves userdata bootstrap and selected/preferred recovery rules.

    - It preserves saves root resolution and no-silent-switch behavior.

    - It preserves ordinary content-root precedence as input to deterministic
      resolution, not universal runtime authority.

    - It preserves roots as namespaces, not Packs.

    - It preserves manifest-based deterministic scanning.

    - It preserves default symlink refusal.

    - It preserves manifests as whole artifacts and prevents manifest merging.

    - It preserves lazy deep scanning of save-associated retained Pack material.

    - It replaces SavePack as Pack-kind vocabulary with SaveBundle-aware wording.

    - It states that SaveBundle is not a Pack.

    - It describes SaveBundle-local retained/copied Pack material as
      context-bound unless another owning document explicitly says otherwise.

    - It avoids AppInstance and PackContext terminology unless explicitly declared
      as legacy aliases elsewhere.

    - It uses Application / ApplicationRun / SaveBundle / ModCallContext where
      those concepts must be named.

    - It keeps PackManager helpfulness outside ordinary discovery.

    - It keeps PackManager repair and graph preparation DA-29-owned.

    - It keeps Application/ApplicationRun identity DA-20-owned.

    - It keeps ModCallContext semantics DA-30-owned.

    - It keeps importing/module loading DA-12-owned.

    - It keeps activation lifecycle DA-14-owned.

    - It keeps resolution/selector behavior DA-11-owned.

    - It keeps dependency semantics DA-13-owned.

    - It keeps trace schema/storage/retention/loss DA-03-owned.

    - It does not define concrete path-config persistence, filesystem watching,
      SaveBundle format, PackManager repair schema, selector resolution schema,
      activation plan schema, capability permission, or trace storage.

    - It does not mention audit provenance, rewrite process, old/new design, V3,
      Codex, candidate status, or branch history as ordinary architecture text.

==============================================================================
10. FINAL EDITOR INSTRUCTION
==============================================================================

Keep DA-09.

Do not perform a heavy conceptual rewrite.

Do perform a targeted terminology and stop-line rewrite against Proposal P02 and
recent audit results for DA-20, DA-29, and DA-30.

Use REWRITE-DA-09 only as translated boundary-preservation guidance. Do not keep
it as an obsolete historical artifact and do not copy its stale SavePack,
AppInstance, or PackContext vocabulary into the rewritten DA.

Do not include audit/source metadata or version/process framing in the final
DA-09 documentation. The final DA-09 should not say this is V3 design, in V3,
new design, old design, rewritten design, created by Codex, decided by audit, or
part of a rewrite-history process.

DA-09 should remain the root-origin, root-category, candidate-root, bootstrap
path, discovery scanning, discovery output, SaveBundle-related discovery-boundary,
and discovery-domain trace document.

DA-09 should not become:

    - Pack identity and visibility specification
    - generic resolution specification
    - selector parsing specification
    - dependency solving specification
    - importing or module-loading specification
    - activation lifecycle specification
    - ExecutionAdapter specification
    - ModCallContext specification
    - Application/ApplicationRun lifecycle specification
    - SaveBundle storage-format specification
    - PackManager repair or graph-preparation specification
    - capability permission specification
    - concrete trace schema or storage specification
    - concrete filesystem watcher or path-config implementation specification

The main work is to preserve DA-09's strict discovery boundaries while migrating
fully out of the SavePack/AppInstance/PackContext layer into the
SaveBundle/Application/ApplicationRun/ModCallContext terminology where those
concepts must be named.
