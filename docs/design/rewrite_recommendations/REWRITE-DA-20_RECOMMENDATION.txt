SUMMARY
=======

DA-20 is Dv3-compatible, but it currently narrows AppInstance meaning.

No heavy rewrite is recommended before the AppPack-backing decision is made.

DA-20 currently defines:

    AppInstance is a live runtime instance of one AppPack.

and:

    An AppInstance has exactly one active AppPack identity.

This may be correct if Dv3 chooses the model where every AppInstance is
formally AppPack-backed, including embedded, scripted, test, and internal usage
through synthetic or internal AppPacks.

This is not yet safe to preserve as universal doctrine if the broader Dv3 thesis
remains:

    Turnix runs AppInstances.
    AppPack is one declarative way to create an AppInstance.
    AppPack may be absent in embedded/scripted/test usage.

Current required source-level changes:

    1. Resolve AppPack-backing scope.

    2. Replace "durable executed state" with "durable AppInstance state."

    3. Add or preserve a compact AppInstance lifecycle stop-line.

    4. Add DA-05 / DA-06 / DA-25 / DA-26 stop-lines where save context,
       committed values, configuration, retained evidence, artifacts, export,
       comparison, Replay, Resume, Retry, or audit workflows are mentioned.

    5. Clarify AppInstance "resumed" and "retried" wording so it does not imply
       DA-26 Resume or Retry semantics unless explicitly routed through DA-26.

Overall recommendation:

    KEEP WITH REQUIRED APPPACK-BACKING DECISION / SAVEPACK /
    DA-26 WORDING WATCH

ACTUAL DA-20 CHANGE 0: RESOLVE APPPACK-BACKING SCOPE
====================================================

DA-20 currently says:

    AppInstance is a live runtime instance of one AppPack.

and:

    An AppInstance has exactly one active AppPack identity.

This narrows the broader Dv3 thesis that:

    Turnix runs AppInstances.
    AppPack is one declarative way to create an AppInstance.
    AppPack may be absent in embedded/scripted/test usage.

Future rewrite must explicitly choose one model.

Model A:

    All AppInstances are formally AppPack-backed.

    Embedded, scripted, test, and internal usage create synthetic or internal
    AppPacks before AppInstance creation.

    In this model, DA-20's one-AppPack rule is correct and should be kept.

Model B:

    AppPack-backed AppInstances are the normal product-facing path, but not the
    only possible AppInstance creation path.

    In this model, DA-20 must be rewritten so the generic AppInstance concept is
    not defined as necessarily AppPack-backed.

Recommended current audit stance:

    Do not silently preserve the one-AppPack rule as universal until this
    architecture decision is made.

    Preserve the broader invariant:

        Turnix runs AppInstances.

    Preserve the narrower DA-20 rule only as the current AppPack-backed
    AppInstance lifecycle model.

If Model A is chosen, DA-20 should say how embedded/scripted/test usage is
represented, for example by synthetic or internal AppPacks.

If Model B is chosen, DA-20 should distinguish generic AppInstance lifecycle
from AppPack-backed AppInstance lifecycle.


ACTUAL DA-20 CHANGE 1: SAVEPACK WORDING SHOULD BE UPDATED
=========================================================

DA-20 currently says:

    SavePack stores durable executed state for an AppPack.

Recommended future rewrite:

    SavePack stores durable AppInstance state for an AppPack.

Reason:

    "Executed state" is too narrow and can imply that SavePack is only the
    result of past execution.

    "Durable AppInstance state" better matches the current Dv3 model.

Preserve the underlying boundary:

    SavePack identity is not AppInstance identity.

    Binding a SavePack to an AppInstance does not make adapter-executed code a
    SavePack writer.

    SavePack mutation occurs only through Kernel-mediated state and persistence
    authority.

    Authoritative mutation remains governed by DA-04.

    Committed value representation remains governed by DA-05.

    Configuration semantics remain governed by DA-06.

    Persistent I/O remains governed by DA-07.

    Window and retained evidence behavior remains governed by DA-08.

Do not expand DA-20 into detailed SavePack persistence, representation,
configuration, Window artifact, or Replay / Resume / Retry semantics.


ACTUAL DA-20 CHANGE 2: APPINSTANCE LIFECYCLE STOP-LINE
======================================================

DA-20 should contain a compact source-level boundary statement.

Recommended source-level boundary:

    AppInstance lifecycle identifies and bounds a live runtime instance.

    In the current DA-20 source model, that runtime instance is AppPack-backed.

    AppInstance lifecycle does not by itself define pack activation outcome,
    adapter lifecycle outcome, RPC transport outcome, Job terminal outcome,
    OrchestrationUnit terminal outcome, Window finalization, RuntimeHost
    lifecycle outcome, PackManager operation outcome, artifact/export
    authority, comparison result, Replay outcome, Resume outcome, Retry outcome,
    audit-workflow outcome, or committed-state truth.

    When AppInstance lifecycle events affect another domain, the owning domain
    defines the resulting outcome.

    Correlation between AppInstance lifecycle and another domain outcome must be
    explicit.

This belongs in DA-20 because DA-20 owns AppInstance lifecycle and runtime
identity.

Detailed ownership mapping belongs in the guardrail section, not in the source
document.

DA-20 says ending an AppInstance does not by itself define whether related work

    resumed

This is directionally correct, but DA-26 now gives Resume and Retry formal

Recommended future rewrite:

PRESERVATION RULE 1: APPINSTANCE IS RUNTIME IDENTITY
====================================================

Preserve AppInstance as runtime identity, not pack identity.

Current DA-20 source models AppInstance as a live runtime instance of one
AppPack.

Do not treat that as universally settled until ACTUAL DA-20 CHANGE 0 is
resolved.

Always preserve:

    Turnix runs AppInstances.

    AppInstance identity is distinct from AppPack identity.

    AppInstance lifecycle provides the runtime container boundary in which
    activation, state mutation, Windows, capabilities, Views, adapters,
    debugging, tracing, OrchestrationUnits, and Jobs may occur.

Do not rewrite AppInstance as:

    - AppPack
    - SavePack
    - RuntimeHost
    - View
    - adapter
    - Job
    - OrchestrationUnit
    - activation graph
    - selected graph
    - committed state
    - payload representation
    - configuration
    - Window
    - export
    - Replay / Resume / Retry workflow
    - persistence record only

If the one-AppPack model is kept, define how embedded/scripted/test usage is
represented, for example by synthetic or internal AppPacks.

If the broader model is kept, define AppPack-backed AppInstance as one creation
path rather than the whole AppInstance concept.


PRESERVATION RULE 2: APPINSTANCE IDENTITY IS DISTINCT
=====================================================

Preserve appInstanceId semantics.

appInstanceId identifies one AppInstance.

appInstanceId is stable for the lifetime of that AppInstance.

appInstanceId is not reused for a different AppInstance during the same kernel
run.

appInstanceId is the correlation identity used by AppInstance-owned trace
evidence.

appInstanceId does not identify:

    - AppPack by itself
    - SavePack by itself
    - View by itself
    - execution adapter by itself
    - Job by itself
    - OrchestrationUnit by itself
    - RuntimeHost by itself
    - workspace by itself
    - Window by itself
    - artifact/export by itself
    - Replay / Resume / Retry workflow by itself

An AppInstance record may include enough context to relate:

    - appInstanceId
    - active AppPack identity, when the AppInstance is AppPack-backed
    - active SavePack or save identity when applicable
    - RuntimeHost identity when such identity is defined
    - workspace identity when such identity is defined

RuntimeHost identity and workspace identity remain owned by DA-28.


PRESERVATION RULE 3: APPPACK BINDING MUST BE EXPLICIT
=====================================================

Preserve explicit AppPack binding for AppPack-backed AppInstances.

Current DA-20 source says:

    An AppInstance has exactly one active AppPack identity.

This should be preserved only if Dv3 intentionally chooses the model where all
AppInstances are AppPack-backed.

If Dv3 keeps embedded/scripted/test AppInstances without AppPack identity, this
section must be rewritten to distinguish:

    - AppPack-backed AppInstance
    - non-AppPack-backed AppInstance, if supported

In either model:

    AppInstance creation must not reopen AppPack resolution silently.

    Loading a different AppPack must not silently mutate an existing
    AppInstance into a different application identity.

    AppInstance runtime behavior must remain constrained by the selected
    creation source, resolved graph, policy, and authority boundaries.

If the one-AppPack model is kept:

    An AppInstance has exactly one active AppPack identity.

    The active AppPack identity identifies the executable application pack whose
    runtime instance is represented by the AppInstance.

    An AppInstance is not itself a Pack.

    An AppInstance does not change AppPack identity during its lifetime.

    Loading a different AppPack creates a different AppInstance.

    Pack discovery and resolution choose the AppPack identity before
    AppInstance creation.

    AppPack dependency resolution remains owned by the pack and resolution
    documents.

If the broader model is kept:

    AppPack identity becomes required only for AppPack-backed AppInstances.

    DA-20 must define how non-AppPack-backed AppInstances identify their
    creation source without pretending they are AppPacks.

    Non-AppPack-backed creation paths must still be Kernel-mediated and must not
    bypass authority, policy, trace, transaction, or persistence boundaries.


PRESERVATION RULE 4: SAVE CONTEXT IS OPTIONAL AND DISTINCT
==========================================================

Preserve SavePack/save context separation.

An AppInstance may have one active SavePack identity when running from or
against a durable save context.

Absence of active SavePack identity means no durable save context is bound.

Absence of active SavePack identity does not invalidate the AppInstance
identity.

Active save context identifies the save scope against which committed state,
configuration, Windows, retained evidence, and save-local material are
interpreted.

SavePack identity is not AppInstance identity.

AppInstance identity is not SavePack identity.

Save-local pack material remains constrained by pack and save-scope documents.

DA-05 still owns committed payload representation.

DA-06 still owns configuration semantics.

DA-07 still owns persistent I/O authority.

DA-08 still owns Window semantics.

DA-25 still owns artifact/export semantics.

DA-26 still owns comparison, Replay, Resume, Retry, and audit workflow
semantics.


PRESERVATION RULE 5: CREATION PATHS ARE KERNEL-MEDIATED
=======================================================

Preserve AppInstance creation path rules.

Current DA-20 source says AppInstance creation begins only after an AppPack
identity has been resolved.

This is correct for AppPack-backed AppInstance creation.

If Dv3 keeps only AppPack-backed AppInstances, preserve that rule as universal.

If Dv3 keeps non-AppPack-backed AppInstances, rewrite this rule so it applies to
AppPack-backed creation only, and define the non-AppPack-backed creation source
without bypassing Kernel mediation.

Current DA-20 source defines two primary save-related creation paths:

    - new save path
    - existing save path

New save path means Turnix creates a new SavePack or save context for the
resolved AppPack before or as part of AppInstance creation.

Existing save path means Turnix loads an existing compatible SavePack or save
context for the resolved AppPack before or as part of AppInstance creation.

If non-AppPack-backed AppInstances remain possible, DA-20 must define whether
these save paths apply only to AppPack-backed AppInstances or whether equivalent
save-context creation paths exist for other AppInstance creation modes.

Save generation behavior is AppPack-provided executable behavior when the
creation path is AppPack-backed.

Save generation behavior remains subject to:

    - activation boundaries
    - adapter boundaries
    - capability boundaries
    - OrchestrationUnit boundaries when mutation authority is involved
    - policy boundaries
    - persistence boundaries
    - DA-04 committed-state rules
    - DA-05 committed-value representation when committed values are produced
    - DA-06 configuration semantics when configuration is produced
    - DA-07 persistence authority
    - DA-08 Window semantics where Window material is produced

Existing save path validates compatibility between resolved AppPack and selected
SavePack/save context.

Compatibility validation failure prevents AppInstance creation unless explicit
migration, override, or recovery policy permits another path.

AppInstance creation failure is explicit and trace-visible.

AppInstance creation failure does not create a partially valid AppInstance.

RuntimeHost startup modes and command surfaces use DA-20 AppInstance creation
paths rather than defining separate creation semantics.

DA-28 owns the RuntimeHost rule that all entry surfaces use the same
Kernel-mediated save creation and save loading paths.


PRESERVATION RULE 6: WRITABLE SAVEPACK IS SINGLE-WRITER
=======================================================

Preserve writable SavePack ownership.

A writable SavePack is owned by at most one running AppInstance at a time.

Writable SavePack ownership prevents silent multi-writer mutation of durable
AppInstance state.

A second AppInstance does not silently acquire writable ownership of the same
SavePack.

A second RuntimeHost does not silently acquire writable ownership of the same
workspace or SavePack.

RuntimeHost workspace ownership semantics are defined by DA-28.

Read-only inspection of a SavePack may be allowed by explicit tooling, audit,
export, or policy rules.

Read-only inspection does not create writable ownership.

Multi-writer SavePack behavior is not defined by DA-20.

Any future multi-writer mode requires an explicit authoritative design defining:

    - conflict handling
    - transaction boundaries
    - persistence ordering
    - recovery semantics

Concrete workspace locking and writable ownership implementation remain open,
but that does not weaken the single-writer semantic rule.


PRESERVATION RULE 7: APPINSTANCE LIFECYCLE DOES NOT DEFINE OTHER OUTCOMES
=========================================================================

Preserve lifecycle separation.

AppInstance lifecycle phases may include:

    - requested
    - creating
    - save binding
    - starting
    - active
    - stopping
    - stopped
    - failed
    - crashed
    - closed

Lifecycle phase names do not define:

    - Job terminal outcomes
    - OrchestrationUnit terminal outcomes
    - Window finalization outcomes
    - adapter lifecycle outcomes
    - RuntimeHost lifecycle outcomes
    - PackManager operation outcomes
    - artifact/export authority
    - comparison outcomes
    - Replay / Resume / Retry workflow outcomes
    - committed-state truth

An AppInstance active region is the bounded runtime interval during which an
AppInstance is active.

At most one active region exists for one AppInstance at a time.

Ending an AppInstance active region does not by itself define whether in-flight
work:

    - committed
    - aborted
    - was cancelled
    - was superseded
    - detached
    - retained a result
    - finalized a Window
    - created an artifact or export
    - entered DA-26 Replay
    - entered DA-26 Resume
    - entered DA-26 Retry

Window finalization semantics are defined by DA-08.

Artifact/export semantics are defined by DA-25.

Replay, Resume, Retry, comparison, and audit workflow semantics are defined by
DA-26.

Pack activation failure semantics are defined by DA-14.

Job lifecycle semantics are defined by DA-19.

OrchestrationUnit lifecycle semantics are defined by DA-24.

Adapter lifecycle semantics are defined by DA-23 / DA-27.

RuntimeHost lifecycle semantics are defined by DA-28.


PRESERVATION RULE 8: APPINSTANCE LIFECYCLE IS NOT PACK ACTIVATION
=================================================================

Preserve activation separation.

Pack activation occurs inside or in relation to an AppInstance active region.

AppInstance creation does not by itself activate every pack.

AppInstance activation of the AppPack and runtime participants remains governed
by DA-14 when the AppInstance is AppPack-backed.

AppInstance lifecycle is not pack activation lifecycle.

Pack activation success does not by itself mean AppInstance shutdown will
succeed.

Pack activation failure may cause AppInstance start failure when the failed
activation is required for the AppInstance to become active.

NotActivatedError remains an activation-domain outcome under DA-14.

AppInstance lifecycle evidence may causally link to activation trace evidence
when activation affects AppInstance lifecycle.

If non-AppPack-backed AppInstances remain possible, their executable
participation must still have an explicit activation/execution-authority model
or must explicitly state that no pack activation path is involved.


PRESERVATION RULE 9: PARTICIPANTS DO NOT OWN APPINSTANCE
========================================================

Preserve participant separation.

Adapters:

    - may attach to or participate in an AppInstance
    - do not become the AppInstance
    - have identity distinct from AppInstance identity
    - have lifecycle distinct from AppInstance lifecycle
    - do not own AppInstance state
    - request AppInstance state mutation only through Kernel-mediated boundaries

Adapter readiness does not imply AppInstance readiness.

Adapter failure does not automatically stop the AppInstance.

Views and frontend clients:

    - may present or control one AppInstance when View class and policy permit
    - have identity distinct from AppInstance identity
    - disconnect does not automatically stop an AppInstance

RPC and transports:

    - may target or originate from participants associated with an AppInstance
    - have message/channel identity distinct from appInstanceId
    - have lifecycle distinct from AppInstance lifecycle
    - disconnect or timeout does not automatically stop or fail an AppInstance

Jobs:

    - may execute inside or in relation to an AppInstance active region
    - have jobId distinct from appInstanceId
    - have lifecycle distinct from AppInstance lifecycle
    - terminal outcome does not automatically stop an AppInstance
    - AppInstance stop does not automatically define Job terminal outcome

OrchestrationUnits:

    - may own or coordinate mutation flow inside an AppInstance active region
    - have orchestrationUnitId distinct from appInstanceId
    - have lifecycle distinct from AppInstance lifecycle
    - terminal outcome does not automatically stop an AppInstance
    - AppInstance stop does not automatically define OrchestrationUnit terminal
      outcome


PRESERVATION RULE 10: RUNTIMEHOST AND PACKMANAGER DO NOT OWN APPINSTANCE IDENTITY
================================================================================

Preserve RuntimeHost / PackManager / AppInstance separation.

RuntimeHost may host zero, one, or multiple AppInstances.

RuntimeHost identity is not AppInstance identity.

RuntimeHost startup modes and command surfaces may request AppInstance
creation, loading, stopping, or inspection through Kernel-mediated paths.

RuntimeHost command acceptance does not itself create a valid AppInstance.

RuntimeHost operation success is not AppInstance lifecycle success by default.

PackManager may inspect, present, prepare, validate, repair, modify, or explain
pack catalogs and selected pack graph intent.

PackManager graph preparation does not create an AppInstance by itself.

PackManager repair suggestions do not mutate AppInstance state by themselves.

PackManager-triggered work must still use the AppInstance creation, lifecycle,
policy, transaction, and persistence boundaries owned by the relevant documents.


PRESERVATION RULE 11: APPINSTANCE TRACE IS CORRELATION, NOT REPLACEMENT
=======================================================================

Preserve AppInstance trace ownership.

DA-20 owns AppInstance-domain trace reasons used for:

    - AppInstance lifecycle
    - active-region span boundaries

AppInstance trace evidence may record context such as:

    - appInstanceId
    - active AppPack identity when applicable
    - active SavePack or save identity when applicable
    - creation request identity when applicable
    - RuntimeHost identity when applicable
    - workspace identity when applicable
    - active region span identity when applicable
    - viewId when applicable
    - adapter identity when applicable
    - RPC message identity when applicable
    - jobId when applicable
    - orchestrationUnitId when applicable
    - failure reason category
    - stop reason category
    - crash reason category

AppInstance trace evidence does not replace:

    - activation trace evidence
    - adapter trace evidence
    - RPC trace evidence
    - Job trace evidence
    - OrchestrationUnit trace evidence
    - Window finalization evidence
    - RuntimeHost trace evidence
    - PackManager trace evidence
    - artifact/export trace evidence
    - Replay / Resume / Retry workflow trace evidence
    - committed-state trace evidence

DA-03 owns the trace substrate, not AppInstance lifecycle semantics.

Trace wording should follow the DA-03 cross-document trace wording check.

WATCH ITEM: SAVEPACK TERMINOLOGY
================================

Replace "durable executed state" with "durable AppInstance state" unless a

Use the replacement carefully:

    It should not imply SavePack is AppInstance identity.

    It should not imply SavePack owns runtime lifecycle.

WATCH ITEM: RESTART / RETAINED-RESULT / RESUME / RETRY SEMANTICS
================================================================

DA-20 leaves exact AppInstance restart semantics and retained-result behavior
when clients disconnect open.

Future rewrite should preserve:

    - AppInstance restart is not Job retry by default
    - AppInstance restart is not DA-26 Retry by default
    - AppInstance restart is not DA-26 Resume by default
    - AppInstance restart is not reuse of appInstanceId unless explicitly
      defined
    - retained results are not committed state merely because they are retained
    - frontend/RPC disconnect does not automatically stop AppInstance or discard
      results
    - Job retained-result semantics remain DA-19 / DA-17 / workflow-owned
    - DA-26 owns Replay, Resume, Retry, and related audit workflow semantics


WATCH ITEM: CREATION FAILURE AND RECOVERY POLICY
================================================

Compatibility validation failure prevents AppInstance creation unless explicit
migration, override, or recovery policy permits another path.

Future edits should preserve:

    - no partially valid AppInstance after creation failure
    - migration that changes authoritative committed state remains governed by
      DA-04 and DA-06
    - recovery decisions remain governed by DA-17
    - RuntimeHost startup modes and command surfaces do not define separate
      creation semantics

    DA-19 owns Job lifecycle, timeout, cancellation, progress, result, and
    terminal outcome semantics.

    DA-21 owns RPC, channel, transport, timeout, disconnect, and cancellation
    message semantics.

    DA-22 owns UI, View, and frontend runtime semantics.

    DA-23 owns abstract execution adapter authority boundaries.

    DA-24 owns OrchestrationUnit lifecycle, mutation authority, and terminal
    outcome semantics.

    DA-25 owns Window artifacts, WindowManifests, WindowExports, Minimal Audit
    Bundles, optional digest representation, partial export, missing material,
    and offline inspection artifact semantics.

    DA-26 owns ComparisonResult, equality modes, Replay, Resume, Retry, and
    audit workflow semantics.

    DA-27 owns adapter lifecycle, trust, isolation, failure, disconnect, and
    adapter-domain trace semantics.

    DA-28 owns RuntimeHost lifecycle, startup mode, command surface, workspace
    ownership, local-first, and LAN exposure semantics.

    DA-29 owns PackManager catalog, graph-preparation, repair, View, write, and
    PackManager-domain trace semantics.

Local rewrite rule:

    DA-20 may name these concepts when needed to protect AppInstance lifecycle
    and runtime identity boundaries.

    DA-20 should not define their detailed behavior.

    DA-20 should remain the AppInstance lifecycle, runtime identity,
    save-context binding, writable SavePack ownership, AppInstance creation,
    active-region, participant-separation, and AppInstance-domain trace
    document.

    AppPack binding remains part of DA-20, but its universal scope must be
    decided before preserving the one-AppPack rule as final doctrine.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-20.

No heavy rewrite is recommended before the AppPack-backing decision is made.

Required future edit:

    - resolve whether all AppInstances are formally AppPack-backed, or whether
      AppPack-backed AppInstances are one creation path among others

Recommended future edits:

    - replace "durable executed state" with "durable AppInstance state"
    - add DA-05, DA-06, DA-25, and DA-26 stop-lines where needed
    - clarify AppInstance "resumed" / "retried" wording so it does not imply
      DA-26 Resume / Retry semantics
    - keep DA-20 focused on AppInstance lifecycle and runtime identity
    - preserve AppInstance/AppPack/SavePack/RuntimeHost identity separation
    - preserve optional save context and single-writer writable SavePack rule
    - preserve shared Kernel-mediated AppInstance creation paths across
      RuntimeHost startup modes and command surfaces
    - preserve lifecycle separation from activation, adapters, Views, RPC,
      Jobs, OrchestrationUnits, Windows, RuntimeHost, PackManager,
      artifact/export, Replay, Resume, Retry, comparison, audit workflows, and
      committed state
    - leave exact appInstanceId, restart, retained-result, SavePack generator,
      compatibility-validation, non-AppPack-backed creation if accepted, and
      implementation substate details to later implementation specifications
