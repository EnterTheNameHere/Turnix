SUMMARY
=======

DA-23 is strong and highly Dv3-compatible.

No heavy rewrite is recommended.

DA-23 defines the abstract execution-boundary authority model for declared pack
code and ExecutionAdapters.

It defines how Turnix executes declared pack code across host languages and
runtime environments without allowing host-language convenience, process
location, transport choice, RuntimeHost entry surfaces, or frontend convenience
to bypass Kernel authority.

DA-23 should preserve this core boundary:

    Kernel owns authority.

    ExecutionAdapters execute declared pack code.

    Transports carry messages.

    RPC defines the logical communication boundary.

    Capabilities define what adapter-executed code may do.

    RuntimeHost exposes controlled entry surfaces under DA-28.

    Pack code participates only through Turnix-managed context, capability,
    RPC-shaped, lifecycle, policy, trace, and state boundaries.

Required or likely future cleanup:

    1. SavePack wording:
        Current DA-23 text uses older "durable executed state" / "persisted
        executed state for an AppPack" wording.

    2. FrontendAdapter terminology:
        Keep ExecutionAdapter as the umbrella term.
        Treat frontend/browser adapter as a specific UI-facing realization or
        subtype.

    3. Trace wording:
        Follow the DA-03 cross-document trace wording check.

Rewrite-boundary guardrails:

    DA-23 owns the abstract execution-boundary authority model.

    DA-23 should not absorb detailed generic resolution, importing, activation
    lifecycle, capability permission, policy decision, Job lifecycle,
    AppInstance lifecycle, RPC, UI/View, OrchestrationUnit lifecycle,
    adapter lifecycle/trust/isolation, RuntimeHost command-surface, concrete
    RPC schema, concrete WebSocket, concrete adapter implementation, concrete
    JavaScript loader, concrete CLI syntax, or concrete workspace locking
    semantics.

    Those details belong to their subject-owning documents.

Overall recommendation:

    KEEP WITH SMALL TERMINOLOGY / SAVEPACK WORDING WATCH

WATCH ITEM 1: SAVEPACK WORDING
===============================

Current DA-23 wording uses older phrases:

    SavePack stores durable executed state.

    SavePack stores persisted executed state for an AppPack.

Do not patch this independently yet.

Pending DA-20 / SavePack / AppInstance audit, likely better wording may become:

    SavePack stores durable AppInstance state.

or:

    SavePack stores persisted state for a concrete AppInstance.

Recommendation:

    Revisit after DA-20 / SavePack / AppInstance documents are audited.

    If DA-01 or DA-02 SavePack terminology changes first, mirror the terminology
    here.


WATCH ITEM 2: FRONTENDADAPTER TERMINOLOGY
=========================================

Preserve ExecutionAdapter as the umbrella term.

Treat frontend/browser adapter as a specific UI-facing ExecutionAdapter
realization or subtype.

Do not use FrontendAdapter as the general execution-boundary concept.

Reason:

    DA-23 owns the abstract execution-boundary model.

    Browser/frontend behavior is only one adapter realization.


WATCH ITEM 3: TRACE WORDING
===========================

DA-23 uses trace-visible and adapter/direct-call trace wording.

This should follow the DA-03 cross-document trace wording check.

Correct reading:

    Adapter-domain and direct-call trace evidence is a domain emission
    obligation where applicable.

    Trace retention and loss remain governed by DA-03.

    Adapter trace evidence does not become committed-state authority.

    Direct-call trace visibility does not imply trace persistence is guaranteed.

Recommendation:

    Do not repeat full DA-03 trace doctrine in DA-23.

    Keep only DA-23-specific trace obligations and cross-domain causal links.


PRESERVATION RULE 1: KERNEL AUTHORITY IS NOT IMPLIED BY EXECUTION LOCATION
=========================================================================

Preserve DA-23's Kernel authority boundary.

Kernel authority is not delegated merely because:

    - code runs in the same process
    - code runs in the same language
    - a transport is in-process
    - a frontend can send a message
    - a RuntimeHost entry surface can send a command
    - a pack declares code

Kernel may expose authority through capabilities, policies, and
Turnix-controlled contexts.

Exposed authority remains scoped by the capability, policy, context,
AppInstance, SavePack, RuntimeHost, and lifecycle boundaries that grant it.


PRESERVATION RULE 2: EXECUTIONADAPTER IS A BOUNDARY PARTICIPANT, NOT AUTHORITY
==============================================================================

Preserve ExecutionAdapter as the abstract boundary concept.

An ExecutionAdapter is a Turnix-managed environment capable of loading and
executing declared pack code.

An ExecutionAdapter is a boundary participant, not authority by itself.

An ExecutionAdapter may run code:

    - in the browser
    - in the backend process
    - in another process
    - over a local socket or pipe
    - over a LAN transport
    - inside a container or virtual machine
    - through another explicitly defined runtime environment

Execution location does not define authority.

RuntimeHost deployment location does not define adapter authority.

Adapter mediation does not imply sandboxing.

Adapter sandboxing, trust classification, lifecycle, concrete adapter classes,
and adapter trace reason ownership belong to DA-27.

RuntimeHost identity, workspace ownership, startup modes, entry surfaces, and
command-surface semantics belong to DA-28.


PRESERVATION RULE 3: CODE ARTIFACT PHASES STAY SEPARATE
=======================================================

Preserve the executable code phase model.

Executable code handling is separated into:

    - recognition
    - declaration
    - binding
    - permission
    - activation
    - execution

No phase silently implies a later phase.

Recognition does not imply declaration.

Declaration does not imply binding success.

Binding does not imply execution permission.

Permission does not imply activation success.

Activation dispatch does not imply execution success.

Execution success does not imply committed-state mutation.

Execution success does not imply RuntimeHost command acceptance, RuntimeHost
operation success, or workspace ownership change.


PRESERVATION RULE 4: DECLARATION DOES NOT GRANT AUTHORITY
=========================================================

Preserve declared executable artifact rules.

A pack does not execute code merely because a file with a recognized extension
exists.

Executable artifacts are declared explicitly.

Declaration does not grant:

    - capability permission
    - persistent I/O authority
    - committed-state mutation authority
    - RuntimeHost command-surface authority

Declared executable code remains subject to adapter binding, permission,
activation, capability, and policy checks.


PRESERVATION RULE 5: PACK CODE IS NOT BACKEND IMPLEMENTATION CODE
=================================================================

Preserve same-language and same-process authority doctrine.

Backend implementation code is trusted platform implementation code.

Pack-provided code is content supplied by packs.

Pack-provided code is not backend implementation code merely because:

    - it is written in the backend implementation language
    - it runs in the backend process

Pack-provided code is not frontend authority merely because it runs in the
browser.

Pack-provided code is not RuntimeHost authority merely because it runs inside a
RuntimeHost-owned process or entry surface.

Pack-provided code receives controlled participation through:

    - PackContext
    - capability calls
    - RPC-shaped messages
    - declared lifecycle entrypoints

Pack-provided code does not:

    - import backend internals as an authority path
    - directly mutate Kernel-owned authoritative state
    - directly write SavePack state as an authority path
    - bypass tracing, policy, capability, permission, lifecycle, or transaction
      boundaries through native language convenience
    - bypass RuntimeHost workspace ownership, startup-mode, entry-surface, or
      command-surface boundaries through native language convenience

Any allowed same-process or same-language integration remains a
Turnix-controlled boundary, not a backend authority grant.


PRESERVATION RULE 6: PACKCONTEXT IS SCOPED PARTICIPATION
========================================================

Preserve the PackContext model.

PackContext is the Turnix-controlled context object or context interface
provided to adapter-executed pack code.

PackContext exposes scoped participation in Turnix.

PackContext may expose:

    - pack identity
    - AppInstance identity when applicable
    - View identity when applicable
    - RuntimeHost identity when applicable and permitted
    - capability call surfaces
    - event or request surfaces
    - state access surfaces when allowed
    - logging or trace correlation helpers
    - cancellation or lifecycle helpers when allowed

PackContext does not expose:

    - general backend internals
    - unrestricted filesystem authority
    - unrestricted committed-state mutation
    - unrestricted capability invocation
    - unrestricted RuntimeHost control authority

PackContext is scoped to the pack, adapter, AppInstance, RuntimeHost,
lifecycle, permission, and policy context that created it.

PackContext authority does not outlive the lifecycle boundary that created it
unless an explicit retained handle model is defined.

Host-language representation differences do not change PackContext authority
meaning.


PRESERVATION RULE 7: RPC-SHAPED DOES NOT MEAN WEBSOCKET OR NETWORK
===================================================================

Preserve the RPC-shaped execution boundary.

Adapter-executed code communicates with Kernel authority through an RPC-shaped
boundary.

RPC-shaped boundary means the interaction preserves:

    - message or call envelope semantics
    - route or capability target identity
    - permission checks
    - lifecycle ownership
    - trace correlation
    - structured result, error, cancellation, and readiness reporting
    - AppInstance and SavePack state authority boundaries
    - RuntimeHost entry-surface and command-surface authority boundaries when
      host-level behavior is targeted

RPC-shaped boundary is not equivalent to WebSocket.

RPC-shaped boundary is not necessarily networked.

It may be implemented by in-process call, local queue, WebSocket, stdio, local
socket, named pipe, TCP socket, postMessage, or another explicitly defined
transport.

Concrete transport does not define authority.


PRESERVATION RULE 8: DIRECT-CALL OPTIMIZATION DOES NOT BYPASS AUTHORITY
=======================================================================

Preserve direct-call optimization boundaries.

Direct in-process calls may implement transport or dispatch optimization.

Direct in-process calls do not bypass the RPC-shaped authority boundary.

A direct call remains valid only when it preserves:

    - route or capability target identity
    - permission checks
    - lifecycle ownership
    - trace correlation
    - structured result and error handling
    - OrchestrationUnit boundaries when mutation or lifecycle authority is
      involved
    - transaction and commit boundaries when state mutation occurs
    - AppInstance and SavePack state authority
    - RuntimeHost authority boundaries when host-level behavior is involved

A direct call that bypasses those requirements is backend implementation
behavior, not pack-code authority.

Pack-provided code does not acquire direct-call authority merely because a
direct-call implementation path exists.

Direct-call optimization must remain explainable and trace-visible where the
equivalent message-shaped path would be trace-visible.

Trace wording should follow the DA-03 cross-document trace wording check.


PRESERVATION RULE 9: TRANSPORT DOES NOT DEFINE EXECUTION AUTHORITY
==================================================================

Preserve the DA-21 / DA-23 transport split.

Transport is the concrete mechanism carrying messages or call envelopes.

Transport may be local, remote, in-process, process-boundary, browser-boundary,
or networked.

Transport does not define authority.

Transport does not grant:

    - capability permission
    - adapter execution authorization

Transport does not define:

    - AppInstance lifecycle
    - RuntimeHost lifecycle
    - Job lifecycle

Transport failure does not by itself define adapter failure.

Adapter failure does not by itself define transport failure.

Transport timeout does not by itself define Job timeout, adapter timeout, or
RuntimeHost timeout.


PRESERVATION RULE 10: ADAPTER-EXECUTED CODE DOES NOT OWN APPINSTANCE, SAVEPACK, OR RUNTIMEHOST
==============================================================================================

Preserve AppInstance / SavePack / RuntimeHost authority boundaries.

Adapter-executed code participates in an AppInstance through the Kernel-owned
authority model.

Adapter-executed code does not own the AppInstance merely because it runs
application logic.

Adapter-executed code does not own the SavePack merely because its work affects
persisted state.

Adapter-executed code does not own the RuntimeHost merely because it runs inside
a RuntimeHost-bound process, adapter, View, or entry surface.

SavePack persistence remains under Kernel-owned persistence authority.

A writable SavePack is not written through adapter-owned state authority.


PRESERVATION RULE 11: ACTIVATION DISPATCH IS NOT LATER AUTHORITY
================================================================

Preserve activation boundaries.

Activation lifecycle semantics are defined by DA-14.

Activation dispatch through an adapter is one activation mechanism.

Activation dispatch does not imply activation success.

Adapter artifact loading does not imply activation success.

Adapter readiness does not imply activation success.

Activation success does not imply:

    - committed-state mutation
    - unrestricted capability permission
    - RuntimeHost command acceptance
    - RuntimeHost operation success


PRESERVATION RULE 12: NATIVE IMPORTS CANNOT BYPASS TURNIX SEMANTICS
===================================================================

Preserve import/module-loading boundaries.

Importing and module-loading semantics are defined by DA-12.

Native language imports cannot bypass Turnix semantics.

Python pack code does not import backend internals as an authority path.

JavaScript pack code does not bypass Turnix resolution, visibility, activation,
or capability boundaries through native or arbitrary loading mechanisms.

turnixImport-style mechanisms remain Turnix-controlled loading surfaces where
JavaScript pack code needs cross-pack access.

A successful native import does not imply:

    - Turnix permission
    - activation
    - state authority
    - capability permission
    - RuntimeHost command authority


PRESERVATION RULE 13: CAPABILITY PERMISSION REMAINS KERNEL-MEDIATED
===================================================================

Preserve DA-16 / DA-23 capability boundaries.

Adapter-executed code receives no general backend access.

Adapter-executed code receives capability-scoped access through its
Turnix-controlled context.

Capability permission is checked by Kernel-owned authority paths.

Adapter identity may participate in permission decisions when the governing
permission model defines such participation.

Adapter identity, pack identity, transport identity, and RuntimeHost identity do
not grant permission by themselves.

Capability invocation that mutates state remains constrained by DA-04 and
DA-24.

Capability invocation through RPC remains constrained by DA-21.

Capability invocation that targets RuntimeHost behavior remains constrained by
DA-28.


PRESERVATION RULE 14: POLICY DECISIONS DO NOT BROADEN THEMSELVES
================================================================

Preserve DA-17 dependency.

Execution authorization may require policy evaluation or user decision.

Trust decisions for unsafe or unsandboxed adapter execution are policy-scoped
decisions.

A policy decision authorizes only the scope it states.

A remembered policy decision does not silently broaden itself to:

    - new adapter kinds
    - new packs
    - new capabilities
    - new SavePacks
    - new RuntimeHost entry surfaces
    - new trust classes

Policy decision storage does not become pack authority.


PRESERVATION RULE 15: ADAPTER WORK DOES NOT BECOME JOB, OU, OR RUNTIMEHOST OUTCOME BY DEFAULT
============================================================================================

Preserve Job / OrchestrationUnit / RuntimeHost separation.

Adapter-executed work may be associated with a Job when the owning workflow
defines Job-backed behavior.

Adapter-executed work may create or enter an OrchestrationUnit when it seeks
Turnix mutation guarantees or lifecycle authority.

Adapter execution acceptance is not Job success.

Adapter execution failure is not Job failure by default.

Adapter disconnect is not Job cancellation by default.

Adapter execution failure is not OrchestrationUnit failure by default.

Adapter execution acceptance is not RuntimeHost operation success.

RuntimeHost operation success is not adapter execution success by default.

Job and OrchestrationUnit relationships to adapter-executed work are explicit
and trace-visible when they exist.

Trace wording should follow the DA-03 cross-document trace wording check.


PRESERVATION RULE 16: BROWSER / FRONTEND STATE IS NOT AUTHORITATIVE STATE
=========================================================================

Preserve View/frontend runtime boundaries.

Browser state is not authoritative AppInstance state.

Browser reload, tab close, client disconnect, or frontend state loss does not
redefine committed state.

Frontend adapters may hold render state, temporary UI state, input fields,
scroll position, local cache, and pending view interaction state.

Frontend adapters do not own authoritative AppInstance state.

Frontend adapters do not own RuntimeHost authority merely because they render a
launcher, management, CLI-like, or RuntimeHost control surface.


SOURCE BOUNDARY STATEMENT: DA-27 AND DA-28 DO NOT WEAKEN DA-23
==============================================================

DA-23 may state the source-level boundary:

    DA-27 may define adapter lifecycle, trust, isolation, concrete adapter
    classes, adapter failure/disconnect meaning, and adapter-domain trace reason
    identifiers.

    DA-28 may define RuntimeHost identity, workspace ownership, startup modes,
    entry surfaces, command-surface semantics, local-first and LAN exposure
    semantics, and RuntimeHost-domain trace reason identifiers.

    Those later details do not weaken DA-23's abstract execution-boundary
    authority model.

    If DA-23 and DA-27 or DA-28 appear to conflict, use the interpretation that
    preserves Kernel authority, capability mediation, workspace ownership, and
    the RPC-shaped execution boundary until the documents are corrected.

This source-level boundary is useful because DA-23 explicitly owns the abstract
execution-boundary authority model.

The detailed DA-27 / DA-28 ownership map belongs in the guardrail section below.
