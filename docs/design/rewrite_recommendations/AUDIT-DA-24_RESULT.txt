==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Mostly correct, with terminology translation required.

    The recommendation correctly preserves DA-24's central model:
    OrchestrationUnit coordinates mutation authority, but does not bypass DA-04
    committed-state/transaction authority, DA-05 value representation, DA-06
    configuration semantics, DA-07 persistent-I/O authority, DA-19 Job lifecycle,
    DA-16 Capability/permission mediation, DA-21 RPC/transport, DA-23/DA-27
    adapter boundaries, DA-28 RuntimeHost boundaries, DA-29 PackManager outcomes,
    or DA-25/DA-26 artifact/export/workflow meanings.

    The recommendation still uses stale AppInstance and SavePack wording in some
    guardrails. Translate those ideas into Application/ApplicationRun and
    SaveBundle/persistence terminology where they must be named.

Document verdict:
    Keep with small but important fixes.

DA-24 is architecturally strong and already reflects much of the current model.

No heavy conceptual rewrite is recommended.

The main required fixes are:

    - use OrchestrationUnit consistently as the canonical first-class type name
    - preserve the execution-authority wording as coordination authority, not
      arbitrary contained-code authority
    - add or preserve DA-05 / DA-06 / DA-07 stop-lines for payload,
      configuration, migration, and persistent I/O meanings
    - replace vague durable-save ownership wording with SaveBundle/persistence
      ownership stop-lines
    - add DA-25 / DA-26 stop-lines for artifact/export, comparison, Replay,
      Resume, Retry, and audit workflow meanings
    - expand trace-owner stop-lines so OrchestrationUnit trace evidence does not
      replace capability, decision, RPC, artifact/export, workflow, PackManager,
      or RuntimeHost trace evidence
    - preserve single-lane ApplicationRun mutation orchestration as the default
    - keep future concurrency modes explicitly open
    - avoid final-document version/process metadata leakage

Primary conclusion:
    Keep DA-24 as the OrchestrationUnit lifecycle, mutation-authority,
    transaction relation, Job relation, Window relation, ApplicationRun relation,
    capability/RPC/adapter/RuntimeHost relation, outcome, single-lane mutation,
    and OrchestrationUnit-domain trace document. Apply targeted stop-line and
    terminology fixes only.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-24 should not keep older terminology as a historical artifact.

Specifically, the rewrite should not preserve:

    - AppInstance as runtime identity vocabulary
    - SavePack as durable persistence vocabulary
    - Orchestration Unit as an informal separate concept where OrchestrationUnit
      is the canonical type name
    - execution-authority unit as arbitrary backend authority
    - execution-authority unit as arbitrary contained-code committed-state
      authority
    - OrchestrationUnit terminal outcome as automatic transaction commit/abort
    - OrchestrationUnit terminal outcome as Job terminal outcome
    - OrchestrationUnit terminal outcome as Window finalization
    - OrchestrationUnit terminal outcome as RuntimeHost operation outcome
    - OrchestrationUnit terminal outcome as adapter lifecycle outcome
    - OrchestrationUnit terminal outcome as artifact/export authority
    - OrchestrationUnit terminal outcome as ComparisonResult, Replay, Resume,
      Retry, or audit workflow outcome
    - async suspension/await as concurrency authority
    - PackManager-triggered work as bypassing OrchestrationUnit authority rules
    - RuntimeHost command acceptance as OrchestrationUnit completion

If a legacy alias is intentionally retained, DA-24 should say so explicitly and
should still state the canonical architecture term as primary.

Otherwise, the old terms should be removed or translated.

The useful part of the old recommendation is not the old terminology. The useful
part is the mutation-authority boundary:

    OrchestrationUnit coordinates or owns mutation-bearing work. It does not own
    committed-state truth, value representation, configuration semantics,
    persistent I/O authority, artifact/export authority, workflow authority,
    PackManager outcome, RuntimeHost outcome, adapter outcome, Job outcome, or
    capability permission by itself.

01B. DOCUMENT-METADATA LEAKAGE CHECK
==============================================================================

The final DA-24 document should read as architecture documentation, not as audit,
version, or rewrite-process metadata.

Do not include statements such as:

    - This is V3 design.
    - In V3, OrchestrationUnit replaces Orchestration Unit.
    - The new design uses Proposal P02.
    - This rewrite changed mutation-authority terminology.
    - Unlike V2, ApplicationRun is used here.
    - Codex kept AppInstance wording.
    - This audit decided to use SaveBundle.
    - DA-24 was rewritten because of the audit.

Those facts may be useful in audit files, branch notes, migration notes,
compatibility notes, changelogs, or editor instructions. They do not belong in
the architecture document itself.

The final DA-24 should simply define OrchestrationUnit identity, scope, mutation
authority, transaction relation, Job relation, Window relation, ApplicationRun
relation, capability/RPC/adapter/RuntimeHost relation, outcomes, single-lane
ApplicationRun mutation rule, trace reasons, trace context, unsupported behavior,
and open implementation details.

==============================================================================
02. WHAT DA-24 GETS RIGHT
==============================================================================

02.1. OrchestrationUnit as mutation-authority coordinator
--------------------------------------------------------

DA-24 correctly defines OrchestrationUnit as a kernel-tracked execution-authority
unit that may be permitted to mutate Turnix-managed state within an
ApplicationRun.

It correctly says OrchestrationUnit authority is not general backend authority.

Preserve this.

02.2. Authority is scoped by surrounding domains
------------------------------------------------

DA-24 correctly scopes OrchestrationUnit authority by ApplicationRun identity,
capability/permission boundaries, transaction/commit boundaries, adapter
boundaries, RuntimeHost boundaries, and policy/decision boundaries.

Preserve this.

02.3. Same-language and same-process execution do not bypass authority
---------------------------------------------------------------------

DA-24 correctly says same-language or same-process execution does not bypass
OrchestrationUnit authority rules.

Preserve this strongly.

02.4. RuntimeHost operation convenience does not bypass authority
-----------------------------------------------------------------

DA-24 correctly says RuntimeHost startup modes, entry surfaces, and command
surfaces do not bypass OrchestrationUnit authority rules when they perform or may
perform mutation-bearing work.

Preserve this and keep RuntimeHost semantics DA-28-owned.

02.5. Mutation still crosses DA-04 boundaries
---------------------------------------------

DA-24 correctly says mutation-bearing OrchestrationUnits use DA-04 state and
transaction rules, staged mutation is not authoritative merely because the
OrchestrationUnit exists, and staged mutation becomes authoritative only by commit
under DA-04.

Preserve this.

02.6. OrchestrationUnit / Job / transaction split is strong
----------------------------------------------------------

DA-24 correctly distinguishes OrchestrationUnit, Job, and transaction.

It correctly says OrchestrationUnit outcome does not define Job terminal outcome
and Job terminal outcome does not define OrchestrationUnit outcome.

Preserve this.

02.7. Window relation is mostly strong
--------------------------------------

DA-24 correctly says OrchestrationUnit outcome evidence may contribute to later
Window evidence, but OrchestrationUnit Completed does not mean SafePointWindow was
created and Failed/Cancelled/Superseded does not mean AbortedWindow was created.

Preserve this and add DA-25 artifact/export stop-lines.

02.8. ApplicationRun relation is strong
---------------------------------------

DA-24 correctly says ApplicationRun lifecycle and runtime identity are defined by
DA-20, applicationRunId is distinct from orchestrationUnitId, and ApplicationRun
lifecycle outcome does not by itself define OrchestrationUnit terminal outcome.

Preserve this.

02.9. Capability/RPC/RuntimeHost separation is strong
-----------------------------------------------------

DA-24 correctly says RPC transport acknowledgement does not imply
OrchestrationUnit completion, RPC timeout does not imply OrchestrationUnit
failure/cancellation/supersession, RuntimeHost command acceptance does not imply
OrchestrationUnit completion, RuntimeHost operation completion does not by itself
define OrchestrationUnit terminal outcome, and capability permission approval does
not imply successful OrchestrationUnit completion.

Preserve this.

02.10. Adapter boundary is strong
---------------------------------

DA-24 correctly says adapter-executed code does not mutate committed state
directly and that adapter-executed mutation seeking Turnix guarantees re-enters
through orchestration, capability, transaction, and commit boundaries before
becoming authoritative.

Preserve this and keep DA-23/DA-27 ownership clear.

02.11. OrchestrationUnit outcomes are strong
--------------------------------------------

DA-24 correctly defines terminal outcomes:

    - Completed
    - Failed
    - Cancelled
    - Superseded

It correctly says Superseded is not failure, not timeout, and does not roll back
authoritative state already committed.

Preserve this.

02.12. Single-lane ApplicationRun mutation default is strong
------------------------------------------------------------

DA-24 correctly says Turnix uses deterministic single-lane orchestration within
one ApplicationRun unless an explicit concurrency mode is defined elsewhere.

It correctly says suspension/await does not authorize another state-mutating unit
to run concurrently inside the same ApplicationRun unless explicit concurrency
mode permits it.

Preserve this strongly.

02.13. Trace ownership is mostly strong
---------------------------------------

DA-24 correctly owns OrchestrationUnit-domain trace reason identifiers and says
DA-03 owns the trace substrate.

Preserve this and expand the no-replacement trace stop-lines.

==============================================================================
03. MAJOR REQUIRED FIX: CANONICAL ORCHESTRATIONUNIT TERMINOLOGY
==============================================================================

The target DA-24 frequently uses spaced `Orchestration Unit` in prose.

If the canonical type name is OrchestrationUnit, DA-24 should use that form for
the first-class architecture object.

Recommended rule:

    Use OrchestrationUnit when naming the first-class Turnix type/concept.

    Use "orchestration unit" only as ordinary English if deliberately not naming
    the type.

Potential replacement examples:

    Orchestration Unit lifecycle
        -> OrchestrationUnit lifecycle

    Orchestration Unit identity
        -> OrchestrationUnit identity

    Orchestration Unit outcome
        -> OrchestrationUnit outcome

    Orchestration Unit terminal outcome
        -> OrchestrationUnit terminal outcome

    Orchestration Units, Jobs, and transactions
        -> OrchestrationUnits, Jobs, and transactions

This is not merely cosmetic. It prevents OrchestrationUnit from drifting into an
informal task/work item concept.

==============================================================================
04. MAJOR REQUIRED FIX: EXECUTION-AUTHORITY WORDING
==============================================================================

The phrase `execution-authority unit` is useful, but it can be misread.

DA-24 should explicitly preserve the intended meaning:

    OrchestrationUnit has authority to own or coordinate a mutation flow.

    OrchestrationUnit authority is scoped authority to coordinate a mutation
    flow.

    It is not arbitrary contained-code authority.

    It is not general backend authority.

    It is not direct committed-state authority for arbitrary contained code.

    It does not replace DA-04 transaction and commit boundaries.

This is especially important for:

    - adapter-executed code
    - same-language Python Pack code
    - model/tool callbacks
    - PackManager-triggered graph or lifecycle operations
    - RuntimeHost-triggered operations
    - capability-backed operations
    - artifact/export operations
    - comparison, Replay, Resume, Retry, and audit workflow operations

==============================================================================
05. PAYLOAD / CONFIGURATION / PERSISTENCE STOP-LINES
==============================================================================

DA-24 touches mutation-bearing work, committed state, configuration mutation,
migration work, persistent I/O authority, durable save material, and recovery
implications.

Keep DA-24 as mutation-authority coordination, not as owner of every affected
domain.

Recommended stop-lines:

    DA-24 defines OrchestrationUnit mutation-authority coordination.

    DA-04 defines authoritative committed state and transaction commit/abort
    semantics.

    DA-05 defines committed-value representation, ValueRef, Chunk, ChunkId,
    payload identity, decode, and integrity.

    DA-06 defines configuration semantics, configuration storage layout,
    configuration migration, and policy-file placement.

    DA-07 defines persistent-I/O authority, root boundaries, Reader/Writer
    providers, persistence safety, backup/snapshot behavior, and streaming I/O
    rules.

    SaveBundle/persistence documents own SaveBundle storage, retained material,
    durable persistence closure, persistence compatibility, and recovery details.

    OrchestrationUnit existence, execution, completion, failure, cancellation,
    supersession, suspension, or trace evidence does not bypass those domains.

Replace vague wording such as:

    durable save and recovery implications remain owned by DA-04, DA-05, DA-06,
    and DA-07

with a split that names SaveBundle/persistence ownership where durable
Application persistence closure is meant.

==============================================================================
06. ARTIFACT / EXPORT / WORKFLOW STOP-LINES
==============================================================================

DA-24 allows OrchestrationUnit evidence to contribute to Window evidence and
future audit/export/replay material.

Add or preserve:

    OrchestrationUnit evidence may contribute to Window evidence or later audit
    material.

    OrchestrationUnit evidence does not by itself define Window artifact,
    WindowExport, Minimal Audit Bundle, digest, partial export, missing material,
    ComparisonResult, Replay outcome, Resume outcome, Retry outcome, or audit
    workflow outcome.

    OrchestrationUnit terminal outcome does not by itself create artifact/export
    authority.

    OrchestrationUnit Completed does not by itself mean artifact/export completed.

    DA-25 owns artifact/export semantics.

    DA-26 owns comparison, Replay, Resume, Retry, and audit workflow semantics.

Do not turn DA-24 into DA-25 or DA-26.

==============================================================================
07. TRACE WORDING FIX
==============================================================================

DA-24 should preserve OrchestrationUnit-domain trace obligations but follow DA-03
trace wording.

Correct reading:

    OrchestrationUnit trace evidence is required as a domain emission obligation
    where OrchestrationUnit lifecycle, transaction association, and decision
    waiting events occur.

Not:

    Trace persistence is guaranteed forever.

Not:

    OrchestrationUnit correctness depends on retained OrchestrationUnit trace
    evidence.

Suggested wording:

    OrchestrationUnit-domain trace evidence is required as an emission obligation
    where OrchestrationUnit events occur. Trace representation, retention,
    pruning, and loss remain governed by DA-03.

Add or preserve no-replacement stop-lines:

    OrchestrationUnit trace evidence does not replace:

        - DA-04 transaction trace evidence
        - DA-05 payload / committed-value evidence
        - DA-06 configuration or migration evidence
        - DA-07 persistent-I/O evidence
        - DA-08 Window trace/evidence
        - DA-16 capability trace evidence
        - DA-17 decision/policy trace evidence
        - DA-19 Job trace evidence
        - DA-20 Application/ApplicationRun trace evidence
        - DA-21 RPC trace evidence
        - DA-23 / DA-27 adapter trace evidence
        - DA-25 artifact/export trace evidence
        - DA-26 comparison / Replay / Resume / Retry / audit workflow evidence
        - DA-28 RuntimeHost trace evidence
        - DA-29 PackManager trace evidence

==============================================================================
08. SINGLE-LANE APPLICATIONRUN DEFAULT
==============================================================================

DA-24 already preserves this well.

Keep:

    Turnix uses deterministic single-lane orchestration within one ApplicationRun
    unless an explicit concurrency mode is defined elsewhere.

    Within one ApplicationRun, Turnix does not execute multiple
    OrchestrationUnits concurrently when those units may mutate the same
    ApplicationRun state.

    Awaited input/output, model calls, adapter calls, RuntimeHost calls,
    persistent I/O, export work, audit work, comparison work, or other I/O may
    suspend the current unit.

    Suspension does not authorize another state-mutating unit to run concurrently
    in the same ApplicationRun unless an explicit concurrency mode permits that
    behavior.

Future concurrency modes must define:

    - mutation conflict boundaries
    - transaction interaction
    - ordering rules
    - trace obligations
    - persistence and recovery implications
    - artifact/export interaction if artifacts or exports are affected
    - Replay / Resume / Retry and audit workflow interaction if workflows are
      affected
