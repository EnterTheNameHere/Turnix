SUMMARY
=======

DA-01 should remain the top-level philosophy anchor.

No heavy rewrite is recommended.

DA-01 should define:

    - Turnix core identity
    - Core Truth Doctrine
    - locked project invariants
    - highest-level runtime authority ordering
    - adjustable design attitudes
    - explicitly open philosophical questions

Required DA-01 changes:

    1. Rewrite project identity so Turnix is clearly a runtime, not a
       pack-built application system.

    2. Patch trace wording so trace is not treated as merely optional
       diagnostics, while also not making trace persistence equivalent to
       committed-state authority.

    3. Clarify local-first so it means user-controlled local infrastructure,
       not same-machine-only and not local-only forever.

    4. Keep pack identity general so packs remain first-class without becoming
       the whole identity of Turnix.

    5. Align SavePack wording with the AppInstance model:
       SavePack stores durable AppInstance state.

    6. Preserve the AppInstance/AppPack distinction without resolving the DA-20
       AppPack-backing question inside DA-01.

    7. Add compact stop-lines for completed foundational runtime domains so
       DA-01 does not absorb payload, configuration, persistent I/O, UI,
       debugger, artifact/export, comparison, Replay, Resume, or Retry
       semantics.

Overall recommendation:

    KEEP BUT UPDATE

ACTUAL DA-01 CHANGE 1: PROJECT IDENTITY
=======================================

Current problem:

    DA-01 currently says Turnix exists to enable a persistent, local,
    identity-stable system "built on modular packs".

Why this should change:

    The phrase "built on modular packs" can make packs sound like the
    foundation of Turnix identity.

    That points toward:

        Turnix = pack-based app system

    Dv3 wants:

        Turnix = runtime domain
        packs = first-class composition/distribution/deployment mechanism
        apps = one kind of thing the runtime can host

Recommended DA-01 change:

    Rewrite the opening identity section so Turnix is described as a runtime,
    not as a pack-built app system.

Suggested DA-01 replacement direction:

    02.1. Turnix exists to provide a persistent, local-first, identity-stable
          runtime for traceable and orchestrated systems.

    02.2. Turnix is not defined by any single launch mode, pack format, user
          interface, host process, model provider, application packaging
          strategy, catalog surface, graph-preparation tool, persistence layout,
          artifact/export format, comparison workflow, replay workflow,
          debugging surface, UI surface, or RuntimeHost realization.

    02.3. Modular packs are a first-class Turnix mechanism for describing,
          distributing, composing, extending, and persisting runtime behavior,
          but packs do not define the whole identity of Turnix.

    02.4. Turnix is not:
          - a plugin loader
          - a dynamic script runner
          - a web app framework
          - a convenience-first modding system
          - a pack-only application launcher
          - a pack manager
          - a catalog system
          - a graph-preparation tool
          - a root-discovery system
          - a pack-discovery system
          - a storage backend
          - a configuration file format
          - a UI framework
          - a debugger
          - an export format
          - a replay tool

    02.5. Turnix is:
          - a runtime continuity engine
          - a deterministic resolver
          - a policy-driven orchestrator
          - an explainable system
          - a controlled execution and state boundary

Core doctrine to preserve:

    Turnix does not merely run AppPacks.

    Turnix runs AppInstances.

    AppPack is one first-class declarative way to create an AppInstance.

    Packs remain first-class, but they are not identity-defining.


ACTUAL DA-01 CHANGE 2: TRACE OPTIONALITY
========================================

Current problem:

    In the best-effort section, traces are listed with logs and analytics as
    explicitly optional data.

Why this should change:

    Dv3 treats trace as structured runtime evidence, not merely debugging
    output.

    But trace must also not be confused with committed state.

Recommended DA-01 change:

    Patch the best-effort section to avoid saying "traces are optional" as a
    global doctrine.

    Do not overcorrect by making trace persistence equivalent to committed-state
    persistence.

Suggested DA-01 replacement direction:

    04.10. Best-effort behavior is acceptable only for explicitly optional
           non-authoritative data such as:
           - diagnostic logs
           - verbose diagnostic traces
           - analytics

    04.11. Domain-required trace evidence is not optional as an emission
           obligation.

    04.12. Trace persistence and retention are policy-governed. Retained trace
           evidence may be bounded, rotated, or lossy when loss is represented
           honestly.

    04.13. Trace loss weakens evidential completeness. It does not by itself
           change committed-state correctness.

    04.14. Committed-state truth is governed by the authoritative commit model,
           not by trace completeness.

Preserve these distinctions:

    Trace evidence is not merely optional diagnostics.

    Domain-owning documents may require trace emission for meaningful actions.

    Required trace emission is an emission obligation.

    Trace persistence and retention are policy-governed.

    Trace loss weakens evidential completeness.

    Trace loss does not by itself change committed-state correctness.

    Committed-state truth is governed by DA-04's commit model.

Avoid these interpretations:

    - trace is just optional logging
    - trace persistence failure invalidates committed state
    - retained trace evidence is as authoritative as committed state
    - Turnix uses trace-backed correctness


ACTUAL DA-01 CHANGE 3: LOCAL-FIRST CLARIFICATION
================================================

Current problem:

    DA-01 says Turnix is local-first and assumes local filesystem, limited
    hardware, and limited context window.

    This is mostly correct, but the wording should not accidentally become:

        local-only forever

Recommended DA-01 change:

    Clarify local-first as baseline authority and state ownership, not
    same-machine-only execution.

Suggested DA-01 replacement direction:

    04.19. Turnix is local-first.

    04.20. Local-first means authoritative runtime and state remain under
           user-controlled local infrastructure.

    04.21. Local-first does not require same-machine execution.

    04.22. Explicit, policy-governed LAN, server, remote-resource, or
           federated modes may exist without replacing local-first as the
           baseline authority, persistence model, failure model, and recovery
           model.

    04.23. Turnix assumes:
           - local filesystem
           - limited hardware
           - limited context window

    04.24. Server-scale patterns are rejected by default, including:
           - lazy global registries
           - infinite retries
           - implicit availability

Preserve this doctrine:

    local-first, not local-only

    user-controlled local infrastructure, not necessarily one process or one
    physical machine


ACTUAL DA-01 CHANGE 4: KEEP PACK IDENTITY GENERAL
=================================================

Current problem:

    DA-01 is a top-level philosophy document.

    It should not drift from:

        Turnix has packs, discovery, resolution, activation, import, and pack
        management.

    into:

        Turnix is the pack manager, launcher, catalog, discovery system,
        resolver, importer, activator, or graph-preparation system.

Recommended DA-01 change:

    Keep pack-related wording broad and doctrinal.

    DA-01 may say packs are first-class mechanisms for describing,
    distributing, composing, extending, and persisting runtime behavior.

    DA-01 may say pack-related systems are runtime subsystems inside Turnix.

    DA-01 should not define their detailed behavior.

Suggested DA-01-level wording:

    Pack-related systems such as discovery, visibility, resolution, dependency
    resolution, importing, activation, and pack management are runtime
    subsystems inside Turnix.

    They support Turnix's runtime model, but they do not define Turnix's
    identity and must not be treated as authority roots by themselves.

Do not describe Turnix as:

    - a pack manager
    - a launcher
    - a catalog system
    - an AppPack runner
    - a graph-preparation tool
    - a pack-management application
    - a root-discovery system
    - a pack-discovery system
    - a visibility/indexing system
    - a generic resolver
    - a dependency solver
    - an import/module-loading system
    - an activation system

Do not explain detailed PackManager, discovery, identity, visibility, indexing,
resolution, dependency, activation, import, or pack-management semantics inside
DA-01.


ACTUAL DA-01 CHANGE 5: SAVEPACK / APPINSTANCE TERMINOLOGY
=========================================================

Current issue:

    DA-01 uses or preserves the phrase:

        SavePack stores durable executed state.

After the AppInstance lifecycle audit, the better working phrase is:

        SavePack stores durable AppInstance state.

Recommended DA-01 change:

    Replace high-level SavePack wording with:

        SavePack stores durable AppInstance state.

Preserve this distinction:

    SavePack is not AppInstance identity.

    SavePack does not own AppInstance lifecycle.

    SavePack does not grant adapter-executed code authority.

    SavePack mutation remains governed by the authoritative commit model and
    persistence authority.

Do not expand DA-01 into detailed SavePack semantics.

Use the updated phrase only as high-level runtime-authority ordering.

Watch:

    Later SavePack documents may define a more precise canonical phrase.

    If they do, DA-01 should adopt that phrase at doctrine level without
    absorbing detailed SavePack semantics.


ACTUAL DA-01 CHANGE 6: DO NOT RESOLVE APPPACK-BACKING IN DA-01
==============================================================

Current issue:

    The broader Dv3 thesis says:

        Turnix runs AppInstances.

        AppPack is one first-class declarative way to create an AppInstance.

    DA-20 currently defines the AppPack-backed AppInstance lifecycle and says an
    AppInstance is a live runtime instance of one AppPack.

Risk:

    DA-01 could accidentally turn the DA-20 source wording into global Turnix
    identity doctrine before the AppPack-backing question is resolved.

Recommended DA-01 change:

    Preserve the broader top-level invariant:

        Turnix runs AppInstances.

        AppPack is one first-class declarative way to create an AppInstance.

    Do not make DA-01 say or imply:

        Every possible AppInstance is necessarily AppPack-backed.

        Turnix runs AppPacks.

        AppPack is Turnix identity.

DA-01 should not settle whether embedded, scripted, test, or internal
AppInstances require synthetic/internal AppPacks.

That decision belongs to DA-20, AppPack documents, SavePack documents, or later
runtime-creation specifications.

DA-01 should remain broad enough to survive either model:

    Model A:
        every AppInstance is formally AppPack-backed, including non-product
        usages through synthetic/internal AppPacks

    Model B:
        AppPack-backed AppInstance is the normal product-facing path, but not
        the only AppInstance creation path

Current issue:

    DA-01 may name runtime domains at philosophy level, but later audited

PRESERVATION RULE 1: SAME-LANGUAGE AUTHORITY DOCTRINE
=====================================================

Preserve same-language authority doctrine.

Internal Turnix Python is trusted backend implementation.

Pack-provided Python is external code.

Pack-provided code should not gain direct backend authority merely because it:

    - is written in the same language
    - happens to run in the same process
    - communicates through an in-process transport
    - uses direct-call optimization
    - sends frontend messages
    - is triggered through RuntimeHost command surfaces
    - appears in pack declarations
    - receives PackContext access

PackContext access is scoped participation, not backend internals access.

Same-language or same-process execution must not collapse authority boundaries.


PRESERVATION RULE 2: RUNTIME AUTHORITY ORDERING
===============================================

Preserve runtime authority ordering.

Current ordering to preserve with updated SavePack wording:

    Kernel owns authority.

    RuntimeHost exposes controlled entry surfaces.

    IoManager mediates persistent I/O.

    Adapters execute declared pack code.

    Transports carry messages.

    RPC defines the logical communication boundary.

    Capabilities define what code may do.

    SavePack stores durable AppInstance state.

This ordering is compatible with Kernel being important but intentionally not
over-specified.

RuntimeHost is not Kernel authority.

IoManager protects persistence but does not define committed-state truth.

Entry surfaces and command surfaces may request, observe, or control through
mediated runtime paths, but they do not become authority themselves.


PRESERVATION RULE 3: NO GUARANTEES OUTSIDE ORCHESTRATION
========================================================

Preserve the "no guarantees outside orchestration" invariant.

Mutation outside orchestration does not acquire Turnix guarantees by
implication.

OrchestrationUnit authority does not bypass DA-04 transaction and commit rules.

PackManager can prepare and explain selected pack graph intent, but it does not
silently:

    - activate
    - import
    - load
    - execute
    - mutate SavePack state
    - mutate active AppInstance graph state
    - remember decisions
    - broaden policy
    - grant capability permission
    - bypass Kernel-mediated operation paths

UI, debugger tooling, persistence helpers, artifact export tools, comparison
tools, Replay, Resume, and Retry workflows also do not acquire Turnix guarantees
or authority by existing near the runtime.

They must remain mediated by their owning domain rules.


PRESERVATION RULE 4: DA-01 REMAINS PHILOSOPHY ANCHOR
====================================================

Preserve DA-01 scope.

DA-01 may name core runtime domains at philosophy level.

DA-01 should not define detailed subsystem behavior.

DA-01 should not become:

    - full architecture specification
    - pack-chain specification
    - RuntimeHost specification
    - AppInstance specification
    - SavePack specification
    - trace substrate specification
    - memory/state specification
    - ValueRef / Chunk representation specification
    - configuration/schema/migration specification
    - IoManager / persistence specification
    - Window/finalized-history specification
    - Window artifact/export specification
    - comparison/replay/resume/retry specification
    - OrchestrationUnit specification
    - Job specification
    - capability specification
    - RPC specification
    - UI/View/frontend-runtime specification
    - debugger/breakpoint specification
    - adapter specification
    - PackManager specification

DA-01 should remain the top-level anchor for identity, truth doctrine, runtime
authority ordering, and project invariants.


WATCH ITEM: MACHINE INTERPRETATION OF EXAMPLES
==============================================

DA-01 intentionally avoids RFC-style MUST/SHOULD/MAY language and says
normative meaning comes from sentence structure and context.

This is acceptable.

However, examples inside locked-invariant sections can become global doctrine
for a machine assistant.

Known risks:

    Trace risk:
        Listing "traces" beside "logs" and "analytics" under optional
        best-effort data may be interpreted as a broad statement that traces
        are nonessential.

    PackManager risk:
        Words such as "repair", "prepare", "manage", or "help choose" can be
        misread as permission for PackManager to automatically fix pack graphs.

    Pack-chain risk:
        Words such as "discover", "available", "candidate", "root",
        "catalog", "listed", "visible", "resolved", "required", "imported",
        "loaded", or "active" can be misread as runtime availability or
        authority.

    AppInstance/AppPack risk:
        Words such as "AppPack runtime", "AppPack instance", or "AppPack
        execution" can be misread as settling that all AppInstances are
        necessarily AppPack-backed.

    Persistence risk:
        Words such as "saved", "written", "stored", "restored", "backed up",
        "snapshotted", or "exported" can be misread as defining committed-state
        truth rather than persistence or artifact representation.

    UI/debugger risk:
        Words such as "clicked", "confirmed", "paused", "edited", "resumed",
        or "debugged" can be misread as authority rather than mediated
        frontend/debugger requests.

    Replay/resume/retry risk:
        Words such as "replay", "resume", or "retry" can be misread as live
        handle continuation or re-running external effects.

Handle this by preserving compact distinctions in the source document and
leaving detailed semantics to the owning documents.


RECOMMENDED EDIT ORDER
======================

1. Rewrite the identity section first.

    Goal:
        Move Turnix from "pack-built system" toward "runtime domain".

2. Patch trace optionality.

    Goal:
        Prevent contradiction with Dv3 trace doctrine while preserving the
        distinction between trace evidence and committed state.

3. Add local-first clarification.

    Goal:
        Preserve local-first as baseline authority without banning future
        explicit LAN/server/remote-resource/federated modes.

4. Align SavePack wording.

    Goal:
        Use "durable AppInstance state" instead of "durable executed state."

5. Preserve AppInstance/AppPack distinction.

    Goal:
        Keep DA-01 broad enough to survive the DA-20 AppPack-backing decision.

6. Keep pack identity general.

    Goal:
        Preserve packs as first-class without making Turnix into AppPack runner,
        PackManager, catalog system, launcher, graph-preparation tool,
        root-discovery system, pack-discovery system, visibility/indexing
        system, generic resolver, dependency solver, importer, or activator.

7. Add compact stop-lines for completed DA sweep domains.

    Goal:
        Prevent DA-01 from absorbing payload, configuration, persistence, UI,
        debugger, artifact/export, comparison, Replay, Resume, or Retry
        semantics.

8. Do not expand DA-01 into detailed subsystem doctrine.

    Goal:
        DA-01 should remain the top-level philosophy anchor.


REWRITE-BOUNDARY GUARDRAILS, NOT SUGGESTED DA-01 CONTENT
=========================================================

This section is not suggested DA-01 wording.

It exists to prevent architectural drift during rewrite when the editor knows
DA-01 but may not have every related document loaded.

Use these as guardrails only.

Identity and runtime guardrails:

    Turnix is a runtime domain, not a pack-built app system.

    Turnix runs AppInstances.

    AppPack is one first-class declarative way to create an AppInstance.

    DA-01 does not settle whether all AppInstances must be formally
    AppPack-backed.

    Packs are first-class but not identity-defining.

    RuntimeHost is a running host boundary, not Kernel and not Turnix identity.

    AppInstance is runtime identity, not RuntimeHost.

    SavePack stores durable AppInstance state, not RuntimeHost identity.

    Entry surfaces and command surfaces are not authority.

Pack-chain guardrails:

    Discovery is input/candidate production, not runtime identity.

    Visibility is eligibility to be seen, not runtime authority.

    Resolution selects from an explicit context, not runtime identity.

    Dependency declarations are hard requirements, not activation or permission.

    Importing/module loading is not activation or execution authority.

    Activation is controlled executable participation, not project identity.

    PackManager is a management domain, not Turnix identity or authority root.

Trace and state guardrails:

    Trace is evidence, not committed state.

    Trace emission obligation is not trace persistence guarantee.

    Trace loss weakens evidential completeness.

    Trace loss does not by itself change committed-state correctness.

    Committed-state truth is governed by the authoritative commit model.

Payload / configuration / persistence guardrails:

    ValueRef / Chunk identity is committed-value representation, not Turnix
    identity.

    Configuration is specialized authoritative state, not a separate state
    architecture.

    effectiveConfig is runtime view, not separate authority.

    IoManager is persistent-I/O authority, not committed-state truth.

    Root writability is not state-mutation authority.

    Persistence protects truth; it does not define truth.

Window / artifact / workflow guardrails:

    SafePointWindow is a committed boundary, but optional retained evidence
    inside it does not add authority.

    ActiveWindow is non-authoritative in-flight history.

    AbortedWindow is non-authoritative abort evidence.

    WindowExport changes portability, not semantics.

    Minimal Audit Bundle is non-authoritative evidence.

    ComparisonResult does not imply replayability, resumability, or audit
    completeness.

    Replay restores retained committed state and causal story; it does not
    re-run external effects.

    Resume and Retry are new work.

UI / debugger guardrails:

    UI is presentation and interaction, not authority.

    View readiness is not AppInstance, RuntimeHost, activation, or Job success.

    View disconnect does not silently decide AppInstance, Job, adapter,
    RuntimeHost, transport, or committed-state outcomes.

    Debugger tooling is semantic and mediated, not raw authority.

    Debugger safe point is not automatically SafePointWindow.

    Debugger mutation is explicit, staged, trace-visible, and authority-bound.

Same-language and execution guardrails:

    Same-language execution does not grant backend authority.

    Same-process execution does not grant backend authority.

    Direct-call optimization does not bypass authority.

    PackContext is scoped participation, not backend internals access.

Owning-document guardrails:

    DA-03 owns trace substrate, trace retention, trace loss, and trace DAG
    semantics.

    DA-04 owns authoritative committed state, transactions, and commit
    boundaries.

    DA-05 owns payload identity, Chunk, ChunkId, and ValueRef representation
    semantics.

    DA-06 owns configuration, schema, materialization, migration, and policy-file
    placement semantics.

    DA-07 owns IoManager and persistent-I/O authority semantics.

    DA-08 owns Window, SafePointWindow, ActiveWindow, AbortedWindow, and
    finalized runtime history semantics.

    DA-09 owns root and discovery semantics.

    DA-10 owns pack identity, hierarchy, and visibility semantics.

    DA-11 owns generic resolution semantics.

    DA-12 owns importing, module loading, and code-boundary semantics.

    DA-13 owns dependency, requirement, and PackRequest dependency semantics.

    DA-14 owns activation lifecycle and execution guarantees.

    DA-16 owns service, capability, and permission semantics.

    DA-17 owns user decision and remembered policy semantics.

    DA-18 owns debugger, inspection, breakpoint, manual-pause, safe-point, and
    debugger mutation semantics.

    DA-19 owns Job lifecycle and terminal outcome semantics.

    DA-20 owns AppInstance lifecycle and runtime identity semantics, including
    the unresolved AppPack-backing decision.

    DA-21 owns RPC, channel, and transport semantics.

    DA-22 owns UI, View, frontend runtime, and frontend presentation semantics.

    DA-23 and DA-27 own execution adapter and adapter lifecycle/trust semantics.

    DA-24 owns OrchestrationUnit mutation-authority semantics.

    DA-25 owns Window artifact, WindowExport, Minimal Audit Bundle, optional
    digest, and offline-inspection artifact semantics.

    DA-26 owns comparison, ComparisonResult, Replay, Resume, Retry, and audit
    workflow semantics.

    DA-28 owns RuntimeHost, workspace ownership, command surface, local-first,
    and LAN exposure semantics.

    DA-29 owns detailed PackManager semantics.

Local rewrite rule:

    DA-01 may name these concepts at philosophy level.

    DA-01 should not define their detailed behavior.

    DA-01 should not become a mini-index of Turnix architecture.

    DA-01 should only anchor that these are runtime domains or subsystems inside
    Turnix, not Turnix identity and not authority roots by themselves.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-01.

Rewrite the project identity so Turnix is clearly a runtime, not merely an
AppPack/modular-pack application system.

Preserve packs as first-class, but not identity-defining.

Preserve:

    Turnix runs AppInstances.

    AppPack is one first-class declarative way to create an AppInstance.

Do not use DA-01 to settle whether every AppInstance must be formally
AppPack-backed.

Patch trace wording so trace is not treated as merely optional diagnostics.

Use DA-03/DA-04-compatible wording for trace:

    domain-required trace emission is not optional as an obligation

    trace persistence is policy-governed and may be lossy when loss is
    represented honestly

    trace loss weakens evidential completeness

    committed-state correctness is governed by DA-04, not trace completeness

Clarify local-first using DA-28-compatible wording:

    local-first, not local-only

    user-controlled local infrastructure, not necessarily same-machine-only

Replace high-level SavePack wording with:

    SavePack stores durable AppInstance state.

Do not weaken same-language authority doctrine.

Do not weaken the no-guarantees-outside-orchestration invariant.

Do not expand DA-01 into a detailed RuntimeHost, trace, memory, ValueRef,
configuration, persistent-I/O, OrchestrationUnit, Job, Capability, PackManager,
root discovery, pack discovery, identity, visibility, indexing, resolution,
dependency, activation, import, AppInstance, SavePack, Window, artifact/export,
comparison, Replay, Resume, Retry, UI/View/frontend-runtime, debugger, RPC, or
ExecutionAdapter specification.
