SUMMARY
=======

DA-01 is a strong grounding document and should be kept.

It already contains several important Dv3-compatible ideas:

    - Turnix is not merely a plugin loader.
    - Turnix is not merely a dynamic script runner.
    - Turnix values continuity, determinism, explicitness, reversibility, and
      explicit uncertainty.
    - Kernel owns runtime authority but should not be over-specified.
    - RuntimeHost, adapters, transports, RPC, capabilities, and SavePack are
      already separated conceptually.
    - Same host language does not imply same authority.
    - Pack-provided Python is not automatically trusted backend implementation
      code just because Turnix backend is written in Python.
    - Turnix does not guarantee behavior outside Turnix orchestration.

Required Dv3 changes:

    1. Rewrite project identity so Turnix is clearly a runtime, not a
       pack-built application system.

    2. Patch trace wording so trace is not treated as merely optional
       diagnostics, while also not making trace persistence equivalent to
       committed-state authority.

    3. Clarify local-first so it means user-controlled local infrastructure,
       not same-machine-only and not local-only forever.

    4. Preserve existing authority boundaries without expanding DA-01 into
       detailed RuntimeHost, Memory, Trace, Job, OrchestrationUnit,
       Capability, PackManager, AppInstance, SavePack, RPC, or adapter specs.

Overall recommendation:

    KEEP BUT UPDATE

RECOMMENDED CHANGE 1: PROJECT IDENTITY
======================================

Current problem:

    DA-01 currently describes Turnix as a persistent, local, identity-stable
    system "built on modular packs".

Why this is a problem:

    The phrase "built on modular packs" can make packs sound like the
    foundation of Turnix's identity.

    That points toward:

        Turnix = pack-based app system

    Dv3 wants:

        Turnix = runtime domain
        packs = first-class composition/distribution/deployment mechanism
        apps = one kind of thing the runtime can host

    Later audited documents reinforce this:

        DA-28:
            RuntimeHost is the running host boundary, not Turnix identity.
            Startup modes, command surfaces, launcher mode, browser frontend,
            remote clients, deployment shape, and command syntax do not become
            runtime identity or authority.

        DA-29:
            PackManager is an official Turnix management domain, but it is not
            Turnix identity.
            PackManager helps choose and explain what Turnix will try, but
            accepted graph, activation plan, policy, and operation still run
            through Kernel-mediated boundaries.

    Therefore DA-01 should avoid making any of these the project identity:

        - AppPack
        - modular pack system
        - PackManager
        - catalog UI
        - launcher
        - graph-preparation tool
        - command surface
        - frontend/backend implementation shape
        - current RuntimeHost realization

New intended doctrine:

    Turnix does not merely run AppPacks.

    Turnix runs AppInstances.

    AppPack is one declarative way to create an AppInstance.

    Packs remain first-class, but they are not identity-defining.

Recommended change:

    Rewrite the opening identity section so Turnix is described as a runtime,
    not as a pack-built app system.

Suggested replacement direction:

    02.1. Turnix exists to provide a persistent, local-first, identity-stable
          runtime for traceable and orchestrated systems.

    02.2. Turnix is not defined by any single launch mode, pack format, user
          interface, host process, model provider, or application packaging
          strategy.

    02.3. Modular packs are a first-class Turnix mechanism for describing,
          distributing, composing, extending, and persisting runtime behavior,
          but packs do not define the whole identity of Turnix.

    02.4. Turnix is not:
          - a plugin loader
          - a dynamic script runner
          - a web app framework
          - a convenience-first modding system
          - a pack-only application launcher
          - a pack manager
          - a catalog system
          - a graph-preparation tool

    02.5. Turnix is:
          - a runtime continuity engine
          - a deterministic resolver
          - a policy-driven orchestrator
          - an explainable system
          - a controlled execution and state boundary

Reasoning:

    This keeps the original philosophy while changing the center of gravity.

    The old text says, in effect:

        persistent local identity-stable system built on modular packs

    The new text says:

        persistent local-first identity-stable runtime for traceable
        orchestrated systems, with packs as first-class mechanisms

    This matches the Dv3 runtime-domain direction while preserving packs as
    important composition and distribution mechanisms.


RECOMMENDED CHANGE 2: TRACE OPTIONALITY
=======================================

Current problem:

    In the best-effort section, traces are listed with logs and analytics as
    explicitly optional data.

Why this is a problem:

    Dv3 treats trace as structured runtime evidence, not merely debugging
    output.

    However, DA-03 and DA-04 also clarify that trace must not be confused with
    committed state.

Relevant doctrine from later audited documents:

    DA-03:
        Trace is structured evidence.
        Trace is not logging.
        Trace is not committed state.
        Trace retention is policy-governed.
        Trace loss is acceptable only when represented as loss evidence.
        Trace proves only within retained trace evidence.

    DA-04:
        Committed state is authoritative only after commit.
        Traces are non-authoritative material.
        Committed-state correctness is not trace-backed correctness.
        Retained authoritative material restores committed state, not trace
        alone.

Corrected Dv3 trace doctrine:

    Trace evidence is not merely optional diagnostics.

    Domain-owning documents may require trace emission for meaningful actions.

    Required trace emission is an emission obligation.

    Trace persistence and retention are policy-governed.

    Trace may be bounded, rotated, or lossy when loss is represented honestly.

    Trace loss weakens evidential completeness.

    Trace loss does not by itself change committed-state correctness.

    Committed-state truth is governed by DA-04's commit model.

Incorrect interpretations to avoid:

    1. Trace is just optional logging.

    2. Trace persistence failure invalidates committed state.

    3. Retained trace evidence is as authoritative as committed state.

    4. Turnix uses trace-backed correctness.

Required distinction:

    There are at least three relevant categories:

        1. Domain-required trace emission
           A subject-owning document may require that a domain attempt to emit
           trace evidence for a meaningful action.

           This is an emission obligation.

        2. Trace persistence / retention
           The trace substrate does not guarantee that all emitted trace
           evidence is durably retained forever.

           Retention is policy-governed and may be bounded or lossy when loss
           is represented honestly.

        3. Optional diagnostic / verbose trace
           Development-mode or diagnostic enrichment that may be best-effort
           and non-authoritative.

Recommended change:

    Patch the best-effort section to avoid saying "traces are optional" as a
    global doctrine.

    Do not overcorrect by making trace persistence equivalent to committed-state
    persistence.

Suggested replacement direction:

    04.10. Best-effort behavior is acceptable only for explicitly optional
           non-authoritative data such as:
           - diagnostic logs
           - verbose diagnostic traces
           - analytics

    04.11. Domain-required trace evidence is not optional as an emission
           obligation.

    04.12. Trace persistence and retention are policy-governed. Retained trace
           evidence may be bounded, rotated, or lossy when loss is represented
           honestly.

    04.13. Trace loss weakens evidential completeness. It does not by itself
           change committed-state correctness.

    04.14. Committed-state truth is governed by the authoritative commit model,
           not by trace completeness.

Reasoning:

    This preserves the old intent that some observability data can be best
    effort, while preventing the architecture from treating all traces as
    disposable.

    It also preserves the DA-03/DA-04 distinction:

        trace explains and proves within retained evidence
        committed state defines authoritative state truth

    The corrected middle is:

        required trace emission where a domain owns such an obligation
        honest loss evidence when trace is missing/lost
        committed-state correctness remains governed by DA-04


RECOMMENDED CHANGE 3: LOCAL-FIRST CLARIFICATION
===============================================

Current problem:

    DA-01 says Turnix is local-first and assumes local filesystem, limited
    hardware, and limited context window.

    This is mostly correct, but Dv3 now allows Turnix to run through different
    host shapes:

        - same-machine desktop runtime
        - RuntimeHost on one LAN machine and frontend on another
        - home server RuntimeHost with local SavePack/state ownership
        - powerful local AI machine hosting execution while lighter clients
          present UI
        - explicit remote-resource or federated modes under policy

    The local-first doctrine should not accidentally become:

        local-only forever

Relevant doctrine from later audited documents:

    DA-28:
        Local-first does not require same-machine execution.

        Local-first means authoritative runtime and state remain under
        user-controlled local infrastructure.

        RuntimeHost is the running host boundary through which Kernel-owned
        authority is started, exposed, coordinated, and closed.

Recommended clarification:

    Local-first should mean local operation remains the baseline authority,
    persistence model, failure model, and recovery model.

    It should not ban explicit, policy-governed LAN, server, remote-resource,
    or federated modes.

Suggested replacement direction:

    04.19. Turnix is local-first.

    04.20. Local-first means authoritative runtime and state remain under
           user-controlled local infrastructure.

    04.21. Local-first does not require same-machine execution.

    04.22. Explicit, policy-governed LAN, server, remote-resource, or
           federated modes may exist without replacing local-first as the
           baseline authority, persistence model, failure model, and recovery
           model.

    04.23. Turnix assumes:
           - local filesystem
           - limited hardware
           - limited context window

    04.24. Server-scale patterns are rejected by default, including:
           - lazy global registries
           - infinite retries
           - implicit availability

Reasoning:

    This keeps local-first as the default philosophy while leaving room for
    runtime-hosted, LAN, server, remote-resource, or federated modes under
    explicit policy.

    This also matches the existing open-question section, which already does
    not fully ban remote assets, remote compilers, or federated indexes.


RECOMMENDED CHANGE 4: KEEP PACK IDENTITY GENERAL
================================================

Current problem:

    DA-01 is a top-level philosophy document.

    Once PackManager exists as an official domain, there is a risk that DA-01
    may drift from:

        Turnix has packs and pack management.

    into:

        Turnix is the pack manager / launcher / catalog / graph-preparation
        system.

Why this is a problem:

    DA-29 intentionally creates PackManager so pack catalog, graph preparation,
    graph repair, risk presentation, source management, and selected-graph
    intent handling can exist in one domain without making the rest of Turnix
    clever or heuristic.

    But DA-29 also prevents PackManager from becoming hidden authority.

Relevant doctrine from later audited documents:

    DA-29:
        PackManager is the official Turnix pack-management and
        graph-preparation domain.

        PackManager is not Kernel authority, discovery, generic resolution,
        importing, activation, execution adapter, mechanical loader,
        capability permission, persistence authority, View authority, policy
        owner, AppInstance lifecycle owner, SavePack authority, or Turnix
        identity.

        PackManager helps choose and explain what Turnix will try.

        Turnix still performs only accepted graph, activation plan, policy, and
        operation through Kernel-mediated boundaries.

Recommended change:

    Keep pack references in DA-01 broad and doctrinal.

    DA-01 may say packs are first-class mechanisms for describing,
    distributing, composing, extending, and persisting runtime behavior.

    DA-01 should not describe Turnix as:

        - a pack manager
        - a launcher
        - a catalog system
        - an AppPack runner
        - a graph-preparation tool
        - a pack-management application

    DA-01 should not explain detailed PackManager semantics.

Reasoning:

    DA-01 should anchor the identity:

        Turnix is a runtime.
        Packs are first-class but not identity-defining.
        PackManager is an official management domain inside Turnix.

    DA-29 owns detailed PackManager semantics.


WHAT SHOULD NOT CHANGE
======================

The same-language authority doctrine should remain.

Reason:

    It protects one of the most important Dv3 boundaries:

        Internal Turnix Python is trusted backend implementation.
        Pack-provided Python is external code.

    Pack-provided code should not gain direct backend authority merely because
    it is written in the same language or happens to run in the same process.

    DA-16 reinforces the same rule from the capability side:

        same process, same runtime, or same language does not bypass capability
        mediation.

The runtime authority ordering should remain.

Reason:

    It already supports Dv3:

        Kernel owns authority.
        RuntimeHost exposes controlled entry surfaces.
        Adapters execute declared pack code.
        Transports carry messages.
        RPC defines the logical communication boundary.
        Capabilities define what code may do.
        SavePack stores durable executed state.

    This is compatible with the idea that Kernel is important but intentionally
    not over-specified.

    DA-28 confirms that RuntimeHost is not Kernel authority. It is the running
    host boundary through which Kernel-owned authority is started, exposed,
    coordinated, and closed.

    Entry surfaces and command surfaces may request, observe, or control
    through mediated runtime paths, but they do not become authority
    themselves.

SavePack wording should remain watched, but not changed in DA-01 yet.

Reason:

    DA-04 confirms that committed state, not trace, is authoritative.

    The phrase "SavePack stores durable executed state" may eventually need to
    be checked against later SavePack/AppInstance documents.

    If SavePack wording is revised later, likely preferred wording may become:

        SavePack stores durable AppInstance state.

    Do not change this in DA-01 until SavePack/AppInstance documents are
    audited.

The "no guarantees outside orchestration" invariant should remain.

Reason:

    This strongly supports the Dv3 Job / OrchestrationUnit model.

    DA-24 confirms that mutation outside orchestration does not acquire Turnix
    guarantees by implication.

    DA-24 also confirms that OrchestrationUnit authority does not bypass DA-04
    transaction and commit rules.

    DA-29 confirms the same invariant from the PackManager side.

    PackManager can prepare and explain selected pack graph intent, but it does
    not silently activate, import, load, execute, mutate SavePack state, mutate
    active AppInstance graph state, remember decisions, broaden policy, grant
    capability permission, or bypass Kernel-mediated operation paths.


READABILITY / MACHINE INTERPRETATION NOTE
=========================================

DA-01 intentionally avoids RFC-style MUST/SHOULD/MAY language and says
normative meaning comes from sentence structure and context.

This is acceptable.

However, examples inside locked-invariant sections can become global doctrine
for a machine assistant.

Known risks and handling:

    Trace risk:
        Listing "traces" beside "logs" and "analytics" under optional
        best-effort data may be interpreted as a broad statement that traces
        are nonessential.

        Handle this by splitting trace categories:
            - optional diagnostic/verbose traces
            - domain-required trace emission obligations
            - policy-governed trace persistence/retention/loss evidence

        Preserve the DA-04 rule:
            committed-state correctness is not trace-backed correctness

    PackManager risk:
        Words such as "repair", "prepare", "manage", or "help choose" can be
        misread as permission for PackManager to automatically fix pack graphs.

        Handle this by preserving the distinction between:
            - pack management
            - selected graph intent
            - resolution
            - activation
            - importing
            - execution
            - capability permission
            - persistence authority
            - runtime identity

        PackManager repair must mean explicit, scoped, policy/user-mediated
        graph-preparation repair, not hidden automatic correction.


RECOMMENDED EDIT ORDER
======================

1. Rewrite the identity section first.

   Goal:
       Move Turnix from "pack-built system" toward "runtime domain".

2. Patch trace optionality.

   Goal:
       Prevent contradiction with Dv3 trace doctrine while preserving the
       distinction between trace evidence and committed state.

       Required final doctrine:

           trace emission may be required by domain obligation
           trace persistence is policy-governed
           trace loss weakens evidential completeness
           committed-state correctness is governed by DA-04

3. Add local-first clarification.

   Goal:
       Preserve local-first as baseline authority without banning future
       explicit LAN/server/remote-resource/federated modes.

       Make clear that local-first means user-controlled local infrastructure,
       not same-machine-only.

4. Keep pack identity general.

   Goal:
       Preserve packs as first-class without making Turnix into AppPack runner,
       PackManager, catalog system, launcher, or graph-preparation tool.

5. Do not expand DA-01 into detailed subsystem doctrine.

   Goal:
       DA-01 should remain the top-level philosophy anchor.

       DA-01 should not become the detailed specification for:
           - RuntimeHost
           - Trace
           - Memory
           - OrchestrationUnit
           - Job
           - Capability
           - PackManager
           - AppInstance
           - SavePack
           - RPC
           - ExecutionAdapter


POSSIBLE FUTURE FOLLOW-UP
=========================

Later documents should define in more detail:

    - RuntimeHost
    - Kernel
    - AppInstance
    - AppPack
    - SavePack
    - ExecutionAdapter
    - RPC protocol vs transport
    - Capabilities
    - Jobs
    - OrchestrationUnit

    - Memory latest-state guarantee
    - IOManager authority
    - PackManager
    - standalone subsystem usage

DA-01 should only anchor the doctrine.

It should not become the full Turnix architecture specification.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-01.

Rewrite the project identity so Turnix is clearly a runtime, not merely an
AppPack/modular-pack application system.

Preserve packs as first-class, but not identity-defining.

Do not describe Turnix as PackManager, catalog system, launcher, AppPack runner,
or graph-preparation tool.

Patch trace wording so trace is not treated as merely optional diagnostics.

Use DA-03/DA-04-compatible wording for trace:

    domain-required trace emission is not optional as an obligation

    trace persistence is policy-governed and may be lossy when loss is
    represented honestly

    trace loss weakens evidential completeness

    committed-state correctness is governed by DA-04, not by trace completeness

Clarify local-first using DA-28-compatible wording:

    local-first, not local-only
    user-controlled local infrastructure, not necessarily same-machine-only

Do not weaken the same-language authority doctrine.

Do not weaken the "no guarantees outside orchestration" invariant.

Do not expand DA-01 into a detailed RuntimeHost, trace, memory,
OrchestrationUnit, Job, Capability, PackManager, AppInstance, SavePack, RPC, or
ExecutionAdapter specification.
