SUMMARY
=======

DA-01 should remain the top-level philosophy anchor.

No heavy rewrite is recommended.

DA-01 currently defines:

    - Turnix core identity
    - the Core Truth Doctrine
    - locked project invariants
    - highest-level runtime authority ordering
    - adjustable design attitudes
    - explicitly open philosophical questions

DA-01 already states that it does not define detailed subsystem mechanics such
as pack formats, resolution rules, activation mechanics, RPC schemas,
transport behavior, persistence formats, storage layout, UI behavior, tooling
implementation, concrete adapter behavior, RuntimeHost behavior, workspace
ownership, command-surface behavior, or transport implementation details.

The rewrite should therefore make DA-01 clearer without turning it into the
full architecture specification.

Required DA-01 content changes:

    1. Rewrite project identity so Turnix is clearly a runtime, not a
       pack-built application system.

    2. Patch trace wording so trace is not treated as merely optional
       diagnostics, while also not making trace persistence equivalent to
       committed-state authority.

    3. Clarify local-first so it means user-controlled local infrastructure,
       not same-machine-only and not local-only forever.

    4. Keep pack identity general so packs remain first-class without becoming
       the whole identity of Turnix.

Rewrite-boundary guardrails:

    Later DA documents provide detailed ownership of pack discovery,
    visibility, resolution, dependencies, importing, activation, capabilities,
    RPC, adapters, RuntimeHost, PackManager, Jobs, state, and orchestration.

    Those ownership notes are not suggested DA-01 content.

    They exist to prevent DA-01 from absorbing detailed subsystem semantics or
    accidentally redefining subsystem authority.

Overall recommendation:

    KEEP BUT UPDATE

ACTUAL DA-01 CHANGE 1: PROJECT IDENTITY
=======================================

Current problem:

    DA-01 currently says Turnix exists to enable a persistent, local,
    identity-stable system "built on modular packs".

Why this should change:

    The phrase "built on modular packs" can make packs sound like the
    foundation of Turnix's identity.

    That points toward:

        Turnix = pack-based app system

    Dv3 wants:

        Turnix = runtime domain
        packs = first-class composition/distribution/deployment mechanism
        apps = one kind of thing the runtime can host

Recommended DA-01 change:

    Rewrite the opening identity section so Turnix is described as a runtime,
    not as a pack-built app system.

Suggested DA-01 replacement direction:

    02.1. Turnix exists to provide a persistent, local-first, identity-stable
          runtime for traceable and orchestrated systems.

    02.2. Turnix is not defined by any single launch mode, pack format, user
          interface, host process, model provider, application packaging
          strategy, catalog surface, graph-preparation tool, or RuntimeHost
          realization.

    02.3. Modular packs are a first-class Turnix mechanism for describing,
          distributing, composing, extending, and persisting runtime behavior,
          but packs do not define the whole identity of Turnix.

    02.4. Turnix is not:
          - a plugin loader
          - a dynamic script runner
          - a web app framework
          - a convenience-first modding system
          - a pack-only application launcher
          - a pack manager
          - a catalog system
          - a graph-preparation tool
          - a root-discovery system
          - a pack-discovery system

    02.5. Turnix is:
          - a runtime continuity engine
          - a deterministic resolver
          - a policy-driven orchestrator
          - an explainable system
          - a controlled execution and state boundary

Core DA-01 doctrine to preserve:

    Turnix does not merely run AppPacks.

    Turnix runs AppInstances.

    AppPack is one declarative way to create an AppInstance.

    Packs remain first-class, but they are not identity-defining.


ACTUAL DA-01 CHANGE 2: TRACE OPTIONALITY
========================================

Current problem:

    In the best-effort section, traces are listed with logs and analytics as
    explicitly optional data.

Why this should change:

    Dv3 treats trace as structured runtime evidence, not merely debugging
    output.

    But trace must also not be confused with committed state.

Recommended DA-01 change:

    Patch the best-effort section to avoid saying "traces are optional" as a
    global doctrine.

    Do not overcorrect by making trace persistence equivalent to committed-state
    persistence.

Suggested DA-01 replacement direction:

    04.10. Best-effort behavior is acceptable only for explicitly optional
           non-authoritative data such as:
           - diagnostic logs
           - verbose diagnostic traces
           - analytics

    04.11. Domain-required trace evidence is not optional as an emission
           obligation.

    04.12. Trace persistence and retention are policy-governed. Retained trace
           evidence may be bounded, rotated, or lossy when loss is represented
           honestly.

    04.13. Trace loss weakens evidential completeness. It does not by itself
           change committed-state correctness.

    04.14. Committed-state truth is governed by the authoritative commit model,
           not by trace completeness.

Doctrine to preserve during rewrite:

    Trace evidence is not merely optional diagnostics.

    Domain-owning documents may require trace emission for meaningful actions.

    Required trace emission is an emission obligation.

    Trace persistence and retention are policy-governed.

    Trace loss weakens evidential completeness.

    Trace loss does not by itself change committed-state correctness.

    Committed-state truth is governed by DA-04's commit model.

Avoid these interpretations:

    - trace is just optional logging
    - trace persistence failure invalidates committed state
    - retained trace evidence is as authoritative as committed state
    - Turnix uses trace-backed correctness

DA-03 owns detailed trace substrate semantics.

DA-04 owns committed-state authority.


ACTUAL DA-01 CHANGE 3: LOCAL-FIRST CLARIFICATION
================================================

Current problem:

    DA-01 says Turnix is local-first and assumes local filesystem, limited
    hardware, and limited context window.

    This is mostly correct, but the wording should not accidentally become:

        local-only forever

Recommended DA-01 change:

    Clarify local-first as baseline authority and state ownership, not
    same-machine-only execution.

Suggested DA-01 replacement direction:

    04.19. Turnix is local-first.

    04.20. Local-first means authoritative runtime and state remain under
           user-controlled local infrastructure.

    04.21. Local-first does not require same-machine execution.

    04.22. Explicit, policy-governed LAN, server, remote-resource, or
           federated modes may exist without replacing local-first as the
           baseline authority, persistence model, failure model, and recovery
           model.

    04.23. Turnix assumes:
           - local filesystem
           - limited hardware
           - limited context window

    04.24. Server-scale patterns are rejected by default, including:
           - lazy global registries
           - infinite retries
           - implicit availability

Doctrine to preserve during rewrite:

    local-first, not local-only

    user-controlled local infrastructure, not necessarily one process or one
    physical machine

DA-28 owns detailed RuntimeHost and local/LAN exposure semantics.


ACTUAL DA-01 CHANGE 4: KEEP PACK IDENTITY GENERAL
=================================================

Current problem:

    DA-01 is a top-level philosophy document.

    It should not drift from:

        Turnix has packs, discovery, resolution, activation, import, and pack
        management.

    into:

        Turnix is the pack manager, launcher, catalog, discovery system,
        resolver, importer, activator, or graph-preparation system.

Recommended DA-01 change:

    Keep pack-related wording broad and doctrinal.

    DA-01 may say packs are first-class mechanisms for describing,
    distributing, composing, extending, and persisting runtime behavior.

    DA-01 may say pack-related systems are runtime subsystems inside Turnix.

    DA-01 should not define their detailed behavior.

Suggested DA-01-level wording:

    Pack-related systems such as discovery, visibility, resolution, dependency
    resolution, importing, activation, and pack management are runtime
    subsystems inside Turnix.

    They support Turnix's runtime model, but they do not define Turnix's
    identity and must not be treated as authority roots by themselves.

Do not describe Turnix as:

    - a pack manager
    - a launcher
    - a catalog system
    - an AppPack runner
    - a graph-preparation tool
    - a pack-management application
    - a root-discovery system
    - a pack-discovery system
    - a visibility/indexing system
    - a generic resolver
    - a dependency solver
    - an import/module-loading system
    - an activation system

Do not explain detailed PackManager, discovery, identity, visibility, indexing,
resolution, dependency, activation, import, or pack-management semantics inside
DA-01.


REWRITE-BOUNDARY GUARDRAILS, NOT SUGGESTED DA-01 CONTENT
=========================================================

This section is not suggested DA-01 wording.

It exists to prevent architectural drift during rewrite when the editor knows
DA-01 but may not have the later DA documents loaded.

Use these as guardrails only.

Pack-chain guardrails:

    Packs are first-class but not identity-defining.

    Discovery is input/candidate production, not runtime identity.

    Visibility is eligibility to be seen, not runtime authority.

    Resolution selects from an explicit context, not runtime identity.

    Dependency declarations are hard requirements, not activation or permission.

    Importing/module loading is not activation or execution authority.

    Activation is controlled executable participation, not project identity.

    PackManager is a management domain, not Turnix identity or authority root.

Owning-document boundaries:

    DA-09 owns root and discovery semantics.

    DA-10 owns pack identity, hierarchy, and visibility semantics.

    DA-11 owns generic resolution semantics.

    DA-12 owns importing, module loading, and code-boundary semantics.

    DA-13 owns dependency, requirement, and PackRequest dependency semantics.

    DA-14 owns activation lifecycle and execution guarantees.

    DA-29 owns detailed PackManager semantics.

Local rewrite rule:

    DA-01 may name these concepts at philosophy level.

    DA-01 should not define their detailed behavior.

    DA-01 should not become a mini-index of pack architecture.

    DA-01 should only anchor that these are runtime subsystems inside Turnix,
    not Turnix identity and not authority roots by themselves.


WHAT SHOULD NOT CHANGE
======================

Same-language authority doctrine should remain.

Reason:

    Internal Turnix Python is trusted backend implementation.

    Pack-provided Python is external code.

    Pack-provided code should not gain direct backend authority merely because
    it is written in the same language or happens to run in the same process.

Preserve this boundary for:

    - same-language execution
    - same-process execution
    - in-process transport
    - direct-call optimization
    - frontend messages
    - RuntimeHost command surfaces
    - pack declarations
    - PackContext access

DA-16 owns capability mediation detail.

DA-23 owns detailed ExecutionAdapter, PackContext, same-language, same-process,
and direct-call boundary semantics.


Runtime authority ordering should remain.

Current ordering to preserve:

    Kernel owns authority.
    RuntimeHost exposes controlled entry surfaces.
    Adapters execute declared pack code.
    Transports carry messages.
    RPC defines the logical communication boundary.
    Capabilities define what code may do.
    SavePack stores durable executed state.

This ordering is compatible with Kernel being important but intentionally not
over-specified.

RuntimeHost is not Kernel authority.

Entry surfaces and command surfaces may request, observe, or control through
mediated runtime paths, but they do not become authority themselves.


SavePack wording should remain watched, but not changed in DA-01 yet.

Current wording:

    SavePack stores durable executed state.

Possible later wording after SavePack/AppInstance audit:

    SavePack stores durable AppInstance state.

Do not change this in DA-01 until SavePack/AppInstance documents are audited.


The "no guarantees outside orchestration" invariant should remain.

Reason:

    Mutation outside orchestration does not acquire Turnix guarantees by
    implication.

    OrchestrationUnit authority does not bypass DA-04 transaction and commit
    rules.

    PackManager can prepare and explain selected pack graph intent, but it does
    not silently activate, import, load, execute, mutate SavePack state, mutate
    active AppInstance graph state, remember decisions, broaden policy, grant
    capability permission, or bypass Kernel-mediated operation paths.


READABILITY / MACHINE INTERPRETATION NOTE
=========================================

DA-01 intentionally avoids RFC-style MUST/SHOULD/MAY language and says
normative meaning comes from sentence structure and context.

This is acceptable.

However, examples inside locked-invariant sections can become global doctrine
for a machine assistant.

Known risks and handling:

    Trace risk:
        Listing "traces" beside "logs" and "analytics" under optional
        best-effort data may be interpreted as a broad statement that traces
        are nonessential.

        Handle this by splitting trace categories:
            - optional diagnostic/verbose traces
            - domain-required trace emission obligations
            - policy-governed trace persistence/retention/loss evidence

    PackManager risk:
        Words such as "repair", "prepare", "manage", or "help choose" can be
        misread as permission for PackManager to automatically fix pack graphs.

        Handle this by preserving the distinction between:
            - pack management
            - selected graph intent
            - resolution
            - activation
            - importing
            - execution
            - capability permission
            - persistence authority
            - runtime identity

    Pack-chain risk:
        Words such as "discover", "available", "candidate", "root", "catalog",
        "listed", "visible", "resolved", "required", "imported", "loaded", or
        "active" can be misread as runtime availability or authority.

        Handle this by preserving the distinction between:
            - root existence
            - discovered candidate
            - listed pack
            - visible pack
            - selected graph member
            - resolved dependency
            - activated pack
            - imported code
            - runtime-loaded code
            - capability availability
            - runtime identity


RECOMMENDED EDIT ORDER
======================

1. Rewrite the identity section first.

   Goal:
       Move Turnix from "pack-built system" toward "runtime domain".

2. Patch trace optionality.

   Goal:
       Prevent contradiction with Dv3 trace doctrine while preserving the
       distinction between trace evidence and committed state.

3. Add local-first clarification.

   Goal:
       Preserve local-first as baseline authority without banning future
       explicit LAN/server/remote-resource/federated modes.

4. Keep pack identity general.

   Goal:
       Preserve packs as first-class without making Turnix into AppPack runner,
       PackManager, catalog system, launcher, graph-preparation tool,
       root-discovery system, pack-discovery system, visibility/indexing
       system, generic resolver, dependency solver, importer, or activator.

5. Do not expand DA-01 into detailed subsystem doctrine.

   Goal:
       DA-01 should remain the top-level philosophy anchor.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-01.

Rewrite the project identity so Turnix is clearly a runtime, not merely an
AppPack/modular-pack application system.

Preserve packs as first-class, but not identity-defining.

Do not describe Turnix as PackManager, catalog system, launcher, AppPack runner,
graph-preparation tool, root-discovery system, pack-discovery system,
visibility/indexing system, generic resolver, dependency solver, importer, or
activator.

Patch trace wording so trace is not treated as merely optional diagnostics.

Use DA-03/DA-04-compatible wording for trace:

    domain-required trace emission is not optional as an obligation

    trace persistence is policy-governed and may be lossy when loss is
    represented honestly

    trace loss weakens evidential completeness

    committed-state correctness is governed by DA-04, not by trace completeness

Clarify local-first using DA-28-compatible wording:

    local-first, not local-only
    user-controlled local infrastructure, not necessarily same-machine-only

Do not weaken the same-language authority doctrine.

Do not weaken the "no guarantees outside orchestration" invariant.

Do not expand DA-01 into a detailed RuntimeHost, trace, memory,
OrchestrationUnit, Job, Capability, PackManager, root discovery, pack discovery,
identity, visibility, indexing, resolution, dependency, activation, import,
AppInstance, SavePack, RPC, or ExecutionAdapter specification.
