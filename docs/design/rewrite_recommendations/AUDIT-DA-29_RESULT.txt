==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Superseded by Proposal P02 in its terminology layer; useful only as
    translated boundary-preservation guidance.

    Do not keep the recommendation as an obsolete historical artifact. Use it
    only to preserve still-valid PackManager boundaries after translating
    SavePack, AppInstance, and PackContext into the architecture model.

Document verdict:
    Keep with terminology and boundary fixes.

DA-29 is architecturally strong as a PackManager boundary document.

The recommendation file correctly identifies that DA-29 should not receive a
heavy rewrite. It correctly protects PackManager as the official Turnix
pack-management and graph-preparation domain without turning it into Kernel,
discovery, resolver, importer, activator, loader, capability, permission,
persistence, policy, user-decision, View, RuntimeHost, or adapter authority.

The recommendation also correctly highlights the main local watch item:

    repair must mean explicit, scoped, policy/user-accepted graph-preparation
    repair, not automatic hidden correction.

However, both the recommendation and the DA-29 candidate still use older
architecture vocabulary from before Proposal P02.

Proposal P02 updates the model from:

    AppInstance -> Application / ApplicationRun
    SavePack    -> SaveBundle
    PackContext -> ModCallContext

That means DA-29's PackManager role, responsibilities, and stop-lines should be
preserved, but its old identity and persistence vocabulary must be replaced
before it is treated as accepted architecture documentation.

Primary conclusion:
    Keep DA-29's PackManager model, but rewrite it into canonical architecture
    vocabulary. Do not preserve SavePack/AppInstance/PackContext wording as
    historical residue inside the current document.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-29 should not keep older terminology as a historical artifact.

Specifically, the rewrite should not preserve:

    - SavePack as a Pack kind
    - SavePack listing as ListPacks filtered to SavePack kind
    - AppInstance as runtime identity vocabulary
    - PackContext as gateway vocabulary
    - old trace/context names merely for continuity if there is no compatibility
      reason

If a legacy alias is intentionally retained, DA-29 should say so explicitly and
should still state the canonical architecture term as primary.

Otherwise, the old names should be removed or translated.

The useful part of the old recommendation is not the old terminology. The useful
part is the PackManager boundary:

    PackManager can inspect, explain, prepare, validate, repair, and manage
    catalog/graph intent, but it does not become Kernel, resolver, activator,
    loader, capability authority, persistence authority, RuntimeHost, View,
    Application lifecycle owner, SaveBundle owner, or ModCallContext owner.

==============================================================================
01B. DOCUMENT-METADATA LEAKAGE CHECK
==============================================================================

The final DA-29 document should read as architecture documentation, not as audit,
version, or rewrite-process metadata.

Do not include statements such as:

    - This is V3 design.
    - In V3, PackManager works differently.
    - The new design uses Proposal P02.
    - This rewrite changed PackManager terminology.
    - Unlike V2, DA-29 now uses SaveBundle.
    - Codex kept SavePack wording.
    - This audit decided to use ModCallContext.
    - DA-29 was rewritten because of the audit.

Those facts may be useful in audit files, branch notes, migration notes,
compatibility notes, changelogs, or editor instructions. They do not belong in
the architecture document itself.

The final DA-29 should simply define PackManager catalog operations,
graph-preparation authority boundaries, repair/risk handling, PackManager views,
write boundaries, and PackManager-domain trace ownership.

==============================================================================
02. WHAT DA-29 GETS RIGHT
==============================================================================

02.1. PackManager boundary is strong
------------------------------------

DA-29 correctly defines PackManager as the official Turnix pack-management and
graph-preparation domain.

It correctly says PackManager prepares, explains, validates, repairs, and
manages selected pack graph intent.

It correctly blocks PackManager from becoming:

    - Kernel authority
    - discovery
    - generic resolution
    - importing
    - activation
    - execution adapter
    - mechanical loader
    - capability permission
    - persistence authority
    - View authority

This boundary should be preserved.

02.2. Catalog is not graph
--------------------------

DA-29 correctly separates catalog listing from graph selection.

It correctly says ListPacks is a listing primitive and that listed packs are not
necessarily selected, dependencies, activated, importable, or capability
available.

This distinction should be preserved.

02.3. Graph is not activation
-----------------------------

DA-29 correctly separates selected pack graph, activation plan, import,
execution, activation, and ModCallContext gateway authority.

It correctly states that preparing an activation plan does not activate packs,
import code, execute code, or create gateway authority.

This distinction should be preserved.

02.4. Repair and risky graph semantics are strong
-------------------------------------------------

DA-29 correctly states that risk acceptance does not make a graph safe, does not
rewrite pack metadata, does not satisfy hard dependencies by itself, does not
grant capability permission, and does not convert failure into success.

It correctly treats expected-break evidence as diagnostic evidence, not success.

It correctly defines repair as explicit and scoped rather than hidden automatic
correction.

This should be preserved and made more visible in the revised file.

02.5. View and frontend boundaries are strong
---------------------------------------------

DA-29 correctly says PackManager Views are presentation and interaction surfaces.

It correctly says displaying PackManager UI does not grant PackManager authority
to the displaying surface.

It correctly says frontend PackManager code does not directly mutate pack
catalogs, selected graphs, roots, SaveBundle/Application material, or
configuration.

Keep this model, but use canonical names.

02.6. Trace ownership is mostly correct
---------------------------------------

DA-29 correctly owns PackManager-domain trace reason identifiers and correctly
says they do not replace trace reasons owned by other domains.

Keep this, but update trace context vocabulary to canonical architecture type
names.

==============================================================================
03. MAJOR REQUIRED FIX: CANONICAL ARCHITECTURE TERMINOLOGY
==============================================================================

The current DA-29 still uses older names in many places:

    SavePack
    AppInstance
    PackContext

Proposal P02 updates the type map:

    Application:
        one durable application individual

    ApplicationRun:
        one live execution period of an Application

    SaveBundle:
        durable persistence closure of the Application

    ModCallContext:
        invocation-scoped Pack-bound gateway into Turnix

DA-29 should be migrated to these names.

This is not cosmetic. These names carry different architecture boundaries.

03.1. SavePack -> SaveBundle
----------------------------

Replace SavePack with SaveBundle where DA-29 is referring to durable persisted
application closure, copied packs, pinned pack references, last-used graph
evidence, last-known-good graph evidence, export/import, or save-local retained
material.

Important correction:
    SaveBundle is not a Pack.

Therefore DA-29 must not define SavePack listing as ListPacks filtered to
SavePack kind unless the project deliberately keeps a separate Pack-like
SavePack concept. Under Proposal P02, that would be wrong.

Current risky wording:

    SavePack listing is ListPacks filtered to SavePack kind and relevant save
    roots or save contexts.

Required correction:

    SaveBundle listing is not ListPacks filtered by Pack kind.

    PackManager may list SaveBundles, SaveBundle-associated graph evidence,
    copied Pack material, pinned Pack bindings, retained Pack material, and
    SaveBundle compatibility evidence through a SaveBundle/catalog or
    persistence-aware operation.

    Pack listing remains about Packs.

    SaveBundle listing remains about durable application persistence closures.

Where DA-29 needs to talk about packs physically contained in a SaveBundle, say:

    copied or retained Pack material inside a SaveBundle

not:

    SavePack as a Pack kind

03.2. AppInstance -> Application / ApplicationRun
-------------------------------------------------

Replace AppInstance according to meaning:

    Application:
        use when referring to the durable application individual, its identity,
        its SaveBundle binding, its accepted graph lineage, or future reload.

    ApplicationRun:
        use when referring to one active runtime incarnation, active graph
        evidence, running packs, currently active adapters, live Views, live Jobs,
        current runtime contexts, or changes affecting a running application.

Examples:

    OLD:
        PackManager operations may exist before any AppInstance exists.

    BETTER:
        PackManager operations may exist before any Application exists.

    OLD:
        PackManager operations may also be requested from an AppInstance.

    BETTER:
        PackManager operations may also be requested from an ApplicationRun when
        policy, capability, RuntimeHost, and authority boundaries permit that
        request.

    OLD:
        PackManager may prepare a graph for AppInstance creation.

    BETTER:
        PackManager may prepare a graph for Application creation or for a future
        ApplicationRun, depending on the operation.

    OLD:
        PackManager may inspect active graph evidence for an AppInstance.

    BETTER:
        PackManager may inspect active graph evidence for an ApplicationRun when
        policy permits that inspection.

    OLD:
        PackManager graph changes affecting a running AppInstance require...

    BETTER:
        PackManager graph changes affecting a running ApplicationRun require...

03.3. PackContext -> ModCallContext
-----------------------------------

Replace PackContext with ModCallContext where the document refers to the Pack-
facing invocation gateway.

Examples:

    OLD:
        PackManager does not grant PackContext authority.

    NEW:
        PackManager does not grant ModCallContext gateway authority.

    OLD:
        Activation plan does not grant PackContext authority.

    NEW:
        Activation plan does not grant ModCallContext gateway authority.

This matters because DA-30 now exists as the ModCallContext semantics document.

03.4. Add DA-30 to upstream / ownership references
--------------------------------------------------

DA-29 currently references DA-14 for ModCallContext gateway authority in one
place. That was reasonable before DA-30 existed, but now DA-30 owns
ModCallContext invocation gateway semantics.

Update the upstream/stop-line references to include DA-30.

Recommended boundary:

    activation lifecycle remains DA-14

    ModCallContext gateway semantics remain DA-30

    ExecutionAdapter boundary remains DA-23 / DA-27

Do not make DA-29 define ModCallContext.

==============================================================================
04. SECONDARY FIXES
==============================================================================

04.1. SaveBundle is not PackManager's Pack-kind listing target
--------------------------------------------------------------

Review every use of:

    AppPack, SavePack, ViewPack, ContentPack, and ModPack listing as filters over
    Pack kind

Update it to avoid classifying SaveBundle as a Pack kind.

Possible replacement:

    ListPacks is the general pack-listing primitive.

    AppPack, ViewPack, ContentPack, and ModPack listings are ListPacks filtered
    by Pack kind.

    SaveBundle-related listing is a separate persistence/catalog operation over
    durable Application persistence closures and their retained Pack graph
    evidence. It may expose copied, pinned, embedded, or retained Pack material,
    but the SaveBundle itself is not a Pack.

04.2. Scope vocabulary needs canonical architecture alignment
------------------------------------------------------------

Current scopes include:

    RuntimeHost scope
    workspace scope
    AppPack scope
    SavePack scope
    AppInstance scope
    tooling scope
    test scope

Update to:

    RuntimeHost scope
    Workspace scope
    AppPack / AppDefinition scope
    SaveBundle scope
    Application scope
    ApplicationRun scope
    tooling scope
    test scope

Define the split clearly:

    Application scope:
        durable application identity, saved graph lineage, migrations, and
        SaveBundle-bound graph planning.

    ApplicationRun scope:
        active graph inspection, active activation evidence, pending graph
        changes affecting a live run, and operations that may affect running
        Pack material.

04.3. Trace context identifiers need canonical architecture alignment
--------------------------------------------------------------------

Current trace context includes appInstanceId and SavePack identity.

Update to use:

    applicationId
    applicationRunId when applicable
    SaveBundle identity when applicable

Use appInstanceId only if the project deliberately keeps AppInstance as alias.
If kept as alias, the document should say so explicitly elsewhere. Otherwise,
do not preserve old terminology by accident.

04.4. Locked summary needs canonical architecture alignment
----------------------------------------------------------

Update the locked summary so it does not lock stale names.

Replace:

    SavePack
    AppInstance
    PackContext

with:

    SaveBundle
    Application
    ApplicationRun
    ModCallContext

as appropriate.

04.5. Recommendation file has old terminology too
-------------------------------------------------

The recommendation file has merit only after translation into canonical
architecture terms.

When using it as guidance, translate:

    SavePack -> SaveBundle
    AppInstance -> Application / ApplicationRun
    PackContext -> ModCallContext

Do not copy its old names into the revised DA-29 unless intentionally preserving
legacy aliases.

Do not preserve the old terminology as historical material inside DA-29.

==============================================================================
05. WHAT TO PRESERVE FROM CURRENT DA-29
==============================================================================

Preserve these PackManager boundaries almost unchanged, except for terminology
migration:

    - PackManager is official Turnix management and graph-preparation domain.
    - PackManager is not authority root.
    - PackManager is not discovery.
    - PackManager is not generic resolution.
    - PackManager is not importing.
    - PackManager is not activation.
    - PackManager is not execution adapter.
    - PackManager is not mechanical loader.
    - PackManager is not capability permission.
    - PackManager is not persistence authority by itself.
    - PackManager is not policy or user-decision authority.
    - PackManager is not View authority.
    - PackManager helps choose and explain what Turnix will try.
    - Turnix performs accepted graph, activation plan, policy, and runtime
      operations through Kernel-mediated boundaries.
    - Catalog operations do not lazily rescan filesystem.
    - Catalog listing does not imply selected graph membership.
    - Catalog listing does not imply activation.
    - Catalog listing does not imply importability.
    - Catalog listing does not imply capability availability.
    - Visibility presentation does not grant visibility.
    - Resolution presentation does not persist hidden decisions.
    - Advisory relations do not become hard dependencies by themselves.
    - Risk acceptance does not make a graph safe.
    - Expected-break evidence does not convert failure into success.
    - Selected graph and activation plan do not execute, import, activate, or
      grant ModCallContext authority.
    - PackManager does not call onLoad(ctx).
    - PackManager does not authorize adapter execution.
    - PackManager does not grant capability permission.
    - PackManager writes use Kernel-mediated persistence, configuration,
      transaction, and policy boundaries.
    - PackManager Views are presentation and interaction surfaces.
    - PackManager UI does not own the semantics it presents.
    - PackManager trace reasons do not replace trace reasons owned by other
      domains.

06. WHAT TO ADD OR CHANGE IN THE REVISED DA-29
==============================================================================

06.1. Add a canonical terminology note
--------------------------------------

Add a short note near the document role or interpretation section:

    This document uses canonical architecture type names:

        Application
        ApplicationRun
        SaveBundle
        ModCallContext

    Older terms such as AppInstance, SavePack, and PackContext are not used
    unless explicitly declared as legacy aliases in another document.

Do not write this as "V3 names", "new names", or "after the rewrite".

Do not overdo this section. It is there to prevent stale-name drift.

06.2. Adjust the document description
-------------------------------------

Current description says PackManager handles user policy, SavePack history, and
selected graph intent before activation.

Update to:

    user policy, SaveBundle graph evidence, retained Pack material, and selected
    graph intent before activation.

Avoid implying SaveBundle is a Pack.

06.3. Adjust the `It defines` list
----------------------------------

Replace SavePack references with SaveBundle references.

Remove SavePack from Pack-kind listing.

Add SaveBundle-related catalog/persistence operation language.

06.4. Adjust the `It does NOT define` list
------------------------------------------

Update ownership references:

    AppPack/Application/ApplicationRun identity remains DA-20 or newer successor.

    SaveBundle persistence closure and ownership remain DA-20 / SaveBundle
    documents / persistence documents as appropriate.

    ModCallContext gateway semantics remain DA-30.

06.5. Adjust PackManager scopes
-------------------------------

Replace SavePack scope and AppInstance scope with:

    SaveBundle scope
    Application scope
    ApplicationRun scope

Describe each one compactly.

06.6. Adjust trace reason names only if desired
-----------------------------------------------

Existing trace reason identifiers include names like SavePackGraphCheckRequested.

Do not rename trace reason identifiers casually if the project treats them as
stable event vocabulary. However, because this terminology is still being aligned,
consider whether the trace reason identifiers should become SaveBundleGraph*
instead of SavePackGraph*.

If keeping old trace reason identifiers as compatibility names, document the
reason and make clear they are not canonical conceptual terminology.

If not keeping them, rename them consistently.

Recommendation:
    Prefer SaveBundleGraph* unless there is a compatibility reason to keep
    SavePackGraph*.

06.7. Keep implementation-schema details open
---------------------------------------------

Do not define concrete catalog envelopes, selected graph schema, activation-plan
schema, PackManager capability identifiers, command syntax, RPC fields, package
source/index protocols, or active ApplicationRun graph-change policy in DA-29.

Those remain implementation/specification work.

==============================================================================
08. ACCEPTANCE CONDITIONS FOR THE REVISED DA-29
==============================================================================

A revised DA-29 is acceptable when all of the following are true:

    - It preserves PackManager as official management and graph-preparation
      domain.

    - It preserves PackManager as tooling/management surface, not authority root.

    - It preserves catalog/graph/activation/import/capability distinctions.

    - It preserves no-lazy-rescan catalog listing semantics.

    - It preserves advisory relation versus hard dependency distinction.

    - It preserves repair as explicit, scoped, policy/user-accepted
      graph-preparation repair.

    - It preserves risk acceptance as diagnostic/accepted-risk evidence, not
      safety and not success.

    - It preserves expected-break evidence as diagnostic evidence, not success.

    - It preserves selected graph and activation plan as intent/preparation, not
      execution, import, activation, or ModCallContext authority.

    - It preserves PackManager Views as presentation and interaction surfaces,
      not authority.

    - It preserves PackManager writes as Kernel-mediated persistence,
      configuration, transaction, and policy operations.

    - It preserves PackManager-domain trace reason ownership without replacing
      other domains' trace reasons.

    - It removes stale SavePack-as-Pack-kind semantics.

    - It uses SaveBundle for durable application persistence closure material.

    - It uses Application and ApplicationRun instead of AppInstance where
      appropriate.

    - It uses ModCallContext instead of PackContext for gateway authority.

    - It includes DA-30 as the owning document for ModCallContext gateway
      semantics.

    - It does not keep old SavePack/AppInstance/PackContext terminology as a
      historical layer inside the current DA-29 text.

    - It keeps concrete schemas, command syntax, RPC fields, package-source
      protocols, and active ApplicationRun graph-change policy open.

    - It does not mention audit provenance, rewrite process, old/new design, V3,
      Codex, candidate status, or branch history as ordinary architecture text.

==============================================================================
09. FINAL EDITOR INSTRUCTION
==============================================================================

Keep DA-29 as the PackManager catalog and graph-preparation document.

Do not perform a heavy conceptual rewrite of the PackManager boundary.

Do perform a terminology and boundary-alignment rewrite against Proposal P02 and
the checkpoint posture.

Use the REWRITE-DA-29 recommendation only as translated boundary-preservation
guidance. Do not keep the recommendation as an obsolete historical artifact and
do not copy its stale terminology into the rewritten DA.

Do not include audit/source metadata or version/process framing in the final
DA-29 documentation. The final DA-29 should not say this is V3 design, in V3,
new design, old design, rewritten design, created by Codex, decided by audit, or
part of a rewrite-history process.

The revised DA-29 should still feel like the same architecture document:
PackManager owns catalog operation semantics, selected graph intent,
activation-plan preparation, repair/risky-graph presentation, PackManager Views,
PackManager write boundaries, and PackManager-domain trace reasons.

The revised DA-29 should not become a SaveBundle specification, Application
lifecycle specification, ModCallContext specification, activation specification,
resolution specification, visibility specification, dependency specification,
RuntimeHost specification, or concrete catalog/graph schema specification.

The main work is to remove accidental old-model vocabulary so the otherwise
strong PackManager document does not fossilize pre-P02 terminology or preserve
old persistence/runtime concepts as architecture terminology.
