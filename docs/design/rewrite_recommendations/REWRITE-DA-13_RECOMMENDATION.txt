SUMMARY
=======

DA-13 should be kept.

No heavy rewrite is recommended.

DA-13 owns dependency declaration semantics and dependency-specific resolution
policy above DA-11 generic resolution mechanics.

DA-13 should preserve the core rule:

    Dependencies are hard functional requirements.

    Dependencies are contracts, not preferences.

    Advisory pack relations are hints, not dependencies.

Declaring or resolving a dependency does not:

    - load code
    - activate a pack
    - grant visibility
    - grant capabilities
    - grant runtime access
    - grant capability permission
    - define activation order
    - consult last-known-good fallback during dependency resolution

Overall recommendation:

    KEEP WITH SMALL PROVIDER-ROLE / REGISTRATION WATCH

PRESERVATION RULE 1: DEPENDENCIES ARE HARD CONTRACTS
====================================================

Preserve DA-13's core concept.

A dependency expresses a hard functional requirement:

    This pack cannot function correctly unless another pack exists that
    satisfies this request.

Dependencies are contracts, not preferences.

Failure to satisfy a hard dependency is a hard failure unless an explicit
policy or user decision from the owning decision layer resolves it.

Do not add automatic disabling, downgrade, substitution, or best-effort
continuation to DA-13.


PRESERVATION RULE 2: SHARED PACK-SPECIFIER STRUCTURE DOES NOT MEAN SHARED SEMANTICS
===================================================================================

Preserve the shared pack-specifier model.

A hard dependency field, advisory field, and role-related field may reuse the
same pack-specifier structure while producing different higher-level meaning.

Shared syntax does not imply shared semantics.

Do not let shared syntax become shared authority.

Fingerprint is an optional strengthening of an exact concrete pack form.

Fingerprint is an exact-artifact lock, not a vague compatibility hint.


PRESERVATION RULE 3: PACKS FIELD MEANS HARD DEPENDENCIES ONLY
=============================================================

Preserve hard dependency declaration semantics.

DA-13 defines the manifest field:

    packs

as the hard dependency field.

Rules:

    - absence of "packs" means no hard dependencies
    - an empty list means explicitly no hard dependencies
    - every entry under "packs" is a hard dependency
    - list order carries no semantic meaning by itself

DA-13 does not define optional, soft, or advisory dependency semantics for the
"packs" field.


PRESERVATION RULE 4: PACKREQUEST IN DEPENDENCY CONTEXT ADDS DEPENDENCY POLICY
==============================================================================

Preserve the DA-11 / DA-13 split.

DA-11 owns PackRequest grammar and generic resolution mechanics.

DA-13 owns how a PackRequest is interpreted when the requesting relationship is
a dependency.

In dependency context, PackRequest means:

    - resolve one satisfying concrete dependency target
    - obey dependency-source policy
    - obey dependency version and fingerprint rules
    - fail explicitly if no permitted dependency outcome exists

Dependency context does not change PackRequest structure.

Dependency context adds dependency policy around DA-11 mechanics.


PRESERVATION RULE 5: ACCEPTED-ENTRY NORMALIZATION PRESERVES EXACT-ARTIFACT LOCKS
================================================================================

Preserve accepted-entry normalization.

A dependency is satisfied if at least one normalized accepted entry can be
resolved successfully under the active dependency-resolution source and context.

Fingerprint requires exact concrete version.

Invalid forms remain invalid:

    - name plus fingerprint with no version
    - name plus range plus fingerprint
    - name plus wildcard plus fingerprint

Multiple accepted entries in the same dependency express one-of semantics at
the accepted-entry level.

Fingerprint expectation is an exact-artifact lock for that accepted entry.


PRESERVATION RULE 6: DEPENDENCY-RESOLUTION SOURCES ARE MUTUALLY EXCLUSIVE
=========================================================================

Preserve the dependency-resolution source model.

DA-13 defines three mutually exclusive dependency-resolution sources:

    - SaveOnly
    - GlobalPinned
    - GlobalNormal

Every hard dependency is resolved from exactly one dependency-resolution source.

The resolver does not mix these sources silently.

The resolver does not fall back between these sources silently.

Source meanings:

    SaveOnly:
        SavePack copied material only.

    GlobalPinned:
        pinned global identity only.

    GlobalNormal:
        ordinary global registry only.


PRESERVATION RULE 7: SAVEONLY IS SAVEPACK COPIED MATERIAL ONLY
==============================================================

Preserve SaveOnly semantics.

SaveOnly applies when the dependency's packTreeId is listed in SavePack
metadata as copied.

Under SaveOnly:

    - only copied packs inside that SavePack are eligible
    - the global registry is not consulted
    - absence of the copied pack is a hard error

Saved packs under this model:

    - are identified by full identity
      (author + packTreeId + version)
    - are owned by the SavePack
    - are immutable unless explicitly replaced
    - are visible only within that save context

This preserves save-local isolation and prevents global content from silently
repairing missing copied SavePack material.


PRESERVATION RULE 8: GLOBALPINNED IS PINNED GLOBAL IDENTITY ONLY
================================================================

Preserve GlobalPinned semantics.

GlobalPinned applies when the dependency is bound to a pin in SavePack metadata.

Under GlobalPinned:

    - only the pinned concrete identity is eligible
    - resolution occurs in the global registry only
    - a missing pinned identity is a hard error
    - the pin does not imply copying or saving

Pins express explicit historical intent and bypass selector-based candidate
choice.

Do not let GlobalPinned fall back to GlobalNormal.


PRESERVATION RULE 9: GLOBALNORMAL IS ORDINARY GLOBAL REGISTRY ONLY
==================================================================

Preserve GlobalNormal semantics.

GlobalNormal applies in all other dependency cases.

Under GlobalNormal:

    - resolution occurs in the global registry only
    - SavePack content is not consulted
    - selection follows the deterministic GlobalNormal procedure

GlobalNormal does not apply to:

    - SaveOnly copied material
    - GlobalPinned pinned identity
    - copied SavePack material
    - pinned graph identity
    - explicit selected graph semantics


PRESERVATION RULE 10: VERSION AND FINGERPRINT ENFORCEMENT STAY HARD
===================================================================

Preserve version and fingerprint enforcement.

If a semantic-version requirement is present, only candidates allowed by that
requirement remain eligible.

If a concrete version is requested:

    - only that version is eligible
    - mismatch is a hard failure

If a version range is requested:

    - only matching versions are eligible
    - surrounding policy may restrict further

If no semantic-version requirement exists, or if "*" is used:

    - all versions remain eligible

If no eligible versions remain, dependency resolution fails with
VersionMismatchError.

If an accepted entry declares a fingerprint:

    - the resolved dependency must also match that fingerprint
    - fingerprint mismatch is a non-success outcome for that accepted entry


PRESERVATION RULE 11: GLOBALNORMAL SELECTION IS DETERMINISTIC AND SCOPED
========================================================================

Preserve GlobalNormal selection procedure.

No scoring model exists.

Procedure:

    Step 1 - version handling
        - if a concrete version is specified:
          only that version remains eligible
        - if a range or versionless form is specified:
          the highest semantic version is preferred
        - packs without version metadata are ordered last

    Step 2 - author relationship ordering
        1) exact requested author
        2) same author as the requesting pack
        3) different known author
        4) unknown author

    Step 3 - root precedence
        custom
        first-party
        third-party

    Step 4 - final tie-break
        lexicographic order of:
        "<author>@<packTreeId>@<version>"

Selection rule:

    - the first eligible candidate is selected
    - silent substitution is forbidden

GlobalNormal ordering must not be applied to SaveOnly or GlobalPinned.

GlobalNormal ordering must not override SavePack copied material, pinned
dependencies, pinned graph identity, or explicit selected graph semantics.


PRESERVATION RULE 12: PROVIDER ROLES ARE NOT CAPABILITY CALLS
=============================================================

Preserve requiredRoles / providedRoles separation.

DA-13 defines role requirements separately from hard pack dependencies.

Manifest field for role requirements:

    requiredRoles

Manifest field for role providers:

    providedRoles

A required role means the pack expects one provider of that named role to be
available when the surrounding runtime logic uses it.

requiredRoles is a dependency/resolution-layer declaration.

requiredRoles is not a runtime capability call.

providedRoles means a pack can serve as a provider for those roles.

providedRoles does not itself grant capability permission.

requiredRoles does not itself force loader reordering or magical
dependency-graph mutation.

PackManager may use role metadata to help users build sensible load lists, but
runtime behavior remains explicit.


WATCH ITEM: PROVIDER-ROLE REGISTRATION
======================================

DA-13 says that if several providers declare the same role, runtime/provider
selection behavior is defined outside this document.

It also says that by current locked design, the first registered provider wins
by default, and specific-provider request may be used programmatically.

This remains a watch item.

Provider/runtime documents must define:

    - what "registered" means
    - who may register providers
    - where provider registration lives
    - whether registration order is deterministic
    - whether activation order controls registration order
    - whether PackManager load-list order controls registration order
    - whether provider selection is trace-visible
    - whether provider selection grants capability-like power
    - whether specific-provider request bypasses policy or permission

"First registered provider wins" is safe only if registration order itself is
deterministic, scoped, trace-visible, and authority-safe.


PRESERVATION RULE 13: ADVISORY PACK RELATIONS ARE HINTS
=======================================================

Preserve advisory pack relation semantics.

Advisory fields:

    - supportedPacks
    - conflictingPacks
    - recommendedPacks

They reuse the shared pack-specifier structure.

The surrounding advisory field defines the meaning.

Advisory pack relations are hints.

Advisory pack relations are not:

    - hard dependencies
    - hard activation blockers
    - generic resolution constraints
    - loader/runtime warning rules by themselves

Advisory pack relations are for:

    - PackManager
    - UI
    - compatibility presentation
    - helping the user assemble a load list

Advisory pack relations do not participate in dependency graph enforcement or
activation validity.

A shared pack-specifier structure does not upgrade advisory metadata into
dependency semantics.


PRESERVATION RULE 14: AMBIGUITY REQUIRES EXTERNAL INVOLVEMENT
==============================================================

Preserve ambiguity handling.

If deterministic dependency selection cannot produce one unambiguous candidate,
dependency resolution pauses.

Ambiguity is surfaced explicitly.

User decision or accepted policy input is then required.

Once such a decision is made, future runs remain deterministic.

The resolver does not guess.

DA-17 owns remembered-decision scope and no silent broadening.


PRESERVATION RULE 15: DEPENDENCY FAILURE IS EXPLICIT AND NOT SILENT FALLBACK
============================================================================

Preserve failure conditions.

Dependency resolution fails explicitly if:

    - no candidates remain after hard constraints
    - dependency-resolution source rules are violated
    - a pinned or saved identity is missing
    - ambiguity cannot be resolved
    - no permitted decision path exists

Dependency-resolution failure is:

    - explicit
    - classified
    - observable
    - never silently resolved by fallback


PRESERVATION RULE 16: LAST-KNOWN-GOOD IS NOT DEPENDENCY-RESOLUTION FALLBACK
===========================================================================

Preserve last-known-good fallback boundary.

Turnix stores the last successfully activated graph per SavePack.

Resolution always attempts fresh dependency resolution first.

Last-known-good is not consulted during dependency resolution.

Last-known-good fallback is used only after activation failure.

Fallback procedure:

    1) abort current activation
    2) attempt activation using the stored graph
    3) propagate failure if fallback fails

Correct model:

    Dependency resolution remains strict.

    Activation may later decide to attempt last-known-good graph fallback.

    That fallback is activation/recovery behavior, not dependency success.


SOURCE BOUNDARY STATEMENT: DEPENDENCIES ARE CONTRACTS, ADVISORY RELATIONS ARE HINTS
===================================================================================

DA-13 may include this compact source-level boundary:

    Dependencies are hard functional requirements.

    Dependency declarations are contracts, not preferences.

    Advisory pack relations are hints, not dependencies.

    Shared pack-specifier syntax does not imply shared semantics.

    Dependency resolution uses DA-11 generic mechanics but adds dependency-source
    policy, version and fingerprint enforcement, and dependency-context outcome
    rules above those mechanics.

    Declaring or resolving a dependency does not load code, activate a pack,
    grant visibility, grant capabilities, grant runtime access, define
    activation order, or consult last-known-good fallback during dependency
    resolution.

This source-level boundary is useful because DA-13 owns dependency semantics and
dependency-specific resolution policy.

Detailed ownership mapping belongs in the guardrail section.


WATCH ITEM: GLOBALNORMAL ROOT PRECEDENCE
========================================

custom > first-party > third-party is correct inside GlobalNormal.

Keep verifying that this does not apply to:

    - SaveOnly
    - GlobalPinned
    - copied SavePack material
    - pinned graph identity
    - explicit selected graph semantics


WATCH ITEM: DA-17 DECISIONS
===========================

Ambiguity decisions and accepted policy input must not silently broaden across:

    - packs
    - versions
    - SavePacks
    - RuntimeHosts
    - trust classes
    - provider roles

DA-13 should not define remembered-decision behavior.

DA-17 owns remembered-decision scope.


WATCH ITEM: TRACE WORDING
=========================

Follow the DA-03 cross-document trace wording check.

Dependency trace obligations are dependency-domain emission obligations.

Trace retention and loss remain governed by DA-03.

Do not let trace wording imply that dependency trace evidence is committed
state or that trace persistence is guaranteed forever.


WATCH ITEM: PACKMANAGER USE OF ADVISORY RELATIONS
=================================================

DA-29 should use advisory pack relations for presentation and graph preparation
without turning them into:

    - hard dependencies
    - hard activation blockers
    - generic resolution constraints
    - loader/runtime warning rules by themselves

PackManager may present advisory relation evidence and help prepare graph
intent.

PackManager must not silently upgrade advisory metadata into dependency
authority.


WATCH ITEM: SAVEPACK / APPINSTANCE GRAPH SEMANTICS
==================================================

SavePack / AppInstance documents should define copied, pinned, and selected
graph behavior consistently with:

    - SaveOnly
    - GlobalPinned
    - GlobalNormal

SaveOnly and GlobalPinned must remain source-specific dependency policies.

Selected graph, pinned graph, copied pack graph, and durable AppInstance state
must not be silently collapsed into ordinary GlobalNormal resolution.

CURRENT FINAL RECOMMENDATION
============================

Keep DA-13.

No heavy rewrite is recommended.

Recommended future edits:

    - keep dependencies as hard contracts
    - keep advisory relations as hints only
    - keep shared pack-specifier syntax from implying shared semantics
    - keep dependency-resolution sources mutually exclusive
    - keep SaveOnly / GlobalPinned / GlobalNormal source boundaries strict
    - keep GlobalNormal precedence scoped to GlobalNormal only
    - keep fingerprint as exact-artifact lock
    - keep provider roles separate from capability invocation and permission
    - define provider registration and selection in the owning provider/runtime
      document
    - keep ambiguity decisions external and DA-17-scoped
    - keep last-known-good as activation/recovery fallback only, not
      dependency-resolution fallback

Do not expand DA-13 into detailed PackRequest parsing grammar, generic
Phase-A / Phase-B resolution mechanics, trace schema/storage, activation
lifecycle, visibility rules beyond dependency gating, PackManager heuristics,
PackManager load-list generation, capability invocation, capability permission,
provider runtime registration, Job lifecycle, AppInstance lifecycle,
RuntimeHost behavior, or concrete activation recovery behavior.
