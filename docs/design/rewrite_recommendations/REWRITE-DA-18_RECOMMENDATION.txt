ACTUAL DA-18 CHANGE 1: WINDOW CROSS-REFERENCE SHOULD BE UPDATED
===============================================================

DA-18 currently says it does not define:

    authoritative committed state, transactions, or windows (see DA-04)

Recommended future rewrite:

    DA-18 does not define:
        - authoritative committed state or transaction semantics (see DA-04)
        - Window, SafePointWindow, ActiveWindow, AbortedWindow, or Window
          finalization semantics (see DA-08)

Reason:

    DA-04 owns committed-state truth and transaction semantics.

    DA-08 owns Window kinds, Window ordering, SafePointWindow, ActiveWindow,
    AbortedWindow, Window finalization, and Window-domain trace obligations.

This is a source-level cross-document correction, not a conceptual rewrite.

PRESERVATION RULE 1: DEBUGGING IS SEMANTIC, NOT LANGUAGE-INTERNAL FIRST
======================================================================

Preserve the debugging model.

Debugging in Turnix is not primarily:

    - print-statement debugging
    - ad-hoc logging
    - attaching debuggers to arbitrary threads

Debugging in Turnix is:

    - intentional
    - observable
    - reversible where the surrounding state model allows reversal
    - scoped

Turnix debugging operates on Turnix concepts rather than language internals as
the primary debugging surface.

Primary debugging targets include:

    - packs
    - activation
    - pipelines
    - memory layers
    - capabilities
    - Jobs when Jobs exist

Python frames or JavaScript call stacks may appear as contextual information.

They are not the primary debugging model.


PRESERVATION RULE 2: BREAKPOINTS ARE SEMANTIC
=============================================

Preserve semantic breakpoint classes.

Turnix supports semantic breakpoints rather than code-line breakpoints.

Supported semantic breakpoint classes include:

    - pipeline-stage breakpoints
    - memory breakpoints
    - capability breakpoints
    - Job-scoped breakpoints when Jobs exist

Pipeline-stage breakpoints may inspect prompt, memory composition, and
transformations.

Memory breakpoints observe state transitions rather than storage mechanics.

Capability breakpoints may observe capability invocations that later create or
attach to Jobs.

Capability breakpoints do not own Job lifecycle when a Job is created or
attached.


PRESERVATION RULE 3: MEMORY BREAKPOINTS ALIGN WITH DA-04 TRANSACTION AUTHORITY
==============================================================================

Preserve transaction-aware memory breakpoint semantics.

Definitions:

    staged mutation:
        write into a transactional layer

    committed mutation:
        write that becomes visible in a committed authoritative memory layer
        after successful commit

    aborted mutation:
        staged mutation discarded during abort

By default, memory breakpoints trigger on committed mutations only.

Writing into a transactional layer does not trigger a memory breakpoint by
default.

Aborting a transaction does not trigger a memory breakpoint by default.

Only the moment a value becomes authoritative is breakpoint-visible by default.

Memory breakpoints may explicitly observe staged mutations.

If staged observation is enabled, a breakpoint may specify:

    - observeStaged = true
    - observeCommitted = true or false

Every memory-breakpoint hit is classified as exactly one of:

    - StagedMutation
    - CommittedMutation

A child transaction commit into a parent transaction is not treated as a
committed mutation.

Only the outermost transaction commit produces authoritative
committed-mutation events.

This preserves determinism and aligns debugger semantics with DA-04.


PRESERVATION RULE 4: DEBUGGER INSPECTION IS READ-ONLY BY DEFAULT
================================================================

Preserve live debugging without pause.

Debugger inspection may be used while Turnix is running normally.

Debugger inspection does not require:

    - a breakpoint hit
    - Turnix to be paused

A user may open inspectors, browse state, and request read-only views at any
time.

Inspection is read-only by default.

Inspection surfaces do not silently collapse committed and staged state into one
undifferentiated view.

Inspecting transactional state does not turn staged values into authoritative
state.

Inspecting committed-state history does not bypass the committed-state
authority model.

Inspecting a Job does not grant direct access to the underlying execution
mechanism.

If debugger inspection presents committed values represented by ValueRef /
Chunk material, DA-05 still owns the representation and decode semantics.

Debugger inspection does not make hidden filesystem or storage access
authority. Persistent reads remain DA-07-mediated where persistent material is
accessed.


PRESERVATION RULE 5: BREAKPOINT PAUSE DOES NOT MUTATE OR DECIDE OUTCOMES
========================================================================

Preserve breakpoint behavior.

When a breakpoint triggers:

    - execution of the triggering unit pauses
    - mutation-capable execution for the owning AppInstance pauses
    - other AppInstances may continue if the runtime supports that
    - non-mutating Kernel activity may continue unless configured otherwise
    - debugger tooling is notified
    - relevant state becomes inspectable

Breakpoints do not:

    - auto-resume silently
    - alter execution order
    - mutate state by default
    - silently cancel Jobs
    - silently supersede Jobs

Breakpoint pause is not:

    - Job terminal outcome
    - OrchestrationUnit terminal outcome
    - AppInstance stop
    - Window finalization
    - RuntimeHost failure
    - adapter lifecycle outcome
    - DA-26 Replay / Resume / Retry workflow outcome


PRESERVATION RULE 6: DEBUGGER ACTIONS DO NOT BYPASS ORCHESTRATION OR PERSISTENCE
================================================================================

Preserve debugger action authority boundaries.

Debugger actions execute through:

    - Turnix-controlled RPC
    - capabilities
    - equivalent Turnix-mediated interfaces

Debugger tooling does not bypass Turnix orchestration.

Debugger tooling does not access raw filesystem input or output directly as a
bypass path.

Persistence-affecting debugger actions execute through the same authority path
as normal runtime actions.

Debugger-originated Job control actions execute through Turnix lifecycle and
policy surfaces.

Debugger tooling does not mutate Job terminal state directly.

Debugger tooling does not become:

    - Kernel authority
    - persistence authority
    - committed-state authority
    - payload representation authority
    - configuration authority
    - Window finalization authority
    - RuntimeHost authority


PRESERVATION RULE 7: CONTROLLED MUTATION IS EXPLICIT, STAGED, TRACEABLE
=======================================================================

Preserve controlled mutation semantics.

Explicit debugger mutation is allowed only through:

    - debugger actions
    - explicit user confirmation where required
    - trace logging

Examples include:

    - editing a memory value
    - disabling or modifying a breakpoint
    - forcing resume / continue or abort of a debugger pause scope

Every debugger-initiated mutation emits trace evidence.

Debugger tooling may create its own temporary transactional overlay for
controlled staged edits.

A debugger-created temporary transactional overlay remains subject to the same:

    - authority rules
    - scope rules
    - ownership rules
    - trace rules
    - transaction rules

that govern other transactional mutation.

A debugger-created temporary transactional overlay does not become authoritative
merely because the debugger created it.

If debugger tooling uses such an overlay, the overlay remains distinct from
committed state until normal commit rules make the mutation authoritative.

Job lifecycle control is not controlled mutation of committed state.

Job lifecycle control remains constrained by DA-19 and policy handling when
policy participates.


PRESERVATION RULE 8: MUTATION WHILE RUNNING REQUIRES PAUSE OR SAFE POINT
========================================================================

Preserve mutation-while-running constraints.

Controlled mutation may be performed while Turnix is active and not paused.

Rules:

    - mutation is explicit user action in debugger tooling
    - mutation is traceable and labeled as debugger-initiated
    - mutation obeys the same permission, ownership, and scope rules as normal
      runtime actions

If a mutation affects data that active execution units may read concurrently,
the debugger either:

    - requires a manual pause
    - enforces deterministic apply-at-safe-point semantics

Debugger mutation while running must not become hidden concurrent mutation.

Debugger mutation while running must not bypass:

    - DA-04 transaction and commit rules
    - DA-05 committed-value representation when committed values are affected
    - DA-06 configuration semantics when configuration is affected
    - DA-07 persistent-I/O authority when persistent material is affected


PRESERVATION RULE 9: MANUAL PAUSE AND APPLY-AT-SAFE-POINT ARE NON-TERMINAL
===========================================================================

Preserve manual pause and apply-at-safe-point semantics.

Manual pause may operate by enforcing quiescence at defined safe points such as:

    - between pipeline stages
    - between capability calls
    - before commit points for persistence

Manual pause is deterministic.

Manual pause does not silently cancel in-flight work.

Manual pause does not silently supersede in-flight work.

Manual pause of a Job remains non-terminal unless a later explicit lifecycle or
policy outcome changes the Job state under DA-19.

When Turnix is not paused, debugger-initiated mutations may be staged and
applied only at a deterministic safe point.

Rules:

    - staging is traceable
    - the exact safe point where mutation becomes visible is traceable
    - staged mutations do not partially apply
    - if the safe point is never reached, the staged mutation is discarded
      deterministically and traced

Debugger safe point is an execution/mutation safety boundary.

Debugger safe point is not SafePointWindow by default.

Debugger pause-at-safe-point does not automatically create Window finalization.


PRESERVATION RULE 10: UNDO IS NEW EXPLICIT MUTATION
==================================================

Preserve undo/redo semantics.

Debugger tooling may support undo of debugger-initiated changes within the
boundaries defined by the Turnix state model.

Undo that affects authoritative state operates on committed revisions.

Undo that affects authoritative state is performed as a new explicit
debugger-initiated mutation.

Undo that affects authoritative state is trace-visible.

Undo does not bypass:

    - transaction rules
    - permission rules
    - ownership rules
    - scope rules
    - safe-point rules
    - persistent-I/O authority when persistence is affected

Redo history is debugger-local, ephemeral, and non-authoritative.

Redo history does not become committed state merely because debugger tooling
remembers it.

Redo history is discarded deterministically when a new committed revision makes
the stored redo path no longer valid.

Debugger tooling does not present ephemeral redo state as authoritative system
history.


PRESERVATION RULE 11: DEBUGGER UI DOES NOT OWN DEBUGGER SEMANTICS
=================================================================

Preserve debugger UI boundaries.

Debugger user interfaces may:

    - subscribe via RPC
    - receive breakpoint-hit events
    - show causal context
    - allow resume / continue, step, abort of a debugger pause scope, undo, or
      redo where supported
    - request Job pause-at-safe-point, cancellation, or supersession where
      supported

Debugger user interfaces are optional but supported.

Debugger user interfaces do not present Superseded Job outcomes as failures.

Debugger user interfaces do not present paused-at-safe-point Jobs as terminal.

DA-22 owns debugger UI as frontend surface.

DA-18 owns debugger inspection, breakpoint, pause, mutation, disconnect, and
Job-control semantics.


PRESERVATION RULE 12: STEP MODES DO NOT REDEFINE JOB OR DA-26 WORKFLOWS
========================================================================

Preserve step-mode boundaries.

Supported step modes may include:

    - resume / continue from debugger pause
    - step over, meaning the next stage or memory change
    - abort, meaning fail the current debugger-controlled execution scope

Unsupported step modes include:

    - instruction-level stepping
    - time travel as a runtime debugger mode in DA-18

Step modes do not redefine Job lifecycle states.

If step or abort actions affect a Job, the resulting Job lifecycle outcome
remains governed by DA-19.

Abort of a debugger-controlled execution scope is not automatically the same as
Job cancellation, Job failure, AppInstance failure, or Window abort unless the
owning lifecycle document and policy define that outcome.

Debugger resume / continue does not mean DA-26 Resume.

Debugger abort does not mean AbortedWindow by default.

Debugger step does not imply Replay, Resume, Retry, comparison, or audit
workflow semantics.


PRESERVATION RULE 13: JOB DEBUGGING IS JOB-AWARE BUT NOT JOB-AUTHORITY
======================================================================

Preserve Job-aware debugger boundaries.

If Jobs exist:

    - Jobs are observable through status, owner, progress, terminal outcome,
      and causal trace links
    - Jobs are controlled only through Turnix lifecycle, orchestration, or policy
      surfaces
    - Job lifecycle semantics remain owned by DA-19

Debugger interaction with Jobs may include requests for:

    - pause-at-safe-point for a Job
    - breakpoint-at-safe-point for a Job
    - resume / continue of a paused Job
    - cancellation request for a Job
    - supersession request for a Job where supported

Manual pause does not implicitly cancel Jobs.

Manual pause does not implicitly supersede Jobs.

If a Job cannot reach a safe point:

    - that fact is surfaced explicitly
    - no silent cancellation is permitted
    - no silent supersession is permitted

A paused-at-safe-point Job remains non-terminal.

Debugger-originated cancellation, supersession, continuation, or hold behavior
may require work-lifecycle policy handling under DA-17.

The debugger does not directly write a Job terminal state.

Job terminal outcomes caused or requested through debugger action are recorded
through Job lifecycle evidence owned by DA-19.


PRESERVATION RULE 14: BREAKPOINT SCOPING IS EXPLICIT
====================================================

Preserve breakpoint scoping rules.

Breakpoints may be scoped to:

    - global
    - AppInstance
    - view
    - pack
    - pipeline
    - Job when Jobs exist

Unscoped breakpoints are discouraged.

A Job-scoped breakpoint does not create a Job.

A Job-scoped breakpoint applies only to the Job lifecycle or work region
selected by debugger configuration.

If breakpoint scope crosses AppInstance, View, pack, pipeline, Job, or
OrchestrationUnit boundaries, the owning identity and authority rules still
apply.

A breakpoint scope is not authority by itself.


PRESERVATION RULE 15: DEBUGGER DISCONNECT OUTCOME IS POLICY-GOVERNED
====================================================================

Preserve debugger disconnect failure-mode semantics.

If the debugger disconnects:

    - execution resumes, cancels, supersedes, aborts the affected
      debugger-controlled scope, or refuses to hold according to policy
    - the chosen outcome is trace-visible
    - deadlock is not allowed

Debugger disconnect outcome trace evidence distinguishes:

    - execution resumed after debugger disconnect by policy
    - active work cancelled, superseded, or aborted after debugger disconnect by
      policy
    - hold refused because holding is unsupported, unsafe, or impossible

If breakpoint logic errors:

    - the breakpoint is disabled
    - the error is trace-visible

If debugger disconnect policy affects a Job, the Job lifecycle outcome remains
governed by DA-19.

If debugger disconnect policy is a work-lifecycle policy decision, policy
handling remains governed by DA-17.

Debugger disconnect does not silently define:

    - OrchestrationUnit terminal outcome
    - AppInstance lifecycle outcome
    - adapter lifecycle outcome
    - RuntimeHost lifecycle outcome
    - Window finalization
    - Replay / Resume / Retry workflow outcome
    - committed-state mutation outcome


PRESERVATION RULE 16: DEBUGGER TRACE REASONS DO NOT DEFINE OTHER OUTCOMES
=========================================================================

Preserve debugger-domain trace reason ownership.

DA-18 owns debugger-domain trace reason identifiers used for:

    - debugger inspection
    - breakpoints
    - manual pause
    - safe-point pause
    - debugger disconnect outcomes
    - debugger-initiated mutation

Debugger-domain trace reasons describe debugger-domain behavior only.

They do not define:

    - Job terminal outcome
    - OrchestrationUnit terminal outcome
    - Window finalization
    - AppInstance lifecycle outcome
    - adapter lifecycle outcome
    - RuntimeHost lifecycle outcome
    - Replay / Resume / Retry workflow outcome
    - committed-state mutation outcome

DA-03 defines trace event structure, trace DAG semantics, span mechanics, and
trace retention semantics.

DA-17 defines work-lifecycle policy trace obligations when policy participates.

DA-19 defines Job lifecycle trace obligations when debugger-originated control
affects a Job.

Trace evidence remains evidence.

Trace evidence is not committed state.


WATCH ITEM: SAFE-POINT SEMANTICS AND DA-08 ALIGNMENT
====================================================

DA-18 uses safe-point language for manual pause, apply-at-safe-point mutation,
and Job pause-at-safe-point behavior.

Future rewrite should align this with DA-08 without collapsing the domains.

Preserve:

    - debugger safe point is an execution/mutation safety boundary
    - SafePointWindow is a Window finalization committed boundary
    - debugger safe point does not automatically create a SafePointWindow
    - SafePointWindow AtQuiescence does not automatically imply debugger pause
    - debugger pause-at-safe-point does not automatically imply Window
      finalization
    - Job pause-at-safe-point remains non-terminal

When debugger safe-point behavior affects Window creation, DA-08 governs Window
finalization and SafePointWindow creation semantics.

Do not let debugger tooling bypass OrchestrationUnit boundaries.

Do not let debugger tooling bypass transaction and commit boundaries.

Do not let debugger tooling bypass policy decisions.

Do not let debugger tooling bypass capability mediation.

Do not let debugger tooling bypass adapter boundaries.

Do not let debugger tooling bypass DA-07 persistence authority.

Do not let debugger tooling write raw filesystem input/output directly as a
Turnix authority path.

Do not let debugger UI own debugger semantics.

Do not let debugger UI directly write committed state.

Do not let debugger UI directly write Job terminal state.

Do not treat debugger-created transactional overlays as authoritative merely
because the debugger created them.

Do not treat staged debugger mutations as committed state.

Do not apply debugger-staged mutation partially.

Do not hide discarded debugger-staged mutation.

Do not treat undo as rollback magic; undo that affects authoritative state is
new explicit mutation.

Do not treat redo history as authoritative system history.

Do not silently cancel Jobs from debugger tooling.

Do not silently supersede Jobs from debugger tooling.

Do not directly write Job terminal state from debugger tooling.

Do not treat paused-at-safe-point Jobs as terminal.

Do not present Superseded as failure.

Do not let manual pause cancel or supersede in-flight work silently.

Do not let debugger disconnect create deadlock.

Do not treat debugger disconnect policy as Job lifecycle authority; DA-19 owns
Job lifecycle outcome.

Do not treat debugger disconnect policy as work-lifecycle policy authority;
DA-17 owns policy handling.

Do not treat debugger safe point as SafePointWindow by default.

Do not let debugger pause-at-safe-point automatically create Window
finalization.

Do not let debugger "Resume" mean DA-26 Resume unless explicitly routed through
DA-26 semantics.

Do not let debugger "replay-from-trace" mean DA-26 Replay unless explicitly
routed through DA-26 semantics.

Do not let trace-backed debugger behavior imply trace is committed state.

Do not let trace evidence alone restore committed state.

Do not let snapshot / restore bypass DA-04 committed-state authority.

Do not let snapshot / restore bypass DA-05 payload representation.

Do not let snapshot / restore bypass DA-07 persistence authority.

Do not let snapshot / restore bypass DA-08 Window finalization.

Do not let snapshot / restore bypass DA-25 artifact/export semantics.

Do not let snapshot / restore bypass DA-26 Replay / Resume / Retry semantics.

Do not introduce arbitrary Python debugger injection.

Do not introduce JavaScript eval debugging.

Do not modify pack code at runtime.

Do not hot-patch logic without reload.

Do not introduce time-travel runtime debugging under DA-18 without separate
architecture.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-18.

No heavy rewrite is recommended.

Recommended future edits:

    - update the "does NOT define" section so Window semantics point to DA-08,
      not DA-04
    - add modern stop-line references to DA-05, DA-07, DA-08, DA-20, DA-21,
      DA-22, DA-23, DA-24, DA-25, DA-26, DA-27, and DA-28 where needed
    - normalize duplicate local subsection numbering under section 03
    - clarify debugger step-mode Resume as resume / continue from debugger
      pause, not DA-26 Resume
    - clarify replay-from-trace wording as trace-based causal-history inspection
      or explicitly defer formal Replay semantics to DA-26
    - keep DA-18 focused on semantic breakpoints, inspection, controlled
      mutation, manual pause, safe-point application, debugger undo/redo,
      debugger-originated Job control requests, failure modes, and
      debugger-domain trace obligations
    - preserve debugger mutation as explicit, staged, trace-visible, and
      governed by normal authority boundaries
    - preserve debugger safe-point behavior as execution/mutation safety, not
      Window finalization by default
    - preserve debugger-originated Job control as explicit, trace-visible, and
      governed by DA-17 and DA-19
    - leave conditional breakpoint language, snapshot/restore, time-travel,
      trace-based causal-history inspection, and exact debugger UI affordances
      to later documents without weakening current authority boundaries
