==============================================================================
SUMMARY
==============================================================================

ODA-C is a useful optional tooling and ecosystem-support document. Its central
boundary is correct: authoring tools, scaffolds, catalogs, visualizations,
previews, and ecosystem recommendations can reduce friction, but they do not
become runtime authority, do not replace runtime checks, do not activate packs,
do not grant permissions, and do not create new correctness guarantees.

The document is already compact and mostly well-scoped. The required fixes are
small terminology and boundary fixes:

    - translate old AppInstance / SavePack wording into current
      Application / ApplicationRun / SaveBundle terminology
    - clarify that PackManager UX extensions prepare, preview, or explain graph
      intent but do not activate, import, resolve by authority, or repair
      silently
    - prevent "dry-run activation" from being misread as adapter loading, code
      execution, lifecycle callback execution, or provisional runtime mutation
    - clarify ordinary Pack scaffolding around "service provider" so it does not
      expose backend service objects or recreate service-authority confusion
    - keep generated documentation and ecosystem policy advisory, not authority

==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. The tooling boundary is strong.

    The document repeatedly says tooling is advisory, does not change runtime
    semantics, and does not become a runtime authority source.

2. Authoring friction is separated from runtime correctness.

    The document correctly allows development-time help while preserving strict
    runtime behavior.

3. Manifest and configuration tooling are appropriately non-authoritative.

    Manifest tooling does not execute code merely by recognizing artifacts, and
    migration simulation does not commit authoritative state.

4. Catalog and documentation generation are scoped as derived views.

    Capability catalogs do not grant capability permission. Generated
    documentation does not replace the manifest, schema, trace, or runtime
    source material from which it was derived.

5. Ecosystem policy support is framed as advisory.

    Compatibility badges, soft deprecation warnings, advisory version
    constraints, and trust notes are not silently enforced by virtue of ODA-C.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. Current naming/model drift: AppInstance and SavePack wording is stale.

    Proposal P02 updates the current platform model to Application,
    ApplicationRun, SaveBundle, AppPack/AppDefinition, Workspace, and Pack
    activation. ODA-C still uses AppInstance and SavePack wording in graph
    visualization and relation sections.

    Required correction:
        Translate AppPack-to-SavePack and AppInstance relationships into current
        Application / ApplicationRun / SaveBundle terminology.

    Suggested local replacements:

        AppPack to SavePack relationships when available

    should become:

        AppPack/AppDefinition to Application and SaveBundle relationships when
        available

    and:

        AppInstance relationships when viewing runtime evidence

    should become:

        Application and ApplicationRun relationships when viewing runtime
        evidence

    The relation-to-other-areas section should replace DA-20 for AppInstance
    runtime identity with the current Application / ApplicationRun lifecycle and
    runtime-identity design area wording.

2. "Dry-run activation" can be misread as real activation without side effects.

    Section 10 lists dry-run activation and then says dry-run activation does not
    become real activation. That stop-line is helpful, but the phrase remains
    risky because activation has specific semantics: adapter loading, lifecycle
    callbacks, ModCallContext participation, registration surfaces, barriers, and
    possible staged mutation.

    Required correction:
        Prefer "activation-plan preview" or "activation simulation" for tooling
        that does not load code or run lifecycle callbacks.

    Required boundary:
        A tooling preview does not load adapters, evaluate modules, run lifecycle
        callbacks, publish registrations, create Pack participation, create
        ApplicationRun readiness, or mutate accepted runtime state.

    If a future tool actually executes activation-like work, it is not an
    advisory preview. It is separate orchestrated work and must follow the owning
    runtime, adapter, activation, policy, Job, trace, and transaction boundaries.

3. "Previewing the effect of enabling a pack" risks importing enablement as a
   runtime authority concept.

    The word "enabling" can be acceptable as PackManager or UI language, but the
    final document should not imply that ODA-C defines pack enablement semantics,
    activation, visibility, resolution, dependency satisfaction, or permission.

    Required correction:
        Phrase this as previewing selected graph intent, prospective inclusion,
        or a user-selected graph change.

    Required boundary:
        PackManager UX previews do not become discovery, resolution, activation,
        import, visibility grant, dependency satisfaction, capability permission,
        execution authorization, or persistence authority.

4. "Service provider" scaffolding is ambiguous.

    Section 08 says optional generators may create a service provider. In the
    current architecture, Service is trusted internal runtime wiring, while
    Capability is the Pack-facing mediated operation model. Ordinary Pack code
    should not receive or expose raw service objects.

    Required correction:
        Clarify that ordinary Pack scaffolding should prefer capability-provider,
        hook, event, processor, adapter-binding, or other mediated Pack-facing
        patterns.

    If service-provider scaffolding remains, scope it narrowly:
        It applies only to first-party/internal/runtime-extension contexts where
        service registration is explicitly allowed by the owning service/runtime
        documents. It does not expose backend service objects to ordinary Pack
        code and does not collapse capability mediation.

5. Static analysis wording should avoid implying complete proof.

    The document already says static analysis may be incomplete and does not
    replace runtime enforcement. Preserve that. When adding more checks, avoid
    wording that suggests static tooling can prove runtime authority, activation
    success, or execution safety in all cases.

    Required correction:
        Keep static-analysis results as warnings, previews, or early diagnostics
        unless an owning document defines a hard validation rule.

6. Pack graph visualization must not create graph truth.

    Section 06 correctly says visualized relationships do not create authority or
    dependency truth beyond the underlying evidence. Preserve and slightly tighten
    this boundary for current model terms.

    Required correction:
        Say graph tooling visualizes discovered, selected, retained, or
        trace-backed relationships depending on context. It must distinguish
        design-time manifest relationships, selected graph intent, accepted
        runtime graph, retained evidence, and generated documentation output.

7. Ecosystem policy support must not become hidden policy enforcement.

    Section 12 already says ecosystem-policy support is not silently enforced by
    ODA-C alone. Preserve that boundary.

    Required correction:
        Add that ecosystem badges, soft deprecations, recommendations, and
        advisory version constraints do not become hard dependencies, resolution
        constraints, activation blockers, trust decisions, permission decisions,
        or policy decisions unless an owning authoritative document explicitly
        makes them so.

==============================================================================
OBSOLETE-PRESERVATION RISKS
==============================================================================

The main obsolete-preservation risk is old AppInstance / SavePack terminology.

Do not preserve AppInstance as the current primary runtime identity term merely
because older source documents used it. Translate into the current platform
model:

    Application
        durable application individual

    ApplicationRun
        one live execution period of that Application

    SaveBundle
        durable persistence closure of the Application

For ODA-C, most graph/tooling wording should distinguish:

    - AppPack / AppDefinition
        reusable application definition or accepted application-definition source

    - Application
        durable application identity created from an AppPack or accepted
        AppDefinition source

    - ApplicationRun
        live runtime execution period and live diagnostic evidence

    - SaveBundle
        durable persistence closure and retained generations/evidence

    - selected graph intent
        PackManager-prepared or user-selected graph proposal

    - accepted runtime graph
        graph actually accepted by the owning runtime flow

Do not keep AppInstance or SavePack as compatibility/history notes inside final
ODA-C unless the user explicitly wants historical or migration material.
