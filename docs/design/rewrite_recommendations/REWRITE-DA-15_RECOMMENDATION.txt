SUMMARY
=======

DA-15 is Dv3-compatible.

No heavy rewrite is recommended.

Keep DA-15 as the visibility enforcement and reachability access-control
document.

DA-15 should preserve the rule that visibility answers:

    Is pack A permitted to reference pack B?

Visibility is permissioned reachability.

Visibility is not:

    - activation
    - code loading
    - execution order
    - dependency satisfaction
    - version compatibility
    - runtime capability access
    - runtime service access
    - AppInstance authority
    - RuntimeHost authority
    - adapter authority
    - PackManager authority

Visibility violations are hard failures.

No silent bypass, fallback, probing, or runtime negotiation by packs should be
introduced.

Overall recommendation:

    KEEP WITH SMALL DA-10 OVERLAP / PERMISSIONDENIED WORDING WATCH

ACTUAL DA-15 CHANGE 1: CLARIFY DA-10 / DA-15 OWNERSHIP SPLIT
============================================================

DA-10 and DA-15 overlap in visibility concepts.

Preserve this local split:

    DA-10:
        Pack identity, hierarchy, local/global visibility model,
        exportNestedPacks, importPacksFromParent as identity/visibility
        structure.

    DA-15:
        Visibility enforcement, reference reachability, source-domain
        isolation, SavePack visibility isolation, failure behavior, and
        access-control consequences.

Do not expand DA-15 into a full duplicate of DA-10.

Do not remove DA-15 merely because DA-10 exists.

DA-15 is useful as the enforcement/access-control document.


ACTUAL DA-15 CHANGE 2: VISIBILITY STOP-LINE
===========================================

DA-15 should contain a compact source-level boundary statement.

Recommended source-level boundary:

    Visibility answers whether one pack is permitted to reference another pack.

    Visibility is permissioned reachability.

    Visibility does not activate packs, load code, imply execution order,
    satisfy dependencies, grant version compatibility, grant capability access,
    grant service access, authorize adapter execution, create AppInstances,
    grant RuntimeHost command authority, grant PackManager authority, or mutate
    committed state.

    Visibility violations are hard failures.

    Visibility failures do not silently fall back, probe, negotiate, or bypass
    through alternate sources.

This belongs in DA-15 because DA-15 owns visibility enforcement and
access-control consequences.

Detailed ownership mapping belongs in the guardrail section, not in the source

PRESERVATION RULE 1: VISIBILITY IS REFERENCE PERMISSION
=======================================================

Preserve the rule:

    Visibility answers whether one pack is permitted to reference another pack.

Visibility is about reachability and permission only.

Visibility does not:

    - activate packs
    - load code
    - imply execution order
    - imply dependency satisfaction
    - imply version compatibility
    - grant runtime capabilities
    - grant runtime services
    - authorize adapter execution
    - grant RuntimeHost command authority
    - grant PackManager authority
    - mutate committed state

Dependency declaration expresses requirement.

Visibility expresses permission.

A pack may depend on another pack and still be forbidden from referencing it.

If visibility forbids a dependency target, the dependency fails.

No silent bypass is allowed.


PRESERVATION RULE 2: VISIBILITY IS ENFORCED AT USE POINTS
=========================================================

Preserve visibility checks during:

    - dependency resolution
    - resolvePack calls
    - turnixImport resolution

Visibility is not bypassed or deferred.

Visibility is evaluated dynamically between:

    - the requesting pack
    - the target pack

Visibility is not pre-expanded into a static graph.

This allows visibility enforcement to remain contextual without becoming
runtime negotiation by packs.

Adapter execution does not skip visibility.

Same-language execution does not skip visibility.

Same-process execution does not skip visibility.

RuntimeHost command surfaces do not skip visibility.

PackManager presentation does not skip visibility.


PRESERVATION RULE 3: EXPORTNESTEDPACKS REMAINS DIRECT-CHILD ONLY
================================================================

Preserve exportNestedPacks as direct-child export control.

Allowed values:

    - true
    - false
    - list of localId strings

Required constraints:

    - only direct children may be listed
    - dotted identifiers are forbidden
    - non-existent localId is an error
    - exportNestedPacks does not apply transitively

Do not introduce deep implicit export.

Do not let exportNestedPacks become a general visibility wildcard.

Do not let PackManager repair or presentation silently expand
exportNestedPacks.


PRESERVATION RULE 4: IMPORTPACKSFROMPARENT DOES NOT GRANT SERVICES OR CAPABILITIES
=================================================================================

Preserve importPacksFromParent as parent-to-child reference visibility only.

importPacksFromParent does not imply:

    - export
    - capability access
    - service access
    - permission inheritance
    - activation
    - adapter execution authorization
    - RuntimeHost authority

Default values remain:

    - ViewPack -> false
    - all other pack kinds -> true

The ViewPack default should remain isolated unless later source documents
explicitly change view semantics.

List resolution should remain parent-relative:

    resolvedId = parent.packTreeId + "." + selector

Escaping the parent tree is forbidden.

Invalid resolution is a hard error.

Visibility checks still apply after list resolution.


PRESERVATION RULE 5: RESOLUTION SOURCE RESTRICTS VISIBILITY DOMAIN
==================================================================

Preserve this ordering:

    Resolution source is determined first.

    Visibility is evaluated inside that active source domain.

Rules:

    - only packs inside the active source are considered visible candidates
    - packs outside the active source are not visible regardless of declared
      visibility or globalVisibility
    - save-scoped resolution ignores global packs
    - global resolution ignores save-scoped copies
    - visibility does not bridge resolution sources

This is important for DA-13 source rules:

    - SaveOnly
    - GlobalPinned
    - GlobalNormal

Do not let visibility bridge SavePack-local and global source domains.

Do not let PackManager graph preparation, RuntimeHost command surfaces, or
adapter execution bridge source-domain isolation.


PRESERVATION RULE 6: SAVEPACK VISIBILITY IS STRICTLY ISOLATED
=============================================================

Preserve SavePack visibility isolation.

Rules:

    - SavePack is never globally visible
    - SavePack is visible only within its AppInstance context
    - copied packs inside a SavePack are visible only within that save
    - copied packs inside a SavePack are not visible globally
    - copied packs shadow global packs of the same identity within that save
      domain

If a pack is resolved from a save-scoped source:

    - global packs with the same identity are not visible
    - the global registry is not consulted

Do not let SavePack-local copied packs leak into global visibility.

Do not let global custom precedence override SavePack-local copied material by
default.

Do not let RuntimeHost workspace ownership, AppInstance creation, PackManager
views, or adapter execution weaken SavePack visibility isolation.


PRESERVATION RULE 7: CAPABILITIES AND SERVICES ARE NOT VISIBILITY
=================================================================

Preserve capability separation.

Visibility does not:

    - grant capabilities
    - inherit capabilities
    - imply capability access
    - bypass capability request/grant rules
    - satisfy capability permission
    - authorize Job-backed capability execution
    - authorize OrchestrationUnit-backed mutation

Capability access requires explicit request and grant.

Capability permission remains owned by DA-16 and DA-17.

Preserve service separation.

Services are runtime wiring objects.

Visibility does not grant service access.

Service access requires:

    - service registration
    - explicit lookup
    - allowed PackContext or runtime wiring path

Service access remains governed by DA-16 and PackContext authority boundaries.

Visible pack does not mean usable service.

Visible pack does not mean callable capability.

Visible pack does not mean granted permission.


PRESERVATION RULE 8: VISIBILITY DOES NOT AUTHORIZE EXECUTION
===========================================================

Preserve execution-boundary separation.

Visibility may allow a pack to reference another pack.

Visibility does not authorize:

    - importing/module loading
    - activation
    - adapter binding
    - adapter execution
    - adapter lifecycle transition
    - execution authorization for a declared artifact
    - PackContext authority
    - capability invocation
    - RuntimeHost command execution

Declared executable code remains subject to importing, activation,
ExecutionAdapter, capability, permission, policy, RPC-shaped, and
OrchestrationUnit boundaries owned by the relevant documents.

Same-language and same-process execution must not bypass visibility
enforcement.


PRESERVATION RULE 9: PACKMANAGER PRESENTATION IS NOT VISIBILITY AUTHORITY
=========================================================================

Preserve PackManager / visibility separation.

PackManager may inspect, present, prepare, validate, repair, modify, or explain
pack catalogs and selected pack graph intent.

PackManager presentation of visibility does not become visibility authority.

PackManager repair suggestions do not silently override visibility rules.

PackManager graph preparation does not bridge source-domain isolation.

PackManager does not grant capability access, service access, activation,
adapter execution, RuntimeHost authority, AppInstance authority, or committed
state mutation by showing or preparing a graph.

DA-29 owns PackManager graph-management semantics.

DA-15 owns visibility enforcement/access-control consequences.


WATCH ITEM: PERMISSIONDENIEDERROR NAMING
========================================

DA-15 says visibility failure raises PermissionDeniedError.

This is acceptable if the standard error model treats visibility denial as a
permission/access-control failure.

Future edit should check whether the error taxonomy wants a more specific
visibility-denial subtype.

Do not change semantics:

    visibility failure is hard

    visibility failure is classified

    visibility failure includes requesting pack identity, target pack identity,
    and violated rule

    no fallback is permitted

    no probing is permitted

Only the exact error name is a possible taxonomy watch item.


WATCH ITEM: DA-10 / DA-15 DUPLICATION
=====================================

DA-15 restates local visibility, globalVisibility, exportNestedPacks, and
importPacksFromParent concepts also covered by DA-10.

This is not currently harmful.

Future rewrite should avoid divergence:

    DA-10 should own identity/hierarchy/computed visibility model.

    DA-15 should own enforcement/access-control consequences.

If wording differs, preserve the interpretation that maintains:

    - visibility as eligibility/reference permission
    - source-domain isolation
    - SavePack isolation
    - hard failure on violation
    - no capability/service inheritance

    Visibility is not activation.

    Visibility is not adapter execution authorization.

    Visibility is not RuntimeHost authority.

    Visibility is not AppInstance authority.

    Visibility is not PackManager authority.

    Visibility is not committed-state authority.

    Visibility does not grant service access.

    Visibility does not grant PackContext authority.

    Visibility does not grant OrchestrationUnit mutation authority.

    Visibility failure is a hard failure.

    Visibility failure does not permit fallback.

    Visibility failure does not permit probing.

    Visibility failure does not permit runtime negotiation by packs.

    exportNestedPacks is not transitive export.

Local rewrite rule:

    DA-15 may name these concepts when needed to protect visibility enforcement

    DA-15 should not define their detailed behavior.

    DA-15 should remain the visibility enforcement, source-domain isolation,
    SavePack visibility isolation, hard-failure, and access-control consequence

CURRENT FINAL RECOMMENDATION
============================

Keep DA-15.

No heavy rewrite is recommended.

Recommended future edits:

    - keep DA-15 focused on visibility enforcement and access-control
      consequences
    - preserve DA-10 / DA-15 ownership split
    - keep visibility failure hard and explicit
    - keep SavePack visibility strictly isolated
    - check PermissionDeniedError naming only as error-taxonomy polish
    - do not weaken service/capability separation
    - do not let RuntimeHost, PackManager, adapter execution, same-language
      execution, same-process execution, AppInstance context, or SavePack-local
      material bypass visibility enforcement
