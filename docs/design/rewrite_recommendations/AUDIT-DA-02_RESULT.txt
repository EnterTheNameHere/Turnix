==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Correct in substance, but partly stale in terminology.

    The recommendation correctly says DA-02 should be kept and should remain the
    high-level contract-boundary and implementation-independence document.

    However, its AppInstance / SavePack phrasing should not be copied forward as
    current terminology. Translate those terms to Application, ApplicationRun,
    and SaveBundle vocabulary where appropriate.

Document verdict:
    Keep with minor clarification.

DA-02 should remain the high-level document that prevents Turnix platform truth
from becoming defined by a current implementation stack, current RuntimeHost
realization, current adapter strategy, current transport, first-party tooling,
same-process convenience, same-language convenience, direct-call convenience,
current storage backend, current UI/runtime surface, debugger surface, artifact
format, comparison tool, or Replay/Resume/Retry tooling.

The target document is already mostly aligned. It already says platform truth is
contractual, not implementation-shaped. It already separates Kernel authority,
RuntimeHost entry surfaces, adapters, transports, RPC, capabilities, committed
state, ApplicationRun live identity, and durable save persistence.

Main required fixes:

    - preserve platform truth as contractual, not implementation-shaped
    - preserve that platform core is not monolithic
    - preserve same-language, same-process, and direct-call paths as optimizations
      or realization choices, not boundary erasure
    - preserve official first-party tooling as implementation/tooling, not
      platform authority
    - preserve service access as not capability permission
    - preserve ExecutionAdapter as the general adapter category
    - preserve RuntimeHost below Kernel authority
    - preserve interoperability envelope / RPC / transport separation
    - preserve distinction between RPC acknowledgement, request acceptance,
      Job creation, handler execution, adapter execution, RuntimeHost operation,
      and final work outcome
    - preserve discovery as candidate production, not resolution, activation,
      import, runtime loading, or runtime identity
    - preserve implementation independence for payload representation,
      configuration layout, persistent I/O backend, UI/frontend realization,
      debugger surface, artifact/export format, comparison tools, Replay, Resume,
      Retry, and audit tooling
    - translate AppInstance/AppPack/SavePack wording to current Application,
      ApplicationRun, AppDefinition/AppPack, and SaveBundle vocabulary
    - avoid deciding unresolved AppDefinition/AppPack-backing questions in DA-02
    - add or preserve compact owner stop-lines for DA-03 through DA-30 domains
      where DA-02 names them
    - avoid final-document rewrite/process metadata leakage

Primary conclusion:
    Keep DA-02. Do not perform a heavy rewrite. The necessary work is minor
    clarification and terminology alignment.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-02 should not preserve older terms merely because they appear in older source
material or recommendation text.

Specifically, the rewrite should not preserve as current terminology:

    - AppInstance where ApplicationRun is meant
    - AppInstance identity where ApplicationRun live identity is meant
    - AppInstance lifecycle where Application/ApplicationRun lifecycle is meant
    - SavePack where SaveBundle is meant
    - SavePack stores durable AppInstance state as current canonical wording
    - AppPack as the unavoidable backing identity of every possible ApplicationRun
    - PackContext as scoped participation if ModCallContext is meant
    - same-process convenience as authority
    - direct-call convenience as authority
    - first-party tooling convenience as authority
    - current frontend/browser stack as UI truth
    - current WebSocket transport as RPC truth
    - current storage backend or IoManager implementation as committed-state truth
    - current debugger surface as debugger semantics
    - current artifact/export/comparison/replay tool as platform truth

Canonical translations:

    AppInstance -> ApplicationRun where one live execution/incarnation is meant
    AppInstance -> Application where durable application identity is meant
    AppInstance lifecycle -> Application/ApplicationRun lifecycle where both
        durable and live identity layers are involved
    AppPack -> AppDefinition/AppPack where reusable declarative application
        source is meant
    SavePack -> SaveBundle where durable persistence closure is meant
    SavePack stores durable AppInstance state -> SaveBundle stores durable
        Application/ApplicationRun persistence material, or durable save
        persistence stores accepted Application state, depending on intended
        scope
    PackContext -> ModCallContext where invocation-scoped Pack facade is meant
    PackContext -> activation context / entry context where DA-14 activation
        participation is meant

Important clarification:
    The current target already uses ApplicationRun and accepted Application state
    language in the authority ordering. Preserve that direction. Do not regress to
    AppInstance / SavePack wording from the recommendation.

==============================================================================
01B. DOCUMENT-METADATA LEAKAGE CHECK
==============================================================================

The final DA-02 document should read as architecture documentation, not as audit,
version, or rewrite-process metadata.

Do not include statements such as:

    - This is V3 design.
    - In V3, platform truth is contractual.
    - The audit decided to keep DA-02.
    - The recommendation says no heavy rewrite.
    - This rewrite updates SavePack wording.
    - Codex preserved stale AppInstance wording.

Those facts may be useful in audit files, migration notes, compatibility notes,
branch notes, changelogs, or explicitly historical documents. They do not belong
in the architecture document itself.

The final DA-02 should simply define contract boundaries and implementation
independence.

==============================================================================
02. WHAT DA-02 GETS RIGHT
==============================================================================

02.1. Platform truth is correctly contractual
---------------------------------------------

DA-02 correctly says Turnix platform truth is defined by contracts, guarantees,
orchestration semantics, and continuity behavior, not by a specific language,
framework, RuntimeHost realization, adapter strategy, transport, or current stack.

Preserve this as the central doctrine.

02.2. Platform core is not monolithic
-------------------------------------

DA-02 correctly says the platform core does not need to be monolithic to remain
the source of platform truth.

Preserve this. Do not equate platform core with one module, package, process,
language, service object, RuntimeHost realization, or all first-party code.

02.3. Contract boundaries survive implementation convenience
------------------------------------------------------------

DA-02 correctly says same-language and same-process implementation does not erase
contract boundaries. In-process calls may realize a boundary only when they
preserve the same contract meaning an explicit boundary would have provided.

Preserve this strongly.

02.4. RuntimeHost is correctly below Kernel authority
-----------------------------------------------------

DA-02 correctly says RuntimeHost is a running host boundary, not the Kernel
authority owner.

Preserve this and keep DA-28 as RuntimeHost detail owner.

02.5. Interoperability envelope / RPC / transport separation is strong
----------------------------------------------------------------------

DA-02 correctly separates logical communication boundary from concrete transport.
RPC is a logical communication boundary; transport carries messages and does not
define authority.

Preserve this and keep DA-21 / IS documents in their lanes.

02.6. Replaceable implementation layers are correctly non-authoritative
-----------------------------------------------------------------------

DA-02 correctly says replacing backend, frontend, RuntimeHost realization,
adapter, transport, storage, debugger surface, artifact format, comparison tool,
Replay tool, Resume tool, Retry tool, audit tool, or first-party management tool
does not change Turnix identity when owning contracts remain preserved.

Preserve this.

==============================================================================
03. REQUIRED FIX: APPLICATION / APPLICATIONRUN / SAVE BUNDLE LANGUAGE
==============================================================================

The recommendation still says to use:

    SavePack stores durable AppInstance state.

Do not use that as current canonical wording.

The current target already uses a better high-level authority ordering:

    ApplicationRun binds live runtime identity.

    durable save persistence stores accepted Application state.

Keep that direction.

Recommended wording pattern:

    ApplicationRun binds live runtime identity.

    Durable save persistence stores accepted Application state and associated
    persistence material under SaveBundle / persistence-domain rules.

    Reusable AppDefinition/AppPack material may be a source of Application or
    ApplicationRun creation, but AppDefinition/AppPack is not platform identity.

Boundary statement:

    DA-02 may state the ordering and separation at a high level.

    DA-20 owns Application and ApplicationRun lifecycle and runtime identity
    semantics.

    SaveBundle-owner documents own durable persistence closure semantics.

    DA-02 should not settle whether every possible ApplicationRun must be backed
    by an AppDefinition/AppPack.

==============================================================================
04. REQUIRED FIX: DO NOT RESOLVE APPDEFINITION / APPPACK BACKING QUESTION
==============================================================================

DA-02 should preserve the distinction between Application/ApplicationRun runtime
identity and reusable AppDefinition/AppPack source material.

DA-02 should not say or imply:

    - every ApplicationRun is necessarily AppDefinition/AppPack-backed
    - Turnix platform truth is AppDefinition/AppPack-shaped
    - AppDefinition/AppPack is Turnix platform identity
    - Application identity is the same thing as AppDefinition/AppPack source

Recommended boundary:

    Application / ApplicationRun identity is runtime/platform identity.

    AppDefinition/AppPack is reusable declarative source material that can define
    or contribute to Application/ApplicationRun creation where the owning creation
    model says so.

    DA-02 does not decide all possible ApplicationRun backing forms.

That question belongs to DA-20, AppDefinition/AppPack documents, SaveBundle
documents, or later runtime-creation specifications.

==============================================================================
05. REQUIRED FIX: COMPLETED DOMAIN STOP-LINES
==============================================================================

DA-02 is the high-level implementation-independence document. It should name many
implementation forms as non-authoritative, but it should not define their details.

Add or preserve compact stop-lines:

    - DA-03 owns trace substrate, retention, loss, trace DAG, event structure, and
      span semantics.
    - DA-04 owns committed-state truth, transactions, and commit boundaries.
    - DA-05 owns payload identity, Chunk, ChunkId, ValueRef, decode, integrity,
      and retained-root reachability.
    - DA-06 owns configuration, schema, materialization, migration, and policy
      storage placement.
    - DA-07 owns IoManager, persistent-I/O authority, Reader / Writer providers,
      root boundaries, and persistence safety.
    - DA-08 owns Window, SafePointWindow, ActiveWindow, AbortedWindow, and
      finalized runtime history semantics.
    - DA-09 owns root and discovery semantics.
    - DA-10 owns pack identity, hierarchy, and visibility semantics.
    - DA-11 owns generic resolution semantics.
    - DA-12 owns importing, module loading, and code-boundary semantics.
    - DA-13 owns dependency, requirement, and dependency-graph semantics.
    - DA-14 owns activation lifecycle and execution guarantees.
    - DA-16 owns Services, Capabilities, and Permissions.
    - DA-17 owns user decision and remembered policy semantics.
    - DA-18 owns debugger, inspection, breakpoint, manual-pause, safe-point, and
      debugger mutation semantics.
    - DA-19 owns Job lifecycle, timeout, cancellation, progress, result, and
      terminal outcome semantics.
    - DA-20 owns Application/ApplicationRun lifecycle and runtime identity
      semantics.
    - DA-21 owns RPC, channel, and transport semantics.
    - DA-22 owns UI, View, frontend runtime, and frontend presentation semantics.
    - DA-23 and DA-27 own ExecutionAdapter boundaries, same-language,
      same-process, direct-call, adapter lifecycle, trust, and isolation
      semantics.
    - DA-24 owns OrchestrationUnit mutation-authority semantics.
    - DA-25 owns Window artifact, WindowExport, Minimal Audit Bundle, optional
      digest, and offline-inspection artifact semantics.
    - DA-26 owns comparison, ComparisonResult, Replay, Resume, Retry, and audit
      workflow semantics.
    - DA-28 owns RuntimeHost, workspace ownership, startup mode, command surface,
      local-first, and LAN exposure semantics.
    - DA-29 owns PackManager semantics.
    - DA-30 owns ModCallContext facade semantics where Pack invocation context is
      in scope.

DA-02 may name these concepts to protect implementation independence. It should
not define their detailed behavior.

==============================================================================
06. REQUIRED FIX: OFFICIAL TOOLING DOES NOT BECOME AUTHORITY
==============================================================================

Preserve the rule that first-party or official tooling status does not itself
create platform authority.

This applies to:

    - PackManager
    - debugger tooling
    - audit tools
    - launcher surfaces
    - catalog tools
    - export tools
    - comparison tools
    - Replay workflows
    - Resume workflows
    - Retry workflows
    - UI tools
    - RuntimeHost-facing command surfaces

Recommended boundary:

    Official tooling may inspect, list, explain, prepare graph intent, present
    risks, request decisions, expose Views, expose commands, expose capabilities,
    create artifacts, compare artifacts, or request workflows.

    Official tooling does not become Kernel, RuntimeHost authority, discovery
    authority, resolver, loader, activator, persistence authority, View authority,
    debugger authority, artifact authority, Replay authority, policy owner,
    Application/ApplicationRun lifecycle owner, SaveBundle authority,
    committed-state authority, or Turnix identity merely because it is official.

==============================================================================
07. REQUIRED FIX: SERVICES / CAPABILITIES / MODCALLCONTEXT BOUNDARY
==============================================================================

DA-02 should preserve that services and capabilities do not erase boundaries
inside one runtime.

Recommended wording:

    Services are runtime/internal wiring objects.

    Capabilities are named, versioned, permissioned, Turnix-mediated operation
    interfaces.

    Service access does not become capability permission.

    Capability permission does not become execution authorization.

    Same process, same runtime, same language, or direct-call optimization does
    not bypass capability mediation.

    ModCallContext exposes scoped Pack participation in Turnix. It does not expose
    unrestricted backend internals, filesystem authority, committed-state
    mutation, capability invocation, RuntimeHost control authority, or Kernel
    authority.

Keep detailed Services/Capabilities/Permissions in DA-16 and ModCallContext in
DA-30.

==============================================================================
08. REQUIRED FIX: STORAGE / PAYLOAD / CONFIGURATION / ARTIFACT STOP-LINES
==============================================================================

DA-02 should continue to state that current storage, payload, configuration, and
artifact implementations do not define platform truth.

Recommended boundary:

    Platform truth is contractual. It is not defined by current storage backend,
    payload representation realization, configuration file layout, frontend
    runtime, debugger surface, artifact/export format, comparison tool, replay
    tool, or first-party management tool.

    These systems implement or expose Turnix contracts. They do not become the
    contracts merely by being official, convenient, local, in-process, or
    currently used.

Specific stop-lines:

    ValueRef / Chunk representation is DA-05, not DA-02.

    Configuration schema and layout are DA-06, not DA-02.

    IoManager and persistent-I/O mechanics are DA-07, not committed-state truth.

    Window artifacts and exports are DA-25, not platform identity.

    ComparisonResult does not imply Replay, Resume, Retry, or audit completeness.

    Replay, Resume, and Retry are DA-26 workflows, not DA-02 platform identity.

==============================================================================
09. REQUIRED FIX: UI AND DEBUGGER SURFACES DO NOT DEFINE PLATFORM TRUTH
==============================================================================

Preserve implementation-independence for presentation and inspection domains.

Recommended boundary:

    UI is presentation and interaction, not authority.

    View is a Kernel-bound frontend runtime surface, not ApplicationRun,
    RuntimeHost, activation, or Job success.

    Debugger tooling is semantic, mediated, staged, trace-visible, and
    authority-bound. It is not Kernel authority.

    Debugger safe point is not automatically SafePointWindow.

    Debugger mutation is explicit, staged, trace-visible, and authority-bound.

Do not expand DA-02 into detailed DA-18 or DA-22 semantics.

==============================================================================
10. WHAT TO PRESERVE FROM CURRENT DA-02
==============================================================================

Preserve these boundaries, translating stale terminology where needed:

    - Turnix platform truth is contractual, not implementation-shaped
    - current implementation stack is a realization, not Turnix identity
    - backend language, frontend technology, RuntimeHost realization, adapter
      strategy, transport, or implementation vehicle do not define Turnix identity
    - Turnix remains one platform across language and implementation changes
    - platform core is the source of platform guarantee meaning
    - platform core does not need to be monolithic
    - contract meaning is primary; internal realization is secondary
    - contract boundaries survive same-language and same-process implementation
    - in-process calls may realize a boundary only if they preserve boundary
      meaning
    - first-party modularity does not weaken platform guarantees
    - host-language adaptation does not reinterpret platform contracts
    - same host language does not imply same authority
    - pack-provided code is not platform core implementation code merely because it
      is written in the same language
    - ExecutionAdapter semantics are defined outside DA-02
    - RuntimeHost semantics are defined outside DA-02
    - interoperability envelopes preserve boundary clarity, request/response
      meaning, tracing, permission/capability semantics, and continuity-safe
      interaction
    - RPC is the logical communication boundary
    - transport is carrier, not authority
    - replaceable implementation layers do not redefine platform meaning
    - implementation independence is a consequence of contract primacy and
      architectural truth

==============================================================================
11. SPECIFIC PHRASE REPLACEMENTS
==============================================================================

Use these as a starting pass. Context still matters.

    AppInstance
        -> ApplicationRun where live runtime identity is meant
        -> Application where durable application identity is meant

    AppInstance lifecycle
        -> Application/ApplicationRun lifecycle

    AppPack
        -> AppDefinition/AppPack where reusable declarative app source is meant

    SavePack
        -> SaveBundle where durable persistence closure is meant

    SavePack stores durable AppInstance state
        -> durable save persistence stores accepted Application state
        or -> SaveBundle stores accepted Application/ApplicationRun persistence
              material
        depending on local wording

    PackContext
        -> ModCallContext where invocation-scoped Pack facade is meant
        -> activation context where DA-14 activation participation is meant

    frontend/browser adapter
        -> UI-oriented ExecutionAdapter realization, if a concrete subtype is meant

    interoperability envelope / RPC / transport
        -> keep separated; RPC is logical boundary, transport is carrier

    direct-call optimization
        -> dispatch optimization that must preserve contract meaning

    official tooling
        -> official tooling / first-party surface, not authority owner

==============================================================================
12. ACCEPTANCE CONDITIONS FOR THE REVISED DA-02
==============================================================================

A revised DA-02 is acceptable when all of the following are true:

    - It preserves platform truth as contractual, not implementation-shaped.

    - It preserves platform core as semantic guarantee source, not one monolithic
      implementation object.

    - It preserves same-language, same-process, and direct-call paths as unable to
      erase contract boundaries.

    - It keeps RuntimeHost below Kernel authority.

    - It keeps ExecutionAdapter as the general adapter category where adapter
      category is meant.

    - It preserves interoperability envelope / RPC / transport separation.

    - It preserves the distinction between RPC acknowledgement, request
      acceptance, Job creation, handler execution, adapter execution, RuntimeHost
      operation, and final work outcome.

    - It preserves official first-party tooling as non-authority by default.

    - It preserves service access as not capability permission.

    - It preserves ModCallContext as scoped Pack participation, not backend
      internals access.

    - It preserves discovery as candidate production, not resolution, activation,
      import, runtime loading, or runtime identity.

    - It preserves current storage, payload, configuration, UI, debugger,
      artifact/export, comparison, Replay, Resume, Retry, audit, and first-party
      management tooling as implementation or domain realizations, not platform
      identity.

    - It keeps detailed ownership in the owning DA/IS documents instead of
      absorbing those domains.

    - It translates AppInstance / SavePack wording to Application / ApplicationRun
      / SaveBundle terminology where appropriate.

    - It preserves AppDefinition/AppPack separation from Application/ApplicationRun
      identity without resolving the unresolved all-runs-must-be-AppPack-backed
      question.

    - It does not include audit provenance, rewrite process, old/new design, V3,
      Codex, candidate status, or branch history as ordinary architecture text.

==============================================================================
13. FINAL EDITOR INSTRUCTION
==============================================================================

Keep DA-02.

Do not perform a heavy conceptual rewrite.

Make targeted edits:

    - preserve platform truth as contractual, not implementation-shaped
    - preserve platform core as not monolithic
    - preserve contract boundaries across same-language, same-process, and
      direct-call realizations
    - preserve RuntimeHost as below Kernel authority
    - preserve ExecutionAdapter as the general adapter category
    - preserve interoperability envelope / RPC / transport separation
    - preserve official first-party tooling as non-authority by default
    - preserve service access as not capability permission
    - preserve ModCallContext as scoped Pack participation, not backend internals
      access
    - preserve discovery as candidate production, not resolution, activation,
      import, runtime loading, or runtime identity
    - preserve storage, payload, configuration, UI, debugger, artifact/export,
      comparison, Replay, Resume, Retry, audit, and first-party tooling as
      implementation/domain realizations, not platform truth
    - translate AppInstance / SavePack wording to Application / ApplicationRun /
      SaveBundle terminology where appropriate
    - preserve AppDefinition/AppPack separation from Application/ApplicationRun
      identity without resolving the AppPack-backing question
    - add or preserve compact owner stop-lines for completed DA domains when DA-02
      names them

Do not include audit/source metadata or version/process framing in the final
DA-02 documentation. The final DA-02 should not say this is V3 design, in V3,
new design, old design, rewritten design, created by Codex, decided by audit, or
part of a rewrite-history process.

DA-02 should remain the high-level contract-boundary and implementation-
independence document.

DA-02 should not become the detailed specification for RuntimeHost, PackManager,
root discovery, indexing, resolution, dependencies, importing, activation,
Services, Capabilities, Jobs, ExecutionAdapters, ModCallContext, RPC, transport,
OrchestrationUnits, Application, ApplicationRun, AppDefinition/AppPack backing,
SaveBundle, committed state, ValueRef, Chunk, configuration, persistent I/O,
Windows, artifacts, exports, comparison, Replay, Resume, Retry, audit workflows,
UI/View/frontend runtime, or debugger tooling.

The main work is to preserve DA-02's implementation-independence doctrine while
modernizing stale terminology and preventing implementation convenience from
silently becoming platform truth.
