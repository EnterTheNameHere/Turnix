SUMMARY
=======

DA-02 is strongly compatible with the Dv3 runtime-domain direction.

It already defines Turnix platform truth as contracts, guarantees,
orchestration semantics, and continuity behavior, rather than any current
implementation language, framework, RuntimeHost realization, adapter strategy,
transport, or runtime stack.

This file should mostly be kept.

Unlike DA-01, DA-02 does not strongly bind Turnix identity to modular packs or
AppPack execution. It already protects Turnix from collapsing into current
implementation choices.

Update after DA-28:

    DA-28 confirms the RuntimeHost boundary that DA-02 requires.

    RuntimeHost remains below Kernel authority.

    RuntimeHost is not Kernel, AppInstance, SavePack, CLI, execution adapter,
    transport, Job, or Orchestration Unit.

    DA-28 also confirms that startup modes, command surfaces, browser frontend,
    launcher mode, remote clients, deployment shape, and command syntax do not
    become Turnix identity or authority.

Update after DA-29:

    DA-29 confirms DA-02's contract-boundary doctrine from the PackManager side.

    PackManager is official first-party Turnix tooling, but official tooling
    status does not erase contract boundaries.

    PackManager does not become Kernel, discovery, generic resolution,
    importing, activation, execution adapter, mechanical loader, capability
    permission, persistence authority, View authority, policy owner,
    AppInstance lifecycle owner, SavePack authority, or Turnix identity.

    This confirms the DA-02 rule:

        First-party implementation does not automatically become platform
        authority.

        Convenience surfaces do not become authority merely because they are
        useful, official, or close to the runtime.

WHAT IS ALREADY NAILED
======================

The document already says Turnix platform truth is not defined by:

    - implementation language
    - framework
    - current runtime stack
    - backend language
    - frontend technology
    - RuntimeHost realization
    - adapter strategy
    - transport
    - current implementation vehicle

This directly supports the Dv3 move:

    Turnix is a runtime/domain architecture, not merely the thing that runs
    AppPacks or the current Python/FastAPI/WebSocket/browser stack.

The contract-boundary doctrine is especially important:

    Same-language or same-process implementation does not erase a contract
    boundary.

This protects Dv3 from the Python trap:

    Backend is Python.
    Pack code is Python.
    Therefore pack code may call backend internals.

DA-02 already rejects that.

It also allows in-process calls only when they preserve the same contract
meaning an explicit boundary would provide.

That is the correct doctrine:

    Fast path may be allowed.
    Boundary violation is not.

Update after DA-29:

    DA-29 extends the same boundary principle to official first-party tooling.

    PackManager is official Turnix tooling, but it still does not gain authority
    merely because it is official, convenient, or runtime-adjacent.

    This protects Dv3 from another common collapse:

        PackManager is first-party.
        PackManager knows about packs.
        Therefore PackManager may silently resolve, repair, activate, import,
        mutate, persist, or authorize pack behavior.

    DA-29 rejects that.

    Official tooling may expose controlled operations, but it does not erase
    ownership boundaries.


PRIMARY WATCH ITEM: PLATFORM CORE
=================================

Potential risk:

    "Platform core" is a useful term, but later documents must not turn it into
    one concrete god-object package or monolithic implementation blob.

Current DA-02 already says:

    The platform core does not need to be monolithic.

This should be preserved.

Intended Dv3 reading:

    platform core = the set of semantics and trusted runtime components required
    to preserve Turnix platform truth

Not:

    platform core = one Python module that owns everything

Recommendation:

    No immediate DA-02 rewrite required unless later documents reveal confusion.
    Carry this warning forward into Kernel/core/runtime documents.

    This must be preserved when auditing DA-28.

    Later DA-28 must not make RuntimeHost into:

        - Kernel

ADAPTER TERMINOLOGY
===================

DA-02 already uses "execution adapter", which matches Dv3 better than the older
"FrontendAdapter" framing.

Dv3 decision:

    Use ExecutionAdapter as the general adapter category.

Specific realizations may include:

    - Browser/Electron adapter
    - Python adapter
    - Unity/C# adapter
    - Lua adapter
    - C++ adapter
    - remote process adapter
    - test adapter

FrontendAdapter should either become obsolete or become a narrow UI-specific
subtype, not the general concept.

Update after DA-28:

    DA-28 contains minor wording around "frontend adapter" when discussing
    browser frontend behavior.

    This does not break architecture, because the wording is tied to browser
    frontend as a specific surface.

    However, future documents should consistently use ExecutionAdapter as the
    umbrella term.

    Browser/frontend adapter should be treated only as a UI-oriented adapter
    realization or subtype.

Recommended terminology:

    ExecutionAdapter = general category.

    Browser/frontend adapter = specific UI-facing realization, if the term is
    kept at all.

Update after DA-29:

    DA-29 correctly uses ExecutionAdapter terminology when separating
    PackManager graph preparation from adapter execution.

    DA-29 confirms that PackManager may present adapter requirements,
    availability, trust warnings, and incompatibilities, but presentation does
    not authorize adapter execution.

    This reinforces ExecutionAdapter as a separate authority boundary.


INTEROPERABILITY ENVELOPE NOTE
==============================

DA-02 correctly distinguishes:

    - interoperability envelope
    - RPC
    - transport
    - concrete message schema / wire detail

Later documents should keep this stack clear.

Suggested conceptual relationship:

    capability request / event / job request
        -> RPC logical message
            -> interoperability envelope / boundary wrapper
                -> transport carrier

Or more abstractly:

    Interoperability envelope = cross-boundary interaction wrapper.
    RPC = current logical protocol realization.
    Transport = concrete carrier.

No immediate DA-02 rewrite required, but later RPC/transport docs should avoid
collapsing these meanings.

Update after DA-29:

    DA-29 confirms that PackManager operations may be exposed through
    RuntimeHost commands, capabilities, RPC, Views, or test surfaces, but those
    surfaces remain mediated request surfaces.

    A PackManager View, command, or RPC operation does not become PackManager
    authority merely because it presents or requests PackManager behavior.

    This supports DA-02's interoperability-envelope distinction:

        request surface is not authority
        transport is not authority
        envelope is not authority
        authority remains in the owning domain and Kernel-mediated path


SAVEPACK WORDING
================

DA-02 repeats the DA-01 authority ordering:

    SavePack stores durable executed state.

This is not necessarily wrong, but Dv3 may eventually prefer:

    SavePack stores durable AppInstance state.

Reason:

    "Executed state" is slightly ambiguous.

SavePack may include:

    - AppInstance identity
    - selected AppPack identity/version
    - resolved dependency information
    - latest memory state
    - memory history, if enabled
    - settings
    - runtime state
    - user data
    - trace references or trace snapshots
    - adapter/orchestration state

Recommendation:

    Do not patch DA-02 independently unless DA-01 authority ordering is changed.
    If DA-01 changes this phrase, mirror the terminology here.

Update after DA-29:

    DA-29 reinforces that SavePack graph evidence, copied pack material, pinned
    pack references, and selected graph records are not casually mutable just
    because PackManager can inspect or prepare graph changes.

    PackManager does not silently mutate SavePack state, SavePack-owned copied
    pack graphs, or last-known-good graph behavior.

    This supports the future need to define SavePack as durable AppInstance
    state with its own authority rules.


PACKMANAGER / OFFICIAL TOOLING BOUNDARY
=======================================

DA-29 introduces PackManager as an official Turnix pack-management and
graph-preparation domain.

This is compatible with DA-02.

It confirms a useful rule:

    Official tooling status does not erase contract boundaries.

PackManager may:

    - inspect catalogs
    - list packs
    - present visibility evidence
    - prepare selected graph intent
    - prepare activation plans
    - explain dependency and advisory relation evidence
    - present risks
    - request user or policy decisions
    - suggest or perform authorized graph repair
    - expose Views, commands, capabilities, RPC operations, or test surfaces

But PackManager does not become:

    - Kernel
    - discovery
    - generic resolution
    - importing
    - activation
    - execution adapter
    - mechanical loader
    - capability permission
    - persistence authority
    - View authority
    - policy owner
    - AppInstance lifecycle owner
    - SavePack authority
    - Turnix identity

This matters because PackManager is deliberately useful and official.

Without DA-02's boundary doctrine, "official useful tool" could become
"silent authority blob."

DA-29 prevents that.

Recommendation:

    Keep this as confirmation of DA-02.

    No source rewrite needed unless DA-02 later needs an explicit example of
    first-party tooling not erasing contract boundaries.


NO MAJOR DV3 CONFLICT FOUND
===========================

DA-02 does not bind Turnix to:

    - AppPack as mandatory root
    - modular packs as whole project identity
    - Python
    - FastAPI
    - WebSocket
    - browser frontend
    - current RuntimeHost realization
    - direct calls as valid authority
    - same-language privilege

This is exactly what DA-02 should prevent.

Update after DA-28:

    DA-28 confirms that DA-02's implementation-independence doctrine is being
    preserved in the RuntimeHost design area.

    RuntimeHost does not collapse into launcher, CLI, server process, browser
    frontend, command surface, transport, or implementation framework.

Update after DA-29:

    DA-29 confirms that DA-02's contract-boundary doctrine is being preserved
    in the PackManager design area.

    PackManager does not collapse into catalog UI, launcher behavior, graph
    resolver, activator, importer, loader, capability authority, persistence
    authority, SavePack mutator, AppInstance graph mutator, or platform identity.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-02.

Only minor future clarifications are likely needed:

    1. Preserve "platform core is not monolithic".
    2. Keep RuntimeHost below Kernel authority.
       DA-28 currently satisfies this.
    3. Use ExecutionAdapter as the general Dv3 adapter category.
    4. Treat frontend/browser adapter only as a specific UI-oriented adapter
       realization or subtype.
    5. Keep interoperability envelope / RPC / transport distinct.
    6. If DA-01 changes SavePack wording, mirror that change here.
    7. Preserve the rule that official first-party tooling does not erase
       contract boundaries.
       DA-29 currently satisfies this for PackManager.

No heavy rewrite recommended at this stage.
