ACTUAL DA-02 CHANGE 1: SAVEPACK / APPINSTANCE TERMINOLOGY
=========================================================

Current issue:

    DA-02 repeats the older authority-ordering phrase:

        SavePack stores durable executed state.

After the AppInstance lifecycle audit, the better canonical phrase is:

        SavePack stores durable AppInstance state.

Recommended DA-02 change:

    When DA-02 repeats the high-level runtime authority ordering, use:

        SavePack stores durable AppInstance state.

Reason:

    "Executed state" is slightly ambiguous.

It can be misread as:

    adapter-executed code owns SavePack truth

or:

    any executed work becomes durable SavePack state

The intended meaning is closer to:

    committed AppInstance state and selected durable instance material are
    SavePack concerns

Preserve this distinction:

    SavePack is not AppInstance identity.

    SavePack does not own AppInstance lifecycle.

    SavePack does not grant adapter-executed code authority.

    SavePack mutation remains governed by authoritative committed-state and
    persistence documents.

Do not expand DA-02 into detailed AppInstance or SavePack semantics.


PRESERVATION RULE 1: PLATFORM TRUTH IS CONTRACTUAL
==================================================

Preserve DA-02's core doctrine:

    Turnix platform truth is contractual, not implementation-shaped.

DA-02 should continue to prevent Turnix from being defined by:

    - Python
    - FastAPI
    - WebSocket
    - browser frontend
    - current RuntimeHost realization
    - current adapter strategy
    - current transport
    - current launcher or command shape
    - current pack-management tooling
    - current implementation convenience

Do not rewrite DA-02 into a concrete implementation-stack document.


PRESERVATION RULE 2: PLATFORM CORE IS NOT A MONOLITH
====================================================

Preserve DA-02's rule:

    The platform core does not need to be monolithic.

Intended Dv3 reading:

    platform core = the set of semantics and trusted runtime components
    required to preserve Turnix platform truth

Not:

    platform core = one Python module that owns everything

The platform core may be realized through several Kernel-mediated or
Kernel-composed runtime systems.

Those systems can be separately implemented, tested, replaced, or embedded
where their contracts allow it.

Do not rewrite "platform core" into:

    - one package
    - one process
    - one module
    - one language
    - one service object
    - one god object
    - one RuntimeHost realization


PRESERVATION RULE 3: CONTRACT BOUNDARIES SURVIVE SAME-LANGUAGE, SAME-PROCESS, AND DIRECT-CALL PATHS
===================================================================================================

Preserve DA-02's same-language and same-process boundary doctrine.

Same-language or same-process implementation does not erase a contract
boundary.

In-process calls may be allowed only when they preserve the same contract
meaning an explicit boundary would provide.

This prevents the bad rewrite:

    Python pack code can call backend internals because Turnix backend is also
    Python.

It also prevents:

    direct call = authority bypass

    in-process transport = no boundary

    same RuntimeHost = unrestricted access

    first-party module = platform authority

    PackContext = backend internals access

    service object = capability permission

Direct in-process calls may optimize transport or dispatch, but they must
preserve the same logical authority, permission, lifecycle, trace, structured
error, capability, transaction, commit, AppInstance, SavePack, RuntimeHost, and
OrchestrationUnit boundaries.

Do not expand DA-02 into detailed ExecutionAdapter, PackContext, capability, or
RPC specifications.


PRESERVATION RULE 4: OFFICIAL TOOLING DOES NOT BECOME AUTHORITY
===============================================================

Preserve the rule:

    First-party implementation or official tooling status does not
    automatically become platform authority.

This applies to PackManager and other first-party management, debugging, audit,
launcher, catalog, and tooling surfaces.

Such tooling may inspect, list, explain, prepare graph intent, present risks,
request decisions, expose Views, expose commands, expose capabilities, or expose
RPC operations.

Official tooling does not become:

    - Kernel
    - RuntimeHost authority
    - discovery authority beyond the discovery domain
    - generic resolution authority
    - importing authority
    - activation authority
    - ExecutionAdapter authority
    - mechanical loader authority
    - capability permission
    - persistence authority
    - View authority
    - policy owner
    - AppInstance lifecycle owner
    - SavePack authority
    - Turnix identity

Do not add detailed PackManager or discovery semantics to DA-02.


PRESERVATION RULE 5: SERVICES AND CAPABILITIES DO NOT ERASE BOUNDARIES INSIDE ONE RUNTIME
=========================================================================================

Preserve DA-02's contract-boundary doctrine for in-runtime object access.

Services are runtime wiring objects.

Capabilities are named, permissioned, Turnix-mediated operations.

Runtime object access does not erase contract boundaries.

Service access does not become capability permission.

Capability permission does not become execution authorization.

Job-backed capability execution remains capability-mediated.

Same process, same runtime, or same language does not bypass capability
mediation.

PackContext exposes scoped participation in Turnix.

PackContext does not expose unrestricted:

    - backend internals
    - filesystem authority
    - committed-state mutation
    - capability invocation
    - RuntimeHost control authority
    - Kernel authority

Do not expand DA-02 into detailed Service, Capability, Permission, Job, or
PackContext semantics.


PRESERVATION RULE 6: EXECUTIONADAPTER IS THE UMBRELLA ADAPTER TERM
==================================================================

Preserve ExecutionAdapter as the umbrella term.

Use:

    ExecutionAdapter = general adapter category

Treat these as specific realizations or subtypes:

    - Browser/Electron adapter
    - frontend/browser adapter
    - Python adapter
    - Unity/C# adapter
    - Lua adapter
    - C++ adapter
    - remote process adapter
    - test adapter

Do not use FrontendAdapter as the umbrella concept.

Frontend/browser adapter wording is acceptable only when the text is
specifically about browser/frontend behavior.


PRESERVATION RULE 7: INTEROPERABILITY ENVELOPE, RPC, TRANSPORT, CAPABILITY, AND JOB REMAIN DISTINCT
===================================================================================================

Preserve DA-02's distinction between:

    - interoperability envelope
    - RPC
    - transport
    - concrete message schema / wire detail

RPC is a logical communication boundary.

RPCChannel is the transport-neutral interface.

Transport is the concrete carrier.

WebSocket is one transport.

JSON or another schema format is concrete envelope/schema representation.

Preserve this doctrine:

    Request surface is not authority.

    Transport is not authority.

    Envelope is not authority.

    RPC acknowledgement is not request success.

    Request acceptance is not final work success unless the operation contract
    explicitly defines acceptance as the result.

    RPC request is not automatically Job.

    Capability invocation is not automatically Job.

    Direct call is not authority bypass.

    Authority remains in the owning domain and Kernel-mediated path.

Do not add detailed RPC envelope, channel, timeout, disconnect, or cancellation
semantics to DA-02.


WATCH ITEM: MACHINE INTERPRETATION OF "CORE"
============================================

DA-02 can say platform core is not monolithic.

Future edits should avoid making "core" sound like:

    - one package
    - one module
    - one god object
    - one RuntimeHost realization
    - all first-party code
    - all official tooling

The useful meaning is:

    the set of semantics and trusted runtime components required to preserve
    Turnix platform truth.


REWRITE-BOUNDARY GUARDRAILS, NOT SUGGESTED DA-02 CONTENT
=========================================================

This section is not suggested DA-02 wording.

It exists to prevent architectural drift during rewrite when the editor knows
DA-02 but may not have every related document loaded.

Use these as guardrails only.

Boundary guardrails:

    RuntimeHost is a running host boundary, not Kernel authority.

    ExecutionAdapter is the general adapter category.

    Pack-provided code is external code, even when written in the same language
    or running in the same process as backend implementation code.

    RPC is a logical communication boundary, not a concrete transport.

    Transport carries messages but does not define authority.

    RPC acknowledgement is not request success.

    Request acceptance is not final work success unless the operation contract
    explicitly defines acceptance as the result.

    Capability invocation is not automatically Job.

    Service object access is not capability permission.

    PackContext is scoped participation, not backend internals access.

    Discovery is candidate production, not visibility, resolution, activation,
    import, runtime loading, or runtime identity.

    Importing/module loading is not activation.

    Activation is controlled executable participation, not import.

    PackManager is first-party management/tooling domain, not Kernel,
    RuntimeHost authority, resolver, loader, activator, policy owner,
    persistence authority, or Turnix identity.

    Direct-call optimization may optimize dispatch but must not erase contract
    meaning.

    SavePack stores durable AppInstance state, but does not own AppInstance
    lifecycle or adapter execution authority.

Owning-document guardrails:

    DA-03 owns trace substrate, trace retention, trace loss, and trace DAG
    semantics.

    DA-04 owns authoritative committed state, transactions, and commit
    boundaries.

    DA-08 owns Window, SafePointWindow, AbortedWindow, and finalized runtime
    history semantics.

    DA-09 owns root and discovery semantics.

    DA-10 owns pack identity, hierarchy, and visibility semantics.

    DA-11 owns generic resolution semantics.

    DA-12 owns importing, module loading, and code-boundary semantics.

    DA-13 owns dependency, requirement, and PackRequest dependency semantics.

    DA-14 owns activation lifecycle and execution guarantees.

    DA-16 owns Services, Capabilities, and Permissions.

    DA-17 owns user decision and remembered policy semantics.

    DA-19 owns Job lifecycle, timeout, cancellation, progress, result, and
    terminal outcome semantics.

    DA-20 owns AppInstance lifecycle and runtime identity semantics.

    DA-21 owns RPC, channel, and transport semantics.

    DA-23 and DA-27 own ExecutionAdapter, PackContext, same-language,
    same-process, direct-call, adapter lifecycle, trust, and isolation semantics.

    DA-24 owns OrchestrationUnit mutation-authority semantics.

    DA-28 owns RuntimeHost, workspace ownership, startup mode, command surface,
    local-first, and LAN exposure semantics.

    DA-29 owns PackManager semantics.

Local rewrite rule:

    DA-02 may name these concepts when needed to protect implementation
    independence and contract boundaries.

    DA-02 should not define their detailed behavior.

    DA-02 should remain the high-level contract-boundary and implementation-
    independence document.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-02.

No heavy rewrite is recommended.

Apply only minor future clarifications:

    1. Preserve platform truth as contractual, not implementation-shaped.

    2. Preserve "platform core is not monolithic".

    3. Keep RuntimeHost below Kernel authority.

    4. Use ExecutionAdapter as the general Dv3 adapter category.

    5. Treat frontend/browser adapter only as a specific UI-oriented adapter
       realization or subtype.

    6. Preserve interoperability envelope / RPC / transport separation.

    7. Preserve distinction between RPC acknowledgement, request acceptance, Job
       creation, handler execution, adapter execution, RuntimeHost operation,
       and final work outcome.

    8. Preserve the rule that direct-call optimization and RPC-shaped
       in-process execution do not erase authority boundaries.

    9. Preserve the rule that official first-party tooling does not erase
       contract boundaries.

    10. Preserve the rule that service object access, in-process calls,
        PackContext, and same-language execution do not erase capability
        mediation or Kernel authority.

    11. Preserve the rule that discovery is candidate production, not platform
        authority, runtime identity, resolution, activation, import, or runtime
        loading.

    12. Align SavePack wording with DA-01 and DA-20:

        SavePack stores durable AppInstance state.

DA-02 should remain the high-level contract-boundary and implementation-
independence document.

It should not become the detailed specification for RuntimeHost, PackManager,
root discovery, indexing, resolution, dependencies, importing, activation,
Services, Capabilities, Jobs, ExecutionAdapters, PackContext, RPC, transport,
OrchestrationUnits, AppInstance, SavePack, or Windows.
