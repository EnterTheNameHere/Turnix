==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Mostly yes, with stale-terminology correction.

Document verdict:
    Keep with small terminology, source-stack, and trace-boundary fixes.

DA-27 is architecturally strong.

It correctly preserves the DA-23 / DA-27 / DA-28 ownership split:

    DA-23 owns the abstract execution-boundary authority model.

    DA-27 owns operational adapter lifecycle, trust, isolation, traceability, and
    initial adapter classes.

    DA-28 owns RuntimeHost identity, workspace ownership, startup modes, entry
    surfaces, command-surface semantics, local-first interpretation, LAN exposure,
    and RuntimeHost trace reason ownership.

DA-27 also correctly preserves the central doctrine:

    Adapter mediation is not sandboxing.

    Sandboxing does not grant Kernel authority.

    Lack of sandboxing does not grant backend implementation authority.

    Adapter class, trust class, isolation class, readiness, failure, disconnect,
    closure, or trace evidence does not silently become another domain's
    authority or outcome.

No heavy rewrite is recommended.

The current candidate already integrated many recommendation points. The remaining
work is mostly current-Dv3 terminology and a few extra source-stack alignments:

    - active save identity -> SaveBundle identity when applicable
    - AppInstance-era wording in the recommendation -> Application/ApplicationRun
    - SavePack-era wording in the recommendation -> SaveBundle
    - PackContext-era wording in the recommendation -> ModCallContext / DA-30
    - Orchestration Unit -> OrchestrationUnit when used as the type name
    - DA-14 trace and activation references should align with P01/multi-phase
      activation audit result
    - adapter trace context should include activationAttemptId / activation-entry
      identity when adapter execution is part of activation
    - BrowserJSAdapter wording should not imply frontend/browser state owns
      authoritative Application/ApplicationRun state

Primary conclusion:
    Keep DA-27 and perform a light alignment rewrite.

==============================================================================
02. WHAT DA-27 GETS RIGHT
==============================================================================

02.1. Adapter mediation versus sandboxing is clear
--------------------------------------------------

DA-27 correctly states that adapter mediation is not sandboxing.

It correctly defines mediation as adapter-executed code participating through
Turnix-controlled context, RPC-shaped boundaries, capabilities, lifecycle,
policy, and trace correlation.

It correctly defines sandboxing as a security isolation mechanism that restricts
what code can do outside Turnix semantic boundaries.

Preserve this.

02.2. Trust and isolation boundaries are strong
-----------------------------------------------

DA-27 correctly states:

    - Browser JavaScript has browser-provided sandbox properties.
    - Python in-process execution is not a security sandbox.
    - Python subprocess execution provides process separation but not complete
      security by itself.
    - Containerized/VM/remote execution provides only the isolation actually
      defined and enforced by implementation specifications.
    - Unsandboxed adapter-executed code requires explicit trust or policy
      treatment.
    - Trust decisions are scoped.
    - Trust decisions do not grant capability permission, direct committed-state
      mutation, direct persistent I/O, RuntimeHost control, workspace ownership,
      LAN exposure, or command-surface acceptance unless owning documents define
      that combined effect explicitly.

Preserve this.

02.3. Initial adapter classes are useful but non-authoritative
-------------------------------------------------------------

DA-27 correctly treats BrowserJSAdapter, PythonInProcessAdapter,
PythonSubprocessAdapter, CliAdapter, RemoteClientAdapter, and TestAdapter as
initial/descriptive adapter classes.

It correctly says adapter class names are descriptive unless a later
implementation specification locks concrete identifiers.

Preserve this.

02.4. Adapter lifecycle separation is strong
--------------------------------------------

DA-27 correctly states that adapter lifecycle does not replace activation,
ApplicationRun, Job, transport, RuntimeHost, or capability lifecycle.

It correctly says adapter readiness does not imply Pack activation success,
capability permission, ApplicationRun readiness, RuntimeHost readiness, or Job
success.

Preserve this.

02.5. Failure/disconnect boundaries are strong
----------------------------------------------

DA-27 correctly states that adapter failure and disconnect are explicit when
detected and do not silently redefine Job, ApplicationRun, RuntimeHost,
committed-state, Window, OrchestrationUnit, transport, UI/View, or RuntimeHost
outcomes.

Preserve this and keep the DA-25/DA-26 additions.

02.6. Trace ownership is mostly correct
---------------------------------------

DA-27 correctly owns adapter-domain trace reason identifiers and says adapter
trace evidence does not replace activation, RPC, capability, Job,
ApplicationRun, OrchestrationUnit, UI, or RuntimeHost trace evidence.

Preserve this and expand it only where needed for current Dv3 terminology and
P01 activation diagnostics.

==============================================================================
03. REQUIRED TERMINOLOGY ALIGNMENT
==============================================================================

03.1. active save identity -> SaveBundle identity
-------------------------------------------------

DA-27 currently uses:

    active save identity

in adapter trace context.

Replace with:

    SaveBundle identity when applicable

or, if the surrounding context is user-facing rather than architectural:

    active save / SaveBundle identity when applicable

Architecture identity should be SaveBundle.

03.2. AppInstance -> Application / ApplicationRun
-------------------------------------------------

The candidate already uses ApplicationRun in most places, which is good.

The recommendation still uses AppInstance. Do not copy it forward.

Use:

    Application:
        durable application individual

    ApplicationRun:
        live runtime incarnation

Adapter readiness and failure usually relate to ApplicationRun, not Application.

03.3. SavePack -> SaveBundle
----------------------------

The recommendation still uses SavePack. Do not copy it forward.

Use SaveBundle where the durable persistence closure is meant.

Do not classify SaveBundle as a Pack or adapter class.

03.4. PackContext -> ModCallContext
-----------------------------------

The recommendation still uses PackContext. Do not copy it forward.

DA-27 candidate currently says adapter mediation uses Turnix-controlled context.
That is acceptable as a summary, but the current Dv3 name is ModCallContext.

Recommended wording:

    Adapter mediation means adapter-executed Pack code participates in Turnix
    through ModCallContext, RPC-shaped boundaries, capabilities, lifecycle,
    policy, and trace correlation.

Detailed ModCallContext lifetime, facade, and absent-surface semantics belong to
DA-30.

03.5. Orchestration Unit -> OrchestrationUnit
---------------------------------------------

DA-27 still uses "Orchestration Unit" in several places.

Use OrchestrationUnit when referring to the first-class type name, unless the
project deliberately keeps the spaced form as a display alias.

==============================================================================
04. REQUIRED SOURCE-STACK ALIGNMENT
==============================================================================

04.1. DA-14 / P01 activation alignment
--------------------------------------

DA-27 says adapter lifecycle may include:

    loading artifact
    executing activation

and defines trace reasons such as:

    AdapterArtifactLoadStarted
    AdapterArtifactLoadFailed
    AdapterActivationDispatchStarted

This is acceptable, but should align with the P01/DA-14 audit result.

DA-14 should own the activation lifecycle protocol, including Stage 0, Phase 1,
Phase 2, Phase 3, phase barriers, registration publication scopes, and cyclic
activation group semantics.

DA-27 should own only adapter-domain lifecycle and traceability around adapter
loading/evaluation/dispatch.

Add a boundary statement:

    Adapter entry loading/evaluation, adapter readiness, and adapter activation
    dispatch are adapter-domain lifecycle evidence.

    They do not define Pack activation completion, Phase 1/Phase 2/Phase 3
    completion, cyclic-group activation, registration publication, or final
    externally visible Activated state.

    DA-14 owns those activation lifecycle meanings.

04.2. Add activationAttemptId / activation-entry identity to adapter trace context
---------------------------------------------------------------------------------

Because P01 introduces activation attempts, activation entries, and cyclic group
activation, DA-27 trace context should include activation-related fields when
adapter behavior occurs during activation.

Add to adapter trace context when available:

    activationAttemptId
    activation-entry identity
    lifecycle phase when applicable
    dependency component identity when applicable
    cyclic-group identity when applicable

Keep these as correlation fields, not DA-14 ownership transfer.

04.3. DA-30 / ModCallContext alignment
--------------------------------------

DA-27 should not define ModCallContext semantics.

It may say adapter-executed Pack code uses ModCallContext where Pack-facing
platform access is needed.

Add or preserve stop-line:

    DA-30 owns ModCallContext invocation gateway lifetime, facade, retention,
    and absent-surface semantics.

    DA-27 does not grant ctx.services, ctx.kernel, ctx.runtimeHost,
    ctx.rawFilesystem, or other DA-30-forbidden surfaces by selecting a trust or
    isolation class.

04.4. DA-28 / RuntimeHost ownership alignment
---------------------------------------------

DA-27 already preserves DA-28 ownership well.

After AUDIT-DA-28, clarify that RuntimeHost does not independently own Workspace
authority outside TurnixRuntime/Kernel.

DA-27 can simply say:

    RuntimeHost and Workspace ownership semantics are DA-28 and
    TurnixRuntime/Kernel constrained. Adapter class, deployment topology, LAN
    access, CLI access, or RemoteClientAdapter access does not acquire, release,
    recover, downgrade, or override Workspace ownership.

04.5. DA-25 / DA-26 additions are valid
---------------------------------------

The recommendation correctly asks DA-27 to keep DA-25/DA-26 stop-lines.

The candidate already includes a compact DA-25/DA-26 stop-line in the core
concept section, but it should also extend the failure/disconnect and trace
sections.

Keep the rule:

    Adapter artifact loading, adapter execution, adapter readiness, adapter
    failure, adapter disconnect, adapter trace evidence, or adapter closure does
    not by itself define artifact/export authority, missing-material semantics,
    ComparisonResult, Replay outcome, Resume outcome, Retry outcome, or audit
    workflow outcome.

04.6. DA-05 / DA-06 / DA-07 additions are valid
-----------------------------------------------

The recommendation correctly asks DA-27 to keep DA-05/DA-06/DA-07 stop-lines.

The candidate already includes them in the core concept section.

Make sure future edits keep:

    Adapter lifecycle, trust class, isolation class, readiness, failure,
    disconnect, artifact loading, execution, or trace evidence does not grant
    committed-value representation authority, configuration authority, or
    persistent I/O authority.

==============================================================================
05. WHAT TO PRESERVE FROM CURRENT DA-27
==============================================================================

Preserve these boundaries almost unchanged, except terminology alignment:

    - DA-23 owns the abstract execution adapter authority boundary.
    - DA-27 owns adapter lifecycle, trust, isolation, traceability, and initial
      adapter classes.
    - DA-28 owns RuntimeHost identity, workspace ownership, startup modes, entry
      surfaces, command-surface semantics, local-first interpretation, LAN
      exposure, and RuntimeHost trace reason ownership.
    - Adapter mediation is not sandboxing.
    - Sandboxing does not grant Kernel authority.
    - Lack of sandboxing does not grant backend implementation authority.
    - Isolation mechanism does not change Turnix semantic authority.
    - Isolation mechanism does not change RuntimeHost authority semantics.
    - Unsandboxed adapter-executed code requires explicit trust or policy
      treatment.
    - Trust decisions are scoped.
    - Trust decisions do not grant capability permission, committed-state
      mutation, persistent I/O, RuntimeHost control, workspace ownership, LAN
      exposure, command-surface acceptance, artifact/export authority, or
      DA-26 workflow authority unless owning documents explicitly define the
      combined effect.
    - Adapter class names are descriptive unless later implementation specs lock
      concrete identifiers.
    - BrowserJSAdapter owns no authoritative persistent state.
    - PythonInProcessAdapter is not backend implementation authority.
    - PythonSubprocessAdapter gives process separation, not complete security by
      itself.
    - CliAdapter is not Kernel or RuntimeHost authority by itself.
    - RemoteClientAdapter does not own state authority or RuntimeHost authority.
    - TestAdapter does not weaken runtime authority boundaries.
    - Adapter lifecycle does not replace activation, ApplicationRun, Job,
      transport, RuntimeHost, capability, Window, OrchestrationUnit, artifact,
      export, comparison, Replay, Resume, Retry, or audit workflow lifecycles.
    - Adapter readiness does not imply activation success, capability permission,
      ApplicationRun readiness, RuntimeHost readiness, or Job success.
    - Adapter failure and disconnect do not silently redefine other domain
      outcomes.
    - DA-27 owns adapter-domain trace reason identifiers.
    - Implementation-specific trace reason extensions do not redefine DA-27
      meanings.

    active save identity
        -> SaveBundle identity when applicable

        -> ModCallContext, when Pack-facing adapter execution is meant

        -> ApplicationRun where live runtime incarnation is meant
        -> Application where durable application individual is meant

        -> SaveBundle

    PackContext
        -> ModCallContext

    Orchestration Unit
        -> OrchestrationUnit when used as the first-class type name

    Adapter readiness does not imply pack activation success
        -> Adapter readiness does not imply Pack activation success or final

        -> Adapter activation dispatch does not imply Phase 1/Phase 2/Phase 3

==============================================================================
08. ACCEPTANCE CONDITIONS FOR THE REVISED DA-27
==============================================================================

A revised DA-27 is acceptable when all of the following are true:

    - It preserves adapter mediation as distinct from sandboxing.

    - It preserves sandboxing as not Kernel authority.

    - It preserves lack of sandboxing as not backend implementation authority.

    - It preserves adapter class, trust class, and isolation class as not
      authority roots by themselves.

    - It preserves scoped trust decisions.

    - It preserves explicit unsafe-adapter policy handling.

    - It preserves DA-23 abstract execution-boundary ownership.

    - It preserves DA-28 RuntimeHost/local-first/LAN/Workspace ownership
      ownership.

    - It does not make RuntimeHost deployment shape into adapter authority.

    - It uses current Dv3 names: Application, ApplicationRun, SaveBundle,
      ModCallContext, ExecutionAdapter, OrchestrationUnit.

    - It avoids stale AppInstance, SavePack, and PackContext wording unless
      explicitly declared as legacy aliases elsewhere.

    - It keeps BrowserJSAdapter state non-authoritative.

    - It keeps PythonInProcessAdapter from becoming backend implementation
      authority.

    - It keeps CliAdapter and RemoteClientAdapter from becoming RuntimeHost
      authority by themselves.

    - It keeps adapter lifecycle separate from activation, ApplicationRun, Job,
      transport, RuntimeHost, View/UI, OrchestrationUnit, capability,
      artifact/export, comparison, Replay, Resume, Retry, and audit workflow
      lifecycles.

    - It keeps adapter readiness separate from final Activated state.

    - It aligns adapter activation dispatch wording with DA-14/P01.

    - It keeps adapter failure/disconnect from silently redefining other domain
      outcomes.

    - It keeps DA-05/DA-06/DA-07 stop-lines for committed-value/configuration/I-O
      authority.

    - It keeps DA-25/DA-26 stop-lines for artifact/export and workflow outcomes.

    - It keeps adapter trace evidence as adapter-domain evidence, not substitute
      evidence for activation, RPC, capability, policy, Job, ApplicationRun,
      OrchestrationUnit, UI/View, RuntimeHost, artifact/export, workflow,
      persistent I/O, or committed state.

    - It keeps concrete adapter identifiers, trust classes, isolation classes,
      lifecycle state machines, implementation protocols, and implementation-
      specific trace extensions open for later specifications.

==============================================================================
09. FINAL EDITOR INSTRUCTION
==============================================================================

Keep DA-27.

Do not perform a heavy conceptual rewrite.

Do perform a small terminology and source-stack alignment rewrite.

Use REWRITE-DA-27 as mostly valid preservation guidance, but do not copy stale
AppInstance/SavePack/PackContext vocabulary into the revised file.

DA-27 should remain the adapter lifecycle, trust, isolation, concrete adapter
class, and adapter-domain traceability document.

DA-27 should not become:

    - abstract execution-boundary authority spec
    - ModCallContext spec
    - activation lifecycle protocol
    - RuntimeHost command/Workspace ownership spec
    - capability permission spec
    - policy spec
    - Job spec
    - OrchestrationUnit spec
    - ApplicationRun spec
    - SaveBundle spec
    - View/UI spec
    - artifact/export spec
    - Replay/Resume/Retry/audit workflow spec
    - concrete adapter implementation spec

The main work is to preserve the strong adapter boundary while aligning names and
trace/activation boundaries with Proposal P01, Proposal P02, DA-14, DA-23,
DA-28, and DA-30.
