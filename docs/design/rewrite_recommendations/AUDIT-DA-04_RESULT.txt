==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Mostly correct, with terminology translation required.

    The recommendation correctly preserves DA-04's central model: committed state
    is authoritative truth; runtime memory, transaction staging, trace, progress,
    tool views, debugger views, UI/View presentation, frontend state, adapter
    state, RuntimeHost command output, PackManager presentation, Job lifecycle
    state, OrchestrationUnit lifecycle state, capability invocation records, RPC
    acknowledgements, diagnostic output, Window evidence, journal evidence,
    artifact/export packaging, comparison output, Replay reports, Resume attempts,
    and Retry attempts do not become committed-state authority unless relevant
    material crosses the DA-04 commit boundary.

    The recommendation still uses stale PackContext and AppInstance wording in
    guardrails and refers to durable save / SavePack-local copied material. Those
    should be translated to ModCallContext, Application/ApplicationRun, and
    SaveBundle/persistence terminology where they must be named.

Document verdict:
    Keep with targeted terminology and stop-line fixes.

DA-04 is architecturally strong and already contains much of the desired trace and
commit-authority separation.

No heavy conceptual rewrite is recommended.

The main required fixes are:

    - remove Session from memory-layer and nested-transaction examples because
      Session has been removed from Turnix core
    - use ProcessingPipeline / ProcessingRun or OrchestrationUnit wording instead
      of pipeline-session inheritance where that is the intended concept
    - normalize OrchestrationUnit naming where the canonical first-class type is
      meant
    - translate durable save / SavePack-related wording to SaveBundle/persistence
      wording
    - ensure trace-visible means state/transaction trace emission obligation, not
      retained-trace persistence guarantee and not committed-state authority
    - add or preserve a compact committed-state stop-line covering UI, debugger,
      Job, OrchestrationUnit, RuntimeHost, PackManager, artifacts/exports,
      comparison, Replay, Resume, Retry, and audit workflow outputs
    - preserve DA-04 as owner of committed-state truth and transaction semantics
    - avoid final-document version/process metadata leakage

Primary conclusion:
    Keep DA-04. Apply a small targeted cleanup pass, not a rewrite. The largest
    semantic cleanup is removing Session-era examples from the transaction/layer
    discussion and translating persistence wording to SaveBundle/persistence.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-04 should not keep older terminology as a historical artifact.

Specifically, the rewrite should not preserve:

    - Session as a Turnix core state/memory owner
    - child session as a nested transaction/pipeline example
    - MainSession / HiddenSession / TemporarySession / SessionRegistry language
    - ctx.sessions or Session-owned pipeline/memory assumptions
    - AppInstance as runtime identity vocabulary
    - PackContext as Pack-facing mutation or state authority vocabulary
    - SavePack as durable persistence vocabulary
    - durable save as an undefined substitute for SaveBundle/persistence
    - Orchestration Unit as a separate informal concept where OrchestrationUnit is
      the canonical type name
    - trace as committed state
    - trace persistence as required for committed-state correctness
    - persistence as defining committed-state truth
    - artifact/export/workflow material as committed-state authority by packaging
      or presentation
    - semi-authoritative / soft-authoritative / diagnostic-authoritative authority
      classes

If legacy names appear in explanatory examples, they should be translated to
canonical terms or scoped as compatibility aliases.

Canonical translations:

    AppInstance -> ApplicationRun where live runtime lifecycle is meant
    AppInstance -> Application where durable application identity is meant
    PackContext -> ModCallContext where Pack-facing gateway authority is meant
    SavePack -> SaveBundle where durable persistence closure is meant
    durable save -> SaveBundle or durable Application persistence closure where
        that is the intended architecture object
    Orchestration Unit -> OrchestrationUnit when the first-class type is meant

The useful part of the old recommendation is not old wording. The useful part is
the committed-state authority split:

    Committed state is authority. Everything else is staging, observation,
    presentation, representation support, lifecycle state, tooling output,
    artifact/export packaging, workflow output, or diagnostic evidence unless it
    crosses the DA-04 commit boundary.

==============================================================================
02. WHAT DA-04 GETS RIGHT
==============================================================================

02.1. Committed state is authoritative truth
--------------------------------------------

DA-04 correctly says runtime memory and committed state are distinct.

It correctly says runtime memory is not authoritative merely because it is
resident, visible, active, or currently in use.

It correctly says committed state is authoritative only because it crossed the
explicit commit boundary defined by DA-04.

Preserve this.

02.2. Observation is not authority
----------------------------------

DA-04 correctly says observational material may explain what happened but does
not define committed truth.

It correctly says Turnix does not treat observation as authority and does not
require observational completeness for committed-state correctness.

Preserve this.

02.3. Trace-visible mutation wording is already mostly correct
--------------------------------------------------------------

DA-04 already says trace-visible mutation means state and transaction domains
have a trace emission obligation, retained trace evidence is not required for
committed-state correctness, and trace evidence does not become committed-state
authority.

Preserve this and align all later `trace-visible` wording with that meaning.

02.4. Authority classes are binary
----------------------------------

DA-04 correctly distinguishes exactly two authority classes:

    - Authoritative
    - Non-authoritative

Preserve this.

Do not introduce semi-authoritative, soft-authoritative, diagnostic-authoritative,
trace-authoritative-for-state, lifecycle-authoritative-for-state, artifact-
authoritative, comparison-authoritative, or replay-authoritative categories.

02.5. Transaction model is strong
---------------------------------

DA-04 correctly defines transaction as temporary staging overlay, with staged
mutation not authoritative until commit.

It correctly says commit and abort are atomic and partial propagation does not
occur.

Preserve this.

02.6. Conflict detection is strong
----------------------------------

DA-04 correctly uses baseRevisionId and committed revision comparison for
conflict detection when committing into committed layers.

It correctly rejects silent merge, last-write-wins, heuristic reconciliation,
fallback, guesswork, or convenience behavior.

Preserve this.

02.7. Persistence protects truth but does not define truth
---------------------------------------------------------

DA-04 correctly says persistence protects committed state against loss, but
persistence does not define what state truth is.

Preserve this and translate durable save wording to SaveBundle/persistence where
needed.

02.8. Patch versus Copy is strong
---------------------------------

DA-04 correctly says static data is read-only by default and mutation intent is
explicitly Patch or Copy.

It correctly forbids silently substituting Patch for Copy or Copy for Patch.

Preserve this.

02.9. Latest committed state remains restorable
-----------------------------------------------

DA-04 correctly says state garbage collection may remove older revisions and
unreachable historical committed states, but must not remove data required to
reconstruct the latest committed state for each committed key.

Preserve this.

02.10. Tooling does not bypass commit authority
-----------------------------------------------

DA-04 correctly says tooling-originated mutation occurs inside a transaction and
follows the same commit/abort rules as runtime mutation.

Preserve this and keep debugger/management UI behavior in their owning documents.

02.11. Restoration boundary is strong
-------------------------------------

DA-04 correctly says deterministic restoration covers committed state, not
uncommitted runtime activity, external side effects, pending Job execution,
active OrchestrationUnit execution, adapter state, RuntimeHost output, UI/View
state as committed truth, Window evidence as committed truth, artifact/export
material as committed truth, comparison output, or Resume/Retry outcome from
prior evidence.

Preserve this.

02.12. Migration commit rule is strong
--------------------------------------

DA-04 correctly says migration that changes authoritative committed state occurs
as normal orchestrated work inside a transaction, is abortable, and does not
bypass the normal commit boundary.

Preserve this.

==============================================================================
03. MAJOR REQUIRED FIX: REMOVE SESSION-ERA EXAMPLES
==============================================================================

The target DA-04 still contains Session-era wording:

    Example layer kinds include:
        - session

and:

    If a pipeline run creates or enters a child session while an enclosing
    pipeline run is active, the child session inherits the enclosing
    transactional view.

Session has been removed from Turnix core. DA-04 should not preserve Session as a
core memory owner or nested transaction example.

03.1. Memory layer example correction
-------------------------------------

Replace the example layer list with canonical concepts such as:

    - kernel-global
    - applicationRun
    - view, if View-local presentation state is intentionally represented as a
      memory layer but remains non-authoritative unless committed through DA-04
    - orchestrationUnit or transaction scope, if that is the intended staging
      layer
    - transactional

Do not include `session` unless it is explicitly scoped as a legacy compatibility
or external application-level concept.

03.2. Nested transaction wording correction
-------------------------------------------

Replace child-session wording with ProcessingRun / OrchestrationUnit / child
transaction wording depending on intended meaning.

Suggested replacement:

    If orchestrated work creates or enters a child transaction while an enclosing
    transaction is active, the child transaction inherits the enclosing
    transactional view.

or:

    If a ProcessingRun or OrchestrationUnit enters a child transaction while an
    enclosing transaction is active, reads resolve first-match from the child
    transaction downward through the inherited stack.

Do not imply Session-owned pipeline, Session-owned memory, or ctx.sessions.

03.3. Preserve the transaction semantics
----------------------------------------

The semantics to preserve are:

    - child transaction inherits enclosing transactional view
    - reads resolve from child transaction downward through inherited stack
    - writes target child transaction
    - child commit propagates into parent transaction
    - child transaction does not commit directly into committed layers while an
      enclosing transaction exists
    - only outermost transaction commit mutates committed layers

Only the Session vocabulary needs replacement.

==============================================================================
04. REQUIRED TRACE WORDING STOP-LINE
==============================================================================

DA-04 should preserve and possibly repeat the DA-03 trace wording rule:

    State and transaction trace obligations are emission obligations.

    Trace retention and loss are governed by DA-03.

    Loss of trace evidence affects evidential completeness, not committed-state
    correctness.

    Trace evidence does not become committed-state authority.

This prevents two opposite errors:

    - treating trace evidence as committed-state authority
    - treating lossy trace persistence as permission to skip state/transaction
      trace emission obligations

DA-04 owns state/transaction trace emission obligations.

DA-03 owns trace substrate, event structure, DAG semantics, span mechanics,
retention, pruning, and loss.

==============================================================================
05. REQUIRED COMMITTED-STATE STOP-LINE
==============================================================================

DA-04 should contain or preserve a compact committed-state stop-line.

Recommended wording:

    Committed state is authoritative state.

    Runtime memory, transactional staging layers, trace, progress, tool views,
    debugger views, UI/View presentation, frontend state, adapter state,
    RuntimeHost command-surface output, PackManager presentation, Job lifecycle
    state, OrchestrationUnit lifecycle state, capability invocation records, RPC
    acknowledgement, diagnostic output, Window evidence, journal evidence,
    retained historical evidence, artifact packaging, export packaging, Minimal
    Audit Bundle material, comparison output, Replay reports, Resume attempts,
    Retry attempts, and audit workflow reports are not committed-state authority
    unless their relevant material is committed through the DA-04 commit model.

    Persistence protects committed truth but does not define truth.

    Trace explains or reports what happened where evidence is retained; trace
    does not define committed truth.

This belongs in DA-04 because DA-04 owns committed-state authority.

==============================================================================
06. PAYLOAD / CONFIGURATION / PERSISTENCE BOUNDARIES
==============================================================================

DA-04 should preserve these ownership boundaries:

    DA-05 owns payload identity, Chunk, ChunkId, ValueRef, decode, integrity, and
    reachability representation.

    Payload material participates in committed-state restoration only when it is
    retained authoritative material referenced by committed state.

    DA-06 owns configuration scopes, schemas, defaults, overrides,
    effectiveConfig, materialization, migration, storage layout, and policy-file
    placement.

    Committed configuration is authoritative when committed through DA-04.

    effectiveConfig is a runtime-visible derived view, not a separate authority
    class.

    DA-07 owns persistent I/O authority.

    SaveBundle/persistence documents own durable persistence closure, retained
    material, SaveBundle storage, persistence compatibility, and recovery details.

    Persistence protects committed truth but does not define committed truth.

DA-04 may name those domains to protect committed-state authority, but it should
not define their detailed behavior.

==============================================================================
07. ARTIFACT / EXPORT / WORKFLOW BOUNDARIES
==============================================================================

DA-04 should preserve these boundaries:

    DA-08 owns Window kinds and Window finalization.

    SafePointWindow contains committed boundary material, but optional retained
    evidence inside it does not add committed-state authority.

    DA-25 owns WindowManifest, WindowExport, Minimal Audit Bundle, digest,
    partial export, missing-material artifact semantics, and offline inspection
    artifact semantics.

    Artifact/export representation does not add committed-state authority.

    DA-26 owns ComparisonResult, equality modes, Replay, Resume, Retry, and audit
    workflow semantics.

    ComparisonResult does not define committed-state truth.

    Replay restores retained committed state within DA-04 boundaries; it does not
    create new committed truth by itself and does not re-run external effects.

    Resume and Retry are new work and do not retroactively commit prior
    uncommitted activity.

Do not let artifacts, exports, digests, comparison output, Replay reports, Resume
attempts, Retry attempts, or audit reports become committed-state authority by
presentation or packaging.

==============================================================================
08. TOOLING / ADAPTER / HOST BOUNDARIES
==============================================================================

DA-04 should preserve these boundaries:

    Tooling may inspect through controlled surfaces.

    Tooling-originated mutation uses the same transaction and commit model as
    runtime mutation.

    Debugger mutation that affects authoritative state still uses DA-04
    transaction and commit rules.

    Adapter-executed mutation seeking Turnix guarantees re-enters through
    orchestration, capability, transaction, and commit boundaries before becoming
    authoritative.

    Same-language or same-process execution does not bypass committed-state
    authority.

    ModCallContext does not expose unrestricted committed-state mutation.

    RuntimeHost command surfaces do not directly mutate committed state.

    PackManager views, repair suggestions, graph preparation, and management
    operations do not directly mutate committed state.

    Debugger or management tooling must use the same transaction/commit model
    when initiating state mutation.

Replace stale PackContext wording with ModCallContext where gateway authority is
meant.

==============================================================================
09. ORCHESTRATIONUNIT AND JOB BOUNDARIES
==============================================================================

DA-04 should preserve these boundaries:

    DA-19 owns Job lifecycle, Job result, Job timeout, Job cancellation, progress,
    retained result, late completion, and Job trace semantics.

    Job lifecycle state is not committed state.

    Job result payloads become authoritative only if their relevant material is
    committed through the owning state/transaction domain.

    DA-24 owns OrchestrationUnit lifecycle, mutation-authority ownership,
    terminal outcomes, single-lane ApplicationRun orchestration, and
    OrchestrationUnit trace reason ownership.

    OrchestrationUnit existence or lifecycle state is not committed state.

    OrchestrationUnit coordinates mutation flow, but does not bypass the DA-04
    commit boundary.

    OrchestrationUnit terminal outcome does not by itself define transaction
    commit or abort.

    Transaction commit or abort does not by itself define OrchestrationUnit
    terminal outcome.

Normalize `Orchestration Unit` to `OrchestrationUnit` when the first-class type is
meant.
