SUMMARY
=======

DA-16 is strong and highly Dv3-compatible.

No heavy rewrite is recommended.

DA-16 defines the strict, auditable runtime interaction model used by Turnix for
cross-pack wiring and cross-pack execution.

It defines:

    - Services as runtime wiring objects
    - Capabilities as permissioned, Turnix-mediated operations
    - permission classes and decision triggers
    - capability identity and version rules
    - conflict rules for capability identities
    - capability invocation flow and execution modes
    - capability relationship to execution adapters
    - capability relationship to Jobs when execution is Job-backed
    - trace and audit requirements for capability calls
    - cross-runtime and cross-adapter symmetry

DA-16 should preserve this core split:

    Service = runtime wiring object

    Capability = named, permissioned, Turnix-mediated operation

    Job = optional observable lifecycle handle when the capability operation
          needs Job semantics

Required small cleanups:

    1. Fix duplicate 09.1 section numbering around "Capability Execution Modes
       and Jobs".

    2. Clarify, if desired, that capability-call trace evidence is required as
       an emission obligation, while trace retention and loss remain governed by
       DA-03.

Rewrite-boundary guardrails:

    DA-16 owns Services, Capabilities, permission classes, capability invocation
    mediation, capability-domain trace reasons, and cross-pack execution
    boundary behavior.

    DA-16 should not absorb detailed importing, activation, adapter lifecycle,
    persistence, remembered-decision precedence, trace storage, or Job lifecycle
    semantics.

    Those details belong to their subject-owning documents.

Overall recommendation:

PRESERVATION RULE 1: SERVICE / CAPABILITY DISTINCTION
=====================================================

Preserve the Service / Capability split.

Services provide shared runtime wiring.

Capabilities provide named, permissioned, Turnix-mediated operations.

Services are not:

    - permission layer
    - adapter authority
    - PackContext authority
    - backend-internal exposure to adapter-executed code
    - cross-pack execution shortcut
    - in-process adapter bypass
    - Job lifecycle boundary bypass
    - persistence authority

Capabilities are not:

    - Services
    - Jobs
    - OrchestrationUnits
    - RPC messages
    - direct service objects
    - committed-state authority
    - PackManager authority
    - adapter authority
    - execution authorization
    - persistence authority

This prevents the bad model:

    I got a service object, therefore I can call whatever I want.

Correct model:

    Services are runtime wiring.

    Capabilities are mediated execution boundaries.


PRESERVATION RULE 2: CAPABILITY / JOB RELATION
==============================================

Preserve the Capability / Job split.

A capability invocation may complete without creating a Job.

A capability invocation may create or attach to a Job when the operation
requires observable Job lifecycle semantics.

Not every capability invocation creates a Job.

A Job-backed capability remains a capability invocation.

Job-backed execution does not bypass capability mediation.

Job-backed execution does not expose service internals.

Job-backed execution does not expose raw implementation objects.

Job-backed execution does not grant callers direct access to the underlying
execution mechanism.

Correct model:

    Capability invocation may be direct.

    Capability invocation may be Job-backed.

    Job-backed capability is still a capability invocation.

    Job lifecycle semantics belong to DA-19.

    Permission and mediation semantics belong to DA-16.


PRESERVATION RULE 3: PERMISSION IDENTITY AND EXECUTION AUTHORIZATION REMAIN SEPARATE
====================================================================================

Preserve the permission model defined here.

Permission classes are:

    - none
    - soft
    - hard

Permission class is immutable per major version.

Permission classification is capability-defined and is not negotiated by
callers.

Remembered capability permission matching uses the exact versioned capability
identifier.

DA-16 does not introduce wildcard, prefix, family, or versionless fallback
matching for remembered capability decisions.

Capability permission is distinct from DA-23 execution authorization for a code
artifact.

A code artifact may be allowed to run while a specific capability invocation is
still denied.

This prevents the bad model:

    adapter code is allowed to execute, therefore it may do everything.

DA-17 remains load-bearing for remembered-decision semantics.


PRESERVATION RULE 4: RUNTIME EXPORT OVERRIDES MANIFEST INTENT
=============================================================

Preserve the runtime export / manifest declaration split.

Capability export happens at runtime through explicit capability registration.

Capability export defines authoritative runtime behavior.

Capability usage happens through a mediated capability-call surface.

Manifest capability declarations are optional and advisory only.

Manifest declarations may support tooling, diagnostics, and user experience.

Manifest intent does not override runtime reality.

Adapter metadata or adapter binding does not substitute for runtime capability
export.

Implementation warning:

    Do not make manifest declarations look like granted/exported capabilities.


PRESERVATION RULE 5: INVOCATION FLOW AND PERMISSION PAUSE
=========================================================

Preserve the invocation flow.

When a mediated capability request is invoked:

    1. Turnix evaluates permission.

    2. If allowed, handler executes or accepted Job-backed execution begins.

    3. If undecided, execution pauses for decision handling.

During undecided permission handling:

    - decision surface may be shown
    - user or policy input is obtained
    - resulting decision is recorded according to DA-17 policy rules
    - execution resumes only after that decision path completes

Turnix remains responsive while execution is paused for decision handling.

No background mutation may occur while paused.

Execution resumes deterministically from the pause point.

Permission evaluation occurs before capability execution begins.

Job-backed, adapter-mediated, and in-process invocation do not skip permission
evaluation.


PRESERVATION RULE 6: STRICT SERVICE / CAPABILITY SEPARATION
===========================================================

Preserve strict cross-pack execution mediation.

Capabilities must not expose service internals directly as a bypass path.

One pack must not call another pack's service-provided behavior directly across
pack boundaries.

Cross-pack execution must go through capability mediation.

Adapter-executed cross-pack behavior must go through capability mediation.

Job-backed capability execution does not expose service internals.

Job handles do not provide direct service access.


PRESERVATION RULE 7: COMPUTED AND REACTIVE BEHAVIOR IS RUNTIME-ONLY
===================================================================

Preserve the anti-hidden-mutation rule.

Packs may react to runtime state or configuration by:

    - observing values
    - computing derived behavior
    - adjusting runtime output

But such behavior remains runtime-only.

It does not mutate stored configuration or memory by itself.

It does not intercept persistence.

It does not replace the authoritative source of truth.


PRESERVATION RULE 8: CAPABILITY CONFLICTS DO NOT SILENTLY RESOLVE
=================================================================

Preserve explicit conflict handling.

Multiple packs exporting the same capability identity are not allowed by
default.

Conflict is explicit.

Resolution requires:

    - explicit user choice
    - or hard failure if no permitted resolution path exists

Silent override is forbidden.

Adapter selection does not silently resolve capability conflicts.


PRESERVATION RULE 9: TRACE OWNERSHIP STAYS DOMAIN-SPECIFIC
==========================================================

Preserve capability-domain trace ownership.

DA-16 owns capability-domain trace reason identifiers.

Capability-call trace evidence distinguishes at least:

    - denied execution
    - deferred execution while waiting on decision handling
    - direct successful execution
    - direct failed execution
    - Job-backed execution accepted by the capability boundary

Job-backed execution acceptance is not a Job terminal outcome.

Job-backed execution acceptance is not capability success by itself unless the
operation's contract defines successful acceptance as the direct capability
result.

When a capability invocation creates or attaches to a Job, the Job lifecycle
trace remains causally linked to the capability invocation trace evidence.

DA-19 owns Job-domain trace reasons.

DA-23 owns adapter-domain trace obligations.

Trace wording should follow the DA-03 cross-document trace wording check.


PRESERVATION RULE 10: CROSS-RUNTIME AND CROSS-ADAPTER SYMMETRY
==============================================================

Preserve the cross-runtime capability model.

The same interaction model applies across supported runtimes.

The same interaction model applies across execution adapters.

Python packs may expose capabilities used by JavaScript packs.

JavaScript packs may invoke Python logic through capabilities.

Browser frontend adapters may invoke Kernel-mediated capabilities only through
Turnix-mediated surfaces.

Python in-process adapters may invoke capabilities only through Turnix-mediated
surfaces.

Direct cross-language object access is not part of this model.

Direct cross-adapter object access is not part of this model.

Capabilities remain the universal mediated execution boundary.

Job-backed capability execution does not change cross-runtime or cross-adapter
boundary rules.


REWRITE-BOUNDARY GUARDRAILS, NOT SUGGESTED DA-16 CONTENT
=========================================================

This section is not suggested DA-16 wording.

It exists to prevent architectural drift during rewrite when the editor knows
DA-16 but may not have every subject-owning document loaded.

Use these as guardrails only.

Capability-boundary guardrails:

    Services are runtime wiring objects, not permission gates.

    Capabilities are named, permissioned, Turnix-mediated operations.

    Capability permission is not execution authorization for a code artifact.

    Execution authorization does not grant all capability permissions.

    Capability invocation is not automatically Job.

    Job-backed capability execution is still capability-mediated.

    Job handles do not expose service internals.

    Service access does not grant capability permission.

    Manifest capability declarations do not override runtime capability export.

    Adapter metadata does not substitute for runtime capability export.

    PackContext is scoped participation, not unrestricted capability invocation.

    In-process invocation does not skip permission evaluation.

    Cross-pack execution goes through capabilities, not direct service calls.

    Capability-call trace evidence is an emission obligation where capability
    calls occur.

    Capability-call trace evidence is not committed-state authority.

    Capability conflict resolution is explicit, not silent adapter selection.

Owning-document boundaries:

    DA-03 owns trace substrate, trace event schema, trace storage, trace
    retention, and trace loss semantics.

    DA-06 owns configuration schemas and policy storage formats.

    DA-07 owns persistence rules and file I/O.

    DA-12 owns importing and module-loading rules.

    DA-14 owns activation semantics and execution guarantees.

    DA-17 owns remembered-decision precedence and user-decision persistence
    semantics.

    DA-19 owns Job lifecycle, Job result, Job timeout, Job cancellation,
    supersession, progress, and late completion semantics.

    DA-21 owns RPC semantics.

    DA-23 owns execution adapter boundary semantics and adapter-executed code
    authority boundaries.

    DA-24 owns OrchestrationUnit mutation authority and execution-authority
    coordination.

    DA-27 should preserve ExecutionAdapter/capability separation from the
    concrete adapter lifecycle side when audited.

Local rewrite rule:

    DA-16 may name these concepts when needed to protect service, capability,
    and permission boundaries.

    DA-16 should not define their detailed behavior.

    DA-16 should remain the Services, Capabilities, Permissions, and
    capability-mediated cross-pack interaction document.


WATCH ITEMS
===========

Decision persistence watch:

    DA-17 remains load-bearing for remembered capability decisions.

    When DA-17 is revised or audited, verify that it preserves:

        - exact versioned capability identity matching
        - no wildcard/prefix/family/versionless fallback unless explicitly
          introduced by policy
        - run/save/global remembered-decision ordering
        - user-decision reversibility and explainability
        - no adapter-owned permission decision authority

Adapter lifecycle watch:

    DA-27 should preserve the separation between:

        - adapter lifecycle
        - adapter execution authorization
        - PackContext authority
        - capability invocation
        - capability permission
        - Job-backed capability lifecycle

    Adapter lifecycle must not become capability permission or service access.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-16.

No heavy rewrite is recommended.

Required small cleanups:

    1. Fix duplicate 09.1 section numbering around "Capability Execution Modes
       and Jobs".

    2. If desired, clarify that capability-call trace evidence is required as
       an emission obligation, while trace retention/loss remains governed by
       DA-03.

Preserve:

    - Service / Capability separation
    - Capability / Job separation
    - permission identity versus execution authorization
    - runtime export versus manifest intent
    - invocation pause and permission decision flow
    - strict cross-pack capability mediation
    - computed/reactive behavior as runtime-only
    - explicit capability conflict handling
    - domain-specific trace ownership
    - cross-runtime and cross-adapter capability symmetry

Do not expand DA-16 into detailed importing, activation, adapter lifecycle,
persistence, configuration schema, remembered-decision precedence, trace storage,
Job lifecycle, RPC, OrchestrationUnit, or concrete adapter protocol semantics.
