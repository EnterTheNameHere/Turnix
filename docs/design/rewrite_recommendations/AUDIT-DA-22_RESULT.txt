==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Correct in substance, with current-name translation required.

    The recommendation correctly preserves DA-22's central model: UI is
    presentation and interaction, not authority by itself; a View is a
    Kernel-bound frontend runtime surface; frontend runtime code is adapter-
    executed code under the execution-adapter boundary; user interaction becomes
    meaningful only after Kernel acceptance; frontend-side validation does not
    replace Kernel validation; View disconnect does not silently decide Job,
    adapter, RuntimeHost, Window, artifact, or workflow outcomes; and UI-domain
    trace evidence does not replace owning-domain trace evidence.

    The recommendation still uses AppInstance and session-era examples in some
    places. Translate those to Application, ApplicationRun, SaveBundle, Window,
    View, trace scope, or DA-26 workflow scope as appropriate.

Document verdict:
    Keep with targeted terminology and owner-boundary fixes.

DA-22 is architecturally strong and should not be heavily rewritten.

The target already includes many of the right stop-lines: UI is not committed
state, not capability authority, not policy authority, not persistence authority,
not RuntimeHost authority, and not artifact/workflow authority by presentation.

The main required fixes are:

    - replace AppInstance / appInstanceId wording with ApplicationRun /
      applicationRunId where live runtime incarnation is meant, or Application /
      applicationId where durable application identity is meant
    - remove or translate AppInstance-based View identity and lifecycle wording
    - replace PackContext in the non-ownership list with ModCallContext where the
      Pack-facing invocation gateway is meant
    - add DA-05, DA-06, DA-07, DA-25, DA-26, and likely DA-27 to upstream or
      cross-reference visibility where DA-22 already depends on those boundaries
    - clarify DA-23 / DA-27 split for frontend adapter boundary versus adapter
      lifecycle semantics
    - preserve DA-28 as RuntimeHost owner and avoid making View an entry-surface
      authority by itself
    - preserve debugger UI resume / continue as DA-18 debugger-control wording,
      not DA-26 Resume
    - preserve Retry wording as DA-26 Retry only when routed through DA-26 workflow
      semantics
    - preserve UI trace as UI-domain trace emission, not owning-domain outcome
      authority or DA-03 trace substrate
    - avoid final-document version/process metadata leakage

Primary conclusion:
    Keep DA-22 as the UI, View, frontend runtime, frontend-client binding,
    presentation, interaction, frontend adapter participation, presentation-state,
    decision-presentation, debugger UI, accessibility transform, reconnect,
    multi-client, and UI-domain trace document. Apply targeted current-terminology
    and owner-boundary fixes only.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-22 should not keep older terminology merely because it appears in older source
material or recommendations.

Specifically, the rewrite should not preserve:

    - AppInstance as primary current runtime identity vocabulary
    - appInstanceId as primary current trace identity when ApplicationRun is meant
    - Session as a core architecture identity
    - PackContext as the current Pack-facing invocation gateway
    - FrontendAdapter as the umbrella term for all adapters
    - View as owner of Application/ApplicationRun lifecycle
    - View as owner of RuntimeHost lifecycle or workspace authority
    - View as owner of Window lifecycle or Window finalization
    - View as owner of artifact/export authority
    - View as owner of Replay, Resume, Retry, comparison, or audit workflow
      outcome
    - UI trace evidence as owning-domain trace evidence
    - UI trace evidence as committed-state truth
    - visible state as authoritative merely because it is visible
    - frontend-side validation as Kernel validation, capability permission,
      execution authorization, policy evaluation, or persistence authority
    - debugger UI resume as DA-26 Resume
    - ordinary retry wording as DA-26 Retry unless routed through DA-26 workflow
      semantics
    - View disconnect as automatic cancellation, supersession, detachment,
      retention, discard, adapter failure, RuntimeHost stop, Window finalization,
      artifact authority, or workflow outcome

Canonical translations:

    AppInstance -> ApplicationRun where live runtime incarnation is meant
    AppInstance -> Application where durable application identity is meant
    appInstanceId -> applicationRunId where live runtime identity is meant
    appInstanceId -> applicationId only where durable Application identity is meant
    PackContext -> ModCallContext where invocation-scoped Pack gateway is meant
    FrontendAdapter -> frontend adapter family / frontend adapter role under the
        ExecutionAdapter umbrella
    Orchestration Unit -> OrchestrationUnit if that wording appears in DA-22
    session -> ApplicationRun, View, Window, trace scope, SaveBundle, or DA-26
        workflow scope depending on intended current meaning

The useful part of the older recommendation is not old naming. The useful part is
this boundary:

    DA-22 owns presentation and interaction semantics. It does not own committed
    state, configuration, persistence, capabilities, policy, decisions, jobs,
    debugger semantics, RuntimeHost authority, Window finalization, artifacts,
    exports, comparison, Replay, Resume, Retry, or audit workflow outcomes.

01B. DOCUMENT-METADATA LEAKAGE CHECK
==============================================================================

The final DA-22 document should read as architecture documentation, not as audit,
version, or rewrite-process metadata.

Do not include statements such as:

    - This is V3 design.
    - In V3, View is only presentation.
    - The new design removes AppInstance.
    - This rewrite added DA-25 and DA-26 stop-lines.
    - Unlike V2, UI does not own sessions.
    - Codex kept AppInstance wording.
    - This audit decided DA-22 should not own RuntimeHost authority.
    - DA-22 was rewritten because of the audit.

Those facts may be useful in audit files, migration notes, compatibility notes,
branch notes, changelogs, or explicitly historical documents. They do not belong
in the architecture document itself.

The final DA-22 should simply define UI, View, frontend client, frontend runtime,
frontend adapter family, View identity, View lifecycle, frontend runtime authority
boundary, View pack participation, presentation state, frontend event flow,
decision presentation, debugger UI, accessibility and presentation transforms,
reconnect/multi-client behavior, UI-domain trace obligations, implementation-spec
boundaries, unsupported behaviors, open questions, and locked summary.

02. WHAT DA-22 GETS RIGHT
==============================================================================

02.1. UI is presentation and interaction, not authority
-------------------------------------------------------

DA-22 correctly says UI is a presentation and interaction surface and is not
authoritative state, capability authority, policy authority, or persistence
authority by itself.

Preserve this strongly.

02.2. View is a Kernel-bound frontend runtime surface
-----------------------------------------------------

DA-22 correctly says a View is a Kernel-bound frontend runtime surface that
receives state and sends interaction through Turnix-mediated channels.

Preserve this, while translating AppInstance references to current Application /
ApplicationRun terminology.

02.3. User interaction requires Kernel acceptance
-------------------------------------------------

DA-22 correctly says user interaction becomes meaningful only when Kernel accepts
the corresponding command, decision, capability call, or RPC message.

Preserve this.

02.4. Frontend runtime code remains adapter-executed code
---------------------------------------------------------

DA-22 correctly says frontend runtime code is adapter-executed frontend code under
DA-23 and does not grant authority by itself.

Preserve this, while aligning the adapter terminology with ExecutionAdapter and
DA-27 lifecycle ownership.

02.5. RuntimeHost entry-surface boundary is strong
--------------------------------------------------

DA-22 correctly says a View or frontend client may act as a RuntimeHost entry
surface only when DA-28 and the relevant runtime workflow define that relationship.

Preserve this.

02.6. DA-05 / DA-06 / DA-07 and DA-25 / DA-26 stop-lines are partly present
----------------------------------------------------------------------------

DA-22 already says UI presentation of state, configuration, or stored material
must not define DA-04, DA-05, DA-06, or DA-07 authority.

It also already says UI/audit-viewer/reconnect/result wording does not define
artifact export, comparison, Replay, Resume, Retry, or audit workflow semantics
unless routed through DA-25 or DA-26.

Preserve and move those dependencies into upstream/cross-reference visibility.

02.7. View identity separation is mostly strong
-----------------------------------------------

DA-22 correctly separates View identity from frontend client identity, user
identity, frontend adapter identity, RuntimeHost identity, Window identity,
artifact/export identity, and workflow identity.

Preserve this, but update AppInstance identity references.

02.8. View lifecycle separation is strong
-----------------------------------------

DA-22 correctly says View creation does not activate Packs, View creation does
not create application runtime work by itself, View readiness does not imply
RuntimeHost readiness or Pack activation success, and View disconnect does not
silently decide other lifecycle outcomes.

Preserve this, with Application/ApplicationRun terminology.

02.9. Frontend-side validation is not authority
-----------------------------------------------

DA-22 correctly says frontend-side validation may improve UX but does not replace
Kernel validation, capability permission, execution authorization, or policy
evaluation.

Preserve this.

02.10. Decision presentation is not decision ownership
------------------------------------------------------

DA-22 correctly says UI may present Kernel-originated decision points, but DA-17
owns decision and policy semantics and Kernel remains the arbiter of accepted
responses.

Preserve this.

02.11. Debugger UI is not debugger authority
--------------------------------------------

DA-22 correctly says debugger UI is a frontend surface for debugger behavior and
DA-18 owns debugger semantics.

Preserve this, while making debugger resume / continue distinct from DA-26
Resume.

02.12. Presentation transforms are non-authoritative
----------------------------------------------------

DA-22 correctly says presentation transforms for accessibility, readability,
localization, scaling, filtering, grouping, or layout do not mutate authoritative
state by themselves.

Preserve this.

02.13. Multi-client/reconnect behavior remains explicit
-------------------------------------------------------

DA-22 correctly leaves concrete reconnect and multi-client behavior to
implementation specifications while preserving the invariant that multiple
frontend clients do not create multiple authoritative truths.

Preserve this.

02.14. UI-domain trace reasons do not define owning-domain outcomes
-------------------------------------------------------------------

DA-22 correctly says UI-domain trace reasons describe UI/View behavior only and
do not define capability outcome, Job terminal outcome, decision outcome,
debugger outcome, adapter outcome, RuntimeHost outcome, or committed-state
mutation outcome.

Preserve and expand this to Window, artifact/export, comparison, Replay, Resume,
Retry, and audit workflow outcomes.

==============================================================================
03. REQUIRED FIX: APPLICATION / APPLICATIONRUN TERMINOLOGY
==============================================================================

DA-22 still uses AppInstance and appInstanceId heavily.

Replace AppInstance according to meaning:

    ApplicationRun:
        one live runtime incarnation / one running execution period

    Application:
        durable application individual

Examples:

    relationship between Views, AppInstances, and frontend clients
        -> relationship between Views, Applications, ApplicationRuns, and frontend
           clients

    A View may present one AppInstance
        -> A View may present one ApplicationRun, one Application, or another
           Kernel-recognized surface depending on the surface class

    One AppInstance may have zero, one, or multiple Views
        -> One ApplicationRun may have zero, one, or multiple Views, depending on
           runtime and policy model

    A View may exist for a non-AppInstance surface
        -> A View may exist for a non-ApplicationRun surface

    View identity is distinct from AppInstance identity
        -> View identity is distinct from Application and ApplicationRun identity

    appInstanceId when applicable
        -> applicationRunId when live runtime identity is meant; applicationId
           only where durable Application identity is meant

DA-20 owns Application/ApplicationRun lifecycle and runtime identity.
DA-22 may reference those identities only to define View presentation and binding
scope.

==============================================================================
04. REQUIRED FIX: PACKCONTEXT / MODCALLCONTEXT TERMINOLOGY
==============================================================================

The target says DA-14 owns activation lifecycle and PackContext authority.

Current canonical Pack-facing invocation gateway is ModCallContext, not
PackContext.

Recommended replacement:

    DA-14 owns activation lifecycle.

    DA-30 owns ModCallContext invocation gateway semantics.

If DA-22 needs only a stop-line, use:

    This document does not define activation lifecycle (DA-14) or Pack-facing
    invocation gateway semantics (DA-30).

Do not preserve PackContext as current vocabulary unless an explicit compatibility
note requires it.

==============================================================================
05. REQUIRED FIX: UPSTREAM / OWNER VISIBILITY
==============================================================================

DA-22 already references or depends on several DA boundaries that are missing
from the upstream list.

Add or otherwise expose these owner references:

    DA-05:
        committed-value representation, ValueRef, Chunk, ChunkId, decode,
        integrity, retained payload material

    DA-06:
        configuration semantics, configuration storage layout, configuration
        migration, presentation-persisted user preferences

    DA-07:
        persistent-I/O authority, Reader/Writer providers, root boundaries,
        storage safety, filesystem rules

    DA-25:
        Window artifacts, exports, Minimal Audit Bundle, digest representation,
        partial export, missing material, offline inspection artifact semantics

    DA-26:
        comparison, ComparisonResult, Replay, Resume, Retry, and audit workflow
        semantics

    DA-27:
        adapter lifecycle semantics, especially where frontend adapter lifecycle
        is mentioned

    DA-30:
        ModCallContext invocation gateway semantics, if Pack-facing UI pack or
        Pack code gateway semantics are named

This does not mean DA-22 owns those domains. It means DA-22 should name the
owning documents when it touches their boundaries.

==============================================================================
06. REQUIRED FIX: DA-23 / DA-27 ADAPTER SPLIT
==============================================================================

DA-22 currently names DA-23 for adapter boundary semantics and also uses DA-23
where adapter lifecycle classification is meant.

Current split:

    DA-23:
        execution adapter boundary semantics

    DA-27:
        adapter lifecycle semantics and adapter lifecycle classification

Recommended replacement where lifecycle is meant:

    If View disconnect affects frontend adapter lifecycle, DA-23 and DA-27 govern
    adapter boundary and adapter lifecycle classification.

Also preserve:

    Frontend adapter means a frontend-role ExecutionAdapter, not the umbrella term
    for all adapters.

Do not regress to FrontendAdapter as the general adapter category.

==============================================================================
07. DA-25 / DA-26 WORKFLOW AND ARTIFACT STOP-LINES
==============================================================================

DA-22 correctly allows UI to present audit viewers, artifact viewers, comparison
views, workflow controls, retained evidence, retained updates, and export
progress.

Preserve this boundary:

    UI may present and request interactions for artifact/export and workflow
    domains.

    Presentation, acknowledgement, subscription delivery, reconnect delivery,
    result retrieval, or user interaction does not define artifact/export
    authority, ComparisonResult, Replay outcome, Resume outcome, Retry outcome, or
    audit workflow outcome.

    DA-25 owns artifact/export meanings.

    DA-26 owns comparison, Replay, Resume, Retry, and audit workflow meanings.

Do not let UI display or UI event order become artifact/workflow authority.

==============================================================================
08. DEBUGGER RESUME / DA-26 RESUME SPLIT
==============================================================================

DA-22 should preserve the distinction between debugger resume / continue and
DA-26 Resume.

Recommended wording:

    Debugger UI may request resume / continue from debugger pause only through
    Turnix-mediated channels.

    Debugger UI resume / continue is debugger-control behavior under DA-18.

    Debugger UI resume / continue does not mean DA-26 Resume after
    SafePointWindow restoration.

Do not let the word Resume carry DA-26 workflow semantics unless the workflow is
explicitly routed through DA-26.

==============================================================================
09. VIEW CLOSURE / RETRY WORDING
==============================================================================

DA-22 currently says View closure does not define whether AppInstance work was
opened again.

The recommendation discusses retried/retry wording. Under DA-26, Retry has a
formal meaning.

Recommended replacement:

    View closure does not by itself define whether ApplicationRun work committed,
    aborted, continued, detached, requested DA-26 Retry, requested DA-26 Resume,
    finalized a Window, created an artifact/export, or completed an audit
    workflow.

If the document uses ordinary retry language, make it explicit whether it is
informal UI retry, Job retry, or DA-26 Retry.

==============================================================================
10. TRACE WORDING
==============================================================================

Follow the DA-03 cross-document trace wording check.

UI trace requirements are UI-domain emission obligations.

Trace retention, trace pruning, trace loss, event structure, trace DAG semantics,
span mechanics, and trace storage semantics remain owned by DA-03.

DA-22 owns UI-domain trace reasons for View lifecycle, frontend binding, frontend
command receipt, decision presentation, and UI-originated control requests.

UI trace evidence does not replace owning-domain trace evidence, including:

    - RPC trace evidence
    - adapter trace evidence
    - decision trace evidence
    - RuntimeHost trace evidence
    - capability trace evidence
    - Job trace evidence
    - debugger trace evidence
    - Application/ApplicationRun trace evidence
    - Window trace evidence
    - artifact/export trace evidence
    - comparison / Replay / Resume / Retry / audit workflow trace evidence
    - committed-state trace evidence

Do not let UI trace wording imply that trace evidence is committed state or that
trace persistence is guaranteed forever.
