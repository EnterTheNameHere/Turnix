IS document verdict:
    Keep with targeted terminology and authority-boundary fixes.

    IS-02 is a useful implementation specification for concrete WebSocket RPC
    transport flow. It should not be rewritten from scratch. Its strongest parts
    are the repeated separation between WebSocket transport, RPC envelope

    idempotency.

==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. Correct implementation-specification scope.

    IS-02 clearly states that it defines concrete bootstrap, handshake,
    connection-lifecycle, and message-flow behavior for WebSocket RPC transport.

    It also says that it does not introduce new runtime authority semantics,
    permission rules, policy rules, abstract RPC semantics, execution adapter
    boundary semantics, View semantics, Job lifecycle semantics, or higher-level
    routing/capability semantics.

2. Correct transport/RPC separation.

    The document repeatedly says that WebSocket is one concrete transport, not
    the RPC model itself and not Kernel authority.

    This is the correct boundary for an implementation specification: WebSocket
    can carry RPCMessage envelopes, but it does not own RPC semantics.

3. Good separation between transport lifecycle and higher lifecycles.

    IS-02 repeatedly distinguishes:

        - transport flow from Job lifecycle
        - transport timeout from Job timeout
        - transport disconnect from Job cancellation
        - transport disconnect from adapter failure
        - request acceptance as Job-backed work from final Job success
        - request acceptance as adapter-mediated work from adapter or work success

    These are important and should be preserved.

4. Good IS-01 dependency boundary.

    IS-02 uses IS-01 for RPCMessage envelope schema and isComplete completion
    marker behavior instead of redefining the envelope schema locally.

    This is correct. IS-02 should remain a flow document, not become a duplicate
    RPCMessage schema.

5. Good cancel handling.

    The dispatch section already treats cancel as routed/requested behavior that
    affects transport-local waits, subscriptions, Job-backed work, or
    adapter-mediated work only according to message type, route, operation
    contract, and policy.

    It correctly says cancel does not directly kill arbitrary underlying
    execution.

6. Good timeout handling.

    The document clearly separates transport timeout, Job timeout, and adapter
    timeout.

    It correctly says transport timeout may affect frontend Promise handling or
    emit a cancellation request when policy and operation contract allow it, but
    does not automatically transition a Job, cancel a Job, stop execution, or
    fail an execution adapter.

7. Good observability ownership.

    IS-02 owns RPC transport-domain trace reason identifiers while leaving trace
    substrate semantics to DA-03, Job lifecycle trace obligations to DA-19, and
    adapter lifecycle trace obligations to DA-23.

8. Good intentional openness.

    The OPEN questions section correctly avoids locking final Job-backed
    response, progress, retained-result, and subscription-delivery patterns while
    DA-19 Job envelope questions remain unresolved.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. Session terminology reintroduces a removed core architecture concept.

    IS-02 uses Session language in multiple places:

        - session and generation tracking
        - Session manager
        - transport/session context
        - session state
        - active session expectation
        - transport/session continuity failure

    Current source-stack correction:
        Proposal P02 removes Session from the Turnix core architecture. It also
        rejects Session-based RPC routing.

    Required consequence for IS-02:
        Replace Session wording with connection-generation, RPCConnection,
        frontend client binding, View binding, or transport-continuity wording,
        depending on the local meaning.

        Safe direction:

            Session manager
                -> RPCConnection / connection-state manager / transport
                   connection state

            session and generation tracking
                -> connection generation and continuity tracking

            transport/session context
                -> transport connection context

            current view or session state
                -> current View binding / connection state snapshot

            active session expectation
                -> active connection-generation expectation

            transport/session continuity failure
                -> connection-generation or transport-continuity failure

        Do not preserve Session wording as harmless colloquial text.

2. AppInstance terminology is superseded by Application / ApplicationRun.

    IS-02 still uses AppInstance in several places:

        - frozen bootstrap object does not become authoritative AppInstance state
        - View bootstrap does not define AppInstance lifecycle
        - transport lifecycle is not AppInstance lifecycle
        - welcome does not imply AppInstance readiness
        - generation mismatch does not define AppInstance failure
        - trace context includes appInstanceId
        - transport observability does not define AppInstance semantics
        - higher documents own AppInstance lifecycle

    Current source-stack correction:
        Proposal P02 replaces the older combined AppInstance layer with:

            Application
                durable application individual

            ApplicationRun
                one live execution period of that Application

            SaveBundle
                durable persistence closure of the Application

    Required consequence for IS-02:
        Replace AppInstance with Application and/or ApplicationRun according to
        meaning.

        Safe direction:

            authoritative AppInstance state
                -> authoritative Application state / committed Application state

            AppInstance lifecycle
                -> Application and ApplicationRun lifecycle, or ApplicationRun
                   lifecycle if the local subject is live runtime connection

            AppInstance readiness
                -> ApplicationRun readiness, unless durable Application identity
                   readiness is specifically meant

            AppInstance failure
                -> ApplicationRun failure or Application lifecycle effect, only
                   when a higher owner defines such an outcome

            appInstanceId
                -> applicationId and/or applicationRunId

3. Principal derivation wording risks trusting message-carried authority.

    Section 11 says backend behavior derives the principal from the message and
    verifies required capability permissions.

    Risk:
        This can be read as allowing an incoming RPC payload to declare its own
        authority principal.

    Required correction:
        The final IS should say the backend derives the effective principal from
        authenticated connection context, View/client binding, runtime-owned
        correlation, and allowed message metadata. It must not trust arbitrary
        client-supplied payload fields as authority.

        Add a stop-line:

            Message fields may carry correlation metadata, but they do not let a
            caller forge a principal, permission identity, acting Pack, Kernel
            authority, Application identity, or ApplicationRun authority.

4. Object handler routing needs a raw-object access stop-line.

    IS-02 routes requests to object handlers and capability-based request
    handlers.

    This may be valid, but it must not imply direct access to raw backend objects
    or internal service objects.

    Required correction:
        Add or preserve wording that object handlers are explicit RPC routing
        targets known to the routing layer. Object routing does not grant raw
        backend-object access, service-object access, filesystem access,
        committed-state authority, capability permission, or Kernel authority.

5. ViewRegistry wording should remain subordinate to View semantics.

    The document says ViewRegistry stores server-side viewToken, ensures only the
    authenticated client can bind to a view, and may allow multiple tabs or
    distinct viewTokens.

    This is acceptable because it is already subordinate to DA-22. The rewrite
    should preserve the stop-line that ViewRegistry behavior does not define
    View authority, Application identity, ApplicationRun lifecycle, Job outcome,
    adapter lifecycle, committed state, or persistence root.

6. clientReady module-load wording could be overread as pack activation.

    clientReady reports module-load status and the backend processes
    frontend-reported module metadata for loading. The document already says
    clientReady does not by itself mean AppInstance readiness, pack activation
    success, or adapter execution success.

    Required correction:
        Translate AppInstance readiness to ApplicationRun readiness, and make
        the frontend-module status boundary explicit:

            clientReady is frontend transport/readiness evidence. It is not Pack
            activation success, ExecutionAdapter lifecycle success, Application
            readiness, ApplicationRun readiness, or capability availability.

7. Idempotency wording needs to stay below Replay/Retry/retained-result doctrine.

    IS-02 allows idempotency to return cached replies, avoid re-running handlers,
    or return existing accepted Job/adapter-work metadata when supported by the
    operation contract.

    This is useful, but it must remain request/message deduplication and must not
    become architectural Replay, Resume, Retry, retained Job result doctrine,
    Job identity reuse doctrine, OrchestrationUnit identity reuse, or
    ProcessingRun identity reuse.

    Required correction:
        Add a compact stop-line:

            Idempotency is RPC request/message deduplication. It does not define
            Replay, Resume, Retry, retained Job result behavior, Job identity
            reuse, OrchestrationUnit identity reuse, ProcessingRun identity reuse,
            or adapter-work identity reuse except where a higher owner and the
            operation contract explicitly define the relationship.

8. Trace-context appInstanceId must become current runtime identity.

    IS-02 trace context lists appInstanceId.

    Required correction:
        Replace with applicationId and/or applicationRunId. For transport
        correlation, both may be useful:

            applicationId
                durable Application identity when known

            applicationRunId
                live run identity when known

9. RPCRequestDispatched to object handler needs same object-route guardrail.

    The trace reason definition says RPCRequestDispatched is emitted when a
    request is routed to an object handler or capability-based request handler.

    This is acceptable if object handler means an explicit RPC routing target.
    It must not imply backend object exposure or service-object invocation.

10. OPEN questions should remain, but not as outdated DA-19 uncertainty if later
    source files resolve them.

    At this audit point, IS-02 intentionally leaves Job envelope and retained
    result patterns open under DA-19.

    Required correction:
        Keep those open questions only if the current source stack has not
        resolved them. If a later Job/transport source resolves them before final
        rewrite, update IS-02 accordingly instead of preserving stale OPEN text.

==============================================================================
OBSOLETE-PRESERVATION RISKS
==============================================================================

1. Do not preserve Session terminology.

    The current architecture removed Session from core. Replace all IS-02
    Session-language with connection-generation, RPCConnection, View/client
    binding, or transport-continuity wording.

2. Do not preserve AppInstance terminology.

    Translate AppInstance to Application and/or ApplicationRun according to the
    local meaning. Use ApplicationRun for live runtime connection/readiness/failure
    contexts, and Application for durable committed application state.

3. Do not preserve appInstanceId as the only runtime correlation identity.

    Replace with applicationId and applicationRunId where useful.

4. Do not preserve old retry/result uncertainty if later source-stack material
   resolves it.

    IS-02 may keep explicit OPEN questions only while those questions remain open
    in the current source stack.

ACCEPTANCE CONDITIONS FOR FINAL REWRITTEN IS-02
==============================================================================

Accept the rewritten IS-02 only if all of the following are true:

1. It remains an implementation specification for concrete WebSocket RPC flow.

2. It does not redefine RPCMessage envelope schema beyond using IS-01.

3. It does not introduce new runtime authority, permission, policy, lifecycle,
   Job, adapter, View, Application, ApplicationRun, SaveBundle, trace-retention,
   or committed-state semantics.

4. WebSocket remains one concrete transport, not the RPC model and not Kernel
   authority.

5. All Session wording has been removed or translated into connection-generation,
   RPCConnection, View/client binding, or transport-continuity wording.

6. All AppInstance/appInstanceId wording has been translated into Application,
   ApplicationRun, applicationId, and/or applicationRunId according to meaning.

7. Principal derivation cannot be read as trusting arbitrary message payload
   fields for authority.

8. Object handler routing cannot be read as raw backend object access, service
   object access, filesystem authority, Kernel authority, committed-state
   authority, or capability permission.

9. clientReady remains frontend transport/readiness evidence only and does not
   imply Pack activation success, ExecutionAdapter lifecycle success,
   ApplicationRun readiness, capability availability, or committed-state truth.

10. Transport disconnect and transport timeout remain distinct from Job
    cancellation, Job timeout, adapter failure, adapter timeout, ApplicationRun
    failure, and committed-state mutation.

11. Idempotency remains RPC request/message deduplication and does not define
    Replay, Resume, Retry, retained Job result behavior, Job identity reuse,
    OrchestrationUnit identity reuse, ProcessingRun identity reuse, or
    adapter-work identity reuse except under a higher owner and operation
    contract.

12. RPC transport trace reasons remain transport-domain evidence and do not
    define Job terminal outcomes, adapter terminal outcomes, capability
    permission, policy, ApplicationRun lifecycle, or committed-state mutation.

13. The explicit OPEN questions remain open only if still unresolved by the
    current source stack.
