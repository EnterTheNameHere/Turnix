PRESERVATION RULE 1: ADAPTER MEDIATION IS NOT SANDBOXING
========================================================

Preserve the distinction:

    Adapter mediation means adapter-executed code participates in Turnix through
    Turnix-controlled context, RPC-shaped boundaries, capabilities, lifecycle,
    policy, and trace correlation.

    Sandbox means a security isolation mechanism that restricts what code can
    do outside Turnix semantic boundaries.

Adapter mediation is not sandboxing.

An adapter may provide sandboxing.

An adapter may run without strong sandboxing.

Absence of sandboxing does not convert adapter-executed code into backend
implementation code.

Presence of sandboxing does not convert adapter-executed code into Kernel
authority.

Isolation mechanism does not change Turnix semantic authority.

Lack of isolation does not grant backend authority.

Isolation mechanism does not change RuntimeHost authority semantics.

Isolation mechanism does not grant artifact/export or Replay / Resume / Retry
workflow authority.


PRESERVATION RULE 2: TRUST DECISIONS ARE SCOPED
===============================================

Preserve trust and policy boundaries.

Unsandboxed adapter-executed code requires explicit trust or policy treatment.

Third-party or externally supplied executable code is not executed through
unsafe adapters unless explicit policy permits that path.

Trust classification, permission prompts, and policy persistence remain governed
by the owning decision and policy documents.

A trust decision authorizes only the declared trust scope.

A trust decision does not grant capability permission unless the governing
capability and decision documents define that combined effect explicitly.

A trust decision does not authorize direct committed-state mutation.

A trust decision does not authorize direct payload representation authority.

A trust decision does not authorize direct configuration mutation.

A trust decision does not authorize direct persistent I/O as a Turnix authority
path.

A trust decision does not authorize RuntimeHost control, workspace ownership
change, LAN exposure, or command-surface acceptance unless the governing
RuntimeHost and policy documents define that combined effect explicitly.

A trust decision does not authorize artifact/export authority, comparison,
Replay, Resume, Retry, or audit workflow authority unless the owning documents
define that combined effect explicitly.


PRESERVATION RULE 3: ADAPTER CLASSES DO NOT DEFINE AUTHORITY
============================================================

Preserve class-specific authority boundaries.

BrowserJSAdapter:

    - runs JavaScript pack code in a browser frontend runtime
    - is normally used for View packs, UI packs, and frontend presentation
      surfaces
    - owns no authoritative persistent state
    - owns no committed-value representation authority
    - owns no artifact/export authority
    - owns no Replay / Resume / Retry workflow authority

PythonInProcessAdapter:

    - runs Python pack code in the same process as backend implementation
    - is trusted or policy-gated adapter execution
    - still uses Turnix context, capability, trace, and lifecycle boundaries
    - is not backend implementation authority
    - does not gain direct persistence, configuration, payload, artifact, or
      workflow authority merely because it runs in-process

PythonSubprocessAdapter:

    - runs Python pack code in a worker process
    - communicates with Kernel through an RPC-shaped boundary over an
      implementation-defined transport
    - provides process separation but not complete security by itself

CliAdapter:

    - may present command-line interaction and may act as a control surface for
      RuntimeHost
    - is not Kernel by itself
    - is not RuntimeHost authority by itself
    - command-surface semantics are owned by DA-28

RemoteClientAdapter:

    - connects to Kernel or RuntimeHost-facing surface over explicit transport
    - does not own state authority
    - does not own RuntimeHost authority

TestAdapter:

    - provides controlled execution and observation surfaces for tests
    - does not weaken runtime authority boundaries merely because it exists for
      testing

Adapter class names are descriptive unless a later implementation specification
locks concrete identifiers.

A concrete adapter class does not define authority by itself.


PRESERVATION RULE 4: ADAPTER LIFECYCLE IS NOT OTHER LIFECYCLES
==============================================================

Preserve lifecycle separation.

Adapter lifecycle may include:

    - declared
    - selected
    - created
    - connected
    - ready
    - loading artifact
    - executing activation
    - running
    - stopping
    - disconnected
    - failed
    - closed

Concrete adapter lifecycle states may be refined by implementation
specifications.

Adapter lifecycle does not replace:

    - pack activation lifecycle
    - AppInstance lifecycle
    - Job lifecycle
    - transport lifecycle
    - RuntimeHost lifecycle
    - Window finalization
    - OrchestrationUnit lifecycle
    - capability permission
    - payload representation
    - configuration semantics
    - persistent I/O authority
    - artifact/export lifecycle
    - comparison workflow lifecycle
    - Replay lifecycle
    - Resume lifecycle
    - Retry lifecycle
    - audit workflow lifecycle

Adapter readiness means the adapter can participate in the expected runtime
flow.

Adapter readiness does not imply:

    - pack activation success
    - capability permission
    - AppInstance readiness
    - RuntimeHost readiness
    - Job success
    - artifact/export readiness
    - comparison readiness
    - Replay readiness
    - Resume readiness
    - Retry readiness
    - audit workflow readiness

Adapter connection does not imply adapter readiness.

Adapter loading does not imply adapter activation-dispatch success.

Adapter activation dispatch does not imply activation success.

Adapter closed does not silently redefine committed-state meaning.

Adapter closed does not silently define RuntimeHost stop, failure, or
command-surface outcome.

Adapter closed does not silently define artifact/export, comparison, Replay,
Resume, Retry, or audit workflow outcome.


PRESERVATION RULE 5: ADAPTER FAILURE AND DISCONNECT ARE NOT SILENT DOMAIN OUTCOMES
=================================================================================

Preserve failure/disconnect boundaries.

Adapter failure is explicit.

Adapter disconnect is explicit when detected.

Adapter failure does not silently redefine:

    - Job terminal outcome
    - AppInstance lifecycle
    - RuntimeHost lifecycle
    - committed-state meaning
    - payload representation
    - configuration semantics
    - persistent I/O authority
    - Window finalization
    - AbortedWindow creation
    - OrchestrationUnit terminal outcome
    - capability permission
    - transport outcome
    - artifact/export outcome
    - ComparisonResult
    - Replay outcome
    - Resume outcome
    - Retry outcome
    - audit workflow outcome

Adapter disconnect does not automatically:

    - cancel Job-backed work
    - supersede Job-backed work
    - time out Job-backed work
    - detach Job-backed work
    - retain Job-backed result
    - discard Job-backed result
    - cancel an OrchestrationUnit
    - fail an AppInstance
    - stop, fail, or close a RuntimeHost
    - finalize an ActiveWindow
    - create an AbortedWindow
    - mutate committed state
    - create artifact/export authority
    - create missing-material semantics
    - cancel Replay / Resume / Retry workflow work
    - define audit workflow outcome

If adapter failure or disconnect affects accepted work, decision,
OrchestrationUnit, Job, and policy documents govern the resulting lifecycle
handling.

If adapter failure or disconnect affects transport state, DA-21 and the
relevant implementation specification govern the transport-side behavior.

If adapter failure or disconnect affects UI or View state, DA-22 governs the UI
and View-side behavior.

If adapter failure or disconnect affects RuntimeHost behavior, DA-28 governs
RuntimeHost lifecycle, host-operation, and command-surface classification.

If adapter failure or disconnect affects Window finalization, DA-08 governs
Window outcome semantics.

If adapter failure or disconnect affects committed state, DA-04 governs whether
any material becomes authoritative.

If adapter failure or disconnect affects retained value representation, DA-05
governs representation meaning.

If adapter failure or disconnect affects persistent material, DA-07 governs
persistent I/O authority.

If adapter failure or disconnect affects artifact/export material, DA-25
governs artifact/export semantics.

If adapter failure or disconnect affects comparison, Replay, Resume, Retry, or
audit workflow state, DA-26 governs workflow semantics.


PRESERVATION RULE 6: ADAPTER TRACE DOES NOT REPLACE OTHER DOMAIN TRACE
======================================================================

Preserve adapter-domain trace ownership.

DA-27 owns adapter-domain trace reasons for:

    - adapter lifecycle
    - artifact loading
    - activation dispatch
    - adapter execution
    - disconnect
    - closure

Adapter trace evidence may record context such as:

    - adapter kind
    - adapter instance identity
    - pack identity
    - declared artifact identity
    - runtimeHostId when applicable
    - RuntimeHost operation identity when applicable
    - appInstanceId when applicable
    - active save identity when applicable
    - transport kind when applicable
    - channel identity when applicable
    - RPC message identity when applicable
    - capability identity when applicable
    - jobId when applicable
    - orchestrationUnitId when applicable
    - viewId when applicable
    - execution authorization result when applicable
    - failure reason category when failure occurs
    - disconnect reason category when disconnect occurs
    - trust or isolation class when applicable

Adapter trace evidence does not replace:

    - activation trace evidence
    - RPC trace evidence
    - capability trace evidence
    - policy trace evidence
    - Job trace evidence
    - AppInstance trace evidence
    - OrchestrationUnit trace evidence
    - Window trace evidence
    - UI-domain trace evidence
    - RuntimeHost trace evidence
    - artifact/export trace evidence
    - comparison / Replay / Resume / Retry / audit workflow trace evidence
    - committed-state trace evidence
    - persistent-I/O evidence

Trace wording should follow the DA-03 cross-document trace wording check.

Implementation-specific trace reason extensions do not redefine the
adapter-domain reason meanings owned by DA-27.


PRESERVATION RULE 7: RUNTIMEHOST AND LOCAL-FIRST SEMANTICS REMAIN DA-28
=======================================================================

Preserve DA-28 ownership.

DA-27 must not define RuntimeHost identity, workspace ownership, startup modes,
entry surfaces, command-surface semantics, local-first interpretation, LAN
exposure, or RuntimeHost trace reason ownership.

CLI may be implemented as or through an adapter, but CLI RuntimeHost
command-surface meaning is defined by DA-28.

Browser frontend may be implemented through BrowserJSAdapter, but browser
RuntimeHost entry-surface meaning is defined by DA-28.

LAN clients may be implemented through remote client adapters or frontend
clients, but LAN exposure and local-first meaning are defined by DA-28.

Local-first deployment shape does not redefine adapter authority.

RuntimeHost deployment shape does not redefine adapter authority.

Remote or LAN access does not imply remote state authority.

Remote or LAN access does not imply adapter execution authority.

A second RuntimeHost does not silently acquire writable ownership of the same
workspace under DA-28.

Workspace ownership and host locking semantics are owned by DA-28 and later
implementation specifications constrained by DA-28, DA-20, DA-04, and DA-07.

DA-27 does not define RuntimeHost lifecycle or workspace ownership semantics.


WATCH ITEM: TRUST AND ISOLATION CLASS VOCABULARY
================================================

DA-27 leaves exact adapter trust classification vocabulary and exact isolation
classification vocabulary open.

Future edits should preserve current semantics:

    - trust class describes policy/trust treatment, not authority root
    - isolation class describes containment properties, not Kernel authority
    - unsafe adapter paths require explicit policy
    - trust decisions are scoped
    - trust decisions do not grant capability permission, committed-state
      mutation, payload representation, configuration mutation, persistent I/O,
      RuntimeHost control, workspace ownership, LAN exposure, command-surface
      acceptance, artifact/export authority, or Replay / Resume / Retry
      workflow authority unless the owning documents explicitly define the
      combined effect


WATCH ITEM: PAYLOAD / CONFIGURATION / PERSISTENCE AUTHORITY
===========================================================

DA-27 touches active save identity, BrowserJSAdapter persistent state,
persistent I/O trust limits, workspace ownership, and adapter trace context.

Future edits should preserve:

    - DA-05 owns payload identity, Chunk, ChunkId, ValueRef, decode, integrity,
      and retained value representation
    - DA-06 owns configuration semantics and policy-file placement
    - DA-07 owns persistent I/O authority, root boundaries, Reader / Writer
      providers, storage safety, backup/snapshot behavior, and streaming I/O
      rules
    - adapter lifecycle, readiness, failure, disconnect, trace, trust class, or
      isolation class does not grant those authorities


WATCH ITEM: ARTIFACT / EXPORT / WORKFLOW AUTHORITY
==================================================

DA-27 owns adapter-domain lifecycle and traceability.

Future edits should preserve:

    - DA-25 owns artifact/export semantics
    - DA-26 owns comparison, Replay, Resume, Retry, and audit workflow semantics
    - adapter artifact loading is adapter-domain evidence, not DA-25
      artifact/export authority by itself
    - adapter execution success is not artifact/export success by default
    - adapter execution failure is not artifact/export failure by default
    - adapter disconnect is not missing-material semantics by default
    - adapter execution success is not ComparisonResult
    - adapter execution success is not Replay / Resume / Retry success
    - adapter execution failure is not Replay / Resume / Retry failure by default
    - adapter trace evidence may support workflow explanation, but does not own
      workflow outcome


WATCH ITEM: TRACE WORDING
=========================

Follow the DA-03 cross-document trace wording check.

Adapter trace requirements are adapter-domain emission obligations.

DA-03 owns trace substrate, retention, loss, event structure, trace DAG
semantics, span mechanics, and trace storage semantics.

Do not let adapter trace wording imply that trace evidence is committed state,
that trace persistence is guaranteed forever, or that adapter trace evidence
replaces activation, RPC, capability, policy, Job, AppInstance,
OrchestrationUnit, Window, UI, RuntimeHost, artifact/export, workflow,
persistent-I/O, or committed-state trace evidence.

CURRENT FINAL RECOMMENDATION
============================

Keep DA-27.

No heavy rewrite is recommended.

Recommended future edits:

    - keep DA-27 focused on adapter lifecycle, trust, isolation, and
      adapter-domain traceability
    - preserve DA-23 / DA-27 / DA-28 ownership split
    - preserve scoped trust-decision semantics
    - add DA-05 / DA-06 / DA-07 stop-lines where adapter lifecycle, trust,
      isolation, trace context, active save identity, BrowserJSAdapter
      persistent state, persistent I/O, workspace ownership, or storage behavior
      are mentioned
    - add DA-25 / DA-26 stop-lines where adapter artifact loading, adapter
      execution, failure, disconnect, trace evidence, retained evidence,
      artifact/export, comparison, Replay, Resume, Retry, or audit workflow
      wording appears
    - preserve adapter lifecycle separation from activation, AppInstance, Job,
      transport, RuntimeHost, Window, OrchestrationUnit, capability,
      artifact/export, comparison, Replay, Resume, Retry, and audit workflow
      lifecycle
    - preserve no silent outcome conversion on adapter failure or disconnect
    - define trust and isolation vocabulary later without changing authority
      boundaries
    - define concrete adapter state machines later without replacing activation,
      AppInstance, Job, transport, RuntimeHost, Window, OrchestrationUnit,
      capability, payload, configuration, persistence, artifact/export, or
      workflow semantics
