RECOMMENDED CLEANUP: FRONTEND ADAPTER TERMINOLOGY
=================================================

Current issue:

    DA-28 says browser frontend is a frontend surface or frontend adapter into
    the RuntimeHost.

This is not a major conflict because the sentence is specifically about browser
frontend behavior.

However, Dv3 has selected ExecutionAdapter as the general adapter category.

Recommendation:

    Do not use FrontendAdapter as the umbrella adapter concept.

Possible future wording:

    Browser frontend is a frontend surface exposed through an ExecutionAdapter
    or frontend-specific adapter realization.

Or:

    Browser frontend is a UI/front-end surface into RuntimeHost, mediated by the
    relevant execution adapter and RPC boundaries.

Important distinction:

    ExecutionAdapter = general category

    Browser/frontend adapter = specific realization or subtype


RECOMMENDED PRESERVATION 1: RUNTIMEHOST DOES NOT REPLACE KERNEL
===============================================================

Preserve RuntimeHost / Kernel separation.

Kernel owns runtime authority.

RuntimeHost owns the running host boundary through which Kernel authority is
started, exposed, coordinated, and eventually closed.

RuntimeHost must not make non-Kernel code Kernel authority.

RuntimeHost must not let command surfaces, adapters, transports, frontend
clients, or LAN clients bypass Kernel-owned authority paths.

RuntimeHost is not:

    - Kernel
    - AppInstance
    - SavePack
    - CLI
    - transport
    - ExecutionAdapter
    - Turnix identity


RECOMMENDED PRESERVATION 2: WORKSPACE OWNERSHIP PREVENTS SILENT MULTI-HOST MUTATION
===================================================================================

Preserve workspace ownership rules.

A writable workspace is owned by at most one RuntimeHost at a time unless a later
authoritative multi-host design defines another mode.

A second RuntimeHost does not silently:

    - acquire writable ownership
    - downgrade to read-only
    - ignore existing ownership evidence
    - overwrite stale ownership evidence
    - take over stale ownership

Stale ownership recovery is explicit, policy-governed, and trace-visible.

Reason:

    This prevents silent multi-host mutation of durable Turnix-managed state.


RECOMMENDED PRESERVATION 3: RUNTIMEHOST IS NOT APPINSTANCE OR SAVEPACK
======================================================================

Preserve RuntimeHost / AppInstance / SavePack separation.

A RuntimeHost may load zero, one, or multiple AppInstances.

RuntimeHost is not AppInstance.

RuntimeHost may host AppInstances, but AppInstance lifecycle and mutation
authority remain governed by their owning design areas.

SavePack creation/loading is not owned by CLI or browser launcher behavior.

All entry surfaces use the same Kernel-mediated new-save and existing-save
paths.

Reason:

    This prevents CLI, browser, test, launcher, or remote-client paths from
    inventing separate save semantics.


RECOMMENDED PRESERVATION 4: STARTUP MODES ARE ENTRY WORKFLOWS
=============================================================

Preserve startup-mode boundaries.

Startup modes are entry workflows over shared Kernel-mediated runtime
operations.

Startup modes do not define independent runtime semantics.

Examples such as:

    - interactive host mode
    - one-shot command mode
    - serve mode
    - connect mode
    - test mode
    - launcher mode

are different ways to enter Turnix, not different versions of Turnix.

Reason:

    Command syntax and launcher behavior must not become architecture.


RECOMMENDED PRESERVATION 5: ENTRY SURFACES AND COMMAND SURFACES ARE NOT AUTHORITY
=================================================================================

Preserve entry-surface and command-surface boundaries.

Entry surfaces and command surfaces request, observe, or control through
mediated runtime paths.

They do not become authority themselves.

A command surface does not own:

    - Kernel authority
    - workspace ownership
    - AppInstance creation
    - SavePack creation/loading semantics
    - RuntimeHost operation success
    - OrchestrationUnit completion
    - Job terminal outcome
    - capability permission
    - adapter execution authorization
    - transport authority

CLI, launcher, browser frontend, remote client, management surface, and test
surface must all use mediated Kernel-owned paths.


RECOMMENDED PRESERVATION 6: LOCAL-FIRST DOES NOT MEAN SAME-MACHINE-ONLY
========================================================================

Preserve DA-28's local-first clarification.

Local-first does not require same-machine execution.

Local-first means authoritative runtime and state remain under user-controlled
local infrastructure.

Allowed examples:

    - same-machine RuntimeHost and frontend
    - LAN machine hosting RuntimeHost with another machine as frontend
    - home server hosting RuntimeHost and SavePack state
    - powerful local AI machine hosting RuntimeHost-adjacent execution with
      lighter client presentation surface

Core doctrine:

    local-first, not local-only

    user-controlled local infrastructure, not necessarily same-machine-only


RECOMMENDED PRESERVATION 7: LAN AND REMOTE EXPOSURE DO NOT BECOME AUTHORITY
===========================================================================

Preserve LAN/remote exposure boundaries.

LAN or remote exposure may exist only as explicit, policy-governed exposure
mode.

LAN exposure does not redefine:

    - Kernel authority
    - RuntimeHost identity
    - workspace ownership
    - AppInstance authority
    - SavePack authority
    - command acceptance
    - capability permission
    - adapter authorization
    - transport authority

Remote clients are entry surfaces or participants through mediated boundaries.

They do not become RuntimeHost owners merely because they can connect.


RECOMMENDED PRESERVATION 8: RUNTIMEHOST TRACE OWNERSHIP STAYS DOMAIN-SPECIFIC
==============================================================================

Preserve RuntimeHost-domain trace ownership.

DA-28 owns RuntimeHost-domain trace reason identifiers.

DA-03 owns the trace substrate.

RuntimeHost trace reasons include:

    - lifecycle
    - workspace ownership
    - entry surfaces
    - LAN and remote exposure
    - command surfaces
    - startup modes
    - host-level runtime operations

RuntimeHost trace evidence should follow the DA-03 cross-document trace wording
check:

    domain-required trace evidence is an emission obligation

    trace retention and loss remain governed by DA-03

    trace loss weakens evidential completeness but does not by itself change
    committed-state correctness

RuntimeHost trace evidence does not replace:

    - DA-04 state/transaction evidence
    - DA-16 capability evidence
    - DA-19 Job evidence
    - DA-21 RPC evidence
    - DA-23 adapter evidence
    - DA-24 OrchestrationUnit evidence
    - DA-29 PackManager evidence


RECOMMENDED PRESERVATION 9: RUNTIMEHOST OUTCOME IS NOT ORCHESTRATION OUTCOME BY DEFAULT
======================================================================================

Preserve RuntimeHost / OrchestrationUnit separation.

RuntimeHost command acceptance does not imply OrchestrationUnit completion.

RuntimeHost operation outcome does not by itself define OrchestrationUnit
terminal outcome unless the owning workflow maps those outcomes explicitly.

This prevents CLI, command surface, RuntimeHost operation, transport ACK, or
entry-surface behavior from becoming orchestration outcome authority.


RECOMMENDED PRESERVATION 10: IMPLEMENTATION SHAPE DOES NOT DEFINE TURNIX IDENTITY
================================================================================

Preserve DA-28's implementation-independence boundary.

DA-28 must not bind Turnix to:

    - CLI
    - launcher mode
    - browser frontend
    - FastAPI
    - WebSocket
    - Python
    - service wrappers
    - subprocesses
    - containers
    - virtual machines
    - local-only execution
    - single AppInstance forever
    - command syntax as authority

RuntimeHost is the running host boundary, not a concrete implementation shape.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-28.

No heavy rewrite is recommended.

Only minor terminology alignment is needed around frontend adapter wording.

Recommended terminology direction:

    ExecutionAdapter = general category.

    Browser/frontend adapter = specific UI-facing realization or subtype, if
    the term is kept at all.

Preserve:

    - RuntimeHost does not replace Kernel
    - workspace ownership prevents silent multi-host mutation
    - RuntimeHost is not AppInstance or SavePack
    - startup modes are entry workflows
    - entry surfaces and command surfaces are not authority
    - local-first does not mean same-machine-only
    - LAN and remote exposure do not become authority
    - RuntimeHost trace ownership is domain-specific
    - RuntimeHost outcome is not OrchestrationUnit outcome by default
    - implementation shape does not define Turnix identity

Future audits should check:

    - DA-27 preserves ExecutionAdapter terminology and adapter authority
      boundaries.

DA-01, DA-02, DA-03, DA-21, DA-23, and DA-24 have already been consolidated with
the relevant DA-28 findings.
