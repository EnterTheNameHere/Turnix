==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Superseded by Proposal P02 in its SavePack/AppInstance/PackContext vocabulary
    and by DA-16/DA-30 in its service-access wording; useful only as translated
    boundary-preservation guidance.

    The recommendation correctly preserves DA-15's main semantic model:
    visibility is permissioned reachability, visibility violations are hard
    failures, exportNestedPacks is direct-child only, importPacksFromParent does
    not grant service/capability access, source-domain isolation is strict,
    PackManager presentation is not visibility authority, and visibility does not
    authorize activation, import, execution, capabilities, services, RuntimeHost,
    adapter, committed-state, or PackManager outcomes.

    However, the recommendation still frames isolation around SavePack/AppInstance
    and service access around PackContext. Use it only after translating those
    ideas into SaveBundle/Application/ApplicationRun/ModCallContext terminology.

Document verdict:
    Keep with targeted terminology and service-boundary fixes.

DA-15 is architecturally strong as the visibility enforcement and access-control
consequence document.

No heavy conceptual rewrite is recommended.

The main required fixes are:

    - replace SavePack visibility isolation with SaveBundle-local retained/copied
      Pack material visibility isolation
    - replace AppInstance context with Application / ApplicationRun context where
      needed
    - remove SavePack from default visibility kind list unless the project keeps a
      current SavePack alias explicitly
    - remove `services are accessed via ctx.services` because DA-16/DA-30 reject
      ctx.services as an ordinary Pack-facing surface
    - replace PackContext authority wording with ModCallContext gateway authority
    - preserve visibility as reference permission only
    - preserve hard failure on visibility violation
    - preserve source-domain isolation
    - keep DA-10 / DA-15 ownership split clean
    - avoid final-document version/process metadata leakage

Primary conclusion:
    Keep DA-15, but rewrite it out of the SavePack/AppInstance/PackContext layer
    and remove service-object access wording that contradicts DA-16/DA-30.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-15 should not keep older terminology as a historical artifact.

Specifically, the rewrite should not preserve:

    - SavePack as the durable persistence object
    - SavePack as a Pack kind in the default visibility list
    - SavePack as globally visible or directly referenceable Pack material
    - SavePack visibility isolation where SaveBundle-local retained/copied Pack
      material isolation is meant
    - copied packs inside SavePack as ordinary global Pack candidates
    - AppInstance context where Application / ApplicationRun context is meant
    - PackContext authority where ModCallContext gateway authority is meant
    - ctx.services as an ordinary ModCallContext surface
    - service access as direct cross-Pack Service object access

If a legacy alias is intentionally retained, DA-15 should say so explicitly and
should still state the canonical architecture term as primary.

Otherwise, the old names and assumptions should be removed or translated.

The useful part of the old recommendation is not the old terminology. The useful
part is the visibility boundary:

    Visibility answers whether one Pack is permitted to reference another Pack.
    It is permissioned reachability. It does not bridge source domains, grant
    runtime authority, grant service/capability access, activate code, import code,
    select adapters, define dependency success, or authorize execution.

==============================================================================
01B. DOCUMENT-METADATA LEAKAGE CHECK
==============================================================================

The final DA-15 document should read as architecture documentation, not as audit,
version, or rewrite-process metadata.

Do not include statements such as:

    - This is V3 design.
    - In V3, SaveBundle replaces SavePack.
    - The new design removes ctx.services.
    - This rewrite changed visibility isolation terminology.
    - Unlike V2, DA-15 now uses ApplicationRun.
    - Codex kept SavePack wording.
    - This audit decided to remove PackContext.
    - DA-15 was rewritten because of the audit.

Those facts may be useful in audit files, branch notes, migration notes,
compatibility notes, changelogs, or editor instructions. They do not belong in
the architecture document itself.

The final DA-15 should simply define visibility, exports, parent import rules,
source-domain isolation, SaveBundle-local retained/copied Pack material
visibility, service/capability separation, execution-boundary separation,
PackManager separation, hard failure behavior, and visibility-denial error
requirements.

==============================================================================
02. WHAT DA-15 GETS RIGHT
==============================================================================

02.1. Visibility as reference permission
----------------------------------------

DA-15 correctly says visibility answers exactly one question:

    Is Pack A permitted to reference Pack B?

It correctly says visibility is about reachability and permission only.

Preserve this.

02.2. Visibility is not later authority
---------------------------------------

DA-15 correctly says visibility is not activation, code loading, execution order,
dependency satisfaction, version compatibility, runtime capability access,
runtime service access, ApplicationRun authority, RuntimeHost authority, adapter
authority, or PackManager authority.

Preserve and extend this stop-line where useful.

02.3. Visibility / dependency distinction is strong
---------------------------------------------------

DA-15 correctly says dependency declaration expresses requirement and visibility
expresses permission.

It correctly says a Pack may depend on another Pack and still be forbidden from
referencing it.

It correctly says dependency may fail because visibility forbids the dependency
target and no silent bypass is allowed.

Preserve this.

02.4. Visibility evaluation at use points is strong
---------------------------------------------------

DA-15 correctly says visibility is evaluated during dependency resolution,
resolvePack calls, and turnixImport resolution.

It correctly says visibility is not bypassed or deferred.

Preserve this.

02.5. exportNestedPacks semantics are strong
--------------------------------------------

DA-15 correctly defines exportNestedPacks as direct-child export control only.

It correctly allows true, false, or a list of localId strings.

It correctly forbids dotted identifiers, non-existent localId values, and
transitive export.

Preserve this and keep DA-10 as owner of the identity/hierarchy/computed
visibility structure.

02.6. importPacksFromParent semantics are strong
------------------------------------------------

DA-15 correctly says importPacksFromParent controls parent-to-child reference
visibility and does not imply export, capability access, or service access.

It correctly says ViewPack defaults to false and other Pack kinds default to true.

Preserve this unless DA-10 or a future View-specific design explicitly changes
the default.

02.7. Source-domain isolation is strong
---------------------------------------

DA-15 correctly says resolution source is determined first and visibility is
evaluated inside that active source domain.

It correctly says visibility does not bridge resolution sources.

Preserve this strongly.

02.8. Capability and service separation is needed
-------------------------------------------------

DA-15 correctly says visibility does not imply capability access or service
access.

Preserve this, but rewrite service wording so it does not expose ctx.services or
direct Service object lookup.

02.9. Failure behavior is strong
--------------------------------

DA-15 correctly says visibility failure is hard, classified, includes requesting
Pack identity, target Pack identity, and violated rule, and permits no fallback or
probing.

Preserve this.

==============================================================================
03. MAJOR REQUIRED FIX: SAVEBUNDLE-LOCAL VISIBILITY ISOLATION
==============================================================================

DA-15 currently has a section named:

    SAVEPACK VISIBILITY

and says:

    SavePack has a dedicated visibility domain.
    SavePack is never globally visible.
    SavePack is visible only within its AppInstance context.
    copied packs inside a SavePack are visible only within that save.
    copied packs inside a SavePack are not visible globally.
    copied packs inside a SavePack shadow global packs of the same identity
    within that save domain.

Proposal P02 changes the durable persistence object to SaveBundle. SaveBundle is
not a Pack.

DA-15 should preserve the isolation semantics but translate the object model.

03.1. Replace SavePack section with SaveBundle-local retained/copied Pack material isolation
------------------------------------------------------------------------------------------

Recommended model:

    SaveBundle is not a Pack and is not globally visible as ordinary Pack
    material.

    SaveBundle-local retained or copied Pack material has a dedicated
    SaveBundle/Application visibility context.

    SaveBundle-local retained or copied Pack material is visible only within the
    owning SaveBundle/Application context unless another owning document
    explicitly exposes it.

    SaveBundle-local retained or copied Pack material is not visible globally.

    SaveBundle-local retained or copied Pack material may shadow global Packs of
    the same identity inside that SaveBundle/Application context according to
    dependency-source and graph rules.

    If a Pack is resolved from a SaveBundle-local source, global Packs with the
    same identity are not visible for that resolution path and the global registry
    is not consulted unless DA-13 / graph policy selects a global source.

This preserves DA-15's source-domain isolation without keeping SavePack as a
current architecture object.

03.2. Remove SavePack from default visibility kind list
-------------------------------------------------------

DA-15 currently lists default manifest visibility for Pack kinds including
SavePack.

Under Proposal P02, SaveBundle is not a Pack kind.

Recommended correction:

    Default visibility applies to Pack kinds such as ContentPack, AppPack,
    ViewPack, and ModPack.

    SaveBundle does not use Pack manifest visibility as its own visibility
    identity. SaveBundle-local retained or copied Pack material follows
    SaveBundle/Application context rules plus the retained Pack's own identity and
    visibility rules as defined by owning documents.

Do not add SaveBundle as a Pack kind.

03.3. Source-domain wording
---------------------------

Replace:

    save-scoped resolution ignores global packs
    global resolution ignores save-scoped copies
    visibility does not bridge resolution sources

with SaveBundle-aware wording where appropriate:

    SaveBundle-local dependency/source resolution ignores ordinary global Packs
    unless a global source is explicitly selected.

    Global dependency/source resolution ignores SaveBundle-local retained or
    copied Pack material unless a SaveBundle-local source is explicitly selected.

    Visibility does not bridge dependency/source domains.

Do not weaken the isolation boundary.

==============================================================================
04. MAJOR REQUIRED FIX: SERVICE ACCESS AND MODCALLCONTEXT SURFACES
==============================================================================

DA-15 currently says:

    services are registered during activation
    services are accessed via ctx.services
    visibility does not grant service access

This conflicts with the DA-16 audit and DA-30 audit.

DA-30 treats ctx.services as an absent/forbidden ModCallContext backdoor.

DA-16 should make Services runtime/internal wiring and keep cross-Pack execution
through Capabilities, not direct Service object retrieval.

04.1. Remove ctx.services as visibility example
-----------------------------------------------

DA-15 should not say Services are accessed via ctx.services as current
architecture text.

Recommended replacement:

    Services are runtime/internal wiring owned by DA-16 and related runtime
    documents.

    Visibility does not grant access to Services.

    Service access, if any, requires an explicitly defined runtime-owned or
    capability-mediated surface in DA-16/DA-30 or another owning document.

    Cross-Pack execution uses Capabilities rather than direct Service object
    lookup.

04.2. Preserve the visibility/service separation
------------------------------------------------

Keep the important rule:

    Visible Pack does not mean usable Service.

But avoid describing a direct Service lookup path that DA-16/DA-30 reject.

04.3. Replace PackContext authority wording
-------------------------------------------

Where the recommendation says PackContext authority, use ModCallContext gateway
authority.

Do not make visibility grant ModCallContext authority.

==============================================================================
05. REQUIRED OWNER STOP-LINES
==============================================================================

DA-15 should stay the visibility enforcement and access-control consequence
document.

It may name other domains to preserve stop-lines, but it should not define their
detailed behavior.

Recommended owner mapping:

    DA-10 owns Pack identity, hierarchy, local/global visibility model,
    exportNestedPacks, and importPacksFromParent structure.

    DA-11 owns generic resolution semantics.

    DA-12 owns importing, module loading, and code-boundary rules.

    DA-13 owns dependency, requirement, PackRequest dependency semantics,
    dependency-source policy, SaveOnly, GlobalPinned, and GlobalNormal behavior.

    DA-14 owns activation lifecycle and execution guarantees.

    DA-16 owns Services, Capabilities, permission semantics, and capability
    invocation.

    DA-17 owns user decision and remembered policy semantics.

    DA-20 owns Application/ApplicationRun lifecycle and runtime identity.

    DA-21 owns RPC, channel, transport, timeout, disconnect, cancellation message,
    and acknowledgement semantics.

    DA-23 owns abstract ExecutionAdapter boundary semantics.

    DA-24 owns OrchestrationUnit mutation authority and execution-authority
    coordination.

    DA-27 owns adapter lifecycle, trust, isolation, failure, disconnect, and
    adapter-domain trace semantics.

    DA-28 owns RuntimeHost lifecycle, startup mode, command surface, Workspace
    ownership, local-first, and LAN exposure semantics.

    DA-29 owns PackManager catalog, graph-preparation, repair, View, write, and
    PackManager-domain trace semantics.

    DA-30 owns ModCallContext gateway semantics, facade shape, lifetime, and
    absent surfaces.

    SaveBundle and persistence documents own SaveBundle storage, ownership,
    retained material, graph evidence, and loading details.

DA-15 may name these concepts when needed to protect visibility enforcement and
access-control consequences, but it should not define their detailed behavior.

==============================================================================
06. PERMISSIONDENIEDERROR NAMING WATCH
==============================================================================

DA-15 currently says visibility failure raises PermissionDeniedError.

This is acceptable if the standard error model treats visibility denial as a
permission/access-control failure.

Future edit should check whether the error taxonomy wants a more specific
visibility-denial subtype.

Do not change the semantics:

    - visibility failure is hard
    - visibility failure is classified
    - visibility failure includes requesting Pack identity, target Pack identity,
      and violated rule
    - no fallback is permitted
    - no probing is permitted
    - no runtime negotiation by Packs is permitted

Only the exact error name is a possible taxonomy watch item.

==============================================================================
07. WHAT TO PRESERVE FROM CURRENT DA-15
==============================================================================

Preserve these boundaries, but rewrite SavePack/AppInstance/PackContext/service
surface assumptions where present:

    - Visibility answers whether one Pack is permitted to reference another Pack.
    - Visibility is permissioned reachability.
    - Visibility is not activation.
    - Visibility is not code loading.
    - Visibility is not execution order.
    - Visibility is not dependency satisfaction.
    - Visibility is not version compatibility.
    - Visibility is not runtime capability access.
    - Visibility is not runtime service access.
    - Visibility is not ApplicationRun authority.
    - Visibility is not RuntimeHost authority.
    - Visibility is not adapter authority.
    - Visibility is not PackManager authority.
    - Dependency declaration expresses requirement.
    - Visibility expresses permission.
    - A Pack may depend on another Pack and still be forbidden from referencing it.
    - Visibility failure during dependency resolution is a hard dependency failure.
    - Visibility checks occur during dependency resolution, resolvePack calls, and
      turnixImport resolution.
    - Visibility is evaluated dynamically between requesting Pack and target Pack.
    - Visibility is not pre-expanded into a static graph.
    - exportNestedPacks remains direct-child only and not transitive.
    - importPacksFromParent controls parent-to-child reference visibility only.
    - importPacksFromParent does not imply export, capability access, service
      access, permission inheritance, activation, adapter execution authorization,
      or RuntimeHost authority.
    - ViewPack default importPacksFromParent remains false unless an owning View
      document changes it.
    - Resolution source is determined before visibility evaluation.
    - Visibility does not bridge source domains.
    - SaveBundle-local retained/copied Pack material remains isolated from global
      visibility by default.
    - Visibility does not grant capabilities.
    - Visibility does not grant service access.
    - Visibility does not authorize importing/module loading, activation, adapter
      execution, capability invocation, RuntimeHost command execution, or
      OrchestrationUnit-backed mutation.
    - PackManager presentation of visibility is not visibility authority.
    - PackManager repair suggestions do not silently override visibility rules.
    - Visibility failure is hard, classified, and no fallback/probing is allowed.
    - Identifiers used in visibility checks are case-sensitive and byte-exact.

==============================================================================
08. WHAT TO ADD OR CHANGE IN THE REVISED DA-15
==============================================================================

08.1. Add canonical terminology note
------------------------------------

Add a compact note near the interpretation or concept section:

    DA-15 uses canonical architecture names:

        SaveBundle:
            durable persistence closure of an Application

        Application:
            durable application individual

        ApplicationRun:
            one live execution period of an Application

        ModCallContext:
            invocation-scoped Pack-facing gateway into Turnix

    Older notes may use SavePack, AppInstance, or PackContext. DA-15 does not use
    those names as primary architecture terms unless a compatibility note
    explicitly says so.

Do not write this as "V3 names", "new names", or "after the rewrite".

08.2. Rewrite SavePack visibility section
-----------------------------------------

Replace `SAVEPACK VISIBILITY` with a SaveBundle-aware isolation section.

Suggested title:

    SAVEBUNDLE-LOCAL PACK MATERIAL VISIBILITY

or:

    SAVEBUNDLE-LOCAL VISIBILITY ISOLATION

Keep the semantics from section 03 of this audit.

08.3. Remove SavePack from Pack-kind default visibility
------------------------------------------------------

Do not list SaveBundle as a Pack kind.

If old SavePack compatibility exists, scope it as legacy and avoid making it a
primary architecture type.

08.4. Rewrite services section
------------------------------

Remove `services are accessed via ctx.services`.

Replace with DA-16/DA-30-compatible service/capability wording.

Keep visibility/service separation.

08.5. Add DA-30 stop-line
-------------------------

Add DA-30 to owner stop-lines as the owner of ModCallContext gateway semantics
and absent surfaces.

08.6. Keep DA-10 / DA-15 ownership split
----------------------------------------

Do not duplicate the full DA-10 identity/hierarchy/computed visibility model in
DA-15.

DA-10 owns structure.

DA-15 owns enforcement and access-control consequences.

08.7. Keep implementation details open
--------------------------------------

Do not define final visibility graph visualization, exact UI phrasing, error
subtype taxonomy, PackManager repair behavior, SaveBundle storage format,
capability permission flow, service registry shape, or ModCallContext facade
shape unless an owning document explicitly fixes them.

09. SPECIFIC PHRASE REPLACEMENTS
==============================================================================

Use these as a starting pass. Context still matters.

    SavePack
        -> SaveBundle where durable persistence closure is meant
        -> SaveBundle-local retained/copied Pack material where copied Pack
           material is meant

    SavePack-specific visibility isolation
        -> SaveBundle-local retained/copied Pack material visibility isolation

    SavePack has a dedicated visibility domain
        -> SaveBundle-local retained/copied Pack material has a dedicated
           SaveBundle/Application visibility context

    SavePack is never globally visible
        -> SaveBundle is not ordinary globally visible Pack material

    SavePack is visible only within its AppInstance context
        -> SaveBundle-local retained/copied Pack material is visible only within
           its SaveBundle/Application context unless another owning document
           explicitly says otherwise

    copied packs inside a SavePack
        -> retained or copied Pack material inside a SaveBundle

    copied packs inside a SavePack are visible only within that save
        -> SaveBundle-local retained/copied Pack material is visible only within
           that SaveBundle/Application context

    copied packs inside a SavePack are not visible globally
        -> SaveBundle-local retained/copied Pack material is not visible globally
           by default

    copied packs inside a SavePack shadow global packs
        -> SaveBundle-local retained/copied Pack material may shadow global Packs
           within that SaveBundle/Application context according to dependency and
           graph rules

    AppInstance authority
        -> ApplicationRun authority where live runtime authority is meant

    AppInstance context
        -> ApplicationRun context or Application/SaveBundle context, depending on
           durable-vs-live meaning

    PackContext authority
        -> ModCallContext gateway authority

    services are accessed via ctx.services
        -> remove; replace with DA-16/DA-30-compatible wording that Services are
           runtime/internal wiring and visibility does not grant service access

    current Dv3 terminology / current Dv3 type names / current Dv3 names
        -> canonical architecture terminology / canonical architecture type names

    Any final-document wording like "In V3, SaveBundle..."
        -> replace with direct architecture language such as "SaveBundle..."

10. ACCEPTANCE CONDITIONS FOR THE REVISED DA-15
==============================================================================

A revised DA-15 is acceptable when all of the following are true:

    - It preserves visibility as permissioned reference reachability.

    - It preserves visibility violations as hard failures.

    - It preserves no silent bypass, fallback, probing, or runtime negotiation by
      Packs.

    - It preserves DA-10 / DA-15 ownership split.

    - It preserves exportNestedPacks as direct-child only and non-transitive.

    - It preserves importPacksFromParent as parent-to-child reference visibility
      only.

    - It preserves ViewPack default isolation unless an owning View document
      changes it.

    - It preserves source-domain isolation.

    - It rewrites SavePack visibility isolation into SaveBundle-local
      retained/copied Pack material visibility isolation.

    - It states or implies that SaveBundle is not a Pack.

    - It removes SavePack from current Pack-kind default visibility unless an
      explicit compatibility alias is retained.

    - It prevents SaveBundle-local retained/copied Pack material from leaking into
      global visibility by default.

    - It prevents global content-root precedence from overriding SaveBundle-local
      retained/copied Pack material by default.

    - It preserves visibility/capability separation.

    - It preserves visibility/service separation without exposing ctx.services as
      an ordinary Pack-facing path.

    - It keeps Services and Capabilities DA-16-owned.

    - It keeps ModCallContext gateway semantics and absent surfaces DA-30-owned.

    - It preserves visibility as not import authority, activation, adapter
      execution authorization, RuntimeHost authority, PackManager authority,
      ApplicationRun authority, committed-state authority, capability access,
      service access, or OrchestrationUnit mutation authority.

    - It keeps PackManager visibility presentation and graph preparation DA-29-owned.

    - It keeps Application/ApplicationRun lifecycle DA-20-owned.

    - It keeps dependency-source policy DA-13-owned.

    - It keeps importing/module-loading DA-12-owned.

    - It keeps activation DA-14-owned.

    - It keeps ExecutionAdapter and adapter lifecycle DA-23/DA-27-owned.

    - It keeps RuntimeHost behavior DA-28-owned.

    - It keeps SaveBundle storage, retained material, graph evidence, and loading
      details owned by SaveBundle/persistence documents.

    - It keeps exact error subtype taxonomy, UI wording, graph visualization,
      service registry shape, capability permission flow, and ModCallContext
      facade shape open unless an owning document fixes them.

    - It does not mention audit provenance, rewrite process, old/new design, V3,
      Codex, candidate status, or branch history as ordinary architecture text.

==============================================================================
11. FINAL EDITOR INSTRUCTION
==============================================================================

Keep DA-15.

Do not perform a heavy conceptual rewrite.

Do perform a targeted rewrite of SavePack/AppInstance/PackContext terminology and
service-access wording.

Use REWRITE-DA-15 only as translated boundary-preservation guidance. Do not keep
it as an obsolete historical artifact and do not copy its stale SavePack,
AppInstance, PackContext, or ctx.services assumptions into the rewritten DA.

Do not include audit/source metadata or version/process framing in the final
DA-15 documentation. The final DA-15 should not say this is V3 design, in V3,
new design, old design, rewritten design, created by Codex, decided by audit, or
part of a rewrite-history process.

DA-15 should remain the visibility enforcement, source-domain isolation,
SaveBundle-local retained/copied Pack material visibility isolation, hard-failure,
and access-control consequence document.

DA-15 should not become:

    - Pack identity and hierarchy specification
    - generic resolution specification
    - dependency-source policy specification
    - importing/module-loading specification
    - activation lifecycle specification
    - Service/Capability/permission specification
    - ModCallContext specification
    - Application/ApplicationRun lifecycle specification
    - RuntimeHost specification
    - PackManager operation or UI specification
    - SaveBundle storage-format specification
    - concrete error taxonomy or UI phrasing specification

The main work is to preserve DA-15's strong visibility enforcement model while
migrating out of the SavePack/AppInstance/PackContext layer and removing service-
object access wording that conflicts with DA-16/DA-30.
