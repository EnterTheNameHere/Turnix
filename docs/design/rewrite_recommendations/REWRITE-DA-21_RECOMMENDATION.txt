SUMMARY
=======

DA-21 is strong and highly Dv3-compatible.

No heavy rewrite is recommended.

DA-21 defines the Turnix model for RPC communication between runtime
participants, execution adapters, frontend surfaces, tools, and
Kernel-mediated execution paths.

It defines:

    - RPC as a logical communication boundary
    - RPC message-flow categories
    - RPCChannel as the transport-neutral communication interface
    - transport as an interchangeable carrier of RPC messages
    - peer identity and connection context
    - request, emit, subscribe, cancel, reply, error, and acknowledgement
      meaning
    - routing boundaries for object and capability messages
    - relationship between RPC and execution adapters
    - separation between RPC transport lifecycle and Job lifecycle
    - relationship between RPC requests and Job-backed work
    - transport timeout and disconnect semantics at the abstract level
    - message correlation and trace obligations
    - relation between DA-level RPC semantics and implementation specifications

DA-21 should preserve the core split:

    RPC = logical communication boundary

    RPCChannel = transport-neutral interface

    Transport = concrete carrier

    WebSocket = one concrete transport

    JSON = concrete envelope/schema representation

Required small cleanup:

    Clarify that trace-visible RPC flow means RPC-domain trace emission
    obligation where applicable, while trace retention and loss remain governed
    by DA-03.

Rewrite-boundary guardrails:

    DA-21 owns abstract RPC semantics.

    DA-21 should not absorb detailed concrete JSON envelope fields, concrete
    WebSocket frame flow, trace substrate, capability permission, decision
    policy, Job lifecycle, AppInstance lifecycle, ExecutionAdapter lifecycle,
    frontend UI layout, or RuntimeHost command-surface semantics.

    Those details belong to their subject-owning documents.

Overall recommendation:

    KEEP WITH SMALL TRACE WORDING CLARIFICATION

ACTUAL DA-21 CLEANUP 1: TRACE-VISIBLE RPC FLOW
==============================================

Current issue:

    DA-21 says RPC message flow remains trace-visible where trace evidence
    exists.

This should follow the DA-03 cross-document trace wording check.

Correct reading:

    RPC-domain trace evidence is a domain emission obligation where applicable.

    Trace retention and loss remain governed by DA-03.

    RPC observability does not replace capability, decision, Job, adapter,
    RuntimeHost, AppInstance, debugger, or Window trace evidence.

Not:

    RPC trace persistence is guaranteed forever.

Not:

    RPC trace evidence becomes committed-state authority.

Not:

    RPC observability replaces the owning domain's evidence.

No heavy DA-21 rewrite is needed.


PRESERVATION RULE 1: RPC IS LOGICAL BOUNDARY, NOT TRANSPORT
===========================================================

Preserve the core model:

    RPC = logical communication boundary

    RPCChannel = transport-neutral interface

    Transport = concrete carrier

    WebSocket = one concrete transport

    JSON = concrete envelope/schema representation

RPC is not:

    - transport
    - WebSocket
    - JSON
    - capability authority
    - adapter authority
    - RuntimeHost authority
    - Job lifecycle
    - final work outcome


PRESERVATION RULE 2: ACKNOWLEDGEMENT IS NOT OUTCOME
===================================================

Preserve acknowledgement semantics.

Acknowledgement means message receipt or transport-level handling only.

Acknowledgement does not imply:

    - request success
    - capability execution
    - adapter execution
    - Job creation
    - Job success

This prevents the bad model:

    packet arrived, therefore work happened

Correct model:

    Acknowledgement says something about communication handling.

    It does not say the target operation executed.

    It does not say authority was granted.

    It does not say work succeeded.


PRESERVATION RULE 3: ROUTING IS NOT AUTHORITY
=============================================

Preserve routing boundaries.

RPC routing identifies the logical target of a message.

RPC routes may target:

    - objects
    - capabilities
    - adapter-facing endpoints
    - control endpoints
    - subscription endpoints

But RPC routing does not:

    - grant permission
    - activate packs
    - select or authorize an ExecutionAdapter
    - bypass capability mediation
    - grant workspace ownership
    - accept RuntimeHost commands by itself
    - create AppInstances by itself
    - expose LAN by itself

Capability-routed RPC remains subject to DA-16.

Adapter-facing RPC remains subject to DA-23.

RuntimeHost control-surface RPC remains subject to DA-28.


PRESERVATION RULE 4: REQUEST ACCEPTANCE IS NOT FINAL SUCCESS
============================================================

Preserve request/acceptance/outcome separation.

An RPC request may end in:

    - immediate reply
    - structured error
    - accepted Job-backed work
    - accepted adapter-mediated work
    - accepted RuntimeHost operation
    - rejected-before-Job outcome

Request acceptance means the request crossed the RPC dispatch boundary and was
accepted by the target operation.

Request acceptance is not final operation success unless the operation contract
explicitly defines successful acceptance as the result.

Accepted work may expose correlation to later lifecycle evidence, but lifecycle
meaning remains owned by the relevant domain.


PRESERVATION RULE 5: RPC REQUEST IS NOT JOB
===========================================

Preserve RPC / Job separation.

Once Job-backed work exists, DA-19 owns Job lifecycle semantics.

A request rejected before Job-backed work exists does not produce a Job terminal
outcome.

RPC request identity and jobId remain distinct.

RPC correlation may link request identity to jobId only when a Job exists.

A request accepted as Job-backed work may return a Job handle, immediate
accepted-work response, subscription relationship, or other operation-defined
lifecycle surface.

Correct model:

    RPC request may cause or expose Job-backed work.

    RPC request is not Job.

    RPC rejection before Job exists is not Job failure.

    Job lifecycle remains DA-19-owned.


PRESERVATION RULE 6: RPC DOES NOT BYPASS CAPABILITY, ADAPTER, OR RUNTIMEHOST OWNERSHIP
=====================================================================================

Preserve cross-domain ownership.

Capability-routed RPC remains capability-mediated.

RPC routing does not bypass capability mediation.

RPC acknowledgement does not imply capability execution.

Capability permission remains owned by DA-16.

Adapter-facing RPC messages remain subject to DA-23.

RPC acknowledgement does not imply adapter execution.

A request rejected before adapter-mediated work exists does not produce adapter
execution failure unless DA-23 classifies that relationship explicitly.

Adapter lifecycle semantics remain owned by DA-23.

RuntimeHost entry surfaces and command surfaces may use RPC to communicate with
Kernel-mediated runtime paths.

RPC use by a RuntimeHost entry surface does not make RPC the RuntimeHost
authority owner.

RuntimeHost entry-surface, command-surface, startup-mode, workspace ownership,
and host lifecycle semantics remain owned by DA-28.

RuntimeHost control-surface routing does not grant workspace ownership, command
acceptance, AppInstance creation, or LAN exposure by itself.

A request rejected before RuntimeHost command acceptance does not produce
RuntimeHost operation completion or failure unless DA-28 classifies that
relationship explicitly.


PRESERVATION RULE 7: SUBSCRIPTION DELIVERY IS NOT DOMAIN TRUTH
==============================================================

Preserve emit/subscribe/update boundaries.

Subscription delivery may carry:

    - state updates
    - event updates
    - Job progress
    - adapter lifecycle updates
    - RuntimeHost operation updates
    - other operation-defined update material

But subscription delivery does not by itself define:

    - Job lifecycle state
    - adapter lifecycle state
    - RuntimeHost lifecycle
    - RuntimeHost command outcome
    - committed-state truth

If subscription delivery reports Job progress or terminal outcome, the reported
Job meaning remains owned by DA-19.

If subscription delivery reports adapter lifecycle state, the reported adapter
meaning remains owned by DA-23.

If subscription delivery reports RuntimeHost lifecycle or operation state, the
reported RuntimeHost meaning remains owned by DA-28.

Unsubscribe withdraws interest in future subscription delivery.

Unsubscribe does not by itself cancel the underlying work unless the operation
contract or policy explicitly connects unsubscribe to cancellation.


PRESERVATION RULE 8: TRANSPORT TIMEOUT, DISCONNECT, AND CANCELLATION ARE NOT DOMAIN OUTCOMES
===========================================================================================

Preserve timeout/disconnect/cancellation separation.

Transport timeout is an RPC, channel, or transport concern.

Job timeout is a Job lifecycle concern.

Adapter timeout, if defined, is an adapter lifecycle concern.

RuntimeHost timeout, if defined, is a RuntimeHost lifecycle or operation
concern.

Transport timeout does not automatically:

    - transition a Job to TimedOut
    - fail an adapter instance
    - fail a RuntimeHost

Transport disconnect does not automatically:

    - cancel a Job
    - supersede a Job
    - discard a Job result
    - close or fail an ExecutionAdapter
    - stop, fail, or close a RuntimeHost

If accepted or in-flight work exists when transport disconnect occurs, policy
may decide whether work continues, cancels, supersedes, detaches, retains
result, or discards result.

DA-17 owns decision and policy handling.

DA-19 owns Job terminal outcomes when a policy outcome affects a Job.

DA-23 owns adapter lifecycle outcomes when a policy outcome affects adapter
execution.

DA-28 owns RuntimeHost lifecycle or host-operation outcomes when a policy
outcome affects RuntimeHost behavior.

RPC cancellation messages are requests.

RPC cancellation messages do not directly kill arbitrary execution.


PRESERVATION RULE 9: RPCCHANNEL IS TRANSPORT-NEUTRAL
====================================================

Preserve RPCChannel contract.

RPCChannel is the abstract communication surface used by the RPC host or
equivalent runtime owner.

RPCChannel does not define:

    - message schema
    - WebSocket behavior
    - Job semantics
    - adapter lifecycle semantics
    - RuntimeHost lifecycle or command-surface semantics

Concrete channel implementations adapt concrete transports into this abstract
interface.

A channel implementation preserves peer identity and connection context when
the transport provides them.

A channel implementation reports loss of connection explicitly.

A channel implementation does not silently transform disconnect into:

    - work cancellation
    - adapter failure
    - RuntimeHost stop, failure, or command cancellation


PRESERVATION RULE 10: RPC TRACE OWNERSHIP STAYS DOMAIN-SPECIFIC
===============================================================

Preserve RPC-domain trace ownership.

DA-21 owns RPC-domain trace and observability obligations.

DA-03 owns the trace substrate.

RPC observability does not replace trace evidence owned by capability,
decision, Job, debugger, AppInstance, adapter, RuntimeHost, or Window documents.

RPC observability preserves causal links between RPC messages and higher-domain
events when those events exist.

Trace wording should follow the DA-03 cross-document trace wording check.


PRESERVATION RULE 11: DA / IS SPLIT
===================================

Preserve the DA / IS authority split.

DA-21 owns DA-level RPC semantics.

IS-01 defines concrete RPC message envelope schema.

IS-02 defines concrete WebSocket RPC flow.

IS documents may define:

    - concrete field names
    - JSON representation
    - WebSocket frame flow
    - handshake sequence
    - serialization checks
    - concrete transport reason identifiers
    - concrete adapter metadata fields when constrained by DA-23
    - concrete RuntimeHost metadata fields when constrained by DA-28

IS documents do not redefine:

    - RPC as a logical boundary
    - channel and transport separation
    - capability authority
    - adapter authority
    - RuntimeHost authority boundaries
    - Job lifecycle
    - decision and policy semantics

If an IS document needs a semantic rule not defined here, DA-21 is updated first
or alongside the IS document.


REWRITE-BOUNDARY GUARDRAILS, NOT SUGGESTED DA-21 CONTENT
=========================================================

This section is not suggested DA-21 wording.

It exists to prevent architectural drift during rewrite when the editor knows
DA-21 but may not have every subject-owning document loaded.

Use these as guardrails only.

RPC-boundary guardrails:

    RPC is a logical communication boundary, not a transport.

    RPCChannel is transport-neutral.

    Transport is the concrete carrier.

    WebSocket is one concrete transport.

    JSON is one concrete envelope/schema representation.

    Message delivery is not work completion.

    Acknowledgement is not request success.

    Request acceptance is not final success.

    RPC request is not Job.

    RPC request identity is not jobId.

    RPC routing is not permission.

    RPC routing is not activation.

    RPC routing is not adapter authorization.

    RPC routing is not RuntimeHost authority.

    Capability-routed RPC remains capability-mediated.

    Adapter-facing RPC remains subject to ExecutionAdapter boundaries.

    RuntimeHost control-surface RPC remains subject to RuntimeHost boundaries.

    Subscription delivery is not domain truth.

    Unsubscribe is not automatic cancellation.

    Transport timeout is not Job timeout.

    Transport disconnect is not Job cancellation.

    RPC cancellation message is a request, not arbitrary execution kill.

    RPC observability is not committed-state authority.

    RPC observability does not replace capability, decision, Job, adapter,
    RuntimeHost, debugger, AppInstance, Window, or PackManager trace evidence.

Owning-document boundaries:

    DA-03 owns trace event structure, trace DAG semantics, span mechanics,
    trace storage, trace retention, and trace loss semantics.

    DA-16 owns capability permission semantics and capability-domain trace
    reasons.

    DA-17 owns user decision, remembered policy, and policy handling for
    disconnect/cancellation choices where applicable.

    DA-19 owns Job lifecycle, Job terminal outcomes, Job timeout, Job result,
    and Job-domain trace reasons.

    DA-20 owns AppInstance lifecycle and runtime identity semantics.

    DA-22 owns frontend UI layout and presentation behavior.

    DA-23 owns execution adapter boundary semantics and adapter-domain trace
    reasons.

    DA-28 owns RuntimeHost identity, workspace ownership, startup modes, entry
    surfaces, command-surface semantics, and RuntimeHost-domain trace reasons.

    IS-01 owns concrete RPC envelope fields.

    IS-02 owns concrete WebSocket handshake and frame flow.

Local rewrite rule:

    DA-21 may name these concepts when needed to protect RPC/channel/transport
    boundaries.

    DA-21 should not define their detailed behavior.

    DA-21 should remain the abstract RPC, RPCChannel, transport, routing, and
    message-flow semantics document.


WATCH ITEMS
===========

Concrete RPC envelope watch:

    IS-01 should preserve DA-21 logical RPC semantics while defining concrete
    envelope fields.

    IS-01 must not make concrete envelope fields redefine request acceptance,
    Job lifecycle, capability authority, adapter authority, RuntimeHost
    authority, or committed-state truth.

Concrete WebSocket flow watch:

    IS-02 should preserve DA-21 transport/RPC separation while defining concrete
    WebSocket flow.

    IS-02 must not make WebSocket connection, acknowledgement, timeout,
    disconnect, reconnect, or frame delivery redefine Job, adapter, RuntimeHost,
    capability, or committed-state semantics.

Policy watch:

    DA-17 should preserve policy handling for disconnect, cancellation, and
    remembered decisions.

    Policy may classify what happens after disconnect or cancellation request,
    but transport events must not silently become domain outcomes.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-21.

No heavy rewrite is recommended.

Required small cleanup:

    Clarify that trace-visible RPC flow means RPC-domain trace emission
    obligation where applicable, while trace retention/loss remains governed by
    DA-03.

Preserve:

    - RPC as logical boundary, not transport
    - acknowledgement is not outcome
    - routing is not authority
    - request acceptance is not final success
    - RPC request is not Job
    - RPC does not bypass Capability, ExecutionAdapter, or RuntimeHost ownership
    - subscription delivery is not domain truth
    - transport timeout, disconnect, and cancellation are not domain outcomes
    - RPCChannel is transport-neutral
    - RPC trace ownership is domain-specific
    - DA / IS authority split

Do not expand DA-21 into detailed concrete JSON envelope fields, WebSocket frame
flow, trace substrate, capability permission, user-decision policy, Job
lifecycle, AppInstance lifecycle, ExecutionAdapter lifecycle, frontend UI,
RuntimeHost command-surface, or concrete transport implementation semantics.
