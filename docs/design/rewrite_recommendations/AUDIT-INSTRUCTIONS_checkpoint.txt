==============================================================================
TURNIX DV3 DOCUMENTATION AUDIT INSTRUCTIONS CHECKPOINT
==============================================================================

Document status:
    Rehydration checkpoint for the Turnix Dv3 documentation audit.

Purpose:
    Keep the audit focused across multiple assistant turns.

    This file describes how to audit one design document at a time, how to use
    anchor/proposal material, how to decide whether a Codex rewrite or rewrite
    recommendation has merit, and how to write an audit result file that later
    assistant editors can use without losing important semantic findings.

Repository / branch context:
    Repository:
        EnterTheNameHere/Turnix

    Audit branch:
        CODEX_Dv3

    Important branch note:
        CODEX_Dv3 is a documentation-only working branch. Large non-documentation
        deletions on this branch are expected branch-shaping noise and are not
        themselves evidence that Codex damaged the project.

        Do not merge CODEX_Dv3 directly into main.

        Treat CODEX_Dv3 as a source branch for audited documentation material.
        Accepted documentation changes should later be applied onto a clean
        branch from main so code and non-documentation files are left untouched.

==============================================================================
01. AUDIT ROLE
==============================================================================

The assistant is acting as a semantic architecture reviewer.

The assistant is not acting as:

    - a formatting linter
    - a CMR compliance checker
    - a prose beautifier
    - an automatic merge assistant
    - a code reviewer for implementation files

The audit should answer:

    - Can this document be misunderstood?
    - Did the rewrite preserve the intended Dv3 architecture?
    - Did Codex flatten an important boundary?
    - Did Codex turn a working idea into a false locked rule?
    - Did Codex remove an important warning or stop-line?
    - Did Codex over-integrate proposal text into the wrong document?
    - Did Codex reintroduce old Session/View/Pipeline meanings?
    - Did Codex create contradictions with the anchor/proposal source stack?
    - Did Codex invent implementation details that should remain open?
    - Did Codex omit something needed to prevent future misinterpretation?

The audit should not spend time on ordinary heading style, line wrapping, index
formatting, or other CMR-style formatting issues unless the formatting itself
creates a semantic ambiguity.

Project style reminder:
    Turnix documentation deliberately does not use RFC keyword machinery such as
    MUST, MUST NOT, MAY, SHOULD, or SHOULD NOT as normative keywords.

    Use rule-like prose instead.

==============================================================================
02. PRIMARY SOURCE STACK
==============================================================================

For the Dv3 rewrite audit, use this source stack:

    1. docs/design/rewrite_recommendations/ANCHOR-06_checkpoint.txt

       Role:
           Base architecture map for the audited Dv3 state before the later
           standalone proposals were applied.

    2. docs/design/rewrite_recommendations/PROPOSAL-P01_TURNIX_PACK_ENTRY_MULTI_ADAPTER_AND_CYCLIC_ACTIVATION_PROTOCOL.txt

       Role:
           Update source for Pack activation entries, multi-adapter activation,
           lifecycle phase barriers, and cyclic dependency activation.

    3. docs/design/rewrite_recommendations/PROPOSAL-P02_TURNIX_STANDALONE_RUNTIME_PLATFORM_MODEL.txt

       Role:
           Update source for the current standalone platform model, including
           TurnixRuntime, Kernel, RuntimeHost, Workspace, Application,
           ApplicationRun, SaveBundle, ExecutionAdapter, ModCallContext,
           OrchestrationUnit, Job, Transaction, ProcessingPipeline,
           ProcessingRun, Capability, Hook, Event, Timer, View, resources,
           mediated I/O, trace, and Session removal.

    4. The target DA document being audited.

    5. The matching rewrite recommendation file, if one exists.

       Pattern:
           docs/design/rewrite_recommendations/REWRITE-DA-XX_RECOMMENDATION.txt

       Exception:
           Newly-created DA documents may have no matching recommendation file.
           In that case, audit the candidate DA document directly.

The proposal files update the checkpoint. Do not treat the checkpoint as the
latest source when a proposal intentionally supersedes it.

Use the target DA document's own role and stop-lines to decide what belongs
inside that DA and what belongs elsewhere.

==============================================================================
03. SECONDARY SOURCES
==============================================================================

CMR files:
    CMR files are formatting, index, and canonical-document-management material.

    Do not use CMR files as semantic architecture authority for DA audit results.

    CMR-04 may be read only as an index to locate document identifiers and
    filenames when needed.

DD doctrine files:
    Do not use DD doctrine files as primary audit sources by default.

    Read a DD file only if the target DA document appears to alter or weaken a
    doctrine-level invariant.

    Examples of doctrine-level issues that may justify reading a DD file:

        - Turnix is not a security product.
        - Implementation is not the architecture.
        - If not traced, did not happen.
        - Capabilities are mediated operations, not magical trust.
        - Pack code is mediated, not trusted backend code.
        - Runtime authority and Pack-facing authority are separate.

    If a DD file is consulted, use it as semantic doctrine context, not as
    formatting law.

Code files:
    Do not read code files for the rewrite audit unless the user explicitly asks
    for implementation alignment.

    The purpose of the CODEX_Dv3 branch was to keep Codex focused on
    documentation truth rather than current implementation structure.

==============================================================================
04. PER-DOCUMENT AUDIT PROCEDURE
==============================================================================

For each DA file:

    1. Identify the target document.

       Example:
           docs/design/DA-30_MODCALLCONTEXT_INVOCATION_GATEWAY_SEMANTICS.txt

    2. Identify the expected recommendation file.

       Example:
           docs/design/rewrite_recommendations/REWRITE-DA-30_RECOMMENDATION.txt

       If the file does not exist and the DA is known to be newly created, note
       that absence as expected.

    3. Read the target DA file on CODEX_Dv3.

    4. Read the matching recommendation file if it exists.

    5. Read only the relevant parts of ANCHOR-06 and proposals.

       Avoid rereading entire long source files unless needed.

    6. Decide whether the recommendation has merit.

       Possible recommendation verdicts:

           yes
           partial
           no
           not applicable because the DA is newly created

    7. Decide whether the target DA rewrite has merit.

       Possible document verdicts:

           keep
           keep with small fixes
           keep with rewrite/expansion
           rewrite substantially
           reject

    8. Identify semantic risks.

       Focus on ambiguity, drift, contradiction, missing stop-lines, missing
       authority boundaries, false locking of open design, accidental old model
       language, and misleading implications.

    9. Identify concrete fixes.

       Concrete fixes may include:

           - replace one dangerous phrase
           - add a missing stop-line
           - add a missing explicit absence
           - split concepts that were merged
           - restore a warning
           - move material to another DA
           - remove premature implementation detail
           - expand an under-specified boundary

    10. Decide whether to write a corrected replacement DA text now.

        If the user asks only for audit, write the audit result file first.

        If the user asks for the DA rewrite, produce the revised DA file after
        the audit result is agreed or after the audit result gives clear rewrite
        instructions.

==============================================================================
05. AUDIT RESULT FILE
==============================================================================

For each audited DA document, create an audit result file in:

    docs/design/rewrite_recommendations/

Filename pattern:

    AUDIT-DA-XX_RESULT.txt

Example:

    docs/design/rewrite_recommendations/AUDIT-DA-30_RESULT.txt

The audit result file is not the rewritten DA file.

The audit result file is an instruction file for a later assistant editor or
human editor. It should preserve all semantic findings, not just a short chat
summary.

The audit result file should include:

    - document title
    - target DA path
    - source stack used
    - whether a recommendation file exists
    - recommendation verdict, if applicable
    - DA document verdict
    - what the document gets right
    - major semantic risks
    - required fixes
    - suggested rewrite structure, when useful
    - required content by section, when useful
    - specific phrase replacements, when useful
    - acceptance conditions for the final rewritten DA
    - final editor instruction
    - end marker
    - doc-meta block

Do not drop audit details merely because they were already explained in chat.

The audit file should be self-contained enough that a later assistant can read
it and understand what to do without relying on chat memory.

==============================================================================
06. AUDIT RESULT FILE CREATION PROCEDURE
==============================================================================

Before writing:

    1. Check whether the intended AUDIT-DA-XX_RESULT.txt file already exists on
       CODEX_Dv3.

    2. If it does not exist, create it.

    3. If it exists, ask the user whether to update it unless the user already
       explicitly asked to replace/update it.

When writing:

    - Write complete UTF-8 text.
    - Keep the audit file in plain text.
    - Include a clear END marker near the end.
    - Include doc-meta after the END marker.
    - Do not rely on a short summary if the audit contained many separate
      findings.

After writing:

    1. Fetch the file back from CODEX_Dv3.

    2. Fetch enough line ranges to cover the full file.

    3. Confirm that the fetched content includes:

        - the first title/header
        - all major sections expected from the audit
        - the acceptance conditions or equivalent final checklist
        - the final editor instruction
        - the END marker
        - the doc-meta block

    4. Be careful when reporting line numbers from fetched chunks.

       GitHub connector fetches may display chunk-local line numbers that restart
       from 1 in each response. Do not present chunk-local line numbers as if
       they were absolute repository-file line numbers.

    5. If truncation is suspected, fetch later ranges and verify the actual file
       reaches its END marker.

    6. If the file is truncated or missing major sections, update the file with
       full content and fetch it again.

==============================================================================
07. AUDIT OUTPUT IN CHAT
==============================================================================

After each audit file is created and verified, report briefly:

    - file path
    - branch
    - commit SHA returned by GitHub
    - whether the fetched-back file reached the END marker
    - whether all expected audit sections were present

Do not paste the whole audit file into chat unless the user asks.

If a line-number statement is needed, say whether the line numbers are absolute
file lines or local fetched-chunk display lines.

08. COMMON DRIFT RISKS TO WATCH
==============================================================================

Watch for these recurrent Dv3 documentation drift patterns:

    Session reintroduction:
        Any required Session, MainSession, HiddenSession, TemporarySession,
        SessionRegistry, ctx.sessions, Session-owned ProcessingPipeline,
        View-owned Session, Session-based RPC routing, or mandatory Session for
        processor/LLM calls is suspect.

    View authority inflation:
        View is presentation and interaction surface. It does not own Session,
        Pipeline, Memory, processor execution, application identity, RPC
        authority, or persistence root.

    Pipeline terminology drift:
        ProcessingPipeline is the reusable staged procedure. ProcessingRun is
        one execution with temporary working state. Avoid old Pipeline/PipelineRun
        conflation.

    AppPack/Application/SaveBundle confusion:
        AppPack is reusable application definition. Application is a durable
        application individual. ApplicationRun is one live runtime incarnation.
        SaveBundle is durable persistence closure and is not a Pack.

    Workspace confusion:
        Workspace is a managed set of role-based roots and storage scopes used
        by one TurnixRuntime. It is not Application identity, SaveBundle identity,
        View identity, Pack identity, or RuntimeHost identity.

    Runtime authority inflation:
        Kernel and runtime services own authority. Pack-facing code gets mediated
        gateway operations through ModCallContext and related facades.

    ModCallContext backdoors:
        Watch for ctx.kernel, ctx.runtimeHost, ctx.services, ctx.journal,
        ctx.rawFilesystem, ctx.transaction.commit, ctx.job.setTerminalState, and
        ctx.sessions.

    Capability/service confusion:
        Capabilities are explicit semantic operation interfaces. Service objects
        remain internal runtime wiring.

    Event/hook/lifecycle confusion:
        Lifecycle callbacks are lifecycle protocol. Hooks are controlled
        ProcessingRun participation. Events are cheap semantic notifications.
        Do not use Event when producer needs listener output to shape result.

    Timer retained-context confusion:
        Timer registrations retain owner/callback/schedule/policy metadata, not
        old ModCallContexts. Timer firing creates fresh orchestrated work and a
        fresh context.

    Trace/state confusion:
        Trace is evidence and diagnostics. Trace is not committed-state
        authority.

    I/O escape hatch:
        Pack code should not receive unrestricted raw filesystem access. Use
        mediated resources and scoped I/O. Direct SaveBundle-directory mutation
        should not be exposed.

    Proposal over-integration:
        Do not dump all proposal text into every DA. Integrate only what belongs
        in the target DA's responsibility and preserve stop-lines.

    False finalization:
        Do not lock open implementation details as final architecture. Mark open
        issues where exact API shapes, schemas, or adapter-specific mechanisms
        remain future work.

==============================================================================
09. BRANCH AND INTEGRATION DISCIPLINE
==============================================================================

CODEX_Dv3 should remain an audit and candidate-document branch.

Do not treat it as directly mergeable into main.

For final integration later:

    - create a clean integration branch from main
    - apply accepted documentation changes only
    - leave code and non-documentation files untouched
    - preserve deliberate non-code repository contents from main unless the user
      explicitly chooses otherwise

When using GitHub compare output, ignore intentional non-documentation deletions
unless the user asks to analyze branch-shaping damage.

==============================================================================

    We are auditing Turnix Dv3 documentation rewrites on CODEX_Dv3.

    We read one DA document at a time.
