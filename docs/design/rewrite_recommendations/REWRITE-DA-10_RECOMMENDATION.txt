SUMMARY
=======

DA-10 is strong and highly Dv3-compatible.

No heavy rewrite is recommended.

DA-10 defines how Turnix identifies packs, how pack hierarchy is formed, and how
visibility is computed without conflating visibility with resolution,
activation, import authority, capability authority, or permission.

DA-10 should preserve these core boundaries:

    Pack is the general container concept.

    AppPack, ModPack, ViewPack, ContentPack, and SavePack are specific pack kinds
    within that broader container model.

    Pack hierarchy is structural containment, not runtime activation order.

    Identity answers what a pack is, where it sits in hierarchy, which author
    scope it belongs to, and which version identity applies.

    Visibility answers whether one pack is eligible to be seen from another
    context.

    Visibility does not decide resolution winner, activation order, capability
    authority, or permission grant.

Main watch item:

    Preserve SavePack-local visibility.

    Packs copied into a SavePack do not leak into global visibility merely
    because they exist inside that SavePack.

    Save-local copied packs may override external candidates within that
    SavePack context.

    Exact internal visibility rules inside one SavePack should be resolved with
    SavePack/AppInstance and selected-graph documents.

Rewrite-boundary guardrails:

    DA-10 owns pack identity, hierarchy, visibility declarations, computed
    visibility, parent-import visibility, capability/visibility separation, and
    save-local visibility constraints.

    DA-10 should not absorb detailed root discovery, resolution winner/source
    selection, activation lifecycle, importing/module loading authority,
    capability schema, permission prompts, enforcement mechanics, PackManager
    UI, PackManager repair, SavePack runtime behavior, AppInstance lifecycle, or
    broader pack addressing syntax.

    Those details belong to their subject-owning documents.

Overall recommendation:

    KEEP WITH SAVEPACK VISIBILITY WATCH

PRESERVATION RULE 1: PACK IS THE GENERAL CONTAINER CONCEPT
==========================================================

Preserve Pack as the general container concept in Turnix.

Specific pack kinds include:

    - AppPack
    - ModPack
    - ViewPack
    - ContentPack
    - SavePack

Specific pack kinds are uses of the broader pack container model.

This preserves the Dv3 distinction:

    Packs are first-class.

    Packs are not the whole identity of Turnix.

    Pack kinds are specific uses of the broader pack model.


PRESERVATION RULE 2: PACK IDENTITY LAYERS STAY DISTINCT
=======================================================

Preserve DA-10's identity-layer split.

DA-10 defines distinct identity layers and says they are not conflated.

The main layers are:

    - declaredId
    - packTreeId
    - author
    - version

declaredId is local to its parent pack context.

declaredId is not globally unique.

packTreeId is computed from hierarchy.

packTreeId is not filesystem-based.

packTreeId is unique only within relevant author and version scope.

author is part of identity rather than decoration.

If author cannot be resolved through declaration or inheritance, the pack is
invalid.

Author resolution failure is explicit and is not repaired through silent
substitution.

This prevents identity from becoming filesystem location, display name, or
best-effort guesswork.


PRESERVATION RULE 3: VERSION IDENTITY IS IDENTITY INPUT, NOT COMPATIBILITY MAGIC
================================================================================

Preserve version identity rules.

DA-10 says:

    declaredVersion is the raw manifest version value or None.

    version is parsed version identity used by later resolution.

    Parsing occurs after discovery.

    Invalid version syntax causes pack rejection.

Version inheritance rules are:

    - if version is missing, inherit from parent
    - if a root pack has no version, use engine-defined default behavior

Version affects pack identity and later resolution compatibility.

Watch item:

    DA-11 / resolution rules should ensure inherited/default root versions do
    not become hidden compatibility magic.


PRESERVATION RULE 4: HIERARCHY AND CONTAINMENT DO NOT GRANT AUTHORITY
=====================================================================

Preserve hierarchy as structural containment.

A child pack belongs to the pack tree of its parent.

Parent-child hierarchy contributes to packTreeId construction.

Parent-child hierarchy does not by itself grant:

    - visibility
    - capability authority
    - activation
    - permission
    - runtime execution order

This prevents the bad model:

    child is inside parent, therefore child can do whatever parent can do

Hierarchy is structural first.

Later areas define runtime behavior over that structure.


PRESERVATION RULE 5: VISIBILITY IS ELIGIBILITY TO BE SEEN
=========================================================

Preserve DA-10's visibility model.

Visibility is eligibility to be seen from another pack context.

Visibility is not the same as:

    - dependency declaration
    - import use
    - activation order
    - capability authority
    - permission grant

Local visibility values are:

    - public
    - private

Current default local visibility is:

    - ContentPack -> public
    - AppPack -> private
    - ViewPack -> private
    - ModPack -> private
    - SavePack -> private

Local visibility is only one input to broader visibility outcome.

This conservative default model should remain unless another authoritative
document explicitly changes it.


PRESERVATION RULE 6: EXPORTNESTEDPACKS CONTROLS DIRECT CHILD EXPORT ONLY
========================================================================

Preserve exportNestedPacks semantics.

exportNestedPacks controls whether direct children become externally visible
beyond the local parent context.

Allowed forms:

    - false
    - true
    - list of declaredId values

Semantics:

    - false -> no direct children exported
    - true  -> all direct children exported
    - list  -> only listed direct children exported

List entries are direct-child declaredId values only.

Dotted hierarchical ids are not valid inside exportNestedPacks.

exportNestedPacks applies only to direct children.

This avoids ambiguous deep export semantics.


PRESERVATION RULE 7: COMPUTED GLOBAL VISIBILITY IS NOT RESOLUTION
=================================================================

Preserve computed global visibility semantics.

DA-10 defines computed visibility after hierarchy is known.

For a root pack:

    globalVisibility = visibility

For a non-root pack:

    if visibility is private:
        globalVisibility = private

    else if parent.exportNestedPacks is false:
        globalVisibility = private

    else if parent.exportNestedPacks is true:
        globalVisibility = public

    else if parent.exportNestedPacks is a list:
        globalVisibility = public if declaredId is listed
                           else private

Computed visibility is static relative to the discovered/indexed pack tree.

Computed visibility is not a runtime resolution outcome.


PRESERVATION RULE 8: IMPORTPACKSFROMPARENT IS IMPORT-VISIBILITY, NOT AUTHORITY
==============================================================================

Preserve importPacksFromParent semantics.

importPacksFromParent controls which parent-context packs are import-visible to
a child pack.

importPacksFromParent does not imply:

    - export
    - capability inheritance
    - permission inheritance
    - native import authority
    - activation authority

Allowed forms:

    - false
    - true
    - list of declaredId values or relative packTreeId fragments

Semantics:

    - false -> no parent-context packs imported
    - true  -> all visible parent-context packs imported
    - list  -> explicit whitelist

Resolution of listed entries is relative to the immediate parent context and
remains subject to visibility rules.

Current defaults:

    - ViewPack -> false
    - all other pack kinds -> true

Rationale:

    - views do not automatically inherit parent UI mods
    - view isolation is preserved
    - unintended UI contamination is reduced

Watch item:

    DA-12 / importing rules should ensure importPacksFromParent does not become
    native import authority or capability permission.


PRESERVATION RULE 9: VISIBILITY IS NOT RESOLUTION
=================================================

Preserve visibility / resolution separation.

Visibility is static and computed from structure plus visibility declarations.

Resolution is contextual.

A pack may exist but be invisible.

A visible pack may still fail resolution.

Visibility is not dependency satisfaction.

DA-10 defines eligibility to be seen, not selection of a winner.

Correct pipeline:

    DA-09 discovery finds candidates.

    DA-10 identity / visibility computes identity and eligibility to be seen.

    DA-11 resolution selects candidates contextually.

Visibility must remain an input to resolution, not resolution itself.


PRESERVATION RULE 10: CAPABILITIES ARE NOT VISIBILITY
=====================================================

Preserve capability / visibility separation.

Capability exports are not inherited through visibility alone.

Capability imports remain explicit.

Parent visibility does not grant capability authority.

Capabilities are behavioral power and remain governed by capability and
permission documents.

This separation prevents accidental privilege escalation through structural
visibility alone.


PRESERVATION RULE 11: SAVEPACK VISIBILITY STAYS SAVE-LOCAL
==========================================================

Preserve SavePack visibility boundaries.

SavePack visibility remains save-local.

Packs copied into a SavePack do not leak into global visibility merely because
they exist inside that SavePack.

Save-local copied packs may override external candidates within that SavePack
context.

Open questions remain:

    - exact internal visibility rules inside one SavePack
    - interaction with exportNestedPacks inside SavePack context
    - tooling and UI representation of SavePack-local visibility graphs

Recommendation:

    Keep DA-10 as-is for now.

    Resolve SavePack internal visibility later with SavePack/AppInstance and
    selected-graph documents.

    Do not let SavePack-local copied packs become globally visible.

    Do not let global custom precedence override save-local copied material by
    default.

    Do not let PackManager UI display of SavePack-local visibility grant global
    visibility or runtime authority.

SOURCE BOUNDARY STATEMENT: VISIBILITY IS ELIGIBILITY, NOT AUTHORITY
===================================================================

DA-10 may state the source-level boundary:

    Pack identity defines what a pack is, where it sits in hierarchy, which
    author scope it belongs to, and which version identity applies.

    Visibility defines whether one pack is eligible to be seen from another
    pack context.

    Visibility does not decide resolution winner, activation order, dependency
    satisfaction, native import authority, capability authority, permission
    grant, runtime execution order, or SavePack global visibility.

    Hierarchy and containment do not grant authority by themselves.

    SavePack-local copied packs remain SavePack-context-local unless another
    authoritative document explicitly states otherwise.

This source-level boundary is useful because DA-10 owns pack identity,
hierarchy, and visibility semantics.

The detailed ownership map belongs in the guardrail section below.

Pack identity / visibility guardrails:

    Pack is the general container concept, not Turnix identity.

    Pack hierarchy is structural containment, not activation order.

    declaredId is local, not globally unique.

    packTreeId is computed from hierarchy, not filesystem path.

    author is identity, not decoration.

    author resolution failure is explicit and is not silently repaired.

    version identity affects later resolution compatibility, but DA-10 does not
    own resolution winner selection.

    visibility is eligibility to be seen, not resolution.

    visibility is not dependency satisfaction.

    visibility is not import execution.

    visibility is not activation.

    visibility is not capability authority.

    visibility is not permission grant.

    visibility is not runtime execution order.

    computed global visibility is not runtime-loaded state.

    importPacksFromParent is import-visibility, not capability inheritance.

    exportNestedPacks controls direct child export only.

    SavePack visibility is save-local.

    SavePack-local copied packs do not leak into global visibility merely
    because they exist inside a SavePack.

    Global custom precedence does not override SavePack-local copied material by
    default.

    PackManager UI display of SavePack-local visibility does not grant global
    visibility or runtime authority.

Owning-document boundaries:

    DA-09 owns root discovery boundaries and discovered candidate production.

    DA-11 owns resolution winner selection, source selection, selector
    resolution, and deterministic resolution semantics.

    DA-12 owns importing, module loading, and native/runtime import authority.

    DA-13 owns dependency semantics and advisory relation semantics.

    DA-14 owns activation order and runtime lifecycle.

    DA-16 owns capability schema, permission prompts, enforcement mechanics, and
    capability authority.

    DA-20 owns AppInstance lifecycle and runtime identity semantics.

    DA-21 owns RPC, channel, and transport semantics.

    DA-23 owns execution adapter boundary semantics.

    DA-24 owns OrchestrationUnit and mutation-authority semantics.

    DA-28 owns RuntimeHost workspace ownership and command-surface semantics.

    DA-29 owns PackManager inspection, UI presentation, graph preparation,
    repair, and PackManager-domain trace semantics.

Local rewrite rule:

    DA-10 may name these concepts when needed to protect pack identity,
    hierarchy, and visibility boundaries.

    DA-10 should not define their detailed behavior.

    DA-10 should remain the pack identity, hierarchy, visibility, parent-import
    visibility, capability/visibility separation, and SavePack-local visibility

WATCH ITEMS

    Do not let SavePack-local visibility leak globally.

Import visibility watch:

    DA-12 should preserve importPacksFromParent as import-visibility.

    It must not become native import authority or capability permission.

Resolution watch:

    DA-11 should preserve visibility as eligibility-to-be-seen.

    It must not become winner selection.

Capability watch:

Numbering watch:
