==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. Correct implementation-specification scope.

    IS-10 correctly defines the default launcher runtime flow without defining
    root discovery, pack identity, PackRequest resolution, import/module loading,
    dependency semantics, activation semantics, service/capability execution,
    policy, Job lifecycle, RPC, UI/frontend runtime, adapter authority,
    RuntimeHost lifecycle, PackManager semantics, concrete ListPacks envelopes,
    browser component layout, CSS, JavaScript module syntax, CLI syntax, JSON-RPC
    envelope fields, or WebSocket envelope fields.

2. Strong launcher non-authority invariant.

    The document repeatedly says Turnix Default Launcher is not Kernel,
    RuntimeHost, PackManager, a pack catalog, or a manager for user persistence by
    itself.

    Launcher UI is presentation and interaction. Launcher actions request
    RuntimeHost, PackManager, catalog, settings, lifecycle, or persistence
    operations through mediated Turnix boundaries.

3. Good replaceable launcher boundary.

    The default launcher is replaceable by configuration, policy, or later
    launcher-selection rules. Replacement changes which AppPack is requested for
    launcher startup, but does not redefine RuntimeHost, catalog, PackManager,
    persistence, application lifecycle, or activation semantics.

    Replacement launcher status grants no extra authority.

4. Good explicit fallback boundary.

    If the launcher AppPack cannot be resolved, startup fails unless an explicit
    fallback launcher or recovery policy is defined and accepted. Silent fallback
    to another launcher is not supported.

5. Good View/presentation boundary.

    Launcher Main Menu labels are user-facing presentation labels. They do not
    define authority by themselves and do not mutate state by being displayed.

    User interaction becomes meaningful only when Turnix accepts the corresponding
    command, capability request, RPC message, decision, or RuntimeHost operation.

6. Good ToolStateContext placement intent.

    ToolStateContext is not stored under the launcher AppPack content directory,
    not stored under first-party/third-party/custom content roots as pack content,
    and not stored under normal saves by default.

    Persistent ToolStateContext belongs under userdata. Its placement does not
    make userdata a content root and does not make the launcher AppPack writable
    by runtime execution.

7. Good temporary-state boundary.

    Temporary ToolStateContext use is explicit and trace-visible. Temporary state
    is not silently presented as persistent state, and UI may present temporary
    status when relevant to user expectations.

8. Good action delegation.

    New, Load, Settings, and Exit are launcher actions, not authority owners.

    New does not own application creation or persistence creation semantics.
    Load does not own persistence loading or migration semantics. Settings does
    not mutate configuration merely by being opened. Exit does not always mean
    RuntimeHost shutdown.

9. Good launcher / PackManager boundary.

    The launcher uses PackManager and catalog operations as a client surface. It
    does not own PackManager semantics, ListPacks semantics, graph preparation,
    package management, roots, selected graphs, persistence, configuration, or
    policy.

10. Good launcher access boundary.

    Launcher AppPack authority is ordinary AppPack authority. It does not include
    raw Kernel internals, unrestricted filesystem access, unrestricted PackManager
    operations, or unrestricted persistence mutation. Replacement launchers follow
    the same rules.

11. Good exit/shutdown separation.

    Exit can close launcher interaction, stop the launcher run, or request
    RuntimeHost shutdown only according to the active startup workflow, accepted
    command, or policy. Presentation labels such as Close Launcher and Quit
    Turnix do not collapse those meanings.

12. Good open-question discipline.

    The document leaves concrete launcher identity, manifest declaration shape,
    ToolStateContext schema, ToolStateContext identity, path encoding, launcher
    View layout, frontend component structure, settings envelopes, launcher action
    identifiers, bounded startup policy, multi-run coexistence policy,
    PackManager View embedding, and launcher trace fields open.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. AppInstance terminology is superseded by Application / ApplicationRun.

    IS-10 uses AppInstance throughout:

        - launcher AppInstance creation
        - launcher runs as an AppInstance
        - launcher AppInstance identity
        - user AppInstance
        - AppInstance creation semantics
        - AppInstance lifecycle/runtime identity semantics
        - AppInstance-domain trace reasons
        - multi-AppInstance coexistence
        - active AppInstances
        - launcher appInstanceId

    Current source-stack correction:
        Proposal P02 defines Application as the durable application individual and
        ApplicationRun as one live execution period of an Application.

    Required consequence for IS-10:
        Translate AppInstance to Application and/or ApplicationRun according to
        meaning.

        Likely replacements:

            launcher AppInstance creation
                -> launcher ApplicationRun creation/start, if the launcher
                   Application already exists or is durable tool Application
                   identity
                -> launcher Application creation plus ApplicationRun creation, if
                   first launcher startup creates a durable launcher Application

            launcher runs as an AppInstance
                -> launcher runs as an ApplicationRun of the launcher Application

            user AppInstance
                -> user Application / user ApplicationRun according to context

            appInstanceId
                -> applicationId and/or applicationRunId

            AppInstance lifecycle outcome
                -> Application lifecycle outcome or ApplicationRun lifecycle
                   outcome; usually ApplicationRun where live launcher execution
                   is meant

2. SavePack terminology is superseded by SaveBundle.

    IS-10 uses SavePack in several places:

        - launcher not becoming SavePack authority
        - ToolStateContext is not a normal user SavePack
        - ToolStateContext not listed by ListSavePacks
        - New does not own SavePack creation
        - Load lists or loads SavePacks
        - selected SavePack identity
        - launcher-owned SavePack creation/loading semantics

    Current source-stack correction:
        Proposal P02 defines SaveBundle as durable persistence closure of an
        Application. SaveBundle is not a Pack and not authority by itself.

    Required consequence for IS-10:
        Translate SavePack to SaveBundle where the meaning is durable persistence
        closure or user save identity.

        Likely replacements:

            normal user SavePack
                -> normal user SaveBundle

            ListSavePacks
                -> ListSaveBundles or SaveBundle listing operation, aligned with
                   the final IS-09 correction

            selected SavePack identity
                -> selected SaveBundle identity

            SavePack creation/loading/migration
                -> SaveBundle creation/loading/migration

3. ToolStateContext as "save context for AppInstance lifecycle purposes" is too
   old-model and ambiguous.

    IS-10 says ToolStateContext is a save context for AppInstance lifecycle
    purposes while also saying it is not a normal user SavePack.

    Current-model risk:
        SaveBundle is the durable persistence closure of an Application, and
        ApplicationRun composes live runtime contexts including SaveBundle binding.
        Calling ToolStateContext a save context may imply it is a SaveBundle,
        a SaveBundle substitute, or a generic persistence root for a launcher
        ApplicationRun.

    Required consequence for IS-10:
        Decide and state the current relationship precisely.

        Safe direction:

            ToolStateContext is a tool-state persistence context for launcher and
            tool Applications. It is stored under userdata and mediated by Kernel
            persistence/state authority. It is not a user SaveBundle, not a Pack,
            not a content root, not a normal save, and not application committed
            state for user Applications.

        If ToolStateContext is implemented as a special SaveBundle-like durable
        closure for tool Applications, state that as a special tool-state
        persistence closure, not as a normal user SaveBundle and not as SavePack.

        If ToolStateContext is separate from SaveBundle, say so directly.

4. Launcher AppPack as replaceable entry surface must not become an authority
   elevation path.

    IS-10 already says replacement launcher status grants no authority.

    Required consequence for IS-10:
        Preserve and strengthen that configured/default launcher identity does not
        grant Kernel authority, RuntimeHost authority, PackManager authority,
        raw filesystem access, SaveBundle mutation authority, capability
        permission, policy approval, or ApplicationRun lifecycle authority beyond
        mediated operations.

5. Launcher startup flow must be recast to current lifecycle operations.

    Current flow:

        resolve configured launcher AppPack
        create or load ToolStateContext
        create Launcher AppInstance
        start Launcher AppInstance
        create launcher View
        bind frontend client

    Required current flow should use current terms:

        resolve configured launcher AppPack / accepted launcher AppDefinition
        create or load ToolStateContext
        create or locate launcher Application, if a durable launcher Application
        identity is used
        create Launcher ApplicationRun
        start Launcher ApplicationRun
        create launcher View
        bind frontend client

    Exact operation names may remain open, but the semantic model should no
    longer be AppInstance.

6. New action composition uses obsolete SavePack/AppInstance operation names.

    Current list includes:

        CreateSavePack or create save context
        ValidateSavePackCompatibility
        BindSaveContext
        CreateAppInstance
        StartAppInstance

    Required current translation:

        CreateApplication when new durable user Application is created
        CreateSaveBundle or create Application persistence closure
        ValidateSaveBundleCompatibility
        BindSaveBundle or bind Application persistence context
        CreateApplicationRun
        StartApplicationRun
        CreateView when applicable

    The final wording should follow the owning lifecycle/persistence documents
    and not invent independent launcher-owned operation semantics.

7. Load action composition uses obsolete SavePack/AppInstance operation names.

    Current list includes:

        ListPacks filtered to SavePack
        ResolveAppPack associated with selected SavePack
        LoadSavePack
        ValidateSavePackCompatibility
        BindSaveContext
        CreateAppInstance
        StartAppInstance

    Required current translation:

        ListSaveBundles or SaveBundle listing operation aligned with IS-09
        Resolve AppPack / accepted AppDefinition source associated with selected
        SaveBundle
        LoadSaveBundle
        ValidateSaveBundleCompatibility
        Check last-used / last-known-good graph evidence
        BindSaveBundle or bind Application persistence context
        CreateApplicationRun
        StartApplicationRun
        CreateView when applicable

8. Exit action needs current ApplicationRun terminology and retained-work guardrail.

    IS-10 already distinguishes launcher exit from RuntimeHost shutdown and
    active work from silent stopping.

    Required current translation:
        Replace launcher AppInstance stop with launcher ApplicationRun stop.
        Replace active AppInstances with active Applications/ApplicationRuns as
        appropriate, usually active ApplicationRuns.

        Preserve that launcher Exit does not silently stop active ApplicationRuns,
        Jobs, adapters, Views, OrchestrationUnits, or retained work.

9. Settings action should explicitly separate ToolStateContext from configuration
   and policy.

    IS-10 already says ToolStateContext does not replace configuration state owned
    by DA-06 or remembered policy decisions owned by DA-17.

    Required consequence:
        Preserve this. Also ensure launcher-local settings stored in
        ToolStateContext do not become global configuration, workspace
        configuration, SaveBundle committed state, or policy decisions unless a
        mediated accepted mutation explicitly writes to the owning domain.

10. Trace context must be updated.

    IS-10 uses launcher appInstanceId and AppInstance-domain trace reasons.

    Required current translation:
        Use launcher applicationId and/or launcher applicationRunId.
        Use Application/ApplicationRun trace reason ownership once the owning
        lifecycle trace vocabulary is updated.

        Preserve that launcher trace evidence does not replace RuntimeHost,
        Application, ApplicationRun, UI, activation, PackManager, catalog,
        decision, persistence, capability, or SaveBundle evidence.

11. ToolStateContext normal listing boundary must align with IS-09.

    IS-10 says ToolStateContext is not listed by normal ListSavePacks.

    Required current translation:
        ToolStateContext is not listed by normal ListSaveBundles or user
        SaveBundle listing. It may be listed only by explicit tooling,
        diagnostics, audit, or tool-state operations when such operations are
        defined and permitted.

12. Launcher Main Menu labels are good but should remain non-final UI design.

    The labels New, Load, Settings, Exit are useful default presentation labels.
    They should not be overread as concrete component layout, exact UX behavior,
    exact command identifiers, or fixed localization text.

    Required consequence:
        Preserve that labels are presentation labels and exact launcher View
        layout/action identifiers remain open.

    Preserve that Exit does not always mean RuntimeHost shutdown and does not

10. Update trace fields and ownership.

11. Preserve temporary-state guardrails.

    Keep temporary ToolStateContext explicit, trace-visible, not silently

12. Preserve replacement launcher guardrails.

ACCEPTANCE CONDITIONS FOR FINAL REWRITTEN IS-10
==============================================================================

Accept the rewritten IS-10 only if all of the following are true:

1. It remains an implementation specification for default launcher startup flow,
   launcher AppPack role, ToolStateContext placement, launcher actions, launcher
   use of PackManager/catalog operations, and launcher exit behavior.

2. It does not redefine root discovery, pack identity, PackRequest resolution,
   import/module loading, dependency semantics, activation lifecycle, capability
   execution, policy, Job lifecycle, Application lifecycle, ApplicationRun
   lifecycle, SaveBundle lifecycle/binding, RPC, UI/frontend runtime, adapter
   authority, RuntimeHost lifecycle, PackManager semantics, ListPacks envelopes,
   browser layout, CSS, JavaScript module syntax, CLI syntax, JSON-RPC fields, or
   WebSocket fields.

3. All AppInstance terminology has been translated to Application and/or
   ApplicationRun according to meaning.

4. All SavePack terminology has been translated to SaveBundle terminology or the
   final IS-09 save-listing term.

5. ToolStateContext ontology is explicit: it is either a tool-state persistence
   context separate from user SaveBundles or a special tool-state persistence
   closure for tool Applications. It is not left as vague generic save context.

6. ToolStateContext is not AppPack content, not a content root, not normal user
   SaveBundle state, not configuration authority, not policy authority, not
   PackManager authority, and not raw filesystem authority.

7. Persistent ToolStateContext remains under userdata and does not make userdata a
   content root or the launcher AppPack writable.

8. Temporary ToolStateContext remains explicit, trace-visible, and not silently
   presented as persistent state.

9. Default launcher and replacement launchers remain ordinary AppPacks or accepted
   launcher AppDefinition sources and receive no extra authority merely by being
   configured as launcher.

10. Launcher startup uses current Application/ApplicationRun lifecycle terms and
    does not create a user Application/ApplicationRun or user SaveBundle merely by
    opening the launcher.

11. New and Load actions request owning operations; they do not own Application,
    ApplicationRun, SaveBundle, graph, activation, PackManager, View, or
    persistence semantics.

12. Settings view opening remains presentation/read-only until an accepted
    mediated mutation occurs.

13. Exit remains distinct from RuntimeHost shutdown and does not silently stop
    active ApplicationRuns, Jobs, adapters, Views, OrchestrationUnits, retained
    work, or required entry surfaces.

14. Launcher use of PackManager and catalog operations remains client-surface use.
    It does not grant PackManager authority or ListPacks authority to the
    launcher AppPack.

15. Launcher frontend runtime does not directly mutate committed state,
    ToolStateContext, configuration, roots, packs, SaveBundles, selected graphs,
    or policy.

16. Launcher trace evidence remains evidence only and does not replace owning
    RuntimeHost, Application, ApplicationRun, UI, activation, PackManager,
    catalog, decision, persistence, capability, or SaveBundle evidence.

17. Open questions remain open unless a later authoritative source resolves them.
