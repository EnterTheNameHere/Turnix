RECOMMENDED PRESERVATION 1: JOB IS LIFECYCLE HANDLE, NOT EXECUTION PRIMITIVE
============================================================================

Preserve the definition:

    Job = observable lifecycle handle for requested work

A Job is not:

    - Promise
    - coroutine
    - callback
    - thread
    - task
    - process
    - model request
    - transport message
    - RPC request
    - capability
    - OrchestrationUnit
    - transaction
    - committed state
    - execution mechanism
    - result payload

Runtime primitives may implement Jobs, but those primitives do not define Job
lifecycle semantics.

Job identity must remain distinct from:

    - RPC request identity
    - OrchestrationUnit identity
    - underlying execution identity
    - result payload identity


RECOMMENDED PRESERVATION 2: JOB / ORCHESTRATIONUNIT / TRANSACTION TRIAD
=======================================================================

Preserve the core triad:

    Job answers:
        What requested work is waiting, running, succeeded, failed, cancelled,
        timed out, superseded, or paused?

    OrchestrationUnit answers:
        What owns or coordinates execution authority?

    Transaction answers:
        What staged mutation may become committed truth?

A Job does not become authoritative committed state merely because it exists,
runs, or reaches terminal outcome.

A Job result envelope does not become authoritative committed state merely
because the Job succeeded.

Job effects become authoritative only through the documents that own those
effects:

    - state
    - transaction
    - Window
    - capability
    - persistence

A Job terminal outcome does not automatically commit, abort, or roll back an
OrchestrationUnit.

State mutation authority remains constrained by DA-04 even when work is
represented as a Job.


RECOMMENDED PRESERVATION 3: JOB LIFECYCLE STATES STAY FINAL AND EXCLUSIVE
=========================================================================

Preserve Job lifecycle states:

    - Pending
    - Running
    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

Preserve terminal states:

    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

A Job reaches exactly one terminal state.

Terminal state is final.

Closed Jobs are not restarted.

Retry is new work unless a later document explicitly defines a retry
relationship.

Retry does not reuse the previous jobId.


RECOMMENDED PRESERVATION 4: RESULT ONLY EXISTS FOR SUCCEEDED
============================================================

Preserve the rule:

    A Job result exists only for Succeeded.

Later concrete envelope specs must not smuggle these into result:

    - partial output
    - diagnostic metadata
    - cancellation metadata
    - timeout metadata
    - supersession metadata
    - failure metadata

Recommended later convention:

    result = successful result only

    failure / cancellation / timeout / supersession / diagnostic / partial data
    = separate metadata or event structures

Reason:

    This prevents non-success terminal states from quietly becoming partial
    success.


RECOMMENDED PRESERVATION 5: PROGRESS IS OBSERVATIONAL
=====================================================

Preserve the progress rule:

    Progress is observational lifecycle evidence.

Progress is not authoritative mutation.

Progress updates do not commit authoritative state by themselves.

Progress does not prove eventual success.

Trace/progress/UI visibility must not become committed-state authority.


RECOMMENDED PRESERVATION 6: CANCELLATION IS REQUEST / OUTCOME / STOP ATTEMPT SPLIT
=================================================================================

Preserve the cancellation split:

    - cancellation request
    - cancellation outcome
    - execution-stop attempt
    - execution-stop result

Cancellation is explicit.

Cancellation is intentional.

Cancellation is not failure.

A cancellation request does not guarantee immediate cancellation.

Cancelling before execution begins does not require execution-stop because no
underlying execution exists yet.

Cancelling after execution begins may attempt to stop the underlying execution
mechanism, but Job cancellation outcome and execution-stop outcome remain
distinct.


RECOMMENDED PRESERVATION 7: JOB TIMEOUT IS NOT TRANSPORT TIMEOUT
================================================================

Preserve the timeout split:

    Job timeout is a Job lifecycle concern.

    RPC transport timeout is not Job timeout.

    Job timeout is not RPC transport timeout.

Timeout uses a monotonic clock.

Timeout policy source is explicit.

TimedOut is distinct from Cancelled and Failed.

DA-21 owns RPC/transport timeout semantics.

DA-19 owns Job timeout semantics.


RECOMMENDED PRESERVATION 8: SUPERSESSION IS TERMINAL NON-ERROR OUTCOME
======================================================================

Preserve Superseded as a first-class terminal non-error outcome.

Supersession is:

    - explicit
    - intentional
    - not failure
    - not timeout
    - not ordinary user cancellation, although user action may cause it

Superseded means newer accepted input, newer work, or higher-priority work made
the old Job no longer relevant.

Superseded does not roll back authoritative state already committed.

Superseded does not allow new authoritative mutation from the superseded Job
after terminal transition.

Open transactional staging is resolved by DA-04.


RECOMMENDED PRESERVATION 9: LATE COMPLETION CANNOT CHANGE TERMINAL OUTCOME
==========================================================================

Preserve the late-completion rule.

Late completion after terminal outcome:

    - does not change the Job terminal state
    - does not produce a Job result
    - does not deliver a reply/result
    - may be traced as diagnostic evidence
    - may not commit new authoritative mutation after the terminal transition

Reason:

    Cancelled, timed-out, or superseded work must not appear to succeed later.


RECOMMENDED PRESERVATION 10: JOB TRACE OWNERSHIP STAYS DOMAIN-SPECIFIC
======================================================================

Preserve Job-domain trace ownership.

DA-19 owns Job-domain trace reason identifiers.

DA-03 owns the trace substrate.

DA-19 owns only the Job-domain ownership of trace reasons and required
correlation evidence.

Trace wording should follow the DA-03 cross-document trace wording check.

DA-19 trace evidence must not replace:

    - DA-04 state/transaction trace obligations
    - DA-16 capability trace reasons
    - DA-21 RPC trace reasons
    - DA-23 adapter trace reasons
    - DA-24 OrchestrationUnit trace reasons
    - DA-28 RuntimeHost trace reasons
    - DA-29 PackManager trace reasons


RECOMMENDED PRESERVATION 11: RPC / TRANSPORT / JOB STAY SEPARATE
================================================================

Preserve the RPC/transport/Job split.

Job lifecycle is distinct from RPC transport lifecycle.

A transport acknowledgement does not prove that a Job exists.

A Job may exist even if the transport that caused it later disconnects.

A transport timeout does not automatically imply Job timeout.

A Job timeout does not automatically imply transport timeout.

A request may be rejected before a Job exists.

A request may be accepted as Job-backed work.

DA-21 owns RPC and transport semantics.

DA-19 owns Job lifecycle semantics.


RECOMMENDED PRESERVATION 12: CAPABILITY / JOB RELATION STAYS OPTIONAL AND MEDIATED
=================================================================================

Preserve the Capability / Job split.

A capability invocation may complete without creating a Job.

Long-running, cancellable, progress-reporting, timeout-managed, or observable
capability execution may create or attach to a Job.

A Job handle is a lifecycle handle.

A Job handle is not:

    - raw service object
    - direct reference to implementation internals

Job-backed capability execution remains capability-mediated.

Job-backed capability execution does not expose service internals, raw
implementation objects, or the underlying execution mechanism.

DA-16 owns capability mediation.

DA-19 owns Job lifecycle.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-19.

No heavy rewrite is recommended.

Preserve:

    - Job as observable lifecycle handle, not execution primitive
    - Job / OrchestrationUnit / Transaction separation
    - final and exclusive terminal states
    - result only for Succeeded
    - progress as observational evidence
    - cancellation request / outcome / stop-attempt split
    - Job timeout versus transport timeout
    - Superseded as terminal non-error outcome
    - late completion safety rule
    - Job-domain trace ownership
    - RPC / transport / Job separation
    - optional and mediated Capability / Job relation

Main future watch item:

    Later concrete result/error/envelope specs must not smuggle partial output,
    diagnostic metadata, cancellation metadata, timeout metadata, or supersession
    metadata into "result" in a way that weakens the rule:

        result = successful result only

Future audits should check:

    - IS-01 RPC preserves Job/RPC identity separation.
    - IS-02 WebSocket flow preserves Job/transport lifecycle separation.
    - DA-18 Debugger preserves safe-point pause semantics.
    - DA-08 Window semantics preserves Job outcome / Window finalization
      separation.

DA-16 and DA-21 have already been audited and preserve the required
Capability/Job and RPC/Job separations.
