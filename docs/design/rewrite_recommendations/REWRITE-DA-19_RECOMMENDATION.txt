SUMMARY
=======

DA-19 is Dv3-compatible.

No heavy rewrite is recommended.

DA-19 defines the Turnix Job lifecycle and identity model.

Preserve the core split:

    Job = observable lifecycle handle for requested work

    OrchestrationUnit = execution-authority unit coordinating mutation flow

    Transaction = mutation staging and commit boundary

    RPC / transport = communication path

    Capability = named, permissioned, Turnix-mediated operation

    Execution mechanism = implementation primitive

    Replay / Resume / Retry = DA-26 workflow concepts, not Job lifecycle states

Current required source-level changes:

    1. Add or preserve a compact Job lifecycle stop-line.

    2. Clarify Retry wording now that DA-26 exists:
       Retry is new work and does not reuse the previous jobId.

    3. Clarify "resumed" lifecycle-event wording so it does not imply DA-26
       Resume workflow.

    4. Add DA-25 / DA-26 as stop-lines where Job wording touches artifacts,
       exports, comparison, Replay, Resume, Retry, or audit workflows.

Main watch item:

    Later concrete result/error/envelope specs must not weaken the rule that a
    Job result exists only for Succeeded.

Overall recommendation:

    KEEP WITH SMALL DA-26 RETRY / RESUME WORDING WATCH

Future edits should preserve:

ACTUAL DA-19 CHANGE 1: JOB LIFECYCLE STOP-LINE
==============================================

DA-19 should contain a compact source-level boundary statement.

Recommended source-level boundary:

    Job is an observable lifecycle handle for requested work.

    Job lifecycle state does not directly define underlying execution state,
    OrchestrationUnit outcome, transaction commit or abort, committed-state
    truth, Window finalization, AppInstance lifecycle, adapter lifecycle,
    RuntimeHost lifecycle, PackManager operation outcome, RPC request outcome,
    transport outcome, artifact/export authority, comparison outcome, Replay
    outcome, Resume outcome, Retry outcome, or audit-workflow outcome.

    If a Job outcome affects another domain, that domain defines the resulting
    consequence.

    Correlation between a Job and another domain outcome must be explicit.

This belongs in DA-19 because DA-19 owns Job lifecycle and Job-domain trace
reason semantics.

Detailed ownership mapping belongs in the guardrail section, not in the source
document.


ACTUAL DA-19 CHANGE 2: RETRY WORDING NOW THAT DA-26 EXISTS
==========================================================

DA-19 currently says:

    Retry is modeled as new work unless a later document explicitly defines a
    retry relationship.

Checkpoint 06 now has DA-26 defining Retry as new work.

Recommended source-level replacement:

    Retry is new work.

    Retry does not reuse the previous jobId.

    A Retry workflow may reference earlier Job evidence to explain why the new
    attempt exists, but that reference does not reopen or continue the earlier
    Job lifecycle.

    DA-26 owns Retry workflow semantics.

Reason:

    DA-19 owns Job lifecycle identity.

    DA-26 owns Retry workflow semantics.

    Retry does not restart a closed Job.

    Retry does not make the original jobId reusable.


ACTUAL DA-19 CHANGE 3: CLARIFY "RESUMED" LIFECYCLE-EVENT WORDING
=================================================================

DA-19 says that "resumed" is a lifecycle event, phase, or control condition
rather than a primary Job state.

This is locally valid Job wording, but DA-26 now gives Resume a formal workflow
meaning.

Recommended source-level clarification:

    Resume from paused Job state is a Job control event or lifecycle condition.
    It is not DA-26 Resume after SafePointWindow restoration.

Or use wording such as:

    continued after pause

instead of bare "resumed" where the context is Job pause control.

Reason:

    DA-19 owns Job pause/control lifecycle events.

    DA-26 owns Replay / Resume / Retry workflow semantics.

    The same word should not silently carry both meanings.


ACTUAL DA-19 CHANGE 4: ADD DA-25 / DA-26 STOP-LINES
===================================================

DA-19 should acknowledge DA-25 and DA-26 where needed.

Recommended source-level stop-lines:

    DA-25 defines WindowManifest, WindowExport, Minimal Audit Bundle, digest,
    partial export, missing material, and artifact/export semantics.

    DA-26 defines ComparisonResult, equality modes, Replay, Resume, Retry, and
    audit workflow semantics.

    A Job result, Job terminal outcome, Job trace event, or Job progress event
    does not by itself define artifact/export authority, comparison result,
    Replay, Resume, Retry, or audit workflow outcome.

Reason:

    Jobs can be involved in export, audit, replay, resume, retry, or comparison
    workflows, but DA-19 must not become the owner of those workflow meanings.


PRESERVATION RULE 1: JOB IS LIFECYCLE HANDLE, NOT EXECUTION PRIMITIVE
=====================================================================

Preserve the definition:

    Job = observable lifecycle handle for requested work

A Job is not:

    - Promise
    - coroutine
    - callback
    - thread
    - task
    - process
    - model request
    - transport message
    - RPC request
    - capability
    - OrchestrationUnit
    - transaction
    - committed state
    - execution mechanism
    - result payload
    - Window
    - artifact
    - export
    - Replay workflow
    - Resume workflow
    - Retry workflow

Runtime primitives may implement Jobs, but those primitives do not define Job
lifecycle semantics.

Job identity must remain distinct from:

    - RPC request identity
    - OrchestrationUnit identity
    - AppInstance identity
    - adapter identity
    - RuntimeHost identity
    - underlying execution identity
    - result payload identity
    - Window identity
    - artifact/export identity
    - Replay / Resume / Retry workflow identity


PRESERVATION RULE 2: JOB / ORCHESTRATIONUNIT / TRANSACTION TRIAD
================================================================

Preserve the core triad:

    Job answers:
        What requested work is waiting, running, succeeded, failed, cancelled,
        timed out, superseded, paused, or controlled at safe point?

    OrchestrationUnit answers:
        What owns or coordinates execution authority?

    Transaction answers:
        What staged mutation may become committed truth?

A Job does not become authoritative committed state merely because it exists,
runs, or reaches terminal outcome.

A Job result envelope does not become authoritative committed state merely
because the Job succeeded.

Job effects become authoritative only through the documents that own those
effects:

    - state
    - transaction
    - Window
    - capability
    - persistence
    - artifact/export
    - workflow

A Job terminal outcome does not automatically commit, abort, roll back, or
complete an OrchestrationUnit.

State mutation authority remains constrained by DA-04 even when work is
represented as a Job.


PRESERVATION RULE 3: JOB LIFECYCLE STATES STAY FINAL AND EXCLUSIVE
==================================================================

Preserve Job lifecycle states:

    - Pending
    - Running
    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

Preserve terminal states:

    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

A Job reaches exactly one terminal state.

Terminal state is final.

Closed Jobs are not restarted.

Retry is new work under DA-26.

Retry does not reuse the previous jobId.

Retry may reference earlier Job evidence, but referencing earlier Job evidence
does not reopen the earlier Job lifecycle.


PRESERVATION RULE 4: RESULT ONLY EXISTS FOR SUCCEEDED
=====================================================

Preserve the rule:

    A Job result exists only for Succeeded.

Later concrete envelope specs must not smuggle these into result:

    - partial output
    - diagnostic metadata
    - cancellation metadata
    - timeout metadata
    - supersession metadata
    - failure metadata
    - retained artifact metadata
    - comparison metadata
    - Replay / Resume / Retry workflow metadata

Recommended later convention:

    result = successful result only

    failure / cancellation / timeout / supersession / diagnostic / partial /
    workflow / artifact data = separate metadata or event structures

Reason:

    This prevents non-success terminal states from quietly becoming partial
    success.

    This also prevents workflow or artifact metadata from pretending to be the
    successful Job result.


PRESERVATION RULE 5: PROGRESS IS OBSERVATIONAL
==============================================

Preserve the progress rule:

    Progress is observational lifecycle evidence.

Progress is not authoritative mutation.

Progress updates do not commit authoritative state by themselves.

Progress does not prove eventual success.

Trace, progress, subscription delivery, and UI visibility must not become
committed-state authority.

Progress evidence does not define Window finalization.

Progress evidence does not define artifact/export authority.

Progress evidence does not define Replay, Resume, Retry, comparison, or audit
workflow outcome.


PRESERVATION RULE 6: CANCELLATION IS REQUEST / OUTCOME / STOP ATTEMPT SPLIT
===========================================================================

Preserve the cancellation split:

    - cancellation request
    - cancellation outcome
    - execution-stop attempt
    - execution-stop result

Cancellation is explicit.

Cancellation is intentional.

Cancellation is not failure.

A cancellation request does not guarantee immediate cancellation.

Cancelling before execution begins does not require execution-stop because no
underlying execution exists yet.

Cancelling after execution begins may attempt to stop the underlying execution
mechanism, but Job cancellation outcome and execution-stop outcome remain
distinct.

RPC cancellation messages are requests, not arbitrary execution kill.

Transport disconnect is not Job cancellation by itself.

Policy may decide what happens after disconnect or cancellation request when
in-flight or accepted work exists.

Cancellation does not define Retry unless a later policy or workflow explicitly
requests new work through DA-26 Retry semantics.


PRESERVATION RULE 7: JOB TIMEOUT IS NOT TRANSPORT TIMEOUT
========================================================

Preserve the timeout split:

    Job timeout is a Job lifecycle concern.

    RPC transport timeout is not Job timeout.

    Job timeout is not RPC transport timeout.

Timeout uses a monotonic clock.

Timeout policy source is explicit.

TimedOut is distinct from Cancelled and Failed.

DA-21 owns RPC and transport timeout semantics.

DA-19 owns Job timeout semantics.

Transport timeout does not by itself define Job timeout.

Job timeout does not by itself define transport timeout, adapter timeout,
RuntimeHost timeout, OrchestrationUnit timeout, Window finalization, Retry,
Replay, Resume, export, comparison, or audit workflow outcome.


PRESERVATION RULE 8: SUPERSESSION IS TERMINAL NON-ERROR OUTCOME
===============================================================

Preserve Superseded as a first-class terminal non-error outcome.

Supersession is:

    - explicit
    - intentional
    - not failure
    - not timeout
    - not ordinary user cancellation, although user action may cause it

Superseded means newer accepted input, newer work, or higher-priority work made
the old Job no longer relevant.

Superseded does not roll back authoritative state already committed.

Superseded does not allow new authoritative mutation from the superseded Job
after terminal transition.

Open transactional staging is resolved by DA-04.

Superseded does not itself create Retry.

A later Retry is new work under DA-26.


PRESERVATION RULE 9: LATE COMPLETION CANNOT CHANGE TERMINAL OUTCOME
===================================================================

Preserve the late-completion rule.

Late completion after terminal outcome:

    - does not change the Job terminal state
    - does not produce a Job result
    - does not deliver a reply/result
    - may be traced as diagnostic evidence
    - may not commit new authoritative mutation after the terminal transition
    - may not create artifact/export authority
    - may not silently trigger Replay, Resume, Retry, comparison, or audit
      workflow outcome

Reason:

    Cancelled, timed-out, or superseded work must not appear to succeed later.


PRESERVATION RULE 10: JOB TRACE OWNERSHIP STAYS DOMAIN-SPECIFIC
===============================================================

Preserve Job-domain trace ownership.

DA-19 owns Job-domain trace reason identifiers.

DA-03 owns the trace substrate.

DA-19 owns only the Job-domain ownership of trace reasons and required
correlation evidence.

Trace wording should follow the DA-03 cross-document trace wording check.

DA-19 trace evidence must not replace trace evidence owned by:

    - DA-04 state/transaction trace obligations
    - DA-08 Window trace/evidence
    - DA-16 capability trace reasons
    - DA-17 decision/policy trace evidence
    - DA-20 AppInstance trace reasons
    - DA-21 RPC trace reasons
    - DA-23 / DA-27 adapter trace reasons
    - DA-24 OrchestrationUnit trace reasons
    - DA-25 artifact/export trace obligations
    - DA-26 workflow trace obligations
    - DA-28 RuntimeHost trace reasons
    - DA-29 PackManager trace reasons


PRESERVATION RULE 11: RPC / TRANSPORT / JOB STAY SEPARATE
=========================================================

Preserve the RPC/transport/Job split.

Job lifecycle is distinct from RPC transport lifecycle.

A transport acknowledgement does not prove that a Job exists.

A Job may exist even if the transport that caused it later disconnects.

A transport timeout does not automatically imply Job timeout.

A Job timeout does not automatically imply transport timeout.

A request may be rejected before a Job exists.

A request may be accepted as Job-backed work.

RPC request identity and jobId remain distinct.

Request acceptance is not final Job success.

DA-21 owns RPC and transport semantics.

DA-19 owns Job lifecycle semantics.


PRESERVATION RULE 12: CAPABILITY / JOB RELATION STAYS OPTIONAL AND MEDIATED
===========================================================================

Preserve the Capability / Job split.

A capability invocation may complete without creating a Job.

Long-running, cancellable, progress-reporting, timeout-managed, or observable
capability execution may create or attach to a Job.

A Job handle is a lifecycle handle.

A Job handle is not:

    - raw service object
    - direct reference to implementation internals

Job-backed capability execution remains capability-mediated.

Job-backed capability execution does not expose service internals, raw
implementation objects, or the underlying execution mechanism.

DA-16 owns capability mediation.

DA-19 owns Job lifecycle.


PRESERVATION RULE 13: JOB DOES NOT DEFINE OTHER DOMAIN OUTCOMES
===============================================================

Preserve cross-domain lifecycle separation.

Job terminal outcome does not automatically:

    - stop or fail an AppInstance
    - complete or fail an OrchestrationUnit
    - commit or abort a transaction
    - create SafePointWindow
    - create AbortedWindow
    - define adapter lifecycle outcome
    - define RuntimeHost operation outcome
    - define PackManager operation outcome
    - mutate committed state
    - create WindowExport
    - create Minimal Audit Bundle
    - define artifact/export authority
    - define ComparisonResult
    - trigger DA-26 Replay
    - trigger DA-26 Resume
    - trigger DA-26 Retry
    - define audit workflow outcome

AppInstance stop does not automatically define Job terminal outcome.

Adapter failure does not automatically define Job terminal outcome.

RuntimeHost operation outcome does not automatically define Job terminal
outcome.

Window finalization does not automatically define Job terminal outcome.

Artifact/export creation does not automatically define Job terminal outcome.

Replay, Resume, or Retry workflow outcome does not automatically define prior
Job terminal outcome.

PackManager operation outcome does not automatically define Job terminal
outcome.

Relationships between Job outcome and other domain outcomes must be explicit.


WATCH ITEM: CONCRETE RESULT / ERROR / ENVELOPE
==============================================

Later concrete result/error/envelope specs must not smuggle partial output,
diagnostic metadata, cancellation metadata, timeout metadata, supersession
metadata, artifact metadata, comparison metadata, or workflow metadata into
"result" in a way that weakens the rule:

    result = successful result only


WATCH ITEM: RETRY / RESUME WORDING
==================================

DA-19 source uses retry and resumed wording.

Preserve:

    - Retry is new work under DA-26
    - Retry does not reuse the previous jobId
    - Retry may reference earlier Job evidence but does not reopen earlier Job
      lifecycle
    - Job "resumed" means resumed / continued from a Job pause or control
      condition
    - Job "resumed" does not mean DA-26 Resume after SafePointWindow restoration
    - closed Jobs are not restarted


WATCH ITEM: CONCRETE RPC / WEBSOCKET
====================================

IS-01 should preserve Job/RPC identity separation.

IS-02 should preserve Job/transport lifecycle separation.

Concrete RPC and WebSocket fields must not make acknowledgement, request
acceptance, frame delivery, reconnect, timeout, or disconnect redefine Job
lifecycle semantics.


WATCH ITEM: DEBUGGER SEMANTICS
==============================

DA-18 should preserve safe-point pause semantics.

Debugger pause must not become Job terminal outcome.

Debugger breakpoint behavior must not imply Job result.

Debugger safe-point pause is not Job Succeeded, Failed, Cancelled, TimedOut, or
Superseded.

Debugger resume / continue from pause is not DA-26 Resume.


WATCH ITEM: WINDOW AND ARTIFACT SEMANTICS
=========================================

DA-08 should preserve Job outcome / Window finalization separation.

Window finalization must not redefine Job terminal state.

SafePointWindow creation is not Job Succeeded by default.

AbortedWindow creation is not Job Failed, Cancelled, TimedOut, or Superseded by
default.

DA-25 should preserve that WindowManifest, WindowExport, Minimal Audit Bundle,
optional digest, partial export, and missing-material semantics do not redefine
Job lifecycle.

DA-26 should preserve that Replay, Resume, Retry, comparison, and audit workflow
semantics do not redefine prior Job lifecycle.

    Job terminal outcome is not Window finalization by default.

    Job terminal outcome is not artifact/export authority by default.

    Transport timeout is not Job timeout.

CURRENT FINAL RECOMMENDATION
============================

Keep DA-19.

No heavy rewrite is recommended.

Recommended future edits:

    - add or preserve compact Job lifecycle stop-line
    - update Retry wording now that DA-26 exists:
      Retry is new work and does not reuse the previous jobId
    - clarify Job resume / continue from pause so it does not imply DA-26 Resume
    - preserve Job as observable lifecycle handle, not execution primitive
    - preserve Job / OrchestrationUnit / Transaction separation
    - preserve final and exclusive terminal states
    - preserve result only for Succeeded
    - preserve progress as observational evidence
    - preserve cancellation request / outcome / stop-attempt split
    - preserve Job timeout versus transport timeout
    - preserve Superseded as terminal non-error outcome
    - preserve late completion safety rule
    - preserve Job-domain trace ownership
    - preserve RPC / transport / Job separation
    - preserve optional and mediated Capability / Job relation
    - preserve Job separation from AppInstance, adapter, RuntimeHost, Window,
      OrchestrationUnit, PackManager, artifact/export, Replay, Resume, Retry,
      comparison, audit-workflow, and committed-state outcomes

Do not expand DA-19 into detailed trace substrate, committed-state,
transaction, Window, activation, capability, permission, decision persistence,
debugger UI, AppInstance, RPC, transport, adapter lifecycle, RuntimeHost,
PackManager, artifact/export, comparison, Replay, Resume, Retry, or audit
workflow semantics.

Main future watch item:

    Later concrete result/error/envelope specs must not weaken the rule that a
    Job result exists only for Succeeded.
