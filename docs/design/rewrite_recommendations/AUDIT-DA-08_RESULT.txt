==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Correct in substance, with current-name translation required.

    The recommendation correctly preserves DA-08's central model: Windows group
    bounded runtime history; SafePointWindow is the finalized authoritative
    committed boundary; ActiveWindow is non-authoritative in-flight history;
    AbortedWindow is finalized non-authoritative abort evidence; journal material
    is non-authoritative evidence; optional retained evidence does not add
    committed-state authority; Window finalization is distinct from Job terminal
    outcome, OrchestrationUnit terminal outcome, and transaction commit/abort; and
    DA-25 / DA-26 own exports, bundles, comparison, Replay, Resume, Retry, and
    audit workflows.

    The recommendation still uses stale AppInstance wording and spaced
    Orchestration Unit wording. Translate those to ApplicationRun and
    OrchestrationUnit where the current architecture concept is meant.

Document verdict:
    Keep with small terminology and filename/title-scope fixes.

DA-08 is architecturally strong and should not be heavily rewritten.

The target already correctly delegates WindowManifest, WindowExport, Minimal
Audit Bundle, digest, offline inspection artifacts, equality modes,
ComparisonResult, Replay, Resume, Retry, and audit workflows to DA-25 / DA-26.

The main required fixes are:

    - translate AppInstance / appInstanceId wording to ApplicationRun /
      applicationRunId where live runtime incarnation is meant
    - normalize Orchestration Unit to OrchestrationUnit where the first-class type
      is meant
    - preserve DA-20 as owner of Application/ApplicationRun lifecycle and identity
    - preserve DA-19 as owner of Job lifecycle, terminal state, timeout,
      cancellation, progress, result, and late-completion semantics
    - preserve DA-24 as owner of OrchestrationUnit lifecycle and mutation-authority
      semantics
    - preserve DA-25 / DA-26 boundaries and do not move export, bundle,
      comparison, Replay, Resume, Retry, or audit workflow details into DA-08
    - consider filename normalization later because the current filename still
      claims exports and offline comparison while the title/body delegate them
      elsewhere
    - keep trace-visible Window wording as Window-domain trace emission obligation
      with DA-03-owned retention/loss semantics
    - avoid final-document version/process metadata leakage

Primary conclusion:
    Keep DA-08 as the Window kind, Window ordering, ActiveWindow,
    SafePointWindow, AbortedWindow, Window finalization, bounded runtime history,
    journal evidence, retained evidence, and Window-domain trace document. Apply
    targeted current-terminology and scope-alignment fixes only.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-08 should not keep older terminology merely because it appears in the older
source document or recommendation.

Specifically, the rewrite should not preserve:

    - AppInstance as runtime identity vocabulary
    - appInstanceId as primary current Window trace identity if ApplicationRun is
      the current live-runtime identity
    - Orchestration Unit as spaced informal wording where OrchestrationUnit is the
      current first-class type
    - cross-session audit workflow as a current phrase if DA-26 uses current
      ApplicationRun / Application / SaveBundle terminology instead
    - Window filename wording that implies DA-08 owns exports or offline
      comparison when the body delegates those semantics to DA-25 and DA-26
    - Journal evidence as state
    - ActiveWindow as committed truth
    - AbortedWindow as committed boundary
    - Optional retained evidence as added authority
    - Job terminal outcome as Window finalization
    - OrchestrationUnit terminal outcome as Window finalization
    - transaction commit/abort as Window finalization by itself
    - SafePointWindow timeout/cancellation as Job timeout/cancellation
    - trace completeness as required for committed-state correctness
    - retained history as hidden correctness dependency

Canonical translations:

    AppInstance -> ApplicationRun where one live runtime incarnation is meant
    AppInstance -> Application where durable application identity is meant
    appInstanceId -> applicationRunId where live runtime identity is meant
    Orchestration Unit -> OrchestrationUnit when the first-class type is meant
    cross-session audit workflow -> cross-run, cross-Application, or cross-
        SaveBundle audit workflow only if DA-26 uses that current terminology

The useful part of the older recommendation is not the old naming. The useful
part is the Window authority split:

    SafePointWindow may carry authoritative committed material. ActiveWindow and
    AbortedWindow carry non-authoritative evidence. Journal and optional retained
    evidence explain what happened but do not become committed-state truth.

DA-25/DA-26 boundaries, open questions, and locked summary.

==============================================================================
02. WHAT DA-08 GETS RIGHT
==============================================================================

02.1. DA-08 owns Windows and finalized runtime history
------------------------------------------------------

DA-08 correctly defines how Turnix groups runtime history into bounded Windows
and how Window finalization preserves committed boundaries and non-authoritative
evidence without turning retained history into hidden correctness dependency.

Preserve this.

02.2. DA-08 does not redefine committed state
---------------------------------------------

DA-08 correctly says it does not redefine the general memory and authoritative-
state model.

It correctly keeps DA-04 as owner of committed-state truth and transaction
boundaries.

Preserve this.

02.3. Journal is non-authoritative evidence
-------------------------------------------

DA-08 correctly says journal content is append-oriented, non-authoritative,
non-blocking, and evidence-oriented rather than correctness-defining.

It correctly says journal data is not state, journal data is not required for
correctness, and journal loss does not change committed-state meaning.

Preserve this strongly.

02.4. Window sequence is explicit
---------------------------------

DA-08 correctly says every Window in the ordered sequence is exactly one of:

    - SafePointWindow
    - AbortedWindow
    - ActiveWindow

It correctly says at most one ActiveWindow exists for a live run at a time and
that ActiveWindow is the unique mutable tail of the sequence.

Preserve this, translating AppInstance to ApplicationRun.

02.5. SafePointWindow boundary is strong
----------------------------------------

DA-08 correctly says SafePointWindow is a finalized authoritative committed
boundary and that its authoritative portion contains committed state material
only.

It correctly says transactional layer contents are not authoritative
SafePointWindow material.

Preserve this.

02.6. Optional retained evidence does not add authority
-------------------------------------------------------

DA-08 correctly says revision history, journal material, additional trace
evidence, Job lifecycle evidence, OrchestrationUnit lifecycle evidence, and other
non-authoritative evidence may be retained by policy, but optional retained
evidence does not add authority.

Preserve this.

02.7. ActiveWindow is non-authoritative
---------------------------------------

DA-08 correctly says ActiveWindow is the current in-flight region and does not
define committed truth.

It correctly says ActiveWindow may be discarded during recovery and is not a
deterministic replay boundary.

Preserve this.

02.8. AbortedWindow is non-commit finalized evidence
----------------------------------------------------

DA-08 correctly says AbortedWindow is finalized evidence of a non-commit outcome,
not a committed boundary.

It correctly says AbortedWindow does not acquire authority merely because it is
finalized, retained, or exported.

Preserve this.

02.9. Finalization produces exactly one outcome
-----------------------------------------------

DA-08 correctly says ActiveWindow finalizes as exactly one of SafePointWindow or
AbortedWindow.

It correctly forbids both outcomes, partial finalized artifacts, and unresolved
mixed states.

Preserve this.

02.10. Window finalization is not Job / OrchestrationUnit / transaction outcome
-------------------------------------------------------------------------------

DA-08 correctly says Job terminal outcome, OrchestrationUnit terminal outcome,
and transaction commit/abort do not by themselves define Window finalization.

Preserve this strongly.

02.11. SafePointWindow creation modes are explicit
--------------------------------------------------

DA-08 correctly distinguishes ImmediateCommitted and AtQuiescence request modes.

It correctly says Turnix does not silently substitute one mode for another, does
not silently wait forever, does not silently cancel in-flight work, and does not
silently downgrade AtQuiescence into ImmediateCommitted.

Preserve this.

02.12. DA-25 / DA-26 boundary is strong
---------------------------------------

DA-08 correctly delegates WindowManifest, WindowExport, Minimal Audit Bundle,
digest, partial export, missing material, offline inspection artifacts,
ComparisonResult, equality modes, Replay, Resume, Retry, and audit workflows to
DA-25 and DA-26.

Preserve this strongly.

==============================================================================
03. REQUIRED FIX: APPLICATIONRUN TERMINOLOGY
==============================================================================

DA-08 still uses AppInstance and appInstanceId in several places.

Replace these with current Application/ApplicationRun terminology according to
meaning.

For Window sequence ownership, the likely current wording is:

    One ApplicationRun maintains one explicit ordered Window sequence.

    At most one ActiveWindow exists for one ApplicationRun at a time.

    If an ActiveWindow exists, it is the unique mutable tail of that
    ApplicationRun's Window sequence.

For trace fields, prefer:

    applicationRunId

where the field identifies the live runtime incarnation associated with Window
history.

If a durable Application identity is also needed, include it separately as:

    applicationId

Do not use appInstanceId as a current primary field unless a compatibility alias
is explicitly retained.

DA-20 owns Application/ApplicationRun lifecycle and runtime identity details.
DA-08 may reference those identities only to scope Window history.

==============================================================================
04. REQUIRED FIX: ORCHESTRATIONUNIT TERMINOLOGY
==============================================================================

DA-08 uses spaced `Orchestration Unit` wording.

Normalize to:

    OrchestrationUnit

where the first-class current architecture type is meant.

Preserve these semantics:

    - OrchestrationUnit lifecycle ordering is distinct from Window ordering.
    - OrchestrationUnit lifecycle evidence can be correlated to Windows through
      trace and retained evidence.
    - OrchestrationUnit reaching Completed does not by itself create a
      SafePointWindow.
    - OrchestrationUnit reaching Failed, Cancelled, or Superseded does not by
      itself create an AbortedWindow.
    - OrchestrationUnit terminal outcome does not by itself define Window
      finalization.
    - retained OrchestrationUnit evidence inside finalized Window evidence remains
      non-authoritative unless committed under DA-04.

DA-24 owns OrchestrationUnit lifecycle and mutation-authority semantics.

DA-08 owns only Window correlation/finalization boundaries involving
OrchestrationUnit evidence.

==============================================================================
06. TRACE WORDING
==============================================================================

Follow the DA-03 cross-document trace wording check.

Window trace requirements are Window-domain emission obligations.

Trace retention, trace pruning, trace loss, event structure, trace DAG semantics,
span mechanics, and trace storage semantics remain owned by DA-03.

DA-08 owns Window-domain trace reason identifiers and required Window-domain trace
attributes where the document defines them.

Do not let DA-08 wording imply that trace evidence is committed state or that
trace persistence is guaranteed forever.

Preserve the distinction:

    Trace, journal, and retained evidence may explain Window history.

    Authoritative committed-state truth remains DA-04.

==============================================================================
08. WHAT TO PRESERVE FROM CURRENT DA-08
==============================================================================

Preserve these boundaries, translating stale terminology where present:

    - runtime history is grouped into ordered Windows
    - Windows are SafePointWindow, AbortedWindow, and ActiveWindow
    - at most one ActiveWindow exists for one ApplicationRun at a time
    - ActiveWindow is the unique mutable tail of the Window sequence
    - Window ordering is explicit and does not rely on timestamps, inference, or
      presentation order
    - journal is non-authoritative evidence
    - journal data is not state
    - journal loss does not change committed-state meaning
    - SafePointWindow is a finalized authoritative committed boundary
    - SafePointWindow authoritative portion contains committed state only
    - transactional layer contents are not authoritative SafePointWindow material
    - optional retained evidence does not add authority
    - retained SafePointWindow completeness requires retained trace identity and
      scope evidence sufficient to identify the Window and committed scope
    - ActiveWindow is non-authoritative and not a deterministic replay boundary
    - ActiveWindow evidence does not convert Pending or Running Jobs into
      replayable work
    - AbortedWindow is finalized non-authoritative non-commit evidence
    - AbortedWindow does not acquire authority because it is finalized, retained,
      or exported
    - ActiveWindow finalizes as exactly one outcome: SafePointWindow or
      AbortedWindow
    - finalization never produces both outcomes, partial artifact, or unresolved
      mixed state
    - Job terminal outcome does not define Window finalization
    - OrchestrationUnit terminal outcome does not define Window finalization
    - transaction commit/abort does not define Window finalization by itself
    - ImmediateCommitted and AtQuiescence request modes remain explicit
    - AtQuiescence does not silently wait forever, cancel in-flight work, or
      downgrade to ImmediateCommitted
    - SafePointWindow creation timeout is not Job timeout
    - SafePointWindow creation cancellation is not Job cancellation
    - DA-08 owns Window-domain trace reason identifiers where defined
    - DA-25 owns Window artifacts/exports/bundles/offline inspection artifacts
    - DA-26 owns comparison, Replay, Resume, Retry, and audit workflow semantics
