SUMMARY
=======

DA-04 is strong and highly Dv3-compatible.

It answers the question left by DA-03:

    If trace is evidence, where does authoritative truth live?

DA-04 answers:

    committed state

This is the correct architecture.

DA-04 defines how Turnix distinguishes runtime memory from authoritative state,
how state is layered and mutated, and how committed state changes become
deterministic, restorable, and traceable without depending on observational
history.

Overall recommendation:

    KEEP

No heavy rewrite is recommended.

WHAT IS ALREADY NAILED
======================

DA-04 correctly says runtime memory is not authoritative merely because it is:

    - resident
    - visible
    - active
    - currently in use

Committed state becomes authoritative only after crossing the explicit commit
boundary defined by this document.

This prevents the bad model:

    value is in RAM, therefore value is truth

Correct Dv3 model:

    memory = runtime representation
    state = committed authority
    trace = evidence / observation
    persistence = protection


RELATION TO DA-03
=================

DA-03 says trace is evidence, not committed state.

DA-04 confirms this by placing traces in non-authoritative material.

DA-04 also says observational material may explain what happened, but it does
not define committed truth.

Correct combined model:

    Trace can prove or explain within retained evidence.
    Trace does not define committed truth.
    Trace loss does not corrupt committed state.
    Committed state is restorable without requiring non-authoritative
    observational history.

This means the earlier DA-01 recommendation should be refined:

    trace emission obligations may be required
    trace persistence may still be policy-governed and lossy
    trace loss affects evidential completeness, not committed-state correctness


AUTHORITY CLASSES
=================

DA-04 correctly uses exactly two authority classes:

    Authoritative
    Non-authoritative

This is good.

Avoid introducing semi-authoritative or partially-authoritative categories.

Material may be important, required to attempt, useful for explanation, or
required by policy, but for committed-state truth it is either authoritative or
non-authoritative.

This binary distinction should survive.


MEMORY LAYER MODEL
==================

DA-04 correctly defines memory as layered by:

    - authority
    - scope
    - lifetime
    - rollback boundary

It also says there is no single global memory object.

This matches the Dv3 runtime model.

Concrete layer kinds should be defined later as implementation/spec detail.

The example list should not become a closed taxonomy.


TRANSACTION MODEL
=================

DA-04's transaction model is strong.

A transaction is temporary staging overlay.

Staged mutation is not authoritative.

A transaction resolves only by:

    - commit
    - abort

Commit and abort are atomic.

Partial propagation does not occur.

A transaction does not remain half-committed.

This should remain unchanged.


NESTED TRANSACTION MODEL
========================

Child transaction commits propagate into parent transactions, not directly into
committed layers while an enclosing transaction exists.

Only the outermost transaction commit mutates committed layers.

This is important for nested pipeline/session behavior.

It allows child work to complete locally without becoming committed system
truth until the enclosing boundary commits.


CONFLICT DETECTION
==================

DA-04's conflict detection model is strong.

A transaction records the base committed revision visible when a key was first
touched.

Commit conflicts occur when committed existence or committed revision changed.

A conflicting commit fails deterministically.

Turnix does not silently use:

    - merge
    - last-write-wins
    - heuristic reconciliation

Any override requires explicit user decision or explicit policy elsewhere.

This is exactly the right no-magic behavior.


TRACE-VISIBLE STATE MUTATION
============================

DA-04 says authoritative state mutation and transaction outcomes remain
trace-visible.

This is correct.

After DA-03, this should be interpreted carefully:

    trace-visible = the domain has a trace emission obligation

Not:

    retained trace evidence is required for committed-state correctness

DA-04 already supports this interpretation because it says traces are
non-authoritative and committed-state correctness does not depend on trace
completeness.

Possible future clarification:

    State and transaction trace obligations are emission obligations. Trace
    retention and loss are governed by DA-03. Loss of trace evidence affects
    evidential completeness, not committed-state correctness.


PERSISTENCE AS PROTECTION, NOT TRUTH
====================================

This is one of the strongest sections.

DA-04 correctly says:

    Persistence protects committed state against loss.
    Persistence does not define what state truth is.
    Committed state truth is determined by the commit model.
    Persistence failure does not silently redefine committed-state truth.

This gives the clean stack:

    Commit model decides truth.
    Persistence protects truth.
    Trace explains or reports what happened.


STATIC DATA MUTATION INTENT
===========================

Patch vs Copy should remain.

Static data is read-only by default.

Mutation intent must be explicit:

    Patch:
        original key remains authoritative
        patch is applied on read
        patch is persisted as overlay data

    Copy:
        new key is created
        data is copied and modified
        original remains unchanged

Turnix must not silently substitute Patch for Copy or Copy for Patch.

This will matter for packs, mods, content, prompt fragments, defaults, and
templates.


REVISION RETENTION AND LATEST STATE
===================================

DA-04 correctly allows revision retention to be policy-driven.

Older revisions may be removed.

However, garbage collection does not remove data required to reconstruct the
latest committed state for each committed key.

This matches the Dv3/latest-state requirement:

    latest committed state must remain restorable

History can be bounded.

Current committed truth cannot be silently rewritten by retention policy.


TOOLING MUTATION
================

Tooling can inspect through controlled surfaces.

Tooling-initiated mutation occurs inside a transaction and follows the same
commit/abort rules as runtime mutation.

Tooling does not bypass authority boundaries merely because it is privileged
tooling.

This is important for debugger, memory viewer, CLI inspection, and future
editor-like tools.

The debug UI must not become a separate state authority path.


RESTORATION BOUNDARY
====================

DA-04's restoration boundary is correct.

Turnix supports deterministic restoration of committed state from retained
authoritative material.

This does not imply:

    - deterministic reconstruction of in-flight activity
    - deterministic replay of external side effects
    - reproducibility of uncommitted activity

Correct model:

    Restore committed state: yes.
    Reconstruct uncommitted runtime activity: no.
    Replay external side effects: no.


EXPLICIT NON-REQUIREMENTS
=========================

DA-04 correctly says Turnix does not require:

    - infinite committed history retention
    - journal-backed determinism
    - journal-backed recovery
    - trace-backed correctness
    - concurrency-first execution
    - deterministic reconstruction of uncommitted runtime activity

This is a useful anti-overengineering shield.

Especially keep:

    no trace-backed correctness


CURRENT FINAL RECOMMENDATION
============================

Keep DA-04.

No heavy rewrite is recommended.

Main future clarification:

    Align "trace-visible" wording with DA-03's distinction between trace
    emission obligation and trace persistence guarantee.

Do not make trace authoritative state.

Do not make persistence define truth.

Do not let tooling, adapters, same-language execution, or Orchestration Unit
existence bypass the commit boundary.
