SUMMARY
=======

DA-04 is strong and highly Dv3-compatible.

No heavy rewrite is recommended.

DA-04 defines the authoritative memory and state model used by Turnix.

It defines:

    - what memory means in Turnix
    - what state means in Turnix
    - authority boundaries between committed and non-committed material
    - layer-based runtime memory structure
    - transactional staging and commit or abort rules
    - commit conflict detection for authoritative mutation
    - state and transaction trace obligations
    - persistence as protection against loss rather than the definition of truth
    - static-data mutation intent
    - revision and state-retention rules
    - migration commit rules for authoritative state mutation
    - state-boundary constraints for tooling-initiated mutation
    - restoration boundary rules for committed state

Required DA-04 clarification:

    "Trace-visible" state mutation should be understood as a trace emission
    obligation, not as a trace-persistence requirement for committed-state
    correctness.

Rewrite-boundary guardrails:

    DA-04 owns committed-state truth.

    DA-04 should not absorb detailed trace storage semantics, pack activation,
    capability semantics, Job lifecycle semantics, AppInstance lifecycle,
    ExecutionAdapter semantics, OrchestrationUnit lifecycle, debugger behavior,
    replay workflow, audit bundle, or concrete IO authority.

    Those details belong to their subject-owning documents.

Overall recommendation:

    KEEP WITH SMALL TRACE-WORDING CLARIFICATION

ACTUAL DA-04 CHANGE 1: TRACE-VISIBLE STATE MUTATION
===================================================

Current issue:

    DA-04 says authoritative state mutation and transaction outcomes remain
    trace-visible.

This is correct, but after DA-03, "trace-visible" should be interpreted using
the DA-03 cross-document trace wording check.

Correct meaning:

    trace-visible = the state/transaction domain has a trace emission
    obligation

Not:

    retained trace evidence is required for committed-state correctness

Not:

    trace evidence becomes committed-state authority

Recommended DA-04 clarification:

    State and transaction trace obligations are emission obligations.

    Trace retention and loss are governed by DA-03.

    Loss of trace evidence affects evidential completeness, not committed-state
    correctness.

Reason:

    This prevents a reader or machine assistant from turning trace evidence into
    committed-state authority.

    It also prevents the opposite error, where "trace may be lossy" is misread
    as "state mutation trace obligations are optional."


PRESERVATION RULE 1: COMMITTED STATE IS AUTHORITATIVE TRUTH
===========================================================

Preserve DA-04's core authority split:

    memory = runtime representation
    state = committed authority
    trace = evidence / observation
    persistence = protection

Runtime memory is not authoritative merely because it is:

    - resident
    - visible
    - active
    - currently in use

Committed state becomes authoritative only after crossing the explicit commit
boundary defined by DA-04.

Do not rewrite DA-04 to make any of these committed-state authority:

    - trace
    - runtime memory
    - logs
    - journals
    - debugger views
    - tool views
    - adapter state
    - RuntimeHost command-surface output
    - PackManager views
    - Job lifecycle state
    - OrchestrationUnit existence
    - capability invocation records
    - RPC acknowledgement
    - diagnostic output


PRESERVATION RULE 2: TRACE IS NOT COMMITTED STATE
=================================================

Preserve the DA-03 / DA-04 split:

    Trace can prove or explain within retained evidence.

    Trace does not define committed truth.

    Trace loss does not corrupt committed state.

    Committed state is restorable without requiring non-authoritative
    observational history.

Do not rewrite DA-04 to make committed-state correctness depend on trace
completeness.

Keep the explicit non-requirement:

    no trace-backed correctness


PRESERVATION RULE 3: AUTHORITY CLASSES REMAIN BINARY
====================================================

Preserve the two authority classes:

    Authoritative
    Non-authoritative

Avoid introducing:

    - semi-authoritative
    - partially-authoritative
    - soft-authoritative
    - trace-authoritative-for-state
    - diagnostic-authoritative
    - view-authoritative

Material may be important, required to attempt, useful for explanation, or
required by policy, but for committed-state truth it is either authoritative or
non-authoritative.


PRESERVATION RULE 4: TRANSACTIONS DEFINE MUTATION STAGING
=========================================================

Preserve DA-04's transaction model:

    A transaction is a temporary staging overlay.

    Staged mutation is not authoritative.

    A transaction resolves only by commit or abort.

    Commit and abort are atomic.

    Partial propagation does not occur.

    A transaction does not remain half-committed.

Nested transaction rule to preserve:

    Child transaction commits propagate into parent transactions, not directly
    into committed layers while an enclosing transaction exists.

    Only the outermost transaction commit mutates committed layers.


PRESERVATION RULE 5: NO SILENT CONFLICT RECONCILIATION
======================================================

Preserve deterministic conflict handling.

A transaction records the base committed revision visible when a key was first
touched.

Commit conflicts occur when committed existence or committed revision changed.

A conflicting commit fails deterministically.

Turnix must not silently use:

    - merge
    - last-write-wins
    - heuristic reconciliation

Any override requires explicit user decision or explicit policy elsewhere.


PRESERVATION RULE 6: PERSISTENCE PROTECTS TRUTH, BUT DOES NOT DEFINE TRUTH
=========================================================================

Preserve DA-04's persistence model:

    Persistence protects committed state against loss.

    Persistence does not define what state truth is.

    Committed state truth is determined by the commit model.

    Persistence failure does not silently redefine committed-state truth.

Clean stack to preserve:

    Commit model decides truth.

    Persistence protects truth.

    Trace explains or reports what happened.


PRESERVATION RULE 7: STATIC DATA MUTATION INTENT REMAINS EXPLICIT
=================================================================

Preserve the Patch vs Copy distinction.

Static data is read-only by default.

Mutation intent must be explicit:

    Patch:
        original key remains authoritative
        patch is applied on read
        patch is persisted as overlay data

    Copy:
        new key is created
        data is copied and modified
        original remains unchanged

Turnix must not silently substitute Patch for Copy or Copy for Patch.

This matters for packs, mods, content, prompt fragments, defaults, templates,
and SavePack-local copied material.


PRESERVATION RULE 8: LATEST COMMITTED STATE REMAINS RESTORABLE
==============================================================

Preserve the revision-retention rule:

    Revision retention may be policy-driven.

    Older revisions may be removed.

    Garbage collection must not remove data required to reconstruct the latest
    committed state for each committed key.

History can be bounded.

Current committed truth cannot be silently rewritten by retention policy.


PRESERVATION RULE 9: TOOLING DOES NOT BYPASS COMMIT AUTHORITY
=============================================================

Preserve tooling mutation constraints.

Tooling can inspect through controlled surfaces.

Tooling-initiated mutation occurs inside a transaction and follows the same
commit/abort rules as runtime mutation.

Tooling does not bypass authority boundaries merely because it is privileged
tooling.

This applies to:

    - debugger
    - memory viewer
    - CLI inspection
    - PackManager tools
    - editor-like tools
    - future management Views

The debug UI must not become a separate state authority path.


PRESERVATION RULE 10: RESTORATION BOUNDARY STAYS LIMITED
========================================================

Preserve DA-04's restoration boundary.

Turnix supports deterministic restoration of committed state from retained
authoritative material.

This does not imply:

    - deterministic reconstruction of in-flight activity
    - deterministic replay of external side effects
    - reproducibility of uncommitted activity

Correct model:

    Restore committed state: yes.

    Reconstruct uncommitted runtime activity: no.

    Replay external side effects: no.


REWRITE-BOUNDARY GUARDRAILS, NOT SUGGESTED DA-04 CONTENT
=========================================================

This section is not suggested DA-04 wording.

It exists to prevent architectural drift during rewrite when the editor knows
DA-04 but may not have every subject-owning document loaded.

Use these as guardrails only.

State-authority guardrails:

    Trace is evidence, not committed state.

    Persistence protects truth, but does not define truth.

    Job lifecycle state is not committed state.

    Job result payloads become authoritative only if committed through the
    owning state/transaction domain.

    OrchestrationUnit coordinates mutation flow, but does not bypass commit.

    Capability invocation does not become committed state by existing.

    RPC acknowledgement does not become committed state.

    Adapter execution does not directly mutate committed state.

    PackContext does not expose unrestricted committed-state mutation.

    RuntimeHost command surfaces do not directly mutate committed state.

    PackManager views, repair suggestions, graph preparation, and management
    operations do not directly mutate committed state.

    Debugger or management tooling must use the same transaction/commit model
    when initiating state mutation.

Owning-document boundaries:

    DA-03 owns tracing structure, trace event schema, trace storage semantics,
    and trace retention/loss semantics.

    DA-07 owns concrete persistent I/O authority, Readers, Writers, and
    filesystem rules.

    DA-08, DA-25, and DA-26 own windows, manifests, exports, replay workflows,
    and audit bundles.

    DA-14 owns pack activation semantics and PackContext authority.

    DA-16 owns service, capability, and permission semantics.

    DA-19 owns Job lifecycle, Job result, Job timeout, and Job cancellation
    semantics.

    DA-20 owns AppInstance lifecycle and runtime identity semantics.

    DA-23 owns execution adapter boundary semantics.

    DA-24 owns OrchestrationUnit lifecycle, mutation-authority ownership,
    terminal outcomes, single-lane AppInstance orchestration, and
    OrchestrationUnit trace reason ownership.

    DA-18 owns debugger pause, breakpoint, and execution-control behavior.

Local rewrite rule:

    DA-04 may name these concepts when needed to protect committed-state
    authority.

    DA-04 should not define their detailed behavior.

    DA-04 should remain the authoritative memory/state/commit model document.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-04.

No heavy rewrite is recommended.

Clarify "trace-visible" wording using the DA-03 cross-document trace wording
check:

    State and transaction trace obligations are emission obligations.

    Trace retention and loss are governed by DA-03.

    Loss of trace evidence affects evidential completeness, not committed-state
    correctness.

Do not make trace authoritative state.

Do not make persistence define truth.

Do not introduce semi-authoritative state categories.

Do not let tooling, adapters, same-language execution, PackManager operations,
RuntimeHost command surfaces, capability invocation, Job lifecycle state,
RPC acknowledgement, PackContext access, or OrchestrationUnit existence bypass
the commit boundary.
