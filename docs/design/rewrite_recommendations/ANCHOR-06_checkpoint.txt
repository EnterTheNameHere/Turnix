TURNIX DV3 ARCHITECTURE CHECKPOINT 06
=====================================

Purpose:
    Rehydration anchor for the Turnix Dv3 architecture audit.

Status:
    Current understanding after completing the DA document sweep for the Dv3
    architecture documents audited so far.

    This checkpoint includes the Dv3 runtime spine, state model, trace model,
    payload/value representation, configuration, persistent I/O authority,
    Window/finalized-history model, Window artifacts/exports, offline comparison
    and replay/resume/retry workflows, discovery / identity / visibility /
    resolution / import / dependency / activation chain, service/capability/
    permission model, policy-decision handling, debugger model, Job lifecycle,
    AppInstance lifecycle, RPC boundary, UI/View/frontend runtime, adapter
    boundaries, OrchestrationUnit mutation authority, RuntimeHost boundary, and
    PackManager graph-preparation model.

This checkpoint is not a final specification.
It is the current working architecture map and should be updated when later
non-DA documents revise the model.

Major conceptual additions since Checkpoint 05:

    - DA-05 confirms storage-neutral committed value representation:
      committed values are represented through immutable ValueRefs and Chunks,
      not live runtime object identity.

    - DA-06 confirms configuration as specialized authoritative state built on
      DA-04, not a separate state architecture. effectiveConfig is a derived
      runtime-visible view, not a separate authoritative state class.

    - DA-07 confirms IoManager as the sole persistent-I/O authority. Persistence
      protects committed truth but does not define truth.

    - DA-18 confirms debugger authority remains semantic, mediated, staged,
      trace-visible, and constrained by the same transaction, policy, Job,
      Window, AppInstance, adapter, and persistence boundaries as runtime work.

    - DA-22 confirms UI/View/frontend runtime as presentation and interaction,
      not authority. View lifecycle and frontend disconnect do not define
      AppInstance, Job, adapter, RuntimeHost, transport, or committed-state
      outcomes.

    - DA-25 confirms Window artifacts, WindowExports, Minimal Audit Bundles, and
      optional digests as retained artifact/export representation, not new
      authority.

    - DA-26 confirms equality, comparison, Replay, Resume, Retry, and audit
      workflows as explicit workflow claims over retained finalized artifacts.
      Replay is committed-state restoration plus retained causal story, not
      re-running external effects. Resume and Retry are new work.

Important correction since Checkpoint 05:

    DA-20 currently defines AppInstance as a live runtime instance of one
    AppPack. That is now treated as a required AppPack-backing decision, not

            Turnix runs AppInstances.

            AppPack is one first-class declarative way to create an

REWRITE RECOMMENDATION COMPRESSION RULE
=======================================

Rewrite recommendation files are not audit reports.

They should preserve only information needed to guide a future rewrite safely.

Keep only:

    - rewrite decisions
    - required clarifications
    - preservation rules that prevent bad rewrites
    - source-level boundary statements that the target document itself needs
    - watch items that affect future edits
    - cross-document dependency notes that change local interpretation
    - final recommendation
    - metadata

Remove:

    - general praise
    - "already nailed" sections unless converted into preservation rules
    - long confirmations
    - repeated doctrine already owned elsewhere
    - stale addenda
    - update history
    - audit-pass history
    - unnecessary "confirmed by later audit" text
    - unnecessary "after the DA pass" / "after the ODA pass" / "after the IS
      pass" text
    - audit-report style narrative
    - broad lists of audited documents unless they change local rewrite behavior

REWRITE RECOMMENDATION PLACEMENT AND HISTORY RULES
==================================================

Rewrite recommendations should represent current rewrite guidance, not audit
history.

Checkpoints may record audit phase, consolidation history, and how the current
architecture map was reached.

Rewrite recommendation files should not encode audit-pass history as rewrite
guidance.

Avoid wording such as:

    - after the DA sweep
    - completed DA sweep
    - post-DA-sweep
    - after the ODA audit
    - after the IS audit
    - later documents confirmed
    - this was confirmed by later audit

Use current architecture wording instead.

Good:

    Current architecture context requires this boundary.

Bad:

    After the DA sweep, add this stop-line.

Rewrite recommendations must distinguish:

    - actual source-document changes
    - rewrite-boundary guardrails

Actual source-document changes are compact statements that should be added,
removed, rewritten, clarified, or preserved in the target source document.

Rewrite-boundary guardrails are not suggested source wording.

Rewrite-boundary guardrails exist to prevent architectural drift during rewrite
when the editor may not have every owning document loaded.

For each boundary note, apply the placement test:

    Source-level boundary
        Use when the target source document itself needs a compact statement to
        avoid being misread.

    Rewrite-boundary guardrail
        Use when the recommendation needs cross-document ownership reminders to
        prevent the rewrite from absorbing another document's domain.

If both are true, include both.

Do not hide a boundary the source document needs only inside a guardrail
section.

Do not expand the source document into a mini-index of neighboring domains.

The source document should state its own compact authority or ownership
boundary.

The guardrail section should explain which neighboring domains not to absorb.

Do not update a rewrite recommendation merely because later audited documents
confirm existing guidance.

Update only when current architecture context changes local rewrite behavior,
such as narrowing a warning, removing a stale warning, clarifying ownership,
adding a real watch item, changing edit order, or preventing a likely wrong
rewrite.


CURRENT DV3 THESIS
==================

Turnix is a reusable runtime for persistent, local-first, traceable, stateful,
orchestrated AI applications and adjacent runtime systems.

Turnix is not primarily:

    - a launcher
    - an AppPack runner
    - a pack format
    - a pack manager
    - a catalog system
    - a graph-preparation tool
    - a frontend/backend template
    - a plugin loader
    - a dynamic script runner
    - a web app framework
    - a convenience-first modding system

Turnix is primarily:

    - a runtime continuity engine
    - a deterministic resolver
    - a policy-driven orchestrator
    - an explainable system
    - a controlled execution and state boundary
    - a host for AppInstances and other runtime-managed work

Core Dv3 correction:

    Turnix does not merely run AppPacks.

    Turnix runs AppInstances.

    AppPack is one first-class declarative way to create an AppInstance.

Important DA-20 tension:

    DA-20 currently defines the AppPack-backed AppInstance lifecycle.

    It remains open whether every possible AppInstance must be formally
    AppPack-backed, including embedded/scripted/test usage through synthetic or
    internal AppPacks.

    Until resolved, do not rewrite Turnix identity as "Turnix runs AppPacks."

Packs remain first-class, but packs do not define the whole identity of Turnix.

PackManager is an official Turnix management domain, but PackManager also does
not define the whole identity of Turnix.


HIGH-LEVEL RUNTIME MODEL
========================

Turnix Runtime contains or composes:

    - Kernel
    - RuntimeHost
    - Trace substrate
    - Memory / committed state model
    - Payload / ValueRef / Chunk representation model
    - Configuration / schema / migration model
    - IoManager / persistence authority
    - Window / finalized runtime history system
    - Window artifact / export / Minimal Audit Bundle model
    - Offline comparison / Replay / Resume / Retry / audit workflow model
    - Service system
    - Permission system
    - Capability system
    - Job system
    - OrchestrationUnit system
    - RPC / interoperability boundary
    - transport implementations
    - UI / View / frontend runtime system
    - ExecutionAdapters
    - Debugger / inspection / breakpoint system
    - PackManager
    - AppInstance system
    - SavePack / durable AppInstance state system
    - pack discovery and resolution
    - pack identity and visibility
    - pack visibility enforcement / access-control
    - pack dependency and activation systems
    - importing / module-loading boundary
    - user decision and policy-handling system
    - LLM pipeline / LLM driver systems

Most subsystems should be independently useful where possible.

Examples:

    Memory can be useful without LLMs.
    Trace can be useful without a frontend.
    ValueRef / Chunk representation can be useful without a specific storage
    backend.
    Configuration can reuse memory/state representation without becoming Memory.
    IoManager can protect persistent artifacts without defining state truth.
    Window history can be useful without offline export.
    WindowExport can be useful without Replay or Resume.
    Replay can restore retained committed state without resuming live work.
    LLMDriver can be replaceable.
    RPC should be transport-agnostic.
    ExecutionAdapters should be replaceable.
    Pack system should be first-class but not mandatory for every embedded use,
    unless the AppPack-backing decision intentionally chooses synthetic/internal
    AppPacks for all AppInstances.
    PackManager can help manage pack graph intent without owning activation,
    importing, persistence, policy, or Kernel authority.

Once these parts need to work together as one runtime, Kernel and RuntimeHost
compose them under Turnix-owned lifecycle, authority, policy, orchestration, and
state boundaries.


AUTHORITY GUARDRAILS
====================

Preserve authority boundaries.

Do not let convenience, implementation proximity, same-language execution,
same-process execution, direct-call optimization, first-party tooling, adapter
trust, adapter readiness, frontend presentation, debugger power, policy
remembering, retained evidence, export packaging, digest presence, persistence
mechanics, root writability, or RuntimeHost command surfaces collapse authority
boundaries.

Kernel owns runtime authority.

RuntimeHost exposes controlled entry surfaces but is not Kernel authority.

IoManager owns persistent-I/O authority but not committed-state truth.

Payload identity is DA-05 representation, not filesystem or storage-container
identity.

Configuration is specialized authoritative state, not separate state
architecture.

ExecutionAdapter runs external or adapter-mediated code but is not Kernel
authority.

RPC is the logical communication boundary, not a transport.

Transport carries messages but does not define authority.

UI is presentation and interaction, not authority.

Debugger tooling is semantic and mediated, not a raw authority bypass.

Capability invocation is not automatically Job.

Service object access is not capability permission.

PackContext is scoped participation, not backend internals access.

Discovery is candidate production, not visibility, resolution, activation,
import, runtime loading, or runtime identity.

Visibility is reference permission / eligibility-to-be-seen, not resolution,
dependency satisfaction, activation, import, service access, capability access,
or permission inheritance.

Resolution is deterministic selection under one explicit context, not discovery,
activation, import, PackManager repair, policy guessing, or source mixing.

Importing/module loading is not activation.

Activation is controlled executable participation, not import.

Dependencies are hard contracts, not preferences, activation, import, capability
permission, or advisory metadata.

Advisory pack relations are metadata for PackManager/UI presentation, not hard
dependencies, hard activation blockers, resolution constraints, or loader rules
by themselves.

Policy reduces repeated friction; it does not redefine authority.

Adapter mediation is not sandboxing.

Sandboxing does not grant Kernel authority.

Lack of sandboxing does not grant backend implementation authority.

AppInstance is runtime identity, not AppPack, SavePack, RuntimeHost, View,
adapter, Job, Window, OrchestrationUnit, or committed state.

Window retained evidence is not committed-state truth unless the retained
material is authoritative committed material under DA-04.

Artifact/export representation does not add authority.

ComparisonResult does not imply replayability, resumability, or completeness.

Replay is committed-state restoration plus retained causal story, not re-running
external effects.

Resume and Retry are new work.

PackManager is first-party management/tooling domain, not Kernel, RuntimeHost
authority, resolver, loader, activator, policy owner, persistence authority, or
Turnix identity.


KERNEL
======

Kernel is the runtime authority root.

Kernel should remain intentionally small and should not become a god object.

Kernel owns or coordinates:

    - runtime authority
    - root runtime context
    - service registries
    - AppInstance management
    - Job management
    - Capability registry
    - Permission manager
    - TraceHub / trace substrate access
    - IoManager / persistence access
    - adapter manager
    - RuntimeHost connection points
    - approved internal routing paths
    - Kernel-mediated decision points

Kernel is not:

    - Memory
    - ValueRef / Chunk representation
    - configuration storage layout
    - IOManager implementation
    - LLMPipeline
    - LLMDriver
    - PackResolver
    - PackManager
    - RuntimeHost
    - AppInstance
    - frontend
    - adapter
    - application logic
    - mod logic
    - storage codec logic
    - prompt logic
    - Window finalization semantics
    - Window export semantics
    - comparison / Replay / Resume / Retry workflow semantics

Kernel rule:

    If a subsystem can work without Kernel, it should be allowed to.

    If multiple subsystems need to work together as one runtime, Kernel composes
    them and enforces the contract boundaries between them.

Kernel should be small, boring, and hard to abuse.


RUNTIMEHOST
===========

RuntimeHost is the running host boundary.

RuntimeHost is not Kernel authority.

RuntimeHost owns the running host boundary through which Kernel-owned authority
is started, exposed, coordinated, and closed.

RuntimeHost is not:

    - Kernel
    - AppInstance
    - SavePack
    - CLI
    - ExecutionAdapter
    - transport
    - Job
    - OrchestrationUnit
    - PackManager
    - IoManager
    - View
    - Turnix identity
    - launcher identity
    - AppInstance creation semantics owner
    - Window finalization owner
    - persistence authority owner by itself

RuntimeHost may expose controlled entry surfaces.

Entry surfaces and command surfaces can request, observe, or control runtime
operations only through mediated paths.

They do not become authority themselves.

Startup modes are entry workflows, not separate runtime semantics.

RuntimeHost startup modes and command surfaces must use the same
Kernel-mediated AppInstance creation paths.

Examples:

    interactive host mode
    one-shot command mode
    serve mode
    connect mode
    test mode
    launcher mode

These are different ways to enter Turnix, not different Turnixes.


LOCAL-FIRST
===========

Turnix is local-first, not local-only.

Local-first does not require same-machine execution.

Local-first means authoritative runtime and state remain under user-controlled
local infrastructure.

This can include:

    - RuntimeHost and frontend on the same machine
    - RuntimeHost on one LAN machine and frontend on another
    - home server RuntimeHost with local SavePack/state ownership
    - powerful local AI machine hosting execution while lighter clients present UI

Local-first does not prohibit explicit, policy-governed:

    - LAN mode
    - server hosting
    - remote-resource mode
    - federated discovery
    - remote clients

But those modes must not replace local-first as the baseline authority,
persistence model, failure model, recovery model, or SavePack ownership model.

Remote or LAN access does not imply remote state authority.

Remote or LAN access does not imply adapter execution authority.

Remote or LAN access does not imply persistence authority.


TRACE
=====

Trace is structured evidence.

Trace is not:

    - committed state
    - logging
    - memory
    - persistence truth
    - UI presentation
    - artifact authority

Trace answers:

    What happened?
    What caused what?
    Why?

Trace evidence is proof only within retained trace evidence.

If an action is not present in retained trace evidence, trace cannot prove that
it happened.

If trace evidence was lost, the loss itself must be represented honestly when
possible.

Important distinction:

    Domain-required trace emission:
        A subject-owning document may require that a domain attempt to emit
        trace evidence for meaningful actions.

        This is an emission obligation.

    Trace persistence / retention:
        Trace persistence is policy-governed.

        Retained trace evidence may be bounded, rotated, or lossy when loss is
        represented honestly.

    Optional diagnostic / verbose trace:
        Development-mode or diagnostic enrichment that is best-effort and
        non-authoritative.

Trace loss weakens evidential completeness.

Trace loss does not by itself change committed-state correctness.

Committed-state truth is governed by DA-04, not by trace completeness.

Corrected mantra:

    If not traced, trace cannot prove it happened.

Not:

    If trace persistence failed, committed state is invalid.

Trace reason ownership is domain-specific:

    DA-03 = trace substrate
    DA-04 = state / transaction trace obligations
    DA-05 = representation / integrity / decode / reachability trace obligations
    DA-06 = configuration trace obligations
    DA-07 = persistence I/O outcome trace obligations
    DA-08 = Window finalization and Window-domain trace reasons
    DA-09 = discovery trace reasons
    DA-11 = resolution trace reasons
    DA-14 = activation trace reasons
    DA-16 = capability trace reasons
    DA-17 = decision and policy trace obligations
    DA-18 = debugger trace obligations
    DA-19 = Job trace reasons
    DA-20 = AppInstance-domain trace reasons
    DA-21 = RPC trace evidence and message-flow observability
    DA-22 = UI / View trace reasons
    DA-24 = OrchestrationUnit trace reasons
    DA-25 = artifact/export trace obligations where artifact creation occurs
    DA-26 = workflow trace obligations for comparison / Replay / Resume / Retry
    DA-27 = adapter-domain trace reasons
    DA-28 = RuntimeHost trace reasons
    DA-29 = PackManager trace reasons

DA-03 should not become the catalog of every domain trace reason.

Cross-document trace wording rule:

    When a document says trace-visible or requires trace evidence, treat that
    as a domain trace emission obligation unless the document explicitly
    defines stronger persistence semantics under DA-03.

    Do not let trace wording imply that retained trace evidence is committed
    state, that trace persistence is guaranteed forever, or that trace loss
    invalidates committed-state truth.


MEMORY AND COMMITTED STATE
==========================

Memory is not merely chat history.

Memory is not merely prompt context.

Memory is not authoritative merely because it is:

    - resident
    - visible
    - active
    - currently in use

Committed state becomes authoritative only after crossing the DA-04 commit
boundary.

Correct state model:

    memory = runtime representation
    state = committed authority
    trace = evidence / observation
    persistence = protection

DA-04 uses exactly two authority classes:

    Authoritative
    Non-authoritative

Avoid introducing semi-authoritative state categories.

A thing may be important, required to attempt, useful for explanation, or
policy-required, but for committed-state truth it is either authoritative or
non-authoritative.


TRANSACTIONS AND COMMIT
=======================

A transaction is a temporary staging overlay.

Staged mutation is not authoritative.

A transaction resolves only by:

    - commit
    - abort

Commit and abort are atomic.

Partial propagation does not occur.

A transaction does not remain half-committed.

Nested transaction model:

    Child transaction commits propagate into parent transactions, not directly
    into committed layers while an enclosing transaction exists.

    Only the outermost transaction commit mutates committed layers.

Conflict detection:

    A transaction records the base committed revision visible when a key was
    first touched.

    Commit conflicts occur when committed existence or committed revision
    changed.

    Conflicting commit fails deterministically.

Turnix does not silently use:

    - merge
    - last-write-wins
    - heuristic reconciliation

Any override requires explicit user decision or explicit policy elsewhere.


PAYLOAD IDENTITY, CHUNKS, AND VALUEREF
======================================

DA-05 defines the storage-neutral committed-value representation contract.

Committed values are represented through immutable payload references rather
than live runtime object identity.

Committed state references immutable payload bytes, not runtime pointers.

Runtime objects are decoded views of committed payload material.

Runtime residency is an implementation detail.

A committed key in a committed layer or committed configuration is
representable at the commit boundary as:

    key -> ValueRef

ValueRef:

    - immutable once created
    - deterministic decoding contract for one committed value payload
    - not a pointer to live runtime memory
    - does not depend on transactional layers
    - does not depend on journal completeness
    - does not depend on trace completeness
    - does not depend on hidden runtime side effects

ValueRef forms are exactly:

    - InlineValueRef
    - ChunkValueRef

Arbitrary network references and arbitrary file-path references are not ValueRef
forms.

External references, if ever introduced, do not become valid authoritative
committed-state representation unless deterministic retrieval is explicitly
guaranteed.

Chunk:

    - immutable byte sequence
    - identified by stable ChunkId
    - content-derived
    - storage-neutral
    - path-independent
    - database-row-independent
    - machine-independent
    - timestamp-independent
    - runtime-pointer-independent
    - storage-container-independent

Chunk identity is format-aware.

Different encodings of the same semantic value produce different ChunkIds
unless a later authoritative rule explicitly defines canonical equivalence.

Integrity failure is explicit.

Corrupt payload material is not authoritative.

Decode failure is explicit.

A committed value whose ValueRef cannot be decoded is not treated as valid
authoritative content.

Committed values are schemaless by default.

Schema linkage is optional representation metadata.

Static origin does not bypass committed representation.

Payload sharing across committed state roots, Windows, manifests, traces,
journals, exports, and audit bundles does not change authority boundaries.

Reachability determines retention safety.

Reachability does not redefine artifact authority.

Garbage collection must not collect payload reachable from authoritative
retained roots.

DA-05 defines representation.

DA-07 defines persistent I/O authority.

DA-04 defines committed-state truth.


CONFIGURATION, SCHEMAS, AND MIGRATION
=====================================

Configuration is authoritative state.

Configuration is a specialized use of DA-04 state model, not a separate state
architecture.

Configuration is not:

    - arbitrary JSON blobs
    - free-form user data
    - implicit defaults hidden in code

Committed configuration is authoritative.

Runtime-visible configuration views are not authoritative merely because they
are resident or currently effective.

Configuration persistence protects against loss.

Configuration persistence does not define truth.

Storage layout and file placement define where configuration is persisted, not
what makes it authoritative.

Configuration mutation that changes authoritative committed state follows
normal transaction and commit rules.

Configuration scopes:

    - Engine
    - Pack-global
    - Save-bound

Precedence:

    Save-bound > Pack-global > Engine > Defaults

Ownership:

    Engine scope:
        owned by Kernel

    Pack-global scope:
        owned by one canonicalPackId

    Save-bound scope:
        owned by one canonicalPackId inside one save context

canonicalPackId for persistent configuration ownership:

    resolvedAuthor + "@" + packTreeId

canonicalPackId excludes version.

Schemas define configuration structure, types, constraints, allowed value
shapes, compatibility expectations, and access-level metadata when needed.

Schemas are not runtime defaults.

Schemas do not create authoritative values by themselves.

Defaults:

    - initial values only
    - immutable input material
    - not user configuration
    - not mutable state

Overrides:

    - explicit user-authored persisted deviations from defaults
    - loaded after defaults
    - migrated explicitly
    - not modified silently
    - only user-authored persisted configuration input layer

Duplicate schema/default/config files are selected, not stacked.

Duplicate schema/default/config files are shadowed, not merged.

Configuration materialization stages:

    1) schema interpretation
    2) defaults input
    3) explicit override inputs
    4) migration when required
    5) validation of stored values
    6) computed transforms when allowed
    7) effectiveConfig materialization

Stages 1 through 5 are gating stages.

Stages 6 and 7 are runtime-view stages.

effectiveConfig is final runtime-visible configuration view.

effectiveConfig is not separate authoritative state class.

Computed transforms operate only on effectiveConfig.

Computed transforms do not mutate stored values.

Configuration committed values should reuse DA-05 ValueRef / Chunk
representation where they are stored as Turnix committed payload material.

DA-06 owns configuration meaning, scopes, schema use, materialization,
migration, storage layout, and policy-file placement.

DA-17 owns decision and remembered-policy semantics.


PERSISTENT I/O AND IOMANAGER
============================

All persistence in Turnix is centralized and mediated.

IoManager is the sole authority responsible for persistent I/O.

IoManager responsibilities include:

    - mediating reads and writes
    - enforcing root boundaries and permissions
    - normalizing and validating storage targets
    - selecting appropriate Readers and Writers
    - classifying errors
    - ensuring trace-visible persistence outcomes
    - providing atomic-write guarantees where required
    - managing backups and snapshots per policy
    - preserving rollback points for identity-bearing mutations

IoManager does not replace DA-04 state model.

IoManager enforces how persistence occurs for state and other persisted
artifacts.

IoManager authority does not transfer to:

    - adapters
    - packs
    - services
    - Views
    - transports
    - RPC handlers
    - Jobs
    - tools

merely because they can request persistence.

Reader / Writer providers:

    - format mechanics under IoManager control
    - not authority roots
    - not general backend authority surfaces for adapter-executed code

Raw filesystem handles do not escape Reader / Writer boundary.

Raw paths do not become part of caller runtime surface.

Packs do not receive filesystem handles or unrestricted path APIs.

Adapter-executed code does not receive filesystem handles or unrestricted path
APIs as Turnix persistence authority path.

Built-in provider kinds are available before discovery and indexing:

    - utf8Text
    - binary
    - json
    - json5
    - jsonl

Extended providers may be provided by packs or platform extensions, but:

    - they register with IoManager
    - they declare supported kinds explicitly
    - they are not usable until providing pack is activated
    - Turnix does not auto-discover or load providers mid-read/write operation

Discovery and indexing use built-in Readers only.

Discovery/indexing do not use:

    - pack-provided Readers
    - pack-provided Writers
    - compilers
    - transformers
    - streaming I/O

Runtime writable roots:

    - userdata/
    - saves/

Runtime read-only roots:

    - custom/
    - first-party/
    - third-party/

Root writability does not by itself authorize state mutation.

Adapter-executed code does not gain write authority merely because a root is
writable.

Persistent I/O errors are exactly one of:

    - Unrecoverable
    - User-decidable
    - Optional / best-effort

Identity-bearing data never uses silent fallback.

Optional / best-effort failures such as logs, traces, and caches do not corrupt
authoritative state.

Before user-decidable recovery, a minimal recovery surface must exist.

If the minimal recovery surface is not available, the failure is unrecoverable
for that boot path.

I/O outcomes are trace-visible.

Trace visibility does not make DA-07 trace substrate owner.

Save-local copied packs or save-internal artifacts do not become global indexing
material merely because they exist in save data.

Configuration persistence uses IoManager, but configuration semantics remain
DA-06.

Migrators may exist for configuration, manifests, save structures, and future
persisted artifact classes.

Migrators do not provide rollback by inverse logic.

Rollback safety is provided by IoManager plus DA-04 commit model.

Backups and snapshots protect recoverability.

Backups and snapshots do not define truth.

Streaming I/O is explicit.

Streaming write uses staging.

Streaming write cancellation does not produce partial valid final output.

Final destination update occurs only on commit.

Streaming is forbidden in deterministic early phases such as discovery,
indexing, manifest loading, configuration schema/default/userdata loading,
dependency resolution, and activation-critical reads.

Native filesystem APIs are not Turnix persistence authority path for
pack-provided or adapter-executed code.


WINDOWS AND FINALIZED RUNTIME HISTORY
=====================================

Windows group bounded runtime history and retained evidence for one
AppInstance.

A Window is a bounded region of runtime history and retained evidence associated
with one AppInstance.

Windows distinguish:

    - authoritative committed boundaries
    - non-authoritative in-flight activity
    - non-authoritative historical evidence

Window kinds:

    - SafePointWindow
    - ActiveWindow
    - AbortedWindow

An AppInstance maintains one explicit ordered Window sequence.

At most one ActiveWindow exists for one AppInstance at a time.

If an ActiveWindow exists, it is the unique mutable tail of the Window sequence.

Window ordering is explicit.

Window ordering does not rely on timestamps, inference, or presentation order.

Window ordering is distinct from Job lifecycle ordering.

Window ordering is distinct from OrchestrationUnit lifecycle ordering.

SafePointWindow:

    - finalized authoritative committed boundary
    - contains committed layers and committed config as authoritative material
    - authoritative portion contains committed state material only
    - transactional layer contents are not authoritative material
    - optional retained evidence does not add authority
    - Job reaching Succeeded does not by itself create a SafePointWindow
    - OrchestrationUnit reaching Completed does not by itself create a
      SafePointWindow
    - transaction commit does not by itself create a SafePointWindow

ActiveWindow:

    - current in-flight region after last finalized committed boundary
    - non-authoritative
    - does not define committed truth
    - may be discarded during recovery
    - is not deterministic replay boundary
    - may contain Pending or Running Jobs
    - may contain non-terminal OrchestrationUnits
    - evidence does not convert Pending or Running Jobs into replayable work

AbortedWindow:

    - finalized ActiveWindow that did not produce a new authoritative committed
      boundary
    - finalized evidence of non-commit outcome
    - not a committed boundary
    - does not acquire authority merely because finalized, retained, or exported
    - Job reaching Failed, Cancelled, TimedOut, or Superseded does not by itself
      create an AbortedWindow
    - OrchestrationUnit reaching Failed, Cancelled, or Superseded does not by
      itself create an AbortedWindow
    - transaction abort does not by itself create an AbortedWindow

ActiveWindow finalizes as exactly one outcome:

    - SafePointWindow
    - AbortedWindow

Finalization never produces both outcomes for the same ActiveWindow.

Finalization never produces partial finalized artifact.

Finalization never preserves unresolved mixed state.

Job terminal outcome does not by itself define Window finalization.

OrchestrationUnit terminal outcome does not by itself define Window
finalization.

Transaction commit or abort does not by itself define Window finalization.

Journal is:

    - append-oriented
    - non-authoritative
    - non-blocking
    - evidence-oriented rather than correctness-defining
    - not state
    - not required for correctness

Journal loss does not change committed-state meaning.

SafePointWindow creation modes:

    - ImmediateCommitted
    - AtQuiescence

ImmediateCommitted:

    - attempts SafePointWindow creation without waiting for quiescence
    - succeeds immediately if eligible
    - fails deterministically if not eligible
    - does not silently degrade into waiting behavior

AtQuiescence:

    - attempts SafePointWindow creation only when no OrchestrationUnit is active
      for the target AppInstance
    - may queue explicitly until quiescence
    - queued request is trace-visible
    - queued request does not mean queued Job execution
    - queued request does not alter Job lifecycle state by itself

SafePointWindow creation timeout is not Job timeout.

SafePointWindow creation cancellation is not Job cancellation.


WINDOW ARTIFACTS, EXPORTS, AND AUDIT BUNDLES
============================================

DA-25 owns artifact/export/bundle semantics derived from finalized Windows.

Artifact representation does not add authority.

Exported form changes portability, not semantics.

WindowManifest:

    - immutable manifest representing exactly one finalized Window
    - never represents ActiveWindow
    - exactly one of SafePointWindowManifest or AbortedWindowManifest
    - immutability preserves representation stability only
    - manifest existence does not create authority

SafePointWindowManifest:

    - includes safePointWindowId
    - includes windowType = SafePointWindow
    - includes committedStateRoot
    - may include traceRoot, journalRoot, revisionRoot, mabRoot by policy
    - optional roots are non-authoritative evidence roots

AbortedWindowManifest:

    - includes abortedWindowId
    - includes windowType = AbortedWindow
    - does not define committedStateRoot
    - represents finalized non-authoritative evidence of an aborted Window
      region

WindowExport:

    - portable immutable serialization of one WindowManifest closure
    - exactly one of SafePointWindowExport or AbortedWindowExport
    - changes portability, not semantics
    - does not add authority
    - does not imply replayability
    - does not imply resumability
    - does not imply evidence completeness

SafePointWindowExport is deterministic restoration artifact only if required
committed-state material is present.

A partial SafePointWindowExport lacking required committed material is not a
deterministic restoration artifact.

AbortedWindowExport is not restoration artifact.

AbortedWindowExport is not replay proof.

Minimal Audit Bundle:

    - non-authoritative export artifact for audit, explanation, offline
      inspection
    - not authoritative state
    - not WindowManifest
    - not restoration artifact
    - not replay guarantee
    - not completeness guarantee

Committed-state excerpts inside a Minimal Audit Bundle are non-authoritative
evidence excerpts.

Optional digests:

    - comparison accelerators
    - not identities
    - not authority

Offline inspection:

    - reads retained artifact contents
    - does not run Turnix orchestration logic
    - does not control original Jobs, OrchestrationUnits, adapters, RPC
      channels, transports, Views, or frontends

Partial export and missing material must remain explicit.


OFFLINE COMPARISON, REPLAY, RESUME, RETRY, AUDIT WORKFLOWS
==========================================================

DA-26 owns workflow claims over retained finalized Window-derived artifacts.

ComparisonResult has exactly three values:

    - Equal
    - NotEqual
    - NotComparable

ComparisonResult is not boolean.

ComparisonResult without equality mode is incomplete.

ComparisonResult does not imply:

    - replayability
    - resumability
    - audit completeness

Equality modes are explicit.

Default equality mode is StateEquality unless another mode is explicitly
requested.

StateEquality:

    - compares retained committed key/value pairs only
    - ignores non-authoritative trace/journal/audit/Job/OrchestrationUnit/
      adapter/RPC/View/frontend evidence
    - returns NotComparable when required committed-state material is missing

StrictStateEquality:

    - compares retained committed key/value pairs plus retained revision history
      required by strict mode
    - unsupported strict submodes return NotComparable
    - strict comparison does not silently degrade to StateEquality

EvidenceEquality:

    - compares retained evidence closure
    - does not imply state equality
    - equality of retained Job evidence does not imply resumed or replayable Job
      execution
    - equality of retained OrchestrationUnit evidence does not imply resumed or
      replayable OrchestrationUnit execution

ExportEquality:

    - compares exported packaged closure
    - does not imply state equality unless selected mode includes relevant
      committed-state closure
    - does not imply evidence equality unless selected mode includes relevant
      evidence closure

NotComparable is distinct from NotEqual.

Tools do not silently retry weaker equality mode and present the result as if it
answered the original request.

Digests accelerate comparison only.

Replay:

    - deterministic reconstruction of retained SafePointWindow state plus
      retained causal story where available
    - restores committed state within DA-04 restoration boundary
    - does not re-run external effects
    - does not reconstruct uncommitted ActiveWindow activity
    - does not resume retained Job execution
    - does not resume retained OrchestrationUnit execution
    - does not restart retained adapter execution
    - does not reconnect retained RPC channels, transports, Views, or frontends

Resume:

    - explicit attempt to continue execution after restoring retained
      SafePointWindow
    - new work after restoration
    - not deterministic in outcome
    - does not reuse closed Job identity
    - does not reuse closed OrchestrationUnit identity
    - does not retroactively commit prior uncommitted activity

Retry:

    - new orchestration attempt for a previous failed, incomplete, superseded,
      cancelled, or intentionally retried action
    - new work
    - trace-visible
    - does not reuse previous jobId when represented as Job
    - does not reuse previous orchestrationUnitId
    - does not reuse previous adapter execution identity
    - not implied by Replay
    - not implied by Resume unless Resume policy explicitly selects Retry

Audit workflows:

    - operate over retained evidence and artifacts
    - do not mutate state
    - do not require journal completeness
    - do not assume replayability
    - remain honest about retained gaps, pruned evidence, and incompleteness


PACK DISCOVERY
==============

Discovery is candidate/root production.

Discovery is not:

    - visibility
    - enablement
    - selector resolution
    - dependency satisfaction
    - activation
    - import
    - runtime loading
    - capability authority
    - broader policy authority

Discovery is strict, boring, predictable, and side-effect free.

Discovery identifies candidate pack entities inside allowed roots and classifies
them into discovered or rejected outcomes.

Discovery also establishes candidate roots for non-pack categories such as
userdata and saves.

Discovery output is input to later indexing, visibility, and resolution.

Discovery output is not runtime-loaded result.

Root categories:

    - custom/
    - first-party/
    - third-party/
    - userdata/
    - saves/

userdata/ and saves/ are not content categories.

SavePacks are discoverable as save entities.

SavePacks are not eligible for import as normal content-root packs.

Save-local pack material is a distinct nearer source context and precedes
ordinary content-root precedence.

custom does not override save-local pack material by default.

Content-root precedence:

    custom
    first-party
    third-party

This precedence must not override SaveOnly, GlobalPinned, save-local copied
material, selected graph intent, pinned SavePack graph evidence, or explicit
AppInstance/SavePack semantics unless an authoritative document says so.


PACK IDENTITY, VISIBILITY, AND ACCESS CONTROL
=============================================

Pack is the general container concept.

Pack kinds include:

    - AppPack
    - ModPack
    - ViewPack
    - ContentPack
    - SavePack

Pack identity layers are distinct:

    - declaredId
    - packTreeId
    - author
    - version

declaredId is manifest-local to its parent pack context.

packTreeId is computed from hierarchy and is not filesystem-based.

author is part of identity, not decoration.

If author cannot be resolved through declaration or inheritance, the pack is
invalid.

Visibility answers:

    Is pack A permitted to reference pack B?

Visibility is permissioned reachability.

Visibility is not:

    - activation
    - code loading
    - execution order
    - dependency satisfaction
    - version compatibility
    - runtime capability access
    - runtime service access
    - permission inheritance

Visibility is evaluated during:

    - dependency resolution
    - resolvePack calls
    - turnixImport resolution

Visibility is not bypassed or deferred.

Visibility is evaluated dynamically between requesting pack and target pack.

Visibility is not pre-expanded into a static graph.

exportNestedPacks:

    - direct-child export control only
    - not transitive
    - not wildcard

importPacksFromParent:

    - parent-to-child reference visibility only
    - does not imply export
    - does not imply capability access
    - does not imply service access
    - does not imply permission inheritance

Resolution source restricts visibility domain.

SavePack visibility:

    - SavePack is never globally visible
    - SavePack is visible only within AppInstance context
    - copied packs inside SavePack are visible only within that save
    - copied packs inside SavePack are not globally visible
    - copied packs shadow global packs of same identity within that save domain

Visibility does not grant capabilities.

Visibility does not grant services.

A visible pack may still be unable to use another pack's capabilities or
services.


GENERIC RESOLUTION
==================

Resolution answers:

    Which concrete pack identity satisfies this PackRequest inside the current
    resolution context?

Resolution is deterministic and side-effect free.

Resolution consumes:

    - one PackRequest
    - one registry snapshot
    - one externally supplied resolution context

Resolution outputs exactly one of:

    - one resolved concrete pack identity
    - one classified resolution failure
    - one classified ambiguity requiring external decision

Resolution does not:

    - rescan filesystem
    - read manifests lazily
    - merge manifest fragments
    - activate packs
    - load runtimes
    - guess policy
    - mutate registry snapshot
    - trigger discovery
    - combine partial candidate data into synthetic candidate

Resolution always occurs inside one explicit resolution context.

Resolver does not invent, switch, or silently mix resolution contexts.

Ambiguity requires external policy or user decision.

The generic resolver does not guess.

Importing is not:

    - dependency declaration
    - resolution
    - adapter selection
    - execution authorization
    - activation
    - execution authority
    - capability permission

Native language import systems do not understand Turnix pack resolution,
visibility, save scoping, adapter selection, execution authorization,

Cross-pack code access routes only through Turnix-defined mechanisms.

Same host language does not imply same authority.

Python pack code remains adapter-executed pack code and does not become backend

Cross-pack native Python imports are not allowed.

Python pack code interacts with other packs only through Turnix-mediated APIs.

JavaScript cross-pack loading routes through:

    turnixImport(selector)

turnixImport is a Turnix-defined mediated loader.

turnixImport is not native import().

turnixImport is not:

    - dependency declaration
    - adapter selection request
    - execution authorization request
    - activation request
    - capability permission request
    - visibility override
    - permissive loader
    - best-effort loader
    - version selector
    - Kernel authority grant

Importing respects concrete identity already chosen during dependency

Importing does not reopen dependency resolution.

Semver is not allowed in turnixImport selectors.

Module evaluation caused by JavaScript ESM import is not Turnix-recognized

Import-time execution is not activation.

Background work started outside Turnix orchestration is unsupported by Turnix

DEPENDENCIES AND PACK REQUESTS
==============================

Dependencies are hard functional contracts.

Dependency meaning:

    This pack cannot function correctly unless another pack exists that
    satisfies this request.

Dependencies are not preferences.

Declaring dependency does not:

    - load code
    - activate pack
    - grant visibility
    - grant capabilities
    - define activation order

Manifest field:

    packs

Every entry under packs is hard dependency meaning.

Dependency resolution source model:

    - SaveOnly
    - GlobalPinned
    - GlobalNormal

Every hard dependency is resolved from exactly one dependency-resolution source.

Sources are mutually exclusive.

The resolver does not silently mix or fall back between sources.

SaveOnly:

    - applies when dependency packTreeId is listed in SavePack metadata as copied
    - only copied packs inside SavePack are eligible
    - global registry is not consulted
    - absence of copied pack is hard error

GlobalPinned:

    - applies when dependency is bound to pin in SavePack metadata
    - only pinned concrete identity is eligible
    - global registry only
    - missing pinned identity is hard error
    - pin does not imply copying or saving

GlobalNormal:

    - all other dependency cases
    - global registry only
    - SavePack content not consulted
    - selection follows deterministic procedure

GlobalNormal selection procedure:

    1) version handling
    2) author relationship ordering
    3) root precedence: custom, first-party, third-party
    4) final lexicographic tie-break

Fingerprint requires exact concrete version.

Advisory pack relations:

    - supportedPacks
    - conflictingPacks
    - recommendedPacks

Advisory relations are not hard dependencies, hard activation blockers, generic
resolution constraints, or loader/runtime warning rules by themselves.

Required roles / provided roles are dependency/resolution-layer semantics.

They are not runtime capability invocation semantics.

Provider registration and provider selection remain watch items.


ACTIVATION
==========

Activation is the controlled boundary between inert metadata and
Turnix-recognized executable participation.

Activation answers:

    Has Turnix intentionally brought this pack into recognized executable
    participation under Turnix orchestration?

Activation is a controlled, explicit, one-time state transition.

Before activation:

    - pack exists only as metadata
    - code has no execution authority under Turnix
    - adapter loading or native module evaluation does not make it active

After activation:

    - pack may participate in runtime behavior
    - execution is allowed only through Turnix-controlled orchestration pathways
    - PackContext defines pack-facing authority context

Activation is not:

    - discovery
    - indexing
    - dependency resolution
    - importing
    - adapter selection
    - execution authorization
    - adapter loading
    - visibility granting
    - capability permission

Current activation entrypoint:

    onLoad(ctx)

Activation and execution are distinct.

Execution occurs only after activation when Turnix-recognized.

Execution may happen multiple times.

Execution occurs only when invoked by Turnix orchestration.

Adapter loading does not create partial activation.

Import-time execution is unsupported by Turnix guarantees.

Activation-independent library code may accept PackContext explicitly.

Authority is that of the caller, not the provider.

Provider pack activation state does not change merely because library code
accepted a caller ctx.

Last-known-good fallback is used only after activation failure, not during
dependency resolution.

Any later fallback behavior must remain explicit, trace-visible, policy-bound,
and must not become silent dependency-resolution success.


USER DECISIONS AND POLICY
=========================

Turnix does not make ambiguous decisions silently.

Turnix does not delegate authority implicitly.

Policy reduces repeated friction; it does not redefine authority.

Decision handling exists where Turnix cannot proceed safely or deterministically
on its own.

Decision authority is Kernel-mediated.

Decision-point types:

    - Resolution decisions
    - Permission decisions
    - Recovery decisions
    - Configuration-scope decisions
    - Fingerprint-mismatch decisions
    - Work-lifecycle policy decisions

Permission decisions apply only to actions that:

    - mutate persisted state
    - delete persisted state
    - intentionally cross ownership boundaries

Read access is excluded from permission decisions.

Reads either succeed or return NotFoundOrPermissionDenied.

Remembered capability permission identity uses:

    - packCanonicalId
    - exact versioned capability id

No wildcard, prefix, broader family, or versionless fallback matching exists.

Remembered fingerprint-mismatch policy is keyed by:

    - canonicalPackId
    - packVersion
    - expectedFingerprint
    - actualFingerprint

Policy evaluation order:

    1) run policy
    2) save policy
    3) global policy

Run policy overrides save policy.

Save policy overrides global policy.

Silent or implicit policy creation is forbidden.

Policy does not:

    - override ownership rules
    - bypass access levels
    - grant mutation rights forbidden by system rules
    - convert Job terminal outcomes into ordinary failures
    - treat transport timeout as Job timeout
    - treat Job timeout as transport timeout
    - silently create work
    - silently cancel work
    - silently supersede work
    - silently detach work
    - silently retain result
    - silently discard result

Decision pauses are scoped.

Decision pause does not by itself cancel, supersede, or time out a Job.

While decision is pending:

    - no persisted mutation may be committed
    - no configuration write may be finalized
    - no SavePack mutation may complete
    - affected Job or OrchestrationUnit may not silently cross the
      decision-controlled boundary

Work-lifecycle policy decisions may affect Jobs, OrchestrationUnits, RPC
request handling, scheduler work, and debugger-controlled work.

Work-lifecycle policy decisions do not define Job terminal states.

Remembered work-lifecycle policy is not keyed by jobId alone.

Policy storage location and file structure are DA-06.

Policy meaning is DA-17.


SERVICES AND CAPABILITIES
=========================

Service = runtime wiring object.

A Service is not:

    - permission layer
    - capability authority
    - adapter authority
    - PackContext authority

    - in-process adapter bypass

Job is not:

    - Promise
    - coroutine
    - callback
    - thread
    - task
    - process
    - model request
    - transport message
    - RPC request
    - capability
    - OrchestrationUnit
    - transaction
    - committed state
    - execution mechanism
    - result payload

Job states:

    - Pending
    - Running
    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

Terminal states:

    - Succeeded
    - Failed
    - Cancelled
    - TimedOut
    - Superseded

A Job reaches exactly one terminal state.

Terminal state is final.

Closed Jobs are not restarted.

Retry is new work unless a later document explicitly defines a retry
relationship.

Retry does not reuse previous jobId.

A Job result exists only for Succeeded.

Progress is observational lifecycle evidence.

Progress is not authoritative mutation.

A Job does not become committed state merely because it exists, runs, or reaches
terminal outcome.

A Job result envelope does not become authoritative committed state merely
because Job succeeded.

Cancellation, timeout, and supersession are distinct.

Transport timeout is not Job timeout.

Job timeout is not transport timeout.

Superseded is first-class terminal non-error outcome.

Late completion after terminal outcome:

    - does not change Job terminal state
    - does not produce Job result
    - does not deliver reply/result
    - may be traced as diagnostic evidence
    - may not commit new authoritative mutation after terminal transition


RPC AND TRANSPORT

Transport is concrete carrier.

WebSocket is one possible transport, not the definition of RPC.

Transport timeout does not imply Job timeout.

Job timeout does not imply transport timeout.

A request may be rejected before Job exists.

A request may be accepted as Job.

Transport failure does not by itself define Job failure, adapter failure,

Everything outside trusted backend internals should communicate with backend
internals through controlled boundaries:

    external caller

        -> RPC / interoperability boundary
        -> permission check
        -> capability / orchestration / job
        -> internal service

    - does not silently supersede Jobs

committed-state authority.

interpreted.

is active.

At most one active region exists for one AppInstance at a time.

Transport disconnect, View disconnect, Job terminal outcome, adapter failure,

CURRENT ONE-PARAGRAPH REHYDRATION
=================================

Turnix Dv3 is a runtime-domain architecture for persistent, local-first,
traceable, stateful, orchestrated AI applications. It is not merely an AppPack
runner, launcher, pack manager, catalog, plugin loader, or frontend/backend
template. Turnix runs AppInstances; AppPack is one first-class declarative way
to create one, but DA-20 currently narrows AppInstance to AppPack-backed
lifecycle and that AppPack-backing scope remains an explicit unresolved
decision. Kernel owns runtime authority, while RuntimeHost is only the running
host boundary. Trace is structured evidence, not committed state. DA-04 owns
authoritative committed-state truth through explicit transactions and commits.
DA-05 owns storage-neutral committed-value representation through immutable
ValueRefs and Chunks. DA-06 treats configuration as specialized authoritative
state under DA-04, not a separate state architecture. DA-07 centralizes
persistent I/O through IoManager; persistence protects truth but does not define
truth. Window history groups bounded runtime history and retained evidence:
SafePointWindow is committed boundary, ActiveWindow is non-authoritative
in-flight history, and AbortedWindow is non-authoritative abort evidence. DA-25
artifacts and exports package retained finalized Window material without adding
authority. DA-26 comparison, Replay, Resume, Retry, and audit workflows make
explicit workflow claims over retained artifacts; Replay restores retained
committed state and causal story but does not re-run external effects, while
Resume and Retry are new work. Discovery finds candidate pack/root material but
does not define visibility, resolution, activation, import, or runtime loading.
Visibility is enforced reference permission, not resolution, dependency
satisfaction, service access, or capability access. Resolution is deterministic
snapshot selection under one explicit context, not policy guessing or source
mixing. Importing is not activation. Dependencies are hard contracts, not
activation or advisory metadata. Activation is explicit pack-level executable
participation with PackContext authority. UI/View/frontend runtime is
presentation and interaction, not authority. Debugging is semantic, mediated,
staged, trace-visible, and cannot bypass transaction, persistence, Job,
Window, AppInstance, adapter, or policy boundaries. User decisions are
Kernel-mediated and policy reduces friction without redefining authority.
OrchestrationUnit coordinates mutation flow but cannot bypass commit. Job is an
observable lifecycle handle for requested work, not an OrchestrationUnit,
transaction, RPC request, capability, execution primitive, or committed state.
Service is runtime wiring; Capability is named, permissioned, Turnix-mediated
operation. ExecutionAdapter is the general adapter category; same-language or
same-process execution does not erase boundaries. Adapter readiness/failure/
disconnect does not silently define Job, AppInstance, RuntimeHost, Window,
transport, or committed-state outcomes. Pack-provided Python is external code.
RPC is logical communication boundary; transport is only carrier. PackManager is
the official pack-management and graph-preparation domain, but it does not
become Kernel, resolver, activator, importer, loader, capability permission,
persistence, View, AppInstance, SavePack, RuntimeHost, policy, or Turnix
identity. Turnix guarantees apply only inside Turnix-owned orchestration,
transaction, capability, persistence, policy, trace, and authority boundaries.
