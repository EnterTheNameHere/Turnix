IS document verdict:
    Keep with targeted terminology, operation-surface, source-management,
    decision-handoff, and authority-boundary fixes.

    IS-12 is a useful concrete implementation specification for PackManager
    operation request/response envelopes and operation access from RuntimeHost
    commands, RPC requests, Views, Launcher, tools, tests, and future remote
    clients. It should not be rewritten from scratch.

    Its strongest invariant is correct: entry surfaces request PackManager work
    through one mediated operation model without becoming PackManager authority.
    Operation acceptance is distinct from completion, and operation completion is
    distinct from activation success, ApplicationRun success, Job success, and
    persistence success unless an operation contract explicitly defines a
    projection.

    Required fixes are targeted: replace obsolete SavePack, AppInstance, and
    PackContext terminology; align graph-check and repair operations with
    SaveBundle / Application / ApplicationRun terminology; preserve decision
    handoff through DA-17; and keep placeholder source-management operations from
    becoming concrete package, internet, install, update, remove, verification,
    or index protocols.

==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. Correct implementation-specification scope.

    IS-12 correctly defines PackManager operation request and response envelopes,
    shared context/status fields, graph preparation, activation-plan preparation,
    graph checks, repair suggestions, graph acceptance/supersession,
    source-management placeholder surfaces, entry-surface mapping, decision
    handoff, Job-backed operation boundaries, failure categories, and trace
    correlation.

    It does not attempt to define root discovery, pack identity/visibility,
    PackRequest resolution, import/module loading, dependency semantics,
    activation lifecycle, capability execution, policy/decision semantics, Job
    lifecycle, Application/ApplicationRun lifecycle, SaveBundle binding, RPC,
    UI/View runtime, adapter authority, RuntimeHost lifecycle, PackManager
    doctrine, catalog listing envelopes, Default Launcher behavior,
    ResolvedPackGraph/ActivationPlan fields, concrete package protocols, CLI
    syntax, JSON-RPC/WebSocket fields, or browser layout.

2. Strong entry-surface unification.

    RuntimeHost commands, RPC requests, capability-mediated requests, Views,
    Launcher, tools, tests, and remote clients use the same operation semantics.

    Entry surface does not define operation authority. Different surfaces may use
    different projections, syntax, or presentation, but those differences do not
    change operation meaning.

3. Strong request/response non-authority boundary.

    The request envelope does not authorize access by itself.

    The response envelope does not grant runtime authority.

    OperationContext does not grant authority by itself.

4. Good operation status boundaries.

    Operation acceptance is distinct from operation completion.

    operationStatus is not Job terminal outcome, activation outcome, or lifecycle
    outcome. If an operation is Job-backed, Job lifecycle semantics remain owned
    by DA-19.

5. Good graph and plan operation boundaries.

    PreparePackGraph output can produce a ResolvedPackGraph, but that graph does
    not activate packs and does not guarantee activation success.

    PrepareActivationPlan output can produce an ActivationPlan, but that plan does
    not activate packs and does not guarantee activation success.

6. Good graph acceptance/supersession boundaries.

    AcceptPackGraph does not activate packs and does not write save state unless
    the owning workflow explicitly performs an authorized persistence operation.

    SupersedePackGraph records replacement but does not roll back already
    committed state.

7. Good repair suggestion boundary.

    SuggestSavePackGraphRepair produces repair suggestions and does not apply
    repair by itself. A repair suggestion is not an applied repair and does not
    mutate persistence state.

8. Good source-management placeholder boundary.

    SearchPackSources, InstallPack, UpdatePack, RemovePack, VerifyPackSource, and
    RefreshPackSourceIndex are placeholder operation surfaces. The document says
    these placeholders define operation-surface shape only and do not define
    concrete internet, index, package, verification, or installation protocols.

9. Good decision handoff.

    PackManager operations may require decisions, but DA-17 owns decision
    semantics. A decision record does not resolve itself. PackManager does not
    silently remember decisions.

10. Good Job-backed operation boundary.

    PackManager operations may be Job-backed when long-running, cancellable,
    progress-reporting, timeout-managed, or otherwise requiring Job lifecycle
    semantics. RPC request acceptance remains distinct from Job success.

11. Good trace boundary.

    PackManager operations remain trace-visible. PackManager-domain trace reasons
    are owned by DA-29. Operation trace evidence does not replace catalog,
    resolution, dependency, activation, capability, Job, RuntimeHost, persistence,
    decision, Application, or ApplicationRun evidence.

12. Good open-question discipline.

    Exact identifiers, capability identifiers, JSON Schema format, profile
    vocabularies, source-management protocol split, package source identity,
    source trust vocabulary, progress/Job handle representation, repair
    application operation, CLI syntax, RPC mapping, and View operation binding
    remain open.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. SavePack terminology is superseded by SaveBundle.

    IS-12 uses SavePack throughout:

        - CheckSavePackGraph
        - SuggestSavePackGraphRepair
        - SavePack graph checks
        - SavePack graph repair
        - SavePack visibility semantics
        - SavePack binding behavior
        - savePackId
        - includeSavePackGraphEvidence
        - savePackGraphStatus
        - SavePackGraphCheckFailed
        - CheckSavePackGraph loading or migrating SavePacks
        - selected or checked SavePack graph evidence

    Current source-stack correction:
        Proposal P02 defines SaveBundle as the durable persistence closure of one
        Application. SaveBundle is not a Pack, not Application, not
        ApplicationRun, not RuntimeHost, not live process snapshot, not arbitrary
        writable directory, not Job store, and not authority by itself.

    Required consequence for IS-12:
        Translate SavePack to SaveBundle where the meaning is durable persistence
        closure, save identity, stored graph evidence, copied/pinned retained pack
        material, compatibility evidence, repair evidence, or export/bundling
        context.

        Likely replacements:

            CheckSavePackGraph
                -> CheckSaveBundleGraph

            SuggestSavePackGraphRepair
                -> SuggestSaveBundleGraphRepair

            savePackId
                -> saveBundleId

            includeSavePackGraphEvidence
                -> includeSaveBundleGraphEvidence

            savePackGraphStatus
                -> saveBundleGraphStatus

            SavePackGraphCheckFailed
                -> SaveBundleGraphCheckFailed

        If operation names are already treated as schema vocabulary and cannot be
        renamed immediately, mark old names as compatibility aliases and define
        their current meaning through SaveBundle.

2. AppInstance terminology is superseded by Application / ApplicationRun.

    IS-12 uses AppInstance in operation completion semantics, operationContext,
    activationContext, failure/status boundaries, trace evidence, and locked
    summary.

    Current source-stack correction:
        Proposal P02 defines Application as the durable application individual and
        ApplicationRun as one live execution period of an Application.

    Required consequence for IS-12:
        Replace AppInstance with Application and/or ApplicationRun according to
        meaning.

        Likely replacements:

            appInstanceId
                -> applicationId and/or applicationRunId

            AppInstance success
                -> Application lifecycle success and/or ApplicationRun lifecycle
                   success; usually ApplicationRun when live runtime success is
                   meant

            AppInstance lifecycle outcome
                -> ApplicationRun lifecycle outcome where live operation context
                   is meant

            activationContext AppInstance
                -> Application/ApplicationRun context

3. PackContext and onLoad(ctx) terminology is superseded by ModCallContext and
   current activation-callback wording.

    IS-12 excludes activation lifecycle, onLoad(ctx), and PackContext authority.
    Current architecture replaces PackContext with ModCallContext as an
    invocation-scoped Pack-bound gateway.

    Required consequence for IS-12:
        Replace PackContext with ModCallContext or precise activation-time
        invocation-context wording.

        Replace onLoad(ctx) examples with a general stop-line:

            PackManager operation surfaces do not invoke Pack activation
            callbacks, construct ModCallContext, load executable Pack code, or
            call adapter execution entry points.

4. OperationContext must not become identity-forging authority.

    IS-12 correctly says operationContext does not grant authority by itself.

    Risk:
        Since operationContext may include runtimeHostId, workspaceId, appPackId,
        savePackId, appInstanceId, viewId, commandId, rpcMessageId,
        capabilityIdentity, jobId, and orchestrationUnitId, a caller might treat
        these IDs as authority-bearing.

    Required consequence for IS-12:
        Add a stronger anti-forgery stop-line:

            Caller-provided operationContext fields are correlation and requested
            context evidence only until validated by the receiving boundary. They
            do not let the caller forge RuntimeHost authority, workspace
            ownership, Application identity, ApplicationRun identity, SaveBundle
            identity, View authority, command authority, RPC authority, capability
            permission, Job identity, OrchestrationUnit authority, PackManager
            authority, policy approval, or persistence authority.

5. Operation completion projection needs downstream evidence guardrail.

    IS-12 says operation completion is distinct from activation success,
    AppInstance success, Job success, or persistence success unless the operation
    contract explicitly defines that relationship.

    Required consequence for IS-12:
        Translate AppInstance and preserve the projection boundary.

        A PackManager operation response may summarize downstream records, but it
        must not replace ResolvedPackGraph, ActivationPlan, Job, activation,
        adapter, RuntimeHost, ApplicationRun, persistence, decision, or trace
        evidence unless the owning document defines that projection.

6. AcceptPackGraph persistence mode can be overread as persistence authority.

    IS-12 says AcceptPackGraph records graph acceptance and does not write
    SavePack state unless the owning workflow explicitly performs an authorized
    persistence operation. Good.

    Required consequence:
        Translate SavePack to SaveBundle and preserve that AcceptPackGraph does
        not by itself persist, bind, mutate, load, migrate, activate, or publish
        state unless an owning authorized workflow does so.

7. Source-management placeholders are high-risk if over-expanded.

    Install/update/remove/verify/refresh operation surfaces are listed, but the
    document says they define shape only and do not define concrete protocols.

    Required consequence:
        Preserve and strengthen that placeholder operations do not define:

            internet access
            package registry/index protocol
            trust model
            verification protocol
            installation transaction behavior
            root write permission
            rollback semantics
            package source authenticity
            external network permission

        Source-management writes require explicit policy, permission,
        persistence, and trace handling.

8. Decision records must not self-apply or broaden authority.

    IS-12 says a decision record does not resolve itself and PackManager does not
    silently remember decisions.

    Required consequence:
        Preserve this and add if needed that decisions do not silently broaden
        scope, become remembered policy, grant capabilities, approve adapter
        execution, authorize source-management writes, or mutate persistence
        unless DA-17 and the owning operation explicitly define that effect.

9. Repair suggestions must not become applied repair or safe graph guarantees.

    IS-12 already says repair suggestion is not applied repair and does not
    mutate SavePack state.

    Required consequence:
        Translate SavePack to SaveBundle and preserve that repair suggestions do
        not make a graph safe, do not apply repair, do not mutate persistence, and
        do not bypass dependency, policy, or capability boundaries.

10. Job-backed operations need retained-result / cancellation boundary.

    IS-12 already routes Job lifecycle to DA-19.

    Required consequence:
        Preserve that PackManager operation acceptance, RPC acceptance, command
        acceptance, and Job creation are separate. Cancellation/timeout/progress
        reporting are Job-domain unless an operation contract explicitly maps
        them.

11. Trace evidence must remain evidence only.

    IS-12 already says operation trace evidence does not replace other trace
    evidence.

    Required consequence:
        Translate AppInstance to Application/ApplicationRun and preserve that
        operation trace evidence cannot replace catalog, resolution, dependency,
        activation, capability, Job, RuntimeHost, Application, ApplicationRun,
        SaveBundle, persistence, decision, or source-management evidence.

   workspace ownership, Application identity, ApplicationRun identity, SaveBundle

    catalog, resolution, dependency, activation, capability, Job, RuntimeHost,
    Application, ApplicationRun, SaveBundle, persistence, decision, or
    source-management evidence.

19. Open questions remain open unless a later authoritative source resolves them.
