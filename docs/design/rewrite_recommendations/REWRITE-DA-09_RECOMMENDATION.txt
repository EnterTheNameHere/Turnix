SUMMARY
=======

DA-09 is strong and highly Dv3-compatible.

It defines root origins, root categories, candidate roots, selected roots,
preferred roots, userdata bootstrap, saves root resolution, and discovery
boundaries.

Most importantly, DA-09 keeps discovery boring, strict, predictable, and
side-effect free.

Discovery identifies candidate pack entities inside allowed roots and
classifies them into discovered or rejected outcomes.

Discovery does not decide:

    - visibility
    - enablement
    - selector resolution
    - dependency satisfaction
    - activation
    - runtime loading
    - capability authority
    - policy outcomes beyond the root/bootstrap model defined in DA-09

This is the correct Dv3 model.

Overall recommendation:

    KEEP WITH SMALL PRECEDENCE WATCH

No heavy rewrite is recommended.

WHAT IS ALREADY NAILED
======================

DA-09 correctly defines discovery as answering:

    Where may Turnix look, which root categories may each origin contribute,
    and what discovered or rejected candidate entities may discovery
    legitimately produce?

Discovery is the stage that identifies candidate pack entities inside allowed
roots and classifies them into discovered or rejected outcomes.

Discovery also establishes candidate roots for non-pack categories such as
userdata and saves, but it does not by itself grant runtime meaning beyond the
root/bootstrap model defined by DA-09.

This is exactly the right boundary.


DISCOVERY IS NOT AUTHORITY
==========================

DA-09 correctly says discovery does not decide:

    - visibility
    - enablement
    - selector resolution
    - dependency satisfaction
    - activation
    - runtime loading
    - capability authority
    - policy outcomes beyond the root/bootstrap model defined here

This is important.

Discovery should produce boring facts and classified candidates.

Later domains decide later meanings.

Correct model:

    Discovery finds and classifies candidates.

    Indexing / visibility decide visible catalog shape.

    Resolution decides selected candidates.

    Dependency logic decides dependency satisfaction.

    Activation decides activation.

    Import/module loading decides import behavior.

    ExecutionAdapter/PackContext/capability systems decide runtime code
    participation.

    PackManager may inspect, explain, prepare, and repair graph intent, but it
    does not move this cleverness into discovery.

This should remain.


ROOT ORIGIN AND CATEGORY MODEL
==============================

DA-09 defines root origin kinds:

    - CLI root
    - ENV root
    - user-added root
    - built-in root
    - repo root
    - externally-managed content root

Root origin kind describes where a root came from.

Root origin kind does not by itself determine whether a candidate should win
later resolution.

This is correct.

DA-09 defines root categories:

    - custom/
    - first-party/
    - third-party/
    - userdata/
    - saves/

The categories have distinct semantic meaning.

userdata/ and saves/ are not content categories.

This distinction should remain.


EXTERNALLY-MANAGED CONTENT ROOTS
================================

DA-09 correctly says externally-managed content roots may contribute only
third-party.

They do not contribute:

    - custom
    - first-party
    - userdata
    - saves

This is a provenance and safety-hygiene rule, not a hard adversarial-security
guarantee.

This is good wording.

It avoids overclaiming security while preserving deterministic category
meaning.


SAVEPACK AND SAVE-LOCAL MATERIAL
================================

DA-09 correctly says SavePacks are discoverable as save entities.

SavePacks are not eligible for import as normal content-root packs.

Packs copied into a SavePack remain context-bound to that SavePack only unless
another authoritative document explicitly states otherwise.

Save-local pack material is a distinct nearer source context and precedes
ordinary content-root precedence.

Therefore custom does not override save-local pack material by default.

This is important and should remain.

It prevents the bad model:

    custom always overrides everything, including save-local material

Correct model:

    save-local material is nearer to the SavePack/AppInstance context than
    ordinary content-root precedence.


CANDIDATE / SELECTED / PREFERRED ROOTS
======================================

DA-09 correctly distinguishes:

    - candidate roots
    - selected roots
    - preferred roots

Candidate roots are known possible roots.

Selected roots are explicit user choices for active state categories.

Preferred roots are the last used usable directories for a category.

For userdata and saves:

    selected root is stronger than preferred root

    selected root expresses explicit user choice

    preferred root expresses last used usable operational target

If selected and preferred differ because the selected root became unusable and
controlled recovery used another root, the mismatch must be surfaced to the
user rather than hidden.

This is correct.

It prevents silent path substitution.


CONTENT-ROOT AGGREGATION AND PRECEDENCE
=======================================

DA-09 defines content-root precedence as:

    custom
    first-party
    third-party

This is likely correct for ordinary content-root precedence.

The rationale is also correct:

    custom supports local overrides, authoring, and experimentation

    first-party provides shipped baseline content

    third-party provides external content that does not silently replace the
    baseline merely by existing

DA-09 also says this precedence remains reused consistently across later
resolution, deterministic selection, and tie-breaking unless another
authoritative document explicitly states otherwise.

Watch item:

    This should be checked carefully against DA-11 and DA-29.

Reason:

    Discovery/root category precedence should not accidentally become universal
    runtime authority.

    Save-local material already precedes ordinary content-root precedence.

    Selected graph intent, explicit user choice, pinned SavePack graph evidence,
    and PackManager-prepared activation plans may need their own authority
    semantics.

Recommendation:

    Keep DA-09 wording for ordinary content-root precedence.

    During DA-11 / resolution audit, verify that this precedence is used as an
    input to deterministic resolution, not as a blanket rule that overrides
    save-local, selected graph, pinned, or explicit AppInstance/SavePack
    semantics.


USERDATA BOOTSTRAP
==================

DA-09 has a strong userdata bootstrap model.

userdata has exactly one active root.

CLI userdata is explicit and final.

ENV userdata is a bootstrap seed and follows normal userdata bootstrap behavior.

Redirect applies only to userdata.

Redirect may be followed once.

Only the canonical paths.config.json may define final persisted
selected/preferred userdata state.

If the active userdata root or canonical persisted path-config location becomes
unreadable or unwritable:

    - do not silently switch
    - surface the problem to the user
    - copying or migration may be offered when old userdata remains readable
    - old userdata does not remain a parallel live source
    - inability to persist the new path/config change is explicit failure of
      that persistence action rather than a reason to silently write elsewhere

This is strong and should remain.


SAVES ROOT RESOLUTION
=====================

DA-09 correctly says saves also has exactly one active writable root.

Unlike userdata, saves does not use redirect semantics.

selectedSaves is explicit selected saves root.

savesDirectoryRoots are extra candidate hints and do not imply jump by
themselves.

If selectedSaves exists but is no longer usable:

    - do not silently fall through
    - surface the problem to the user
    - allow controlled recovery or reselection through the normal centralized
      path

If previously used saves root becomes non-writable but remains readable:

    - surface the change explicitly
    - show previous saves path
    - show writable replacement if one is found
    - allow user selection of another saves root
    - continue to expose readable old saves for loading where possible

If a save is later written into the writable saves root, that writable copy
becomes the nearer source and shadows the read-only copy in later
discovery/listing.

This read-only old / writable new shadowing applies to saves only, not userdata.

This is correct.


DISCOVERY ENTRYPOINT RULES
==========================

DA-09 correctly says root directories are namespaces rather than packs.

A manifest located directly in a category root directory is ignored.

Examples:

    first-party/manifest.json5
    custom/manifest.json5
    saves/manifest.json5

This is not treated as fatal error.

Rationale:

    - roots define namespaces rather than pack identities
    - accidental global packs are prevented
    - ambiguity at root level is avoided

This is good.

It prevents accidental global behavior.


DIRECTORY SCANNING
==================

Manifest-based depth is a strong rule.

Discovery depth is defined by manifest nesting rather than raw filesystem
nesting.

Depth increases only when scanning below a discovered manifest.

This preserves nested file layouts without making raw directory depth a false
pack-depth signal.

Maximum scan depth is also good.

totalDepth <= 0 means unlimited.

totalDepth == 1 means immediate subdirectories only.

totalDepth >= 2 means exact recursion limit.

Default totalDepth = 60.

If the limit is exceeded, recursion stops for that branch and discovery
continues elsewhere.

This is not fatal by itself.

This is correct.


SYMLINK HANDLING
================

DA-09 forbids file and directory symlinks by default.

Rationale:

    - determinism
    - security boundary clarity
    - prevention of implicit graph expansion

Later policy-based relaxation may exist, but discovery behavior remains
deterministic regardless.

This is good.

It prevents a filesystem feature from silently expanding the discovery graph.


DISCOVERY OUTPUT CONTRACT
=========================

DA-09's discovery output contract is strong.

Discovery produces PackDescriptor objects in Discovered state.

Discovery classifies candidate pack entities into discovered or rejected
outcomes.

At discovery time:

    - manifest is read
    - declared fields are parsed and type-checked
    - parent relationships are established
    - packTreeId is computed
    - raw manifest data is preserved

Discovery preserves multiple distinct discovered candidates even when later
stages may determine some are equivalent.

This is useful for provenance and diagnostics.

Discovery does not:

    - determine resolution source
    - resolve visibility
    - apply user enable/disable policy
    - parse selectors
    - activate packs
    - load runtimes
    - require compilers or pack-provided providers

Discovery output remains an input to later indexing, visibility, and resolution
stages.

It is not a runtime-loaded result by itself.

This is exactly right.


MANIFESTS ARE WHOLE ARTIFACTS
=============================

DA-09 correctly says discovery treats each manifest as a whole-definition
artifact.

Duplicate manifest candidates are selected, not merged.

Duplicate manifest candidates are shadowed, not stacked.

No additive field composition across duplicate manifests occurs.

Later resolution operates on whole candidate artifacts produced by discovery,
not merged manifest fragments.

This should remain.

It preserves deterministic pack meaning and avoids the cursed “manifest soup”
model.


SAVE DISCOVERY POLICY
=====================

DA-09's save discovery model is good.

By default, Turnix scans:

    saves/*/*/manifest.json5

By default, Turnix does not recurse into SavePack directories.

By default, Turnix does not discover copied packs inside SavePacks eagerly.

Deep scanning of SavePack contents occurs only when:

    - a SavePack is explicitly loaded
    - a management surface inspects a SavePack
    - configuration explicitly enables deep save scanning

At that point:

    - copied packs may be discovered
    - visibility remains limited to SavePack context
    - copied-pack rules apply

This separation should remain locked.

It aligns well with DA-29:

    PackManager and management surfaces may inspect more deeply, but that
    helpfulness must not silently migrate into ordinary discovery.


DISCOVERY GUARANTEES
====================

DA-09 correctly says discovery is fast and side-effect free.

Discovery does not depend on pack activation.

Discovery does not require pack-provided Readers, Writers, compilers, or runtime
providers.

Heavy logic belongs to later indexing, resolution, activation, or
manager/tooling stages rather than discovery.

Discovery failures are classified rather than globally fatal unless required
core prerequisites are unavailable.

Discovery may preserve more provenance information than later deterministic
selection will use.

This is exactly the boring discovery doctrine Dv3 wants.


PACKMANAGER RELATION
====================

DA-09 correctly says PackManager and UI may be more helpful and exploratory,
but that helpfulness must not silently migrate into discovery itself.

This aligns with DA-29.

Correct relation:

    Discovery:
        strict, deterministic, side-effect-free candidate production

    PackManager:
        inspect, explain, prepare, validate, repair, and manage selected graph
        intent through explicit policy/user-mediated operations

PackManager may use discovery output.

PackManager may request explicit rescan where allowed.

PackManager may inspect SavePack contents where the management operation
permits it.

PackManager must not make ordinary discovery clever, heuristic, silently
self-repairing, or side-effectful.


TRACE WORDING
=============

DA-09 uses trace-visible and discovery-domain trace reason wording.

This should follow the DA-03 cross-document trace wording check.

Discovery trace obligations are discovery-domain emission obligations.

Trace retention and loss remain governed by DA-03.

Discovery trace evidence does not define resolution, visibility, activation, or
runtime meaning.

DA-09 already states that discovery trace evidence does not define resolution,
visibility, activation, or runtime meaning.

This is good.


NO MAJOR DV3 CONFLICT FOUND
===========================

DA-09 does not collapse discovery into:

    - visibility
    - indexing
    - resolution
    - selector parsing
    - dependency solving
    - policy authority
    - activation
    - import
    - runtime loading
    - capability authority
    - PackManager repair
    - runtime state authority

This is exactly what the document should prevent.

Keep DA-09.

    2. Trace wording:
       Follow the DA-03 cross-document trace wording check.

       Preserve the rule that PackManager/UI helpfulness must not silently

Future audits should check:

    - DA-11 resolution preserves discovery/resolution separation.

    - DA-14 activation preserves discovery/activation separation.
    - DA-17 policy preserves root/bootstrap/user-decision boundaries.
