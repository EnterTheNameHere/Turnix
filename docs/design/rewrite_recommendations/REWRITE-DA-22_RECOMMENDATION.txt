SUMMARY
=======

DA-22 is strong and Dv3-compatible.

Keep it as the UI, View, frontend runtime, presentation, interaction, frontend
adapter participation, and UI-domain trace document.

Preserve the central rule:

    UI is presentation and interaction, not authority by itself.

    View is a kernel-bound frontend runtime surface.

    Frontend runtime code is adapter-executed frontend code under DA-23.

    User interaction becomes meaningful only when Kernel accepts the
    corresponding command, decision, capability call, or RPC message.

DA-22 must not redefine:

    - RPC/channel/transport semantics
    - execution adapter boundaries
    - RuntimeHost authority
    - committed-state truth
    - importing/module-loading boundaries
    - activation lifecycle
    - service/capability/permission semantics
    - user decision and remembered policy semantics
    - debugger semantics
    - Job lifecycle
    - AppInstance lifecycle


CURRENT CLASSIFICATION
======================

KEEP WITH SMALL FRONTEND-ADAPTER TERMINOLOGY / MULTI-CLIENT WATCH

DA-22 should not be rewritten heavily.

Future edits should preserve:

    - UI as presentation and interaction, not authority
    - View as kernel-bound frontend runtime surface
    - frontend runtime code as adapter-executed code under DA-23
    - View identity distinct from AppInstance, frontend client, frontend
      adapter, and RuntimeHost identity
    - frontend interaction meaningful only after Kernel acceptance
    - frontend commands not authoritative merely because the user clicked,
      typed, dragged, confirmed, or interacted
    - frontend-side validation does not replace Kernel validation
    - frontend-side validation does not replace execution authorization,
      capability permission, or policy evaluation
    - View disconnect does not silently cancel, supersede, detach, retain, or
      discard accepted work
    - View disconnect does not silently fail frontend adapter execution
    - View disconnect does not silently stop, fail, or close RuntimeHost
    - decision presentation is not decision ownership
    - debugger UI is not debugger authority
    - presentation transforms do not mutate authoritative state by themselves
    - UI-domain trace evidence does not replace owning-domain trace evidence


PRESERVATION RULE 1: UI IS PRESENTATION AND INTERACTION, NOT AUTHORITY
=====================================================================

Preserve the core UI boundary.

UI answers:

    How does Turnix present state and decisions to users, receive interaction,
    and connect frontend surfaces to Kernel-mediated behavior without granting
    the frontend hidden authority?

UI is a presentation and interaction surface.

UI is not authoritative state by itself.

UI is not capability authority by itself.

UI is not policy authority by itself.

UI is not persistence authority by itself.

A View is a kernel-bound frontend runtime surface.

A View may present:

    - one AppInstance
    - one tool surface
    - one debugger surface
    - one management surface
    - another Kernel-recognized surface class

A View receives state and sends interaction through Turnix-mediated channels.

A View does not become authoritative merely because the user can see or interact
with it.

User interaction becomes meaningful only when Kernel accepts the corresponding:

    - command
    - decision
    - capability call
    - RPC message


PRESERVATION RULE 2: FRONTEND RUNTIME IS ADAPTER-EXECUTED CODE
==============================================================

Preserve frontend runtime authority boundaries.

Frontend runtime code is adapter-executed frontend code under DA-23.

Frontend adapter execution does not grant authority by itself.

Frontend runtime code executes as presentation and interaction logic.

Frontend runtime code does not gain direct authority over committed state.

Frontend runtime code does not mutate files directly as a Turnix authority path.

Frontend runtime code does not bypass:

    - execution adapter boundaries
    - RPC boundaries
    - capability mediation
    - policy evaluation
    - transaction boundaries
    - persistence boundaries

Frontend runtime code does not bypass RuntimeHost workspace ownership,
startup-mode, entry-surface, or command-surface boundaries under DA-28.

Frontend adapter execution authorization is distinct from capability permission
for frontend-originated requests.


PRESERVATION RULE 3: VIEW IDENTITY IS DISTINCT
==============================================

Preserve UI/View/frontend-client identity separation.

UI means the user-facing presentation and interaction layer.

View means a Kernel-recognized frontend surface with identity, lifecycle, state
delivery, and interaction routing.

Frontend client means a concrete connected client instance such as:

    - browser tab
    - embedded frontend
    - developer tool
    - future frontend host

Frontend runtime means the client-side execution environment that presents a
View and processes frontend interaction.

Frontend adapter means an ExecutionAdapter under DA-23 whose purpose is
presentation, interaction, or frontend runtime participation.

Browser JavaScript frontend runtime is one frontend adapter family.

One frontend client may bind to one View.

Multiple frontend clients may bind to one View only when the View binding model
and policy permit that behavior.

One AppInstance may have zero, one, or multiple Views depending on runtime and
policy model.

A View may exist for non-AppInstance surfaces such as:

    - launcher
    - pack manager
    - configuration editor
    - debugger
    - audit viewer
    - future management surface

View identity is distinct from AppInstance identity.

View identity is distinct from frontend client identity.

Frontend client identity is distinct from user identity.

Frontend adapter identity is distinct from View identity and frontend client
identity.

View identity is distinct from RuntimeHost identity.

Frontend client identity is distinct from RuntimeHost identity.

Concrete cookie, token, and bootstrap details belong to implementation
specifications.


PRESERVATION RULE 4: VIEW LIFECYCLE DOES NOT DEFINE OTHER LIFECYCLES
====================================================================

Preserve View lifecycle separation.

A View lifecycle has explicit observable phases.

View lifecycle phases may include:

    - created
    - bound to frontend client
    - initialized
    - ready
    - disconnected
    - reconnected
    - closed

View creation does not activate packs by itself.

View creation does not create an AppInstance by itself unless an explicit
launcher or runtime workflow defines that behavior.

RuntimeHost startup modes and entry-surface workflows are defined by DA-28.

When a View participates in a launcher or RuntimeHost entry-surface workflow,
the View lifecycle remains distinct from RuntimeHost lifecycle.

View binding associates a frontend client with a Kernel-recognized View
identity.

View readiness means the frontend can receive and process the View's expected
runtime messages.

View readiness does not imply:

    - AppInstance readiness
    - RuntimeHost readiness
    - pack activation success
    - frontend adapter execution success beyond the View readiness condition
      itself

View disconnect is a frontend or transport condition.

View disconnect does not automatically:

    - cancel Jobs
    - fail a frontend adapter
    - deactivate the AppInstance
    - stop, fail, or close a RuntimeHost
    - discard authoritative state

If View disconnect affects accepted or in-flight work, DA-17 and DA-19 govern
policy and Job lifecycle outcomes.

If View disconnect affects frontend adapter lifecycle, DA-23 governs adapter
lifecycle classification.

If View disconnect affects RuntimeHost entry-surface behavior, DA-28 governs
RuntimeHost lifecycle or host-operation classification.

View closure releases the View runtime surface.

View closure does not by itself define whether AppInstance work:

    - committed
    - aborted
    - continued
    - detached
    - retried

View closure does not by itself define RuntimeHost stop, failure, or
command-surface outcome.


PRESERVATION RULE 5: VIEW PACKS REMAIN PACKS
============================================

Preserve View pack and UI pack participation boundaries.

View packs and UI-related packs may provide:

    - frontend modules
    - components
    - layouts
    - interaction behavior

View packs remain packs.

View packs remain subject to:

    - discovery
    - identity
    - resolution
    - dependency
    - import
    - adapter selection
    - execution authorization
    - activation
    - visibility
    - capability rules

A View pack does not gain authority merely because it renders visible UI.

A View pack does not bypass turnixImport or other code-boundary rules.

JavaScript frontend code loaded for a View remains constrained by DA-12 import
and module-loading rules.

View pack activation remains constrained by DA-14.

View pack execution remains constrained by DA-23.

View pack interaction with backend behavior remains mediated through:

    - RPC
    - services
    - capabilities
    - other Turnix-defined surfaces

View pack interaction with RuntimeHost control behavior remains mediated through
DA-28-constrained entry-surface and command-surface rules.

View pack code must not assume another pack is activated merely because that
pack appears in the UI.

UI extension points are explicit.

UI extension points do not imply arbitrary mutation authority.

UI extension points do not imply RuntimeHost control authority.


PRESERVATION RULE 6: PRESENTED STATE IS NOT AUTHORITATIVE BY VISIBILITY
======================================================================

Preserve UI state, presentation state, and authoritative state separation.

UI may present:

    - state snapshots
    - deltas
    - computed projections
    - validation results
    - progress
    - diagnostics
    - decision prompts

Presented state is not authoritative merely because it is presented.

Presentation state may include:

    - selected tab
    - scroll position
    - expanded tree node
    - local filter
    - temporary draft input
    - layout size
    - frontend-only cache

Presentation state is non-authoritative unless explicitly persisted through
Turnix-managed state or configuration.

UI projections may simplify or summarize authoritative state.

UI projections do not replace the authoritative source of truth.

If a UI projection omits, filters, groups, rounds, truncates, or summarizes
state, the projection remains presentation-only.

If a presented value can become stale, the UI does not present stale data as
confirmed current truth.

Kernel remains responsible for authoritative mutation and validation of
submitted changes.

Frontend-side validation may improve user experience.

Frontend-side validation does not replace:

    - Kernel validation
    - capability permission
    - execution authorization
    - policy evaluation


PRESERVATION RULE 7: FRONTEND EVENT ORDER IS NOT COMMITTED-STATE ORDER
=====================================================================

Preserve frontend event and command flow boundaries.

Frontend interactions become Turnix-visible only when sent through a
Turnix-mediated channel.

Frontend interactions may produce:

    - RPC request
    - RPC emit
    - capability-routed request
    - decision response
    - subscription request
    - cancellation request
    - debugger command
    - configuration or management command
    - RuntimeHost entry-surface command

Kernel classifies the received interaction.

Kernel routes the interaction through the appropriate authority surface.

If the interaction invokes a capability, DA-16 governs capability mediation and
permission semantics.

If the interaction crosses an adapter boundary, DA-23 governs adapter boundary
semantics.

If the interaction answers a decision point, DA-17 governs decision handling.

If the interaction controls a Job, DA-19 governs Job lifecycle semantics.

If the interaction controls debugger behavior, DA-18 governs debugger
semantics.

If the interaction controls RuntimeHost behavior, DA-28 governs RuntimeHost
lifecycle, command-surface, entry-surface, and host-operation semantics.

If the interaction mutates committed state, DA-04 governs commit semantics.

If the interaction persists configuration, DA-06 and DA-17 govern configuration
and policy scope behavior.

UI event order does not by itself define committed-state order.

UI event order does not by itself define RuntimeHost operation order.

Committed-state order is defined by relevant Kernel-owned commit and
orchestration boundaries.

RuntimeHost operation order is defined by RuntimeHost and owning
runtime-operation rules under DA-28 and related documents.


PRESERVATION RULE 8: DECISION PRESENTATION IS NOT DECISION OWNERSHIP
====================================================================

Preserve decision presentation boundaries.

UI may present Kernel-originated decision points.

Decision presentation is not decision ownership.

DA-17 owns decision and policy semantics.

UI presents only valid options supplied or authorized by Kernel.

UI does not invent hidden defaults.

UI does not auto-confirm decisions without policy authority.

UI presents consequences, scope, and persistence effect when such information is
available.

UI preserves distinctions between:

    - allow and deny
    - for-this-run and remember
    - soft and hard decisions
    - execution authorization and capability permission
    - capability permission decisions and work-lifecycle policy decisions
    - transport timeout and Job timeout
    - transport disconnect and adapter failure
    - View disconnect and RuntimeHost stop
    - frontend command receipt and RuntimeHost command acceptance
    - cancellation and supersession
    - failure and Superseded

If multiple frontend clients present the same decision point, Kernel remains the
single arbiter of the accepted response.

A stale or already-resolved decision presentation is dismissed or marked
inactive rather than accepted again.


PRESERVATION RULE 9: DEBUGGER UI DOES NOT OWN DEBUGGER SEMANTICS
================================================================

Preserve debugger UI boundaries.

Debugger UI is a frontend surface for debugger behavior.

Debugger UI does not own debugger semantics.

DA-18 owns debugger inspection, breakpoint, pause, mutation, disconnect, and
Job-control semantics.

Debugger UI may request:

    - inspection
    - pause
    - resume
    - mutation
    - cancellation
    - supersession
    - safe-point behavior

only through Turnix-mediated channels.

Debugger UI does not directly write committed state.

Debugger UI does not directly write Job terminal state.

Debugger UI does not bypass policy decisions when policy is required.

Debugger UI does not bypass adapter boundaries when debugger UI code is
frontend adapter code.

Debugger UI distinguishes staged, committed, unavailable, and unresolved state
when those distinctions are surfaced.

Debugger UI does not present paused-at-safe-point Jobs as terminal.

Debugger UI does not present Superseded as failure.


PRESERVATION RULE 10: PRESENTATION TRANSFORMS DO NOT MUTATE AUTHORITY
=====================================================================

Preserve accessibility and presentation transform boundaries.

UI may apply presentation transforms for:

    - accessibility
    - readability
    - localization
    - scaling
    - filtering
    - grouping
    - layout

Presentation transforms are runtime presentation behavior.

Presentation transforms do not mutate authoritative state by themselves.

Presentation transforms do not change:

    - capability semantics
    - permission semantics
    - decision semantics
    - Job semantics
    - adapter semantics
    - RuntimeHost semantics
    - debugging semantics

If a presentation transform is persisted as user preference, that persistence
follows configuration and policy rules defined elsewhere.

Computed-only presentation transforms are not persisted merely because they are
visible.

UI does not silently persist computed-only presentation effects as configuration
or committed state.


PRESERVATION RULE 11: DISCONNECT AND MULTI-CLIENT BEHAVIOR ARE EXPLICIT
=======================================================================

Preserve View disconnect, reconnect, and multi-client boundaries.

A frontend client may disconnect while a View remains meaningful.

A View may reconnect when the connection model permits reconnection.

Reconnect does not imply replay of all missed frontend-local events.

Reconnect may receive:

    - fresh snapshot
    - generation update
    - retained update state
    - another implementation-defined recovery surface

Concrete reconnect flow belongs to implementation specifications.

Multi-client View behavior is explicit.

Multiple frontend clients do not create multiple authoritative truths for the
same View.

If concurrent frontend interactions conflict, Kernel resolves the conflict
through normal authority, ordering, policy, and commit rules.

View disconnect does not silently:

    - cancel accepted work
    - supersede accepted work
    - detach accepted work
    - retain accepted work
    - discard accepted work
    - fail frontend adapter execution
    - stop RuntimeHost execution
    - fail RuntimeHost execution
    - close RuntimeHost execution

Those outcomes require policy or lifecycle authority defined in the owning
documents.


PRESERVATION RULE 12: UI TRACE IS DOMAIN EVIDENCE, NOT REPLACEMENT
==================================================================

Preserve UI trace ownership.

UI and View lifecycle behavior remains trace-visible where trace evidence
exists.

UI trace evidence distinguishes:

    - View created
    - frontend client bound
    - View initialized
    - View ready
    - View disconnected
    - View reconnected
    - View closed
    - frontend command received
    - decision presented
    - decision response submitted
    - UI-originated cancellation requested
    - UI-originated debugger command requested
    - UI-originated RuntimeHost command requested

UI trace evidence records enough context, when available, to explain:

    - viewId
    - frontend client identity
    - frontend adapter identity when applicable
    - runtimeHostId when applicable
    - RuntimeHost operation identity when applicable
    - appInstanceId when applicable
    - active pack identity when applicable
    - active save identity when applicable
    - RPC message identity when applicable
    - decision identity when applicable
    - jobId when applicable
    - debugger request identity when applicable
    - command kind
    - disconnect or reconnect reason category when applicable

UI trace evidence does not replace:

    - RPC trace evidence
    - adapter trace evidence
    - decision trace evidence
    - RuntimeHost trace evidence
    - capability trace evidence
    - Job trace evidence
    - debugger trace evidence
    - AppInstance trace evidence

DA-03 defines the tracing substrate.

DA-21 defines RPC trace correlation semantics.

DA-23 defines adapter-domain trace obligations.

DA-17 defines decision trace obligations.

DA-18 defines debugger trace obligations.

DA-19 defines Job lifecycle trace obligations.

DA-20 defines AppInstance trace obligations.

DA-28 defines RuntimeHost-domain trace obligations.


PRESERVATION RULE 13: UI-DOMAIN TRACE REASONS DO NOT DEFINE OUTCOMES
====================================================================

Preserve UI-domain trace reason boundaries.

DA-22 owns UI-domain trace reason identifiers used for:

    - View lifecycle
    - frontend binding
    - frontend command receipt
    - decision presentation
    - UI-originated control requests

Current UI-domain trace reasons:

    - ViewCreated
    - ViewFrontendBound
    - ViewInitialized
    - ViewReady
    - ViewDisconnected
    - ViewReconnected
    - ViewClosed
    - UICommandReceived
    - UIDecisionPresented
    - UIDecisionResponseSubmitted
    - UICancelRequested
    - UIDebuggerCommandRequested
    - UIRuntimeHostCommandRequested

UIRuntimeHostCommandRequested does not define:

    - RuntimeHost command acceptance
    - RuntimeHost operation success
    - RuntimeHost lifecycle outcome

UI-domain trace reasons describe UI/View behavior only.

UI-domain trace reasons do not define:

    - capability outcome
    - Job terminal outcome
    - decision outcome
    - debugger outcome
    - adapter outcome
    - RuntimeHost outcome
    - committed-state mutation outcome


WATCH ITEM: FRONTEND ADAPTER TERMINOLOGY
========================================

DA-22 uses "frontend adapter" to mean an ExecutionAdapter under DA-23 whose
purpose is presentation, interaction, or frontend runtime participation.

This is acceptable.

Future rewrites should preserve the Dv3 umbrella term:

    ExecutionAdapter

and treat "frontend adapter" as a specific adapter family or role, not the
general adapter category.

Do not regress to using FrontendAdapter as the umbrella term for all adapters.


WATCH ITEM: MULTI-CLIENT VIEW SEMANTICS
=======================================

DA-22 leaves exact multi-client View behavior open.

Future implementation specifications should define:

    - whether multiple frontend clients may bind to one View
    - whether one frontend client may switch Views
    - conflict handling for concurrent frontend interactions
    - retained update behavior after reconnect
    - snapshot/generation/update recovery behavior
    - identity rules for frontend client reconnection

Preserve:

    - multiple frontend clients do not create multiple authoritative truths
    - Kernel resolves conflicts through normal authority, ordering, policy, and
      commit rules
    - reconnect does not imply replay of all missed frontend-local events
    - View disconnect does not silently decide work, adapter, AppInstance, or
      RuntimeHost outcomes


WATCH ITEM: VIEW CREATION VS APPINSTANCE CREATION
=================================================

DA-22 correctly says View creation does not create an AppInstance by itself
unless an explicit launcher or runtime workflow defines that behavior.

Future DA-20 / DA-28 / launcher specifications should preserve:

    - View creation is not AppInstance creation by default
    - RuntimeHost startup modes and entry-surface workflows are DA-28-owned
    - AppInstance creation remains Kernel-mediated
    - UI launch surfaces do not create hidden RuntimeHost startup behavior
    - UI launch surfaces do not create hidden AppInstance creation semantics


WATCH ITEM: TRACE WORDING
=========================

Follow the DA-03 cross-document trace wording check.

UI trace requirements are UI-domain emission obligations.

DA-03 owns trace substrate, retention, loss, event structure, trace DAG
semantics, span mechanics, and trace storage semantics.

Do not let UI trace wording imply that trace evidence is committed state or
that trace persistence is guaranteed forever.


REWRITE-BOUNDARY GUARDRAILS, NOT SUGGESTED DA-22 CONTENT
=========================================================

Use these as rewrite guardrails only.

Do not let frontend-only mutation become authoritative mutation.

Do not treat frontend adapter execution as authority by itself.

Do not let UI bypass execution adapter boundaries.

Do not let UI bypass RPC boundaries.

Do not let UI bypass capability mediation.

Do not let UI bypass decision handling.

Do not let UI bypass RuntimeHost workspace ownership or command-surface
semantics.

Do not let UI bypass persistence authority.

Do not let UI directly access filesystem as a Turnix authority path.

Do not let UI create hidden policy defaults.

Do not let UI create hidden activation behavior.

Do not let UI create hidden pack-loading behavior.

Do not let UI create hidden RuntimeHost startup behavior.

Do not let UI create hidden RuntimeHost command acceptance.

Do not present transport timeout as Job timeout.

Do not present Job timeout as transport timeout.

Do not present transport disconnect as adapter failure.

Do not present adapter failure as transport disconnect.

Do not present View disconnect as RuntimeHost stop.

Do not present RuntimeHost stop as View disconnect.

Do not present Superseded as failure.

Do not treat visible state as authoritative merely because it is visible.

Do not treat visible RuntimeHost control UI as RuntimeHost authority by itself.

Do not treat frontend-side validation as Kernel validation.

Do not treat frontend-side validation as capability permission.

Do not treat frontend-side validation as policy evaluation.

Do not let View packs bypass DA-12 importing or module-loading boundaries.

Do not let View packs bypass DA-14 activation boundaries.

Do not let View packs bypass DA-23 execution adapter boundaries.

Do not let UI extension points imply arbitrary mutation authority.

Do not let UI extension points imply RuntimeHost control authority.

Do not let View readiness imply AppInstance readiness.

Do not let View disconnect silently cancel, supersede, detach, retain, or

CURRENT FINAL RECOMMENDATION
============================

Keep DA-22.

No heavy rewrite is recommended.

Recommended future edits:

    - keep DA-22 focused on UI, View, frontend runtime, presentation,
      interaction, frontend adapter participation, and UI-domain trace
      semantics
    - preserve UI as presentation and interaction, not authority
    - preserve View as a Kernel-bound frontend runtime surface
    - preserve frontend runtime code as adapter-executed frontend code under
      DA-23
    - preserve frontend event flow through Kernel-mediated authority surfaces
    - preserve View identity separation from AppInstance, frontend client,
      frontend adapter, RuntimeHost, and workspace identity
    - preserve View lifecycle separation from AppInstance, Job, adapter,
      RuntimeHost, and committed-state outcomes
    - preserve decision presentation as not decision ownership
    - preserve debugger UI as not debugger authority
    - preserve frontend-side validation as UX only, not Kernel validation
    - preserve presentation transforms as non-authoritative unless explicitly
      persisted through proper configuration/state paths
    - define concrete View registry, frontend bootstrap, frontend adapter
      binding, frontend state synchronization, UI extension catalog,
      multi-client behavior, reconnect behavior, and component conventions later
      without changing these authority boundaries
