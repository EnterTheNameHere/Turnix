==============================================================================
01. VERDICT
==============================================================================

Recommendation verdict:
    Correct in substance.

    The recommendation correctly classifies DA-17 as compatible and advises a
    targeted edit, not a heavy rewrite.

Document verdict:
    Keep with targeted terminology, stop-line, and trace wording fixes.

DA-17 should remain the Kernel-mediated decision and policy-handling document.
It should define when Turnix asks the user or applies remembered policy, what
policy scopes mean, how remembered decision keys are matched, and how decision
outcomes are explained.

DA-17 should not become the owner of the domain outcomes affected by a policy
choice. It may cause, select, or remember a decision response, but the target
domain still owns the resulting domain state.

Primary required fixes:

    - preserve the central rule that Turnix does not make ambiguous decisions
      silently and does not delegate authority implicitly
    - preserve policy as friction reduction, not authority redefinition
    - strengthen the stop-line that policy does not define domain outcomes
    - replace or clarify ordinary "replayable" decision wording so it does not
      imply DA-26 Replay semantics
    - preserve the DA-06 / DA-17 split: DA-06 owns policy storage placement and
      top-level persisted file structure; DA-17 owns decision meaning and
      remembered-policy semantics
    - preserve exact capability permission keying
    - preserve exact fingerprint mismatch keying
    - preserve work-lifecycle policy separation from Job, RPC, OrchestrationUnit,
      adapter, RuntimeHost, Application/ApplicationRun, Window, PackManager,
      Replay, Resume, Retry, artifact/export, audit workflow, and committed-state
      outcome semantics
    - preserve no-prompt-for-read-access rule
    - preserve frontend presentation only; Kernel remains arbiter
    - preserve mod/pack trigger-but-not-handle boundary
    - translate AppInstance and SavePack wording to Application/ApplicationRun and
      SaveBundle terminology where appropriate
    - normalize Orchestration Unit to OrchestrationUnit
    - add or update owner references for DA-21, DA-22, DA-24, DA-25, DA-26,
      DA-27, DA-28, and DA-29 where relevant
    - adjust trace wording so explanations derive from retained trace/policy
      evidence where retained evidence exists; DA-03 owns trace substrate,
      retention, loss, trace DAG, and span semantics
    - clean up local numbering gaps and repeated subsection numbering where stable
      references matter
    - avoid final-document rewrite/process metadata leakage

Primary conclusion:
    Keep DA-17. The work is boundary tightening and terminology modernization,
    not conceptual replacement.

==============================================================================
01A. OBSOLETE-PRESERVATION CHECK
==============================================================================

DA-17 should not preserve older terms merely because they appear in older source
material or recommendation text.

Specifically, the rewrite should not preserve as current terminology:

    - AppInstance where Application or ApplicationRun is meant
    - appInstanceId where applicationId or applicationRunId is meant
    - SavePack where SaveBundle is meant
    - SavePack fingerprint mismatch where SaveBundle-local retained Pack material
      or SaveBundle-associated expected fingerprint is meant
    - Orchestration Unit with a space where the canonical concept is
      OrchestrationUnit
    - RPC transport ownership through IS-01 / IS-02 only if DA-21 is the current
      DA-level owner
    - ordinary "replayable" wording for decision traceability where DA-26 Replay
      is not meant
    - trace explanation wording that implies trace retention is guaranteed forever
    - policy records as hidden authority merely because they are persisted
    - policy storage location as policy meaning
    - policy scope as ownership authority
    - work-lifecycle policy as Job lifecycle state authority
    - frontend presentation as decision authority
    - mod/pack trigger ability as decision-handling authority

Canonical translations:

    AppInstance -> ApplicationRun where one live execution/incarnation is meant
    AppInstance -> Application where durable Application identity is meant
    appInstanceId -> applicationRunId where live execution identity is meant
    appInstanceId -> applicationId only where durable Application identity is meant
    SavePack -> SaveBundle where durable persistence closure is meant
    SavePack-local -> SaveBundle-local where persistent closure scope is meant
    Orchestration Unit -> OrchestrationUnit
    replayable -> auditable / explainable from retained evidence, unless DA-26
        Replay is explicitly meant

Important clarification:
    DA-17 already contains several modern boundaries. Do not rewrite those away.
    The necessary edit is to remove remaining stale terms and make owner
    stop-lines explicit.

==============================================================================
01B. DOCUMENT-METADATA LEAKAGE CHECK
==============================================================================

The final DA-17 document should read as architecture documentation, not as audit,
version, or rewrite-process metadata.

Do not include statements such as:

    - This is V3 design.
    - In V3, policy no longer defines outcomes.
    - The audit decided to replace replayable.
    - The recommendation says to keep DA-17.
    - This rewrite adds DA-24 and DA-29 stop-lines.
    - Codex preserved stale AppInstance wording.

Those facts may be useful in audit files, migration notes, compatibility notes,
branch notes, changelogs, or explicitly historical documents. They do not belong
in the architecture document itself.

The final DA-17 should simply define Turnix decision and policy semantics.

==============================================================================
02. WHAT DA-17 GETS RIGHT
==============================================================================

02.1. Core intent is strong
--------------------------

DA-17 correctly says Turnix does not make ambiguous decisions silently and does
not delegate authority implicitly.

Preserve this as the central doctrine.

02.2. Decision handling is correctly Kernel-mediated
----------------------------------------------------

DA-17 correctly defines user interaction as a Kernel-mediated system concern,
not UI-specific, mod-specific, or frontend-specific.

Preserve this.

02.3. Decision types are usefully distinct
------------------------------------------

DA-17 correctly separates resolution, permission, recovery,
configuration-scope, fingerprint-mismatch, and work-lifecycle policy decisions.

Preserve separate decision classes. Do not collapse them into a generic prompt
model.

02.4. Permission decisions are correctly not read prompts
--------------------------------------------------------

DA-17 correctly says permission decisions apply to mutation, deletion, and
intentional ownership-boundary crossing, but not to read access. Reads either
succeed or return NotFoundOrPermissionDenied.

Preserve this strongly.

02.5. Capability permission keys are correctly exact
---------------------------------------------------

DA-17 correctly keys remembered capability permission by packCanonicalId and the
exact versioned capability id. It correctly forbids wildcard, prefix, family, and
versionless fallback lookup.

Preserve this.

02.6. Fingerprint mismatch keys are correctly exact
--------------------------------------------------

DA-17 correctly keys fingerprint mismatch by canonicalPackId, packVersion,
expectedFingerprint, and actualFingerprint. It correctly says origin alone is not
authenticity proof.

Preserve this.

02.7. Policy scope precedence is strong
---------------------------------------

DA-17 correctly evaluates policy in run, save, then global order. Run overrides
save, and save overrides global.

Preserve this, translating save-scope to SaveBundle-related terminology where
needed without changing the policy precedence model.

02.8. Work-lifecycle policy separation is strong
------------------------------------------------

DA-17 correctly says work-lifecycle decisions are distinct and are not keyed by
jobId alone.

Preserve this, but update owner references and stale terminology.

02.9. Frontend responsibility is correctly presentational
--------------------------------------------------------

DA-17 correctly says frontends present explanation, consequences, scope, and
valid choices. Frontends do not invent defaults, auto-confirm without policy, or
bypass Kernel authority.

Preserve this.

02.10. Decision failure behavior is safe
----------------------------------------

DA-17 correctly says decision handler failure aborts safely, trace-logs failure,
and leaves persisted state unchanged.

Preserve this.

==============================================================================
03. REQUIRED FIX: POLICY DOES NOT DEFINE DOMAIN OUTCOMES
==============================================================================

DA-17 already contains a compact statement that remembered policy reduces
friction and does not define domain outcomes, committed state, Job outcomes,
Window outcomes, Replay, Resume, Retry, artifact export, or audit workflow
results.

Keep and strengthen it.

Recommended source-level boundary:

    Policy decisions choose allowed responses where Turnix cannot safely or
    deterministically proceed on its own.

    Policy does not redefine authority.

    Policy does not directly define Job terminal states, RPC/transport outcomes,
    OrchestrationUnit terminal outcomes, Application/ApplicationRun lifecycle,
    adapter lifecycle, RuntimeHost lifecycle, Window finalization, PackManager
    operation outcomes, Replay / Resume / Retry workflow outcomes,
    artifact/export authority, capability permission, or committed-state truth.

    If a policy decision affects another domain, the owning domain defines the
    resulting domain outcome.

    Correlation between a policy decision and a domain outcome must be explicit.

Reason:
    DA-17 owns decision and remembered-policy semantics. Owning domain documents
    own their outcomes.

==============================================================================
04. REQUIRED FIX: REPLACE OR CLARIFY ORDINARY "REPLAYABLE" WORDING
==============================================================================

If DA-17 says decisions are "replayable," rewrite or qualify that wording.

Reason:
    DA-26 gives Replay a formal meaning. DA-17 decision traceability does not
    imply DA-26 Replay, Resume, Retry, deterministic re-execution, comparison
    success, or audit workflow success.

Preferred replacement:

    All decisions remain traceable and attributable. Retained decision evidence
    may support audit, explanation, and offline inspection where retained evidence
    exists, but decision traceability does not imply DA-26 Replay, Resume, Retry,
    or deterministic re-execution.

Alternative:

    All decisions remain:
        - traceable
        - attributable
        - auditable from retained decision evidence where retained evidence exists
        - explainable from retained trace and policy records where retained
          evidence exists

Do not use bare "replayable" unless DA-26 Replay is explicitly meant.

==============================================================================
05. REQUIRED FIX: DA-06 STORAGE IS NOT DA-17 POLICY MEANING
==============================================================================

DA-17 already says DA-06 owns policy storage location and top-level persistent
file structure, while DA-17 owns decision semantics and remembered-policy
meaning.

Preserve and make this split explicit in the policy persistence section.

Recommended wording:

    Policy storage location and top-level persisted file structure are defined by
    DA-06.

    Decision meaning, remembered-policy matching, policy scope precedence,
    permission policy keys, fingerprint policy keys, and work-lifecycle policy
    semantics are defined by DA-17.

    Storing a policy record does not by itself create a valid policy outcome
    outside DA-17 semantics.

This prevents policies.config.json placement from becoming hidden policy
authority by file placement alone.

==============================================================================
06. REQUIRED FIX: WORK-LIFECYCLE POLICY OWNER STOP-LINES
==============================================================================

DA-17 correctly defines work-lifecycle policy decisions, but it should avoid
becoming owner of every domain named by those decisions.

Add or preserve owner stop-lines:

    DA-18:
        debugger pause, breakpoint, and execution-control behavior

    DA-19:
        Job lifecycle states, terminal outcomes, cancellation, timeout,
        supersession, progress, result, and late completion semantics

    DA-21:
        RPC, RPCChannel, transport, timeout, disconnect, cancellation message,
        and acknowledgement semantics

    DA-22:
        UI, View, frontend runtime, frontend presentation, frontend disconnect,
        and multi-client presentation semantics

    DA-24:
        OrchestrationUnit lifecycle, mutation authority, and terminal outcomes

    DA-25:
        Window artifacts, WindowManifests, WindowExports, Minimal Audit Bundles,
        optional digest representation, partial export, missing material, and
        offline inspection artifact semantics

    DA-26:
        comparison, ComparisonResult, Replay, Resume, Retry, and audit workflow
        semantics

    DA-27:
        adapter lifecycle, trust, isolation, failure, disconnect, and
        adapter-domain trace semantics

    DA-28:
        RuntimeHost lifecycle, startup modes, command surfaces, workspace
        ownership, local-first, and LAN exposure semantics

    DA-29:
        PackManager catalog, graph-preparation, repair, View, write, and
        PackManager-domain trace semantics

Recommended boundary wording:

    Work-lifecycle policy decisions may choose a permitted response to a
    lifecycle-relevant condition.

    The owning lifecycle or workflow document defines the resulting domain
    outcome.

    A remembered policy that applies to cancellation does not imply a remembered
    policy that applies to supersession, timeout, disconnect, detachment, result
    retention, result discard, adapter failure, RuntimeHost failure, Window
    finalization, Replay, Resume, or Retry.

==============================================================================
07. REQUIRED FIX: APPLICATION / APPLICATIONRUN / SAVEBUNDLE TERMINOLOGY
==============================================================================

DA-17 still uses AppInstance and SavePack in several places.

Translate according to meaning:

    AppInstance -> ApplicationRun
        where one live runtime incarnation / current work owner is meant

    AppInstance -> Application
        where durable application identity is meant

    AppInstance lifecycle -> Application/ApplicationRun lifecycle
        if both durable and live identity domains are involved

    SavePack -> SaveBundle
        where durable persistence closure is meant

    SavePack fingerprint mismatch -> SaveBundle-associated expected fingerprint
        mismatch, or SaveBundle-local retained Pack fingerprint mismatch, depending
        on the intended meaning

Do not expand DA-17 into Application/ApplicationRun/SaveBundle lifecycle. DA-20
and SaveBundle-owner documents own those meanings.

==============================================================================
08. REQUIRED FIX: TRACE WORDING
==============================================================================

DA-17 correctly says decisions emit trace events and explanations derive from
trace data.

Refine this so DA-17 does not imply trace retention, trace substrate ownership, or
invented rationale.

Recommended wording:

    Decision trace requirements are decision-domain emission obligations.

    DA-03 owns trace substrate, retention, loss, trace DAG, event structure, and
    span semantics.

    User-facing explanations are derived from retained trace and policy evidence
    where retained evidence exists.

    User-facing surfaces do not invent rationale.

    Trace evidence is not committed state.

    Trace loss does not redefine committed-state truth.

This keeps DA-17 in its decision-domain trace lane.

==============================================================================
09. REQUIRED FIX: FRONTEND / DA-22 BOUNDARY
==============================================================================

DA-17 should continue to own decision semantics, while DA-22 owns UI, View,
frontend runtime, frontend presentation, frontend disconnect, and multi-client
presentation semantics.

Recommended local wording:

    Frontends present decisions and collect valid responses.

    The Kernel remains the decision arbiter.

    Frontend presentation state is not policy state.

    DA-22 owns the UI and frontend runtime mechanics of presenting and dismissing
    decision surfaces.

This preserves DA-17 as decision-semantics owner without taking over UI
implementation semantics.

==============================================================================
10. REQUIRED FIX: MOD / PACK BOUNDARY
==============================================================================

DA-17 should preserve:

    - mods and packs may trigger decision points
    - mods and packs do not handle decisions directly
    - mods and packs do not block while awaiting frontend interaction
    - mods and packs do not invent policy defaults
    - mods and packs do not persist policy decisions directly
    - mods and packs observe outcomes only through Turnix-provided context and
      results

Add DA-30 visibility only if ModCallContext is directly mentioned. Otherwise,
keep this at the Turnix-provided context/results level.

==============================================================================
11. REQUIRED FIX: CROSS-SCOPE COPY AND PROMOTION REMAIN OPEN
==============================================================================

DA-17 accepts cross-scope copy and promotion conceptually but leaves exact API and
interaction model open.

Preserve these constraints:

    - computed-only or derived values are rejected cleanly
    - owner-domain boundaries may impose additional permission checks
    - overwrite and conflict behavior must be explicit
    - source-layer removal vs preservation must be explicit
    - batching must define atomicity
    - trace shape must distinguish copy, promotion, overwrite, refusal, discard,
      and conflict outcomes
    - policy remembering for copy/promotion must not silently broaden authority

Do not introduce implicit promotion or hidden cross-scope copying.

==============================================================================
12. REQUIRED FIX: LOCAL NUMBERING / REFERENCE CLEANUP
==============================================================================

DA-17 currently has local numbering issues that can affect stable reference use:

    - section 02 jumps from 02.9 to 02.12 and 02.13
    - section 04 has both 04.1 decision type list and 04.1 resolution decision
      subsection
    - section 05 has both 05.1 soft decision heading and related nested numbering

Normalize numbering without changing architecture meaning.

This is not a heavy conceptual rewrite, but stable references matter in design
area documents.

==============================================================================
13. WHAT TO PRESERVE FROM CURRENT DA-17
==============================================================================

Preserve these boundaries, translating stale terminology where needed:

    - Turnix does not make ambiguous decisions silently
    - Turnix does not delegate authority implicitly
    - later behavior remains deterministic within the decision scope
    - user interaction exists only when Turnix cannot proceed safely or
      deterministically on its own
    - decisions affecting identity, persistence, authority, safety, work
      lifecycle, or known content equivalence remain explicit and trace-backed
    - policy does not silently create, cancel, supersede, detach, retain, or
      discard work
    - policy does not define domain outcomes
    - DA-06 owns storage location and top-level persistent file structure
    - DA-17 owns decision semantics and remembered-policy meaning
    - user interaction is Kernel-mediated
    - mods and packs may trigger but do not own decisions
    - decision types remain distinct
    - reads are not prompted
    - capability permission keys use packCanonicalId and exact versioned
      capability id
    - no wildcard, prefix, broader family, or versionless capability lookup
    - fingerprint mismatch decisions use exact mismatch pairs
    - origin alone is not authenticity proof
    - run policy overrides save policy and save policy overrides global policy
    - run policy is memory-only
    - persisted policies are explicit, inspectable, and editable through Turnix
      management surfaces
    - work-lifecycle policies are distinct from permission and fingerprint
      policies
    - work-lifecycle policy is not keyed by jobId alone
    - trace evidence records decision type, trigger, scope, options, outcome, and
      policy involvement
    - user-facing surfaces do not invent rationale
    - frontends present only valid choices and do not auto-confirm without policy
    - first valid frontend response wins when multiple frontends are connected
    - decision-handler failure aborts safely and leaves persisted state unchanged
    - disconnect handling does not silently cancel, supersede, detach, retain, or
      discard a Job without explicit policy
    - cross-scope copy/promotion remains open and must not broaden authority
      implicitly

16. FINAL EDITOR INSTRUCTION
==============================================================================

Keep DA-17.

Do not perform a heavy conceptual rewrite.

Make targeted edits:

    - keep DA-17 focused on Kernel-mediated decision and policy handling
    - preserve exact remembered permission and fingerprint policy keys
    - preserve no-prompt-for-read-access rule
    - preserve frontend-as-presentation-only rule
    - preserve mod/pack trigger-but-not-handle rule
    - preserve policy scope precedence: run, save, global
    - preserve policy storage/semantics split with DA-06
    - preserve work-lifecycle policy separation from Job lifecycle, RPC transport,
      OrchestrationUnit lifecycle, adapter lifecycle, RuntimeHost lifecycle,
      Application/ApplicationRun lifecycle, Window finalization, PackManager
      operation, Replay, Resume, Retry, artifact/export, audit workflow, and
      committed-state semantics
    - replace or clarify ordinary "replayable" decision wording so it does not
      imply DA-26 Replay semantics
    - translate AppInstance / appInstanceId to ApplicationRun / applicationRunId or
      Application / applicationId where appropriate
    - translate SavePack wording to SaveBundle wording where durable persistence
      closure is meant
    - normalize OrchestrationUnit terminology
    - update owner stop-lines for DA-21, DA-22, DA-24, DA-25, DA-26, DA-27,
      DA-28, and DA-29 where relevant
    - refine trace explanation wording so DA-03 remains trace substrate,
      retention, loss, trace DAG, and span owner
    - normalize numbering gaps and duplicate local subsection numbering

Do not include audit/source metadata or version/process framing in the final
DA-17 documentation. The final DA-17 should not say this is V3 design, in V3,
new design, old design, rewritten design, created by Codex, decided by audit, or
part of a rewrite-history process.

DA-17 should remain the Kernel-mediated user-decision, policy precedence,
policy persistence, remembered permission, fingerprint mismatch, work-lifecycle
policy, frontend-presentation, and decision-domain trace document.

DA-17 should not become:

    - committed-state truth specification
    - persistent-I/O authority specification
    - configuration storage placement specification
    - Window finalization specification
    - Job lifecycle or terminal-state specification
    - RPC/transport specification
    - UI/View/frontend runtime specification
    - adapter lifecycle/trust/isolation specification
    - RuntimeHost workspace/command-surface specification
    - PackManager operation-outcome specification
    - artifact/export specification
    - comparison / Replay / Resume / Retry / audit workflow specification
    - Application/ApplicationRun lifecycle specification

The main work is to preserve DA-17's decision and remembered-policy boundaries
while removing stale terminology and preventing policy from silently becoming
cross-domain authority.
