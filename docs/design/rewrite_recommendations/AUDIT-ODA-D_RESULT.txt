==============================================================================
SUMMARY
==============================================================================

ODA-D contains a useful practical compatibility idea: Turnix should prefer
reproducibility, reversibility, and explicit uncertainty over pretending that
compatibility can always be proven in advance.

The three-way split between hard compatibility, soft compatibility, and
capability compatibility is worth preserving. The document also correctly says
that adapter compatibility declarations do not prove safe execution and that
capability compatibility declarations do not grant capability permission.

The main issue is that ODA-D is still centered on the older SavePack and
AppInstance model. Current architecture uses Application, ApplicationRun,
SaveBundle, AppPack/AppDefinition, accepted Pack graph, and SaveBundle
generations. The final rewrite should preserve the compatibility-contract idea
but re-anchor it in the current persistence and runtime-identity model.

==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. The practical baseline is sound.

    Reproducibility, reversibility, and explicit uncertainty are the right
    low-burden foundation for compatibility tooling. The document correctly avoids
    claiming that author declarations can prove broad compatibility.

2. The compatibility split is useful.

    Hard compatibility, soft compatibility, and capability compatibility describe
    different classes of information and should remain separated.

3. Hard compatibility is correctly non-negotiable within this optional model.

    If a required engine/API/adapter/runtime boundary is outside the accepted
    range, loading should be blocked rather than converted into a vague warning.

4. Soft compatibility is correctly informational.

    Tested-with declarations can improve diagnostics without forcing authors to
    republish just to silence warnings.

5. Capability compatibility is correctly separated from permission.

    A pack declaring that it relies on a capability does not receive capability
    permission merely by declaring that reliance.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. SavePack is obsolete as the central persistence term.

    The current model uses SaveBundle as the durable persistence closure of one
    Application. SaveBundle preserves applicationId, AppDefinition/AppPack
    binding, accepted concrete Pack graph, committed state, save-bound
    configuration and policy, retained finalized history, retained trace/journal
    evidence, and published generations.

    ODA-D repeatedly uses SavePack as the source-of-truth concept, including:

        - SavePack pinning as deterministic source of truth
        - SavePack pins exact pack versions
        - updates do not overwrite a SavePack
        - a SavePack loads with pinned versions
        - SavePacks do not auto-update packs by default
        - SavePack behavior remains deterministic
        - versions referenced by any SavePack are not deleted
        - SavePack identity versus AppInstance identity
        - multi-writer SavePack mutation

    Required correction:
        Replace SavePack with SaveBundle where durable persistence closure is
        meant.

    Suggested local model:
        SaveBundle records the accepted concrete Pack graph and exact Pack
        bindings for each published generation. Loading a SaveBundle restores
        from a published generation and creates a new ApplicationRun of the same
        Application.

2. AppInstance is obsolete as the current primary runtime identity term.

    ODA-D uses AppInstance for lifecycle semantics, running updates, identity,
    subordinate documents, and higher-document ownership. Current terminology
    should use Application for durable identity and ApplicationRun for live
    execution.

    Required correction:
        Replace AppInstance with Application/ApplicationRun according to meaning.

    Suggested replacements:

        Updating a pack does not silently change an already running AppInstance.

    should become:

        Updating a Pack does not silently change an already running
        ApplicationRun or the accepted Pack graph of an already published
        SaveBundle generation.

    and:

        DA-20 owns AppInstance runtime identity.

    should become:

        The current lifecycle/runtime-identity design owns Application and
        ApplicationRun identity.

3. "Source of truth" wording must not make SaveBundle override domain ownership.

    ODA-D says SavePack pinning is a deterministic source-of-truth concept. In
    the current model, SaveBundle is a persistence carrier and published
    generation head, but it does not replace semantic ownership of Memory,
    configuration, policy, trace, Pack graph, migration, or Application lifecycle
    domains.

    Required correction:
        Say SaveBundle published generations preserve the accepted concrete Pack
        graph and exact version/fingerprint bindings used for restoration. Do not
        say the SaveBundle is the sole truth for all related semantics.

4. Compatibility declarations must not become dependency, resolution, activation,
   adapter, or permission authority.

    The document already says it does not define dependency semantics, generic
    resolution, activation, or adapter semantics. Preserve that. Also strengthen
    the local language so compatibility fields do not silently become hard
    dependencies, visibility grants, import grants, adapter execution grants,
    capability permissions, or policy decisions.

    Required correction:
        Compatibility declarations are inputs to validation, diagnostics, graph
        preparation, and policy/user decision surfaces where owning documents
        allow them. They do not replace DA-11, DA-13, DA-14, DA-16, DA-23, or the
        current Application/SaveBundle model.

5. "The pack does not load" is too broad for hard compatibility.

    Section 04.1 says if hard compatibility fails, the pack does not load. That
    is directionally correct, but the final wording should distinguish discovery,
    graph selection, import/module loading, activation-entry loading, and Pack
    activation.

    Required correction:
        Say hard compatibility failure blocks inclusion in the accepted runtime
        graph or blocks activation/loading at the owning boundary, depending on
        when the failure is detected. Do not use "load" as a catch-all for
        discovery, resolution, import, adapter loading, and activation.

6. Rolling profiles must not mutate already-published generations.

    The document says global rolling profiles may exist and SavePack behavior
    remains deterministic within that rolling-profile environment. Current
    SaveBundle generation semantics require immutable published generations.

    Required correction:
        If rolling profiles remain, they may affect future graph preparation or
        future SaveBundle generations. They do not rewrite already-published
        generations and do not silently change an active ApplicationRun.

7. Storage cleanup must align with SaveBundle generations and retained material.

    Section 07 says versions referenced by any SavePack are not deleted and
    unreferenced versions may be deleted by policy. The current model needs this
    in terms of SaveBundle published generations, copied or pinned Pack material,
    accepted graph evidence, and retained material required for restoration or
    audit.

    Required correction:
        Cleanup may remove only material that is not required by retained
        published generations, accepted graph evidence, explicit pins, retained
        compatibility policy, or other owning-domain retention rules.

==============================================================================
OBSOLETE-PRESERVATION RISKS
==============================================================================

The main obsolete-preservation risk is preserving SavePack/AppInstance as the
center of the compatibility model.

Do not preserve these terms as current architecture merely because the ODA source
uses them. Translate into the current model:

    AppPack / AppDefinition
        reusable application definition or accepted application-definition source

    Application
        durable application individual

    ApplicationRun
        one live execution period of that Application

    SaveBundle
        durable persistence closure of the Application

    SaveBundle generation
        immutable published restoration head containing accepted graph and
        retained state/evidence roots

For ODA-D, the most important rewrite move is not to delete the compatibility
model. It is to move the model from SavePack/AppInstance language into
SaveBundle/Application/ApplicationRun language.

    Replace:

    With:

        Updating a Pack does not silently change an already running

Fix 6: Align rolling profiles with immutable generations.

Fix 7: Align storage cleanup with retained restoration material.

    10. Relation to Higher Documents

==============================================================================
ACCEPTANCE CONDITIONS FOR THE FINAL ODA-D REWRITE
==============================================================================

The final rewritten ODA-D is acceptable when:

    - it no longer uses SavePack as the current persistence model
    - it no longer uses AppInstance as the current primary runtime identity term
    - it uses SaveBundle, SaveBundle generation, Application, ApplicationRun,
      AppPack/AppDefinition, and accepted Pack graph correctly
    - it preserves the hard / soft / capability compatibility split
    - it preserves the baseline of reproducibility, reversibility, and explicit
      uncertainty
    - it does not imply compatibility declarations prove safe execution
    - it does not imply adapter compatibility declarations grant adapter authority
    - it does not imply capability compatibility declarations grant capability
      permission
    - it does not use "load" as a catch-all for discovery, resolution, import,
      adapter loading, and activation
    - it does not let rolling-profile behavior rewrite already-published
      SaveBundle generations or silently change an active ApplicationRun
    - it does not let cleanup delete material required by retained published
      generations, accepted graph evidence, explicit pins, or retention policy
    - it contains no rewrite/history/Codex/process framing as final architecture
      text

==============================================================================
FINAL EDITOR INSTRUCTION
==============================================================================

Keep ODA-D, but perform a stronger model-alignment pass than ODA-B or ODA-C. The
compatibility-contract idea is useful and should not be discarded. The rewrite
should preserve the three-way compatibility split and the practical baseline of
reproducibility, reversibility, and explicit uncertainty, while replacing the old
SavePack/AppInstance center with SaveBundle, SaveBundle generations,
Application, ApplicationRun, and accepted Pack graph terminology.
