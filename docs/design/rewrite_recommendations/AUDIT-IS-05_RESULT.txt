    Keep with targeted terminology, mode-result, and authority-boundary fixes.

    IS-05 is a useful concrete implementation specification for RuntimeHost

==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. Correct implementation-specification scope.

    IS-05 correctly defines concrete startup-mode behavior and leaves
    RuntimeHost, Kernel authority, committed state, persistence, Application /
    ApplicationRun lifecycle, RPC, View, adapter authority, OrchestrationUnit,
    workspace ownership, command-surface flow, shell syntax, launcher behavior,
    terminal rendering, LAN pairing, and authentication to owning documents.

2. Strong shared-operation invariant.

    The document correctly states that startup mode selection determines how
    Turnix is entered, but does not define separate runtime semantics.

    Startup modes are treated as entry workflows over shared Kernel-mediated
    runtime operations.

3. Good mode-category discipline.

    startupMode values are semantic categories, not final CLI names, flags,
    desktop launcher actions, or service-wrapper names.

4. Good normalization boundary.

    Startup request normalization captures invocation and requested-mode data but
    does not grant authority, acquire workspace ownership, create a RuntimeHost,
    or create an AppInstance.

    This boundary should be preserved, with AppInstance translated to the current
    Application / ApplicationRun model.

5. Good workspace ownership separation.

    Startup modes that require writable workspace ownership use IS-03. Connect
    mode and read-only inspection modes avoid writable ownership unless the
    request explicitly permits the necessary behavior.

    The document correctly forbids silent fallback from connect mode to a new
    writable host and silent stale-owner takeover.

6. Good command-surface separation.

    Startup modes that receive or dispatch commands use IS-04. Startup mode
    selection is not command acceptance, command acceptance is not startup mode
    success, and startup readiness is not command success.

7. Good mode-specific safety boundaries.

    serve mode does not silently expose internet-accessible runtime control
    surfaces.

    test mode may bypass human prompts only with explicit policy or decision
    fixtures, and those fixtures do not become production defaults.

    launcher mode does not make browser frontend state authoritative.

8. Good startup-result projection boundary.

    oneShotCommand mode may project command result status into startup result
    status only as an explicit startup-mode surface, while the underlying command
    result remains command-domain evidence under IS-04.

9. Good trace/evidence separation.

    Startup mode trace evidence does not replace RuntimeHost lifecycle,
    workspace ownership, command, AppInstance, Job, adapter, RPC, UI,
    OrchestrationUnit, transaction, or Window evidence.

    This should be preserved with AppInstance translated to current terms.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. AppInstance terminology is superseded by Application / ApplicationRun.

    IS-05 still uses AppInstance in several places:

        - startup modes must not create separate AppInstance semantics
        - AppInstance lifecycle or runtime identity semantics
        - startup mode success is not AppInstance success
        - startupRequestId is distinct from appInstanceId
        - normalization does not create an AppInstance
        - startup mode that creates or starts an AppInstance uses DA-20
        - interactiveHost / serve readiness does not imply AppInstance readiness
        - launcher mode does not create AppInstance semantics
        - startup result envelope carries appInstanceId
        - startupStatus does not redefine AppInstance lifecycle outcome
        - trace context includes appInstanceId
        - startup trace evidence does not replace AppInstance evidence
        - unsupported list and locked summary use AppInstance

    Current source-stack correction:
        Proposal P02 defines:

            Application
                durable application individual

            ApplicationRun
                one live execution period of an Application

    Required consequence for IS-05:
        Replace AppInstance with Application and/or ApplicationRun according to
        local meaning.

        Likely translation:

            appInstanceId
                -> applicationId and/or applicationRunId

            AppInstance success
                -> Application creation success and/or ApplicationRun start
                   success, depending on the mode contract

            AppInstance readiness
                -> ApplicationRun readiness when live execution is meant

            AppInstance lifecycle outcome
                -> ApplicationRun lifecycle outcome when live execution is meant

            AppInstance runtime identity
                -> Application identity and ApplicationRun identity

2. SavePack terminology is superseded by SaveBundle.

    IS-05 uses SavePack in the purpose section, test mode, launcher mode, and
    unsupported/locked summary sections.

    Current source-stack correction:
        Proposal P02 defines SaveBundle as the durable persistence closure of one
        Application. SaveBundle is not a Pack, not an Application, not an
        ApplicationRun, not a RuntimeHost, not a live process snapshot, not a Job
        store, and not authority by itself.

    Required consequence for IS-05:
        Replace SavePack with SaveBundle.

        Do not let startup mode naming imply that SaveBundle is a Pack or that
        startup mode defines separate SaveBundle semantics.

3. Shared startup operation list still contains AppInstance operation wording.

    Section 05 says a startup mode that creates or starts an AppInstance uses
    DA-20.

    Required consequence for IS-05:
        Recast this as Application / ApplicationRun lifecycle behavior.

        Safer wording:

            A startup mode that creates an Application, loads a SaveBundle,
            creates an ApplicationRun, or starts an ApplicationRun follows the
            owning lifecycle and persistence documents.

        If exact operation names are mentioned later, use current names such as:

            CreateApplication
            LoadSaveBundle
            CreateApplicationRun
            StartApplicationRun

4. startupStatus contains lifecycle-looking outcomes.

    startupStatus includes ready, completed, failed, cancelled, and detached.
    The document already says startupStatus does not redefine RuntimeHost,
    command, Job, OrchestrationUnit, or AppInstance lifecycle outcomes.

    Required correction:
        Translate AppInstance to Application / ApplicationRun and preserve the
        stop-lines.

        Also clarify that ready/completed/failed/cancelled/detached are startup
        mode surfaces only unless the mode contract explicitly projects an owning
        command, RuntimeHost operation, Job, adapter, ApplicationRun, or retained
        work outcome.

5. Startup result projection can hide downstream results if not constrained.

    The target correctly says oneShotCommand mode may project command result
    status into startup result status only as an explicit startup-mode surface,
    and command result remains command-domain evidence.

    Required correction:
        Preserve this and extend it to other downstream evidence:

            A startup result envelope may summarize command, RuntimeHost
            operation, workspace ownership, Job, adapter, View, or ApplicationRun
            outcomes only through explicit mode contracts and must not erase the
            owning-domain evidence or trace correlation.

6. test mode must not become a privilege bypass.

    IS-05 already says test mode uses controlled test surfaces without weakening
    boundaries, may bypass human prompts only when explicit policy or decision
    fixtures are supplied, and test fixtures do not become production defaults.

    Required correction:
        Preserve and translate AppInstance / SavePack terms to Application /
        ApplicationRun / SaveBundle.

        Add or preserve a stop-line that test fixtures do not create production
        permissions, production policy defaults, production adapter authority,
        production workspace ownership, or production SaveBundle semantics.

7. launcher mode must not create its own semantics.

    IS-05 says launcher mode does not create AppInstance or SavePack semantics
    separate from DA-20 and DA-28, and does not make browser frontend state
    authoritative.

    Required correction:
        Translate to Application / ApplicationRun / SaveBundle and keep the
        browser-state stop-line.

        Launcher UI is an entry/request surface, not authority.

8. serve mode exposure boundary should remain strong.

    serve mode may expose LAN entry surfaces only when explicit policy or
    configuration permits LAN exposure and never silently exposes internet-
    accessible runtime control surfaces.

    Required correction:
        Preserve this. Do not weaken local/LAN/internet exposure distinction in a
        rewrite.

9. RuntimeHost startup mode must not become TurnixRuntime identity.

    Startup modes may create or connect to a RuntimeHost. Current P02 says
    RuntimeHost is a running host boundary through which Kernel-owned authority is
    started, exposed, coordinated, and closed; RuntimeHost is not Turnix identity
    itself.

    Required correction:
        Preserve that startup mode selects an entry workflow. It does not create
        authority, TurnixRuntime identity, Application identity, ApplicationRun
        identity, SaveBundle authority, workspace ownership, or Kernel authority
        by itself.

10. Open questions should remain implementation-level.

    IS-05 leaves exact startupRequestId representation, result schema, CLI /
    launcher / service request mapping, process exit code mapping, detached work
    behavior, serve bind defaults, connect host discovery, extension mechanism,
    and error classes open.

    Required correction:
        Keep these open unless a later source resolves them. Do not use this IS to
        finalize CLI syntax, launcher behavior, or service wrapper behavior.

1. Replace AppInstance terminology.

    Replace appInstanceId with applicationId and/or applicationRunId.

    Replace AppInstance success/readiness/lifecycle/runtime identity with
    Application and ApplicationRun terminology.

2. Replace SavePack terminology.

    Replace SavePack with SaveBundle in purpose text, test mode, launcher mode,
    unsupported behavior, and locked summary.

3. Update shared startup operation wording.

    Replace:

        A startup mode that creates or starts an AppInstance uses DA-20.

    with current wording such as:

        A startup mode that creates an Application, loads a SaveBundle, creates
        an ApplicationRun, or starts an ApplicationRun follows the owning
        lifecycle and persistence documents.

4. Update startup identity and result fields.

    Replace startupRequestId distinction and result-envelope fields from
    appInstanceId to applicationId and/or applicationRunId.

5. Add startup-input anti-forgery stop-line.

    Add wording that startup request input, executable invocation context, entry
    surface kind, command-line arguments, environment input, requested startup
    mode, test harness context, launcher context, and service wrapper context are
    classification / policy / routing evidence only.

    They do not let the caller forge Kernel authority, RuntimeHost authority,
    TurnixRuntime identity, workspace ownership, Application identity,
    ApplicationRun identity, SaveBundle authority, capability permission,
    adapter authorization, or policy approval.

6. Preserve startup lifecycle stop-lines.

    Keep the distinctions between startup selection, startup mode entry,
    RuntimeHost lifecycle, command status, workspace ownership, Job outcome,
    OrchestrationUnit outcome, adapter outcome, RPC outcome, View/frontend
    outcome, and ApplicationRun outcome.

7. Clarify startup result projection.

    Add wording that startup result envelopes may project command or downstream
    outcomes only through explicit startup-mode contracts and must not erase
    underlying command, RuntimeHost operation, workspace ownership, Job, adapter,
    View, ApplicationRun, policy, or trace evidence.

8. Preserve test mode boundaries.

    Keep the rule that test fixtures do not become production defaults.

    Add or preserve wording that test mode does not create production permission,
    production policy, production adapter authority, production workspace
    ownership, production SaveBundle semantics, or production committed-state
    semantics.

9. Preserve launcher mode boundaries.

    Keep launcher mode as a user-facing entry/request surface.

    Keep the rule that launcher mode does not make browser frontend state
    authoritative and does not create separate Application, ApplicationRun, or
    SaveBundle semantics.

10. Preserve serve/connect safety rules.

    Keep:

        serve mode never silently exposes internet-accessible runtime control
        surfaces.

        connect mode does not silently start a new writable RuntimeHost unless
        explicitly permitted.

        connect mode does not silently take over stale ownership evidence.

11. Preserve open questions.

    Keep exact startupRequestId representation, startup result schema,
    CLI/launcher/service request mapping, process exit code mapping, detached
    work behavior, serve bind defaults, connect host discovery, startup-mode
    extension mechanism, and error classes open unless a later source resolves
    them.
