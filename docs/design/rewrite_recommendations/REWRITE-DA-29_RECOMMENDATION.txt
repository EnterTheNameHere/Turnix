SUMMARY
=======

DA-29 is strong and highly Dv3-compatible.

It defines PackManager as the official Turnix pack-management and
graph-preparation domain while preventing PackManager from becoming hidden
loader, resolver, importer, activator, capability, persistence, View, adapter,
policy, or Kernel authority.

This directly supports the user's intended addition:

    PackManager lets Turnix manage and prepare pack graphs without making the
    rest of Turnix clever, heuristic, or magically self-repairing.

Overall recommendation:

    KEEP

No heavy rewrite is recommended.

WHAT IS ALREADY NAILED
======================

DA-29 correctly says PackManager helps choose and explain what Turnix will try.

Turnix still performs only the accepted graph, activation plan, policy, and
operation requested through Kernel-mediated boundaries.

This prevents PackManager from becoming the magical "make it work" layer.

PackManager may prepare or explain graph intent.

PackManager does not silently:

    - discover
    - resolve
    - import
    - activate
    - load
    - grant PackContext authority
    - grant capability permission
    - mutate persistence
    - mutate SavePack state
    - mutate active AppInstance graph state
    - remember decisions
    - broaden decisions
    - accept risky graphs
    - update active packs
    - bypass policy
    - bypass Kernel authority


CATALOG MODEL
=============

ListPacks is the general pack-listing primitive.

AppPack, SavePack, ViewPack, ContentPack, and ModPack listings are filters over
Pack kind.

Catalog presentation preserves the distinction between:

    - existence
    - visibility
    - resolution eligibility
    - dependency satisfaction
    - selected graph membership
    - activation state
    - importability
    - capability availability

This is important.

A catalog is not a graph.

A graph is not activation.

Activation is not import.

Import is not capability authority.

PackManager must keep these meanings separate.


NO LAZY RESCAN
==============

DA-29 correctly says the pack catalog is derived from discovery and indexing.

Reading/listing catalog data does not perform discovery.

Catalog operations do not lazily rescan the filesystem unless explicit rescan
operation is requested and accepted.

This supports determinism and prevents "inspection changed reality" behavior.


VISIBILITY AND RESOLUTION
=========================

DA-29 correctly says PackManager may present visibility graphs, hidden packs,
shadowed packs, save-local packs, and visibility failures when permitted.

Visibility presentation does not grant visibility.

Visibility does not grant capability authority.

PackManager does not silently bypass visibility constraints to make a graph
work.

DA-29 also correctly says PackManager may call generic resolution with explicit
resolution context, but does not:

    - redefine PackRequest grammar
    - merge manifests
    - turn resolution into discovery
    - silently switch resolution contexts
    - persist resolution decisions by hidden side effect


DEPENDENCIES AND ADVISORY RELATIONS
===================================

DA-29 has a strong hard/advisory split.

PackManager consumes hard dependencies and advisory pack relations.

PackManager does not convert advisory relations into:

    - hard dependencies
    - hard activation blockers
    - loader rules

by itself.

Policy or user decision may turn an advisory warning into a graph-selection
decision for a specific selected graph, but that decision is:

    - explicit
    - scoped
    - trace-visible
    - not a manifest rewrite

Hard dependency failure remains hard failure unless accepted policy or user
decision explicitly resolves it under the owning documents.

Advisory conflict override is not hard dependency satisfaction.

This is exactly right.


SELECTED GRAPH AND ACTIVATION PLAN
==================================

A selected pack graph is explicit graph intent.

An activation plan is selected graph intent refined for activation order and
activation readiness.

PackManager may prepare an activation plan.

PackManager does not activate packs by preparing an activation plan.

PackManager does not execute pack code by preparing selected graph intent.

PackManager does not import code by preparing selected graph intent.

PackManager does not grant PackContext authority by preparing selected graph
intent.

An accepted graph or activation plan may still fail during activation.

Such failure is activation evidence, not proof that PackManager owned
activation.


EXPECTED-BREAK SEMANTICS
========================

DA-29's expected-break/risky-graph section is important.

Risk acceptance does not make the graph safe.

Risk acceptance does not rewrite pack metadata.

Risk acceptance does not satisfy hard dependencies unless an allowed explicit
decision resolves that hard dependency failure.

Risk acceptance does not grant capability permission.

Risk acceptance does not grant execution authorization for unsafe code.

Expected-break evidence does not convert failure into success.

This lets Turnix say:

    The user or policy knowingly accepted a risky graph.
    The graph broke in a known-risk way.
    That helps diagnostics explain the failure.
    It does not turn the failure into success.


IMPORT, ACTIVATION, AND ADAPTER BOUNDARIES
==========================================

DA-29 correctly says PackManager does not import pack code during catalog
listing or graph preparation.

PackManager does not use native imports to inspect pack runtime symbols.

PackManager does not bypass:

    - turnixImport
    - dependency consistency
    - visibility
    - activation
    - execution authority

PackManager does not call onLoad(ctx).

PackManager does not create PackContext authority.

PackManager may present adapter requirements, adapter availability, adapter
trust warnings, or adapter incompatibilities.

Presentation of adapter evidence does not authorize adapter execution.

Adapter execution authorization remains distinct from PackManager graph
preparation.


CAPABILITY AND PERMISSION BOUNDARY
==================================

PackManager operations may be exposed through RuntimeHost commands,
capabilities, RPC, or other mediated request surfaces.

Powerful or persistent operations require permission, policy, persistence, and
trace handling.

Examples:

    - install
    - update
    - remove
    - download
    - search external sources
    - modify selected graphs
    - copy packs into SavePacks
    - export SavePacks
    - change persisted state

PackManager does not grant capability permission.

PackManager does not resolve capability export conflicts silently.

A PackManager service, if one exists internally, is runtime wiring only.

A PackManager service is not a cross-pack authority bypass.


PERSISTENCE AND ACTIVE APPINSTANCE SAFETY
=========================================

PackManager writes may include catalog caches, package source configuration,
installed pack records, selected graph records, SavePack graph evidence, copied
pack material, pinned pack references, user decisions through DA-17-owned
mechanisms, and tool state.

These writes occur only through Kernel-mediated persistence, configuration,
transaction, and policy boundaries.

PackManager does not silently mutate active AppInstance graph state.

PackManager does not silently update packs active in a running AppInstance.

PackManager does not silently make changes to a SavePack-owned copied pack
graph.

PackManager graph changes affecting a running AppInstance require explicit
lifecycle, policy, and trace handling.


VIEW AND UI BOUNDARY
====================

PackManager may expose Views.

PackManager Views are presentation and interaction surfaces.

Displaying a PackManager View does not grant pack-management authority to the
displaying surface.

Frontend PackManager code remains adapter-executed frontend code.

Frontend PackManager code does not directly mutate pack catalogs, selected
graphs, roots, SavePacks, or configuration.

PackManager UI does not own the semantics it presents.


TRACE OWNERSHIP
===============

DA-29 owns PackManager-domain trace reason identifiers.

DA-03 owns the trace substrate.

PackManager trace reason identifiers do not replace:

    - DA-11 resolution trace reasons
    - DA-13 dependency/fallback semantics
    - DA-14 activation trace reasons
    - DA-16 capability trace reasons
    - DA-28 RuntimeHost trace reasons
    - persistence trace evidence

PackManager trace evidence preserves causal links to resolution, decision,
capability, RuntimeHost, Job, AppInstance, SavePack, activation, and persistence
evidence when those events exist.

This fits the DA-03 trace model.


MAIN WATCH ITEM: REPAIR WORDING
===============================

The word "repairs" is useful but dangerous.

DA-29 says PackManager prepares, explains, validates, repairs, and manages
selected pack graph intent.

This is fine because the document repeatedly blocks silent repair.

However, implementation and future specs must preserve this meaning:

    repair = explicit, scoped, policy/user-accepted graph-preparation repair

not:

    repair = automatic hidden correction

Repair must not silently:

    - resolve ambiguity
    - accept risky graphs
    - broaden remembered decisions
    - rewrite manifests
    - bypass visibility
    - satisfy hard dependencies
    - update active AppInstance packs
    - mutate SavePack-owned copied pack graph
    - write roots/config/state/policy decisions


NO MAJOR DV3 CONFLICT FOUND
===========================

DA-29 does not collapse PackManager into:

    - Kernel
    - discovery
    - generic resolution
    - importing
    - activation
    - PackContext authority
    - adapter execution
    - mechanical loading
    - capability permission
    - persistence authority
    - View authority
    - RuntimeHost
    - AppInstance
    - SavePack ownership
    - policy ownership
    - user-decision ownership

This is exactly what the document should prevent.


CURRENT FINAL RECOMMENDATION
============================

Keep DA-29.

No heavy rewrite is recommended.

DA-29 successfully gives Turnix a PackManager domain while keeping the rest of
Turnix deterministic and non-clever.

The main future warning is to preserve the meaning of "repair" as explicit,
scoped, policy/user-mediated graph-preparation repair, not hidden automatic
correction.
