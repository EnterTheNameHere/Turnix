==============================================================================
SUMMARY
==============================================================================

ODA-E contains a useful optional model for cross-pack state access, mutation,
observation, redaction, and derived-value handling. Its central instinct is good:
state access should be explicit, mutation authority should be separate from read
access, adapter mediation should not grant state authority, and diagnostic/export
surfaces should be redacted by default where appropriate.

The document also has several strong boundaries already:

    - it does not attempt sandboxing hostile local behavior
    - adapter identity is not state ownership identity
    - frontend client identity is not state ownership identity
    - RPC peer identity is not state ownership identity
    - adapter-mediated writes remain subject to write-authority rules
    - in-process adapter calls do not bypass write authority
    - computed/effective values do not become authoritative stored state merely
      because they are transported
    - transported frontend/adapter values do not become public by themselves

The main fixes are authority-boundary corrections and current-model terminology.
The final rewrite should avoid treating Kernel as ordinary state storage, replace
SavePack/AppInstance wording, avoid raw "without ctx" access language, clarify
that trace is evidence rather than enforcement authority, and keep Pack-owned
state as namespace/ownership metadata mediated by runtime authority rather than
raw Pack authority.

==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. Cross-pack mutation is explicit.

    The document correctly rejects implicit override behavior. When Pack B
    modifies state owned by Pack A, the target owner domain, permission model,
    and trace outcome are explicit.

2. Read authority and write authority are separated.

    The document correctly treats mutation and deletion as write-class operations
    requiring authority.

3. Adapter mediation is not authority.

    The document repeatedly says adapter-mediated access does not grant adapter
    state authority and that adapter identity is not ownership identity.

4. Redaction defaults are useful.

    PRIVATE and INTERNAL values being redacted by default in normal surfaces,
    traces, and exports is a good leak-minimizing default, as long as it does not
    claim secrecy from the local user.

5. Computed values are correctly non-persistent.

    Computed/effective layers are not ownership scopes, are not persisted
    directly, and do not become authoritative stored state merely because they are
    transported.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. Kernel-as-state-owner wording is too broad.

    ODA-E says every state key has exactly one authority owner and that the owner
    is either the Kernel or a specific Pack. This is useful as a simplified
    optional model, but it can conflict with the current architecture if read
    literally.

    Current architecture distinguishes Kernel authority, Memory/state ownership,
    configuration ownership, IoManager persistence authority, Pack participation,
    Application/ApplicationRun identity, and committed-state truth. Kernel is the
    runtime authority root and coordinator, but that does not mean every
    Kernel-scoped value is ordinary state owned and stored by Kernel as a data
    bucket.

    Required correction:
        Treat Kernel-owned state as Kernel-mediated runtime/domain state or
        runtime-owned state whose owning domain is Kernel-controlled. Do not make
        Kernel a generic storage bucket.

    Suggested wording:
        Each governed state key has one owning authority domain. The domain may
        be Kernel-mediated runtime state, a Pack-owned namespace, or another
        owning domain defined by higher-authority documents. This optional model
        discusses Kernel-mediated and Pack-owned cases, but it does not replace
        DA-04, DA-06, DA-07, DA-16, DA-17, or lifecycle ownership.

2. Pack ownership must not become raw Pack authority.

    ODA-E reasonably says a Pack can own Pack-global or save-bound keys. The
    final wording must keep ownership as namespace/domain ownership mediated by
    runtime authority and ModCallContext/API boundaries, not as raw backend
    authority held by Pack code.

    Required correction:
        Say Pack-owned state is owned in the Turnix state model, but Pack code
        reads or mutates it only through mediated APIs, granted permissions,
        owning-domain rules, transactions, and commit boundaries.

3. "Accessible without ctx" is unsafe wording.

    Section 05.1 says Kernel scope is accessible without ctx where the higher API
    permits that. In the current model, Pack code should not rely on raw Kernel
    access, ctx.kernel, runtimeHost, raw services, or raw filesystem. Access must
    be through authorized runtime, host, diagnostic, or mediated API surfaces.

    Required correction:
        Replace "accessible without ctx" with wording that distinguishes Pack
        invocation access from host/runtime/admin access.

    Suggested wording:
        Kernel-mediated runtime state is accessed only through authorized APIs.
        Pack code accesses state through ModCallContext or another explicitly
        provided mediated surface. Host or diagnostic tools may use separate
        controlled command/API surfaces, but those surfaces do not grant Pack code
        raw Kernel authority.

4. SavePack and AppInstance terminology is stale.

    ODA-E uses SavePacks and AppInstance in state scopes, trace correlation, and
    relation-to-other-documents sections.

    Required correction:
        Replace SavePack with SaveBundle where durable persistence closure is
        meant. Replace AppInstance with Application and/or ApplicationRun
        according to meaning.

    Suggested replacements:

        shared across all SavePacks

    should become:

        shared across Applications or SaveBundle generations where the owning
        persistence/configuration model permits that sharing

    and:

        Save-bound state access remains constrained by AppInstance and SavePack
        binding rules

    should become:

        Save-bound state access remains constrained by Application,
        ApplicationRun, SaveBundle, and accepted Pack graph binding rules.

5. Scope/storage wording needs current Workspace/Application/SaveBundle alignment.

    The document says Kernel and Pack-global state are stored in userdata in this
    model, and Pack-local save-bound state is stored in a SavePack. This is too
    storage-specific and stale.

    Required correction:
        Let DA-04, DA-06, DA-07, Workspace, and SaveBundle documents own actual
        storage layout. ODA-E should describe logical scopes and access semantics,
        not final storage locations.

    Suggested wording:
        Scope names describe logical authority and access boundaries. Physical or
        durable storage location is owned by the higher state, configuration,
        persistence, Workspace, and SaveBundle documents.

6. PUBLIC/PROTECTED/PRIVATE/INTERNAL are useful but must not replace visibility,
   permission, capability, dependency, or discovery semantics.

    Access levels are good as optional state-key metadata. But final wording must
    prevent them from becoming Pack visibility, import permission, dependency
    satisfaction, capability permission, service access, or execution authority.

    Required correction:
        Add a boundary that access-level metadata governs state read/write
        handling only inside this optional model. It does not grant Pack
        visibility, resolution, import, activation, service access, capability
        invocation, or adapter execution rights.

7. "Users may inspect all state through kernel tools" is too broad.

    The document correctly says it does not claim secrecy from the user, but
    "all state" and "kernel tools" can overstate availability and authority.
    Some state may be absent, pruned, corrupt, encrypted, external, unmounted,
    not retained, or only reachable through owning diagnostic/export rules.

    Required correction:
        Say user-controlled diagnostic/admin tooling may inspect retained state
        and evidence through authorized surfaces where the owning documents make
        that material available. Default redaction still applies to normal
        surfaces, traces, and exports unless explicitly overridden through an
        allowed path.

8. Trace is evidence, not enforcement authority.

    The LOCKED summary says "trace-first enforcement." This risks making trace
    sound like the enforcement mechanism or authority source. Current architecture
    treats trace as structured evidence, not committed state, memory, logging,
    persistence truth, UI presentation, or artifact authority.

    Required correction:
        Replace "trace-first enforcement" with "trace-emitting enforcement" or
        "trace-backed diagnostics." Enforcement is performed by the owning
        authority path; trace records evidence of the decision and outcome.

9. Error reproducibility is overpromised.

    Section 15 says errors remain traceable, explainable, and reproducible. This
    should be qualified. Trace retention is policy-governed and may be incomplete;
    external conditions and non-retained inputs can prevent reproduction.

    Required correction:
        Say errors emit or retain structured evidence where the owning tracing
        and retention policies support it. Reproducibility is claimed only where
        retained evidence and owning workflow semantics support reproduction.

10. Watchers and computed handlers must not mutate outside orchestration.

    The open questions already include whether watcher logic may mutate state
    directly or only through normal orchestrated paths. The final rewrite should
    answer the boundary even if the exact API remains open.

    Required correction:
        Watcher, observer, and computed-handler logic may not bypass ordinary
        authority, transaction, orchestration, trace, permission, or commit
        boundaries. Any mutation they trigger is new mediated work, not direct
        hidden mutation.

==============================================================================
OBSOLETE-PRESERVATION RISKS
==============================================================================

The main obsolete-preservation risks are SavePack, AppInstance, and raw ctx
access language.

Do not preserve these as current architecture merely because the ODA source uses
them. Translate into the current model:

    Application
        durable application individual

    ApplicationRun
        one live execution period of that Application

    SaveBundle
        durable persistence closure of the Application

    SaveBundle generation
        immutable published restoration head containing accepted graph and
        retained state/evidence roots

    ModCallContext
        fresh, scoped, Pack-bound invocation gateway for Pack participation

    authorized runtime/host/admin surface
        controlled non-Pack-facing access surface, not raw Kernel authority

The final ODA-E should keep the cross-pack permission model, but it should not
keep old identity/storage wording that conflicts with the current runtime model.
