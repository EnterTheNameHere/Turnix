IS document verdict:
    Keep with targeted terminology, catalog-boundary, and authority-boundary

    IS-09 is a useful concrete implementation specification for RuntimeHost and

==============================================================================
WHAT THE DOCUMENT GETS RIGHT
==============================================================================

1. Correct implementation-specification scope.

    IS-09 correctly defines concrete pack listing operation contracts rather than
    defining root discovery, filesystem scanning, pack identity, hierarchy,
    visibility, PackRequest resolution, importing, module loading, dependency
    semantics, activation, capability execution, policy, Application lifecycle,
    SaveBundle binding, RPC, UI, command surfaces, PackManager doctrine, resolved
    graph schema, activation-plan schema, package install/update/delete, CLI
    syntax, JSON-RPC envelope fields, WebSocket envelope fields, or browser
    component layout.

2. Strong ListPacks primitive.

    The document correctly identifies ListPacks as the shared concrete listing
    primitive and treats kind-specific list operations as filtered forms of
    ListPacks.

3. Strong read-only catalog boundary.

    Listing is read-only catalog access. It does not perform discovery,
    PackRequest resolution, graph selection, activation-plan creation, importing,
    activation, or authority grant.

4. Good request-envelope boundary.

    A request envelope does not authorize access by itself. The entry surface
    remains subject to RuntimeHost, capability, RPC, policy, and permission rules
    where applicable.

5. Good filter/sort/pagination/projection boundaries.

    Filters restrict results without changing pack identity or visibility
    meaning. Filters cannot make invisible packs visible unless the catalog
    context and policy permit diagnostic visibility.

    Sorting is deterministic but does not select a graph or imply resolution
    winner selection.

    Pagination does not change the total ordered result set, and cursors do not
    grant access outside the original permitted catalog context.

    Projection controls result verbosity only and does not change listing
    semantics.

6. Good response and item projection boundary.

    Response envelopes do not grant runtime authority.

    Pack catalog items are listing projections, not pack definitions. They do not
    replace manifests, discovery records, resolution candidates, selected graph
    records, or activation records.

7. Good summary boundary.

    Visibility summary does not grant visibility. Visibility meaning remains
    owned by DA-10.

    Compatibility summary is advisory unless an owning operation or policy turns
    it into a graph-selection decision. Compatibility summary does not replace
    dependency resolution, activation, or policy semantics.

    Dependency summary is not dependency resolution. Dependency semantics remain
    owned by DA-13.

    Advisory summary does not create hard dependency semantics.

8. Good entry-surface discipline.

    CLI, RuntimeHost command, Launcher, PackManager View, remote client,
    application View, AI buddy surface, and test surface usage route to the same
    ListPacks operation semantics.

    CLI syntax, Launcher UI, PackManager View layout, remote transport, and test
    harness access do not define separate listing semantics.

9. Good trace boundary.

    ListPacks remains trace-visible. PackManager-domain trace reasons are owned
    by DA-29, and serialized trace records use IS-08 when serialized through the
    shared trace record envelope.

10. Good open-question discipline.

    Exact request IDs, workspace IDs, catalog item IDs, canonical pack IDs,
    source identities, version range filters, text search matching, cursor format,
    page sizes, filters, vocabularies, CLI syntax, RPC envelope mapping, and JSON
    Schema publication remain open.

==============================================================================
MAJOR SEMANTIC RISKS
==============================================================================

1. SavePack terminology is superseded by SaveBundle.

    IS-09 uses SavePack throughout:

        - SavePack listings
        - ListSavePacks
        - SavePack kind filter
        - SavePack visibility semantics
        - SavePack binding behavior
        - savePackId
        - savePackSummary
        - SavePack compatibility check
        - SavePack-specific listing fields
        - SavePack loading / migration

    Current source-stack correction:
        Proposal P02 defines SaveBundle as the durable persistence closure of one
        Application. SaveBundle is not a Pack, not an Application, not an
        ApplicationRun, not a RuntimeHost, not a live process snapshot, not a Job
        store, and not authority by itself.

    Required consequence for IS-09:
        Translate SavePack terminology to SaveBundle where the listed thing is a
        durable persistence closure or save identity.

        Likely replacements:

            ListSavePacks
                -> ListSaveBundles, if this operation lists durable save bundles

            SavePack listing fields
                -> SaveBundle listing fields

            savePackId
                -> saveBundleId

            savePackSummary
                -> saveBundleSummary

            includeSavePackSummary
                -> includeSaveBundleSummary

            compatibility against SavePack
                -> compatibility against SaveBundle

        If any old SavePack naming is intentionally kept as a compatibility alias,
        mark it explicitly as compatibility terminology, not current architecture.

2. AppInstance terminology is superseded by Application / ApplicationRun.

    IS-09 uses AppInstance in several places:

        - AppInstance lifecycle or SavePack binding behavior
        - appInstanceId in catalogContext
        - appInstance scope
        - AppInstance context
        - compatibility context using AppInstance
        - savePackSummary bind to AppInstance
        - activeInAppInstanceId
        - failure/status not AppInstance lifecycle outcome
        - trace context appInstanceId
        - listing trace evidence does not replace AppInstance evidence
        - locked summary appInstanceId

    Current source-stack correction:
        Proposal P02 defines Application as the durable application individual
        and ApplicationRun as one live execution period of an Application.

    Required consequence for IS-09:
        Replace AppInstance with Application and/or ApplicationRun according to
        local meaning.

        Likely replacements:

            appInstanceId
                -> applicationId and/or applicationRunId

            appInstance scope
                -> application scope and/or applicationRun scope

            activeInAppInstanceId
                -> activeInApplicationRunId

            AppInstance lifecycle outcome
                -> Application lifecycle outcome and/or ApplicationRun lifecycle
                   outcome; usually ApplicationRun when live activation/runtime
                   state is meant

            SavePack bound to AppInstance
                -> SaveBundle bound to Application or loaded into an
                   ApplicationRun, depending on the exact lifecycle model.

3. Pack-kind model may incorrectly treat SaveBundle as a Pack.

    IS-09 defines pack kind names including SavePack and presents ListSavePacks
    as a pack-kind-specific operation.

    Current source-stack correction:
        SaveBundle replaces SavePack as durable persistence closure and is not a
        Pack.

    Required consequence for IS-09:
        Decide whether save listings still belong in a generic pack catalog, or
        whether they should be a sibling catalog operation for SaveBundle records.

        Safe options:

            Option A:
                Keep ListPacks for actual Pack kinds only:
                    AppPack, ModPack, ViewPack, ContentPack
                Add ListSaveBundles as a sibling operation, not a filtered
                ListPacks form.

            Option B:
                Keep ListSaveBundles in this document as a catalog/listing
                operation but explicitly state that SaveBundle entries are not
                Pack descriptors and are included through a catalog projection,
                not as a Pack kind.

        Do not leave SaveBundle as a Pack kind unless later source material
        intentionally defines a compatibility abstraction that treats it that way.

4. AppPack as application-definition source may be too narrow.

    IS-09 frequently uses AppPack context and lists AppPacks as startup
    candidates. P02 allows applications to be created from an AppPack or another
    accepted AppDefinition source.

    Required consequence for IS-09:
        Keep AppPack listing for actual AppPacks, but avoid implying that every
        Application must originate from an AppPack.

        Consider adding appDefinitionSourceId or appDefinitionSourceKind if the
        catalog needs to list or filter accepted non-AppPack AppDefinition
        sources.

5. selectedState and active state may overstate runtime truth.

    selectedState contains selectedStatus, selectedGraphId, activeInAppInstanceId,
    and pendingChangeStatus.

    The document already says selectedState is catalog evidence and does not
    mutate selected graph state.

    Required consequence for IS-09:
        Preserve that boundary and translate activeInAppInstanceId to current
        ApplicationRun identity.

        Add or preserve that selectedState is a catalog summary, not authoritative
        runtime state, activation state, committed state, or current graph owner
        unless the owning graph/runtime document maps it.

6. Compatibility summaries must not become graph-resolution decisions.

    IS-09 already says compatibility summary is advisory unless an owning
    operation or policy turns it into a graph-selection decision.

    Required consequence for IS-09:
        Preserve this. Do not let ListPacks decide graph resolution,
        dependency resolution, activation eligibility, SaveBundle migration,
        or policy decisions by itself.

7. Diagnostic visibility needs a privacy/authority stop-line.

    IS-09 allows includeInvalid, includeShadowed, includeDiagnostics, and
    diagnostic visibility where catalog context and policy permit it.

    Required consequence for IS-09:
        Add or preserve wording that diagnostic inclusion may reveal normally
        hidden, invalid, rejected, or source/path details only when policy and
        catalog context permit it. Diagnostic projection does not bypass
        visibility, policy, privacy, path exposure, or source trust boundaries.

8. Path/source fields need file-access and authenticity guardrails.

    sourcePath records a path only when path exposure is permitted. Source fields
    do not prove authenticity and do not grant authority.

    Required consequence for IS-09:
        Preserve this and add if needed:

            sourcePath is catalog evidence only. It does not grant filesystem
            access, prove current path existence, or authorize direct reads.

9. Stale cache / fresh catalog wording must not imply rescan.

    IS-09 already says requireFreshCatalog does not imply filesystem rescan
    unless an explicit rescan operation has been requested and accepted.

    Required consequence for IS-09:
        Preserve this. Listing is not discovery and not rescan.

10. Counts-only and partial results need completeness guardrails.

    Counts summarize the catalog operation result. Counts do not replace item
    records when item records are required. Partial listing does not silently
    become complete listing.

    Required consequence for IS-09:
        Preserve this. Counts-only, partial, or projected responses must not be
        presented as complete catalog truth unless the profile/operation says so.

11. Entry surfaces must not own catalog semantics.

    IS-09 already gets this right.

    Required consequence for IS-09:
        Preserve that CLI, Launcher, PackManager View, remote clients, application
        Views, AI buddy surfaces, and tests all use the same ListPacks semantics.
        Surface labels, aliases, layout, transport, and test harness behavior do
        not create separate catalog truth.

12. Trace evidence must remain evidence only.

    IS-09 correctly says diagnostics do not replace trace evidence and listing
    trace evidence does not replace discovery, resolution, dependency,
    activation, capability, RuntimeHost, AppInstance, or persistence trace
    evidence.

    Required consequence for IS-09:
        Translate AppInstance to Application/ApplicationRun and preserve the trace
        evidence boundary.

==============================================================================
OBSOLETE-PRESERVATION RISKS
==============================================================================

1. Do not preserve SavePack as current terminology.

    Translate to SaveBundle according to meaning.

2. Do not preserve SavePack as a Pack kind unless a later compatibility layer
   explicitly keeps that abstraction.

3. Do not preserve ListSavePacks as a filtered ListPacks form if SaveBundle is no
   longer a Pack.

    Prefer ListSaveBundles as a sibling catalog operation or explicitly define
    save-bundle catalog entries as non-Pack projections.

4. Do not preserve savePackId / savePackSummary / includeSavePackSummary.

    Translate to saveBundleId / saveBundleSummary / includeSaveBundleSummary, or
    a more precise current persistence field name.

5. Do not preserve AppInstance / appInstanceId / activeInAppInstanceId.

    Translate to Application / ApplicationRun / applicationId / applicationRunId /
    activeInApplicationRunId according to meaning.

6. Do not preserve AppPack as universal application-definition identity if
   accepted non-AppPack AppDefinition sources remain supported.

7. Do not preserve catalog summaries as owning semantics.

    Summaries are projections and evidence, not the owning truth.
