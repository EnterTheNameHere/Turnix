===============================================================================
DESIGN AREA DA-28 - RUNTIME HOST, WORKSPACE OWNERSHIP AND COMMAND SURFACE
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines RuntimeHost identity, Workspace ownership coordination, host
lifecycle, entry surfaces, startup-mode meaning, command-surface authority
boundaries, launcher-surface boundaries, packaged-distribution entry
boundaries, local-first deployment interpretation, RuntimeHost trace reason
ownership, and shared runtime operation composition.

This document owns runtime-host semantics. It consumes Kernel authority
ordering, TurnixRuntime ownership boundaries, Application and ApplicationRun
lifecycle, SaveBundle persistence, RPC, UI/View, ExecutionAdapter,
OrchestrationUnit, persistence, capability, Job, and policy semantics defined
by their owning documents.

Purpose:
--------
This document defines what Turnix is when it is running as a host.

It defines:
- RuntimeHost as the running Turnix host boundary
- runtimeHostId as runtime host correlation identity
- relationship between RuntimeHost, Kernel, TurnixRuntime, Workspace,
  Application, ApplicationRun, SaveBundle, View, ExecutionAdapter, RPC, Job,
  OrchestrationUnit, and command surfaces
- Workspace ownership coordination at the runtime-host boundary
- local-first deployment interpretation for same-machine and LAN use
- startup mode meaning
- shared runtime operation composition across startup modes
- entry surface and command surface boundaries
- launcher-surface and convenience-startup boundaries
- packaged application or game distribution entry boundaries
- command/startup terminology boundaries for host and connect surfaces
- second-host and already-owned Workspace behavior
- RuntimeHost lifecycle phases
- RuntimeHost-domain trace reason identifiers
- minimum RuntimeHost trace context
- explicitly unsupported RuntimeHost behaviors

It does NOT define:
- Kernel authority ordering or platform philosophy (see DA-01 and DA-02)
- trace event structure, trace DAG semantics, or span mechanics (see DA-03)
- authoritative committed state or transaction semantics (see DA-04)
- payload identity, Chunk, or ValueRef representation (see DA-05)
- configuration, schema, or effectiveConfig semantics (see DA-06)
- persistent I/O authority or concrete filesystem rules (see DA-07)
- Window, SafePointWindow, or AbortedWindow semantics (see DA-08)
- service, capability, or permission semantics (see DA-16)
- user decision and remembered policy semantics (see DA-17)
- Job lifecycle, timeout, cancellation, progress, or result semantics
  (see DA-19)
- Application or ApplicationRun lifecycle semantics (see DA-20)
- RPC, channel, and transport semantics (see DA-21)
- UI, View, and frontend runtime semantics (see DA-22)
- execution adapter authority boundaries (see DA-23)
- OrchestrationUnit lifecycle, terminal outcomes, mutation authority, or
  single-lane ApplicationRun mutation semantics (see DA-24)
- Window artifact, export, or bundle semantics (see DA-25)
- comparison, Replay, Resume, Retry, or retained-work workflow semantics
  (see DA-26)
- adapter lifecycle, trust, isolation, concrete adapter classes, or adapter-
  domain trace reason identifiers (see DA-27)
- concrete CLI command syntax
- concrete launcher implementation
- concrete external model-provider process management
- concrete Workspace lock implementation
- concrete ownership claim file layout
- concrete process, socket, service, FastAPI, WebSocket, browser bootstrap,
  container, or virtual-machine implementation

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines runtime-host, Workspace ownership, startup-mode,
      entry-surface, command-surface, and RuntimeHost trace semantics within
      that shared interpretation model.

01.05. This document uses canonical architecture type names for runtime-host
      semantics.

01.06. Canonical type names used by this document include:
      - TurnixRuntime
      - Kernel
      - RuntimeHost
      - Workspace
      - Application
      - ApplicationRun
      - SaveBundle
      - ExecutionAdapter
      - OrchestrationUnit
      - View

01.07. Non-canonical runtime identity or persistence names do not appear in
      this document unless another authoritative document explicitly defines
      them as current aliases.

01.08. The lowercase word "host" is not a global canonical alias for
      RuntimeHost.

01.09. In runtime-host command or startup-mode context, "host" may be used as
      user-facing shorthand for RuntimeHost participation, such as starting,
      stopping, inspecting, connecting to, or exposing a RuntimeHost.

01.10. Outside runtime-host command or startup-mode context, "host" keeps its
       ordinary contextual meaning and does not automatically identify a
       RuntimeHost.

01.11. Client, frontend client, remote client, LAN client, command surface,
       control surface, and entry surface wording does not identify a
       RuntimeHost unless this document explicitly defines a RuntimeHost
       relationship for that surface.

01.12. Launcher wording does not identify a RuntimeHost, Kernel, Application,
       ApplicationRun, Workspace, AppPack, SaveBundle, ExecutionAdapter, model
       provider, or packaged product unless the owning document explicitly
       defines that relationship.

01.13. Launcher wording may describe a convenience entry surface, a separate
       application, a script, a shortcut, a batch file, a graphical wrapper, or
       another user-facing startup helper.

01.14. Packaged application, packaged game, bundled game, distribution, and
       product wording does not define Turnix platform identity by itself.

01.15. A packaged application or game distribution may include Turnix runtime
       material, AppPack material, Packs, assets, launcher surfaces, and
       defaults without becoming the semantic owner of those domains.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. RuntimeHost semantics answer:

          "What owns Turnix host execution while Turnix is running, which
           Workspace or runtime scope is bound, and how do entry surfaces
           reach Kernel-owned authority without becoming authority
           themselves?"

02.02. A RuntimeHost is the running Turnix host boundary that binds a
      Workspace or runtime scope, exposes controlled entry surfaces, and
      coordinates access to Kernel-owned authority.

02.03. RuntimeHost exists inside one TurnixRuntime authority domain.

02.04. RuntimeHost starts, exposes, coordinates, and closes controlled access
      to Kernel-owned authority.

02.05. RuntimeHost does not replace Kernel authority.

02.06. RuntimeHost does not grant authority by deployment shape, process
      location, command syntax, network exposure, launcher implementation, or
      implementation framework.

02.07. RuntimeHost is not a TurnixRuntime.

02.08. RuntimeHost is not Kernel.

02.09. RuntimeHost is not a Workspace.

02.10. RuntimeHost is not an Application.

02.11. RuntimeHost is not an ApplicationRun.

02.12. RuntimeHost is not a SaveBundle.

02.13. RuntimeHost is not a View.

02.14. RuntimeHost is not an ExecutionAdapter.

02.15. RuntimeHost is not a transport.

02.16. RuntimeHost is not a CLI command.

02.17. RuntimeHost is not a client instance.

02.18. RuntimeHost is not a frontend client.

02.19. RuntimeHost is not a remote client.

02.20. RuntimeHost is not a Job.

02.21. RuntimeHost is not an OrchestrationUnit.

02.22. RuntimeHost is not a launcher surface.

02.23. RuntimeHost is not a packaged application or game distribution.

02.24. RuntimeHost is not a model-provider process manager by itself.

02.25. RuntimeHost is not an artifact or export owner by itself.

02.26. RuntimeHost is not a Replay, Resume, Retry, or comparison workflow
       owner by itself.

02.27. RuntimeHost provides the host-level boundary in which Kernel-owned
       Workspace binding, ApplicationRun loading, View exposure,
       ExecutionAdapter participation, RPC communication, Jobs, decisions,
       orchestration, tracing, and persistence may occur under their owning
       documents.

02.28. RuntimeHost Workspace ownership, command surfaces, entry surfaces,
       launcher surfaces, retained work, SaveBundle paths, persistent I/O,
       configuration, and Workspace state do not redefine DA-05, DA-06, or
       DA-07 authority.

02.29. RuntimeHost operations, command surfaces, launcher surfaces, retained
       work behavior, export behavior, comparison, Replay, Resume, Retry, and
       workflow traces do not define DA-25 or DA-26 semantics.

02.30. Later sections refine and apply these rules. They do not weaken them.


===============================================================================
03. RUNTIMEHOST IDENTITY
===============================================================================

03.01. runtimeHostId identifies one RuntimeHost.

03.02. runtimeHostId is stable for the lifetime of that RuntimeHost.

03.03. runtimeHostId is not reused for a different RuntimeHost during the same
      Kernel run or host identity scope.

03.04. runtimeHostId is the correlation identity used by RuntimeHost-owned
      trace evidence.

03.05. runtimeHostId is distinct from:
      - TurnixRuntime identity
      - Workspace identity
      - process identity
      - Application identity
      - AppPack identity
      - SaveBundle identity
      - applicationRunId
      - viewId
      - frontend client identity
      - ExecutionAdapter identity
      - RPC message identity
      - channel identity
      - transport identity
      - capability identity
      - jobId
      - orchestrationUnitId
      - transactionId
      - decision identity
      - launcher surface identity
      - packaged distribution identity

03.06. A RuntimeHost record includes enough identity context, when available,
      to relate:
      - runtimeHostId
      - TurnixRuntime identity when available
      - Workspace identity
      - process identity when available
      - active Kernel or KernelContext identity when such identity is defined
      - active entry surface identities when applicable
      - active launcher surface identity when applicable
      - active Application identities when applicable
      - active ApplicationRun identities when applicable
      - active SaveBundle identities when applicable
      - active View identities when applicable
      - active ExecutionAdapter identities when applicable

03.07. Exact runtimeHostId representation remains open for an implementation
      specification.

03.08. Exact TurnixRuntime, Workspace, process, KernelContext, Application,
      ApplicationRun, SaveBundle, launcher surface, and packaged distribution
      identity representation remains owned by the documents and
      implementation specifications that define those identities.


===============================================================================
04. RELATION TO KERNEL AND TURNIXRUNTIME
===============================================================================

04.01. Kernel owns runtime authority.

04.02. A TurnixRuntime is one runtime authority domain.

04.03. RuntimeHost owns the running host boundary through which Kernel-owned
      authority is started, exposed, coordinated, and eventually closed for a
      Workspace or runtime scope.

04.04. RuntimeHost does not own Kernel authority independently of the
      TurnixRuntime authority domain in which it runs.

04.05. RuntimeHost does not make non-Kernel code Kernel authority.

04.06. RuntimeHost does not let command surfaces, launcher surfaces,
      ExecutionAdapters, transports, frontend clients, or LAN clients bypass
      Kernel-owned authority paths.

04.07. RuntimeHost may create, bind, expose, or close Kernel-facing surfaces
      only through rules defined by this document and by the owning documents
      for the affected domain.

04.08. RuntimeHost implementation code that performs platform work remains
      constrained by Kernel authority, orchestration, persistence, trace,
      capability, and policy boundaries.

04.09. RuntimeHost implementation convenience does not override platform
      truth.

04.10. Replacing FastAPI, WebSocket, browser JavaScript, CLI implementation,
       process layout, service wrapper, launcher implementation, container
       wrapper, or deployment vehicle does not redefine RuntimeHost semantics.

04.11. RuntimeHost realization is replaceable only when runtime-host contract
       meaning, Workspace ownership meaning, entry-surface meaning,
       command-surface meaning, lifecycle meaning, and trace obligations
       remain preserved.


===============================================================================
05. WORKSPACE OWNERSHIP COORDINATION
===============================================================================

05.01. A RuntimeHost may bind a Workspace or runtime scope.

05.02. A RuntimeHost may participate in acquiring and releasing writable
      Workspace ownership for its TurnixRuntime.

05.03. A writable Workspace has at most one owning TurnixRuntime/Kernel
      authority domain at a time unless a later authoritative multi-host
      design defines another mode.

05.04. RuntimeHost coordinates and exposes the host boundary for writable
      Workspace ownership held by the running TurnixRuntime/Kernel authority
      domain.

05.05. RuntimeHost records and exposes host-level ownership evidence.

05.06. RuntimeHost does not become a separate authority root over Workspace
      mutation.

05.07. RuntimeHost Workspace ownership coordination prevents silent multi-host
      or multi-runtime mutation of durable Turnix-managed state.

05.08. A second RuntimeHost does not silently acquire writable ownership of
      the same Workspace.

05.09. A second RuntimeHost does not silently downgrade to read-only behavior
      unless an explicit policy or tooling mode defines and reports that
      behavior.

05.10. A RuntimeHost does not silently ignore existing Workspace ownership
       evidence.

05.11. A RuntimeHost does not silently treat stale ownership evidence as safe
       to overwrite.

05.12. Stale ownership recovery is explicit, policy-governed, and
       trace-visible.

05.13. Read-only inspection of a Workspace or SaveBundle may be allowed by
       explicit tooling, export, or policy rules.

05.14. Read-only inspection does not create writable Workspace ownership.

05.15. Workspace ownership does not grant ExecutionAdapters direct
       SaveBundle write authority.

05.16. Workspace ownership does not bypass ApplicationRun writable
       SaveBundle ownership rules under the owning Application and
       SaveBundle documents.

05.17. Workspace ownership does not bypass persistent I/O authority under
       DA-07.

05.18. Workspace ownership does not bypass committed-state rules under
       DA-04.

05.19. Workspace ownership does not bypass OrchestrationUnit mutation
       authority under DA-24.

05.20. Command surfaces, entry surfaces, and launcher surfaces cannot acquire,
       override, downgrade, recover, or release Workspace ownership except
       through the Kernel-mediated RuntimeHost/Workspace ownership path.

05.21. Concrete claim files, lock files, sockets, process markers,
       ownership records, stale-owner checks, and recovery implementation
       details belong to later implementation specifications.


===============================================================================
06. RELATION TO APPLICATIONS, APPLICATIONRUNS, AND SAVEBUNDLES
===============================================================================

06.01. Application is the durable application individual.

06.02. ApplicationRun is the live runtime execution period of an Application.

06.03. SaveBundle is the durable persistence closure of an Application.

06.04. RuntimeHost may host zero, one, or multiple ApplicationRuns according
      to policy and implementation support.

06.05. Loading an ApplicationRun does not make runtimeHostId equal to
      applicationRunId.

06.06. RuntimeHost does not own Application identity.

06.07. RuntimeHost does not own ApplicationRun identity.

06.08. RuntimeHost does not own SaveBundle identity.

06.09. A RuntimeHost operation that requests Application creation follows the
      owning Application creation semantics.

06.10. A RuntimeHost operation that requests ApplicationRun creation follows
       DA-20 ApplicationRun creation semantics.

06.11. A RuntimeHost operation that creates a SaveBundle follows the
       Kernel-mediated creation path and the owning SaveBundle generation
       rules when such rules are defined.

06.12. A RuntimeHost operation that loads a SaveBundle follows the
       Kernel-mediated loading path and compatibility validation rules.

06.13. All entry surfaces that create a SaveBundle use the same
       Kernel-mediated creation path.

06.14. All entry surfaces that load existing SaveBundle state use the same
       Kernel-mediated loading path and compatibility validation path.

06.15. SaveBundle creation is not owned by CLI.

06.16. SaveBundle loading is not owned by CLI.

06.17. SaveBundle creation is not owned by browser launcher behavior.

06.18. SaveBundle loading is not owned by browser launcher behavior.

06.19. SaveBundle creation is not owned by external launcher behavior.

06.20. SaveBundle loading is not owned by external launcher behavior.

06.21. SaveBundle creation and loading remain Kernel-mediated runtime
       operations even when requested through a command surface, View,
       frontend client, test surface, launcher surface, or remote client.

06.22. A writable SaveBundle may be owned by at most one active
       ApplicationRun under the owning Application and SaveBundle rules.

06.23. RuntimeHost Workspace ownership does not make RuntimeHost the
       SaveBundle writer.

06.24. RuntimeHost Workspace ownership does not make adapter-executed code a
       SaveBundle writer.

06.25. RuntimeHost may host multiple ApplicationRuns, but ApplicationRun
       mutation still follows DA-24 single-lane rules inside each
       ApplicationRun unless an explicit concurrency mode defines otherwise.

06.26. RuntimeHost does not classify SaveBundle as a Pack.

06.27. SaveBundle may carry retained Pack or application material only under
       the owning SaveBundle and Pack documents.


===============================================================================
07. SHARED RUNTIME OPERATION COMPOSITION
===============================================================================

07.01. Startup modes are entry workflows over shared Kernel-mediated runtime
      operations.

07.02. Startup modes do not define independent Application, ApplicationRun,
      SaveBundle, ExecutionAdapter, RPC, capability, policy, persistence,
      OrchestrationUnit, Job, View, trace, export, comparison, Replay,
      Resume, or Retry semantics.

07.03. A command surface may select, compose, or request runtime operations.

07.04. A command surface does not redefine the runtime operations it requests.

07.05. A frontend, launcher surface, test surface, script, shortcut, batch file,
      packaged distribution surface, or remote client may select, compose, or
      request runtime operations.

07.06. A frontend, launcher surface, test surface, script, shortcut, batch file,
      packaged distribution surface, or remote client does not redefine the
      runtime operations it requests.

07.07. Runtime operations may include:
      - ResolveWorkspace
      - BindWorkspace
      - AcquireWorkspaceOwnership
      - ReleaseWorkspaceOwnership
      - StartRuntimeHost
      - StopRuntimeHost
      - ConnectRuntimeHost
      - DiscoverExistingRuntimeHost
      - ResolveAppPack
      - CreateApplication
      - CreateSaveBundle
      - LoadSaveBundle
      - ValidateSaveBundleCompatibility
      - BindSaveBundle
      - CreateApplicationRun
      - StartApplicationRun
      - StopApplicationRun
      - CreateView
      - BindFrontendClient
      - CreateEntrySurface
      - CloseEntrySurface
      - SelectExecutionAdapter
      - ActivateDeclaredArtifact
      - ClassifyCommand
      - DispatchCommand
      - ExposeLanSurface
      - CloseLanSurface
      - InspectRuntimeHost
      - InspectTraceEvidence
      - InspectPolicyDecisions

07.08. Runtime operation names in this section define semantic categories, not
      final API names.

07.09. Concrete API names and command syntax belong to implementation
      specifications.

07.10. RuntimeHost startup modes, command surfaces, launcher flows, browser
       flows, test flows, script flows, shortcut flows, packaged distribution
       flows, and remote-client flows do not create independent mutation paths.

07.11. When a runtime operation creates, loads, binds, migrates, starts,
       stops, recovers, or otherwise mutates Turnix-managed state, it enters
       the same Kernel-mediated orchestration, capability, policy,
       transaction, persistence, and trace boundaries as other mutation-
       bearing Turnix operations.

07.12. A RuntimeHost operation is a host-level requested action.

07.13. An OrchestrationUnit is the Kernel-tracked execution-authority unit
       used when that action performs or may perform orchestrated mutation.

07.14. RuntimeHost operations and OrchestrationUnits remain distinct.

07.15. A RuntimeHost operation may have a parent, cause, or correlation
       relationship to an OrchestrationUnit.

07.16. That relationship does not collapse runtimeHostId, runtime operation
       identity, or orchestrationUnitId into one identity.

07.17. ApplicationRun mutation follows deterministic single-lane
       orchestration under DA-24 unless another authoritative concurrency
       mode explicitly defines different behavior.

07.18. RuntimeHost operation completion, failure, cancellation, detachment,
       retention, stop, crash, or disconnect does not by itself define
       artifact/export success, missing-material semantics, ComparisonResult,
       Replay outcome, Resume outcome, Retry outcome, or audit workflow
       outcome.

07.19. An owning workflow may explicitly map a RuntimeHost operation outcome
       to another domain outcome when that workflow has authority to do so.

07.20. RuntimeHost operation composition may later include operations that
       manage local model-provider processes, external tools, or helper
       processes.

07.21. Such provider or helper process operations do not become DA-28-owned
       provider semantics unless a later authoritative document assigns that
       ownership to DA-28.

07.22. A temporary external launcher may perform provider or helper startup
       outside Turnix while Turnix lacks an owning runtime path.

07.23. Obsoleting such a temporary external launcher does not change
       RuntimeHost, Kernel, ApplicationRun, Workspace, or provider semantics.


===============================================================================
08. STARTUP MODES
===============================================================================

08.01. Startup mode selection determines how Turnix is entered.

08.02. Startup mode selection does not determine separate runtime semantics.

08.03. Startup modes may include:
      - interactive host mode
      - one-shot command mode
      - serve mode
      - connect mode
      - test mode
      - launcher mode

08.04. Interactive host mode means Turnix enters a command-accepting host or
      host-connected control surface.

08.05. One-shot command mode means Turnix performs a bounded requested command
      and exits after the command reaches the operation-defined result or
      error surface.

08.06. Serve mode means Turnix starts or keeps a RuntimeHost available for
      explicitly selected entry surfaces.

08.07. Connect mode means the command or client connects to an existing
      RuntimeHost instead of acquiring writable Workspace ownership for a new
      host.

08.08. Test mode means Turnix uses controlled test surfaces without weakening
      runtime, ExecutionAdapter, ApplicationRun, SaveBundle, orchestration,
      capability, policy, persistence, or trace boundaries.

08.09. Launcher mode means Turnix uses a user-facing launcher surface to
      select or request runtime operations.

08.10. Launcher mode is a convenience entry workflow.

08.11. Launcher mode is not a separate runtime architecture.

08.12. Launcher mode may be entered through a separate application, script,
       shortcut, batch file, graphical wrapper, packaged distribution surface,
       or another user-facing startup helper.

08.13. A launcher surface may exist before a RuntimeHost is started.

08.14. A launcher surface that starts Turnix requests a RuntimeHost path or
       another defined runtime operation.

08.15. A launcher surface that connects to Turnix requests connection to an
       existing RuntimeHost or entry surface.

08.16. A launcher surface does not own Kernel authority, RuntimeHost identity,
       Workspace ownership, ApplicationRun lifecycle, AppPack semantics,
       SaveBundle persistence, provider lifecycle, or Pack semantics.

08.17. A startup mode may start a RuntimeHost when the mode is defined to
       request a host path that acquires writable Workspace ownership through
       the Kernel-mediated RuntimeHost/Workspace ownership path.

08.18. A startup mode may connect to an existing RuntimeHost when the mode is
       defined as a client or control surface.

08.19. A startup mode may request Application or ApplicationRun work through
       shared Kernel-mediated runtime operations.

08.20. A startup mode that requests Application or ApplicationRun work does
       not create separate Application, ApplicationRun, SaveBundle,
       ExecutionAdapter, RPC, capability, policy, persistence,
       OrchestrationUnit, Job, View, trace, export, comparison, Replay,
       Resume, Retry, or audit workflow semantics.

08.21. Expected user-facing command shapes may include:
       - turnix host
       - turnix connect
       - turnix runapp

08.22. "turnix host" is expected command-surface shorthand for requesting a
       persistent RuntimeHost path.

08.23. "turnix connect" is expected command-surface shorthand for requesting a
       client or control surface connection to an existing RuntimeHost.

08.24. "turnix runapp" is expected command-surface shorthand for requesting
       Application or ApplicationRun work through shared Kernel-mediated
       runtime operations.

08.25. The command-shape examples in this section define expected semantic
       direction only.

08.26. The command-shape examples in this section do not lock concrete CLI
       spelling, argument syntax, flags, result envelopes, process behavior,
       shell behavior, or host-discovery mechanics.

08.27. A startup mode may fail when required Workspace ownership, host
       connection, policy, ExecutionAdapter, RPC, persistence, provider, or
       ApplicationRun conditions are not satisfied.

08.28. Startup mode failure is explicit and trace-visible.

08.29. Concrete command names, flags, environment variables, process
       behavior, launcher behavior, provider startup behavior, and shell
       behavior belong to implementation specifications.


===============================================================================
09. ENTRY SURFACES AND COMMAND SURFACES
===============================================================================

09.01. An entry surface is a controlled way to enter, observe, control, or
      interact with a RuntimeHost.

09.02. Entry surfaces may include:
      - CLI control surface
      - browser frontend surface
      - remote client surface
      - test surface
      - launcher surface
      - packaged distribution surface
      - future management surface

09.03. An entry surface is not authority by itself.

09.04. A command surface is an entry surface that receives, classifies, and
      dispatches user, tool, script, or client commands.

09.05. A command surface is not Kernel authority by itself.

09.06. CLI is a command surface or adapter into the RuntimeHost.

09.07. CLI is not Kernel by itself.

09.08. Browser frontend is a UI/frontend surface into RuntimeHost, mediated by
      the relevant ExecutionAdapter, RPC, and frontend runtime boundaries.

09.09. Browser frontend does not own authoritative state.

09.10. Browser frontend wording does not make frontend adapter realization the
       umbrella ExecutionAdapter concept.

09.11. A remote client is a client surface into a RuntimeHost.

09.12. A remote client does not own state authority.

09.13. A test surface provides controlled test entry and observation behavior.

09.14. A test surface does not weaken runtime authority boundaries merely
       because it exists for testing.

09.15. A launcher surface is a convenience entry surface that may request
       Turnix startup, RuntimeHost connection, ApplicationRun work,
       packaged-product selection, or other shared runtime operations.

09.16. A launcher surface may be a separate application, script, shortcut,
       batch file, graphical wrapper, packaged distribution surface, or other
       user-facing startup helper.

09.17. A launcher surface is not RuntimeHost.

09.18. A launcher surface is not Kernel authority.

09.19. A launcher surface does not own ApplicationRun lifecycle.

09.20. A launcher surface does not own Workspace ownership.

09.21. A launcher surface does not own AppPack semantics.

09.22. A launcher surface does not own SaveBundle persistence.

09.23. A launcher surface does not own provider lifecycle semantics.

09.24. A launcher surface may start helper processes outside Turnix only as an
       external implementation behavior.

09.25. External helper startup does not create Turnix guarantees unless the
       startup is accepted through Turnix-mediated runtime authority.

09.26. A temporary external launcher may exist before Turnix owns a startup,
       provider, or helper-process management path.

09.27. Obsoleting a temporary external launcher does not change Turnix
       platform semantics.

09.28. A packaged distribution surface is an entry surface provided by a
       packaged application or game distribution.

09.29. A packaged application or game distribution may bundle Turnix runtime
       material, one or more AppPacks, preinstalled Packs, assets, defaults,
       launcher surfaces, and convenience startup behavior.

09.30. A packaged application or game distribution is a distribution shape.

09.31. A packaged application or game distribution is not Turnix platform
       identity.

09.32. A packaged application or game distribution does not create separate
       RuntimeHost, ApplicationRun, Pack, SaveBundle, Workspace, Kernel,
       ExecutionAdapter, capability, policy, persistence, trace, artifact,
       export, comparison, Replay, Resume, Retry, or audit workflow semantics.

09.33. A client surface is an entry surface that connects to, observes,
       controls, or interacts with a RuntimeHost through Turnix-mediated
       boundaries.

09.34. A client surface is not RuntimeHost by itself.

09.35. A client surface is not Kernel authority by itself.

09.36. A frontend client is a DA-22 frontend runtime concept when the connected
       client participates through UI, View, or frontend runtime semantics.

09.37. A frontend client may be an entry surface into a RuntimeHost only when
       RuntimeHost entry-surface rules and DA-22 frontend rules both define
       that relationship.

09.38. Client instance wording does not define a canonical RuntimeHost alias.

09.39. Client instance wording may describe one concrete connected client
       participant only when the owning UI, RPC, LAN, command-surface, or
       implementation specification defines that participant.

09.40. Entry surfaces submit commands, requests, decisions, interactions,
       subscriptions, cancellations, or connection attempts through Turnix-
       mediated boundaries.

09.41. Entry-surface input becomes meaningful only when Kernel-owned
       authority accepts the corresponding command, request, decision,
       capability call, RPC message, runtime operation, or policy path.

09.42. Entry surface readiness does not imply RuntimeHost readiness.

09.43. Launcher surface readiness does not imply RuntimeHost readiness.

09.44. Packaged distribution surface readiness does not imply RuntimeHost
       readiness.

09.45. RuntimeHost readiness does not imply ApplicationRun readiness.

09.46. RuntimeHost readiness does not imply ExecutionAdapter readiness.

      - inspect policy decisions
      - serve frontend
      - expose LAN surface
      - close entry surface

10.02. Command categories in this section define semantic categories, not
      final CLI syntax.

10.03. "start host" means requesting a RuntimeHost path that starts or keeps a

10.04. "connect to host" means requesting a client or control surface path to
      an existing RuntimeHost.

10.05. "run AppPack" means requesting Application or ApplicationRun work based

10.06. "run AppPack" does not mean that a command surface, CLI command, client
      surface, launcher surface, packaged distribution surface, or RuntimeHost

10.07. Command receipt is not command acceptance.

10.08. Command acceptance is not command completion.

10.09. Command completion is not Job success unless the command contract
      defines that relationship through the owning Job workflow.

10.10. A command that requests Application creation follows the owning
       Application creation semantics.

10.11. A command that requests ApplicationRun creation follows DA-20.

10.12. A command that creates or loads a SaveBundle follows the owning
       SaveBundle and persistence semantics.

10.13. A command that communicates through RPC follows DA-21.

10.14. A command that affects UI or View behavior follows DA-22.

10.15. A command that starts adapter execution follows DA-23 and DA-27.

10.16. A command that mutates Turnix-managed state follows DA-04 and DA-24.

10.17. A command that performs persistent I/O follows DA-07.

10.18. A command that invokes a capability follows DA-16.

10.19. A command that requires policy or user decision follows DA-17.

10.20. A command that creates, observes, cancels, or retrieves Job-backed
       work follows DA-19.

10.21. A command that starts, stops, discovers, or depends on a model provider,
       helper process, external tool, or adjacent service follows the owning
       service, capability, adapter, provider, or implementation
       specification.

10.22. DA-28 does not define model-provider lifecycle semantics merely because
       a RuntimeHost command or launcher surface can request provider-related
       work.

10.23. A command that is rejected before ApplicationRun creation does not
       create a partial ApplicationRun.

10.24. A command that is rejected before SaveBundle creation or loading does

10.25. A command that is rejected before Job-backed work exists does not

10.26. A command that is rejected before adapter-mediated work exists does

10.28. A command that is rejected before provider-related work exists does not
       create a provider lifecycle outcome unless the owning provider workflow

11. SECOND HOST AND EXISTING HOST BEHAVIOR
===============================================================================

11.01. If a Workspace is already owned, a new RuntimeHost does not silently
      take writable ownership.

11.02. A command may connect to the existing RuntimeHost when the command is
      a client or control operation and policy permits that path.

11.03. A command may fail with explicit ownership evidence when the Workspace
      is already owned.

11.04. A command may request stale-owner recovery only through explicit policy
      or tooling rules.

11.05. A command may open read-only inspection only through explicit tooling
      or policy rules.

11.06. A second RuntimeHost does not silently discard another RuntimeHost's
      ownership evidence.

11.07. A second RuntimeHost does not silently supersede another RuntimeHost.

11.08. A second RuntimeHost does not silently detach work from another
      RuntimeHost.

11.09. A second RuntimeHost does not silently claim results, Jobs, Views,
      ExecutionAdapters, Applications, ApplicationRuns, or SaveBundles owned
      by another RuntimeHost or TurnixRuntime authority domain.

11.10. Existing-host discovery, host connection, host unreachable handling,
       stale-owner recovery, and host handoff implementation details belong
       to later implementation specifications.

11.11. A launcher surface may connect to an existing RuntimeHost when it acts
       as a client or control operation and policy permits that path.

11.12. A launcher surface does not silently start a second writable
       RuntimeHost merely because the launcher is user-facing.

11.13. A packaged distribution surface does not silently start a second
       writable RuntimeHost merely because the product was launched by a
       bundled shortcut, executable, script, or wrapper.

12. LOCAL-FIRST AND LAN EXPOSURE
===============================================================================

12.01. Turnix is local-first, not local-only.

12.02. Local-first does not require same-machine execution.

12.03. Local-first means the authoritative runtime and state remain under
      user-controlled local infrastructure.

12.04. Valid local-first forms include:
      - same-machine RuntimeHost and frontend
      - LAN machine hosting RuntimeHost with another machine as frontend
      - home server hosting RuntimeHost and SaveBundle state
      - powerful local AI machine hosting RuntimeHost-adjacent execution with
        a lighter client presentation surface

12.05. Local-first does not prohibit explicit, policy-governed LAN mode,
      server hosting, remote-resource mode, federated discovery, or remote
      clients.

12.06. LAN exposure is explicit and policy-governed.

12.07. RuntimeHost does not silently expose itself to LAN clients.

12.08. RuntimeHost does not silently expose itself to internet clients.

12.09. Default local bind behavior remains implementation-specific but does
      not silently expose runtime control surfaces beyond the configured
      local boundary.

12.10. LAN or remote access does not imply remote state authority.

12.11. LAN or remote access does not imply adapter execution authority.

12.12. LAN or remote access does not imply persistence authority.

12.13. LAN or remote access does not imply capability permission.

12.14. LAN or remote access does not imply user identity.

12.15. Pairing, authentication, token, certificate, local-network discovery,
       firewall, and concrete bind behavior belong to implementation
       specifications or security policy documents.

12.16. A launcher surface or packaged distribution surface does not silently
       change LAN or remote exposure policy.

12.17. A packaged distribution may choose user-facing defaults only within
       the policy and implementation rules that own those defaults.

13. RUNTIMEHOST LIFECYCLE
===============================================================================

13.01. RuntimeHost lifecycle phases may include:
      - requested
      - starting
      - Workspace binding
      - ownership acquired
      - active
      - stopping
      - stopped
      - failed
      - crashed
      - closed

13.02. Concrete implementations may use additional internal states if those
      states preserve the externally visible meanings defined here.

13.03. requested means RuntimeHost start or connection work has been requested
      but host startup or connection has not yet begun.

13.04. starting means Turnix is preparing RuntimeHost identity,
      configuration, Kernel access, and required runtime inputs.

13.05. Workspace binding means Turnix is resolving, validating, creating,
      loading, or binding the Workspace or runtime scope.

13.06. ownership acquired means the RuntimeHost active path has acquired the
      Workspace or runtime ownership needed for its requested writable
      behavior.

13.07. active means the RuntimeHost active region exists and entry surfaces
      may operate according to policy and implementation support.

13.08. stopping means Turnix is intentionally ending the RuntimeHost active
      region.

13.09. stopped means RuntimeHost ended through normal controlled shutdown.

13.10. failed means RuntimeHost lifecycle could not continue because an
       error prevented valid start, Workspace binding, ownership acquisition,
       or controlled operation.

13.11. crashed means the RuntimeHost active region ended because runtime
       continuity failed unexpectedly.

13.12. closed means RuntimeHost identity has been released and is no longer
       usable for new runtime work.

13.13. RuntimeHost lifecycle is distinct from Application lifecycle.

13.14. RuntimeHost lifecycle is distinct from ApplicationRun lifecycle.

13.15. RuntimeHost lifecycle is distinct from SaveBundle lifecycle.

13.16. RuntimeHost lifecycle is distinct from View lifecycle.

13.17. RuntimeHost lifecycle is distinct from ExecutionAdapter lifecycle.

13.18. RuntimeHost lifecycle is distinct from RPC transport lifecycle.

13.19. RuntimeHost lifecycle is distinct from Job lifecycle.

13.20. RuntimeHost lifecycle is distinct from OrchestrationUnit lifecycle.

13.21. RuntimeHost lifecycle is distinct from launcher surface lifecycle.

13.22. RuntimeHost lifecycle is distinct from packaged distribution lifecycle.

13.23. RuntimeHost lifecycle is distinct from provider lifecycle unless an
       owning provider workflow explicitly defines a relationship.

13.24. RuntimeHost stop does not by itself define Job terminal outcome.

13.25. RuntimeHost stop does not by itself define OrchestrationUnit terminal
       outcome.

13.26. RuntimeHost stop does not by itself finalize a Window.

13.27. RuntimeHost failure does not by itself create an AbortedWindow.

13.28. RuntimeHost crash does not silently redefine committed-state meaning.

13.29. RuntimeHost stop, failure, crash, or disconnect does not by itself
       define artifact/export success, ComparisonResult, Replay outcome,
       Resume outcome, Retry outcome, or audit workflow outcome.

13.30. RuntimeHost stop, failure, crash, or disconnect does not by itself
       define provider stop, provider failure, provider crash, or provider
       retained-result outcome.

13.31. If RuntimeHost lifecycle affects Applications, ApplicationRuns,
       SaveBundles, Jobs, Views, ExecutionAdapters, OrchestrationUnits,
       decisions, Windows, artifacts, exports, retained workflows, providers,
       helper processes, launcher surfaces, or packaged distribution surfaces,
       the relationship is explicit, policy-governed where applicable, and
       trace-visible.
