===============================================================================
IMPLEMENTATION SPECIFICATION IS-10 - DEFAULT LAUNCHER APPPACK AND TOOL STATE CONTEXT
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the concrete default launcher startup flow, the replaceable Turnix
Default Launcher AppPack role, launcher ApplicationRun creation and start,
Launcher Main Menu behavior, ToolStateContext placement under userdata,
temporary tool-state fallback, launcher use of RuntimeHost and PackManager
operations, and launcher exit versus RuntimeHost shutdown behavior.

This document implements the launcher-facing runtime flow described by the
owning runtime, application, frontend, RuntimeHost, PackManager, and catalog
operation specifications.

Purpose:
--------
This document defines the default launcher as an ordinary replaceable AppPack
that presents startup interaction without becoming Kernel, RuntimeHost,
PackManager, catalog, SaveBundle, Application, or ApplicationRun authority.

It defines:
- Turnix Default Launcher as the default first-party launcher AppPack
- launcher ApplicationRun creation and start
- launcher Application identity when durable launcher identity is used
- Launcher Main Menu screen meaning
- New, Load, Settings, and Exit launcher actions
- launcher use of catalog and PackManager operations
- ToolStateContext as launcher/tool state stored under userdata
- persistent and temporary ToolStateContext behavior
- launcher state placement rules
- launcher exit versus RuntimeHost shutdown behavior
- launcher trace reason usage

It does NOT define:
- root discovery boundaries or root semantics (see DA-09)
- pack identity, hierarchy, or visibility semantics (see DA-10)
- generic resolution mechanics (see DA-11)
- importing or module-loading behavior (see DA-12)
- dependency and advisory relation semantics (see DA-13)
- activation lifecycle or PackContext authority (see DA-14)
- service, capability, permission, or Job-backed capability semantics
  (see DA-16)
- user decision or remembered policy semantics (see DA-17)
- Job lifecycle, timeout, cancellation, progress, or result semantics
  (see DA-19)
- Application lifecycle or ApplicationRun lifecycle semantics
- RPC, channel, or transport semantics (see DA-21)
- UI, View, or frontend runtime semantics (see DA-22)
- execution adapter authority or adapter lifecycle semantics (see DA-23 and
  DA-27)
- RuntimeHost lifecycle, workspace ownership, startup mode, or command-surface
  semantics (see DA-28)
- PackManager semantics (see DA-29)
- concrete pack or SaveBundle listing operation envelopes (see IS-09)
- ToolStateContext schema or path encoding
- concrete browser layout, component implementation, CSS, or JavaScript module
  syntax
- concrete CLI syntax
- concrete JSON-RPC or WebSocket envelope fields

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and document
      context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines implementation-level default launcher and
      ToolStateContext contracts within that shared interpretation model.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. Default launcher behavior answers:

          "How does Turnix present a default New, Load, Settings, and Exit
           surface without making the launcher special runtime authority?"

02.02. Turnix Default Launcher is a first-party launcher AppPack.

02.03. Turnix Default Launcher is replaceable by configuration, policy, or
      later launcher-selection rules.

02.04. Turnix Default Launcher is not Kernel.

02.05. Turnix Default Launcher is not RuntimeHost.

02.06. Turnix Default Launcher is not PackManager.

02.07. Turnix Default Launcher is not a pack catalog.

02.08. Turnix Default Launcher is not a SaveBundle manager by itself.

02.09. Turnix Default Launcher runs as an ApplicationRun when launched.

02.10. Launcher UI is presentation and interaction.

02.11. Launcher actions request RuntimeHost, PackManager, catalog, settings,
       Application, ApplicationRun, or SaveBundle operations through
       Turnix-mediated boundaries.

02.12. The launcher does not own the operations it presents.


===============================================================================
03. LAUNCHER IDENTITY
===============================================================================

03.01. The default first-party launcher name is:
      Turnix Default Launcher

03.02. The default launcher is identified as an AppPack by normal pack identity
      rules.

03.03. The exact default launcher pack identity remains implementation-defined
      until locked by a manifest or implementation specification.

03.04. The user-facing name Turnix Default Launcher is not a stable pack
      identity by itself.

03.05. Replacing the default launcher changes which AppPack is requested for
      launcher startup.

03.06. A later launcher-selection rule may allow an accepted launcher
      AppDefinition source that is not a discovered first-party AppPack.

03.07. Replacing the default launcher does not redefine RuntimeHost, catalog,
      PackManager, SaveBundle, Application, ApplicationRun, or activation
      semantics.

03.08. A replacement launcher receives no authority merely because it is the
      configured launcher.

03.09. A replacement launcher remains subject to pack, activation, adapter,
      capability, policy, UI, and persistence boundaries.


===============================================================================
04. LAUNCHER STARTUP FLOW
===============================================================================

04.01. A RuntimeHost startup workflow may request the default launcher after
      the RuntimeHost reaches the required startup state.

04.02. Launcher startup uses normal RuntimeHost operation composition.

04.03. Launcher startup normally performs:
      1) resolve configured launcher AppPack or accepted AppDefinition
      2) create or load ToolStateContext
      3) create or locate launcher Application when durable identity is used
      4) create Launcher ApplicationRun
      5) start Launcher ApplicationRun
      6) create launcher View
      7) bind frontend client when a frontend surface is used

04.04. Launcher startup does not create a user Application.

04.05. Launcher startup does not create a user ApplicationRun.

04.06. Launcher startup does not create a normal user SaveBundle.

04.07. Launcher startup does not list packs or SaveBundles by itself unless the
      launcher requests a catalog operation for presentation.

04.08. Launcher startup failure is explicit and trace-visible.

04.09. If the configured launcher AppPack or accepted launcher AppDefinition
      source cannot be resolved, launcher startup fails unless an explicit
      fallback launcher or recovery policy is defined and accepted.

04.10. Fallback launcher selection is explicit and trace-visible.

04.11. Silent fallback to another launcher is not supported.


===============================================================================
05. LAUNCHER APPLICATION AND APPLICATIONRUN
===============================================================================

05.01. The launcher runs as an ApplicationRun.

05.02. A launcher Application may provide durable launcher identity when the
      startup workflow uses durable launcher identity.

05.03. Launcher Application identity is distinct from RuntimeHost identity.

05.04. Launcher Application identity is distinct from ToolStateContext identity.

05.05. Launcher ApplicationRun identity is distinct from RuntimeHost identity.

05.06. Launcher ApplicationRun identity is distinct from View identity.

05.07. Launcher ApplicationRun creation follows the owning ApplicationRun
      lifecycle specifications.

05.08. Launcher activation follows DA-14.

05.09. Launcher frontend runtime follows DA-22, DA-23, and DA-27.

05.10. Launcher ApplicationRun may coexist with user ApplicationRuns when
       RuntimeHost policy and implementation support multiple active runs.

05.11. Launching a user ApplicationRun does not require stopping the launcher
       ApplicationRun unless the startup workflow, launcher policy, or user
       command explicitly requests that outcome.

05.12. Launcher ApplicationRun stop does not by itself stop RuntimeHost unless
       the RuntimeHost startup workflow defines the launcher as the bounded
       reason for the RuntimeHost to exist.


===============================================================================
06. TOOLSTATECONTEXT
===============================================================================

06.01. ToolStateContext stores durable or temporary state for Turnix launcher
      and tool ApplicationRuns.

06.02. Turnix Default Launcher uses a ToolStateContext by default.

06.03. ToolStateContext is a tool-state persistence context stored under
      userdata.

06.04. ToolStateContext is separate from normal user SaveBundles.

06.05. A later ToolStateContext specification may define a special
      SaveBundle-like representation for tool Applications.

06.06. Such a representation does not make ToolStateContext a normal user
      SaveBundle.

06.07. ToolStateContext is not a Pack.

06.08. ToolStateContext is not AppPack content.

06.09. ToolStateContext is not a content root.

06.10. ToolStateContext is not normal user SaveBundle state.

06.11. ToolStateContext is not listed by normal user SaveBundle listing.

06.12. ToolStateContext may be listed only by explicit tooling, diagnostics,
       inspection, or tool-state operations when such operations are defined
       and permitted.

06.13. ToolStateContext may store:
       - launcher UI preferences
       - recent AppPack references
       - recent SaveBundle references
       - last selected workspace reference
       - launcher layout state
       - launcher filter or sort preferences
       - dismissed launcher hints
       - tool-local cache metadata

06.14. ToolStateContext does not store normal user application executed state.

06.15. ToolStateContext does not replace configuration state owned by DA-06.

06.16. ToolStateContext does not replace remembered policy decisions owned by
       DA-17.

06.17. ToolStateContext does not grant PackManager authority.

06.18. ToolStateContext does not grant raw filesystem authority.


===============================================================================
07. TOOLSTATECONTEXT PLACEMENT
===============================================================================

07.01. Persistent ToolStateContext is stored under userdata.

07.02. Persistent ToolStateContext is not stored under the launcher AppPack
      content directory.

07.03. Persistent ToolStateContext is not stored under first-party,
      third-party, or custom content roots as pack content.

07.04. Persistent ToolStateContext is not stored under normal user
      SaveBundles.

07.05. A recommended abstract location form is:
      userdata/tool-state/<packIdentity>/

07.06. The exact path encoding for <packIdentity> remains
      implementation-defined.

07.07. Pack identity path encoding avoids ambiguity, unsafe path characters,
      and filesystem-dependent identity interpretation.

07.08. ToolStateContext writes follow Kernel-mediated persistence and
      configuration/state authority.

07.09. ToolStateContext placement does not make userdata a content root.

07.10. ToolStateContext placement does not make the launcher AppPack writable
       by runtime execution.


===============================================================================
08. PERSISTENT AND TEMPORARY TOOL STATE
===============================================================================

08.01. ToolStateContext may be persistent or temporary.

08.02. Persistent ToolStateContext writes durable tool state under userdata.

08.03. Temporary ToolStateContext stores tool state only for the current runtime
      lifetime.

08.04. Temporary ToolStateContext may be used when:
      - userdata is unavailable
      - persistence fails and the launcher permits temporary fallback
      - safe mode is active
      - recovery mode is active
      - test mode requests temporary state
      - read-only inspection mode requests no persisted launcher state

08.05. Temporary ToolStateContext use is explicit and trace-visible.

08.06. Temporary ToolStateContext is not silently presented as persistent state.

08.07. Launcher UI presents that launcher state is temporary when that
      information is relevant to user expectations.

08.08. A launcher may declare persistent tool state required when such a
      declaration mechanism is defined.

08.09. If persistent tool state is required and unavailable, launcher startup
      fails explicitly unless policy selects another valid launcher path.

08.10. Turnix Default Launcher supports temporary ToolStateContext when normal
       persistence is unavailable and no hard policy forbids that mode.


===============================================================================
09. LAUNCHER MAIN MENU
===============================================================================

09.01. Launcher Main Menu is the default primary View state of Turnix Default
      Launcher.

09.02. Launcher Main Menu presents:
      - New
      - Load
      - Settings
      - Exit

09.03. These labels are user-facing presentation labels.

09.04. The labels do not define authority by themselves.

09.05. The labels do not define concrete component layout, exact UX behavior,
      exact command identifiers, or fixed localization text.

09.06. Launcher Main Menu may present additional diagnostics, warnings,
      temporary-state notices, current workspace information, or active-host
      information when available.

09.07. Launcher Main Menu presentation does not mutate state by itself.

09.08. User interaction becomes meaningful only when Turnix accepts the
      corresponding command, capability request, RPC message, decision, or
      RuntimeHost operation.


===============================================================================
10. NEW ACTION
===============================================================================

10.01. New presents or requests creation of a new user Application and
      ApplicationRun path.

10.02. New normally requests AppPack listing by using ListPacks with AppPack
      kind filtering under IS-09.

10.03. New does not own AppPack listing semantics.

10.04. New does not own SaveBundle creation semantics.

10.05. New does not own Application creation semantics.

10.06. New does not own ApplicationRun creation semantics.

10.07. Selecting an AppPack for New does not create an Application or
      SaveBundle until the corresponding create-new operation is accepted.

10.08. Create-new operation composition may include:
      - ResolveAppPack or accepted AppDefinition source
      - CreateApplication when needed
      - CreateSaveBundle or create Application persistence closure
      - ValidateSaveBundleCompatibility
      - BindSaveBundle or bind Application persistence context
      - CreateApplicationRun
      - StartApplicationRun
      - CreateView when applicable

10.09. Those operation categories remain owned by RuntimeHost, Application,
      ApplicationRun, SaveBundle, persistence, PackManager, activation, and
      UI documents.

10.10. New cannot silently create a separate SaveBundle creation path for the
       launcher.

10.11. New uses the same Kernel-mediated new Application and SaveBundle path
       as other entry surfaces.


===============================================================================
11. LOAD ACTION
===============================================================================

11.01. Load presents or requests loading of an existing user SaveBundle or
      accepted persistence context.

11.02. Load normally requests a SaveBundle listing operation under IS-09.

11.03. Load does not own SaveBundle listing semantics.

11.04. Load does not load a SaveBundle merely by listing SaveBundles.

11.05. Selecting a SaveBundle does not bind or migrate the SaveBundle until the
      corresponding load operation is accepted.

11.06. Load operation composition may include:
      - ListSaveBundles or the accepted SaveBundle listing operation
      - Resolve AppPack or accepted AppDefinition source associated with the
        selected SaveBundle
      - LoadSaveBundle
      - ValidateSaveBundleCompatibility
      - Check last-used or last-known-good graph evidence
      - BindSaveBundle or bind Application persistence context
      - CreateApplicationRun
      - StartApplicationRun
      - CreateView when applicable

11.07. SaveBundle compatibility and graph checks may use PackManager behavior
      defined by DA-29 and later implementation specifications.

11.08. Load cannot silently create a separate SaveBundle loading path for the
      launcher.

11.09. Load uses the same Kernel-mediated existing Application and SaveBundle
      path as other entry surfaces.


===============================================================================
12. SETTINGS ACTION
===============================================================================

12.01. Settings presents or requests settings inspection or mutation surfaces.

12.02. Settings may include categories such as:
      - Turnix
      - Workspace
      - Launcher
      - PackManager
      - Adapters
      - Policy
      - Paths and roots

12.03. Settings listing is read-only unless the user submits a concrete change.

12.04. Launcher-local settings may be persisted in ToolStateContext.

12.05. Launcher-local settings stored in ToolStateContext do not become global
      configuration, workspace configuration, SaveBundle committed state, or
      policy decisions merely because the launcher presents them.

12.06. RuntimeHost or workspace settings remain governed by configuration,
      persistence, policy, and RuntimeHost documents.

12.07. Remembered decisions remain governed by DA-17.

12.08. Settings UI distinguishes temporary, launcher-local, workspace, global,
      save-scoped, and policy-scoped persistence when such distinctions are
      available.

12.09. Frontend-side settings drafts are presentation state until accepted by a
      Kernel-mediated mutation path.

12.10. Settings does not mutate configuration merely by being opened.


===============================================================================
13. EXIT ACTION
===============================================================================

13.01. Exit requests ending the current launcher interaction or launcher
      ApplicationRun according to the active startup workflow.

13.02. Exit does not always mean RuntimeHost shutdown.

13.03. Exit stops the launcher ApplicationRun when accepted as launcher exit.

13.04. RuntimeHost shutdown requires either:
      - a startup workflow where the launcher is the bounded reason for the
        RuntimeHost to exist
      - an explicit host-stop, quit, shutdown, or equivalent accepted command
      - a policy-defined shutdown path

13.05. In bounded launcher startup, Exit may stop the launcher
      ApplicationRun and then stop RuntimeHost when no retained work,
      active ApplicationRuns, required entry surfaces, or host policy
      requires RuntimeHost to remain active.

13.06. In serve mode or persistent RuntimeHost mode, Exit stops or closes the
      launcher surface without stopping RuntimeHost unless an explicit
      RuntimeHost shutdown command is accepted.

13.07. In one-shot run or load mode, RuntimeHost may stop after the requested
      work finishes and no further work remains, independent of launcher Exit.

13.08. If other ApplicationRuns or Jobs are active, Exit does not silently stop
      them.

13.09. If Exit would affect active ApplicationRuns, Jobs, Views, adapters,
      OrchestrationUnits, retained work, or required entry surfaces, policy or
      user decision governs the outcome.

13.10. The UI may present separate labels such as Close Launcher and Quit
       Turnix when both meanings are available.

13.11. Presentation labels do not collapse launcher exit and RuntimeHost
       shutdown semantics.


===============================================================================
14. LAUNCHER USE OF PACKMANAGER AND CATALOG OPERATIONS
===============================================================================

14.01. Launcher uses PackManager and catalog operations as a client surface.

14.02. Launcher does not own PackManager semantics.

14.03. Launcher does not own ListPacks semantics.

14.04. Launcher does not own SaveBundle listing semantics.

14.05. Launcher does not own graph preparation semantics.

14.06. Launcher does not own package install, update, remove, search, or source
      management semantics.

14.07. Launcher may display PackManager Views or PackManager UI fragments.

14.08. Displaying PackManager UI does not grant PackManager authority to the
      launcher AppPack.

14.09. Launcher requests PackManager operations through RuntimeHost, capability,
      RPC, command, or equivalent mediated surfaces.

14.10. PackManager operations that modify packs, roots, selected graphs,
       SaveBundles, configuration, or policy remain subject to DA-29 and owning
       authority documents.


===============================================================================
15. LAUNCHER ACCESS AND PERMISSION BOUNDARY
===============================================================================

15.01. Launcher AppPack authority is ordinary AppPack authority.

15.02. Launcher AppPack authority does not include raw Kernel internals.

15.03. Launcher AppPack authority does not include unrestricted filesystem
      access.

15.04. Launcher AppPack authority does not include unrestricted PackManager
      operations.

15.05. Launcher AppPack authority does not include unrestricted SaveBundle
      mutation.

15.06. Launcher AppPack authority does not include unrestricted Application or
      ApplicationRun lifecycle authority.

15.07. Launcher frontend runtime does not directly mutate committed state,
      ToolStateContext, configuration, roots, packs, SaveBundles, selected
      graphs, or policy.

15.08. Launcher operations that require authority are mediated by Kernel-owned
      command, capability, policy, persistence, transaction, and trace
      boundaries.

15.09. Replacement launchers follow the same rules.


===============================================================================
16. TRACE AND OBSERVABILITY
===============================================================================

16.01. Launcher startup, ToolStateContext handling, launcher actions, and
      launcher exit remain trace-visible.

16.02. Launcher flow may use RuntimeHost-domain trace reasons owned by DA-28.

16.03. Launcher UI and View behavior may use UI-domain trace reasons owned by
      DA-22.

16.04. Launcher Application and ApplicationRun lifecycle may use trace reasons
      owned by the relevant lifecycle specifications.

16.05. Launcher activation uses activation-domain trace reasons owned by DA-14.

16.06. Launcher PackManager/catalog requests use PackManager-domain trace
      reasons owned by DA-29 and listing operation behavior from IS-09.

16.07. Launcher trace evidence records enough context, when available, to
      explain:
      - runtimeHostId
      - launcher AppPack identity
      - launcher applicationId when applicable
      - launcher applicationRunId when applicable
      - ToolStateContext identity or temporary-state marker
      - viewId when applicable
      - frontend client identity when applicable
      - startup mode
      - launcher action
      - requested operation identity when applicable
      - selected AppPack identity when applicable
      - selected SaveBundle identity when applicable
      - policy decision identity when applicable
      - failure reason category when failure occurs

16.08. Serialized trace records use IS-08 when written through the shared trace
      record envelope.

16.09. Launcher trace evidence does not replace RuntimeHost, Application,
      ApplicationRun, UI, activation, PackManager, catalog, decision,
      persistence, capability, or SaveBundle trace evidence.


===============================================================================
17. FAILURE CATEGORIES
===============================================================================

17.01. Launcher failure categories include:
      - LauncherSourceResolutionFailed
      - LauncherActivationFailed
      - LauncherViewCreationFailed
      - ToolStateContextCreateFailed
      - ToolStateContextLoadFailed
      - ToolStateContextPersistenceUnavailable
      - TemporaryToolStateContextRejected
      - LauncherActionRejected
      - LauncherActionFailed
      - LauncherExitDenied
      - RuntimeHostShutdownDenied

17.02. LauncherSourceResolutionFailed means the configured launcher AppPack or
      accepted launcher AppDefinition source could not be resolved.

17.03. LauncherActivationFailed means launcher AppPack activation failed.

17.04. LauncherViewCreationFailed means the launcher View could not be created
      or bound.

17.05. ToolStateContextCreateFailed means persistent ToolStateContext creation
      failed.

17.06. ToolStateContextLoadFailed means persistent ToolStateContext loading
      failed.

17.07. ToolStateContextPersistenceUnavailable means persistence required for
      persistent ToolStateContext was unavailable.

17.08. TemporaryToolStateContextRejected means temporary fallback was not
      allowed.

17.09. LauncherActionRejected means a launcher action was rejected before the
      requested operation was accepted.

17.10. LauncherActionFailed means an accepted launcher action failed.

17.11. LauncherExitDenied means launcher exit was denied by policy, active
       work, or lifecycle handling.

17.12. RuntimeHostShutdownDenied means a requested RuntimeHost shutdown was
       denied.

17.13. Launcher failure categories are not Job terminal outcomes unless a
       Job-owning workflow explicitly maps them under DA-19.

17.14. Launcher failure categories are not activation outcomes except where
       DA-14 activation failure actually occurred.

18.01. Future implementation specifications may define:

       - concrete ToolStateContext path encoding
       - concrete launcher View layout
       - concrete launcher command identifiers
       - concrete settings operation envelopes
       - concrete PackManager View embedding behavior
       - concrete launcher trace field schema

18.02. Future implementation specifications do not redefine:
       - launcher as replaceable AppPack
       - launcher Application and ApplicationRun boundary
       - ToolStateContext placement under userdata

       - launcher not owning PackManager, catalog, or settings semantics

18.03. If a launcher implementation requires a semantic rule not defined here,
      this document is updated first or alongside that implementation
      specification.


===============================================================================
19. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

19.01. The following are not supported:
      - treating Turnix Default Launcher as Kernel
      - treating Turnix Default Launcher as RuntimeHost
      - treating Turnix Default Launcher as PackManager
      - treating launcher View as authority by itself
      - treating replacement launcher status as extra authority
      - storing launcher runtime state under the launcher AppPack content
        directory
      - storing launcher runtime state under normal user SaveBundles by default
      - listing ToolStateContext through normal user SaveBundle listing
      - silently creating a normal user SaveBundle for launcher state
      - silently falling back to another launcher
      - silently treating temporary ToolStateContext as persistent
      - launcher-owned ListPacks semantics
      - launcher-owned SaveBundle listing semantics
      - launcher-owned SaveBundle creation semantics
      - launcher-owned SaveBundle loading semantics
      - launcher-owned Application creation semantics
      - launcher-owned ApplicationRun creation semantics
      - launcher-owned PackManager semantics
      - opening Settings mutating configuration by itself
      - Exit always meaning RuntimeHost shutdown
      - RuntimeHost shutdown occurring silently because launcher ApplicationRun
        stopped
      - stopping active ApplicationRuns, Jobs, adapters, Views, or retained
        work silently from launcher Exit

===============================================================================
21. LOCKED SUMMARY
===============================================================================

21.01. LOCKED:
      - Turnix Default Launcher is a first-party launcher AppPack.
      - Turnix Default Launcher is replaceable.
      - Launcher status does not grant special Kernel, RuntimeHost,
        PackManager, SaveBundle, Application, ApplicationRun, catalog, or
        persistence authority.
      - Launcher runs as an ApplicationRun.
      - Launcher startup resolves launcher AppPack or accepted AppDefinition,
        creates or loads ToolStateContext, creates or locates launcher
        Application when durable identity is used, creates Launcher
        ApplicationRun, starts it, and creates a launcher View when applicable.
      - ToolStateContext stores launcher/tool state.
      - ToolStateContext is a tool-state persistence context under userdata.
      - ToolStateContext is separate from normal user SaveBundles.
      - ToolStateContext is not AppPack content.
      - ToolStateContext is not a content root.
      - ToolStateContext is not listed by normal user SaveBundle listing.
      - Temporary ToolStateContext use is explicit and trace-visible.
      - Launcher Main Menu presents New, Load, Settings, and Exit.
      - New uses AppPack listing and Kernel-mediated Application,
        ApplicationRun, and SaveBundle paths.
      - Load uses SaveBundle listing and Kernel-mediated existing
        ApplicationRun and SaveBundle paths.
      - Settings does not mutate configuration merely by being opened.
      - Exit stops launcher interaction or launcher ApplicationRun according to
        the active startup workflow.
      - Exit does not always mean RuntimeHost shutdown.
      - Launcher uses PackManager and catalog operations as a client surface.
      - Launcher does not own PackManager, ListPacks, or SaveBundle listing
        semantics.
      - Launcher operations that require authority are mediated by Kernel-owned
        command, capability, policy, persistence, transaction, and trace
        boundaries.
      - Launcher flow remains trace-visible and uses IS-08 serialization when
        trace records are serialized.

21.02. OPEN:
      - concrete launcher identity, manifest shape, ToolStateContext schema,
        path encoding, View layout, settings envelopes, action identifiers,
        bounded startup policy, multi-ApplicationRun coexistence, PackManager
        View embedding, and launcher trace fields.
