===============================================================================
IMPLEMENTATION SPECIFICATION IS-03 - WORKSPACE OWNERSHIP AND HOST LOCKING
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the concrete Workspace ownership record, host-lock acquisition flow,
release flow, stale-owner handling, read-only inspection classification, and
trace mapping for RuntimeHost-mediated Workspace ownership.

This document implements Workspace ownership evidence and host-lock behavior.
It remains constrained by RuntimeHost, Application, ApplicationRun,
SaveBundle, committed-state, persistence, and policy semantics owned by their
higher design documents.

Purpose:
--------
This document defines how Turnix records and verifies exclusive writable
Workspace ownership at implementation level.

It defines:
- Workspace ownership record location and purpose
- ownership record fields
- ownership acquisition flow
- ownership release flow
- second-owner rejection flow
- stale-owner detection and recovery flow
- read-only inspection behavior
- crash and abnormal exit handling
- trace mapping to RuntimeHost Workspace ownership trace reasons
- implementation error categories

It does NOT define:
- RuntimeHost semantics (see DA-28)
- TurnixRuntime or Kernel authority ordering (see DA-01 and DA-02)
- committed-state or transaction semantics (see DA-04)
- persistent I/O safety semantics (see DA-07)
- Application lifecycle, ApplicationRun lifecycle, or SaveBundle writable
  ownership semantics
- RPC, channel, or transport semantics (see DA-21)
- Orchestration Unit mutation authority semantics (see DA-24)
- concrete CLI command syntax
- concrete LAN pairing or authentication
- concrete operating-system process supervision

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines implementation-level Workspace ownership and
      host-lock behavior within that shared interpretation model.

01.5. This implementation specification does not create new authority
      semantics.

01.6. This implementation specification implements concrete Workspace
      ownership evidence and host-lock behavior for the RuntimeHost-mediated
      Workspace-opening path.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. Workspace ownership locking answers:

          "How does one TurnixRuntime execution, through RuntimeHost, prove
           that it is the current writable owner of a Workspace, and how does
           another RuntimeHost avoid silently becoming a second writer?"

02.2. A Workspace ownership record is durable evidence that one runtime
      execution claims writable ownership of one Workspace.

02.3. A host lock is the implementation mechanism that prevents silent
      concurrent writable ownership of the same Workspace.

02.4. The ownership record and host lock do not create Kernel authority.

02.5. The ownership record and host lock do not create SaveBundle writable
      ownership.

02.6. The ownership record and host lock do not create ApplicationRun
      lifecycle authority.

02.7. The ownership record and host lock do not create Application
      committed state.

02.8. The ownership record and host lock do not grant adapter state-write
      authority.

02.9. Workspace ownership is host-level and runtime-execution-level
      ownership of Workspace mutable roots.

02.10. Workspace ownership does not grant SaveBundle writable ownership,
       ApplicationRun lifecycle authority, Application committed-state
       mutation authority, or adapter write authority.

02.11. Application, ApplicationRun, and SaveBundle ownership and lifecycle
       semantics remain outside this document.

02.12. Committed-state mutation remains governed by DA-04.

02.13. Persistent I/O safety remains governed by DA-07.


===============================================================================
03. OWNERSHIP RECORD LOCATION
===============================================================================

03.1. A writable RuntimeHost-mediated opening stores Workspace ownership
      evidence inside the Workspace under a Turnix-managed metadata location.

03.2. The initial ownership record path is:

          .turnix/runtime-host/owner.json

03.3. This path is the concrete implementation representation of ownership
      evidence.

03.4. This path is not the architecture-level source of Workspace ownership
      authority.

03.5. The parent directory is created by Turnix when writable Workspace
      ownership is requested and the directory does not already exist.

03.6. The parent directory is Turnix-managed metadata.

03.7. Pack-provided code does not write this record directly.

03.8. Adapter-executed code does not write this record directly.

03.9. User tools may inspect this record when read-only inspection is
      explicitly requested or permitted.

03.10. The ownership record path may be revised by a later implementation
       specification when migration and compatibility rules are defined.


===============================================================================
04. OWNERSHIP RECORD FIELDS
===============================================================================

04.1. The ownership record is UTF-8 JSON.

04.2. The ownership record contains the following fields:
      - schemaVersion
      - workspaceId
      - runtimeId
      - runtimeHostId
      - ownershipMode
      - coordinatorProcessId
      - coordinatorProcessStartIdentity
      - machineId
      - userId
      - openedAtUtc
      - heartbeatAtUtc
      - commandSurface
      - runtimeHostVersion
      - ownerToken
      - lockState

04.3. schemaVersion identifies the ownership record schema version.

04.4. workspaceId identifies the Workspace claimed by the runtime execution.

04.5. runtimeId identifies one TurnixRuntime execution.

04.6. runtimeHostId identifies the RuntimeHost or command-surface host
      boundary that mediated the Workspace-opening request.

04.7. runtimeHostId is not Kernel identity.

04.8. runtimeHostId is not Application identity.

04.9. runtimeHostId is not SaveBundle authority.

04.10. runtimeHostId does not by itself replace runtimeId.

04.11. ownershipMode is writable.

04.12. Read-only inspection is represented by accessMode or by a later
       explicit inspection-session record, not by writable ownershipMode.

04.13. coordinatorProcessId records the operating-system process identifier
       representing the runtime execution when available.

04.14. coordinatorProcessStartIdentity distinguishes the concrete process
       lifetime from later reuse of the same process identifier.

04.15. machineId records a stable local machine identity when available.

04.16. userId records a local user identity when available.

04.17. openedAtUtc records when the ownership claim was created.

04.18. openedAtUtc is informational.

04.19. openedAtUtc does not establish identity or liveness.

04.20. heartbeatAtUtc records the most recent owner heartbeat time.

04.21. commandSurface records the entry surface or startup mode that created
       the ownership claim when available.

04.22. runtimeHostVersion records the RuntimeHost implementation version when
       available.

04.23. ownerToken records an unpredictable value generated for the ownership
       claim.

04.24. lockState is one of:
       - active
       - releasing
       - staleRecoveryPending
       - released

04.25. Unknown fields are preserved by tooling that updates the record only
       when the tooling explicitly supports preservation.

04.26. Unknown fields are ignored for authority decisions unless a later
       schema version defines their meaning.

04.27. Unknown fields do not affect ownership, recovery, policy, identity,
       stale-owner classification, or authority.

04.28. Missing required fields make the ownership record malformed.

04.29. A malformed ownership record is not silently treated as absent.


===============================================================================
05. OWNERSHIP ACQUISITION FLOW
===============================================================================

05.1. Workspace ownership acquisition begins when RuntimeHost requests
      writable ownership of a Workspace for one runtime execution.

05.2. RuntimeHost resolves the Workspace identity before creating or writing
      the ownership record.

05.3. RuntimeHost checks for existing ownership evidence before claiming
      writable ownership.

05.4. Ownership acquisition does not rely on unsafe check-then-overwrite
      behavior.

05.5. Ownership claim creation uses atomic creation, exclusive creation,
      compare-and-swap-equivalent behavior, or another DA-07-constrained
      persistence-safe ownership-claim mechanism.

05.6. If no ownership evidence exists, RuntimeHost creates a new ownership
      record through the selected persistence-safe claim mechanism.

05.7. RuntimeHost verifies the written record after the claim step completes.

05.8. RuntimeHost treats ownership as acquired only when the verified record
      still identifies the same workspaceId, runtimeId, ownershipMode, and
      ownerToken.

05.9. If runtimeHostId participates in the selected schema, verification also
      confirms the expected runtimeHostId.

05.10. If verification fails, ownership acquisition fails.

05.11. Ownership acquisition emits RuntimeHostWorkspaceOwnershipRequested.

05.12. Successful ownership acquisition emits
       RuntimeHostWorkspaceOwnershipGranted.

05.13. Failed ownership acquisition emits RuntimeHostWorkspaceOwnershipRejected
       or a more specific ownership trace reason when one applies.

05.14. Ownership acquisition failure does not create a partially valid
       writable owner.

05.15. Ownership acquisition failure does not create a partial ApplicationRun.

05.16. Ownership acquisition failure does not load a SaveBundle.

05.17. Ownership acquisition failure does not commit Application state.

05.18. Ownership acquisition failure does not define Job terminal outcome
       unless the owning Job workflow maps that failure explicitly.


===============================================================================
06. SECOND-OWNER REJECTION FLOW
===============================================================================

06.1. If an ownership record already exists for writable ownership, a
      requesting RuntimeHost does not silently overwrite it.

06.2. The requesting RuntimeHost reads the existing ownership record.

06.3. If the existing record is well formed and active, the requesting
      RuntimeHost reports the Workspace as already owned.

06.4. The requesting RuntimeHost emits RuntimeHostWorkspaceAlreadyOwned.

06.5. The requesting RuntimeHost emits RuntimeHostSecondOwnerRejected when
      writable ownership is rejected because another owner is present.

06.6. The requesting RuntimeHost may offer explicit alternatives through a
      command surface or policy path, including:
      - connect to existing host
      - open read-only inspection
      - request stale-owner recovery
      - abort

06.7. The requesting RuntimeHost does not select an alternative silently.

06.8. The requesting RuntimeHost does not downgrade to read-only inspection
      silently.

06.9. The requesting RuntimeHost does not detach, supersede, or claim work
      from the existing RuntimeHost.

06.10. The requesting RuntimeHost does not create writable Application state,
       ApplicationRun state, or SaveBundle write ownership for the
       already-owned Workspace.


===============================================================================
07. HEARTBEAT AND LIVENESS EVIDENCE
===============================================================================

07.1. A writable runtime owner periodically refreshes heartbeatAtUtc while it
      owns the Workspace.

07.2. Heartbeat refresh writes preserve the same workspaceId, runtimeId,
      ownershipMode, and ownerToken.

07.3. When runtimeHostId participates in the selected schema, heartbeat
      refresh writes preserve the same runtimeHostId.

07.4. Heartbeat refresh uses persistence-safe write behavior under DA-07.

07.5. Heartbeat failure is trace-visible.

07.6. Heartbeat failure does not automatically release ownership.

07.7. Heartbeat failure may contribute to later crash, failure, or
      stale-owner evidence.

07.8. Heartbeat timing values are implementation parameters, not authority
      semantics.

07.9. A later implementation specification may define concrete heartbeat
      intervals and tolerance windows.


===============================================================================
08. STALE-OWNER DETECTION
===============================================================================

08.1. Stale-owner detection begins only when an existing ownership record
      blocks requested writable ownership or when tooling explicitly requests
      ownership inspection.

08.2. Stale-owner detection checks available evidence, including:
      - ownership record schema validity
      - workspaceId
      - runtimeId
      - runtimeHostId when present
      - ownershipMode
      - coordinatorProcessId when available
      - coordinatorProcessStartIdentity when available
      - machineId when available
      - userId when available
      - heartbeatAtUtc
      - ownerToken
      - lockState

08.3. Stale-owner detection may also check implementation-specific liveness
      evidence when the evidence source is defined.

08.4. A missing process is not sufficient by itself to prove safe recovery on
      a different machine.

08.5. A stale heartbeat is not sufficient by itself to authorize silent
      takeover.

08.6. A process identifier match or mismatch is not sufficient without process
      lifetime evidence when process reuse is possible.

08.7. Malformed ownership evidence is not silently treated as stale.

08.8. Stale-owner detection emits RuntimeHostStaleOwnerDetected only when the
      implementation classifies the existing owner as stale evidence rather
      than merely present evidence.

08.9. Stale-owner detection does not itself acquire ownership.

08.10. Stale-owner detection does not itself overwrite ownership evidence.


===============================================================================
09. STALE-OWNER RECOVERY FLOW
===============================================================================

09.1. Stale-owner recovery is explicit.

09.2. Stale-owner recovery is policy-governed when policy is available.

09.3. Stale-owner recovery emits RuntimeHostStaleOwnerRecoveryRequested.

09.4. If recovery is denied, Turnix emits
      RuntimeHostStaleOwnerRecoveryRejected.

09.5. If recovery is accepted, Turnix emits
      RuntimeHostStaleOwnerRecoveryAccepted.

09.6. Recovery acceptance permits RuntimeHost to replace stale ownership
      evidence only through persistence-safe write behavior under DA-07.

09.7. Recovery acceptance does not grant committed-state mutation authority.

09.8. Recovery acceptance does not grant SaveBundle writable ownership.

09.9. Recovery acceptance does not grant ApplicationRun lifecycle authority.

09.10. Recovery acceptance does not grant Application committed-state mutation
       authority.

09.11. Recovery acceptance does not validate or repair corrupted SaveBundle
       material by itself.

09.12. If ownership replacement fails, Turnix emits
       RuntimeHostStaleOwnerRecoveryFailed.

09.13. If ownership replacement succeeds and verification succeeds, Turnix
       emits RuntimeHostWorkspaceOwnershipGranted.

09.14. Recovery failure leaves the Workspace without a new writable owner.

09.15. Recovery failure does not silently downgrade to read-only inspection.


===============================================================================
10. READ-ONLY INSPECTION FLOW
===============================================================================

10.1. Read-only inspection is an explicit accessMode.

10.2. Read-only inspection does not create writable Workspace ownership.

10.3. Read-only inspection may read the ownership record, trace evidence,
      configuration, manifests, and other inspection-allowed material.

10.4. Read-only inspection does not write SaveBundle material.

10.5. Read-only inspection does not write Application committed state.

10.6. Read-only inspection does not write ownership records.

10.7. Read-only inspection does not write mutable Workspace roots except for
      explicitly policy-defined inspection output.

10.8. Read-only inspection may write optional local tool output only when that
      output is outside the inspected Workspace or when a later policy defines
      safe inspection output inside the Workspace.

10.9. Read-only inspection does not repair malformed ownership evidence.

10.10. Read-only inspection does not release another RuntimeHost's ownership.

10.11. Read-only inspection does not acquire SaveBundle writable ownership.

10.12. Read-only inspection does not create or update the ownership record
       unless a later implementation specification defines an explicit
       inspection-session record separate from writable ownership.


===============================================================================
11. OWNERSHIP RELEASE FLOW
===============================================================================

11.1. Ownership release begins when the writable runtime owner intentionally
      stops owning the Workspace.

11.2. RuntimeHost verifies that the current ownership record still matches the
      expected workspaceId, runtimeId, ownershipMode, and ownerToken before
      releasing ownership.

11.3. When runtimeHostId participates in the selected schema, release
      verification also confirms the expected runtimeHostId.

11.4. If the current ownership record does not match, RuntimeHost does not
      delete or overwrite it.

11.5. RuntimeHost may mark lockState as releasing before final release.

11.6. RuntimeHost removes or marks the ownership record as released only
      through persistence-safe write behavior under DA-07.

11.7. Successful release emits RuntimeHostWorkspaceOwnershipReleased.

11.8. Failed release emits RuntimeHostWorkspaceOwnershipReleaseFailed.

11.9. Failed release is trace-visible and may leave stale ownership evidence
      for later explicit recovery.

11.10. Ownership release does not by itself define ApplicationRun stop
       outcome.

11.11. Ownership release does not by itself define Application lifecycle
       outcome.

11.12. Ownership release does not by itself define SaveBundle publication
       outcome.

11.13. Ownership release does not by itself define Job terminal outcome.

11.14. Ownership release does not by itself finalize a Window.


===============================================================================
12. CRASH AND ABNORMAL EXIT HANDLING
===============================================================================

12.1. A RuntimeHost crash may leave ownership evidence behind.

12.2. Left-behind ownership evidence is not automatically invalid.

12.3. A later RuntimeHost treats left-behind ownership evidence as existing
      ownership evidence until stale-owner detection and recovery classify it
      otherwise.

12.4. Crash handling does not silently update the ownership record.

12.5. Crash handling does not silently create a new owner.

12.6. Crash handling does not silently repair committed state.

12.7. Crash handling may produce RuntimeHostCrashed evidence under DA-28.

12.8. Later recovery flows preserve the distinction between host ownership
      recovery and committed-state repair.


===============================================================================
13. MALFORMED OR INCONSISTENT OWNERSHIP RECORDS
===============================================================================

13.1. A malformed ownership record is explicit error evidence.

13.2. A malformed ownership record blocks silent writable ownership
      acquisition.

13.3. A malformed ownership record may be inspected through read-only
      inspection.

13.4. A malformed ownership record may be replaced only through explicit
      recovery policy or manual repair tooling.

13.5. Malformed record recovery emits stale-owner or ownership-recovery trace
      evidence when the workflow treats the malformed record as recoverable.

13.6. Inconsistent ownership fields are not silently normalized.

13.7. If workspaceId in the record does not match the resolved Workspace,
      Turnix treats the condition as malformed or conflicting ownership
      evidence.

13.8. If runtimeId, runtimeHostId, coordinatorProcessId,
      coordinatorProcessStartIdentity, machineId, or ownerToken conflict with
      the claim being verified, Turnix treats the condition as malformed or
      conflicting ownership evidence according to the selected schema.

13.9. Conflicting ownership evidence is not silently ignored.


===============================================================================
14. TRACE MAPPING
===============================================================================

14.1. IS-03 maps implementation behavior to RuntimeHost Workspace ownership
      trace reasons.

14.2. Ownership acquisition maps to:
      - RuntimeHostWorkspaceOwnershipRequested
      - RuntimeHostWorkspaceOwnershipGranted
      - RuntimeHostWorkspaceOwnershipRejected

14.3. Existing owner detection maps to:
      - RuntimeHostWorkspaceAlreadyOwned
      - RuntimeHostSecondOwnerRejected

14.4. Ownership release maps to:
      - RuntimeHostWorkspaceOwnershipReleased
      - RuntimeHostWorkspaceOwnershipReleaseFailed

14.5. Stale owner detection and recovery map to:
      - RuntimeHostStaleOwnerDetected
      - RuntimeHostStaleOwnerRecoveryRequested
      - RuntimeHostStaleOwnerRecoveryAccepted
      - RuntimeHostStaleOwnerRecoveryRejected
      - RuntimeHostStaleOwnerRecoveryFailed

14.6. Implementation-specific trace evidence may add concrete details, but it
      does not redefine RuntimeHost-domain trace reason meanings.

14.7. Trace evidence includes enough context, when available, to identify:
      - workspaceId
      - runtimeId
      - runtimeHostId when present
      - ownershipMode when ownership exists
      - accessMode when inspection access exists
      - ownerToken when ownership exists
      - coordinatorProcessId
      - coordinatorProcessStartIdentity
      - machineId
      - startup mode
      - command identity
      - policy decision identity
      - failure reason category
      - stale owner evidence category

14.8. Trace evidence does not replace the ownership record.

14.9. The ownership record does not replace trace evidence.

14.10. Trace evidence does not create writable ownership.

14.11. Trace evidence does not repair missing or malformed ownership evidence.


===============================================================================
15. ERROR CATEGORIES
===============================================================================

15.1. Workspace ownership implementation errors include:
      - WorkspaceOwnerAlreadyExists
      - WorkspaceOwnerRecordMalformed
      - WorkspaceOwnerRecordMismatch
      - WorkspaceOwnerClaimFailed
      - WorkspaceOwnerWriteFailed
      - WorkspaceOwnerVerifyFailed
      - WorkspaceOwnerReleaseFailed
      - WorkspaceOwnerRecoveryDenied
      - WorkspaceOwnerRecoveryFailed
      - WorkspaceOwnerLivenessUnknown
      - WorkspaceOwnerIdentityInvariantViolation

15.2. Error category names in this section define semantic categories, not
      final exception class names.

15.3. Concrete exception class names belong to implementation code or a later
      error-schema specification.

15.4. Error reporting preserves the distinction between:
      - already owned
      - malformed ownership evidence
      - conflicting ownership evidence
      - stale ownership evidence
      - recovery denied
      - recovery attempted and failed
      - claim failure
      - write failure
      - verification failure
      - identity invariant violation

15.5. Error reporting does not collapse these outcomes into a generic lock
      failure when the implementation can distinguish them.


===============================================================================
16. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

16.1. The following are not supported:
      - silently creating a second writable owner for the same Workspace
      - silently overwriting existing ownership evidence
      - silently treating malformed ownership evidence as absent
      - silently treating malformed ownership evidence as stale
      - silently normalizing malformed ownership evidence
      - silently treating stale heartbeat as takeover permission
      - silently treating process absence as takeover permission
      - silently downgrading writable ownership request to read-only inspection
      - using Workspace ownership as committed-state mutation authority
      - using Workspace ownership as SaveBundle writable ownership
      - using Workspace ownership as ApplicationRun lifecycle authority
      - using Workspace ownership as adapter SaveBundle or application-data
        write authority
      - pack-provided code directly writing the ownership record
      - adapter-executed code directly writing the ownership record
      - deleting another RuntimeHost's ownership evidence without explicit
        stale-owner recovery or manual repair tooling
      - treating ownership release as ApplicationRun stop success
      - treating ownership release as Job terminal outcome
      - treating ownership acquisition as command completion by itself
      - treating read-only inspection as Workspace ownership

===============================================================================
18. LOCKED SUMMARY
===============================================================================

18.1. LOCKED:
      - IS-03 implements Workspace ownership evidence and host-lock behavior.
      - A writable Workspace is owned by at most one runtime execution at a
        time unless a later authoritative multi-host design defines another
        mode.
      - RuntimeHost mediates the Workspace-opening command surface without
        becoming Kernel authority, Application identity, or SaveBundle
        authority.
      - The initial ownership record path is
        .turnix/runtime-host/owner.json.
      - The ownership record path is concrete implementation representation,
        not architecture-level authority.
      - Existing ownership evidence is not silently overwritten.
      - Ownership acquisition does not use unsafe check-then-overwrite
        behavior.
      - Malformed ownership evidence is not silently treated as absent, stale,
        or normalized.
      - Stale ownership recovery is explicit, policy-governed, and
        trace-visible.
      - Read-only inspection is accessMode, not writable ownershipMode.
      - Read-only inspection does not create writable Workspace ownership.
      - Read-only inspection does not create or update the ownership record
        unless a later inspection-session record is explicitly defined.
      - Workspace ownership does not grant committed-state mutation authority.
      - Workspace ownership does not grant SaveBundle writable ownership.
      - Workspace ownership does not grant ApplicationRun lifecycle authority.
      - Workspace ownership does not grant Application committed-state
        mutation authority.
      - Workspace ownership does not grant adapter SaveBundle or
        application-data write authority.
      - Ownership acquisition, release, stale-owner recovery, and second-owner
        rejection are trace-visible.
      - DA-28 owns RuntimeHost Workspace ownership semantics.
      - DA-07 constrains persistence-safe ownership-record writes.
      - DA-04 constrains committed-state mutation.

18.2. OPEN:
      - concrete identifier representations, accessMode representation,
        heartbeat values, OS liveness behavior, migration behavior, exception
        names, and JSON schema format.
