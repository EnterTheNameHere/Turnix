===============================================================================
IMPLEMENTATION SPECIFICATION IS-09 - RUNTIME CATALOG AND PACK LISTING OPERATIONS
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines concrete RuntimeHost and PackManager catalog/listing operations for
Pack descriptors and SaveBundle catalog entries, including ListPacks as the
shared Pack listing primitive, pack-kind filters for Pack listings,
ListSaveBundles as a sibling catalog operation, catalog context, filter
envelopes, result item fields, visibility and compatibility summaries,
pagination, sorting, and operation failure categories.

This document implements catalog/listing surfaces described by the owning
design documents. It is used by command surfaces, Launcher Views,
PackManager Views, remote clients, tests, and future tooling without making
any of those surfaces own catalog semantics.

Purpose:
--------
This document defines concrete runtime catalog listing operation contracts.

It defines:
- ListPacks as the concrete shared Pack listing operation
- ListAppPacks, ListViewPacks, ListContentPacks, and ListModPacks as
  filtered forms of ListPacks
- ListSaveBundles as a sibling SaveBundle catalog listing operation
- catalog request envelope
- catalog context fields
- filter fields
- sorting and pagination fields
- catalog result envelope
- catalog item fields
- visibility summary fields
- compatibility summary fields
- SaveBundle listing fields
- operation result and failure categories
- command, RPC, View, Launcher, and test usage boundaries
- trace reason usage for catalog listing

It does NOT define:
- root discovery boundaries or filesystem scanning rules (see DA-09)
- pack identity, hierarchy, visibility, or pack visibility semantics
  (see DA-10)
- generic PackRequest resolution mechanics (see DA-11)
- importing or module-loading behavior (see DA-12)
- dependency, provider-role, pinned, copied, or advisory-relation semantics
  (see DA-13)
- activation lifecycle or activation ordering (see DA-14)
- service, capability, permission, or Job-backed execution semantics
  (see DA-16)
- user decision or remembered policy semantics (see DA-17)
- Application lifecycle, ApplicationRun lifecycle, or SaveBundle binding,
  loading, ownership, generation, migration, or repair behavior (see DA-20)
- RPC, channel, or transport semantics (see DA-21)
- UI, View, or frontend runtime semantics (see DA-22)
- RuntimeHost command-surface semantics (see DA-28)
- PackManager semantic boundaries (see DA-29)
- resolved pack graph schema
- activation-plan schema
- package search, install, update, delete, or verification protocols
- concrete CLI syntax
- concrete JSON-RPC or WebSocket envelope fields
- concrete browser component layout

01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines implementation-level runtime catalog and Pack
      listing operation contracts within that shared interpretation model.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. Runtime catalog listing answers:

          "Which Pack descriptors or SaveBundle catalog entries are visible
           to this catalog operation under this explicit catalog context
           and filter?"

02.2. ListPacks is the shared concrete listing primitive for Pack
      descriptors.

02.3. Pack-kind-specific listing operations are filtered forms of ListPacks.

02.4. ListSaveBundles is a sibling catalog listing operation for
      SaveBundle records.

02.5. A SaveBundle catalog item is not a Pack descriptor.

02.6. Listing is read-only catalog access.

02.7. Listing does not perform discovery by itself.

02.8. Listing does not perform filesystem rescan by itself.

02.9. Listing does not perform generic PackRequest resolution by itself.

02.10. Listing does not select a pack graph.

02.11. Listing does not create an activation plan.

02.12. Listing does not import pack code.

02.13. Listing does not activate packs.

02.14. Listing does not load, bind, migrate, repair, or open a SaveBundle.

02.15. Listing does not grant visibility, permission, capability authority,
       execution authorization, persistence authority, or filesystem access.

02.16. Listing may expose visibility, compatibility, dependency, advisory,
       source, state, and SaveBundle summaries when those summaries are
       available and permitted by the catalog context.

02.17. Listing summaries are presentation and operation results.

02.18. Listing summaries do not replace the owning design semantics.


===============================================================================
03. OPERATION NAMES
===============================================================================

03.1. The concrete shared Pack listing operation is:
      ListPacks

03.2. The following pack-kind-specific operations are filtered forms of
      ListPacks:
      - ListAppPacks
      - ListViewPacks
      - ListContentPacks
      - ListModPacks

03.3. ListAppPacks is equivalent to ListPacks with kindFilter containing
      AppPack.

03.4. ListViewPacks is equivalent to ListPacks with kindFilter containing
      ViewPack.

03.5. ListContentPacks is equivalent to ListPacks with kindFilter containing
      ContentPack.

03.6. ListModPacks is equivalent to ListPacks with kindFilter containing
      ModPack.

03.7. ListSaveBundles lists SaveBundle catalog entries when the catalog
      context permits them.

03.8. ListSaveBundles is not a filtered form of ListPacks.

03.9. SaveBundle catalog entries are durable persistence-closure entries,
      not Pack descriptors.

03.10. Implementations may expose command aliases or UI labels for these
       operations.

03.11. Aliases and UI labels do not create separate catalog semantics.


===============================================================================
04. REQUEST ENVELOPE
===============================================================================

04.1. A catalog listing request contains:
      - requestId
      - operation
      - catalogContext
      - filters
      - sort
      - page
      - projection
      - options

04.2. requestId identifies the listing request for correlation.

04.3. operation identifies the requested listing operation.

04.4. catalogContext identifies the context from which the catalog is
      viewed.

04.5. filters restrict which catalog items are included in the result.

04.6. sort controls deterministic result ordering.

04.7. page controls pagination.

04.8. projection controls which optional fields are included.

04.9. options controls operation behavior that does not change catalog
      semantics.

04.10. A request envelope does not authorize access by itself.

04.11. The entry surface that submits the request remains subject to
       RuntimeHost, capability, RPC, policy, and permission rules where
       applicable.


===============================================================================
05. CATALOG CONTEXT
===============================================================================

05.1. catalogContext is a JSON object.

05.2. catalogContext contains enough context to decide which catalog view is
      being requested.

05.3. catalogContext may contain:
      - scope
      - runtimeHostId
      - workspaceId
      - appPackId
      - appDefinitionSourceId
      - appDefinitionSourceKind
      - saveBundleId
      - applicationId
      - applicationRunId
      - viewId
      - requestingPackId
      - requestingSurfaceKind
      - accessMode

05.4. scope identifies the catalog scope for this operation.

05.5. Defined scope values are:
      - runtimeHost
      - workspace
      - appPack
      - appDefinitionSource
      - saveBundle
      - application
      - applicationRun
      - tooling
      - test

05.6. runtimeHostId identifies the RuntimeHost context when applicable.

05.7. workspaceId identifies the Workspace context when applicable.

05.8. appPackId identifies the AppPack context when an actual AppPack is
      the relevant application definition source.

05.9. appDefinitionSourceId identifies an accepted application definition
      source when the source is not necessarily an AppPack.

05.10. appDefinitionSourceKind identifies the class of application
       definition source when available.

05.11. saveBundleId identifies the SaveBundle context when applicable.

05.12. applicationId identifies the durable Application context when
       applicable.

05.13. applicationRunId identifies the live ApplicationRun context when
       applicable.

05.14. viewId identifies the View context when applicable.

05.15. requestingPackId identifies the pack whose authority or visibility
       context is used when applicable.

05.16. requestingSurfaceKind identifies whether the request came from CLI,
       Launcher, PackManager View, application View, remote client, AI buddy,
       test, or another surface.

05.17. accessMode identifies the requested access form.

05.18. Defined accessMode values are:
       - readOnlyInspection
       - runtimeSelection
       - graphPreparation
       - saveCompatibilityCheck
       - toolingInspection
       - testInspection

05.19. readOnlyInspection means the request lists catalog material for
       viewing without selecting or mutating graph state.

05.20. runtimeSelection means the request lists catalog material for a
       possible runtime selection, such as selecting an AppPack to start.

05.21. graphPreparation means the request supports selected graph
       preparation.

05.22. saveCompatibilityCheck means the request supports SaveBundle
       compatibility or repair inspection.

05.23. toolingInspection means the request supports development,
       diagnostics, maintenance, or offline inspection behavior.

05.24. testInspection means the request supports controlled test behavior.

05.25. accessMode does not grant authority by itself.

05.26. The operation owner still enforces policy, permission, visibility,
       privacy, path-exposure, and access boundaries.


===============================================================================
06. FILTERS
===============================================================================

06.1. filters is a JSON object.

06.2. filters may contain:
      - kindFilter
      - rootFilter
      - sourceFilter
      - authorFilter
      - packTreeIdFilter
      - versionFilter
      - visibilityFilter
      - compatibilityFilter
      - selectedStateFilter
      - appDefinitionSourceFilter
      - saveBundleFilter
      - applicationFilter
      - applicationRunFilter
      - textSearch
      - includeShadowed
      - includeInvalid
      - includeSaveLocal
      - includeCopied
      - includePinned

06.3. kindFilter is an array of Pack kind names.

06.4. Defined Pack kind names are:
      - AppPack
      - ModPack
      - ViewPack
      - ContentPack

06.5. SaveBundle is not a Pack kind.

06.6. rootFilter restricts results to one or more root identities or root
      classes.

06.7. sourceFilter restricts results by installation or source
      classification when such classification is available.

06.8. authorFilter restricts Pack results by author identity.

06.9. packTreeIdFilter restricts Pack results by packTreeId or packTreeId
      prefix according to operation-defined matching mode.

06.10. versionFilter restricts Pack results by exact version or version
       range.

06.11. visibilityFilter restricts results by visibility summary.

06.12. compatibilityFilter restricts results by compatibility summary.

06.13. selectedStateFilter restricts results by selected graph state when
       that state is available.

06.14. appDefinitionSourceFilter restricts results by application definition
       source when such filtering is supported.

06.15. saveBundleFilter restricts SaveBundle results by SaveBundle identity
       or SaveBundle listing criteria when supported.

06.16. applicationFilter restricts results by durable Application identity
       when supported.

06.17. applicationRunFilter restricts results by live ApplicationRun identity
       when supported.

06.18. textSearch restricts results by human-readable search over permitted
       metadata fields.

06.19. includeShadowed controls whether shadowed candidates may be included.

06.20. includeInvalid controls whether invalid or rejected records may be
       included for diagnostics.

06.21. includeSaveLocal controls whether save-local pack material is included
       when the catalog context permits it.

06.22. includeCopied controls whether copied SaveBundle pack material is
       included when the catalog context permits it.

06.23. includePinned controls whether pinned dependency references are
       included or surfaced when the catalog context permits them.

06.24. A filter does not change pack identity, SaveBundle identity,
       visibility meaning, or authority.

06.25. A filter cannot make an invisible Pack or SaveBundle visible unless
       the catalog context and policy already permit diagnostic visibility.


===============================================================================
07. SORTING
===============================================================================

07.1. sort is a JSON object.

07.2. sort contains:
      - keys
      - direction

07.3. keys is an ordered array of sort key names.

07.4. direction is ascending or descending.

07.5. Defined sort keys include:
      - displayName
      - packTreeId
      - author
      - version
      - kind
      - rootPrecedence
      - updatedAt
      - compatibilityStatus
      - selectedState
      - saveBundleId
      - applicationId

07.6. Sorting is deterministic.

07.7. If no sort is provided, the default sort order is:
      - kind
      - displayName
      - author
      - packTreeId
      - version

07.8. A final deterministic tie-break uses canonical pack identity,
      SaveBundle identity, and source identity when available.

07.9. Sorting does not select a graph.

07.10. Sorting does not imply resolution winner selection.

07.11. Sorting does not choose an Application, ApplicationRun, or
       SaveBundle binding.


===============================================================================
08. PAGINATION
===============================================================================

08.1. page is a JSON object.

08.2. page may contain:
      - offset
      - limit
      - cursor

08.3. offset is a zero-based result offset.

08.4. limit is the maximum number of items to return.

08.5. cursor is an implementation-defined continuation token.

08.6. Implementations may support offset pagination, cursor pagination, or
      both.

08.7. Pagination does not change the total ordered result set.

08.8. Pagination metadata in the response records whether more results
      exist.

08.9. A cursor does not grant access to records outside the original
      permitted catalog context.

08.10. A cursor does not preserve authority after the original catalog
       context is no longer valid.


===============================================================================
09. PROJECTION
===============================================================================

09.1. projection is a JSON object.

09.2. projection controls optional field inclusion.

09.3. projection may contain:
      - includeDescriptions
      - includePaths
      - includeSourceDetails
      - includeVisibilitySummary
      - includeCompatibilitySummary
      - includeDependencySummary
      - includeAdvisorySummary
      - includeSaveBundleSummary
      - includeTraceLinks
      - includeDiagnostics

09.4. includeDescriptions allows human-readable descriptions when available.

09.5. includePaths allows source path or root-relative path fields when
      policy permits path exposure.

09.6. includeSourceDetails allows package source or installation provenance
      details when available and permitted.

09.7. includeVisibilitySummary allows visibility summary fields.

09.8. includeCompatibilitySummary allows compatibility summary fields.

09.9. includeDependencySummary allows dependency summary fields.

09.10. includeAdvisorySummary allows advisory relation summary fields.

09.11. includeSaveBundleSummary allows SaveBundle-specific listing fields
       when the operation and catalog context support them.

09.12. includeTraceLinks allows trace correlation fields when available.

09.13. includeDiagnostics allows diagnostic details for invalid, shadowed,
       rejected, hidden, or incomplete records.

09.14. Projection controls result verbosity only.

09.15. Projection does not change listing semantics.

09.16. Projection does not bypass visibility, policy, privacy,
       path-exposure, or source-trust boundaries.


===============================================================================
10. OPTIONS
===============================================================================

10.1. options is a JSON object.

10.2. options may contain:
      - allowStaleCache
      - requireFreshCatalog
      - explainFilters
      - explainOmissions
      - includeCountsOnly

10.3. allowStaleCache permits a cached catalog view only when the cache is
      valid under the owning cache policy.

10.4. requireFreshCatalog requires the operation to use a current catalog
      view or fail explicitly.

10.5. requireFreshCatalog does not imply filesystem rescan unless an
      explicit rescan operation has been requested and accepted.

10.6. explainFilters requests response evidence for filters that affected
      result inclusion.

10.7. explainOmissions requests response evidence for omitted categories
      when such evidence is available and permitted.

10.8. includeCountsOnly requests counts instead of item payloads.

10.9. Options do not bypass authority, policy, visibility, privacy,
      path-exposure, or source-trust boundaries.

10.10. A stale cached response records that stale catalog evidence was used
       when the operation profile requires that disclosure.


===============================================================================
11. RESPONSE ENVELOPE
===============================================================================

11.1. A catalog listing response contains:
       - requestId
       - operation
       - resultStatus
       - catalogContext
       - items
       - counts
       - page
       - appliedFilters
       - warnings
       - diagnostics
       - trace

11.2. requestId matches the request when available.

11.3. operation identifies the operation that produced the response.

11.4. resultStatus classifies the operation result.

11.5. catalogContext records the effective catalog context used.

11.6. items contains catalog items.

11.7. counts contains result counts.

11.8. page contains pagination metadata.

11.9. appliedFilters records filters applied by the operation.

11.10. warnings contains non-fatal warning summaries.

11.11. diagnostics contains diagnostic information when requested and
       permitted.

11.12. trace contains trace correlation references when available.

11.13. The response envelope does not grant runtime authority.

11.14. The response envelope does not prove complete catalog truth unless
       the result status and operation profile define a complete result.


===============================================================================
12. RESULT STATUS
===============================================================================

12.1. resultStatus is one of:
       - Completed
       - CompletedWithWarnings
       - Failed
       - Denied
       - NotAvailable
       - Partial

12.2. Completed means the requested listing operation completed without
       operation-level warnings.

12.3. CompletedWithWarnings means the listing operation completed and
       warning evidence exists.

12.4. Failed means the listing operation could not produce a valid response.

12.5. Denied means the request was refused by permission, policy,
       visibility, privacy, or authority boundary before listing completed.

12.6. NotAvailable means the requested catalog context or required catalog
       view is unavailable.

12.7. Partial means the operation produced a partial response under an
       explicit profile or failure mode that permits partial listing.

12.8. Partial listing does not silently become complete listing.

12.9. A partial response records the reason it is partial.

12.10. resultStatus is not Job terminal outcome.

12.11. resultStatus is not Application lifecycle outcome.

12.12. resultStatus is not ApplicationRun lifecycle outcome.

12.13. resultStatus is not activation outcome.

12.14. resultStatus is not SaveBundle migration, repair, ownership, or
       loading outcome.


===============================================================================
13. CATALOG ITEM
===============================================================================

13.1. A catalog item contains:
       - catalogItemId
       - entryKind
       - packIdentity
       - display
       - source
       - visibility
       - compatibility
       - dependencySummary
       - advisorySummary
       - saveBundleSummary
       - selectedState
       - diagnostics
       - trace

13.2. catalogItemId identifies this listing item within the response.

13.3. entryKind identifies the catalog item class.

13.4. Defined entryKind values are:
      - PackDescriptor
      - SaveBundleCatalogEntry

13.5. PackDescriptor means the item represents a Pack descriptor.

13.6. SaveBundleCatalogEntry means the item represents a SaveBundle catalog
      entry.

13.7. Additional catalog item classes appear here only after an owning
      document defines them and this implementation specification includes
      them.

13.8. packIdentity contains identity fields for a Pack descriptor.

13.9. packIdentity is absent when the item is not a Pack descriptor.

13.10. display contains human-readable presentation fields.

13.11. source contains source, root, or provenance fields when included and
       permitted.

13.12. visibility contains visibility summary fields when included and
       permitted.

13.13. compatibility contains compatibility summary fields when included and
       available.

13.14. dependencySummary contains dependency summary fields when included
       and available.

13.15. advisorySummary contains advisory relation summary fields when
       included and available.

13.16. saveBundleSummary contains SaveBundle-specific fields when included
       and applicable.

13.17. selectedState contains selected graph or active-run state when
       included and available.

13.18. diagnostics contains item-level diagnostic fields when included and
       permitted.

13.19. trace contains trace correlation references when available.

13.20. A catalog item is a listing projection, not an owning definition.

13.21. A Pack catalog item does not replace the manifest, discovery record,
       resolution candidate, selected graph record, or activation record.

13.22. A SaveBundle catalog item does not replace the SaveBundle manifest,
       generation record, ownership record, migration record, repair record,
       or loading record.


===============================================================================
14. PACK IDENTITY FIELDS
===============================================================================

14.1. packIdentity is a JSON object.

14.2. packIdentity appears for Pack descriptor items.

14.3. packIdentity contains:
       - author
       - packTreeId
       - version
       - canonicalPackId
       - fingerprint

14.4. author serializes the effective author identity when available.

14.5. packTreeId serializes the computed packTreeId.

14.6. version serializes the parsed version identity when available.

14.7. canonicalPackId serializes the canonical pack identity when
      available.

14.8. fingerprint serializes the pack fingerprint when available and
      permitted.

14.9. Missing fingerprint means no fingerprint was included in this
      response.

14.10. Missing fingerprint does not imply no fingerprint exists.

14.11. Pack identity meaning remains owned by DA-10.

15. DISPLAY FIELDS
===============================================================================

15.2. display may contain:
       - displayName
       - title
       - description
       - summary
       - iconRef
       - tags

15.3. displayName is the preferred short human-readable name when

15.4. title is a longer human-readable title when available.

===============================================================================
16. SOURCE FIELDS
===============================================================================

16.1. source is a JSON object.

16.2. source may contain:
       - rootId
       - rootClass
       - rootPrecedence
       - sourcePath
       - sourceKind
       - installedBy
       - sourceTrustClass
       - packageSourceId

16.3. rootId identifies the root that supplied the catalog record when
      available.

16.4. rootClass identifies the root class, such as custom, first-party,
      third-party, userdata, or saves, when applicable.

16.5. rootPrecedence records root precedence evidence when applicable.

16.6. sourcePath records a path only when path exposure is permitted.

16.7. sourceKind records whether the record came from installed content,
      save-local content, copied SaveBundle content, generated metadata, or
      another defined source.

16.8. installedBy records package-management provenance when available.

16.9. sourceTrustClass records source trust classification when available.

16.10. packageSourceId records package-source identity when available.

16.11. Source fields do not prove authenticity by themselves.

16.12. Source fields do not grant authority.

16.13. sourcePath is catalog evidence only.

16.14. sourcePath does not grant filesystem access.

16.15. sourcePath does not prove current path existence.

16.16. sourcePath does not authorize direct reads.

17. VISIBILITY SUMMARY

17.2. visibility may contain:
       - visibilityStatus
       - localVisibility
       - globalVisibility
       - visibleFromRequestingContext
       - visibilityReasonCategory

17.3. visibilityStatus is one of:

       - Hidden
       - NotEvaluated
       - Denied
       - Unknown

17.9. Visibility summary does not bypass privacy or path-exposure policy.

17.11. SaveBundle listing visibility is catalog evidence only and does not

18.11. Compatibility summary does not replace dependency resolution,

===============================================================================
21. SAVEBUNDLE SUMMARY
===============================================================================

21.1. saveBundleSummary is a JSON object.

21.2. saveBundleSummary appears for SaveBundle catalog entries when
      requested and available.

21.3. saveBundleSummary may also appear as related evidence on Pack catalog
      items when the operation, projection, and catalog context permit it.

21.4. saveBundleSummary may contain:
       - saveBundleId
       - applicationId
       - associatedAppPackId
       - appDefinitionSourceId
       - appDefinitionSourceKind
       - displaySaveName
       - lastOpenedAt
       - lastModifiedAt
       - saveBundleFormatVersion
       - headGenerationId
       - lastKnownGoodGraphId
       - lastUsedGraphId
       - copiedPackCount
       - pinnedDependencyCount
       - compatibilityStatus
       - repairStatus

21.5. saveBundleId identifies the SaveBundle when available.

21.6. applicationId identifies the durable Application associated with the
      SaveBundle when available.

21.7. associatedAppPackId identifies the AppPack associated with the
      SaveBundle when an actual AppPack is the associated application
      definition source.

21.8. appDefinitionSourceId identifies an accepted application definition
      source associated with the SaveBundle when available.

21.9. appDefinitionSourceKind identifies the class of associated
      application definition source when available.

21.10. displaySaveName is a human-readable SaveBundle name.

21.11. lastOpenedAt records last open or use time when available.

21.12. lastModifiedAt records last modified time when available.

21.13. saveBundleFormatVersion records SaveBundle format version when
       available.

21.14. headGenerationId references the current published generation when
       available.

21.15. lastKnownGoodGraphId references last-known-good graph evidence when
       available.

21.16. lastUsedGraphId references last-used graph evidence when available.

21.17. copiedPackCount records copied pack count when available.

21.18. pinnedDependencyCount records pinned dependency count when available.

21.19. compatibilityStatus summarizes compatibility against the current
       catalog context when evaluated.

21.20. repairStatus summarizes whether repair may be needed or available
       when evaluated.

21.21. saveBundleSummary does not load the SaveBundle.

21.22. saveBundleSummary does not bind a SaveBundle to an Application or
       ApplicationRun.

21.23. saveBundleSummary does not perform migration.

21.24. saveBundleSummary does not perform repair.

21.25. saveBundleSummary does not prove that all SaveBundle material needed
       for loading, migration, repair, or restoration is present.


===============================================================================
22. SELECTED STATE SUMMARY
===============================================================================

22.1. selectedState is a JSON object.

22.2. selectedState may contain:
       - selectedStatus
       - selectedGraphId
       - activeInApplicationRunId
       - pendingChangeStatus

22.3. selectedStatus is one of:
       - NotSelected
       - Selected
       - Active
       - Pending
       - NotEvaluated
       - Unknown

22.4. selectedGraphId references the selected graph when available.

22.5. activeInApplicationRunId identifies an ApplicationRun using the pack
      when available.

22.6. pendingChangeStatus records whether changes are pending for a future
      graph or activation plan when available.

22.7. selectedState is catalog evidence.

22.8. selectedState does not mutate selected graph state.

22.9. selectedState is not authoritative runtime state, activation state,
      committed state, or graph ownership by itself.


===============================================================================
23. WARNINGS AND DIAGNOSTICS
===============================================================================

23.1. warnings is an array of warning objects.

23.2. diagnostics is an array or object containing diagnostic evidence.

23.3. Warning objects may contain:
       - warningCategory
       - message
       - relatedPackIdentity
       - relatedField
       - severity

23.4. Diagnostic objects may contain:
       - diagnosticCategory
       - message
       - sourceReference
       - traceEventId
       - relatedPackIdentity
       - relatedOperation

23.5. Warning and diagnostic messages are presentation fields.

23.6. Warning and diagnostic categories are machine-readable fields.

23.7. Warnings do not become hard failures unless the owning operation or
      policy defines that handling.

23.8. Diagnostics do not replace trace evidence.

23.9. Diagnostics may expose hidden, invalid, rejected, shadowed, source,
      path, or provenance details only when catalog context, policy,
      visibility, privacy, path-exposure, and source-trust rules permit that
      exposure.

23.10. Diagnostic inclusion does not bypass the boundary that normally
       prevents those details from being shown.


===============================================================================
24. COUNTS
===============================================================================

24.1. counts is a JSON object.

24.2. counts may contain:
       - total
       - returned
       - byKind
       - byRootClass
       - byCompatibilityStatus
       - byVisibilityStatus
       - bySelectedStatus
       - omitted

24.3. total records total matching items before pagination when available.

24.4. returned records item count returned in this response.

24.5. byKind records counts grouped by catalog item kind when available.

24.6. byRootClass records counts grouped by root class when available.

24.7. byCompatibilityStatus records counts grouped by compatibility status
      when available.

24.8. byVisibilityStatus records counts grouped by visibility status when
      available.

24.9. bySelectedStatus records counts grouped by selected status when
      available.

24.10. omitted records counts of omitted categories when available and
       permitted.

24.11. Counts are summaries of the catalog operation result.

24.12. Counts do not replace item records when item records are required.

24.13. Counts-only responses do not become complete catalog truth unless the
       operation profile defines that meaning.


===============================================================================
25. FAILURE CATEGORIES
===============================================================================

25.1. Listing failure categories include:
       - InvalidCatalogRequest
       - InvalidCatalogContext
       - UnsupportedScope
       - UnsupportedFilter
       - UnsupportedProjection
       - CatalogUnavailable
       - CatalogStale
       - PermissionDenied
       - VisibilityDenied
       - PolicyDenied
       - SourceUnavailable
       - MalformedCatalogRecord
       - InternalCatalogError

25.2. InvalidCatalogRequest means the request envelope is malformed or
      missing required fields.

25.3. InvalidCatalogContext means catalogContext is malformed or
      inconsistent.

25.4. UnsupportedScope means the requested scope is not supported by this
      operation.

25.5. UnsupportedFilter means a supplied filter is not supported.

25.6. UnsupportedProjection means a requested projection is not supported.

25.7. CatalogUnavailable means no usable catalog view exists for the
      request.

25.8. CatalogStale means the available catalog view cannot satisfy the
      request's freshness requirement.

25.9. PermissionDenied means the request is denied by permission handling.

25.10. VisibilityDenied means requested visibility is not permitted.

25.11. PolicyDenied means policy refuses the listing request.

25.12. SourceUnavailable means a required source for this catalog view is
       unavailable.

25.13. MalformedCatalogRecord means a catalog record cannot be represented
       as a valid catalog item.

25.14. InternalCatalogError means an implementation error prevented listing.

25.15. Failure categories are operation errors, not activation outcomes,
       Job terminal outcomes, Application lifecycle outcomes, ApplicationRun
       lifecycle outcomes, or SaveBundle lifecycle outcomes.


===============================================================================
26. ENTRY SURFACE USAGE
===============================================================================

26.1. CLI, RuntimeHost command, Launcher, PackManager View, remote client,
      application View, AI buddy surface, and test surface usage all route to
      the same catalog listing operation semantics.

26.2. CLI syntax does not define separate listing semantics.

26.3. Launcher UI does not define separate listing semantics.

26.4. PackManager View layout does not define separate listing semantics.

26.5. Remote client transport does not define separate listing semantics.

26.6. Test harness access does not weaken listing boundaries.

26.7. Entry surfaces may use different projections or presentation formats.

26.8. Different projections do not create different catalog truth.

26.9. Entry surfaces do not become catalog authority merely because they
      submit, display, cache, test, or forward catalog listing results.


===============================================================================
27. TRACE AND OBSERVABILITY
===============================================================================

27.1. Catalog listing operations remain trace-visible.

27.2. ListPacks uses PackManager-domain trace reasons owned by DA-29.

27.3. ListPacks normally emits or contributes to:
       - PackCatalogListRequested
       - PackCatalogListStarted
       - PackCatalogFilterApplied
       - PackCatalogVisibilityEvaluated
       - PackCatalogListCompleted
       - PackCatalogListFailed

27.4. ListSaveBundles uses the catalog listing operation's trace evidence.

27.5. Any specialized SaveBundle listing trace reason vocabulary remains
      open until an owning document defines it.

27.6. Trace evidence records enough context, when available, to explain:
       - requestId
       - operation
       - catalogContext
       - filters
       - sort
       - page
       - projection
       - resultStatus
       - returned count
       - omitted count when available
       - failure category when failure occurs
       - runtimeHostId when applicable
       - workspaceId when applicable
       - appPackId when applicable
       - appDefinitionSourceId when applicable
       - saveBundleId when applicable
       - applicationId when applicable
       - applicationRunId when applicable
       - viewId when applicable
       - requesting surface kind when applicable
       - requesting pack identity when applicable

27.7. Trace records use IS-08 trace serialization when serialized through
      the shared trace record envelope.

27.8. Listing trace evidence does not replace discovery, resolution,
      dependency, activation, capability, RuntimeHost, Application,
      ApplicationRun, SaveBundle, or persistence trace evidence.

27.9. Trace evidence is evidence only.

27.10. Trace evidence does not grant authority or prove facts outside the
       retained evidence.


===============================================================================
28. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

28.1. The following are not supported:
      - treating ListPacks as discovery
      - treating ListPacks as filesystem rescan
      - treating ListPacks as generic PackRequest resolution
      - treating ListPacks as dependency satisfaction
      - treating ListPacks as selected graph creation
      - treating ListPacks as activation-plan creation
      - treating ListPacks as importing
      - treating ListPacks as activation
      - treating ListPacks as capability permission
      - treating ListSaveBundles as a Pack-kind filter
      - treating SaveBundle entries as Pack descriptors
      - treating listed packs as automatically selected
      - treating listed packs as automatically activated
      - treating SaveBundle listing as SaveBundle loading
      - treating SaveBundle listing as SaveBundle binding
      - treating SaveBundle listing as SaveBundle migration
      - treating SaveBundle listing as SaveBundle repair
      - treating AppPack listing as proof that all Applications originate from
        AppPacks
      - treating compatibility summary as activation success
      - treating advisory summary as hard dependency semantics
      - launcher-owned listing semantics
      - CLI-owned listing semantics
      - remote-client-owned listing semantics
      - test-owned listing semantics
      - filters bypassing visibility or policy
      - projection bypassing visibility or policy
      - diagnostics bypassing privacy or path-exposure boundaries
      - sourcePath authorizing filesystem reads
      - partial listing presented as complete listing
      - counts-only listing presented as complete item listing

===============================================================================
30. LOCKED SUMMARY
===============================================================================

30.1. LOCKED:
      - ListPacks is the shared concrete Pack listing primitive.
      - ListAppPacks, ListViewPacks, ListContentPacks, and ListModPacks are
        filtered forms of ListPacks.
      - ListSaveBundles is a sibling SaveBundle catalog listing operation.
      - SaveBundle entries are not Pack descriptors.
      - Listing is read-only catalog access.
      - Listing does not perform discovery, rescan, resolution, graph
        selection, activation-plan creation, importing, activation,
        capability permission, execution authorization, persistence
        authority, SaveBundle loading, or SaveBundle migration.
      - A catalog listing request contains requestId, operation,
        catalogContext, filters, sort, page, projection, and options.
      - catalogContext identifies runtimeHostId, workspaceId, appPackId,
        appDefinitionSourceId, saveBundleId, applicationId,
        applicationRunId, viewId, requestingPackId,
        requestingSurfaceKind, and accessMode when applicable.
      - accessMode is explicit and does not grant authority by itself.
      - filters restrict catalog results without redefining Pack identity,
        SaveBundle identity, visibility, or authority.
      - sorting is deterministic.
      - pagination does not change the total ordered result set.
      - projection controls result verbosity only.
      - response envelopes distinguish result status, items, counts,
        warnings, diagnostics, and trace references.
      - catalog items are listing projections, not owning definitions.
      - currently defined catalog item classes are PackDescriptor and
        SaveBundleCatalogEntry.
      - sourcePath is catalog evidence only and does not grant filesystem
        access, prove current path existence, or authorize direct reads.
      - SaveBundle summaries do not load, bind, migrate, repair, or prove
        completeness of a SaveBundle.
      - compatibility, dependency, advisory, visibility, selectedState, and
        SaveBundle summaries do not replace their owning semantics.
      - CLI, RuntimeHost command, Launcher, PackManager View, remote client,
        application View, AI buddy surface, and test surface usage route to
        the same catalog listing operation semantics.
      - Catalog listing operations remain trace-visible.
      - ListSaveBundles uses the catalog listing operation's trace evidence.
      - Listing trace evidence remains evidence and does not replace owning
        domain trace evidence.

30.2. OPEN:
      - concrete identifier formats, filter encodings, cursor format, page
        sizes, reason vocabularies, warning/diagnostic vocabularies, CLI
        syntax, RPC envelope mapping, and JSON Schema publication.
