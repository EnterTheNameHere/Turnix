===============================================================================
DESIGN AREA DA-20 - APPLICATION AND APPLICATIONRUN LIFECYCLE & RUNTIME IDENTITY
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines Application identity, ApplicationRun runtime identity, AppDefinition
and AppPack binding, SaveBundle binding, active runtime lifecycle boundaries,
participant separation, writable SaveBundle ownership, and runtime-identity
trace reason identifiers.

This document owns Application and ApplicationRun lifecycle semantics. It does
not own pack activation, SaveBundle storage format, runtime-host workspace
ownership, runtime-host command-surface semantics, adapter execution semantics,
or concrete workspace locking implementation.

Purpose:
--------
This document defines the Application and ApplicationRun lifecycle and runtime
identity anchor for Turnix.

It defines:
- applicationId as durable Application identity
- applicationRunId as live runtime execution identity
- Application as one durable application individual
- ApplicationRun as one live execution period of an Application
- relationship between Application, ApplicationRun, AppDefinition/AppPack
  binding, and SaveBundle
- new Application creation as an ApplicationRun creation path
- existing Application loading as an ApplicationRun creation path
- optional SaveBundle binding and writable SaveBundle ownership
- ApplicationRun runtime lifecycle phases
- relationship between ApplicationRun lifecycle and pack activation
- relationship between ApplicationRun lifecycle and execution adapters
- relationship between ApplicationRun lifecycle, Views, RPC, Jobs,
  OrchestrationUnits, and Windows
- ApplicationRun active-region lifecycle boundaries
- runtime-identity trace reason identifiers
- minimum trace evidence for ApplicationRun lifecycle and active-region events

It does NOT define:
- trace event structure, trace DAG semantics, trace retention, or span
  mechanics
  (see DA-03)
- authoritative committed state or transaction semantics (see DA-04)
- payload identity or committed-value representation (see DA-05)
- configuration semantics or configuration migration (see DA-06)
- persistent I/O authority or filesystem rules (see DA-07)
- Window, SafePointWindow, AbortedWindow, or finalized-history semantics
  (see DA-08)
- pack discovery, identity, dependency, or resolution semantics
  (see DA-09, DA-10, DA-11, and DA-13)
- pack activation semantics, onLoad(ctx), or ModCallContext gateway authority
  (see DA-14)
- service, capability, or permission semantics (see DA-16)
- user decision and remembered policy semantics (see DA-17)
- Job lifecycle or long-running work semantics (see DA-19)
- RPC, channel, and transport semantics (see DA-21)
- UI, View, and frontend runtime semantics (see DA-22)
- execution adapter boundary semantics (see DA-23)
- OrchestrationUnit lifecycle or mutation authority (see DA-24)
- artifact or export semantics (see DA-25)
- comparison, Replay, Resume, or Retry workflow semantics (see DA-26)
- adapter lifecycle, trust, isolation, or traceability semantics (see DA-27)
- RuntimeHost identity, workspace ownership, startup modes, command-surface,
  local-first, or LAN semantics (see DA-28)
- PackManager graph-preparation or catalog-operation semantics (see DA-29)
- ModCallContext invocation gateway details
- concrete workspace locking implementation
- concrete SaveBundle storage format or generation-publication mechanics

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines Application and ApplicationRun lifecycle and
      runtime identity semantics within that shared interpretation model.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. ApplicationRun lifecycle answers:

          "Which live execution of an Application is active, which durable
           Application and SaveBundle are bound when applicable, which
           participants are attached, and when does its runtime authority
           region begin and end?"

02.02. An AppPack is a reusable application definition source.

02.03. An AppDefinition binding is the accepted definition binding used to
      create, load, validate, or run one Application.

02.04. An Application is one durable application individual created from an
      AppDefinition binding.

02.05. An Application may have multiple ApplicationRuns over time.

02.06. An ApplicationRun is one live execution period of one Application.

02.07. A new ApplicationRun receives a fresh applicationRunId.

02.08. An ApplicationRun may be associated with one active SaveBundle when
      durable persistence is requested or required.

02.09. An ApplicationRun may be associated with one active writable SaveBundle
      owner when durable application mutation is allowed.

02.10. Application identity is distinct from AppPack identity.

02.11. Application identity is distinct from SaveBundle identity.

02.12. ApplicationRun identity is distinct from Application identity.

02.13. ApplicationRun identity is distinct from Pack identity.

02.14. ApplicationRun identity is distinct from SaveBundle identity.

02.15. ApplicationRun identity is distinct from View identity.

02.16. ApplicationRun identity is distinct from adapter identity.

02.17. ApplicationRun lifecycle is distinct from pack activation.

02.18. ApplicationRun lifecycle is distinct from execution adapter lifecycle.

02.19. ApplicationRun lifecycle is distinct from RPC transport lifecycle.

02.20. ApplicationRun lifecycle is distinct from Job lifecycle.

02.21. ApplicationRun lifecycle provides the live runtime container boundary in
       which activation, state mutation, Windows, capabilities, Views,
       adapters, debugging, ProcessingRuns, OrchestrationUnits, timers, hooks,
       tracing, and Jobs may occur.

02.22. Ending an ApplicationRun does not by itself define whether related work
       committed, aborted, cancelled, superseded, detached, resumed, retried,
       or retained a result.

02.23. Session is not a core runtime identity in this model.

02.24. ApplicationRun lifecycle does not define committed value representation,
       configuration semantics, retained evidence packaging, artifact export,
       comparison, Replay, Resume, or Retry workflow semantics.

02.25. Later sections refine and apply these rules. They do not weaken them.


===============================================================================
03. APPLICATION IDENTITY
===============================================================================

03.01. applicationId identifies one durable Application.

03.02. applicationId is created once for one Application.

03.03. applicationId persists across runtime shutdown and later loading when the
      Application is retained durably.

03.04. applicationId persists across multiple ApplicationRuns of the same
      Application.

03.05. Loading an existing Application does not create a new applicationId.

03.06. A deliberate clone or fork creates a new Application with a new
      applicationId.

03.07. Application provenance may record the source Application or retained
      generation when a clone or fork is created.

03.08. Application identity is not AppPack identity.

03.09. Application identity is not SaveBundle identity.

03.10. Application identity is not ApplicationRun identity.

03.11. Application identity is not View, adapter, Job, Window,
       OrchestrationUnit, RuntimeHost, Workspace, transport, or artifact
       identity.

03.12. Session does not identify an Application.


===============================================================================
04. APPLICATIONRUN IDENTITY
===============================================================================

04.01. applicationRunId identifies one ApplicationRun.

04.02. applicationRunId is stable for the lifetime of that ApplicationRun.

04.03. applicationRunId is not reused for a different ApplicationRun during the
      same Kernel or TurnixRuntime run.

04.04. applicationRunId is the correlation identity used by
      ApplicationRun-owned trace evidence.

04.05. applicationRunId does not identify an Application by itself.

04.06. applicationRunId does not identify an AppPack by itself.

04.07. applicationRunId does not identify a SaveBundle by itself.

04.08. applicationRunId does not identify a View by itself.

04.09. applicationRunId does not identify an execution adapter by itself.

04.10. applicationRunId does not identify an RPC message, RPC channel, or
       transport by itself.

04.11. applicationRunId does not identify a Job by itself.

04.12. applicationRunId does not identify an OrchestrationUnit by itself.

04.13. applicationRunId does not identify a Window by itself.

04.14. applicationRunId does not identify RuntimeHost or Workspace by itself.

04.15. applicationRunId does not identify artifact, export, comparison,
       Replay, Resume, or Retry workflow identity by itself.

04.16. Session does not identify an ApplicationRun.

04.17. An ApplicationRun record includes enough identity context, when
       available, to relate:
       - applicationRunId
       - applicationId
       - AppDefinition/AppPack binding identity
       - SaveBundle identity when applicable
       - accepted Pack graph identity when applicable
       - runtime host identity when such identity is defined
       - workspace identity when such identity is defined

04.18. RuntimeHost identity and workspace identity are defined by DA-28.


===============================================================================
05. RELATION TO APPDEFINITION AND APPPACK BINDING
===============================================================================

05.01. An Application has one accepted AppDefinition binding for the Application
      state being created, loaded, validated, migrated, or run.

05.02. An AppPack is the normal reusable application definition source.

05.03. Direct-local, synthetic-script, synthetic-test, and internal AppPack
      sources are AppDefinition source classes when those entry paths are used.

05.04. Such sources create normal Applications and ApplicationRuns when runtime
      or persistence use requires Application/ApplicationRun identity.

05.05. A script or runtime test using a synthetic source is not a separate
      execution species.

05.06. An ApplicationRun has one active Application identity.

05.07. An ApplicationRun has one active AppDefinition/AppPack binding for the
      Application being run.

05.08. An ApplicationRun does not silently change its active Application
      identity during its lifetime.

05.09. An ApplicationRun does not silently change its active
      AppDefinition/AppPack binding during its lifetime.

05.10. Switching to another AppDefinition/AppPack binding creates a new
       Application, clone, fork, migration, or explicitly defined transition
       according to owning documents.

05.11. ApplicationRun creation does not reopen AppDefinition/AppPack resolution
       silently.

05.12. AppDefinition/AppPack dependency resolution remains owned by the pack
       and resolution documents.

05.13. ApplicationRun runtime behavior remains constrained by the accepted
       AppDefinition/AppPack binding and accepted dependency graph.

05.14. DA-20 may name AppDefinition source classes only to define Application
       and ApplicationRun identity boundaries.

05.15. DA-20 does not define AppDefinition source mechanics, manifest schema,
       direct-local execution mechanics, synthetic source construction, or
       internal source policy.


===============================================================================
06. RELATION TO SAVEBUNDLE
===============================================================================

06.01. SaveBundle is the durable persistence closure of one Application.

06.02. A SaveBundle preserves Application identity and retained Application
      material according to owning documents.

06.03. SaveBundle material may include AppDefinition/AppPack binding evidence,
      selected Pack graph evidence, committed state, SaveBundle-bound
      configuration and policy material, generated static data, application
      data, finalized Window history, retained evidence, and retained Pack or
      application material.

06.04. This document names SaveBundle material only to define Application and
      ApplicationRun identity and lifecycle boundaries.

06.05. DA-20 does not define SaveBundle storage format.

06.06. DA-20 does not define SaveBundle generation-publication mechanics.

06.07. DA-20 does not define persistent I/O authority for SaveBundle storage.

06.08. An ApplicationRun may have one active SaveBundle identity when running
      from or against durable persistence.

06.09. Absence of active SaveBundle identity means no durable SaveBundle is
      bound, not that the ApplicationRun identity is invalid.

06.10. SaveBundle binding identifies the persistence closure against which
       committed state, Windows, retained evidence, and retained material are
       interpreted for the ApplicationRun.

06.11. SaveBundle identity is not Application identity.

06.12. SaveBundle identity is not ApplicationRun identity.

06.13. SaveBundle being bound to an ApplicationRun does not make
       adapter-executed code a SaveBundle writer.

06.14. SaveBundle mutation occurs only through Kernel-mediated state and
       persistence authority.

06.15. Authoritative mutation remains governed by DA-04.

06.16. Persistent I/O remains governed by DA-07.

06.17. Window and retained evidence behavior remains governed by DA-08.

06.18. SaveBundle-local Pack material remains constrained by pack and
       persistence-scope documents.


===============================================================================
07. APPLICATIONRUN CREATION AND LOADING PATHS
===============================================================================

07.01. ApplicationRun construction begins only after Turnix has resolved or
      reconstructed the Application and its accepted AppDefinition/AppPack
      binding.

07.02. ApplicationRun creation has two primary paths:
      - new Application creation path
      - existing Application loading path

07.03. New Application creation path means Turnix resolves the
      AppDefinition/AppPack source, creates a new Application identity, and
      prepares a SaveBundle when durable persistence is requested or required.
      Turnix then creates an ApplicationRun.

07.04. Existing Application loading path means Turnix inspects and loads an
      existing SaveBundle, validates the Application identity, validates the
      AppDefinition/AppPack binding, validates accepted graph evidence,
      resolves compatibility requirements, acquires writable ownership when
      writable use is requested, and creates a new ApplicationRun.

07.05. Loading an existing Application creates a new ApplicationRun of the same
      Application.

07.06. Loading an existing Application does not create a new Application unless
      an explicit clone, fork, recovery, or transition workflow does so.

07.07. AppDefinition-defined initialization behavior may run during new
      Application creation when such behavior is defined and authorized.

07.08. AppDefinition-defined initialization behavior remains AppPack-provided or
      source-provided executable behavior.

07.09. AppDefinition-defined initialization behavior remains subject to
      activation, adapter, capability, policy, and persistence boundaries.

07.10. Initialization behavior does not bypass DA-04 committed-state rules.

07.11. Initialization behavior does not bypass DA-07 persistence authority.

07.12. Compatibility validation failure prevents ApplicationRun creation unless
       explicit migration, override, or recovery policy permits another path.

07.13. Migration that changes authoritative committed state remains governed by
       DA-04 and DA-06.

07.14. ApplicationRun creation failure is explicit and trace-visible.

07.15. ApplicationRun creation failure does not create a partially valid
       ApplicationRun.

07.16. RuntimeHost startup modes and command surfaces use the Kernel-mediated
       Application/ApplicationRun creation and SaveBundle loading paths defined
       or referenced in this section.

07.17. RuntimeHost startup modes and command surfaces do not define separate
       ApplicationRun creation semantics.

07.18. DA-28 owns the RuntimeHost rule that all entry surfaces use the same
       Kernel-mediated creation and loading paths.

07.19. Loading an existing Application from a SaveBundle may include
       inspection, requirement reconstruction, ownership acquisition, runtime
       context construction, domain rehydration, activation, and
       ApplicationRun readiness.

07.20. DA-20 owns only the ApplicationRun identity and lifecycle part of those
       loading phases.


===============================================================================
08. WRITABLE SAVEBUNDLE OWNERSHIP
===============================================================================

08.01. A writable SaveBundle may be owned by at most one active writable
      ApplicationRun at a time.

08.02. Writable SaveBundle ownership prevents silent multi-writer mutation of
      durable Application state.

08.03. A second ApplicationRun does not silently acquire writable ownership
      of the same SaveBundle.

08.04. A second RuntimeHost does not silently acquire writable ownership of the
      same Workspace or SaveBundle.

08.05. RuntimeHost workspace ownership semantics are defined by DA-28.

08.06. Read-only inspection of a SaveBundle may be allowed by explicit tooling,
      export, review, or policy rules.

08.07. Read-only inspection does not create writable ownership.

08.08. Multi-writer SaveBundle behavior is not defined by this document.

08.09. Any future multi-writer mode requires an explicit authoritative design
      that defines conflict handling, transaction boundaries, persistence
      ordering, and recovery semantics.

08.10. Concrete workspace locking and concrete writable ownership
       implementation remain open for future implementation specifications
       constrained by DA-20, DA-28, DA-04, and DA-07.

08.11. Absence of concrete locking implementation detail does not weaken the
       single-writer semantic rule in this section.


===============================================================================
09. APPLICATIONRUN LIFECYCLE PHASES
===============================================================================

09.01. ApplicationRun lifecycle phases may include:
      - requested
      - creating
      - SaveBundle binding
      - starting
      - active
      - stopping
      - stopped
      - failed
      - crashed
      - closed

09.02. Concrete implementations may use additional internal states if those
      states preserve the externally visible meanings defined here.

09.03. requested means ApplicationRun creation has been requested but creation
      has not yet begun.

09.04. creating means Turnix is constructing ApplicationRun runtime identity and
      validating required creation inputs.

09.05. SaveBundle binding means Turnix is creating, loading, validating, or
      binding the active SaveBundle when such binding is required.

09.06. starting means Turnix is preparing the runtime active region and may
      begin pack activation or adapter preparation according to owning
      documents.

09.07. active means the ApplicationRun runtime active region exists.

09.08. stopping means Turnix is intentionally ending the active runtime region.

09.09. stopped means the ApplicationRun ended through normal controlled
      shutdown.

09.10. failed means ApplicationRun lifecycle could not continue because an
       error prevented valid creation, start, or controlled operation.

09.11. crashed means the ApplicationRun active region ended because the runtime
       failed unexpectedly or the Kernel detected loss of valid runtime
       continuity.

09.12. closed means ApplicationRun runtime identity has been released and is no
       longer usable for new runtime work.

09.13. Lifecycle phase names do not define Job terminal outcomes.

09.14. Lifecycle phase names do not define OrchestrationUnit outcomes.

09.15. Lifecycle phase names do not define Window finalization outcomes.

09.16. Lifecycle phase names do not define adapter lifecycle outcomes.

09.17. Lifecycle phase names do not define artifact or export outcomes.

09.18. Lifecycle phase names do not define Replay, Resume, or Retry outcomes.


===============================================================================
10. APPLICATIONRUN ACTIVE REGION
===============================================================================

10.01. An ApplicationRun active region is the bounded runtime interval during
      which an ApplicationRun is active.

10.02. An active region begins when the ApplicationRun becomes active.

10.03. An active region ends when the ApplicationRun is no longer active.

10.04. At most one active region exists for one ApplicationRun at a time.

10.05. Work occurring inside an ApplicationRun active region remains linkable to
      that ApplicationRun when the owning subsystem records ApplicationRun
      correlation evidence.

10.06. Ending an ApplicationRun active region does not by itself define whether
      in-flight work committed, aborted, retried, resumed, cancelled,
      superseded, detached, or retained a result.

10.07. Ending an ApplicationRun active region does not by itself define Window
      finalization, artifact export, comparison, Replay, Resume, or Retry
      workflow outcome.

10.08. Window finalization semantics are defined by DA-08.

10.09. Pack activation failure semantics are defined by DA-14.

10.10. Job lifecycle semantics are defined by DA-19.

10.11. OrchestrationUnit lifecycle semantics are defined by DA-24.

10.12. Adapter lifecycle semantics are defined by DA-23 and DA-27.


===============================================================================
11. RELATION TO PACK ACTIVATION
===============================================================================

11.01. Pack activation occurs inside or in relation to an ApplicationRun active
      region.

11.02. ApplicationRun creation does not by itself activate every pack.

11.03. ApplicationRun activation of the AppDefinition/AppPack binding and its
      runtime participants remains governed by DA-14.

11.04. ApplicationRun lifecycle is not pack activation lifecycle.

11.05. Pack activation success does not by itself mean ApplicationRun shutdown
      will succeed.

11.06. Pack activation failure may cause ApplicationRun start failure when the
      failed activation is required for the ApplicationRun to become active.

11.07. NotActivatedError remains an activation-domain outcome under DA-14.

11.08. ApplicationRun lifecycle evidence may causally link to activation trace
      evidence when activation affects ApplicationRun lifecycle.

11.09. DA-20 does not define lifecycle hook ordering, activation phase barriers,
      cyclic activation groups, or registration publication scopes.


===============================================================================
12. RELATION TO EXECUTION ADAPTERS
===============================================================================

12.01. Execution adapters may attach to or participate in an ApplicationRun.

12.02. Adapter participation does not make the adapter the ApplicationRun.

12.03. Adapter identity is distinct from ApplicationRun identity.

12.04. Adapter lifecycle is distinct from ApplicationRun lifecycle.

12.05. Adapter readiness does not imply ApplicationRun readiness.

12.06. ApplicationRun readiness does not imply that every possible adapter is
      ready.

12.07. Adapter failure does not automatically stop the ApplicationRun.

12.08. ApplicationRun stop does not automatically define adapter failure.

12.09. If adapter failure affects required ApplicationRun behavior, policy or
      lifecycle rules define whether the ApplicationRun continues, stops,
      fails, detaches the adapter, or enters another explicit outcome.

12.10. Adapter-executed code does not own ApplicationRun state.

12.11. Adapter-executed code requests ApplicationRun state mutation only
       through Kernel-mediated boundaries.

12.12. DA-23 owns execution adapter boundary semantics.

12.13. DA-27 owns adapter lifecycle, trust, isolation, and traceability
       semantics.


===============================================================================
13. RELATION TO VIEWS AND FRONTEND CLIENTS
===============================================================================

13.01. A View may present or control one ApplicationRun when the View class and
      policy permit that relationship.

13.02. View identity is distinct from ApplicationRun identity.

13.03. Frontend client identity is distinct from ApplicationRun identity.

13.04. A frontend client disconnect does not automatically stop an
      ApplicationRun.

13.05. View disconnect does not automatically stop an ApplicationRun.

13.06. ApplicationRun stop does not automatically define View failure.

13.07. If View lifecycle affects ApplicationRun lifecycle, that relationship is
      explicit and governed by View, policy, and ApplicationRun lifecycle
      rules.

13.08. DA-22 owns UI, View, and frontend runtime semantics.


===============================================================================
14. RELATION TO RPC AND TRANSPORTS
===============================================================================

14.01. RPC messages may target or originate from participants associated with an
      ApplicationRun.

14.02. RPC message identity is distinct from applicationRunId.

14.03. RPC channel identity is distinct from applicationRunId.

14.04. Transport lifecycle is distinct from ApplicationRun lifecycle.

14.05. Transport disconnect does not automatically stop an ApplicationRun.

14.06. Transport timeout does not automatically fail an ApplicationRun.

14.07. ApplicationRun stop does not automatically mean the transport failed.

14.08. If transport lifecycle affects ApplicationRun lifecycle, that effect is
      explicit and governed by policy and the owning lifecycle documents.

14.09. DA-21 owns RPC, channel, transport, and message-flow semantics.


===============================================================================
15. RELATION TO JOBS AND ORCHESTRATIONUNITS
===============================================================================

15.01. Jobs may execute inside or in relation to an ApplicationRun active
      region.

15.02. jobId is distinct from applicationRunId.

15.03. Job lifecycle is distinct from ApplicationRun lifecycle.

15.04. ApplicationRun stop does not automatically define Job terminal outcome.

15.05. Job terminal outcome does not automatically stop an ApplicationRun.

15.06. If ApplicationRun lifecycle affects a Job, DA-19 governs Job terminal
      outcome, cancellation, timeout, supersession, progress, late completion,
      and retained result semantics.

15.07. If a Job affects ApplicationRun lifecycle, that effect is explicit and
      governed by the workflow or lifecycle rules that own the relationship.

15.08. OrchestrationUnits may execute inside or in relation to an ApplicationRun
      active region.

15.09. orchestrationUnitId is distinct from applicationRunId.

15.10. OrchestrationUnit lifecycle is distinct from ApplicationRun lifecycle.

15.11. ApplicationRun lifecycle does not grant mutation authority outside
       OrchestrationUnit and transaction boundaries.

15.12. DA-19 owns Job lifecycle semantics.

15.13. DA-24 owns OrchestrationUnit lifecycle and mutation authority semantics.


===============================================================================
16. RELATION TO WINDOWS AND COMMITTED STATE
===============================================================================

16.01. Windows may be associated with one ApplicationRun.

16.02. An ApplicationRun active region may contain an ActiveWindow.

16.03. ApplicationRun lifecycle does not by itself finalize a Window.

16.04. ApplicationRun stop does not by itself create a SafePointWindow.

16.05. ApplicationRun failure does not by itself create an AbortedWindow.

16.06. Window finalization remains governed by DA-08.

16.07. Authoritative committed-state mutation remains governed by DA-04.

16.08. ApplicationRun lifecycle evidence may be retained inside Window evidence
      according to DA-08.

16.09. Retained ApplicationRun evidence does not become authoritative committed
      state merely because it is retained in a Window.

16.10. SafePointWindow, AbortedWindow, Window artifact, export, comparison,
       Replay, Resume, and Retry semantics remain outside DA-20 authority.


===============================================================================
17. RELATION TO PACKMANAGER AND OFFLINE WORKFLOWS
===============================================================================

17.01. PackManager may help prepare, inspect, or manage Pack graph intent
      used by an Application or ApplicationRun.

17.02. PackManager is not the Application.

17.03. PackManager is not the ApplicationRun.

17.04. PackManager does not define ApplicationRun lifecycle.

17.05. PackManager does not own ApplicationRun state authority.

17.06. PackManager graph-preparation and catalog-operation semantics are defined
      by DA-29.

17.07. Artifact and export semantics are defined by DA-25.

17.08. Comparison, Replay, Resume, and Retry workflow semantics are defined by
      DA-26.

17.09. ApplicationRun lifecycle evidence does not imply replayability,
      resumability, retryability, comparison completeness, or export
      completeness.


===============================================================================
18. APPLICATIONRUN TRACE REASON IDENTIFIERS
===============================================================================

18.01. DA-20 owns the runtime-identity trace reason identifiers used for
      ApplicationRun lifecycle and active-region span boundaries.

18.02. The following ApplicationRun-domain trace reasons are defined:

      - ApplicationRunCreationRequested
      - ApplicationRunCreationStarted
      - ApplicationRunSaveBundleBindingStarted
      - ApplicationRunSaveBundleBindingSucceeded
      - ApplicationRunSaveBundleBindingFailed
      - ApplicationRunStartStarted
      - ApplicationRunActiveSpanBegin
      - ApplicationRunStopRequested
      - ApplicationRunStopStarted
      - ApplicationRunActiveSpanEnd
      - ApplicationRunStopped
      - ApplicationRunFailed
      - ApplicationRunCrashed
      - ApplicationRunClosed

18.03. ApplicationRunCreationRequested is emitted when ApplicationRun
      creation is requested.

18.04. ApplicationRunCreationStarted is emitted when Turnix begins constructing
      ApplicationRun runtime identity and validating creation inputs.

18.05. ApplicationRunSaveBundleBindingStarted is emitted when Turnix begins
      creating, loading, validating, or binding the active SaveBundle.

18.06. ApplicationRunSaveBundleBindingSucceeded is emitted when active
      SaveBundle binding succeeds.

18.07. ApplicationRunSaveBundleBindingFailed is emitted when active SaveBundle
      binding fails.

18.08. ApplicationRunStartStarted is emitted when Turnix begins starting the
      ApplicationRun runtime active region.

18.09. ApplicationRunActiveSpanBegin is emitted when an ApplicationRun becomes
      active.

18.10. ApplicationRunStopRequested is emitted when ApplicationRun stop is
       requested.

18.11. ApplicationRunStopStarted is emitted when Turnix begins stopping the
       ApplicationRun active region.

18.12. ApplicationRunActiveSpanEnd is emitted when an ApplicationRun is no
       longer active.

18.13. ApplicationRunStopped is emitted when the ApplicationRun reaches
       controlled stopped state.

18.14. ApplicationRunFailed is emitted when the ApplicationRun lifecycle cannot
       continue because an error prevents valid creation, start, or controlled
       operation.

18.15. ApplicationRunCrashed is emitted when the ApplicationRun active region
       ends because runtime continuity failed unexpectedly.

18.16. ApplicationRunClosed is emitted when ApplicationRun runtime identity is
       released and no longer usable for new runtime work.

18.17. DA-03 defines the trace substrate used to represent ApplicationRun
       evidence.

18.18. DA-20 defines only ApplicationRun-domain ownership of these trace
       reasons and required correlation evidence.


===============================================================================
19. APPLICATIONRUN TRACE CONTEXT
===============================================================================

19.01. ApplicationRun trace evidence records enough context, when available, to
      explain:
      - applicationId
      - applicationRunId
      - AppDefinition/AppPack binding identity when applicable
      - SaveBundle identity when applicable
      - accepted Pack graph identity when applicable
      - creation request identity when applicable
      - runtime host identity when applicable
      - workspace identity when applicable
      - active region span identity when applicable
      - viewId when applicable
      - adapter identity when applicable
      - RPC message identity when applicable
      - jobId when applicable
      - orchestrationUnitId when applicable
      - failure reason category when failure occurs
      - stop reason category when stopping occurs
      - crash reason category when crash is detected

19.02. ApplicationRunActiveSpanBegin trace evidence records enough context to
      explain:
      - applicationId
      - applicationRunId
      - spanIdentity
      - AppDefinition/AppPack binding identity when applicable
      - SaveBundle identity when applicable

19.03. ApplicationRunActiveSpanEnd trace evidence records enough context to
      explain:
      - applicationRunId
      - spanIdentity
      - endReasonCategory

19.04. ApplicationRunActiveSpanEnd endReasonCategory distinguishes:
      - NormalDeactivate
      - Crash
      - ForcedDeactivate
      - KernelExit

19.05. ApplicationRun trace evidence does not replace activation trace evidence.

19.06. ApplicationRun trace evidence does not replace adapter trace evidence.

19.07. ApplicationRun trace evidence does not replace RPC trace evidence.

19.08. ApplicationRun trace evidence does not replace Job trace evidence.

19.09. ApplicationRun trace evidence does not replace OrchestrationUnit trace
      evidence.

19.10. ApplicationRun trace evidence does not replace Window finalization
       evidence.

19.11. ApplicationRun trace evidence does not replace RuntimeHost trace
       evidence.

19.12. ApplicationRun trace evidence does not replace PackManager trace
       evidence.

19.13. ApplicationRun trace evidence does not replace artifact or export trace
       evidence.

19.14. ApplicationRun trace evidence does not replace Replay, Resume, or Retry
       workflow trace evidence.

19.15. ApplicationRun trace evidence does not replace committed-state trace
       evidence.

19.16. ApplicationRun trace evidence does not replace persistent-I/O evidence.

19.17. RuntimeHost trace evidence and RuntimeHost-domain trace reason ownership
       are defined by DA-28.

19.18. ApplicationRun trace evidence is correlation and lifecycle evidence.

19.19. ApplicationRun trace evidence is not committed-state truth.

19.20. ApplicationRun trace evidence is not SaveBundle truth.

19.21. ApplicationRun trace evidence is not a workflow outcome.

20. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

20.01. The following are not supported:
      - treating Application identity as Pack identity
      - treating Application identity as SaveBundle identity
      - treating ApplicationRun identity as Application identity
      - treating ApplicationRun identity as Pack identity
      - treating ApplicationRun identity as SaveBundle identity
      - treating ApplicationRun identity as View identity
      - treating ApplicationRun identity as adapter identity
      - treating ApplicationRun identity as RPC, channel, or transport identity
      - treating ApplicationRun identity as Job identity
      - treating ApplicationRun identity as OrchestrationUnit identity
      - treating ApplicationRun identity as Window identity
      - treating ApplicationRun identity as RuntimeHost or Workspace identity
      - treating ApplicationRun identity as artifact or export identity
      - treating ApplicationRun identity as comparison, Replay, Resume, or
        Retry workflow identity
      - treating Session as core runtime identity
      - changing Application identity silently inside one ApplicationRun
      - changing AppDefinition/AppPack binding silently inside one
        ApplicationRun
      - silent writable multi-writer SaveBundle ownership
      - adapter-owned ApplicationRun state authority
      - frontend-owned ApplicationRun state authority
      - transport disconnect silently stopping an ApplicationRun
      - View disconnect silently stopping an ApplicationRun
      - Job terminal outcome silently stopping an ApplicationRun
      - ApplicationRun stop silently defining Job terminal outcome
      - ApplicationRun stop silently finalizing a Window
      - ApplicationRun failure silently creating an AbortedWindow
      - ApplicationRun creation failure leaving a partially valid
        ApplicationRun
      - RuntimeHost startup mode creating separate ApplicationRun creation
        semantics
      - command surface creating separate ApplicationRun creation semantics

===============================================================================
22. LOCKED SUMMARY
===============================================================================

22.01. LOCKED:
      - Application is one durable application individual
      - applicationId identifies one durable Application
      - ApplicationRun is one live execution period of one Application
      - applicationRunId identifies one live ApplicationRun
      - ApplicationRun has one active Application identity
      - ApplicationRun has one active AppDefinition/AppPack binding
      - ApplicationRun may be bound to a SaveBundle when durable persistence is
        requested or required
      - Application identity is distinct from ApplicationRun identity
      - ApplicationRun identity is distinct from Pack identity
      - ApplicationRun identity is distinct from SaveBundle identity
      - ApplicationRun identity is distinct from View identity
      - ApplicationRun identity is distinct from adapter identity
      - ApplicationRun identity is distinct from Job identity
      - ApplicationRun identity is distinct from OrchestrationUnit identity
      - ApplicationRun identity is distinct from Window identity
      - ApplicationRun lifecycle is distinct from pack activation
      - ApplicationRun lifecycle is distinct from execution adapter lifecycle
      - ApplicationRun lifecycle is distinct from RPC transport lifecycle
      - ApplicationRun lifecycle is distinct from Job lifecycle
      - Session is not a core runtime identity
      - new Application creation and existing Application loading are distinct
        ApplicationRun creation/loading paths
      - RuntimeHost startup modes and command surfaces use the same
        Kernel-mediated Application/ApplicationRun creation and SaveBundle
        loading paths defined or referenced by DA-20
      - a writable SaveBundle may be owned by at most one active writable
        ApplicationRun at a time
      - ApplicationRun active regions have begin and end boundaries
      - ApplicationRun stop does not by itself define Job terminal outcome
      - ApplicationRun stop does not by itself finalize a Window
      - adapter-executed code does not own ApplicationRun state
      - DA-20 owns runtime-identity trace reason identifiers
      - DA-28 owns RuntimeHost-domain trace reason identifiers and runtime-host
        Workspace and command-surface semantics
      - DA-03 owns the trace substrate, not ApplicationRun lifecycle semantics

22.02. OPEN:
      - concrete Application and ApplicationRun identifiers, compatibility
        validation, initialization API, restart, retained-result, fork/clone,
        provenance, and implementation substate details
