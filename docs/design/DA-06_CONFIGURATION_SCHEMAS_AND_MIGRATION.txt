===============================================================================
DESIGN AREA DA-06 - CONFIGURATION, SCHEMAS & MIGRATION
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines configuration as schema-governed authoritative state, explains how
configuration is scoped, layered, materialized, stored, and migrated, and
defines how configuration evolves without silent breakage.

Configuration is data with identity.
Breaking it silently is forbidden.

Purpose:
--------
This document defines how configuration exists, how configuration is
validated, how configuration evolves over time, how configuration is
materialized into persistent files, and how user state is protected.

This area defines:
- configuration as a specialized use of the Turnix state model
- configuration scopes and precedence rules
- schema role for configuration
- defaults and override-input rules
- configuration ownership identity
- the configuration materialization pipeline
- effectiveConfig and computed transform constraints
- configuration-domain trace emission obligations
- config access API semantics
- persistent config storage layout and file placement
- paths.config.json and policies.config.json placement
- duplicate schema/default/config file selection rules
- migration rules and state-safety boundaries
- persistent-I/O mediation requirements for configuration persistence
- error classification and recovery boundaries

This area does NOT define:
- the general memory/state model (see DA-04)
- committed payload representation semantics (see DA-05)
- direct filesystem I/O rules beyond the DA-07 mediation boundary
- tracing schema, retention, pruning, loss, or storage (see DA-03)
- debugger pause and mutation safety semantics (see DA-18)
- the full root/bootstrap candidate model (see DA-09)
- decision and remembered-policy semantics (see DA-17)
- Application, ApplicationRun, AppPack, or SaveBundle identity
- a fully generalized schema system for all structured data domains

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines configuration, schema use for configuration,
      storage materialization for configuration, and migration constraints
      within that shared interpretation model.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. Configuration answers:

          "Which parameters influence Turnix and packs at runtime,
           how are they made safe, stable, and evolvable,
           and where are they persisted?"

02.02. Configuration is authoritative state.

02.03. Configuration is not:
      - arbitrary JSON blobs
      - free-form user data
      - implicit defaults hidden in code

02.04. Configuration follows the general memory/state model defined in
      [constrained-by: DA-04 02], [constrained-by: DA-04 06],
      [constrained-by: DA-04 07], and [constrained-by: DA-04 09].

02.05. This document refines that general model only for:
      - configuration scopes
      - schema-governed validation and interpretation
      - defaults and override inputs
      - effectiveConfig materialization
      - persistent configuration file placement
      - configuration migration and recovery

02.06. Configuration remains explainable, reversible, and protected from
      silent breakage.

02.07. Schema is introduced in this document for configuration first.

02.08. The schema model described here may later serve other structured data
      domains, but this document does not define the full generalized
      schema system for those domains.

02.09. Configuration is authoritative state, but configuration is not a
      separate state architecture.

02.10. DA-06 builds on DA-04 for state authority.

02.11. When configuration values are stored as Turnix committed payload
       material, they use the committed-value representation contract
       defined by DA-05.

02.12. DA-06 defines configuration meaning, scope, schema use,
       materialization, migration, storage placement, and recovery.

02.13. DA-05 defines payload identity, Chunk, ChunkId, ValueRef, decode,
       integrity, and reachability representation.

02.14. DA-06 does not redefine ValueRef, Chunk identity, ChunkId meaning,
       decode, integrity, or payload reachability.


===============================================================================
03. CONFIGURATION AS STATE
===============================================================================

03.01. Configuration uses the same authority boundary as other Turnix state.

03.02. Committed configuration is authoritative.

03.03. Runtime-visible configuration views are not authoritative merely
      because they are resident or currently effective.

03.04. Configuration persistence is protection against loss rather than the
      definition of truth, [constrained-by: DA-04 09].

03.05. Storage layout and file placement defined later in this document do
      not redefine authority.

03.06. Storage layout and file placement define where authoritative
      configuration is persisted.

03.07. Configuration mutation that changes authoritative committed state is
      normal orchestrated work and follows the general transaction and
      commit rules from [constrained-by: DA-04 07] and
      [constrained-by: DA-04 19].

03.08. Configuration writes through Pack-facing or runtime-facing gateways
      stage into the current transaction when they affect authoritative
      Application state.

03.09. This document does not create a separate state architecture for
      configuration.


===============================================================================
04. CONFIGURATION SCOPES, OWNERSHIP, AND IDENTITY (LOCKED)
===============================================================================

04.01. Turnix distinguishes configuration by scope:

      A) Engine
      B) Pack-global
      C) Save-bound

04.02. Engine scope is engine-owned configuration under Kernel authority.

04.03. Pack-global scope is configuration owned by one specific pack and
      shared across Applications where the surrounding design permits it.

04.04. Save-bound scope is configuration owned by one specific pack inside
      one SaveBundle/Application context.

04.05. Scopes are strictly ordered by precedence:

      Save-bound > Pack-global > Engine > Defaults

04.06. Each scope has:
      - schema-governed value shape
      - defaults
      - explicit override inputs
      - migration path

04.07. Ownership rules:

04.07.01. Engine scope is owned by the Kernel-controlled configuration
        domain.

04.07.02. Pack-global scope is owned by one specific canonicalPackId.

04.07.03. Save-bound scope is owned by one specific canonicalPackId inside
        one SaveBundle/Application context.

04.08. Ownership is immutable without migration.

04.09. There is no shared global bag of configuration keys.

04.10. canonicalPackId is the persistent configuration-ownership identity
       for pack-global and save-bound configuration.

04.11. canonicalPackId is exactly:

       resolvedAuthor + "@" + packTreeId

04.12. canonicalPackId does not include version or semver.

04.13. Version metadata may be stored inside configuration files,
       migration metadata, or both, but version is not part of the
       persistent ownership identity.

04.14. resolvedAuthor exists through:
       - declared author
       - inherited author

04.15. If resolvedAuthor cannot be determined, the pack is invalid.

04.16. Configuration ownership and cross-pack mutation authority remain
       constrained by pack identity, dependency, visibility, capability,
       permission, decision, OrchestrationUnit, and ModCallContext
       boundaries.

04.17. Configuration ownership does not grant direct backend access.

04.18. Configuration ownership does not bypass visibility, permission,
       policy, mutation-authority, or gateway constraints.


===============================================================================
05. SCHEMA ROLE FOR CONFIGURATION (LOCKED)
===============================================================================

05.01. Schemas define:
      - structure
      - types
      - constraints
      - allowed value shapes
      - compatibility expectations
      - access-level metadata when configuration authority rules require it

05.02. Schemas are not a source of runtime defaults.

05.03. Schemas do not by themselves create authoritative values.

05.04. In this document, schema governs how configuration values are:
      - interpreted
      - validated
      - migrated safely
      - exposed with correct ownership and access metadata

05.05. The schema model described here is storage-agnostic at the semantic
      level.

05.06. Storage placement and file realization defined later in this document
      do not redefine schema meaning.

05.07. Current schema realization may use JSON-like structured forms, but
      this document does not lock the full implementation dialect.

05.08. Schema evolution rules:

05.08.01. Released schema meaning does not change previous meaning silently.

05.08.02. Breaking schema change requires an explicit compatibility boundary
        and matching migration treatment.

05.08.03. Access-level metadata does not change silently.

05.09. This document defines schema use for configuration first.

05.10. This document does not define the full generalized schema system for
       manifests and other structured data domains.


===============================================================================
06. DEFAULTS AND OVERRIDE INPUTS (LOCKED)
===============================================================================

06.01. Defaults define initial values only.

06.02. Defaults are immutable input material.

06.03. Defaults are not user configuration.

06.04. Defaults are not mutable state.

06.05. Override inputs record explicit user-authored deviations from
      defaults.

06.06. Override inputs never modify defaults.

06.07. Override inputs are loaded after defaults.

06.08. Override inputs are migrated explicitly.

06.09. Override inputs are not modified silently.

06.10. Override inputs are not silently rewritten by storage
       materialization, migration, normalization, or persistence side
       effects.

06.11. Override inputs are the only user-authored persisted configuration
       input layer.

06.12. This does not create an exception to the general DA-04 state model.

06.13. Authoritative committed configuration still follows normal state
       mutation and commit rules.

06.14. Defaults may change between pack or platform versions at author
       responsibility.

06.15. Changed defaults remain authored input change, not user-authored
       override change.

06.16. If changed defaults alter effective behavior, that change remains
       distinguishable from user-authored overrides.

06.17. Duplicate schema, default, or configuration file is selected, not
       stacked.

06.18. Duplicate schema, default, or configuration file is shadowed, not
       merged.

06.19. Deterministic selection rule:
       - first candidate in deterministic order wins
       - later duplicates remain shadowed
       - no additive combination occurs

06.20. Diagnostics and tracing surface duplicate schema, default, or
       configuration files as strongly as available evidence permits.

06.21. Duplicate diagnostics include which file was selected and which
       files were shadowed when that evidence is available.

06.22. Equivalent duplicates remain diagnostics.


===============================================================================
07. CONFIGURATION MATERIALIZATION PIPELINE (LOCKED)
===============================================================================

07.01. Configuration is materialized through the following semantic stages:

      1) schema interpretation
      2) defaults input
      3) explicit override inputs
      4) migration when required
      5) validation of stored values
      6) computed transforms when allowed
      7) effectiveConfig materialization

07.02. Stages 1 through 5 are gating stages.

07.03. Stages 6 and 7 are runtime-view stages.

07.04. Runtime-view stages do not by themselves create authoritative
      committed state.

07.05. Materialization produces a runtime-visible configuration view from
      authoritative committed configuration plus permitted derived
      behavior.

07.06. Materialization remains explainable and traceable.

07.07. Computed layers and effectiveConfig remain compatible with
      [constrained-by: DA-04 02.2] and [constrained-by: DA-04 02.3].

07.08. Explicit and conventional configuration sources are selected by the
      owning configuration-source rules.

07.09. Source selection does not merge explicit and conventional sources
      unless an owning configuration-source rule explicitly defines that
      behavior.


===============================================================================
08. EFFECTIVECONFIG AND COMPUTED TRANSFORMS (LOCKED)
===============================================================================

08.01. effectiveConfig is the final runtime-visible configuration view.

08.02. effectiveConfig is not a separate authoritative state class.

08.03. Some configuration values may be:
      - computed
      - derived
      - transformed
      - adjusted based on other values

08.04. Computed transforms operate only on effectiveConfig.

08.05. Computed transforms do not mutate stored values.

08.06. Computed transforms do not write configuration.

08.07. Removal of a computed transform restores prior stored-value behavior
      automatically.

08.08. Computed layers remain traceable as computed effects.

08.09. Computed effects do not appear as stored mutations.

08.10. Diagnostic validation of effectiveConfig may exist, but stored-value
       validation remains authoritative.

08.11. Runtime-effective configuration may include launch arguments,
       environment input, or runtime-only overrides when another owning
       document permits those inputs.

08.12. Runtime-only overrides do not become persisted configuration merely
       because they affected effectiveConfig.


===============================================================================
09. CONFIGURATION TRACE OBLIGATIONS (LOCKED)
===============================================================================

09.01. Configuration interactions have configuration-domain trace emission
      obligations when they affect:
      - authoritative configuration
      - validation
      - migration
      - materialization
      - recovery
      - duplicate file selection or shadowing

09.02. Configuration trace evidence distinguishes:

      A) Stored mutation
      - change written through the configuration authority path
      - persisted through persistent-I/O authority when persistence is
        required
      - attributed to engine, pack-global, or save-bound scope

      B) Computed effect
      - derived value
      - reactive transform
      - accessibility scaling
      - runtime-only override

      C) Read resolution
      - which layer provided the value
      - defaults versus user override versus save-bound override
      - not-found or permission-denied outcome when applicable

09.03. Computed effects do not appear as stored mutations.

09.04. Configuration trace evidence records enough context to explain:
      - configuration key or subtree identity
      - configuration scope
      - source layer
      - owning pack identity when applicable
      - whether the action was debugger-initiated
      - whether validation, migration, or recovery participated
      - duplicate file selection and shadowing when applicable

09.05. Debugger-initiated configuration changes are labeled explicitly.

09.06. Debugger-initiated configuration changes are not conflated with
      runtime-originated or pack-originated changes.

09.07. Configuration trace obligations remain constrained by DA-04 state and
      transaction authority rules.

09.08. DA-03 defines the tracing substrate used to represent configuration
      trace evidence.

09.09. DA-03 owns trace retention, trace pruning, trace loss, event
      structure, span mechanics, and trace storage semantics.

09.10. Configuration trace evidence is not committed state.

09.11. Trace loss weakens evidential completeness but does not by itself
       change committed-configuration truth.


===============================================================================
10. CONFIG ACCESS API (LOCKED)
===============================================================================

10.01. Configuration access is scope-explicit and ownership-aware.

10.02. Engine scope API:

      config.engine.get(key)
      config.engine.set(key, value)
      config.engine.delete(key)
      config.engine.deleteTree(prefixKey)
      config.engine.tryGet(key)

10.03. Pack-global scope API:

      config.user.get(packSelector, key)
      config.user.set(packSelector, key, value)
      config.user.delete(packSelector, key)
      config.user.deleteTree(packSelector, prefixKey)
      config.user.tryGet(packSelector, key)

10.04. Save-bound scope API for the current owner pack context:

      config.save.get(key)
      config.save.set(key, value)
      config.save.delete(key)
      config.save.deleteTree(prefixKey)
      config.save.tryGet(key)

10.05. Save-bound scope API for explicit target pack ownership:

      config.save.getFrom(packSelector, key)
      config.save.setFrom(packSelector, key)
      config.save.deleteFrom(packSelector, key)
      config.save.deleteTreeFrom(packSelector, prefixKey)
      config.save.tryGetFrom(packSelector, key)

10.06. Read semantics:

10.06.01. get() returns value or raises NotFoundOrPermissionDenied.

10.06.02. tryGet() returns value when present or None when the addressed key
        does not exist.

10.06.03. The API does not distinguish not-found from permission-denied
        programmatically.

10.06.04. The real denial reason remains trace-visible internally.

10.07. Write semantics:

10.07.01. Writes target an explicit owner scope.

10.07.02. Writes may trigger permission decisions or user decisions.

10.07.03. delete() removes exactly the addressed override key.

10.07.04. delete() never mutates defaults.

10.07.05. deleteTree() removes the addressed override node and its subtree.

10.07.06. deleteTree() never mutates defaults.

10.07.07. Delete is a write-class operation.

10.08. Cross-pack configuration access remains constrained by pack identity,
      dependency, visibility, capability, permission, decision,
      OrchestrationUnit, and ModCallContext boundaries.

10.09. Pack-facing gateways expose mediated configuration surfaces.

10.10. Pack-facing gateways do not expose backend configuration services.

10.11. Pack-facing gateways do not expose raw filesystem access through
       configuration APIs.

10.12. Save-bound API calls address the SaveBundle/Application context of
       the current Application unless an explicit target pack ownership API
       is used.


===============================================================================
11. CONFIG STORAGE LAYOUT (LOCKED)
===============================================================================

11.01. Turnix-written live and save-bound configuration files use strict JSON.

11.02. Human-facing defaults and other authored source material may use
      comment-capable JSON dialects where other authoritative documents
      permit it.

11.03. Turnix-written live and save-bound configuration files do not use
      comments as a semantic mechanism.

11.04. Comments never carry structure, authority, migration meaning, or
      loader instructions.

11.05. Engine-global live configuration is stored under:

      userdata/config/engine/

11.06. Pack-global live configuration is stored under:

      userdata/config/packs/

11.07. Save-bound configuration is stored under the SaveBundle or saved
      Application storage scope using deterministic internal configuration
      paths.

11.08. The logical SaveBundle engine configuration path is:

      config/engine/

11.09. The logical SaveBundle pack configuration path is:

      config/packs/

11.10. Engine-global config file form is:

       userdata/config/engine/<name>.config.json

11.11. Pack-global config file form is:

       userdata/config/packs/<canonicalPackId>.config.json

11.12. Save-bound engine config file form inside the SaveBundle
       configuration scope is:

       config/engine/<name>.config.json

11.13. Save-bound pack config file form inside the SaveBundle
       configuration scope is:

       config/packs/<canonicalPackId>.config.json

11.14. Concrete outer SaveBundle directory materialization is storage
       layout, not identity truth.

11.15. Path placeholders do not define Application identity.

11.16. Path placeholders do not define ApplicationRun identity.

11.17. Path placeholders do not define AppPack identity.

11.18. Path placeholders do not define SaveBundle identity.

11.19. paths.config.json is engine-owned configuration and is stored at:

       userdata/config/engine/paths.config.json

11.20. Global policies.config.json is stored at:

       userdata/config/engine/policies.config.json

11.21. Save-bound policies.config.json is stored inside the SaveBundle
       engine configuration scope at:

       config/engine/policies.config.json

11.22. One clearly owned file per owner/name is the current rule.

11.23. For engine config, one engine config domain maps to one file.

11.24. For pack-owned config, one owning pack maps to one file.

11.25. Later expansion to more complex grouping is possible, but this
       document currently locks one clearly owned file per owner/name.

11.26. Defaults and authored configuration material remain load-only at
       runtime.

11.27. Turnix runtime does not rewrite defaults or authored configuration
       material as part of ordinary persistence.

11.28. The root/bootstrap behavior of paths.config.json fields is defined
       in DA-09.

11.29. This document is authoritative for paths.config.json field naming,
       ownership classification, storage placement, and persistence
       materialization.

11.30. paths.config.json is engine-owned persisted configuration.

11.31. paths.config.json file placement does not redefine the higher
       bootstrap semantics that DA-09 governs.

11.32. Locked field names for paths.config.json are:
       - redirectUserdataDirectoryTo
       - userdataDirectoryRoots
       - savesDirectoryRoots
       - customDirectoryRoots
       - firstPartyDirectoryRoots
       - thirdPartyDirectoryRoots
       - selectedUserdata
       - selectedSaves
       - preferredUserdata
       - preferredSaves
       - preferredCustom
       - preferredFirstParty
       - preferredThirdParty

11.33. selected* fields express explicit user-selected roots for active
       state categories.

11.34. preferred* fields express the last used usable directory for their
       category.

11.35. preferred* is sticky.

11.36. Stored preferred* values are always rechecked for continued usability
       and, where writing is required, writability before reuse.

11.37. preferred* is not replaced merely because a different candidate
       becomes writable later.

11.38. selected* for userdata and saves overrides preferred* when usable.

11.39. selected* and preferred* for userdata or saves may differ when a
       previously selected path becomes unusable and controlled recovery
       causes Turnix to use another path.

11.40. DA-09 defines how selected* and *DirectoryRoots participate in
       bootstrap and candidate-root behavior.

11.41. This document does not duplicate DA-09 bootstrap logic.


===============================================================================
12. PERSISTENT-I/O MEDIATION (LOCKED)
===============================================================================

12.01. Configuration services and providers do not perform filesystem I/O
      directly.

12.02. Configuration persistence routes through DA-07 persistent-I/O
      authority.

12.03. Where IoManager is the concrete managed file and persistent-I/O
      surface, it mediates configuration persistence.

12.04. Persistent-I/O authority enforces:
      - root boundaries
      - permission checks
      - atomic writes
      - backup and snapshot policy
      - error classification
      - recovery surfaces

12.05. DA-06 defines storage layout, file placement, and ownership mapping
      for configuration.

12.06. DA-06 does not redefine low-level filesystem behavior.

12.07. DA-06 does not redefine direct filesystem I/O rules.

12.08. DA-06 does not redefine DA-07 persistence mechanics.

12.09. If selected/preferred directories or canonical persisted config
      locations cannot be written:
      - Turnix does not silently fall through to some other writable path
      - the failure is surfaced through persistent-I/O authority or delegated
        manager flow
      - a failed persistence action fails explicitly rather than faking
        success elsewhere

12.10. Path/config placement failure follows the same explicit recovery
       model as other configuration persistence failure.

12.11. Path/config placement failure does not create a separate silent
       fallback path.

12.12. Directory/path queries may yield no usable target when no valid
       directory is currently available.

12.13. Consumers that can tolerate such absence may handle it in controlled
       form.

12.14. Consumers that cannot tolerate such absence propagate failure normally
       into the surrounding error-handling model.

12.15. User prompting and recovery remain centralized through persistent-I/O
       authority or delegated manager flow rather than ad hoc consumer
       logic.

12.16. This remains aligned with the broader decision-handling and failure
       propagation model defined in DA-17.

12.17. Direct SaveBundle-directory mutation is not a configuration
       persistence path.


===============================================================================
13. CONFIGURATION MIGRATION (LOCKED)
===============================================================================

13.01. Configuration migration evolves authoritative configuration state.

13.02. Configuration migration is not a side path outside normal state rules.

13.03. Configuration migration that changes authoritative committed state
      follows [constrained-by: DA-04 19].

13.04. Configuration migration runs before stored-value validation of the
      migrated result.

13.05. Migrators are versioned and ordered.

13.06. Multiple migrators may run sequentially.

13.07. A migrator is a deterministic transformation from one configuration
      representation to another.

13.08. Migration may inspect previous values.

13.09. Migration does not discard user intent silently.

13.10. Migration preserves ownership and access metadata unless an explicit
       accepted migration rule changes them.

13.11. If migration cannot complete safely, migration aborts and
       authoritative configuration remains identical to the pre-migration
       committed state.

13.12. Migration that changes policy storage records does not define policy
       semantics.

13.13. Policy record meaning remains owned by DA-17.


===============================================================================
14. MIGRATION SAFETY, BACKUP, AND RECOVERY (LOCKED)
===============================================================================

14.01. Before writing migrated configuration, persistent-I/O authority may
      create a recoverable snapshot of the last known good state.

14.02. Migrated authoritative configuration writes are atomic.

14.03. Rollback capability remains available when policy requires it.

14.04. No silent fallback is allowed.

14.05. User-mediated recovery options may include:
      - restore last known good
      - reset to defaults
      - quarantine broken configuration
      - abort affected startup or affected operation

14.06. Recovery remains explicit.

14.07. Recovery remains subject to configuration-domain trace emission
      obligations.

14.08. Backups and snapshots protect recoverability.

14.09. Backups and snapshots do not define truth.

14.10. Migrators do not provide rollback safety by inverse logic.


===============================================================================
15. MANIFEST MIGRATION AND CONFIGURATION MIGRATION (LOCKED DISTINCTION)
===============================================================================

15.01. Manifest migration and configuration migration are separate concerns.

15.02. Manifest migration evolves pack or artifact metadata.

15.03. Configuration migration evolves user or engine configuration state.

15.04. These migration classes remain separate even when they use related
      schema ideas.

15.05. This document defines configuration migration only.

15.06. This document does not define manifest migration.


===============================================================================
16. SAVE-BOUND CONFIGURATION (LOCKED)
===============================================================================

16.01. Save-bound configuration is isolated per SaveBundle/Application
      context.

16.02. Save-bound configuration overrides pack-global and engine values
      within that SaveBundle/Application context.

16.03. Save-bound configuration migrates independently.

16.04. Save-bound configuration is included in SaveBundle authoritative
      state and restoration boundaries.

16.05. Corruption or deletion of save-bound configuration does not by itself
      alter global configuration state.

16.06. Engine save-bound configuration is allowed.

16.07. Pack-owned save-bound configuration follows the same owner/file model
      as pack-global configuration, but under the SaveBundle configuration
      scope.

16.08. policies.config.json may exist in save-bound engine config storage
      without changing the general ownership model.

16.09. SaveBundle carries save-bound configuration.

16.10. SaveBundle does not become the semantic owner of configuration
       merely because it carries persisted configuration material.

16.11. The configuration domain remains the semantic owner of configuration
       meaning.


===============================================================================
17. POLICY STORAGE (LOCKED)
===============================================================================

17.01. Global persisted policies are stored in:

      userdata/config/engine/policies.config.json

17.02. Save-scoped persisted policies are stored inside the SaveBundle
      engine configuration scope at:

      config/engine/policies.config.json

17.03. Run-scoped policy is memory-only and is never persisted.

17.04. policies.config.json contains top-level sections:
      - permissionPolicies
      - fingerprintPolicies

17.05. permissionPolicies and fingerprintPolicies are semantically distinct
      remembered-decision classes.

17.06. permissionPolicies persist remembered permission decisions.

17.07. fingerprintPolicies persist remembered fingerprint-mismatch
      acceptance decisions.

17.08. Exact internal JSON record shape inside those sections remains
      intentionally flexible for now.

17.09. DA-06 is authoritative for:
      - policy storage location
      - policy file placement
      - top-level persistent config structure

17.10. DA-17 is authoritative for:
       - decision semantics
       - remembered policy semantics
       - policy scope precedence
       - permission policy identity
       - fingerprint policy identity
       - work-lifecycle policy semantics

17.11. Storing a policy record in policies.config.json does not by itself
       create a valid policy outcome outside DA-17 semantics.

17.12. Additional top-level policy sections require an explicit
       policy-persistence decision by the owning policy semantics.

17.13. This document does not add a work-lifecycle policy storage section.


===============================================================================
18. ERROR HANDLING AND RECOVERY BOUNDARIES (LOCKED)
===============================================================================

18.01. Configuration errors are classified.

18.02. Fatal examples include:
      - missing required schema material
      - missing required defaults material where defaults are mandatory
      - failure before minimal recovery UI is ready

18.03. Recoverable examples include:
      - invalid user value
      - parse errors
      - migration-required state
      - restore-from-backup decisions

18.04. Recovery remains UI-driven or policy-driven where the surrounding
      design permits it.

18.05. Configuration handling does not invent defaults.

18.06. Configuration handling does not ignore invalid stored values.

18.07. Configuration handling does not auto-reset silently.

18.08. Configuration handling does not treat parse errors as empty
      configuration.

18.09. Configuration handling does not silently write to another config file
      because the chosen one failed.

18.10. Configuration handling does not silently move selected/preferred
       config state elsewhere.


===============================================================================
19. DEV-MODE DIAGNOSTICS (LOCKED)
===============================================================================

19.01. Development diagnostics may report:
      - unused keys
      - deprecated keys
      - schema drift
      - effective-config diagnostics
      - access denials as informational diagnostics
      - duplicate schema, default, or configuration files
      - shadowed equivalent or divergent config files

19.02. Development diagnostics are non-fatal unless some other authoritative
      document explicitly states otherwise.

19.03. Development diagnostics do not rewrite stored configuration.

19.04. Development diagnostics do not migrate configuration.

19.05. Development diagnostics do not promote configuration between scopes.

19.06. Development diagnostics do not create policy outcomes.


===============================================================================
20. NO IMPLICIT FALLBACKS (LOCKED)
===============================================================================

20.01. Turnix does not:
      - invent defaults
      - ignore invalid stored values
      - auto-reset without consent or explicit policy
      - treat parse errors as empty configuration
      - silently write to some other config file because the chosen one
        failed
      - silently move selected/preferred config state elsewhere
      - silently promote save-bound configuration to pack-global
      - silently promote pack-global configuration to engine
      - silently broaden policy or configuration authority

20.02. Explicitness takes precedence over convenience.

20.03. Controlled recovery is not silent fallback.

20.04. A recovery path is valid only when the surrounding authority model,
      user decision, or explicit policy permits it.


===============================================================================
21. EXPLICITLY OPEN QUESTIONS
===============================================================================

21.01. OPEN questions include:
      - hot-reload semantics
      - config-diff UI
      - cross-scope promotion UX
      - when the broader generalized schema system splits from
        configuration-first design
      - whether later implementation requires finer-grained policy file
        partitioning
      - exact internal JSON record shape inside persisted policy sections
      - whether work-lifecycle policy persistence requires a top-level
        policies.config.json section, another storage shape, or no DA-06
        storage section
      - exact concrete outer SaveBundle directory materialization paths

21.02. Storage meaning, file placement, and owner/path identity defined in
      this document are otherwise treated as semantically locked.

21.03. OPEN questions do not weaken the no-implicit-fallback rules.

21.04. OPEN questions do not grant configuration authority to another
      subsystem by implication.


===============================================================================
22. LOCKED SUMMARY
===============================================================================

22.01. LOCKED:
      - configuration is authoritative state
      - configuration follows the DA-04 memory/state model
      - configuration is not a separate state architecture
      - configuration committed values use DA-05 representation semantics
        when stored as Turnix committed payload material
      - DA-06 does not redefine ValueRef, Chunk, ChunkId, decode,
        integrity, or reachability representation
      - explicit configuration scopes and ownership
      - precedence is Save-bound > Pack-global > Engine > Defaults
      - canonicalPackId for persistent config ownership is
        resolvedAuthor + "@" + packTreeId
      - canonicalPackId excludes version
      - a pack without resolvable author is invalid
      - schema governs configuration structure, constraints,
        compatibility, validation, migration, and access metadata
      - schemas are not the runtime source of defaults
      - defaults are immutable input material
      - overrides are explicit user-authored persisted deviations
      - effectiveConfig is a derived runtime-visible view, not a separate
        authoritative class
      - computed transforms do not mutate stored values
      - configuration trace obligations are configuration-domain emission
        obligations
      - DA-03 owns trace substrate, retention, pruning, loss, event
        structure, span mechanics, and storage semantics
      - configuration migration follows DA-04 migration commit rules
      - persistent-I/O authority mediates persistence
      - recovery is explicit
      - the public config API is scope-explicit and ownership-aware
      - delete() removes exactly the addressed override key
      - deleteTree() removes the addressed override node and subtree
      - read semantics use NotFoundOrPermissionDenied
      - tryGet() returns None for absent keys and does not expose
        not-found versus permission-denied programmatically
      - engine live config path is
        userdata/config/engine/<name>.config.json
      - pack-global config path is
        userdata/config/packs/<canonicalPackId>.config.json
      - SaveBundle engine config logical path is
        config/engine/<name>.config.json
      - SaveBundle pack config logical path is
        config/packs/<canonicalPackId>.config.json
      - paths.config.json is stored at
        userdata/config/engine/paths.config.json
      - global policies.config.json is stored at
        userdata/config/engine/policies.config.json
      - save-bound policies.config.json is stored inside the SaveBundle
        engine configuration scope at config/engine/policies.config.json
      - path placeholders do not define Application, ApplicationRun,
        AppPack, or SaveBundle identity
      - one clearly owned file per owner/name is the current rule
      - Turnix-written live and save-bound config files use strict JSON
      - duplicate schema, default, or configuration file is selected, not
        stacked
      - duplicate schema, default, or configuration file is shadowed, not
        merged
      - DA-06 owns policy storage location, file placement, and top-level
        persistent config structure
      - DA-17 owns decision and remembered-policy semantics
      - storing a policy record does not by itself create a valid policy
        outcome outside DA-17 semantics
      - development diagnostics are non-mutating
      - no implicit fallbacks

22.02. OPEN:
      - generalized schema-system expansion beyond configuration-first use
      - UX and tooling behavior
      - internal record JSON shape inside persisted policy sections
      - work-lifecycle policy persistence storage shape
      - concrete outer SaveBundle directory materialization paths
