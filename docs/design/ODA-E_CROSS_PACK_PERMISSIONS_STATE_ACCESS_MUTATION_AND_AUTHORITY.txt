===============================================================================
OPTIONAL DESIGN AREA ODA-E - CROSS-PACK PERMISSIONS - STATE ACCESS,
MUTATION & AUTHORITY
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines an optional cross-pack state-access and mutation-authority model for
state governed by Kernel-mediated runtime domains and Pack-owned namespaces.

This area is cross-cutting in topic, but optional in tier. It does not
override higher-authority DA documents.

Purpose:
--------
This document defines an optional ownership-and-access model for cross-pack
state access, mutation, observation, and derived-value handling.

It defines:
- state ownership domains inside this optional model
- logical scope categories for Kernel-mediated and Pack-owned state
- access-level concepts
- separation between read authority and write authority
- computed and derived-value handling
- adapter-mediated state-access constraints
- cross-pack intentional modification requirements
- trace and diagnostic expectations for state access

It does NOT define:
- filesystem access (see DA-07)
- service or capability invocation mechanics (see DA-16)
- execution adapter boundary semantics (see DA-23)
- RPC, channel, or transport semantics (see DA-21)
- lifecycle or runtime identity semantics (see DA-20)
- dependency resolution or visibility semantics
- final authoritative memory, state-layer, or journaling semantics
- final authoritative config-schema representation for access metadata
- final Workspace, Application, ApplicationRun, or SaveBundle storage layout

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines an optional cross-pack state-access and
      mutation-authority model within that shared interpretation model.

01.05. This document does not replace higher-authority state, configuration,
      persistence, permission, lifecycle, adapter, RPC, or tracing semantics.


===============================================================================
02. CORE INTENT
===============================================================================

02.01. This model exists to:
      - prevent accidental cross-pack corruption
      - preserve determinism and reproducibility where retained evidence and
        workflow semantics support them
      - make authority explicit and traceable
      - avoid pretending that hostile local behavior can be fully prevented

02.02. This model exists to:
      - prevent mistakes
      - surface intent
      - make responsibility explicit

02.03. This model does not attempt:
      - sandboxing adversarial code
      - secrecy against a local user
      - moral or trust enforcement

02.04. This document remains subordinate to higher-authority documents that
      define the final state, memory, configuration, permission, adapter, RPC,
      tracing, and lifecycle models.

02.05. Adapter mediation does not change state ownership by itself.

02.06. Pack ownership in this model is ownership of a Turnix-governed state
      namespace or authority domain.

02.07. Pack ownership does not grant raw backend authority to Pack code.


===============================================================================
03. WHAT THIS DOCUMENT GOVERNS
===============================================================================

03.01. This document governs an optional model for cross-pack access to:
      - Kernel-mediated runtime or domain state
      - Pack-global state
      - Pack-local save-bound state
      - computed or derived effective values

03.02. This document considers the following operations:
      - read
      - write or mutation
      - delete
      - observation or watching

03.03. This document applies when state access is requested by
      adapter-executed code through Turnix-mediated surfaces.

03.04. This document does not grant adapter-executed code direct state
      authority.

03.05. Scope names define logical ownership and access boundaries.

03.06. Physical or durable storage location is owned by higher-authority
      state, configuration, Workspace, persistence, and SaveBundle documents.


===============================================================================
04. STATE OWNERSHIP MODEL (LOCKED)
===============================================================================

04.01. In this model, every governed state key has one owning authority
      domain.

04.02. This optional model describes the following owning authority domains:
      - Kernel-mediated runtime or domain state
      - Pack-owned namespaces

04.03. Higher-authority documents may define additional owning domains.

04.04. This document does not replace final state, memory, configuration,
      lifecycle, persistence, or permission semantics.

04.05. Ownership is:
      - defined by domain and key path
      - not inferred dynamically
      - immutable unless changed by migration or a higher-authority
        state-transition rule

04.06. This model does not use a shared undifferentiated global key bag.

04.07. Adapter identity is not state ownership identity.

04.08. Frontend client identity is not state ownership identity.

04.09. RPC peer identity is not state ownership identity.

04.10. ApplicationRun identity is not state ownership identity.

04.11. Pack-owned state remains mediated by runtime authority, granted
       permissions, owning-domain rules, transactions, and commit boundaries.


===============================================================================
05. STATE SCOPES (LOCKED)
===============================================================================

05.01. This model recognizes the following logical scopes:
      - Kernel-mediated runtime scope
      - Pack-global scope
      - Pack-local save-bound scope
      - Computed or effective layer


05.02 KERNEL-MEDIATED RUNTIME SCOPE
----------------------------------

05.02.01. Kernel-mediated runtime scope:
        - is governed by a Kernel-controlled authority domain
        - exists independently of a particular Pack
        - exists independently of a particular SaveBundle
        - is accessed only through authorized APIs

05.02.02. Pack code accesses Kernel-mediated runtime state only through
        ModCallContext or another explicitly provided mediated surface.

05.02.03. Host, runtime, or admin tooling may use separate controlled command
        or diagnostic surfaces.

05.02.04. Controlled host, runtime, or admin surfaces do not grant Pack code
        raw Kernel authority.

05.02.05. Examples include:
        - UI language
        - global UI scale
        - developer-mode toggles


05.03 PACK-GLOBAL SCOPE
----------------------

05.03.01. Pack-global scope:
        - is owned by a specific Pack namespace
        - is shared across Applications or SaveBundle generations only where
          the owning configuration or persistence model permits that sharing
        - becomes addressable only through the relevant mediated runtime
          surfaces

05.03.02. Pack-global scope does not grant Pack visibility, import authority,
        activation authority, service access, or capability invocation rights.

05.03.03. Examples include:
        - UI theme defaults
        - code-formatting preferences
        - accessibility base parameters


05.04 PACK-LOCAL SAVE-BOUND SCOPE
--------------------------------

05.04.01. Pack-local save-bound scope:
        - is owned by a specific Pack namespace inside one save context
        - exists only through an Application and SaveBundle binding
        - is accessed through Pack-aware mediated runtime context

05.04.02. Examples include:
        - game difficulty
        - per-save gameplay modifiers
        - save-specific UI overrides

05.04.03. Save-bound state access remains constrained by Application,
        ApplicationRun, SaveBundle, and accepted Pack graph binding rules.


05.05 COMPUTED OR EFFECTIVE LAYER
--------------------------------

05.05.01. The computed or effective layer:
        - is not an ownership scope
        - is derived at read time or runtime-evaluation time
        - is not persisted directly

05.05.02. Examples include:
        - accessibility scaling applied to UI font size
        - late runtime transforms
        - temporary overrides

05.05.03. Computed or effective values do not become authoritative stored state
        merely because they are read, cached, displayed, or transported.


===============================================================================
06. ACCESS LEVELS (LOCKED)
===============================================================================

06.01. In this model, each governed state key declares an access level.

06.02. Access level is metadata that is:
      - declared in schema or another higher-authority metadata model
      - immutable unless changed through migration or another higher-authority
        schema-evolution rule
      - enforced uniformly across all APIs that honor this model

06.03. Levels in this model are:
      - PUBLIC
      - PROTECTED
      - PRIVATE
      - INTERNAL

06.04. PUBLIC means:
      - readable by any Pack that can address the scope
      - writable only by the owner unless other authority is granted

06.05. PROTECTED means:
      - readable by any Pack that can address the scope
      - writable only with explicit permission or ownership

06.06. PRIVATE means:
      - readable and writable only by the owner
      - hidden or redacted by default in user-facing surfaces and traces

06.07. INTERNAL means:
      - readable and writable only by the owner and the Kernel-mediated
        authority domain allowed by the owning model
      - not discoverable by default through enumeration
      - redacted by default in exports

06.08. These access levels are intended to prevent mistakes.

06.09. These access levels do not claim secrecy against the local user.

06.10. Adapter transport does not change access level meaning.

06.11. PUBLIC, PROTECTED, PRIVATE, and INTERNAL govern state-key read,
       write, enumeration, and redaction behavior inside this optional model.

06.12. Access levels do not grant Pack visibility, dependency satisfaction,
       import permission, activation, service access, capability invocation,
       adapter execution authorization, persistence authority, or lifecycle
       authority by themselves.


===============================================================================
07. READ AUTHORITY VS WRITE AUTHORITY (LOCKED)
===============================================================================

07.01. This model separates read authority from write or delete authority.


07.02 READING
------------

07.02.01. Reading is permissive by default in this model.

07.02.02. Restrictions exist only where needed to prevent misuse, probing, or
        violation of explicit access-level rules.

07.02.03. If access is denied for any reason:
        - the API returns NotFoundOrPermissionDenied
        - the distinction is not exposed programmatically
        - trace records the real reason where tracing policy permits it

07.02.04. No silent fallback occurs.

07.02.05. Adapter-mediated reads remain subject to the same read-authority
        rules.

07.02.06. Frontend presentation does not broaden read authority.

07.02.07. RPC transport does not broaden read authority.


07.03 WRITING AND DELETING
-------------------------

07.03.01. All mutation requires authority.

07.03.02. Delete is explicit and is treated as a write-class operation.

07.03.03. Subtree deletion may be supported.

07.03.04. Mutation authority may come from:
        - ownership
        - explicit permission
        - user-mediated decision where the governing model allows it

07.03.05. Unauthorized mutation does not occur.

07.03.06. Unauthorized mutation emits trace evidence where tracing policy
        permits it.

07.03.07. Unauthorized mutation may trigger a user decision only where a
        higher-authority decision-handling model permits that recovery path.

07.03.08. Adapter-mediated writes remain subject to the same write-authority
        rules.

07.03.09. In-process adapter calls do not bypass write authority.

07.03.10. Pack-owned state is mutated only through mediated APIs, granted
         permissions, owning-domain rules, transactions, and commit
         boundaries.


===============================================================================
08. MUTATION RULES (LOCKED)
===============================================================================

08.01. Defaults are not mutated.

08.02. Schemas are not mutated.

08.03. Only override layers or other higher-authority writable layers are
      written in this model.

08.04. All writes:
      - go through IoManager or another higher-authority persistence path
      - are atomic where the underlying authority model requires atomicity
      - emit trace evidence where tracing policy permits it
      - may produce backups
      - may trigger recovery handling when higher documents permit that

08.05. IoManager owns persistent-I/O authority.

08.06. IoManager does not replace committed-state truth.

08.07. Adapter-executed mutation does not become authoritative until it
      crosses the higher-authority orchestration, transaction, and commit
      boundaries.

08.08. Mutation triggered by observation, watching, or computed handling is
      mediated work.

08.09. Mutation triggered by observation, watching, or computed handling is
      not direct hidden mutation.


===============================================================================
09. COMPUTED AND DERIVED VALUES (LOCKED)
===============================================================================

09.01. Computed layers:
      - react to base-value changes
      - do not overwrite persisted values
      - are applied late
      - are not stored directly

09.02. Removal of a computed layer:
      - reverts behavior automatically
      - does not require migration by itself

09.03. Computed layers:
      - declare dependencies
      - remain traceable where tracing policy permits it
      - avoid cycles

09.04. Computed or effective values do not become authoritative stored state
      merely because they are transported to another runtime.

09.05. Computed-handler logic may not bypass ordinary authority,
      transaction, orchestration, permission, trace, or commit boundaries.

09.06. Any mutation triggered by computed-handler logic is mediated work.


===============================================================================
10. REACTION AND OBSERVATION (LOCKED)
===============================================================================

10.01. Packs may:
      - watch values
      - react to changes
      - recompute derived values

10.02. Packs do not:
      - intercept reads
      - replace owners
      - suppress other observers

10.03. Observation remains additive rather than exclusive.

10.04. Adapter-mediated observation does not grant write authority.

10.05. Watcher and observer logic may not bypass ordinary authority,
      transaction, orchestration, permission, trace, or commit boundaries.

10.06. Any mutation triggered by watcher or observer logic is mediated work.

10.07. Watcher and observer delivery mechanics remain OPEN.


===============================================================================
11. CROSS-PACK INTENTIONAL MODIFICATION (LOCKED)
===============================================================================

11.01. If Pack B modifies state owned by Pack A:
      - Pack B depends on Pack A where the higher design requires that
        relationship
      - the target owner domain is explicit
      - the permission model applies
      - trace records the intent and outcome where tracing policy permits it

11.02. This is explicit cooperation rather than an implicit override.

11.03. If the modifying request originates from adapter-executed code, the
      adapter remains only the execution boundary or communication
      participant.

11.04. Pack or Kernel-mediated authority remains explicit.

11.05. Cross-pack modification does not create a general right to enumerate,
      import, activate, call services, invoke capabilities, or access other
      state owned by the target Pack.


===============================================================================
12. ENUMERATION AND DISCOVERABILITY (LOCKED)
===============================================================================

12.01. Enumeration of keys is explicit rather than implicit.

12.02. INTERNAL keys do not appear by default.

12.03. PRIVATE keys appear only to the owner and to Kernel-mediated tooling
      where the higher diagnostic model permits that access.

12.04. Enumeration exists for tooling rather than for probing.

12.05. Adapter-mediated enumeration remains governed by the same authority
      and redaction rules.

12.06. Enumeration permission does not imply write permission.

12.07. Enumeration permission does not imply visibility, import, activation,
      service access, capability invocation, or persistence authority.


===============================================================================
13. USER VISIBILITY AND DEFAULT REDACTION (LOCKED)
===============================================================================

13.01. User-controlled diagnostic or admin tooling may inspect retained state
      and evidence through authorized surfaces where owning documents make
      that material available.

13.02. Normal surfaces, traces, and exports keep redaction defaults unless an
      allowed path explicitly includes the value.

13.03. PRIVATE and INTERNAL values are redacted by default in normal surfaces.

13.04. Traces redact raw values for PRIVATE or INTERNAL keys by default.

13.05. Exports redact sensitive values unless explicitly included through an
      allowed path.

13.06. This model does not claim secrecy from the user.

13.07. This model defines leak-minimizing defaults for normal surfaces.

13.08. Frontend presentation does not remove redaction requirements.

13.09. Transporting a value to a frontend or remote adapter does not make it
      public by itself.

13.10. A value that is absent, pruned, corrupt, encrypted, external,
       unmounted, or not retained is not made inspectable by this document.


===============================================================================
14. TRACE AND DIAGNOSTIC REQUIREMENTS (LOCKED)
===============================================================================

14.01. Cross-pack state access emits trace evidence including, where
      applicable and available:
      - caller identity
      - adapter identity
      - RPC message identity
      - Application identity
      - ApplicationRun identity
      - owner domain
      - key path
      - access level
      - operation
      - outcome
      - reason

14.02. Raw values are excluded or redacted according to access level and the
      governing tracing model.

14.03. Adapter, RPC, frontend, and ApplicationRun correlation evidence remains
      evidence.

14.04. Correlation evidence does not redefine state ownership, access
      authority, committed-state truth, or lifecycle authority.

14.05. Trace records evidence of access decisions and outcomes.

14.06. Trace is not enforcement authority.

14.07. Trace is not committed-state truth.

14.08. Trace is not persistence authority.


===============================================================================
15. FAILURE SEMANTICS (LOCKED)
===============================================================================

15.01. Denied access results in:
      - deterministic behavior where the governing model defines it
      - no partial mutation
      - no silent override

15.02. Errors emit or retain structured evidence where owning tracing and
      retention policies support it.

15.03. Reproducibility is claimed only where retained evidence and owning
      workflow semantics support reproduction.

15.04. Transport failure does not redefine denied-access meaning.

15.05. Adapter failure does not redefine committed-state meaning.

15.06. Access failure does not grant fallback authority.

===============================================================================
17. OPEN QUESTIONS
===============================================================================

17.01. OPEN questions include:
      - how access-level metadata is represented in the schema dialect
      - policy granularity for write permissions
      - enumeration capability shape and scope

17.02. Watchers and observers are accepted conceptually, but the concrete
      watcher model remains OPEN.

17.03. OPEN watcher and observer questions include:
      - exact public API shape
      - registration and unregistration model
      - whether watching is by exact key, subtree, scope, owner domain, or
        predicate
      - whether notification defaults to committed mutation only
      - whether staged mutation may be observed explicitly
      - how transaction boundaries affect notification visibility
      - ordering guarantees between multiple watchers
      - whether ordering is deterministic and what defines it
      - sync versus async delivery semantics
      - batching, queueing, scheduling, or inline execution behavior
      - cycle prevention, cycle classification, and cycle diagnostics
      - whether recomputation watchers differ from ordinary observers
      - failure isolation and whether one failing watcher affects others
      - trace expectations for registration, delivery, skipped delivery,
        suppression, and failure
      - visibility and permission constraints on observation
      - whether PRIVATE or INTERNAL values may be watched by non-owners
      - debugger and tooling interaction with watcher notifications
      - activation, deactivation, and reload lifecycle rules

17.04. Watcher and observer mutation cannot bypass ordinary mediated work
      boundaries.

17.05. Computed and effective behavior is accepted conceptually, but the
      concrete computed-handler model remains OPEN.

17.06. OPEN computed-handler questions include:
      - exact registration model
      - whether handlers attach by exact key, subtree, scope, owner domain,
        schema rule, or another declared dependency model
      - whether handlers execute on read, on dependency change, or both
      - caching semantics
      - invalidation semantics
      - ordering when multiple transforms or derivations exist
      - cycle handling and cycle diagnostics
      - whether handlers may expose derived values under the same key or
        only through explicit effective-layer resolution
      - permission and visibility rules for computed inputs and outputs
      - trace shape for computation, cache hit, invalidation, skipped
        computation, and failure
      - failure behavior when a handler errors
      - whether computed handlers may perform cross-pack reads freely or
        only within declared dependencies
      - interaction with staged versus committed mutation
      - debugger and tooling interaction with computed values

17.07. Computed-handler mutation cannot bypass ordinary mediated work
      boundaries.

17.08. Transform ordering remains OPEN.

17.09. OPEN transform-ordering questions include:
      - whether ordering is declaration-based, priority-based, dependency-
        based, or another deterministic model
      - whether equal-priority transforms are allowed
      - tie-break behavior
      - whether transform ordering is global, per scope, per owner, or per
        key lineage
      - whether ordering is static after registration or may change during
        runtime
      - trace expectations for chosen transform order

17.10. Restriction metadata beyond configuration keys remains OPEN.

17.11. OPEN restriction-metadata questions include:
       - whether future non-config memory or state domains use schema-
         declared access metadata
       - whether a separate metadata model is required for non-config state
       - how such metadata would attach to non-config keys, values, or
         records
       - whether the same PUBLIC, PROTECTED, PRIVATE, and INTERNAL model
         applies unchanged outside configuration
       - migration and compatibility handling for such metadata

17.12. Cross-runtime transport details for these rules remain OPEN.

17.13. OPEN cross-runtime transport questions include:
       - how read, write, delete, watch, and computed-state operations are
         represented across runtime boundaries
       - how authority, owner domain, and access-level metadata are carried
         in transport envelopes where needed
       - how staged versus committed state distinctions are surfaced across
         runtimes
       - how denied access, missing state, and trace correlation are carried
         across runtime boundaries
       - how watcher delivery, backpressure, cancellation, and ordering are
         preserved when transport is involved
       - how effective or computed values are represented without implying
         authoritative stored state
       - which details belong in implementation specifications versus higher
         semantic documents

17.14. This document does not claim that no other design questions exist
       globally.

17.15. This document states only that these are the major open questions
       inside this optional model.


===============================================================================
18. LOCKED SUMMARY
===============================================================================

18.01. LOCKED:
      - explicit ownership domains
      - a scoped state-access model
      - schema-declared or metadata-declared access levels
      - permissive reads and guarded writes
      - non-persistent computed layers
      - IoManager-mediated or equivalent authoritative persistence path
      - adapter-mediated state access does not grant adapter state authority
      - in-process adapter calls do not bypass write authority
      - transported computed values do not become authoritative stored state
      - trace-emitting enforcement through owning authority paths
      - leak-minimizing diagnostics
      - watcher, observer, and computed-handler mutation remains mediated work

18.02. OPEN:
      - exact schema representation details
      - permission-granularity details
      - enumeration-shape details
      - watcher and observer mechanics
      - computed-handler mechanics
      - transform ordering
      - restriction metadata beyond configuration keys
      - cross-runtime transport details for these rules
