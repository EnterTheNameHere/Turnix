===============================================================================
DESIGN AREA DA-18 - DEBUGGING, INSPECTION & BREAKPOINTS
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines how Turnix can be inspected while running, where execution may be
paused, and how state can be safely observed and modified without breaking
runtime authority, determinism, or traceability.

This area is developer-facing.

Purpose:
--------
This document defines the Turnix debugging model for semantic inspection,
scoped pausing, semantic breakpoints, controlled debugger mutation,
debugger-originated work-control requests, and debugger-domain trace
obligations.

It defines:
- semantic breakpoint types and their trigger semantics
- pause behavior and safe mutation constraints
- inspection surfaces and debugger action boundaries
- manual pause and apply-at-safe-point semantics
- debugger safe points as execution and mutation safety boundaries
- Job-aware breakpoint and pause behavior when Jobs exist
- debugger-originated Job lifecycle-control request boundaries
- undo and redo semantics for debugger tooling
- debugger-domain trace reason identifiers
- trace emission obligations for debugger actions and breakpoint events
- debugger UI authority boundaries
- debugger disconnect failure handling

It does NOT define:
- the tracing substrate, trace event schema, trace DAG mechanics, span
  mechanics, trace storage, trace retention, or trace loss rules (see DA-03)
- authoritative committed state or transaction semantics (see DA-04)
- payload identity, ValueRef, Chunk, ChunkId, decode, or integrity semantics
  for committed value representation (see DA-05)
- configuration semantics or configuration materialization (see DA-06)
- persistent-I/O authority, storage target handling, or persistence-provider
  semantics (see DA-07)
- Window, SafePointWindow, ActiveWindow, AbortedWindow, or Window
  finalization semantics (see DA-08)
- activation semantics beyond debugger pause boundaries (see DA-14)
- decision and policy handling semantics (see DA-17)
- Job lifecycle states, terminal outcomes, or Job result semantics
  (see DA-19)
- Application or ApplicationRun lifecycle and identity semantics (see DA-20)
- RPC, channel, transport, or message-flow semantics (see DA-21)
- concrete user-interface layout for debugger tooling (see DA-22)
- execution adapter boundary semantics (see DA-23)
- OrchestrationUnit lifecycle or mutation-authority semantics (see DA-24)
- Window artifact, export, bundle, or artifact-authority semantics
  (see DA-25)
- formal Replay, Resume, Retry, comparison, or offline workflow semantics
  (see DA-26)
- adapter lifecycle, trust, isolation, or disconnect semantics (see DA-27)
- RuntimeHost command-surface, workspace, or lifecycle semantics (see DA-28)
- ModCallContext invocation gateway semantics (see DA-30)
- concrete breakpoint-condition language
- concrete pause protocol or overlay implementation
- concrete language-runtime debugger internals

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines debugging, inspection, breakpoint, pause,
      safe-point, controlled mutation, and debugger-domain trace behavior
      within that shared interpretation model.


===============================================================================
02. CORE INTENT
===============================================================================

02.01. Debugging in Turnix is not:
      - print-statement debugging
      - ad-hoc logging
      - attaching debuggers to arbitrary threads as the primary model
      - raw language-runtime control as an authority bypass

02.02. Debugging in Turnix is:
      - intentional
      - observable
      - reversible where the surrounding state model allows reversal
      - scoped
      - mediated through Turnix-controlled surfaces
      - aligned with committed-state and transaction authority

02.03. Turnix debugging operates on Turnix concepts rather than on language
      internals as the primary debugging surface.

02.04. Primary debugging targets include:
      - packs
      - activation participation
      - ProcessingPipelines and ProcessingRuns
      - ProcessingPipeline stages
      - memory layers and transactional overlays
      - capabilities
      - OrchestrationUnits
      - Jobs when Jobs exist
      - ApplicationRuns
      - debugger-exposed diagnostic metadata

02.05. Python frames or JavaScript call stacks may appear as contextual
      information, but they are not the primary debugging model.

02.06. Debugger pause and debugger resume or continue wording means
      continuation from a debugger pause.

02.07. Debugger pause and debugger resume or continue wording does not imply
      DA-26 Resume workflow semantics.

02.08. Debugger snapshot or restore behavior, if later defined, does not
      bypass committed-state authority, payload representation, persistent-I/O
      authority, Window semantics, artifact/export boundaries, or DA-26
      workflow semantics.

02.09. Trace-based causal-history inspection is not DA-26 Replay unless it is
      explicitly routed through DA-26 Replay semantics.

02.10. Trace evidence by itself is not committed-state truth.

02.11. Trace evidence by itself does not restore committed state.


===============================================================================
03. BREAKPOINT TYPES
===============================================================================

03.01 General breakpoint model
------------------------------

03.01.01. Turnix supports semantic breakpoints rather than code-line
        breakpoints.

03.01.02. Supported semantic breakpoint classes include:
        - ProcessingPipeline / ProcessingRun stage breakpoints
        - memory breakpoints
        - capability breakpoints
        - Job-scoped breakpoints when Jobs exist

03.02 ProcessingPipeline / ProcessingRun stage breakpoints
----------------------------------------------------------

03.02.01. A ProcessingPipeline / ProcessingRun stage breakpoint pauses
        execution when a ProcessingRun reaches a specific stage.

03.02.02. Use cases include:
        - inspecting a prompt before sending it to an LLM
        - verifying memory composition
        - observing transformations
        - inspecting stage inputs and outputs

03.02.03. Stage breakpoint triggers may include:
        - processingPipelineId
        - processingRunId
        - stageId
        - optional condition

03.02.04. A stage breakpoint does not redefine ProcessingPipeline or
        ProcessingRun semantics.

03.02.05. ProcessingPipeline and ProcessingRun semantics remain owned by their
        owning processing documents.

03.03 Memory breakpoints
------------------------

03.03.01. A memory breakpoint pauses execution when memory changes according
        to the configured trigger.

03.03.02. Memory-breakpoint triggers may include:
        - memory key
        - memory layer
        - change type such as set, delete, or overwrite
        - optional value predicate

03.03.03. Memory breakpoints observe state transitions rather than storage
        mechanics.

03.03.04. Definitions:
        - a staged mutation is a write into a transactional layer
        - a committed mutation is a write that becomes visible in a
          committed authoritative memory layer after successful commit
        - an aborted mutation is a staged mutation discarded during abort

03.03.05. By default, memory breakpoints trigger on committed mutations only.

03.03.06. Writing into a transactional layer does not trigger a memory
        breakpoint by default.

03.03.07. Aborting a transaction does not trigger a memory breakpoint by
        default.

03.03.08. Only the moment a value becomes authoritative is breakpoint-visible
        by default.

03.03.09. Memory breakpoints may be configured to observe staged mutations
        explicitly.

03.03.10. If staged observation is enabled, a breakpoint may specify:
         - observeStaged = true
         - observeCommitted = true or false

03.03.11. When observeStaged is enabled, the breakpoint may trigger when a
         staged value is written.

03.03.12. Staged-mutation breakpoint context includes:
         - transactionId
         - staging-layer identity
         - parent-layer identity
         - commit-eligibility status

03.03.13. Every memory-breakpoint hit is classified as exactly one of:
         - StagedMutation
         - CommittedMutation

03.03.14. Breakpoints do not fire twice for the same mutation phase.

03.03.15. If a breakpoint observes both staged and committed mutation phases,
         the staged hit and committed hit are distinct events.

03.03.16. Those distinct events are trace-linked to the same mutation lineage.

03.03.17. Nested transactions inherit breakpoint semantics unless explicitly
         scoped otherwise.

03.03.18. A child transaction commit into a parent transaction is not treated
         as a committed mutation.

03.03.19. Only the outermost transaction commit produces authoritative
         committed-mutation events.

03.03.20. This model preserves determinism, prevents breakpoint storms during
         speculative execution, and aligns debugging semantics with the
         transactional authority model in DA-04.

03.04 Capability breakpoints
----------------------------

03.04.01. A capability breakpoint pauses execution before or after a
        capability call according to the configured trigger.

03.04.02. Capability-breakpoint triggers may include:
        - capability identifier
        - caller pack
        - permission decision point
        - capability result class

03.04.03. Capability breakpoints may observe capability invocations that later
        create or attach to Jobs.

03.04.04. If a capability invocation creates or attaches to a Job, the Job
        lifecycle remains owned by DA-19 rather than by the capability
        breakpoint.

03.04.05. A capability breakpoint does not grant capability permission.

03.04.06. A capability breakpoint does not convert service object access into
        Pack-facing capability access.

03.05 Job-scoped breakpoints
----------------------------

03.05.01. A Job-scoped breakpoint applies only when the selected Job or work
        region reaches the configured semantic condition.

03.05.02. A Job-scoped breakpoint does not create a Job.

03.05.03. A Job-scoped breakpoint does not redefine Job lifecycle states.

03.05.04. Job lifecycle semantics remain owned by DA-19.


===============================================================================
04. BREAKPOINT BEHAVIOR
===============================================================================

04.01. When a breakpoint triggers:
      - execution of the triggering unit pauses
      - mutation-capable execution for the owning ApplicationRun pauses
      - other ApplicationRuns may continue if the runtime supports that
      - non-mutating Kernel activity may continue unless configured otherwise
      - debugger tooling is notified
      - relevant state becomes inspectable

04.02. Breakpoints do not:
      - auto-resume silently
      - alter execution order
      - mutate state by default
      - silently cancel Jobs
      - silently supersede Jobs
      - create Window finalization by default
      - create SafePointWindows by default

04.03. A breakpoint pause is a debugger pause scope.

04.04. A debugger pause scope is not a Job terminal outcome.

04.05. A debugger pause scope is not a Window finalization outcome.

04.06. A debugger pause scope does not change ApplicationRun lifecycle outcome
      by itself.


===============================================================================
05. LIVE DEBUGGING WITHOUT PAUSE
===============================================================================

05.01. The debugger may be used while Turnix is running normally.

05.02. Debugger inspection does not require a breakpoint hit.

05.03. Debugger inspection does not require Turnix to be paused.

05.04. A user may open inspectors, browse state, and request read-only views
      at any time where debugger access is enabled.

05.05. Such inspection is traceable and marked as debugger or tooling
      activity.

05.06. Live inspection does not acquire mutation authority merely because the
      inspected runtime is active.

05.07. Live inspection does not turn runtime residency into committed-state
      authority.


===============================================================================
06. DEBUGGER ACTIONS VS ORCHESTRATION
===============================================================================

06.01. Debugger actions execute through Turnix-controlled remote procedure
      calls, capabilities, or equivalent Turnix-mediated interfaces.

06.02. Debugger tooling does not bypass Turnix orchestration.

06.03. Debugger tooling does not bypass OrchestrationUnit mutation-authority
      boundaries.

06.04. Debugger tooling does not access raw filesystem input or output
      directly as a bypass path.

06.05. Any persistence-affecting debugger action executes through DA-07
      persistent-I/O authority and the same mediated persistence paths as
      normal runtime actions.

06.06. Debugger tooling does not become persistent-I/O authority.

06.07. Debugger-originated Job control actions execute through Turnix
      lifecycle and policy surfaces.

06.08. Debugger tooling does not mutate Job terminal state directly.

06.09. Debugger tooling does not become Kernel authority, RuntimeHost
      authority, adapter authority, capability authority, or committed-state
      authority.


===============================================================================
07. INSPECTION SURFACES
===============================================================================

07.01. Inspectable objects include:
      - Pack descriptors
      - activation state
      - memory layers
      - ProcessingPipeline and ProcessingRun objects
      - capability registry metadata
      - service registry metadata where permitted
      - OrchestrationUnit metadata where permitted
      - Jobs when Jobs exist
      - ApplicationRun-scoped debugger state

07.02. Inspection is read-only by default.

07.03. Debugger inspection may enumerate memory layers and their composition.

07.04. Debugger inspection may inspect values together with semantic context
      such as:
      - origin layer
      - revision identifiers
      - transactional visibility
      - ValueRef or Chunk metadata when such metadata is exposed

07.05. Debugger inspection may view active transactional stacks when doing so
      is safe and meaningful in the current execution context.

07.06. Debugger inspection may distinguish between:
      - committed values currently authoritative
      - staged values present only in transactional layers
      - unresolved or unavailable state when the requested surface cannot be
        read safely or meaningfully in the current execution context

07.07. Inspection surfaces do not silently collapse committed and staged state
      into one undifferentiated view.

07.08. If a debugger surface presents both committed and staged state, the
      distinction remains explicit.

07.09. Inspection surfaces may show revision identifiers, origin-layer
      identity, payload metadata, and transactional visibility as surfaced
      inspection metadata.

07.10. Inspecting transactional state does not turn staged values into
       authoritative state.

07.11. Inspecting committed-state history does not bypass the committed-state
       authority model defined elsewhere.

07.12. Inspecting ValueRefs, Chunks, ChunkIds, decode status, or integrity
       status does not redefine DA-05 payload representation semantics.

07.13. Debugger inspection may inspect configuration values where permitted.

07.14. Debugger inspection of configuration does not redefine DA-06
       configuration semantics.

07.15. Debugger inspection may inspect Job lifecycle state, owner, progress,
       terminal outcome, and causal trace links when Jobs exist.

07.16. Inspecting a Job does not grant direct access to the underlying
       execution mechanism.

07.17. Service registry inspection is diagnostic metadata inspection.

07.18. Service registry inspection does not grant direct Service authority.

07.19. Pack-facing operation access remains mediated through capabilities,
       ModCallContext-exposed surfaces, or other explicitly defined mediated
       paths.

07.20. Debugger inspection of ModCallContext-related information does not
       expose a retained live ModCallContext after callback completion.

07.21. ModCallContext invocation gateway semantics remain owned by DA-30.


===============================================================================
08. CONTROLLED MUTATION
===============================================================================

08.01. Explicit mutation is allowed only through:
      - debugger actions
      - explicit user confirmation where required
      - trace-visible mutation handling
      - the same authority paths used by normal runtime mutation

08.02. Examples include:
      - editing a memory value
      - editing permitted configuration values
      - disabling or modifying a breakpoint
      - forcing debugger resume or abort of a debugger pause scope

08.03. Every debugger-initiated mutation emits trace evidence.

08.04. Debugger tooling may create its own temporary transactional overlay for
      controlled staged edits.

08.05. A debugger-created temporary transactional overlay remains subject to
      the same authority, scope, ownership, and trace rules that govern other
      transactional mutation.

08.06. A debugger-created temporary transactional overlay does not become
      authoritative merely because the debugger created it.

08.07. If debugger tooling uses such an overlay, the overlay remains distinct
      from committed state until normal commit rules make the mutation
      authoritative.

08.08. Job lifecycle control is not controlled mutation of committed state.

08.09. Job lifecycle control remains constrained by DA-19 and by policy
      handling when policy participates.

08.10. Debugger mutation of configuration remains constrained by DA-06 and by
       the transaction and commit rules that apply to authoritative state.

08.11. Debugger mutation of persisted material remains constrained by DA-07
       mediated persistence paths.

08.12. Debugger mutation does not alter Application, ApplicationRun, Window,
       Job, OrchestrationUnit, adapter, RuntimeHost, or DA-26 workflow
       outcomes except through their owning authority paths.


===============================================================================
09. MUTATION WHILE RUNNING
===============================================================================

09.01. Controlled mutation may be performed while Turnix is active and not
      paused.

09.02. Rules:
      - mutation is explicit user action in debugger tooling
      - mutation is traceable and labeled as debugger-initiated
      - mutation obeys the same permission, ownership, and scope rules as
        normal runtime actions

09.03. If a mutation affects data that active execution units may read
      concurrently, the debugger either:
      - requires a manual pause
      - enforces deterministic apply-at-safe-point semantics

09.04. Mutation while running does not authorize nondeterministic visibility.

09.05. Mutation while running does not authorize partial application.

09.06. Mutation while running does not bypass transaction conflict handling.


===============================================================================
10. MANUAL PAUSE
===============================================================================

10.01. Turnix may support manual pausing even when no breakpoint is hit.

10.02. Manual pause exists to:
      - allow deterministic inspection and mutation
      - prevent important work from being voided by cancellation
      - reach a controlled debugger safe point

10.03. Manual pause is deterministic.

10.04. Manual pause does not silently cancel in-flight work.

10.05. Manual pause does not silently supersede in-flight work.

10.06. If pausing cannot be achieved safely, Turnix refuses the pause request
      with an explicit, traceable reason.

10.07. Manual pause may operate by enforcing quiescence at defined debugger
      safe points such as:
      - between ProcessingPipeline stages
      - between capability calls
      - before commit points for persistence-affecting work
      - before selected OrchestrationUnit mutation-authority boundaries

10.08. Manual pause of a Job remains non-terminal unless a later explicit
      lifecycle or policy outcome changes the Job state under DA-19.

10.09. Manual pause of an ApplicationRun does not define ApplicationRun
      lifecycle outcome.

10.10. ApplicationRun lifecycle and identity semantics remain owned by DA-20.


===============================================================================
11. APPLY-AT-SAFE-POINT
===============================================================================

11.01. When Turnix is not paused, debugger-initiated mutations may be staged
      and applied only at a deterministic debugger safe point.

11.02. Rules:
      - staging is traceable
      - the exact safe point where the mutation becomes visible is traceable
      - staged mutations do not partially apply
      - if the safe point is never reached, the staged mutation is discarded
        deterministically and traced

11.03. Debugger tooling may use a temporary transactional overlay as the
      staging vehicle for apply-at-safe-point mutation.

11.04. If such an overlay is used, the overlay remains debugger-owned staging
      state until the mutation is applied or discarded according to the
      normal rules of this document and DA-04.

11.05. Discard of a debugger-staged overlay is explicit and trace-visible.

11.06. Application of a debugger-staged overlay does not bypass normal
      transaction, ownership, scope, or authority rules.

11.07. Apply-at-safe-point does not by itself create a SafePointWindow.

11.08. Apply-at-safe-point does not by itself finalize a Window.

11.09. If debugger safe-point behavior participates in Window finalization,
      Window finalization remains governed by DA-08.


===============================================================================
12. DEBUGGER SAFE POINTS AND SAFEPOINTWINDOWS
===============================================================================

12.01. A debugger safe point is an execution or mutation safety boundary used
      for debugger pause or apply-at-safe-point mutation.

12.02. A SafePointWindow is a finalized committed Window boundary owned by
      DA-08.

12.03. A debugger safe point is not a SafePointWindow by default.

12.04. Debugger pause-at-safe-point does not automatically create Window
      finalization.

12.05. SafePointWindow creation at quiescence does not automatically imply a
      debugger pause.

12.06. Job pause-at-safe-point remains non-terminal.

12.07. If debugger safe-point behavior affects Window creation, DA-08 governs
      Window finalization and SafePointWindow creation semantics.

12.08. If debugger safe-point behavior affects exported artifacts, DA-25
      governs artifact and export semantics.

12.09. If debugger safe-point behavior affects Replay, Resume, Retry,
      comparison, or offline workflows, DA-26 governs those workflow
      semantics.


===============================================================================
13. UNDO AND REDO SEMANTICS
===============================================================================

13.01. Debugger tooling may support undo of debugger-initiated changes within
      the boundaries defined by the Turnix state model.

13.02. Undo that affects authoritative state operates on committed revisions.

13.03. Undo that affects authoritative state is performed as a new explicit
      debugger-initiated mutation.

13.04. Undo that affects authoritative state is trace-visible.

13.05. Undo does not bypass transaction, permission, ownership, scope, or
      safe-point rules defined elsewhere in this document and in DA-04.

13.06. Undo is not rollback magic.

13.07. Redo history is debugger-local, ephemeral, and non-authoritative.

13.08. Redo history does not become committed state merely because debugger
      tooling remembers it.

13.09. Redo history is discarded deterministically when a new committed
      revision makes the stored redo path no longer valid.

13.10. Debugger tooling does not present ephemeral redo state as if it were
       authoritative system history.


===============================================================================
14. TRACE RETENTION AND DEBUGGER ACTIONS
===============================================================================

14.01. Debugger tooling does not create untraced gaps for debugger actions
      that inspect, pause, resume, abort, stage, apply, discard, or mutate
      Turnix-managed state.

14.02. Debugger actions that affect trace evidence, including export, prune,
      clear, or retention-policy changes, remain trace-visible.

14.03. Debugger-originated trace-affecting actions are marked as
      debugger-initiated through trace attributes.

14.04. Trace retention and loss-evidence rules apply equally to debugger-
      initiated trace-affecting actions.

14.05. DA-03 defines the tracing substrate used to represent debugger trace
      evidence.

14.06. DA-03 defines trace event structure, trace DAG semantics, span
      mechanics, trace storage, trace retention, and trace loss semantics.

14.07. This document defines debugger-specific trace emission obligations.

14.08. This document defines debugger-domain trace reason identifiers.

14.09. Debugger-domain trace reasons describe debugger-domain behavior only.

14.10. Debugger-domain trace reasons do not define:
       - committed-state mutation outcome
       - Job terminal outcome
       - OrchestrationUnit terminal outcome
       - ApplicationRun lifecycle outcome
       - adapter lifecycle outcome
       - RuntimeHost lifecycle outcome
       - Window finalization
       - artifact or export outcome
       - comparison outcome
       - Replay outcome
       - Resume outcome
       - Retry outcome
       - offline workflow outcome

14.11. Trace evidence remains evidence.

14.12. Trace evidence is not committed state.


===============================================================================
15. DEBUGGER USER-INTERFACE INTEGRATION
===============================================================================

15.01. Debugger user interfaces may:
      - subscribe via RPC
      - receive breakpoint-hit events
      - show causal context
      - request debugger resume or continue from a debugger pause
      - request step or abort of a debugger pause scope
      - request undo or redo where supported
      - request Job pause-at-safe-point where supported
      - request Job cancellation where supported
      - request Job supersession where supported

15.02. Debugger user interfaces are optional but supported.

15.03. Debugger user interfaces do not own debugger semantics.

15.04. Debugger UI as a frontend surface remains owned by DA-22.

15.05. RPC, channel, transport, and message-flow semantics remain owned by
      DA-21.

15.06. Debugger user interfaces do not present Superseded Job outcomes as
      failures.

15.07. Debugger user interfaces do not present paused-at-safe-point Jobs as
      terminal.

15.08. Debugger user interfaces do not become Kernel authority, RuntimeHost
      authority, Job authority, persistent-I/O authority, or committed-state
      authority.


===============================================================================
16. STEP MODES
===============================================================================

16.01. Supported step modes include:
      - debugger resume or continue from debugger pause
      - step over, meaning the next semantic stage or memory change
      - abort, meaning fail the current debugger-controlled execution scope

16.02. Unsupported step modes include:
      - instruction-level stepping
      - time travel as a runtime debugger mode in this document

16.03. Step modes do not redefine Job lifecycle states.

16.04. If step or abort actions affect a Job, the resulting Job lifecycle
      outcome remains governed by DA-19.

16.05. If step or abort actions affect an OrchestrationUnit, the resulting
      OrchestrationUnit lifecycle and mutation-authority behavior remains
      governed by DA-24.

16.06. If step or abort actions affect adapter execution, adapter lifecycle
      behavior remains governed by DA-27.


===============================================================================
17. JOBS, LONG-RUNNING WORK, AND BREAKPOINTING
===============================================================================

17.01. Turnix may represent long-running work as explicit Jobs.

17.02. If Jobs exist:
      - Jobs are observable through status, owner, progress, terminal
        outcome, and causal trace links
      - Jobs are controlled only through Turnix lifecycle, orchestration, or
        policy surfaces
      - Job lifecycle semantics remain owned by DA-19

17.03. Debugger interaction with Jobs may include requests for:
      - pause-at-safe-point for a Job
      - breakpoint-at-safe-point for a Job
      - debugger resume or continue of a paused Job
      - cancellation request for a Job
      - supersession request for a Job where supported

17.04. Manual pause does not implicitly cancel Jobs.

17.05. Manual pause does not implicitly supersede Jobs.

17.06. Safe-point pausing or breakpointing of Jobs occurs at boundaries such
      as:
      - between ProcessingPipeline stages
      - before or after capability boundaries
      - before commit points for persistence-affecting work
      - before selected OrchestrationUnit mutation-authority boundaries

17.07. If a Job cannot reach a safe point:
      - that fact is surfaced explicitly
      - no silent cancellation is permitted
      - no silent supersession is permitted

17.08. A paused-at-safe-point Job remains non-terminal.

17.09. Debugger-originated cancellation, supersession, continuation, or hold
      behavior may require work-lifecycle policy handling under DA-17.

17.10. The debugger does not directly write a Job terminal state.

17.11. Job terminal outcomes caused or requested through debugger action are
       recorded through Job lifecycle evidence owned by DA-19.

17.12. Debugger pause-at-safe-point does not imply DA-26 Resume.

17.13. Debugger continuation of a paused Job is debugger-domain continuation
       from a debugger pause.


===============================================================================
18. SCOPING RULES
===============================================================================

18.01. Breakpoints may be scoped to:
      - global debugger scope where explicitly enabled
      - Application
      - ApplicationRun
      - View
      - pack
      - ProcessingPipeline
      - ProcessingRun
      - OrchestrationUnit
      - Job when Jobs exist

18.02. Unscoped breakpoints are discouraged.

18.03. A Job-scoped breakpoint does not create a Job.

18.04. A Job-scoped breakpoint applies only to the Job lifecycle or work
      region selected by the debugger configuration.

18.05. An ApplicationRun-scoped breakpoint applies only to the selected live
      runtime incarnation.

18.06. An Application-scoped breakpoint applies to the selected durable
      application identity according to debugger configuration.

18.07. View scoping does not make a View authoritative over debugger
      semantics.

18.08. RuntimeHost command surfaces may request debugger actions only through
      mediated paths.

18.09. RuntimeHost command surfaces do not become debugger authority merely
      because they expose debugger commands.


===============================================================================
19. DEVELOPMENT VS PRODUCTION
===============================================================================

19.01. In production:
      - breakpoints are disabled by default
      - inspection is limited
      - mutation is disallowed unless explicitly enabled

19.02. In development:
      - debugging features in this document are available when enabled by
        configuration and policy

19.03. Development availability does not allow debugger tooling to bypass Job
      lifecycle, policy, transaction, capability, OrchestrationUnit,
      persistent-I/O, adapter, RPC, RuntimeHost, or ApplicationRun authority
      boundaries.

19.04. Production limits do not change the semantics of enabled debugger
      actions.


===============================================================================
20. FAILURE MODES
===============================================================================

20.01. If the debugger disconnects:
      - execution resumes, cancels, supersedes, aborts the affected
        debugger-controlled scope, or refuses to hold according to policy
      - the chosen outcome is trace-visible
      - deadlock is not allowed

20.02. Debugger disconnect outcome trace evidence distinguishes:
      - execution continued after debugger disconnect by policy
      - active work cancelled, superseded, or aborted after debugger
        disconnect by policy
      - hold refused because holding is unsupported, unsafe, or impossible

20.03. Debugger disconnect outcome trace evidence records enough context to
      explain:
      - debugger client identity
      - policy identity
      - disconnect kind
      - affected target when work is cancelled, superseded, or aborted
      - refusal reason category when hold is refused

20.04. If breakpoint logic errors:
      - the breakpoint is disabled
      - the error is trace-visible

20.05. If debugger disconnect policy affects a Job, the Job lifecycle outcome
      remains governed by DA-19.

20.06. If debugger disconnect policy is a work-lifecycle policy decision, the
      policy handling remains governed by DA-17.

20.07. If debugger disconnect policy affects adapter execution, adapter
      lifecycle behavior remains governed by DA-27.

20.08. If debugger disconnect policy affects an ApplicationRun, ApplicationRun
      lifecycle behavior remains governed by DA-20.

20.09. If debugger disconnect policy affects RuntimeHost command handling,
      RuntimeHost behavior remains governed by DA-28.


===============================================================================
21. RELATION TO TRACING
===============================================================================

21.01. Debugger connection lifecycle trace evidence distinguishes:
      - debugger connected
      - debugger disconnected

21.02. Debugger connection trace evidence records enough context to explain:
      - debugger client identity
      - connectionKind when a debugger connects
      - disconnect kind when a debugger disconnects

21.03. Every breakpoint hit emits trace evidence.

21.04. Breakpoint-hit trace evidence links to the causal chain.

21.05. Breakpoint-hit trace evidence records inspection and mutation actions
      when applicable.

21.06. Breakpoint-hit trace evidence distinguishes breakpoint type.

21.07. Breakpoint-hit trace evidence includes:
      - breakpointId
      - breakpoint type
      - breakpoint scope
      - applicationId when durable application identity applies
      - applicationRunId when live runtime identity applies

21.08. ProcessingPipeline / ProcessingRun stage breakpoint-hit trace evidence
      additionally includes:
      - processingPipelineId when applicable
      - processingRunId when applicable
      - stageId

21.09. Memory breakpoint-hit trace evidence additionally includes:
      - memoryLayerId
      - memory-key identity
      - mutation phase
      - mutationKind
      - transactionId when applicable

21.10. Capability breakpoint-hit trace evidence additionally includes:
       - capability identifier
       - caller-pack identity
       - decisionPoint when applicable

21.11. Job-scoped breakpoint-hit trace evidence additionally includes:
       - jobId
       - Job state when available
       - Job terminal outcome when available

21.12. Breakpoint-hit trace evidence includes orchestrationUnitId or Job
       identity when applicable.

21.13. Manual pause trace evidence distinguishes:
       - pause requested
       - pause granted
       - pause refused
       - pause-at-safe-point requested
       - pause-at-safe-point applied

21.14. Manual pause trace evidence records enough context to explain:
       - request identity
       - pause scope
       - target identity
       - whether a debugger safe point was reached
       - debugger safe-point descriptor when applicable
       - refusal reason category when pause is refused
       - jobId when the target is a Job

21.15. Debugger inspection trace evidence records:
       - inspection kind
       - target kind
       - target identity when applicable

21.16. Debugger mutation trace evidence distinguishes:
       - mutation requested
       - mutation staged
       - mutation applied
       - mutation discarded

21.17. Debugger mutation trace evidence records enough context to explain:
       - mutation request identity
       - mutation lineage identity
       - target kind
       - target identity
       - mutation kind
       - intended debugger safe point when staged
       - applied debugger safe point when applied
       - discard reason category when discarded

21.18. Debugger-originated Job control is trace-visible and remains linked to
       Job lifecycle evidence when it affects a Job.

21.19. Debugger-originated Job control trace evidence records policy source
       when policy participates.

21.20. Debugger actions that stage and apply mutations at debugger safe points
       are traced as distinct events that share a stable mutation-lineage
       identifier.

21.21. DA-18 owns the debugger-domain trace reason identifiers used for
       debugger inspection, breakpoints, manual pause, safe-point pause,
       debugger disconnect outcomes, and debugger-initiated mutation.

21.22. The following debugger-domain trace reasons are defined:

       - DebuggerConnected
       - DebuggerDisconnected
       - DebuggerDisconnectedResume
       - DebuggerDisconnectedAbort
       - DebuggerDisconnectedHoldRefused
       - BreakpointHit
       - BreakpointResumed
       - ManualPauseRequested
       - ManualPauseGranted
       - ManualPauseRefused
       - PauseAtSafePointRequested
       - PauseAtSafePointApplied
       - DebuggerInspection
       - DebuggerMutationRequested
       - DebuggerMutationStaged
       - DebuggerMutationApplied
       - DebuggerMutationDiscarded

21.23. BreakpointResumed and DebuggerDisconnectedResume are debugger-domain
       trace reasons for continuation from debugger pause.

21.24. BreakpointResumed and DebuggerDisconnectedResume do not imply DA-26
       Resume semantics.

21.25. Tracing and debugging are complementary.

21.26. DA-03 defines trace event structure, trace DAG semantics, span
       mechanics, and trace retention semantics.

21.27. DA-17 defines work-lifecycle policy trace obligations when policy
       participates in debugger-originated Job control.

21.28. DA-19 defines Job lifecycle trace obligations when debugger-originated
       control affects a Job.

21.29. DA-24 defines OrchestrationUnit trace obligations when debugger action
       affects OrchestrationUnit lifecycle or mutation authority.

21.30. DA-27 defines adapter lifecycle trace obligations when debugger action
       affects adapter execution.

21.31. DA-28 defines RuntimeHost trace obligations when debugger action
       affects RuntimeHost command-surface behavior.

21.32. This document defines debugger-specific trace obligations.


===============================================================================
22. TRACE-BASED CAUSAL-HISTORY INSPECTION
===============================================================================

22.01. Debugger tooling may inspect retained trace evidence where permitted.

22.02. Trace-based causal-history inspection reads retained evidence.

22.03. Trace-based causal-history inspection does not mutate committed state.

22.04. Trace-based causal-history inspection does not restore committed state.

22.05. Trace-based causal-history inspection is not DA-26 Replay unless it is
      explicitly routed through DA-26 Replay semantics.

22.06. Trace evidence by itself does not prove replayability, resumability, or
      evidence completeness.

22.07. Deterministic restoration requires committed material and the owning
      committed-state, Window, artifact, and workflow rules.

22.08. DA-04 owns committed-state restoration boundaries.

22.09. DA-08 owns Window boundaries used by retained runtime history.

22.10. DA-25 owns Window artifact and export representation.

22.11. DA-26 owns Replay, Resume, Retry, comparison, and offline
       workflow semantics.


===============================================================================
23. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

23.01. The following are not supported:
      - arbitrary Python debugger injection
      - JavaScript eval debugging
      - modifying pack code at runtime
      - hot-patching logic without reload
      - directly writing Job terminal state from debugger tooling
      - silently cancelling or superseding Jobs from debugger tooling
      - treating debugger safe points as SafePointWindows by default
      - treating trace evidence alone as committed-state restoration material
      - treating debugger resume or continue as DA-26 Resume
      - treating trace-based causal-history inspection as DA-26 Replay by
        default
      - treating debugger UI affordances as debugger authority
      - treating debugger tooling as Kernel authority
      - treating debugger tooling as persistent-I/O authority
      - treating debugger tooling as committed-state authority


===============================================================================
24. EXPLICITLY OPEN QUESTIONS
===============================================================================

24.01. OPEN questions include:
      - conditional breakpoint language
      - snapshot or restore state
      - time-travel debugging
      - trace-based causal-history inspection tooling
      - exact debugger UI affordances for Job lifecycle control
      - exact pause protocol
      - exact debugger overlay implementation
      - exact trace payload fields
      - language-runtime debugger integration internals

24.02. OPEN questions do not create supported behavior before they are
      resolved by the owning documents or implementation specifications.

24.03. Snapshot or restore state remains open in this document.

24.04. Snapshot or restore state, if later defined, does not bypass DA-04,
      DA-05, DA-07, DA-08, DA-25, or DA-26.

24.05. Time-travel debugging is not supported as a runtime debugger mode in
      this document.


===============================================================================
25. LOCKED SUMMARY
===============================================================================

25.01. LOCKED:
      - semantic breakpoints
      - ProcessingPipeline / ProcessingRun stage, memory, capability, and
        Job-scoped breakpoints
      - transaction-aware breakpoint semantics
      - committed-mutation-only memory breakpoints by default
      - staged-mutation observation only when explicitly configured
      - read-only inspection by default
      - controlled mutation with debugger-domain trace emission
      - debugger usability while Turnix is running
      - deterministic manual pause
      - manual pause does not silently cancel or supersede Jobs
      - debugger safe points are execution and mutation safety boundaries
      - debugger safe points are not SafePointWindows by default
      - debugger pause-at-safe-point does not automatically finalize Windows
      - apply-at-safe-point mutation semantics
      - undo of authoritative debugger changes operates on committed
        revisions as new explicit debugger-initiated work
      - redo history is debugger-local, ephemeral, and non-authoritative
      - debugger-specific trace obligations are owned here
      - debugger-domain trace reason identifiers are owned by DA-18
      - Job-safe breakpointing and pausing align with DA-19 Job lifecycle
      - debugger-originated Job control is explicit, trace-visible, and
        constrained by DA-17 and DA-19
      - paused-at-safe-point Jobs remain non-terminal
      - debugger tooling does not directly write Job terminal state
      - debugger resume or continue from pause is not DA-26 Resume
      - trace-based causal-history inspection is not DA-26 Replay by default
      - non-blocking debugger behavior

25.02. OPEN:
      - advanced conditional logic
      - snapshot or restore state
      - trace-based causal-history inspection tooling
      - time-travel debugging
      - exact debugger UI affordances for Job lifecycle control
