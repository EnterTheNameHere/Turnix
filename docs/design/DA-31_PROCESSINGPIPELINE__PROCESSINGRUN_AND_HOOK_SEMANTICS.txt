===============================================================================
DESIGN AREA DA-31 - PROCESSINGPIPELINE, PROCESSINGRUN AND HOOK SEMANTICS
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines ProcessingPipeline, ProcessingRun, and Hook as the staged processing
model used by Turnix for processor-backed input-to-output work.

This document generalizes the older LLMPipeline concept into processor-neutral
processing semantics.

Purpose:
--------
This document defines the Turnix processing model.

It defines:
- ProcessingPipeline as a reusable staged input-to-output procedure
- ProcessingRun as one execution of a ProcessingPipeline
- Hook as controlled ambient participation in a ProcessingPipeline stage
- stage contracts and stage transition boundaries
- raw and transformed processing representation boundaries
- ProcessingRun lifecycle outcomes
- ProcessingRun participation policy
- Hook authority, ordering, failure, and mutation limits
- relationships to ModCallContext, OrchestrationUnit, Transaction, Job,
  Capability, Event, Timer, trace, debugger inspection, and View attachment
- the processor-neutral replacement boundary for older LLMPipeline wording

It does NOT define:
- concrete processor provider APIs
- concrete model-provider request or response schemas
- exact public hook declaration syntax
- concrete Hook registration API shape
- concrete ProcessingPipeline stage names for every processor type
- capability permission policy
- Memory commit rules
- OrchestrationUnit terminal outcome rules
- Job lifecycle semantics
- trace record serialization
- View UI layout or frontend stream rendering
- Pack activation lifecycle hooks

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines processing, processing-stage, ProcessingRun, and
      Hook semantics within that shared interpretation model.


===============================================================================
02. DOCUMENT ROLE
===============================================================================

02.1. This document is the primary authority home for ProcessingPipeline,
      ProcessingRun, and Hook semantics.

02.2. ProcessingPipeline replaces older general references to Pipeline when
      the intended meaning is a reusable staged processor procedure.

02.3. ProcessingRun replaces older general references to PipelineRun when the
      intended meaning is one execution of a staged processor procedure.

02.4. LLMPipeline is treated as a processor-specific application of
      ProcessingPipeline.

02.5. An LLM run is treated as a processor-specific ProcessingRun.

02.6. LLM-specific prompt, model, provider, tokenizer, sampler, and response
      details do not define the general ProcessingPipeline authority model.

02.7. This document does not make every input-to-output operation a
      ProcessingPipeline.

02.8. A simple capability implementation may execute without a
      ProcessingPipeline when staged processing semantics are not needed.


===============================================================================
03. CORE CONCEPTS
===============================================================================

03.1. ProcessingPipeline is a reusable staged procedure around an
      input-to-output processor operation.

03.2. ProcessingPipeline defines the processing contract.

03.3. ProcessingRun is one execution of a ProcessingPipeline.

03.4. ProcessingRun owns temporary staged processing state for that execution.

03.5. Hook is controlled ambient participation in a ProcessingPipeline stage.

03.6. A processor is the operation implementation or implementation family that
      performs the domain work behind a ProcessingPipeline stage or processor
      call.

03.7. A provider is a concrete source of processor behavior.

03.8. Provider-specific behavior does not become ProcessingPipeline semantics
      merely because a ProcessingPipeline uses that provider.

03.9. ProcessingPipeline, ProcessingRun, and Hook are Turnix runtime concepts.

03.10. ProcessingPipeline, ProcessingRun, and Hook are not Sessions.

03.11. ProcessingPipeline, ProcessingRun, and Hook do not require Session
       identity.

03.12. Application-defined context references may be attached to a
       ProcessingRun.

03.13. Turnix does not interpret attached context references as a universal
       Session type.


===============================================================================
04. PROCESSINGPIPELINE DEFINITION
===============================================================================

04.1. A ProcessingPipeline defines a reusable staged procedure.

04.2. A ProcessingPipeline may be platform-defined, Pack-defined, or otherwise
      registered through a mediated Turnix surface.

04.3. ProcessingPipeline definition includes:
      - stage identity
      - stage order
      - stage input contracts
      - stage output contracts
      - Hook participation points
      - mutation permission for each stage
      - rejection behavior for each stage
      - retry and restart permissions
      - streaming behavior
      - validation behavior
      - finalization behavior
      - raw representation retention policy
      - transformed representation retention policy
      - trace correlation requirements
      - debugger exposure expectations

04.4. A ProcessingPipeline does not own provider-specific model details.

04.5. A ProcessingPipeline does not own committed Application state.

04.6. A ProcessingPipeline does not own OrchestrationUnit terminal outcomes.

04.7. A ProcessingPipeline does not own Job lifecycle semantics.

04.8. A ProcessingPipeline may be used by a Capability implementation.

04.9. A ProcessingPipeline is not itself the external capability contract unless
      a separate capability explicitly exposes it that way.


===============================================================================
05. PROCESSING STAGES
===============================================================================

05.1. A ProcessingStage is one named stage inside a ProcessingPipeline.

05.2. A ProcessingStage defines the operations and participation allowed at
      that point in the ProcessingRun.

05.3. A ProcessingStage defines which material is visible to participants.

05.4. A ProcessingStage defines whether participants may:
      - observe
      - transform
      - reject
      - validate
      - request retry
      - request restart
      - add metadata
      - redirect according to the stage contract
      - perform staged mutation through granted operations

05.5. A ProcessingStage does not grant authority merely because the stage
      exists.

05.6. Authority at a ProcessingStage derives from the stage contract, current
      ProcessingRun policy, current OrchestrationUnit, current Transaction,
      acting Pack identity, and granted ModCallContext operations.

05.7. A ProcessingRun stage transition changes the current stage authority
      boundary.

05.8. A ModCallContext bound to an earlier ProcessingStage is not retained for
      use after the callback or invocation completes.

05.9. A later stage does not inherit earlier stage permissions unless the
      ProcessingPipeline contract explicitly carries them forward.


===============================================================================
06. PROCESSINGRUN LIFECYCLE
===============================================================================

06.1. ProcessingRun is one execution of a ProcessingPipeline.

06.2. A ProcessingRun is created within Turnix orchestration.

06.3. A ProcessingRun is associated with one ProcessingPipeline.

06.4. A ProcessingRun may be associated with an OrchestrationUnit.

06.5. A ProcessingRun may be represented by or associated with a Job when the
      work needs observable lifecycle handling.

06.6. A ProcessingRun may:
      - complete
      - retry
      - restart from a defined stage
      - abort
      - be cancelled
      - fail
      - be superseded

06.7. ProcessingRun completion does not automatically commit Application state.

06.8. The owning OrchestrationUnit decides commit or abort according to its own
      contract.

06.9. A ProcessingRun does not become persistent Application continuity merely
      because it carries temporary processing state.

06.10. Retained evidence about a ProcessingRun is not committed-state authority
       unless relevant material is committed through the DA-04 commit model.


===============================================================================
07. PROCESSINGRUN STATE
===============================================================================

07.1. ProcessingRun state is temporary processing state.

07.2. ProcessingRun state may include:
      - raw input
      - current transformed input
      - processor request
      - raw stream
      - current transformed stream
      - raw final output
      - current transformed output
      - Hook contributions
      - attempt history
      - retry state
      - restart state
      - validation results
      - errors
      - cancellation state
      - temporary metadata
      - application-defined context references

07.3. Raw and transformed representations remain distinct.

07.4. Raw representation is processor material before permitted Turnix or Hook
      transformation.

07.5. Current representation is the representation after permitted
      transformations at the current ProcessingStage.

07.6. A ProcessingPipeline contract defines which raw and transformed material
      is retained.

07.7. A ProcessingPipeline contract defines which raw and transformed material
      is visible to Hooks.

07.8. Retaining raw material for diagnostics or replay evidence does not make
      that material committed Application state.

07.9. A ProcessingRun may stage selected material into a Transaction only
      through granted operations.

07.10. Material staged into a Transaction becomes authoritative only if the
       relevant Transaction commits under the DA-04 commit model.


===============================================================================
08. HOOK SEMANTICS
===============================================================================

08.1. Hook is controlled ambient participation in a ProcessingPipeline stage.

08.2. A Hook is registered participation, not direct backend access.

08.3. A Hook participates only when the ProcessingPipeline stage contract,
      ProcessingRun policy, registration scope, visibility rules, and granted
      operations allow participation.

08.4. A Hook callback receives a fresh ModCallContext.

08.5. The ModCallContext for a Hook callback is bound to the Hook-owning Pack.

08.6. A Hook callback does not borrow the original requester's authority.

08.7. A Hook callback may receive bindings for:
      - Application
      - ApplicationRun
      - ProcessingPipeline
      - ProcessingRun
      - ProcessingStage
      - OrchestrationUnit
      - Transaction
      - Job, when relevant
      - cause and correlation descriptors
      - cancellation state
      - deadline state
      - granted stage operations

08.8. A Hook may be allowed by stage contract to:
      - observe
      - transform
      - reject
      - request retry
      - add metadata
      - validate
      - redirect according to stage contract

08.9. A Hook cannot perform an operation merely because its host-language code
      can call that operation.

08.10. A Hook performs Turnix operations only through the mediated operations
       granted by its current ModCallContext.

08.11. A Hook does not directly commit Transactions.

08.12. A Hook does not assign terminal Job state.

08.13. A Hook does not become Kernel authority.


===============================================================================
09. HOOK ORDERING AND COMPLETION
===============================================================================

09.1. Hook ordering does not silently depend on registration order.

09.2. The primary ordering tool is correct ProcessingStage design.

09.3. A ProcessingPipeline uses separate stages when ordering is semantically
      important.

09.4. A ProcessingPipeline may define explicit ordering constraints only when
      separate stages are insufficient.

09.5. Hook ordering constraints remain part of the ProcessingPipeline contract.

09.6. A ProcessingRun normally waits for required Hook completion before
      advancing past the stage that requires those Hooks.

09.7. Optional Hook completion affects the ProcessingRun only as defined by the
      stage contract.

09.8. Hook failure affects the ProcessingRun only as defined by the stage
      contract.

09.9. A Hook rejection does not define universal failure semantics.

09.10. The stage contract defines whether rejection aborts, retries, restarts,
       skips a participant, records validation failure, or produces another
       explicit outcome.


===============================================================================
10. PROCESSINGRUN PARTICIPATION POLICY
===============================================================================

10.1. ProcessingRun participation policy controls who may participate in one
      ProcessingRun.

10.2. Initial participation modes include:
      - Cooperative
      - Isolated

10.3. Cooperative mode allows eligible registered Hooks to participate.

10.4. Isolated mode allows only explicitly selected participants and mandatory
      platform infrastructure to participate.

10.5. Participation policy may include separate dimensions for:
      - observability
      - Hook participation
      - mutation permission
      - raw input access
      - raw output access
      - transformed input access
      - transformed output access
      - metadata access

10.6. Turnix does not encode hidden as no observer can observe anything.

10.7. Turnix does not encode public as every participant may change everything.

10.8. Stage contracts and ProcessingRun policy determine allowed
      participation.


===============================================================================
11. AUTHORITY AND MUTATION
===============================================================================

11.1. ProcessingPipeline does not own authoritative state semantics.

11.2. ProcessingRun state is non-authoritative until material is explicitly
      staged into a Transaction.

11.3. Hook contributions are non-authoritative until material is explicitly
      staged into a Transaction.

11.4. A ProcessingRun may participate in staged mutation only through the
      current OrchestrationUnit and Transaction.

11.5. A Hook may request staged mutation only when:
      - the ProcessingStage allows mutation
      - the ProcessingRun policy allows mutation
      - the Hook-owning Pack has the required permission
      - the current ModCallContext grants the operation
      - the current Transaction accepts the staged mutation

11.6. ProcessingRun completion does not bypass commit, rollback, conflict
      detection, or trace obligations owned by the state model.

11.7. ProcessingPipeline finalization does not turn retained evidence into
      committed state.

11.8. ProcessingPipeline retry and restart do not undo committed state unless a
      separate committed-state operation explicitly changes state.


===============================================================================
12. CAPABILITY RELATIONSHIP
===============================================================================

12.1. Capability is an explicit mediated operation interface.

12.2. ProcessingPipeline is a staged execution mechanism.

12.3. A Capability implementation may use a ProcessingPipeline.

12.4. A Capability implementation may execute without a ProcessingPipeline.

12.5. A caller invokes a Capability according to the Capability contract.

12.6. The caller does not gain authority over the ProcessingPipeline merely
      because the Capability implementation uses one.

12.7. The ProcessingPipeline does not expose a provider identity unless the
      Capability or ProcessingPipeline contract explicitly exposes that
      information.

12.8. Provider selection remains mediated by the relevant capability,
      processing, configuration, and permission rules.


===============================================================================
13. EVENTS, TIMERS, AND LIFECYCLE CALLBACKS
===============================================================================

13.1. Hooks are not Events.

13.2. Events are semantic notifications.

13.3. Event handlers react independently unless an explicit orchestration
      contract says otherwise.

13.4. If producer work requires participant completion before the producer
      completes, the design uses Hook, Capability, or explicit orchestration
      rather than Event.

13.5. Hooks are not Timer callbacks.

13.6. Timer firing creates new orchestrated work according to Timer semantics.

13.7. Hooks are not Pack activation lifecycle callbacks.

13.8. Pack activation lifecycle callbacks include activation-process callbacks
      such as onEntryLoaded, onEntriesLoaded, and onLoad.

13.9. Processing Hooks participate in ProcessingPipeline stages.

13.10. Sharing the word "hook" does not merge processing-stage participation
       with Pack activation lifecycle semantics.


===============================================================================
14. TRACE, DEBUGGING, AND VIEW ATTACHMENT
===============================================================================

14.1. ProcessingRun activity is trace-correlated.

14.2. Trace correlation may include:
      - Application
      - ApplicationRun
      - acting Pack
      - invocation
      - OrchestrationUnit
      - Job
      - ProcessingPipeline
      - ProcessingRun
      - ProcessingStage
      - Hook
      - cause descriptors

14.3. Trace evidence explains ProcessingRun behavior.

14.4. Trace evidence does not define committed-state truth.

14.5. ProcessingPipelines, ProcessingRuns, and ProcessingPipeline stages are
      primary semantic debugging targets.

14.6. Debugger inspection of a ProcessingRun does not grant mutation authority.

14.7. Debugger-originated mutation remains constrained by the debugger,
      transaction, OrchestrationUnit, and committed-state rules.

14.8. A View may display ProcessingRun progress, streams, results, and errors.

14.9. A View does not own the ProcessingRun.

14.10. A View may detach while a ProcessingRun continues according to policy.

14.11. A later View may attach to retained or live ProcessingRun information
       according to View and ProcessingRun policy.


===============================================================================
15. FAILURE, CANCELLATION, RETRY, AND RESTART
===============================================================================

15.1. ProcessingRun cancellation is explicit.

15.2. ProcessingRun failure is explicit.

15.3. ProcessingRun retry is allowed only when the ProcessingPipeline contract
      or ProcessingRun policy allows retry.

15.4. ProcessingRun restart is allowed only from stages defined as restart
      boundaries.

15.5. A Hook may request retry only when the current stage contract allows the
      Hook to request retry.

15.6. A Hook retry request does not force retry by itself.

15.7. The ProcessingRun applies retry policy through the stage contract and
      owning orchestration.

15.8. Cancellation does not imply committed-state rollback unless the owning
      Transaction aborts.

15.9. Failure does not imply committed-state rollback unless the owning
      Transaction aborts.

15.10. Retry does not imply external side-effect reversal.

15.11. Restart does not imply external side-effect reversal.


===============================================================================
16. LLM-SPECIFIC PROCESSING
===============================================================================

16.1. LLM generation is one processor domain that can use ProcessingPipeline.

16.2. LLMPipeline is a processor-specific name for an LLM-oriented
      ProcessingPipeline.

16.3. LLM run is a processor-specific name for a ProcessingRun that executes an
      LLM-oriented ProcessingPipeline.

16.4. Prompt construction, provider request construction, stream parsing,
      response parsing, validation, transformation, and finalization may be
      modeled as ProcessingPipeline stages.

16.5. Model-provider details do not become general ProcessingPipeline
      semantics.

16.6. Tokenizer behavior, sampling parameters, provider request schemas, and
      provider response schemas remain processor/provider details unless a
      ProcessingPipeline contract explicitly exposes them.

16.7. A ProcessingPipeline may support non-LLM processors.

16.8. Non-LLM processors are not forced to inherit LLM-specific stage names.


===============================================================================
17. OPEN QUESTIONS
===============================================================================

17.1. OPEN: The default stage set for LLM generation remains to be named.

17.2. OPEN: The default stage set for streaming processors remains to be
      named.

17.3. OPEN: The concrete Hook registration API remains to be defined.

17.4. OPEN: The concrete ProcessingPipeline registration API remains to be
      defined.

17.5. OPEN: The exact policy schema for Cooperative and Isolated
      ProcessingRuns remains to be defined.

17.6. OPEN: The retention policy shape for raw processor material remains to be
      defined.

17.7. OPEN: The exact relationship between ProcessingRun evidence and retained
      Window artifacts remains to be integrated with the Window and artifact
      documents.

17.8. OPEN: Explicit Hook before/after constraints remain undesigned except as
      a future extension point.

17.9. OPEN: The exact trace schema for Hook participation remains to be defined
      by trace schema documents.
