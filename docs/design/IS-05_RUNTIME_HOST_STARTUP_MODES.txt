===============================================================================
IMPLEMENTATION SPECIFICATION IS-05 - RUNTIME HOST STARTUP MODES
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines concrete RuntimeHost startup-mode classification, startup-mode entry
flow, startup-mode operation composition, startup-mode result surfaces, and
trace mapping for interactive host mode, one-shot command mode, serve mode,
connect mode, test mode, and launcher mode.

This document implements the startup-mode semantics defined by DA-28. It uses
IS-03 for workspace ownership and host locking, and IS-04 for command-surface
handling.

Purpose:
--------
This document defines how Turnix enters RuntimeHost execution through different
startup modes without creating separate Application, ApplicationRun,
SaveBundle, adapter, RPC, capability, policy, persistence,
OrchestrationUnit, Job, View, or trace semantics for each mode.

It defines:
- startupMode identity and classification
- startup request normalization
- startup-mode selection flow
- interactive host mode flow
- one-shot command mode flow
- serve mode flow
- connect mode flow
- test mode flow
- launcher mode flow
- startup-mode relationship to workspace ownership
- startup-mode relationship to command surfaces
- startup-mode result envelope
- startup-mode trace mapping to DA-28 trace reasons
- startup-mode error categories

It does NOT define:
- RuntimeHost semantics (see DA-28)
- Kernel authority ordering (see DA-01 and DA-02)
- committed-state or transaction semantics (see DA-04)
- persistent I/O safety semantics (see DA-07)
- Application lifecycle or Application identity semantics (see DA-20)
- ApplicationRun lifecycle or ApplicationRun identity semantics (see DA-20)
- SaveBundle persistence semantics
- RPC, channel, or transport semantics (see DA-21)
- UI, View, or frontend runtime semantics (see DA-22)
- execution adapter authority boundaries (see DA-23)
- OrchestrationUnit mutation authority semantics (see DA-24)
- adapter lifecycle, trust, and trace semantics (see DA-27)
- workspace ownership and host-lock record mechanics (see IS-03)
- RuntimeHost command-surface flow or command result envelope (see IS-04)
- concrete shell syntax, service wrapper syntax, desktop launcher behavior, or
  terminal rendering
- concrete LAN pairing or authentication

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and document
      context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines implementation-level RuntimeHost startup-mode
      behavior within that shared interpretation model.

01.05. This implementation specification does not create new authority
      semantics.

01.06. This implementation specification implements DA-28 startup-mode rules.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. RuntimeHost startup-mode behavior answers:

          "How does Turnix choose and enter a RuntimeHost workflow while
           preserving the same Kernel-mediated runtime operations and
           authority boundaries across CLI, launcher, server, connect, test,
           and one-shot entry shapes?"

02.02. Startup mode selection determines how Turnix is entered.

02.03. Startup mode selection does not define separate runtime semantics.

02.04. Startup modes are entry workflows over shared Kernel-mediated runtime
      operations.

02.05. A startup mode may create or connect to a RuntimeHost.

02.06. A startup mode may create, bind, or use a command surface.

02.07. A startup mode may request workspace ownership.

02.08. A startup mode may avoid workspace ownership when it only connects to an
      existing RuntimeHost or performs explicitly read-only behavior.

02.09. A startup mode is not authority by itself.

02.10. Startup mode success is not Application creation success,
       ApplicationRun readiness, ApplicationRun start success, Job success,
       adapter success, or OrchestrationUnit completion by default.

02.11. Startup request input is classification, policy, and routing evidence.

02.12. Startup request input does not grant Kernel authority.

02.13. Startup request input does not grant RuntimeHost authority.

02.14. Startup request input does not grant TurnixRuntime identity.

02.15. Startup request input does not grant workspace ownership.

02.16. Startup request input does not grant Application identity.

02.17. Startup request input does not grant ApplicationRun identity.

02.18. Startup request input does not grant SaveBundle authority.

02.19. Startup request input does not grant capability permission.

02.20. Startup request input does not grant adapter authorization.

02.21. Startup request input does not grant policy approval.


===============================================================================
03. STARTUP MODE IDENTITY AND CLASSIFICATION
===============================================================================

03.01. startupRequestId identifies one startup request.

03.02. startupRequestId is distinct from:
      - runtimeHostId
      - commandId
      - runtimeOperationId
      - workspace identity
      - applicationId
      - applicationRunId
      - jobId
      - orchestrationUnitId
      - viewId
      - adapter identity
      - RPC message identity
      - transport identity
      - decision identity

03.03. startupMode is one of:
      - interactiveHost
      - oneShotCommand
      - serve
      - connect
      - test
      - launcher

03.04. startupMode values define semantic categories, not final CLI names,
      flags, desktop launcher actions, or service wrapper names.

03.05. Startup mode classification occurs before mode-specific flow begins.

03.06. Startup mode classification emits RuntimeHostStartupModeSelected when a
      startup mode is selected.

03.07. Startup mode rejection emits RuntimeHostStartupModeRejected.

03.08. Unknown or unsupported startup mode input is rejected before RuntimeHost
      ownership acquisition.

03.09. Unknown or unsupported startup mode input does not create a partial
      RuntimeHost.

03.10. Startup mode input does not allow the caller to forge runtime,
       application, ownership, adapter, capability, or policy identity.


===============================================================================
04. STARTUP REQUEST NORMALIZATION
===============================================================================

04.01. Startup request normalization prepares startup input for classification.

04.02. Normalization may include:
      - executable invocation context capture
      - entry surface kind capture
      - command-line argument parsing
      - environment input capture
      - current working directory capture
      - requested workspace path capture
      - requested startup mode capture
      - requested command capture
      - requested local bind behavior capture
      - requested LAN exposure capture
      - test harness context capture
      - launcher context capture
      - service wrapper context capture

04.03. Normalization does not grant authority.

04.04. Normalization does not acquire workspace ownership.

04.05. Normalization does not create a RuntimeHost.

04.06. Normalization does not create an Application.

04.07. Normalization does not create an ApplicationRun.

04.08. Normalization does not load a SaveBundle.

04.09. Normalization failure rejects the startup request.

04.10. Concrete parsing syntax belongs to implementation code or a later CLI,
       launcher, or service-wrapper implementation specification.

04.11. Normalized executable invocation context remains classification and
       routing evidence.

04.12. Normalized environment input remains classification and policy evidence.

04.13. Normalized test harness context remains test-surface evidence.

04.14. Normalized launcher context remains launcher-surface evidence.

04.15. Normalized service wrapper context remains service-wrapper evidence.

04.16. Normalized startup input is not a trusted authority token merely
       because it came from an official entry surface.


===============================================================================
05. SHARED STARTUP OPERATION ORDER
===============================================================================

05.01. Startup modes compose shared RuntimeHost operations rather than defining
      independent runtime semantics.

05.02. Shared startup operations may include:
      - NormalizeStartupRequest
      - ClassifyStartupMode
      - ResolveWorkspace
      - DiscoverExistingRuntimeHost
      - ConnectRuntimeHost
      - BindWorkspace
      - AcquireWorkspaceOwnership
      - StartRuntimeHost
      - CreateEntrySurface
      - CreateCommandSurface
      - DispatchInitialCommand
      - CreateApplication
      - LoadSaveBundle
      - CreateApplicationRun
      - StartApplicationRun
      - StartFrontendSurface
      - ExposeLanSurface
      - RunTestHarness
      - StopRuntimeHost
      - ReleaseWorkspaceOwnership

05.03. Operation names in this section define semantic categories, not final
      API names.

05.04. A startup mode may use a subset of shared operations.

05.05. A startup mode may skip an operation when the mode does not require it.

05.06. Skipping an operation does not redefine the skipped operation's meaning.

05.07. A startup mode that mutates Turnix-managed state enters the same DA-24
      OrchestrationUnit boundaries as other mutation-bearing work.

05.08. A startup mode that requires writable workspace ownership uses IS-03.

05.09. A startup mode that dispatches a command uses IS-04.

05.10. A startup mode that creates an Application follows the owning lifecycle
       documents.

05.11. A startup mode that loads a SaveBundle follows the owning lifecycle and
       persistence documents.

05.12. A startup mode that creates or starts an ApplicationRun follows the
       owning lifecycle documents.

05.13. A startup mode that creates or binds a View uses DA-22.

05.14. A startup mode that selects or starts adapter execution uses DA-23 and
       DA-27.

05.15. A startup mode that communicates through RPC uses DA-21.

05.16. Shared operation ordering does not create independent semantics for
       Application creation, SaveBundle loading, ApplicationRun creation,
       ApplicationRun start, workspace ownership, command dispatch, adapter
       execution, capability invocation, Job handling, RPC, View creation, or
       persistence.


===============================================================================
06. INTERACTIVE HOST MODE
===============================================================================

06.01. interactiveHost mode enters a command-accepting host or host-connected
      control surface.

06.02. interactiveHost mode normally requests or connects to a RuntimeHost and
      creates a command surface.

06.03. interactiveHost mode may acquire writable workspace ownership when it
      starts a writable RuntimeHost.

06.04. interactiveHost mode may connect to an existing RuntimeHost when policy
      and connection rules permit that path.

06.05. interactiveHost mode does not silently choose between starting a host and
      connecting to an existing host when that choice affects ownership or
      authority.

06.06. interactiveHost mode emits RuntimeHostInteractiveModeStarted when the
      mode flow begins.

06.07. interactiveHost readiness does not imply command success.

06.08. interactiveHost readiness does not imply ApplicationRun readiness.

06.09. interactiveHost readiness does not imply ApplicationRun start success.

06.10. interactiveHost readiness does not imply adapter readiness.

06.11. Commands entered after interactiveHost readiness follow IS-04.


===============================================================================
07. ONE-SHOT COMMAND MODE
===============================================================================

07.01. oneShotCommand mode performs a bounded requested command and exits after
      the command reaches its operation-defined result or error surface.

07.02. oneShotCommand mode uses IS-04 for command handling.

07.03. oneShotCommand mode may start a temporary RuntimeHost when the requested
      command requires host ownership or host-local runtime services.

07.04. oneShotCommand mode may connect to an existing RuntimeHost when the
      command is a client or control operation and policy permits that path.

07.05. oneShotCommand mode may perform read-only inspection without writable
      workspace ownership when the command explicitly requests read-only
      inspection.

07.06. oneShotCommand mode does not silently downgrade writable behavior to
      read-only inspection.

07.07. oneShotCommand mode emits RuntimeHostOneShotCommandStarted when the mode
      flow begins.

07.08. oneShotCommand process exit behavior reflects the command result surface,
      not hidden downstream work outcome.

07.09. If oneShotCommand mode detaches from Job-backed or retained work, the
      result surface reports detachment or retention explicitly.

07.10. oneShotCommand exit does not silently cancel detached work unless the
       owning workflow maps process exit to cancellation explicitly.

07.11. oneShotCommand mode may project command result status into startup
       result status only through an explicit startup-mode contract.

07.12. oneShotCommand projection does not replace IS-04 command-domain
       evidence.


===============================================================================
08. SERVE MODE
===============================================================================

08.01. serve mode starts or keeps a RuntimeHost available for explicitly
      selected entry surfaces.

08.02. serve mode normally requests writable workspace ownership when writable
      host behavior is requested.

08.03. serve mode may expose local-only entry surfaces.

08.04. serve mode may expose LAN entry surfaces only when explicit policy or
      configuration permits LAN exposure.

08.05. serve mode never silently exposes internet-accessible runtime control
      surfaces.

08.06. serve mode does not silently expose LAN runtime control surfaces.

08.07. serve mode emits RuntimeHostServeModeStarted when the mode flow begins.

08.08. serve mode readiness does not imply ApplicationRun readiness.

08.09. serve mode readiness does not imply ApplicationRun start success.

08.10. serve mode readiness does not imply command success.

08.11. serve mode readiness does not imply adapter readiness.

08.12. serve mode stop uses RuntimeHost lifecycle and workspace ownership
       release behavior under DA-28 and IS-03.


===============================================================================
09. CONNECT MODE
===============================================================================

09.01. connect mode connects a command or client to an existing RuntimeHost.

09.02. connect mode does not acquire writable workspace ownership for a
      RuntimeHost it did not start.

09.03. connect mode may read workspace ownership evidence to discover or verify
      an existing RuntimeHost.

09.04. connect mode may fail when no compatible existing RuntimeHost is found.

09.05. connect mode may fail when policy denies connection.

09.06. connect mode may fail when the existing RuntimeHost is unreachable.

09.07. connect mode does not silently start a writable RuntimeHost unless the
      startup request explicitly permits fallback to a writable host.

09.08. connect mode does not silently take over stale ownership evidence.

09.09. connect mode emits RuntimeHostConnectModeStarted when the mode flow
      begins.

09.10. Commands sent after successful connection follow IS-04 and any
       transport-specific implementation specification.


===============================================================================
10. TEST MODE
===============================================================================

10.01. test mode uses controlled test surfaces without weakening runtime,
      adapter, Application, ApplicationRun, SaveBundle, orchestration,
      capability, policy, persistence, or trace boundaries.

10.02. test mode may use TestAdapter or test-specific entry surfaces.

10.03. test mode may use temporary workspaces when the test explicitly defines
      temporary workspace behavior.

10.04. test mode may bypass human prompts only when the test harness supplies
      explicit policy or decision fixtures.

10.05. Test fixtures do not become production defaults.

10.06. Test fixtures do not create production permissions.

10.07. Test fixtures do not create production policy defaults.

10.08. Test fixtures do not create production adapter authority.

10.09. Test fixtures do not create production workspace ownership.

10.10. Test fixtures do not create production SaveBundle semantics.

10.11. Test fixtures do not create production committed-state semantics.

10.12. test mode does not silently ignore persistence failures.

10.13. test mode does not silently ignore trace obligations.

10.14. test mode emits RuntimeHostTestModeStarted when the mode flow begins.

10.15. test mode result surfaces distinguish test harness failure,
       RuntimeHost failure, command failure, ApplicationRun failure, Job
       failure, adapter failure, and assertion failure when those distinctions
       are available.


===============================================================================
11. LAUNCHER MODE
===============================================================================

11.01. launcher mode uses a user-facing launcher surface to select or request
      runtime operations.

11.02. launcher mode may start a RuntimeHost to present launcher UI.

11.03. launcher mode may connect to an existing RuntimeHost when policy and
      connection rules permit that path.

11.04. launcher mode may create Views or frontend entry surfaces under DA-22.

11.05. launcher mode does not create Application semantics separate from their
      owning design documents.

11.06. launcher mode does not create ApplicationRun semantics separate from
      their owning design documents.

11.07. launcher mode does not create SaveBundle semantics separate from their
      owning design documents.

11.08. launcher mode does not make browser frontend state authoritative.

11.09. launcher mode emits RuntimeHostLauncherModeStarted when the mode flow
      begins.

11.10. Commands or interactions submitted by launcher surfaces follow IS-04,
       DA-22, and DA-21 as applicable.

11.11. Launcher UI is an entry and request surface.

11.12. Launcher UI is not Kernel authority, RuntimeHost authority, command
       authority, View authority, Application authority, ApplicationRun
       authority, SaveBundle authority, adapter authority, or policy authority.


===============================================================================
12. STARTUP MODE RESULT ENVELOPE
===============================================================================

12.01. A startup mode result envelope represents startup-mode handling outcome.

12.02. A startup mode result envelope contains:
      - schemaVersion
      - startupRequestId
      - startupMode
      - startupStatus
      - runtimeHostId when applicable
      - workspace identity when applicable
      - commandId when applicable
      - runtimeOperationId when applicable
      - applicationId when applicable
      - applicationRunId when applicable
      - viewId when applicable
      - jobId when applicable
      - errorCategory when applicable
      - message
      - details
      - traceCorrelation when available

12.03. startupStatus is one of:
      - selected
      - rejected
      - started
      - connected
      - ready
      - completed
      - failed
      - cancelled
      - detached

12.04. selected means the startup mode was classified.

12.05. rejected means startup handling rejected the request before valid mode
      entry.

12.06. started means startup mode flow began.

12.07. connected means startup mode connected to an existing RuntimeHost.

12.08. ready means the startup mode reached its mode-defined ready surface.

12.09. completed means the startup mode reached its mode-defined completed
      surface.

12.10. failed means startup mode handling reached its mode-defined failed
       surface.

12.11. cancelled means startup mode handling was cancelled at startup level.

12.12. detached means startup mode handling detached from the waiting entry
       surface while owning workflow rules define continued work or retained
       result behavior.

12.13. startupStatus does not redefine RuntimeHost lifecycle outcome.

12.14. startupStatus does not redefine command status under IS-04.

12.15. startupStatus does not redefine Job terminal outcome.

12.16. startupStatus does not redefine OrchestrationUnit terminal outcome.

12.17. startupStatus does not redefine Application lifecycle outcome.

12.18. startupStatus does not redefine ApplicationRun lifecycle outcome.

12.19. A startup mode result envelope may reference a command result envelope
       or commandId.

12.20. A startup mode result envelope does not replace the command result
       envelope unless the startup-mode contract explicitly defines that
       projection.

12.21. oneShotCommand mode may project command result status into startup
       result status only as an explicit startup-mode surface.

12.22. The underlying command result remains command-domain evidence under
       IS-04.

12.23. A startup mode result envelope may summarize downstream outcomes only
       through explicit startup-mode contracts.

12.24. Downstream outcomes include command, RuntimeHost operation, workspace
       ownership, Job, adapter, View, ApplicationRun, policy, and trace
       outcomes.

12.25. Startup result projection does not erase owning-domain evidence.

12.26. Startup result projection does not erase trace correlation.

12.27. Startup result projection does not convert retained downstream evidence
       into startup-mode authority.


===============================================================================
13. RELATION TO WORKSPACE OWNERSHIP
===============================================================================

13.01. Startup modes that require writable workspace ownership use IS-03.

13.02. Startup modes that only connect to an existing RuntimeHost do not acquire
      writable workspace ownership.

13.03. Startup modes that perform explicit read-only inspection do not acquire
      writable workspace ownership.

13.04. Startup mode selection does not itself acquire workspace ownership.

13.05. Workspace ownership acquisition does not itself mean startup mode
      completion.

13.06. Workspace ownership failure may cause startup mode failure when the mode
      requires writable ownership.

13.07. Existing ownership evidence may cause startup mode to offer explicit
      alternatives when the entry surface supports alternatives.

13.08. Startup mode handling does not select those alternatives silently.

13.09. Workspace ownership evidence does not let startup mode handling forge
      RuntimeHost authority, Kernel authority, Application identity,
      ApplicationRun identity, SaveBundle authority, or policy approval.


===============================================================================
14. RELATION TO COMMAND SURFACES
===============================================================================

14.01. Startup modes that receive or dispatch commands use IS-04.

14.02. Startup mode selection does not itself accept a command.

14.03. Command acceptance does not itself mean startup mode success.

14.04. Startup mode readiness does not imply command success.

14.05. oneShotCommand mode may map command result to startup result according to
      its operation contract.

14.06. interactiveHost, serve, and launcher modes may remain ready while later
      commands succeed, fail, or remain pending independently.

14.07. connect mode may pass commands to an existing RuntimeHost after
      connection succeeds.

14.08. test mode may dispatch commands through test-controlled command surfaces
      without weakening IS-04 command-surface boundaries.

14.09. Command-surface availability does not grant startup mode authority over
      command semantics.

14.10. Startup mode result projection does not replace command-domain evidence
       by default.


===============================================================================
15. TRACE MAPPING
===============================================================================

15.01. IS-05 maps implementation behavior to DA-28 RuntimeHost startup-mode
      trace reasons.

15.02. Startup mode classification maps to:
      - RuntimeHostStartupModeSelected
      - RuntimeHostStartupModeRejected

15.03. interactiveHost mode entry maps to RuntimeHostInteractiveModeStarted.

15.04. oneShotCommand mode entry maps to RuntimeHostOneShotCommandStarted.

15.05. serve mode entry maps to RuntimeHostServeModeStarted.

15.06. connect mode entry maps to RuntimeHostConnectModeStarted.

15.07. test mode entry maps to RuntimeHostTestModeStarted.

15.08. launcher mode entry maps to RuntimeHostLauncherModeStarted.

15.09. Startup mode handling may also produce RuntimeHost lifecycle trace
      reasons when it starts, connects to, stops, fails, or closes a
      RuntimeHost.

15.10. Startup mode handling may produce workspace ownership trace reasons
       under IS-03.

15.11. Startup mode handling may produce command trace reasons under IS-04.

15.12. Trace evidence includes enough context, when available, to identify:
       - startupRequestId
       - startupMode
       - runtimeHostId
       - workspace identity
       - entry surface identity
       - commandId
       - runtimeOperationId
       - applicationId
       - applicationRunId
       - viewId
       - jobId
       - orchestrationUnitId
       - policy decision identity
       - error category

15.13. Startup mode trace evidence does not replace RuntimeHost lifecycle trace
       evidence.

15.14. Startup mode trace evidence does not replace workspace ownership trace
       evidence.

15.15. Startup mode trace evidence does not replace command trace evidence.

15.16. Startup mode trace evidence does not replace Application evidence.

15.17. Startup mode trace evidence does not replace ApplicationRun evidence.

15.18. Startup mode trace evidence does not replace Job, adapter, RPC, UI,
       OrchestrationUnit, transaction, or Window evidence.


===============================================================================
16. ERROR CATEGORIES
===============================================================================

16.01. RuntimeHost startup-mode error categories include:
      - StartupModeUnknown
      - StartupModeUnsupported
      - StartupModeInvalidForEntrySurface
      - StartupRequestMalformed
      - StartupWorkspaceRequired
      - StartupWorkspaceOwnershipFailed
      - StartupExistingHostNotFound
      - StartupExistingHostUnreachable
      - StartupExistingHostRejected
      - StartupPolicyDenied
      - StartupPermissionDenied
      - StartupCommandRejected
      - StartupCommandFailed
      - StartupRuntimeHostStartFailed
      - StartupRuntimeHostConnectFailed
      - StartupEntrySurfaceFailed
      - StartupLanExposureDenied
      - StartupImplementationFeatureUnavailable

16.02. Error category names in this section define semantic categories, not
      final exception class names.

16.03. Concrete exception class names belong to implementation code or a later
      error-schema specification.

16.04. Error reporting preserves distinctions between startup classification,
      workspace ownership, host discovery, host connection, command handling,
      policy denial, permission denial, entry-surface failure, and missing
      implementation feature.

16.05. Error reporting does not collapse all startup failure into generic host
      failure when the implementation can distinguish the cause.


===============================================================================
17. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

17.01. The following are not supported:
      - treating startup mode as independent runtime semantics
      - treating startup mode selection as authority
      - treating startup mode selection as workspace ownership acquisition
      - treating startup mode success as Application creation success by
        default
      - treating startup mode success as ApplicationRun success by default
      - treating startup mode success as Job success by default
      - treating startup mode failure as Job failure by default
      - treating startup mode failure as OrchestrationUnit failure by default
      - silently choosing between host start and existing-host connection when
        ownership or authority would change
      - silently falling back from connect mode to a writable host
      - silently downgrading writable startup behavior to read-only inspection
      - silently exposing LAN surfaces in serve mode
      - silently exposing internet-accessible runtime control surfaces
      - test mode bypassing persistence, trace, policy, capability,
        OrchestrationUnit, transaction, adapter, Application, ApplicationRun,
        SaveBundle, or RuntimeHost boundaries
      - launcher mode creating separate SaveBundle, Application, or
        ApplicationRun semantics
      - one-shot process exit silently cancelling detached work by default
      - treating startup result projection as replacement for command-domain
        result evidence by default
      - treating startup request input as an authority grant
      - treating launcher UI state as authoritative state
