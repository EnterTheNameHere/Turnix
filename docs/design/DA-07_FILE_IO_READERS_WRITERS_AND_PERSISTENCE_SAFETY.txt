===============================================================================
DESIGN AREA DA-07 - FILE I/O, READERS / WRITERS & PERSISTENCE SAFETY
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines how Turnix performs persistent I/O, who is allowed to perform it, and
how failures are handled without corrupting authoritative state, retained
material, or user trust.

All persistence in Turnix is centralized and mediated through IoManager.

Purpose:
--------
This document defines how Turnix centralizes persistent I/O behind IoManager,
the centralized persistent-I/O authority, so that persistence remains
deterministic, reversible, trace-visible, and explicitly controlled.

It defines:
- IoManager authority and boundaries
- Reader / Writer provider model
- raw access containment rules
- root read/write permissions
- adapter-executed code persistence boundaries
- persistence safety requirements
- backup, snapshot, and rollback boundaries
- error classification and recovery boundaries
- streaming I/O rules and where streaming is forbidden

It does NOT define:
- the general state model, transaction model, or committed-state truth
  (see DA-04)
- payload identity, Chunk, ChunkId, ValueRef, decode, integrity, or
  retained-root reachability semantics (see DA-05)
- configuration scopes, defaults, overrides, effectiveConfig, schemas, or
  configuration migration semantics (see DA-06)
- Window, SafePointWindow, ActiveWindow, AbortedWindow, ordering, or
  finalization semantics (see DA-08)
- pack discovery rules beyond save scanning implications (see DA-09)
- dependency resolution semantics (see DA-13)
- activation and lifecycle semantics (see DA-14)
- capability schemas, permission prompting, or capability policy (see DA-16)
- user-decision or policy-handling semantics (see DA-17)
- Application, ApplicationRun, or SaveBundle lifecycle and identity semantics
  (see DA-20)
- execution adapter boundary semantics (see DA-23)
- OrchestrationUnit lifecycle, terminal outcome, or mutation authority
  (see DA-24)
- retained artifact, export, digest, or offline inspection artifact semantics
  (see DA-25)
- comparison, Replay, Resume, or Retry workflow semantics (see DA-26)
- adapter lifecycle, trust, isolation, disconnect, or adapter-domain trace
  semantics (see DA-27)
- RuntimeHost workspace ownership, command surfaces, startup modes, or
  LAN/local-first boundaries (see DA-28)
- tracing schema, trace substrate, trace retention, trace loss, span mechanics,
  or trace storage semantics (see DA-03)

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines persistent I/O authority, Reader / Writer
      boundaries, and persistence-safety rules within that shared
      interpretation model.


===============================================================================
02. CORE PRINCIPLE
===============================================================================

02.01. Persistent I/O in Turnix routes through IoManager, the centralized
      persistent-I/O authority.

02.02. Components may request persistence work through Turnix-mediated
      surfaces.

02.03. Request capability does not transfer IoManager authority.

02.04. Packs, tools inside runtime orchestration, adapter-executed code, and
      runtime components do not read or write persistent data by bypassing
      IoManager.

02.05. This applies to:
      - configuration
      - manifests
      - SaveBundle data
      - logs and traces
      - caches
      - compiled assets
      - retained artifacts
      - future databases or storage backends

02.06. Persistent I/O centralization exists to preserve:
      - determinism
      - reversibility
      - explicit uncertainty
      - root-boundary control
      - user-trustworthy recovery behavior

02.07. Persistence protects committed state against loss, but it does not
      define committed-state truth [constrained-by: DA-04 08].

02.08. Committed-state authority remains governed by the committed-state
      model [constrained-by: DA-04 03].

02.09. Migration that changes authoritative committed state remains governed
      by the migration commit rule [constrained-by: DA-04 13].

02.10. Same-language or same-process execution does not create persistence
       authority.

02.11. Python pack code, in-process adapter code, frontend adapter code, and
       other adapter-executed code remain subject to IoManager mediation.


===============================================================================
03. AUTHORITY BOUNDARIES
===============================================================================

03.01. DA-07 owns persistent I/O authority and persistence safety.

03.02. DA-04 owns committed-state truth, transaction rules, restoration
      boundaries, and migration commit semantics.

03.03. IoManager persists, protects, restores, and recovers committed-state
      material under DA-07 authority.

03.04. IoManager does not decide whether a value is committed-state truth.

03.05. DA-05 owns payload identity, Chunk, ChunkId, ValueRef, decode,
      integrity representation, and retained-root reachability.

03.06. IoManager may store, retrieve, verify, copy, stream, back up, snapshot,
      restore, and garbage-collect payload material.

03.07. IoManager does not redefine Chunk identity, ValueRef semantics, decode
      semantics, or logical payload identity.

03.08. Physical storage mapping does not redefine logical payload identity.

03.09. DA-06 owns configuration scopes, defaults, override semantics,
      effectiveConfig semantics, schema semantics, and configuration
      migration semantics.

03.10. IoManager persistence success does not make a configuration value
       semantically valid unless the configuration rules accept it.

03.11. DA-08 owns Window ordering and finalization semantics.

03.12. DA-25 owns retained artifact, export, digest, partial export, missing
       material, and offline inspection artifact semantics.

03.13. DA-26 owns comparison, Replay, Resume, and Retry workflow semantics.

03.14. DA-07 may persist, recover, stream, back up, snapshot, restore, and
       copy retained Window-related and artifact-related material.

03.15. Persisting, backing up, snapshotting, restoring, streaming, or copying
       retained material does not change its authority class.

03.16. Storage success does not imply comparison success, Replay success,
       Resume success, or Retry success.

03.17. DA-24 owns OrchestrationUnit lifecycle, terminal outcome, and mutation
       authority.

03.18. DA-27 owns adapter lifecycle, trust, isolation, disconnect, and
       adapter-domain trace semantics.

03.19. DA-28 owns RuntimeHost workspace ownership, command-surface semantics,
       startup modes, and LAN/local-first boundaries.

03.20. Persistence requests may be correlated with Jobs, OrchestrationUnits,
       adapters, ApplicationRuns, RPC, capabilities, Views, RuntimeHost
       operations, services, artifacts, or tools.

03.21. Correlation does not transfer persistence authority.

03.22. Owning lifecycle documents define their own outcomes.

03.23. IoManager failure, refusal, retry, or recovery evidence does not by
       itself define Job, OrchestrationUnit, ApplicationRun, adapter,
       RuntimeHost, Window, Replay, Resume, Retry, or comparison outcome.


===============================================================================
04. CENTRAL AUTHORITY: IOMANAGER (LOCKED)
===============================================================================

04.01. IoManager is the sole authority responsible for persistent I/O.

04.02. IoManager responsibilities include:
      - mediating reads and writes
      - enforcing root boundaries and permissions
      - normalizing and validating storage targets
      - selecting appropriate Readers and Writers
      - classifying errors
      - ensuring trace-visible persistence outcomes
      - providing atomic-write guarantees where required
      - managing backups and snapshots per policy
      - preserving rollback points for identity-bearing mutations

04.03. No other component bypasses IoManager for persistent I/O.

04.04. IoManager does not replace the DA-04 state model.

04.05. IoManager enforces how persistence occurs for state and other persisted
      artifacts.

04.06. IoManager authority does not transfer to adapters, packs, services,
      Views, transports, RuntimeHost surfaces, tools, or Jobs merely because
      they can request persistence.


===============================================================================
05. READERS AND WRITERS (LOCKED CONCEPT)
===============================================================================

05.01. IoManager does not hardcode all persistence formats.

05.02. IoManager delegates concrete format handling to registered providers:
      - Readers
      - Writers

05.03. A Reader loads data from storage under IoManager control.

05.04. A Writer persists data to storage under IoManager control.

05.05. Each Reader or Writer:
      - supports one or more specific kinds
      - declares its supported formats explicitly
      - is registered with IoManager
      - operates strictly within IoManager control
      - executes in the Turnix-controlled backend environment

05.06. Reader / Writer providers refine persistence mechanics.

05.07. Reader / Writer providers do not redefine platform persistence
      authority.

05.08. Reader / Writer providers do not become general backend authority
      surfaces for adapter-executed code.

05.09. Reader / Writer providers do not become persistence authority roots.


===============================================================================
06. RAW ACCESS BOUNDARY (LOCKED)
===============================================================================

06.01. Reader / Writer implementations may internally use:
      - raw filesystem handles
      - platform-native APIs
      - low-level I/O operations

06.02. Raw handles do not escape the Reader / Writer boundary.

06.03. Raw paths do not become part of the calling runtime surface.

06.04. Packs do not receive filesystem handles or unrestricted path APIs.

06.05. Adapter-executed code does not receive filesystem handles or
      unrestricted path APIs as a Turnix persistence authority path.

06.06. Readers return loaded data or streaming views when explicit streaming
      mode allows it.

06.07. Writers accept data or explicit streams to persist under IoManager
      control.

06.08. The raw filesystem remains an internal implementation detail of
      IoManager and its providers.

06.09. Native filesystem APIs are not a Turnix persistence authority path for
      pack-provided code or adapter-executed code.


===============================================================================
07. BUILT-IN AND EXTENDED PROVIDERS (LOCKED POLICY)
===============================================================================

07.01. Turnix core provides built-in persistence kinds required before
      discovery begins.

07.02. Built-in kinds currently include:
      - utf8Text
      - binary
      - json
      - json5
      - jsonl

07.03. These built-in kinds remain available before discovery and indexing.

07.04. Additional kinds may be provided by packs or later platform extensions.

07.05. Extended providers:
      - register with IoManager
      - declare supported kinds explicitly
      - are not usable until the providing pack is activated

07.06. Provider registration is explicit.

07.07. Provider registration is trace-visible.

07.08. Provider registration does not grant broad backend authority.

07.09. Provider registration does not grant capability permission.

07.10. Provider selection remains deterministic and scoped.

07.11. Turnix does not auto-discover or load providers in the middle of a read
       or write operation.

07.12. Early phases use only built-in providers.

07.13. Provider registration through adapter-executed code remains governed by
       activation, adapter, capability, policy, and IoManager boundaries.

07.14. IoManager remains the authority even when a provider implementation is
       pack-provided.


===============================================================================
08. DISCOVERY- AND INDEXING-TIME I/O LIMITS (LOCKED)
===============================================================================

08.01. Discovery and indexing use built-in Readers only.

08.02. During discovery and indexing, Turnix does not use:
      - pack-provided Readers
      - pack-provided Writers
      - compilers
      - transformers
      - streaming I/O

08.03. Early phases remain deterministic, fast, and independent of pack
      activation.

08.04. Discovery remains candidate/root production.

08.05. Discovery does not activate packs.

08.06. Discovery does not load pack-provided persistence providers.

08.07. These limits remain compatible with DA-09 and DA-14.


===============================================================================
09. ROOT PERMISSIONS AND WRITE AUTHORITY (LOCKED)
===============================================================================

09.01. Writable roots at runtime are:
      - userdata/
      - saves/

09.02. Read-only roots at runtime are:
      - custom/
      - first-party/
      - third-party/

09.03. Runtime orchestration enforces these root rules strictly.

09.04. Authoring tools outside runtime orchestration may define broader editing
      behavior, but those behaviors do not weaken runtime rules.

09.05. IoManager enforces root-boundary rules for runtime persistence.

09.06. Root writability does not by itself authorize state mutation.

09.07. State-mutation authority remains constrained by the relevant higher
      design areas.

09.08. Adapter-executed code does not gain write authority merely because a
      root is writable.

09.09. Writable SaveBundle access remains constrained by Application identity,
      ApplicationRun ownership, SaveBundle ownership, and IoManager authority
      rules.

09.10. Concrete workspace locking and writable SaveBundle ownership
       implementation details remain outside this document.


===============================================================================
10. ERROR CLASSIFICATION (LOCKED)
===============================================================================

10.01. Persistent I/O errors are classified into exactly one category:

      A) Unrecoverable
      B) User-decidable
      C) Optional / best-effort

10.02. Unrecoverable errors include failures such as:
      - failure to load required configuration schema material
      - failure to load required default configuration material
      - corruption of identity-bearing state required before minimal recovery
        UI is available

10.03. Unrecoverable errors terminate the affected operation or runtime path as
      fatal.

10.04. User-decidable errors include failures such as:
      - corrupted user configuration
      - missing optional files required for a chosen action
      - version mismatch requiring migration or reset
      - recoverable restore decisions

10.05. User-decidable errors pause normal continuation and require explicit
      recovery flow.

10.06. Optional / best-effort errors include data such as:
      - logs
      - traces
      - caches

10.07. Optional / best-effort failures do not corrupt authoritative state.

10.08. Identity-bearing data never uses silent fallback.

10.09. Optional trace, log, or cache persistence failure does not redefine
      committed-state truth.


===============================================================================
11. ERROR PRESENTATION AND RECOVERY BOOTSTRAP
===============================================================================

11.01. User recovery is mediated through a minimal guaranteed recovery surface.

11.02. Before that recovery surface is available, recovery decisions do not
      occur.

11.03. Failures before minimal recovery availability are fatal for the affected
      boot path.

11.04. This document does not lock the permanent implementation stack of the
      recovery surface.

11.05. The platform guarantee is:
      - a minimal recovery surface becomes available before user-decidable
        recovery is required
      - if that recovery surface is not yet available, the failure is treated
        as unrecoverable in that moment

11.06. This document does not define frontend implementation details for the
      recovery surface.

11.07. This document does not define RuntimeHost command-surface details for
      recovery actions.

11.08. Recovery decisions remain constrained by the policy and user-decision
      documents that own those semantics.


===============================================================================
12. TRACE VISIBILITY OF I/O OUTCOMES (LOCKED)
===============================================================================

12.01. Refused, skipped, failed, retried, recovered, or completed I/O outcomes
      are trace-visible.

12.02. Trace naming, reason naming, event structure, DAG semantics, span
      mechanics, retention, loss, and trace storage semantics remain governed
      by DA-03.

12.03. This document defines the persistence-side obligation to surface I/O
      outcomes to trace.

12.04. This document does not define the full tracing taxonomy.

12.05. Trace-visible I/O outcomes may include adapter, Application,
      ApplicationRun, RPC, capability, Job, OrchestrationUnit, RuntimeHost,
      View, service, tool, or artifact correlation where the persistence
      request came through those mediated surfaces.

12.06. Correlation does not transfer persistence authority.

12.07. Trace evidence remains evidence.

12.08. Trace evidence is not committed state.

12.09. Trace loss does not redefine committed-state truth.


===============================================================================
13. SAVEBUNDLE DATA HANDLING (LOCKED)
===============================================================================

13.01. SaveBundle data is discovered and loaded under the discovery and
      indexing limits already defined by this document and by DA-09.

13.02. SaveBundle-local copied packs or SaveBundle-internal artifacts do not
      become part of initial global indexing merely because they exist in
      SaveBundle data.

13.03. Deeper SaveBundle inspection occurs only when:
      - a SaveBundle is explicitly loaded
      - a management tool explicitly inspects the SaveBundle
      - explicit configuration or policy enables deeper inspection

13.04. SaveBundle-local visibility remains SaveBundle-local unless some other
      authoritative document explicitly states otherwise.

13.05. Writable SaveBundle access remains constrained by Application identity,
      ApplicationRun ownership, SaveBundle ownership, and persistence
      authority rules.

13.06. This document does not define SaveBundle identity, SaveBundle lifecycle,
      Application identity, or ApplicationRun lifecycle.


===============================================================================
14. CONFIGURATION LOADING RELATIONSHIP
===============================================================================

14.01. Configuration loading and persistence use IoManager mediation.

14.02. Configuration-specific semantics are defined by DA-06.

14.03. This document does not redefine configuration scopes, defaults, override
      semantics, effectiveConfig semantics, schema semantics, configuration
      migration semantics, or policy-file top-level structure.

14.04. This document defines only the I/O authority and persistence-safety
      obligations that configuration obeys.

14.05. IoManager may read, write, back up, snapshot, migrate, or recover
      persisted configuration material under DA-07 authority.

14.06. IoManager persistence success does not make configuration semantically
      valid unless DA-06 configuration rules accept it.


===============================================================================
15. MIGRATORS AND ROLLBACK GUARANTEES (LOCKED)
===============================================================================

15.01. Migrators may exist for:
      - configuration
      - manifests
      - SaveBundle structures
      - future persisted artifact classes

15.02. Migrators are versioned and applied sequentially toward a target
      compatibility state.

15.03. Migrators are deterministic and side-effect controlled within their
      defined scope.

15.04. Migrators do not provide inverse operations by themselves.

15.05. Before any identity-bearing mutation is committed, IoManager creates a
      rollback point according to policy.

15.06. Identity-bearing mutations include, but are not limited to:
      - configuration migrations
      - SaveBundle structure changes
      - manager-driven SaveBundle edits
      - multi-file writes that must remain internally consistent

15.07. Rollback safety is provided by IoManager and by the DA-04 commit model,
      not by per-migrator inverse logic.

15.08. Migration that changes authoritative committed state remains constrained
      by DA-04.

15.09. A persistence rollback point does not by itself define committed-state
      truth.


===============================================================================
16. BACKUPS AND SNAPSHOTS (LOCKED CONCEPT)
===============================================================================

16.01. IoManager supports durability mechanisms such as:
      - file backups
      - snapshots

16.02. File backups are suited to small critical files and prior versions.

16.03. Snapshots are suited to logically related multi-file or multi-artifact
      units.

16.04. Policy controls:
      - retention
      - storage location
      - cleanup behavior
      - restoration availability

16.05. Automatic rollback does not occur without explicit policy or
      user-visible consent where such consent is required.

16.06. Backups and snapshots protect recoverability.

16.07. Backups and snapshots do not redefine committed-state truth.

16.08. Backups and snapshots do not make non-authoritative evidence
      authoritative.

16.09. A backup, snapshot, restore, stream, copy, or export operation does not
      change retained material's authority class.


===============================================================================
17. STREAMING I/O (PARTIALLY LOCKED)
===============================================================================

17.01 STREAMING MODE (LOCKED)
-----------------------------

17.01.01. Streaming is an explicit I/O mode for large or long-lived operations.

17.01.02. Streaming read returns a stream or async iterator.

17.01.03. Streaming write accepts a stream and stages output incrementally.

17.01.04. Core streaming rules:
        - streaming is never implicit
        - the caller requests streaming explicitly
        - staging is mandatory for streaming write
        - cancellation remains safe

17.01.05. Non-streaming kinds remain non-streaming unless explicitly extended.


17.02 STREAMING KINDS (LOCKED)
------------------------------

17.02.01. Examples of streaming kinds include:
        - utf8TextStream
        - binaryStream
        - jsonlStream
        - tarStream
        - saveSnapshotStream

17.02.02. Example names do not by themselves lock the full future streaming
        catalog.


17.03 CANCELLATION AND CLEANUP (LOCKED)
---------------------------------------

17.03.01. Streaming read cancellation closes underlying handles safely.

17.03.02. Streaming read cancellation does not create persistence side effects.

17.03.03. Streaming write cancellation does not produce partial valid final
        output.

17.03.04. Final destination update occurs only on commit.

17.03.05. Staging artifacts remain garbage-collectable and cleanup-compatible.


17.04 WHERE STREAMING IS FORBIDDEN (LOCKED)
-------------------------------------------

17.04.01. Streaming is not used for:
        - discovery
        - indexing
        - manifest loading
        - configuration schema loading
        - default configuration loading
        - userdata configuration loading
        - dependency resolution
        - activation-critical reads

17.04.02. These phases require full deterministic materialization rather than
        partial progressive access.

17.04.03. Streaming convenience does not weaken early-phase determinism.


===============================================================================
18. RECOVERY USING BACKUPS AND SNAPSHOTS (LOCKED)
===============================================================================

18.01. When user-decidable persisted data fails to load, IoManager may offer
      recovery actions such as:
      - restore last known good
      - reset to defaults where that concept exists
      - quarantine broken data
      - proceed without the failed data only if explicit policy allows it

18.02. Recovery actions remain UI-mediated or policy-mediated according to the
      governing higher documents.

18.03. Recovery actions remain trace-visible.

18.04. Recovery action availability does not imply that recovery is safe for a
      specific domain unless the owning domain rules allow it.

18.05. Storage recovery success does not define ApplicationRun, Window,
      comparison, Replay, Resume, Retry, Job, OrchestrationUnit, adapter, or
      RuntimeHost outcome.


===============================================================================
19. NO BACKDOORS (LOCKED)
===============================================================================

19.01. Packs do not bypass IoManager.

19.02. Packs do not access arbitrary persistent paths through unrestricted
      runtime APIs.

19.03. Packs do not intercept core persistence flows.

19.04. Persistent I/O authority remains centralized.

19.05. Adapter-executed code does not bypass IoManager.

19.06. Same-language execution does not bypass IoManager.

19.07. Same-process execution does not bypass IoManager.

19.08. Native filesystem APIs are not a Turnix persistence authority path for
      pack-provided code or adapter-executed code.

19.09. Services, capabilities, Views, RPC handlers, Jobs, tools, RuntimeHost
      surfaces, and OrchestrationUnits do not acquire persistence authority
      merely because they can request persistence-related work.

19.10. Direct access to trusted backend internals is not a supported
       persistence contract for pack code or adapter-executed code.

19.11. Physical possibility does not grant IoManager authority.


===============================================================================
20. EXPLICITLY OPEN QUESTIONS
===============================================================================

20.01. OPEN questions include:
      - streaming backpressure API
      - resumable streaming
      - verification hooks such as hashing or limits
      - encrypted storage backends
      - the future boundary between logical addressing and physical storage
        mapping
      - concrete workspace locking implementation details
      - concrete writable SaveBundle ownership implementation details
      - provider implementation mechanics
      - recovery UI implementation
      - concrete filesystem strategy


===============================================================================
21. LOCKED SUMMARY
===============================================================================

21.01. LOCKED:
      - centralized IoManager authority
      - persistent-I/O authority is the role owned by IoManager
      - persistence mediated through IoManager and controlled Reader / Writer
        providers
      - Reader / Writer provider abstraction
      - controlled raw-access boundary
      - strict runtime root permissions
      - adapter-executed code does not bypass IoManager
      - same-language or same-process execution does not bypass IoManager
      - native filesystem APIs are not a Turnix persistence authority path for
        pack-provided or adapter-executed code
      - Reader / Writer providers do not become authority roots
      - provider registration is explicit, scoped, and trace-visible
      - provider registration does not grant capability permission
      - trace-visible I/O outcomes
      - trace evidence is not committed state
      - rollback points before identity-bearing mutations
      - backups and snapshots protect recoverability, not truth
      - UI-mediated or policy-mediated recovery
      - deterministic early phases
      - no silent fallback for identity-bearing data
      - root writability does not itself authorize state mutation
      - writable SaveBundle access remains mediated and ownership-constrained
      - explicit streaming mode and explicit streaming-forbidden phases
      - correlation with runtime surfaces does not transfer persistence
        authority

21.02. OPEN:
      - performance refinements
      - future storage backends
      - future logical-addressing / physical-mapping refinement
      - concrete workspace locking and writable ownership implementation
      - streaming backpressure and resumable streaming
      - verification hooks and encrypted storage
