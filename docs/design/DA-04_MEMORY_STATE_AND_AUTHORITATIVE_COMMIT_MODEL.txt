===============================================================================
DESIGN AREA DA-04 - MEMORY, STATE & AUTHORITATIVE COMMIT MODEL
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines how Turnix distinguishes runtime memory from authoritative state, how
state is layered and mutated, and how committed state changes become
deterministic, restorable, and trace-visible without depending on
observational history.

Purpose:
--------
This document defines the authoritative memory and state model used by Turnix.

It defines:
- what "memory" means in Turnix
- what "state" means in Turnix
- what "committed state" means in Turnix
- authority boundaries between committed and non-committed material
- layer-based runtime memory structure
- transactional staging, promotion, commit, and abort rules
- commit conflict detection for authoritative mutation
- state and transaction trace obligations
- persistence as protection against loss rather than the definition of truth
- static-data mutation intent
- revision and state-retention rules
- migration commit rules for authoritative state mutation
- state-boundary constraints for tooling-initiated mutation
- restoration boundary rules for committed state
- neighboring-domain boundaries for service, capability, ModCallContext, and
  OrchestrationUnit concepts named by this document

It does NOT define:
- tracing structure, trace event schema, or trace storage semantics
  (see DA-03)
- payload identity, ChunkId, or ValueRef representation contracts
  (see DA-05)
- configuration-specific scope, schema, and migration semantics
  (see DA-06)
- concrete persistent I/O authority, Readers, Writers, or filesystem rules
  (see DA-07)
- Window kinds, Window finalization, finalized history, manifests,
  exports, comparison, Replay, Resume, Retry, or workflow reports
  (see DA-08, DA-25, and DA-26)
- Pack activation semantics (see DA-14)
- service, capability, or permission semantics (see DA-16)
- Job lifecycle, Job result, Job timeout, or Job cancellation semantics
  (see DA-19)
- Application or ApplicationRun lifecycle semantics (see DA-20)
- execution adapter boundary or adapter lifecycle semantics
  (see DA-23 and DA-27)
- OrchestrationUnit lifecycle, mutation-authority ownership, terminal
  outcomes, single-lane ApplicationRun orchestration, or
  OrchestrationUnit trace reason ownership (see DA-24)
- debugger pause, breakpoint, or execution-control behavior (see DA-18)
- RuntimeHost lifecycle, workspace ownership, command surfaces, or
  RuntimeHost-domain trace semantics (see DA-28)
- PackManager catalog, graph-preparation, repair, write, or
  PackManager-domain trace semantics (see DA-29)
- ModCallContext gateway semantics or facade shape (see DA-30)
- concrete transaction API shape
- retained revision policy implementation

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines the authoritative memory and state model within
      that shared interpretation model.


===============================================================================
02. CORE CONCEPT AND TERMINOLOGY
===============================================================================

02.01. This design area answers:

          "Which runtime values are authoritative, when do they become
           authoritative, and how does Turnix preserve deterministic
           committed-state evolution?"

02.02. Turnix distinguishes strictly between:
      - runtime memory
      - committed state
      - non-authoritative observational material

02.03. Runtime memory is not authoritative merely because it is resident,
      visible, active, or currently in use.

02.04. Committed state is authoritative only because it has crossed the
      explicit commit boundary defined by this document.

02.05. Turnix preserves deterministic committed-state evolution by making
      authoritative mutation explicit, staged, and commit-bounded.

02.06. Turnix preserves rollback and restoration by ensuring that committed
      state remains restorable without requiring non-authoritative
      historical material.

02.07. Observational material may explain what happened, but it does not
      define the committed truth of the system.

02.08. Turnix does not treat observation as authority.

02.09. Turnix does not require observational completeness for
      committed-state correctness.

02.10. Turnix does not imply determinism outside the committed-state
       boundary defined by this document.

02.11. Trace-visible mutation means that state and transaction domains have
       trace emission obligations.

02.12. Retained trace evidence is not required for committed-state
       correctness.

02.13. Trace evidence does not become committed-state authority.

02.14. This document uses these architecture names:

       ApplicationRun:
       One live execution period of an Application.

       OrchestrationUnit:
       One bounded work and mutation-authority context.

       ModCallContext:
       One invocation-scoped Pack-facing gateway into Turnix.

       SaveBundle:
       The durable persistence closure of an Application.

02.15. Committed state is authoritative state.

02.16. Committed state is data accepted by the relevant commit boundary as
       system truth for its scope.

02.17. Authoritative does not mean useful, correct, complete, or desirable.

02.18. Authoritative means accepted by the owning commit boundary as state
       truth for the relevant scope.

02.19. A later workflow may decide that committed authoritative data
       requires corrective mutation.

02.20. Corrective mutation is a later authoritative mutation.

02.21. Corrective mutation is not a retroactive erasure of the earlier
       committed state.

02.22. A memory transaction is a staged mutation boundary.

02.23. A memory transaction records intended changes before those changes
       become authoritative.

02.24. A memory transaction is the normal mechanism by which mutation of
       Turnix-managed state is staged before it becomes committed state.

02.25. Mutation authority is the authority to initiate, own, or coordinate
       mutation-bearing work.

02.26. Mutation authority does not by itself make mutation authoritative.

02.27. Mutation becomes authoritative only through the DA-04 transaction and
       commit model.

02.28. DA-24 owns OrchestrationUnit mutation-authority coordination.

02.29. DA-04 owns transaction, commit, rollback, promotion, and
       committed-state truth.

02.30. Runtime memory, transactional staging layers, trace, progress, tool
       views, debugger views, UI/View presentation, frontend state, adapter
       state, RuntimeHost command-surface output, PackManager presentation,
       Job lifecycle state, OrchestrationUnit lifecycle state, capability
       invocation records, RPC acknowledgement, diagnostic output, Window
       evidence, journal evidence, retained historical evidence, artifact
       packaging, export packaging, Minimal Audit Bundle material,
       comparison output, Replay reports, Resume attempts, Retry attempts,
       and audit workflow reports are not committed-state authority unless
       their relevant material is committed through the DA-04 commit model.

02.31. Persistence protects committed truth but does not define truth.

02.32. Persistence is storage and recovery support for committed state.

02.33. Persistence does not make uncommitted material authoritative.

02.34. A persisted artifact, log, or record is committed state only when the
       owning domain commits it as authoritative material.

02.35. Trace explains or reports what happened where evidence is retained.

02.36. Trace does not define committed truth.

02.37. Payload representation, effectiveConfig, UI/View presentation,
       debugger views, artifact packaging, export packaging, comparison
       output, Replay reports, Resume attempts, and Retry attempts are not
       committed state unless the relevant material is committed through
       this document.

02.38. DA-16 owns Service, Capability, capability invocation, and permission
       semantics.

02.39. DA-30 owns ModCallContext identity, lifetime, facade shape, and absent
       surfaces.

02.40. DA-04 names Services, Capabilities, capability invocations, and
       ModCallContext only where those concepts affect committed-state
       boundaries.

02.41. A Service, Capability, capability invocation, or ModCallContext does
       not become authoritative state merely because it is active, visible,
       resident, or referenced by runtime memory.

02.42. Later sections of this document refine and apply these rules.

02.43. Later sections of this document do not weaken these rules.


===============================================================================
03. MEMORY, STATE, AND AUTHORITY CLASSES
===============================================================================

03.01. Memory is the runtime representation of values.

03.02. Memory may:
      - exist only in-process
      - include speculative values
      - include staged transactional values
      - include transient runtime-only values

03.03. Memory is mutable.

03.04. Memory is not inherently authoritative.

03.05. State is the authoritative outcome of committed memory.

03.06. State exists independently of runtime residency.

03.07. State is the source of truth for restoration and deterministic
      comparison.

03.08. Committed state is immutable once committed except through a later
      committed revision.

03.09. Memory may exist without persistence.

03.10. Persisted state may exist without current runtime residency.

03.11. Only committed state is authoritative.

03.12. Runtime memory is not treated as authoritative unless it has become
       committed state through the commit rules defined by this document.

03.01 Authority classes
-----------------------

03.01.01. Turnix distinguishes exactly two authority classes:

        A) Authoritative
        B) Non-authoritative

03.01.02. Authoritative material includes:
        - committed memory layers
        - committed configuration
        - committed state captured by a SafePointWindow
        - other committed state governed by the Turnix commit model

03.01.03. Authoritative material defines current system truth.

03.01.04. Authoritative material is sufficient for deterministic restoration
        within the boundaries defined by this document.

03.01.05. Authoritative material is required for correctness.

03.01.06. Non-authoritative material includes:
        - transactional staging layers
        - uncommitted runtime memory
        - debugger staging artifacts
        - traces
        - journals
        - other observational or explanatory material

03.01.07. Non-authoritative material may support:
        - explanation
        - inspection
        - debugging
        - diagnosis

03.01.08. Non-authoritative material is not required for state correctness.

03.01.09. Non-authoritative material does not affect authoritative-state
        equality.

03.01.10. Non-authoritative material may be incomplete, truncated, or
         missing according to explicit policy without changing committed
         state meaning.

03.02 Authority separation rules
--------------------------------

03.02.01. Authoritative state is derivable without requiring access to:
        - traces
        - journals
        - transactional layers
        - debugger-only artifacts

03.02.02. Non-authoritative material is not required to:
        - restore committed state
        - evaluate committed-state equality
        - validate correctness of committed values

03.02.03. Loss of non-authoritative material does not:
        - corrupt committed state
        - change committed meaning
        - invalidate determinism guarantees for committed restoration

03.02.04. This authority separation preserves correctness without turning
        observation into a hidden dependency.

03.02.05. Turnix does not treat traces, journals, or debugger-only artifacts
        as authoritative state.

03.02.06. Turnix does not allow committed-state correctness to depend on
        whether such material is complete, retained, or present.


===============================================================================
04. IDENTITY AND REVISION TERMS
===============================================================================

04.01. A revisionId identifies one committed revision record for one key
      within one committed layer.

04.02. A baseRevisionId identifies the revisionId that a transaction
      observed when it first touched the key by read or write.

04.03. revisionId is a JSON-safe integer.

04.04. revisionId uniqueness and monotonicity are required only per
      (layer, key).

04.05. Clients may treat revisionId as opaque read-only metadata.

04.06. baseRevisionId supports an absent sentinel meaning:
      "the key was not present in the committed layer at capture time."

04.07. The absent sentinel is represented as baseRevisionId = 0.

04.08. The absent sentinel is not represented as null.

04.09. Valid committed revisionId values start at 1.

04.10. Revision metadata supports conflict detection and committed-state
       history.

04.11. Revision metadata does not by itself create authority outside
       committed state.


===============================================================================
05. MEMORY LAYERS
===============================================================================

05.01. Turnix manages runtime memory as a set of layered stores.

05.02. Layers represent:
      - authority
      - scope
      - lifetime
      - rollback boundaries

05.03. There is no single global memory object.

05.04. Each layer contains real values for its own scope.

05.05. Reads resolve according to the active layer stack for the requesting
      scope.

05.06. Example layer kinds include:
      - kernel-global
      - application
      - applicationRun
      - view
      - orchestrationUnit
      - transactional

05.07. Example layer kinds do not lock the complete future layer catalog.

05.08. View-local presentation state remains non-authoritative unless the
      relevant material is committed through this document.

05.09. A committed layer is representable at the commit boundary through the
      committed value representation contract defined elsewhere.

05.10. Layer serialization preserves committed value meaning rather than
       live runtime object identity.

05.11. Runtime residency is an implementation detail and does not change the
       meaning of a committed layer.

05.12. Layering defines visibility, rollback, and mutation boundaries.

05.13. Layering does not blur the distinction between committed and
       non-committed material.


===============================================================================
06. TRANSACTIONS
===============================================================================

06.01. A transaction is a temporary staging overlay used to record
      speculative mutations before they become authoritative.

06.02. A transaction overlays one or more parent layers.

06.03. A transaction captures all writes during its lifetime.

06.04. A transaction may read from parent layers.

06.05. A transaction is resolved only by commit or abort.

06.06. Primary transaction use includes:
      - ProcessingRun execution
      - capability calls with mutation
      - adapter-mediated capability calls with mutation
      - adapter-executed orchestrated mutation
      - tooling-initiated staged mutation
      - other orchestrated speculative work

06.07. A transaction is not authoritative merely because it contains staged
      values.

06.08. Staged mutation does not become committed truth until commit into an
      authoritative boundary occurs under the rules of this document.

06.09. A transaction may be opened or entered by an owning workflow that
      coordinates mutation-bearing work.

06.10. An owning workflow may include a Job, OrchestrationUnit,
       ProcessingPipeline, ProcessingRun, Pack lifecycle callback,
       capability handler, tooling operation, or other workflow where the
       relevant owning document permits mutation-bearing work.

06.11. An owning workflow commit may promote staged mutation to a parent
       transaction rather than to permanent committed state.

06.12. An owning workflow abort discards that workflow's staged mutation and
       may propagate failure or rollback information to the parent workflow.

06.13. A parent workflow may decide to continue, recover, abort, or
       propagate rollback only where the owning workflow semantics permit
       that decision.

06.14. Permanent committed state is reached only when the top relevant commit
       boundary accepts the mutation into committed layers.

06.15. OrchestrationUnit lifecycle, mutation authority, and single-lane
       ApplicationRun orchestration are defined by DA-24.

06.01 Commit and abort
----------------------

06.01.01. A transaction ends in exactly one outcome:
        - commit
        - abort

06.01.02. Partial propagation does not occur.

06.01.03. Commit is atomic.

06.01.04. Abort is atomic.

06.01.05. Commit and abort outcomes are trace-visible.

06.01.06. Commit and abort preserve rollback guarantees.

06.01.07. On commit, staged values propagate to the target authoritative
        layer or to a parent transaction according to nesting rules.

06.01.08. On abort, all staged mutations are discarded deterministically.

06.01.09. A transaction does not remain in an unresolved half-committed
        state.

06.01.10. Commit does not silently drop part of staged mutation.

06.01.11. Abort does not silently preserve part of staged mutation.

06.01.12. A transaction commit does not directly finalize a
         SafePointWindow.

06.01.13. A transaction abort does not directly finalize an AbortedWindow.

06.02 Nested transaction stacking
---------------------------------

06.02.01. If orchestrated work creates or enters a child transaction while an
        enclosing transaction is active, the child transaction inherits the
        enclosing transactional view.

06.02.02. Reads resolve first-match from the child transaction downward
        through the inherited stack.

06.02.03. Writes target the child transaction.

06.02.04. Committing the child transaction propagates its writes into the
        parent transaction.

06.02.05. No child transaction commits directly into committed layers while an
        enclosing transaction exists.

06.02.06. Only the outermost transaction commit mutates committed layers.

06.02.07. This stacking rule prevents lost updates and desynchronization
        across nested orchestrated activity.

06.02.08. Nested transactional propagation is not itself authoritative
        mutation into committed state.

06.02.09. Transactional propagation to a parent transaction is promotion of
        staged mutation.

06.02.10. Transactional promotion does not guarantee that the promoted
         mutation will become permanent committed state.

06.02.11. A parent transaction may later commit or abort according to the
         same transaction rules.

06.02.12. If the parent transaction aborts, mutation promoted from a child
         transaction is discarded with the parent transaction's staged
         mutation.

06.02.13. Nested transaction stacking permits long-running work to accumulate
         provisional state without making that state permanent before the
         owning top-level workflow succeeds.

06.02.14. An encounter, workflow, or other long-running owning workflow may
         stage internal progress for its duration and commit it to durable
         world state only when the owning top-level commit boundary succeeds.

06.02.15. If the owning top-level workflow fails, aborts, times out, or
         rejects its result, staged mutation from child workflows does not
         become permanent committed state.

06.03 Commit into committed layers and conflict detection
---------------------------------------------------------

06.03.01. Commit conflict detection applies only when a transaction attempts
        to commit into committed layers.

06.03.02. A transaction records, per touched key, the committed base revision
        state visible when the key was first read or first written.

06.03.03. The recorded base state includes:
        - whether the key existed in the committed layer at capture time
        - which committed revisionId the key had if it existed

06.03.04. If the key did not exist at capture time, baseRevisionId is the
        absent sentinel.

06.03.05. If the key existed at capture time, baseRevisionId equals the
        committed key's current revisionId at that time.

06.03.06. When committing into committed layers, the commit is in conflict if
        the recorded existence state differs from the committed layer's
        current existence state.

06.03.07. When committing into committed layers, the commit is in conflict if
        the recorded committed revisionId differs from the committed layer's
        current revisionId.

06.03.08. A conflicting commit fails deterministically.

06.03.09. Silent merge does not occur.

06.03.10. Last-write-wins behavior does not occur.

06.03.11. Heuristic reconciliation does not occur.

06.03.12. Any override requires explicit user decision or explicit policy
         defined elsewhere.

06.03.13. Conflict detection is not applied to child-transaction propagation
         into a parent transaction, because that propagation is not yet an
         authoritative mutation.

06.03.14. Turnix does not silently reconcile conflicting authoritative
         mutation.

06.03.15. Turnix does not silently change conflict meaning through fallback,
         guesswork, or convenience behavior.


===============================================================================
07. STATE AND TRANSACTION TRACE OBLIGATIONS
===============================================================================

07.01. Authoritative state mutation remains trace-visible.

07.02. Transaction commit and abort outcomes remain trace-visible.

07.03. State and transaction trace obligations are emission obligations.

07.04. Trace retention and trace loss are governed by DA-03.

07.05. Loss of trace evidence affects evidential completeness.

07.06. Loss of trace evidence does not affect committed-state correctness.

07.07. Trace evidence does not become committed-state authority.

07.08. State trace evidence distinguishes:
      - staged mutation
      - promoted staged mutation
      - committed mutation
      - aborted staged mutation
      - computed or runtime-only effect

07.09. Computed or runtime-only effects do not appear as committed
      mutations.

07.10. For any committed mutation of a memory key, Turnix has a state trace
       emission obligation with at least:
       - mutationKind
       - applicationRunId
       - memoryLayerId
       - memory key identity
       - baseRevisionId
       - newRevisionId
       - debuggerInitiated
       - transactionId when mutation was committed through a transaction
       - orchestrationUnitId when applicable
       - jobId when applicable

07.11. When retained trace evidence is unavailable, Turnix may reconstruct
       an explanatory representation from retained authoritative state and
       retained metadata where possible.

07.12. Reconstructed explanatory representation does not weaken the state
       trace emission obligation.

07.13. baseRevisionId follows the absent-sentinel and revision rules
       defined in section 04.

07.14. Mutation trace evidence is causally linked to:
       - the transaction commit event when a transaction commits the
         mutation
       - the owning OrchestrationUnit when such ownership exists
       - the owning Job when such ownership exists
       - the owning trace span when such a span exists

07.15. Abort trace evidence does not imply committed mutation.

07.16. Commit trace evidence does not by itself define Window finalization.

07.17. Transaction trace evidence records enough context, when available,
       to explain:
       - transactionId
       - applicationRunId
       - orchestrationUnitId when applicable
       - jobId when applicable
       - affected committed layers when allowed
       - affected keys or scopes when allowed
       - base revision information when relevant
       - new revision information when relevant
       - abort reason when the transaction aborts

07.18. DA-03 defines the tracing substrate used to represent state and
       transaction trace evidence.

07.19. DA-24 defines OrchestrationUnit lifecycle trace reason ownership.


===============================================================================
08. RELATION TO ORCHESTRATIONUNIT
===============================================================================

08.01. DA-24 defines OrchestrationUnit as a kernel-tracked bounded
      execution and mutation-authority context.

08.02. This document defines the transaction, staging, promotion,
      conflict-detection, commit, and restoration boundaries consumed by
      OrchestrationUnit.

08.03. An OrchestrationUnit does not make staged mutation authoritative by
      existing.

08.04. An OrchestrationUnit may open, commit, or abort transactions only
      under the transaction rules defined by this document.

08.05. OrchestrationUnit terminal outcomes are defined by DA-24.

08.06. OrchestrationUnit terminal outcome does not by itself define
      transaction commit or abort.

08.07. Transaction commit or abort does not by itself define
      OrchestrationUnit terminal outcome.

08.08. Adapter-executed mutation seeking Turnix guarantees re-enters through
      OrchestrationUnit, capability, transaction, and commit boundaries
      before becoming authoritative.

08.09. Same-language or same-process execution does not bypass
      committed-state authority.

08.10. Single-lane ApplicationRun mutation orchestration is defined by
       DA-24.

08.11. Mutation authority is the authority to coordinate mutation-bearing
       work.

08.12. Mutation authority is not direct committed-state authority.

08.13. Mutation authority remains constrained by the transaction, promotion,
       commit, and abort rules defined by this document.

08.14. OrchestrationUnit authority may coordinate a mutation flow without
       causing every child transaction commit to become permanent committed
       state.

08.15. A mutation-bearing OrchestrationUnit may receive rollback, abort, or
       failure information from nested work and decide its own outcome only
       under DA-24 semantics.

08.16. If OrchestrationUnit-coordinated work commits a child transaction to a
       parent transaction, that child commit is staged promotion rather than
       permanent committed-state mutation.

08.17. If the outer transaction aborts, staged mutation coordinated by the
       OrchestrationUnit does not become committed state.


===============================================================================
09. PERSISTENCE AS PROTECTION, NOT TRUTH
===============================================================================

09.01. Persistence protects committed state against loss.

09.02. Persistence does not define what state truth is.

09.03. Committed state truth is determined by the commit model defined by
      this document.

09.04. Any committed value may be persisted.

09.05. Persistence of committed state occurs under Turnix authority.

09.06. Persistence ordering is controlled by Turnix.

09.07. Persistence failure is trace-visible.

09.08. Persistence does not imply:
      - immediate disk residency
      - continuous in-memory residency
      - unlimited retention

09.09. This section defines the state-model meaning of persistence only.

09.10. This section does not redefine the separate persistent I/O authority
       defined elsewhere.

09.11. Persistence failure does not silently redefine committed-state truth.

09.12. Persistence exists to protect committed state, not to decide whether
       committed state exists.

09.13. SaveBundle/persistence authority does not make adapters SaveBundle
       writers or persistence writers.

09.14. Persistence remains protection for committed state, not
       adapter-owned authority.

09.15. Persistent storage of runtime material does not make that material
       authoritative unless the relevant material crossed the commit
       boundary defined by this document.

09.16. A persisted log, artifact, record, or diagnostic item may be
       committed state only when its owning domain commits that material as
       authoritative state for its scope.

09.17. Material may be committed and authoritative even when later workflow
       determines that the material is incomplete, malformed, undesirable, or
       no longer useful.

09.18. A later correction to committed material is a later committed
       mutation.

09.19. A later correction does not mean the earlier committed material was
       never committed.


===============================================================================
10. STATIC DATA AND MUTATION INTENT
===============================================================================

10.01. Static data is data provided by:
      - packs
      - configuration defaults
      - bundled resources

10.02. Static data is read-only by default.

10.03. When a mutation is attempted on static data, the intended mutation
      mode is explicit.

10.04. Turnix recognizes exactly two mutation-intent modes for static data:

      A) Patch
      B) Copy

10.05. In Patch mode:
      - the original key remains authoritative
      - a patch is applied on each read
      - the patch is persisted as overlay data

10.06. In Copy mode:
      - a new key is created
      - data is copied and modified
      - the original remains unchanged

10.07. Static-data mutation intent may require explicit user decision or
      policy handling defined elsewhere.

10.08. Static-data mutation intent remains visible and explainable after the
      fact.

10.09. Static data does not become freely mutable merely because a runtime
      actor wants to modify it.

10.10. Turnix does not silently substitute Patch for Copy or Copy for Patch.


===============================================================================
11. REVISIONS AND STATE GARBAGE COLLECTION
===============================================================================

11.01. Committed state values may have revisions.

11.02. Revisions support:
      - rollback
      - inspection
      - debugging
      - committed-state history

11.03. Revision retention is policy-driven.

11.04. State garbage collection may remove:
      - older revisions
      - unreachable historical committed states

11.05. State garbage collection does not remove data required to reconstruct
      the latest committed state for each committed key.

11.06. State garbage collection does not occur silently.

11.07. State garbage collection does not violate rollback guarantees that the
      retained policy still claims to preserve.

11.08. Removal of older revisions may make older committed value
      representations unreachable.

11.09. Historical removal does not invalidate the ability to restore the
      latest retained committed state.

11.10. Turnix does not silently discard material that retained-policy
       guarantees still depend on.

11.11. Retention policy may bound history.

11.12. Retention policy does not silently rewrite current committed truth.


===============================================================================
12. TOOLING-INITIATED STATE MUTATION CONSTRAINTS
===============================================================================

12.01. Tooling may inspect Turnix-managed memory and committed state through
      appropriate controlled surfaces.

12.02. Tooling-initiated edits occur inside a transaction.

12.03. Tooling-created transactions follow the same commit or abort rules as
      runtime transactions.

12.04. Tooling commits propagate according to normal transaction-layer rules.

12.05. Tooling actions do not finalize committed state in the middle of
      active orchestrated work merely because the tooling surface exists.

12.06. Tooling-originated state mutation is labeled distinctly in trace.

12.07. This document defines only the state-contract constraints for
      tooling-initiated mutation.

12.08. Breakpoints, pausing, step control, and debugger execution behavior
      are defined elsewhere.

12.09. Tooling does not bypass normal authority boundaries merely because it
      is privileged tooling.

12.10. Tooling-originated mutation does not become committed truth except
       through the same commit model that governs runtime mutation.

12.11. Tooling through frontend, debugger, CLI, or other adapters still
       obeys the same transaction and commit model.

12.12. Adapter-mediated tooling presentation does not grant tooling a
       separate committed-state authority path.

12.13. Tooling-originated child transactions promote only to parent
       transactions when an enclosing transaction exists.

12.14. Tooling-originated mutation does not become permanent committed state
       merely because a tooling surface commits a nested transaction.


===============================================================================
13. COMMITTED-STATE RESTORATION BOUNDARY
===============================================================================

13.01. Turnix supports deterministic restoration of committed state.

13.02. Deterministic restoration means that committed state can be restored
      from retained authoritative material without requiring
      non-authoritative historical material.

13.03. Deterministic restoration does not imply deterministic reconstruction
      of in-flight runtime activity that never became committed.

13.04. Deterministic restoration does not imply deterministic replay of
      external side effects.

13.05. Restoration of committed state is authoritative.

13.06. Any later resumed or retried work after restoration is new work and is
      not retroactively part of the earlier committed mutation.

13.07. Later workflow concepts such as Replay, Resume, and Retry remain
      constrained by the restoration boundary defined in this section.

13.08. This document defines the restoration boundary only.

13.09. This document does not define the full workflow semantics of Replay,
      Resume, or Retry.

13.10. Turnix does not imply that uncommitted activity becomes reproducible
       merely because committed state is restorable.

13.11. Turnix does not imply that external effects are reversible,
       replayable, or reconstructible merely because committed state can be
       restored.

13.12. DA-26 defines Replay, Resume, Retry, comparison, and workflow
       semantics that consume this restoration boundary.

13.13. Restored committed state includes only material that crossed the
       relevant commit boundary before restoration.

13.14. Staged child transaction material that never reached the top relevant
       commit boundary is not restored as committed state.

13.15. Restoration does not convert abandoned, aborted, failed, or timed-out
       staged mutation into committed state.


===============================================================================
14. MIGRATION COMMIT RULE
===============================================================================

14.01. Migration that changes authoritative committed state occurs as normal
      orchestrated work inside a transaction.

14.02. Migration that changes authoritative committed state results in a new
      committed state boundary on success.

14.03. Migration is abortable.

14.04. If migration aborts, partial authoritative mutation does not occur.

14.05. If one migration operation attempts multiple authoritative changes,
      the migration transaction is atomic with respect to the affected
      committed layers.

14.06. If migration cannot complete safely, it aborts and authoritative
      state remains identical to the pre-migration committed state.

14.07. Migration does not bypass the normal commit boundary.

14.08. Migration does not acquire permission to perform partial
      authoritative mutation merely because it is migration work.

14.09. Migration may use nested transactions where the owning migration
      workflow requires staged sub-work.

14.10. A nested migration transaction commit promotes staged mutation to its
       parent transaction.

14.11. A nested migration transaction commit does not become authoritative
       committed state until the top relevant migration transaction commits
       into committed layers.


===============================================================================
15. NEIGHBORING DOMAIN AUTHORITY BOUNDARY
===============================================================================

15.01. This document may name neighboring domains only to protect
      committed-state authority.

15.02. This document does not define detailed behavior for neighboring
      domains.

15.03. Trace material is evidence.

15.04. Trace material does not become committed state.

15.05. Trace retention and trace loss are defined outside this document.

15.06. Payload representation, configuration materialization, persistent I/O,
      and SaveBundle storage support committed-state restoration only where
      their retained material is referenced by committed state.

15.07. Payload representation, configuration materialization, persistent I/O,
      and SaveBundle storage do not define committed-state truth.

15.08. Finalized history, Window evidence, journal evidence, artifacts,
      exports, comparison output, Replay reports, Resume attempts, Retry
      attempts, and workflow reports do not add committed-state authority by
      being retained, packaged, displayed, or compared.

15.09. Tooling, debugger, RuntimeHost, ExecutionAdapter, and PackManager
      surfaces may request, inspect, stage, present, or coordinate work only
      through their own controlled boundaries.

15.10. Tooling, debugger, RuntimeHost, ExecutionAdapter, and PackManager
       surfaces do not directly mutate committed state by existing.

15.11. Job lifecycle state is not committed state.

15.12. OrchestrationUnit lifecycle state is not committed state.

15.13. Job result payloads become authoritative only if their relevant
       material is committed through the owning state or transaction domain.

15.14. OrchestrationUnit coordinates mutation flow but does not bypass the
       commit boundary defined by this document.

15.15. ModCallContext, capability invocation records, and RPC
       acknowledgements do not expose or create unrestricted
       committed-state mutation authority.

15.16. ModCallContext is the Pack-facing invocation gateway defined by
       DA-30.

15.17. Capability invocation is the mediated operation request model defined
       by DA-16.

15.18. Services are runtime wiring objects defined by DA-16.

15.19. A Service is not committed-state authority.

15.20. A Capability is not committed-state authority.

15.21. A capability invocation is not committed-state authority.

15.22. ModCallContext is not committed-state authority.

15.23. A capability implementation may use a Service internally without
       exposing the backing Service object as committed-state authority.

15.24. Pack code may request memory reads or mutations through
       ModCallContext only when the current invocation has the required
       state authority.

15.25. A Pack-facing save request stages mutation through the transaction
       model defined by this document.

15.26. A Pack-facing save request does not bypass parent transaction,
       workflow, OrchestrationUnit, policy, permission, persistence, or
       commit boundaries.

15.27. Neighboring documents own the detailed lifecycle, representation,
       persistence, workflow, adapter, host, tooling, capability, and RPC
       semantics for their domains.

15.28. This document owns the committed-state authority boundary those
       neighboring domains must not bypass.


===============================================================================
16. WHAT IS EXPLICITLY NOT REQUIRED
===============================================================================

16.01. Turnix does not require:
      - infinite committed history retention
      - journal-backed determinism
      - journal-backed recovery
      - trace-backed correctness
      - concurrency-first execution
      - deterministic reconstruction of uncommitted runtime activity

16.02. Turnix does not imply determinism where determinism does not exist.

16.03. Turnix does not treat observational completeness as a requirement for
      committed-state correctness.

16.04. Turnix does not require non-authoritative history to remain complete in
      order for committed state to remain authoritative.

16.05. Turnix does not require hidden fallback, reconciliation, or
      observational reconstruction in order to preserve committed-state
      correctness.

16.06. This document does not define:
      - exact concrete transaction API shape
      - exact transaction trace payload taxonomy
      - exact retained revision policy shape
      - exact payload representation format
      - exact configuration schema
      - exact persistent I/O provider implementation
      - exact SaveBundle storage format
      - exact artifact or export format
      - exact comparison algorithm
      - exact Replay, Resume, or Retry workflow protocol
      - exact ModCallContext facade shape


===============================================================================
17. LOCKED SUMMARY
===============================================================================

17.01. LOCKED:
      - runtime memory and committed state are distinct
      - only committed state is authoritative
      - authoritative does not mean useful, correct, complete, or desirable
      - committed means accepted by the owning commit boundary as state truth
        for the relevant scope
      - authoritative and non-authoritative material remain separate
      - memory is layered by authority, scope, lifetime, and rollback
        boundary
      - transactions stage speculative mutation and end only in atomic
        commit or atomic abort
      - transaction commit does not directly finalize a SafePointWindow
      - transaction abort does not directly finalize an AbortedWindow
      - nested transaction stacking prevents child authoritative commits
        while an enclosing transaction exists
      - child transaction commit promotes staged mutation to a parent
        transaction
      - promotion to a parent transaction is not permanent committed state
      - only the outermost transaction commit mutates committed layers
      - conflict detection applies when committing into committed layers
      - state and transaction trace obligations are emission obligations
      - trace retention and loss are governed by DA-03
      - trace evidence does not become committed-state authority
      - OrchestrationUnit lifecycle, mutation-authority ownership,
        terminal outcomes, single-lane ApplicationRun orchestration, and
        OrchestrationUnit trace reason ownership are defined by DA-24
      - mutation authority does not by itself create committed-state
        authority
      - OrchestrationUnit existence does not make staged mutation
        authoritative
      - OrchestrationUnit outcome does not by itself define transaction
        outcome
      - transaction commit or abort does not by itself define
        OrchestrationUnit outcome
      - adapter-executed mutation seeking Turnix guarantees re-enters
        through orchestration, transaction, and commit boundaries
      - same-language or same-process execution does not bypass
        committed-state authority
      - persistence protects state against loss but does not define truth
      - persistence does not make uncommitted material authoritative
      - SaveBundle/persistence authority does not make adapters
        SaveBundle writers or persistence writers
      - static-data mutation intent is explicit as Patch or Copy
      - revision retention is policy-driven and does not invalidate latest
        committed-state restoration
      - tooling-initiated mutation obeys the normal transaction model
      - committed-state restoration is deterministic only within the
        committed-state boundary
      - migration that changes authoritative state is transactional and
        abortable
      - DA-16 owns Service, Capability, capability invocation, and
        permission semantics
      - DA-30 owns ModCallContext identity, lifetime, facade shape, and
        absent surfaces
      - Service, Capability, capability invocation, and ModCallContext do
        not become committed-state authority merely by existing

17.02. OPEN:
      - exact concrete transaction API shape
      - exact transaction trace payload taxonomy
      - exact retained revision policy shape
      - exact complete memory-layer catalog
