===============================================================================
DESIGN AREA DA-23 - EXECUTION BOUNDARIES, ADAPTERS & CODE RUNTIMES
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines the Turnix execution boundary for declared Pack code, the abstract role
of ExecutionAdapters, code artifact recognition and activation-entry
boundaries, ModCallContext authority, mechanical loading boundaries, and the
RPC-shaped boundary through which adapter-executed code participates in an
ApplicationRun.

This document owns the abstract execution-boundary authority model. Adapter
lifecycle, trust, isolation, concrete adapter classes, and adapter-domain trace
reason identifiers are defined by DA-27. RuntimeHost identity, Workspace
ownership, startup modes, entry surfaces, and command-surface semantics are
defined by DA-28. ModCallContext invocation-gateway details are defined by
DA-30. Activation lifecycle semantics are defined by DA-14. PackManager graph
preparation and activation-plan preparation are defined by DA-29.

Purpose:
--------
This document defines how Turnix treats executable Pack code across host
languages and runtime environments without allowing host-language convenience,
process location, runtime host entry surfaces, frontend placement, deployment
shape, loader behavior, or adapter implementation details to bypass Kernel
authority.

It defines:
- Kernel authority over adapter-executed code participation
- ExecutionAdapter meaning at the abstract boundary level
- code artifact recognition, declaration, binding, permission, activation,
  and execution phases
- executable artifact declaration requirements
- activation-entry, private-module, and exported-module boundary meaning
- mechanical loading and adapter artifact loading boundaries
- Pack-provided code versus backend implementation code
- ModCallContext authority and limits at the DA-23 boundary level
- RPC-shaped execution boundary semantics
- relationship between adapters and transports
- relationship to AppPack, Application, ApplicationRun, SaveBundle, and
  RuntimeHost
- relationship to activation, activation plans, imports, capabilities,
  decisions, Jobs, Views, OrchestrationUnits, RuntimeHost, and runtime state
- direct-call transport optimization boundaries

It does NOT define:
- generic resolution mechanics (see DA-11)
- importing and module-loading selector details (see DA-12)
- activation lifecycle beyond execution-boundary constraints (see DA-14)
- multi-adapter phase barriers or cyclic activation group semantics
  (see DA-14)
- PackManager graph preparation or activation-plan preparation (see DA-29)
- concrete manifest field syntax or declaration schema
- capability permission semantics (see DA-16)
- user decision and remembered policy semantics (see DA-17)
- Job lifecycle, timeout, cancellation, or progress semantics (see DA-19)
- Application lifecycle or ApplicationRun identity semantics (see DA-20)
- abstract RPC, channel, and transport semantics (see DA-21)
- UI, View, and frontend runtime presentation semantics (see DA-22)
- OrchestrationUnit lifecycle or mutation authority semantics (see DA-24)
- Window artifact, export, comparison, Replay, Resume, Retry, or offline
  inspection workflow semantics (see DA-25 and DA-26)
- adapter lifecycle, adapter trust and isolation, concrete adapter classes, or
  adapter-domain trace reason identifiers (see DA-27)
- RuntimeHost identity, Workspace ownership, startup modes, entry surfaces,
  command-surface semantics, or runtime-host trace reason identifiers
  (see DA-28)
- ModCallContext facade shape, absent surfaces, retention rules, or detailed
  invocation-gateway semantics (see DA-30)
- concrete RPC message schema (see IS-01)
- concrete WebSocket flow (see IS-02)
- concrete Python adapter implementation
- concrete JavaScript loader implementation
- concrete CLI command syntax
- concrete Workspace locking implementation

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.1. This document expresses normative meaning through explicit,
      deterministic prose.

01.2. Normative meaning in Turnix derives from sentence structure and
      document context rather than from RFC-style keywords.

01.3. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.4. This document defines execution-boundary, adapter, and code-runtime
      authority semantics within that shared interpretation model.

01.5. This document uses canonical architecture type names for:
      - Application
      - ApplicationRun
      - SaveBundle
      - ExecutionAdapter
      - ModCallContext
      - OrchestrationUnit
      - RuntimeHost
      - View

01.6. A term not used by this document does not gain alias status inside this
      document merely because another source once used it.

01.7. "Activation entry" is the canonical lifecycle-participation term used by
      this document.

01.8. "Adapter entry" is not a separate platform concept in this document.

01.9. When "adapter entry" appears informally, it means the activation entry
      for one declared adapter/runtime participation.

01.10. "Pack entry" is not a canonical lifecycle term in this document.

01.11. "Mechanical loading" means loading or evaluating a requested artifact,
       module, or activation entry through an applicable adapter or loader
       path.

01.12. Mechanical loading does not imply graph preparation, activation-plan
       preparation, dependency readiness, cyclic activation admission, or final
       Activated state.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.1. This design area answers:

          "How does Turnix execute declared Pack code without allowing host
           language, process location, transport choice, runtime host entry
           surface, frontend convenience, deployment shape, loader behavior,
           or adapter implementation detail to bypass Kernel authority?"

02.2. Kernel owns authority.

02.3. ExecutionAdapters execute declared Pack code.

02.4. Transports carry messages.

02.5. RPC defines the logical communication boundary.

02.6. Capabilities define what adapter-executed code may do.

02.7. Memory owns authoritative state and transaction semantics.

02.8. Transactions provide staged mutation boundaries before commit.

02.9. SaveBundle persistence is reached through Kernel-mediated paths and
      remains constrained by Memory, Transaction, IoManager, ApplicationRun,
      and SaveBundle ownership rules.

02.10. RuntimeHost exposes controlled entry surfaces under DA-28.

02.11. The host language used by Pack code does not grant backend authority.

02.12. Pack-provided Python is not backend implementation code merely because
       Turnix backend implementation is Python.

02.13. Pack-provided JavaScript is not frontend authority merely because it
       runs in a browser.

02.14. Pack code participates in an ApplicationRun only through
       Turnix-managed context, capability, RPC-shaped, lifecycle, policy,
       trace, and state boundaries.

02.15. Pack code does not acquire RuntimeHost control authority merely because
       a RuntimeHost entry surface, CLI surface, frontend surface, or LAN
       surface exists.

02.16. Direct calls may be used as a transport or dispatch optimization.

02.17. Direct backend authority is not a valid authority path for Pack code.

02.18. Adapter-executed code that touches committed values, configuration,
       persistent I/O, SaveBundle material, or direct-call mutation paths
       remains constrained by the documents that own those domains.

02.19. Adapter-executed work may contribute retained evidence used by artifact,
       export, comparison, Replay, Resume, Retry, or inspection workflows.

02.20. Adapter-executed work does not define the authority of those retained
       artifacts or workflows.

02.21. ExecutionAdapter loading does not define dependency order.

02.22. ExecutionAdapter loading does not define activation order.

02.23. ExecutionAdapter loading does not define activation-plan correctness.

02.24. Later sections refine and apply these rules. They do not weaken them.


===============================================================================
03. KERNEL AUTHORITY BOUNDARY
===============================================================================

03.1. Kernel is the trusted Turnix authority owner.

03.2. Kernel owns:
      - platform authority
      - ApplicationRun lifecycle coordination
      - orchestration entry boundaries
      - authoritative state mutation boundaries
      - SaveBundle persistence coordination
      - capability routing
      - policy decision application
      - permission enforcement
      - trace substrate participation
      - adapter boundary translation

03.3. Kernel authority is not delegated merely because code runs in the same
      process.

03.4. Kernel authority is not delegated merely because code runs in the same
      language.

03.5. Kernel authority is not delegated merely because a transport is
      in-process.

03.6. Kernel authority is not delegated merely because a frontend can send a
      message.

03.7. Kernel authority is not delegated merely because a RuntimeHost entry
      surface can send a command.

03.8. Kernel authority is not delegated merely because a Pack declares code.

03.9. Kernel authority is not delegated merely because an ExecutionAdapter can
      load or evaluate Pack code.

03.10. Kernel authority is not delegated merely because an activation plan
       names a Pack, adapter, or activation entry.

03.11. Kernel may expose authority through capabilities, policies, and
       Turnix-controlled contexts.

03.12. Exposed authority remains scoped by the capability, policy, context,
       ApplicationRun, SaveBundle, RuntimeHost, and lifecycle boundaries that
       grant it.


===============================================================================
04. EXECUTIONADAPTER
===============================================================================

04.1. An ExecutionAdapter is a Turnix-managed environment capable of loading
      and executing declared Pack code.

04.2. An ExecutionAdapter is a boundary participant, not authority by itself.

04.3. An ExecutionAdapter may run code:
      - in the browser
      - in the backend process
      - in another process
      - over a local socket or pipe
      - over a LAN transport
      - inside a container or virtual machine
      - through another explicitly defined runtime environment

04.4. Execution location does not define authority.

04.5. RuntimeHost deployment location does not define adapter authority.

04.6. Adapter mediation does not imply sandboxing.

04.7. Adapter sandboxing, trust classification, lifecycle, concrete adapter
      classes, and adapter trace reason ownership are defined by DA-27.

04.8. RuntimeHost identity, Workspace ownership, startup modes, entry surfaces,
      and command-surface semantics are defined by DA-28.

04.9. The minimum abstract adapter role is to:
      - load declared executable artifacts
      - execute code through declared lifecycle entrypoints
      - provide a Turnix-controlled context to Pack code
      - communicate with Kernel through an RPC-shaped boundary
      - report structured result, error, readiness, and failure information
      - preserve trace correlation metadata where available
      - remain subordinate to capability and permission boundaries

04.10. An adapter does not own authoritative persistent state unless a later
       authoritative document defines an explicit delegated state authority.

04.11. An adapter does not become Kernel authority because it is trusted.

04.12. An adapter does not become Kernel authority because it is in-process.

04.13. An adapter does not become Kernel authority because its transport is
       direct.

04.14. An adapter does not become RuntimeHost authority because it is attached
       to a RuntimeHost-owned ApplicationRun or entry surface.

04.15. An adapter does not become PackManager authority because it loads
       artifacts named by an accepted activation plan.

04.16. An adapter does not prepare selected pack graphs by loading Pack code.

04.17. An adapter does not prepare activation plans by loading Pack code.

04.18. An adapter does not decide cyclic activation admission by loading Pack
       code.


===============================================================================
05. CODE ARTIFACT PHASES
===============================================================================

05.1. Recognizing a file as code is not permission to execute it.

05.2. Turnix separates executable code handling into these phases:
      - recognition
      - declaration
      - binding
      - permission
      - activation
      - execution

05.3. Recognition means Turnix identifies a file or manifest entry as a code
      artifact.

05.4. Declaration means Pack metadata identifies code material as executable
      and states its intended role.

05.5. Binding means Turnix determines which adapter kind or adapter provider
      can execute the declared artifact.

05.6. Permission means Turnix determines whether the declared artifact may be
      executed in the current Pack, ApplicationRun, SaveBundle, trust, policy,
      and user-decision context.

05.7. Activation means Turnix dispatches a declared lifecycle entrypoint
      through the selected adapter under DA-14 activation semantics.

05.8. Execution means adapter-executed code runs within the Turnix context and
      boundary provided for that activation or operation.

05.9. No phase silently implies a later phase.

05.10. Recognition does not imply declaration.

05.11. Declaration does not imply binding success.

05.12. Binding does not imply execution permission.

05.13. Permission does not imply activation success.

05.14. Activation dispatch does not imply execution success.

05.15. Execution success does not imply committed-state mutation.

05.16. Execution success does not imply RuntimeHost command acceptance,
       RuntimeHost operation success, or Workspace ownership change.

05.17. Activation-plan membership does not imply binding success.

05.18. Activation-plan membership does not imply loading success.

05.19. Activation-plan membership does not imply activation success.

05.20. Adapter loading success does not imply activation-plan correctness.


===============================================================================
06. DECLARED EXECUTABLE MATERIAL
===============================================================================

06.1. Executable artifacts are declared explicitly.

06.2. A Pack does not execute code merely because a file with a recognized
      extension exists.

06.3. A declaration identifies at least:
      - artifact path or identity
      - adapter kind or runtime requirement
      - lifecycle role
      - entrypoint when applicable
      - requested capabilities when applicable
      - trust or policy requirements when applicable

06.4. Declaration format is owned by the relevant manifest, Pack, activation,
      or implementation specification documents.

06.5. This document owns the authority meaning of declaration, not the final
      manifest field syntax.

06.6. Undeclared executable code is not activated by Turnix.

06.7. Declared executable code remains subject to adapter binding, permission,
      activation, capability, and policy checks.

06.8. A declaration does not grant capability permission by itself.

06.9. A declaration does not grant persistent I/O authority by itself.

06.10. A declaration does not grant committed-state mutation authority by
       itself.

06.11. A declaration does not grant RuntimeHost command-surface authority by
       itself.

06.12. A declaration does not make a file an activation entry unless the
       declaration gives it that lifecycle role.

06.13. A declaration does not make the loader responsible for dependency
       readiness.

06.14. A declaration does not make the adapter responsible for graph
       preparation.


===============================================================================
07. ACTIVATION ENTRIES AND MODULE ROLES
===============================================================================

07.1. Turnix distinguishes declared activation entries from private
      implementation modules and exported module surfaces.

07.2. An activation entry is declared executable Pack material loaded by
      Turnix through one ExecutionAdapter for Pack lifecycle participation.

07.3. "Activation entry" is the canonical lifecycle-participation term used by
      DA-23.

07.4. "Adapter entry" is not a separate platform concept in DA-23.

07.5. When "adapter entry" appears informally, it means the activation entry
      for one declared adapter/runtime participation.

07.6. "Pack entry" is not a canonical lifecycle term in DA-23.

07.7. A private implementation module is loaded by Pack code as needed under
      the relevant adapter-local module rules.

07.8. A private implementation module does not participate in Pack lifecycle
      merely because it exists.

07.9. A private implementation module is not externally addressable through
      Turnix by default.

07.10. An exported module surface is publicly addressable only through an
       explicitly supported mediated module-loading mechanism.

07.11. An exported module surface is loaded on demand unless another owning
       document defines a different supported behavior.

07.12. An exported module surface does not receive lifecycle callbacks merely
       because it is exported.

07.13. Recognition or declaration of code material does not mean every code
       file is an activation entry.

07.14. Only declared activation entries are loaded by Turnix for lifecycle
       participation.

07.15. Private and exported modules remain governed by DA-12, adapter-local
       module contracts, and mediated cross-Pack access rules.

07.16. A Pack may declare multiple adapter or runtime participations.

07.17. Each declared adapter or runtime participation has at most one
       activation entry for lifecycle coordination.

07.18. ExecutionAdapter load or evaluation order is not activation authority.

07.19. ExecutionAdapter load or evaluation order does not define dependency
       order.

07.20. ExecutionAdapter load or evaluation order does not define lifecycle
       callback order.

07.21. ExecutionAdapter load or evaluation order does not define activation-
       plan correctness.

07.22. ExecutionAdapter load or evaluation order does not repair a wrong
       activation plan.

07.23. Cross-adapter prerequisites required during ordinary activation are
       established through lifecycle phases and barriers defined by DA-14.

07.24. Cross-adapter prerequisites are not established merely because one
       adapter loads before another adapter.


===============================================================================
08. MECHANICAL LOADING AND ADAPTER ARTIFACT LOADING
===============================================================================

08.1. Mechanical loading means loading or evaluating a requested artifact,
      module, or activation entry through the applicable loader or adapter
      path.

08.2. Adapter artifact loading is mechanical loading through an
      ExecutionAdapter boundary.

08.3. Mechanical loading loads what Turnix instructs the loader or adapter to
      load.

08.4. Mechanical loading does not select Packs.

08.5. Mechanical loading does not resolve PackRequest ambiguity.

08.6. Mechanical loading does not prepare selected pack graphs.

08.7. Mechanical loading does not prepare activation plans.

08.8. Mechanical loading does not decide dependency order.

08.9. Mechanical loading does not decide activation order.

08.10. Mechanical loading does not decide cyclic activation group admission.

08.11. Mechanical loading does not repair missing dependencies.

08.12. Mechanical loading does not convert advisory relations into hard
       dependency or loader rules.

08.13. Mechanical loading reports load, evaluation, readiness, result, or
       failure information according to the applicable adapter or loader
       contract.

08.14. Loading material in an order not supported by the accepted activation
       plan may fail.

08.15. Such failure is valid boundary behavior.

08.16. Such failure is not hidden graph repair.

08.17. Such failure is not PackManager silently changing the graph.

08.18. Such failure is not proof that the loader owns graph preparation.

08.19. Such failure is not proof that the adapter owns activation ordering.

08.20. DA-29 owns selected graph and activation-plan preparation semantics.

08.21. DA-14 owns activation lifecycle and final Activated-state semantics.

08.22. DA-12 owns importing and module-loading boundary semantics.

08.23. DA-27 owns adapter lifecycle, trust, isolation, and adapter-domain
       failure semantics.


===============================================================================
09. TURNIX-FACING READINESS BEFORE CODE LOADING
===============================================================================

09.1. Before Turnix asks an ExecutionAdapter to load a Pack activation entry,
      the mediated Turnix-facing surfaces required for valid Pack
      participation are operational.

09.2. Operational Turnix-facing surfaces can receive supported:
      - registration requests
      - invocation requests
      - RPC-shaped calls
      - trace emission
      - structured errors
      - ModCallContext interactions
      - other explicitly supported adapter-mediated interactions

09.3. Readiness means Turnix can receive Pack participation.

09.4. Readiness does not mean every requested capability, service, handler,
      event, or other Pack-provided surface is already available.

09.5. The distinction between system readiness and surface availability is
      part of the execution boundary.

09.6. An adapter does not gain authority because the Turnix-facing bridge is
      ready before Pack code is loaded.

09.7. Readiness does not mean dependencies have activated.

09.8. Readiness does not mean the activation plan is complete or correct.

09.9. Readiness does not mean Pack code may bypass lifecycle phases.


===============================================================================
10. ENTRY EVALUATION AND MODULE-LEVEL EFFECTS
===============================================================================

10.1. ExecutionAdapter entry evaluation may run host-language top-level code.

10.2. Top-level side effects are not the safe ordinary activation pattern.

10.3. Turnix permits host-language evaluation effects only within the authority
      boundaries of the selected ExecutionAdapter and Pack context.

10.4. Turnix guarantees cleanup only for Turnix-owned and explicitly
      controlled activation material.

10.5. Unsupported module-level side effects do not become Turnix guarantees.

10.6. Unsupported module-level side effects do not become Kernel authority.

10.7. Unsupported module-level side effects do not become reversible state.

10.8. A creator owns the ordering and availability risk of relying on
      module-level behavior outside the supported lifecycle guarantees.

10.9. Module-level behavior does not establish dependency readiness.

10.10. Module-level behavior does not repair activation-plan ordering.

10.11. Module-level behavior does not admit a cyclic activation group.


===============================================================================
11. PACK CODE VERSUS BACKEND IMPLEMENTATION CODE
===============================================================================

11.1. Backend implementation code is trusted platform implementation code.

11.2. Pack-provided code is content supplied by Packs.

11.3. Pack-provided code is not backend implementation code merely because it
      is written in the backend implementation language.

11.4. Pack-provided code is not backend implementation code merely because it
      runs in the backend process.

11.5. Pack-provided code is not frontend authority merely because it runs in
      the browser.

11.6. Pack-provided code is not RuntimeHost authority merely because it runs
      inside a RuntimeHost-owned process or entry surface.

11.7. Pack-provided code receives controlled participation through
      ModCallContext, capability calls, RPC-shaped messages, and declared
      lifecycle entrypoints.

11.8. Pack-provided code does not import backend internals as an authority
      path.

11.9. Pack-provided code does not directly mutate Kernel-owned authoritative
      state.

11.10. Pack-provided code does not directly write SaveBundle state as an
       authority path.

11.11. Pack-provided code does not bypass tracing, policy, capability,
       permission, lifecycle, or transaction boundaries through native
       language convenience.

11.12. Pack-provided code does not bypass RuntimeHost Workspace ownership,
       startup-mode, entry-surface, or command-surface boundaries through
       native language convenience.

11.13. Any allowed same-process or same-language integration remains a
       Turnix-controlled boundary, not a backend authority grant.


===============================================================================
12. MODCALLCONTEXT
===============================================================================

12.1. ModCallContext is the invocation-scoped, Pack-bound gateway through
      which adapter-executed Pack code interacts with Turnix.

12.2. ModCallContext exposes scoped participation in Turnix.

12.3. ModCallContext may expose:
      - Pack identity
      - Application identity when applicable
      - ApplicationRun identity when applicable
      - View identity when applicable
      - capability call surfaces
      - event or request surfaces
      - state access surfaces when allowed
      - logging or trace correlation helpers
      - cancellation or lifecycle helpers when allowed

12.4. DA-30 owns the detailed ModCallContext facade set.

12.5. DA-30 owns ModCallContext absent-surface rules.

12.6. DA-23 does not define the ModCallContext API shape.

12.7. ModCallContext does not expose general backend internals.

12.8. ModCallContext does not expose unrestricted filesystem authority.

12.9. ModCallContext does not expose unrestricted committed-state mutation.

12.10. ModCallContext does not expose unrestricted capability invocation.

12.11. ModCallContext does not expose unrestricted RuntimeHost control
       authority.

12.12. ModCallContext is scoped to the Pack, adapter, Application,
       ApplicationRun, lifecycle, permission, policy, and invocation context
       that created it.

12.13. The ModCallContext object itself does not outlive the callback,
       lifecycle phase, hook, event, timer, capability call, or processing
       stage that created it.

12.14. A retained handle, if one is defined elsewhere, is a separate mediated
       object with its own authority and lifetime.

12.15. A retained handle is not a retained ModCallContext.

12.16. Registrations store owner Pack, callback endpoint, registration scope,
       and metadata.

12.17. Registrations do not store the ModCallContext object that created them.

12.18. ModCallContext may be represented differently across languages and
       adapters.

12.19. Host-language representation differences do not change ModCallContext
       authority meaning.


===============================================================================
13. RPC-SHAPED EXECUTION BOUNDARY
===============================================================================

13.1. Adapter-executed code communicates with Kernel authority through an
      RPC-shaped boundary.

13.2. RPC-shaped boundary means the interaction preserves:
      - message or call envelope semantics
      - route or capability target identity
      - permission checks
      - lifecycle ownership
      - trace correlation
      - structured result, error, cancellation, and readiness reporting
      - ApplicationRun state authority boundaries
      - SaveBundle persistence authority boundaries
      - RuntimeHost entry-surface and command-surface authority boundaries when
        host-level behavior is targeted

13.3. RPC-shaped boundary is not equivalent to WebSocket.

13.4. RPC-shaped boundary is not necessarily networked.

13.5. RPC-shaped boundary may be implemented by:
      - in-process call
      - local queue
      - WebSocket
      - stdio
      - local socket
      - named pipe
      - TCP socket
      - postMessage
      - another explicitly defined transport

13.6. The concrete transport does not define authority.

13.7. Direct in-process calls may implement an RPC-shaped boundary.

13.8. Direct in-process calls do not bypass capability routing, permission
      checks, lifecycle ownership, trace correlation, structured error
      handling, ModCallContext boundaries, OrchestrationUnit boundaries,
      transaction boundaries, ApplicationRun state authority, SaveBundle
      persistence authority, or RuntimeHost authority boundaries.

13.9. A call that bypasses those boundaries is not treated as valid Pack
      execution authority merely because it works technically.

13.10. DA-21 owns abstract RPC, channel, and transport semantics.

13.11. DA-28 owns RuntimeHost entry-surface and command-surface semantics.

13.12. IS-01 owns concrete RPC message schema.

13.13. IS-02 owns concrete WebSocket flow.


===============================================================================
14. RELATION TO TRANSPORTS
===============================================================================

14.1. Transport is the concrete mechanism carrying messages or call envelopes.

14.2. Transport may be local, remote, in-process, process-boundary,
      browser-boundary, or networked.

14.3. Transport does not define authority.

14.4. Transport does not grant capability permission.

14.5. Transport does not grant adapter execution authorization.

14.6. Transport does not define Application lifecycle.

14.7. Transport does not define ApplicationRun lifecycle.

14.8. Transport does not define RuntimeHost lifecycle.

14.9. Transport does not define Job lifecycle.

14.10. Transport failure does not by itself define adapter failure.

14.11. Adapter failure does not by itself define transport failure.

14.12. Transport timeout does not by itself define Job timeout, adapter
       timeout, or RuntimeHost timeout.

14.13. DA-21 defines the abstract separation between RPC, channels, and
       transports.

14.14. DA-27 defines adapter lifecycle and adapter failure semantics.

14.15. DA-28 defines RuntimeHost lifecycle, entry-surface, and command-surface
       semantics.


===============================================================================
15. RELATION TO APPLICATION RUNTIME IDENTITY
===============================================================================

15.1. AppPack is a reusable application definition.

15.2. Application is one durable application individual.

15.3. ApplicationRun is one live runtime incarnation of an Application.

15.4. Loading a SaveBundle creates a new ApplicationRun of the same
      Application.

15.5. SaveBundle is the durable persistence closure of one Application.

15.6. RuntimeHost is the running Turnix host boundary defined by DA-28.

15.7. Kernel-mediated loading binds AppDefinition or AppPack material,
      Application identity, SaveBundle material, and runtime context to create
      an ApplicationRun.

15.8. This document does not define the full Application loading formula.

15.9. Adapter-executed code participates in an ApplicationRun through the
      Kernel-owned authority model.

15.10. Adapter-executed code does not own the Application merely because it
       runs application logic.

15.11. Adapter-executed code does not own the ApplicationRun merely because it
       runs application logic.

15.12. Adapter-executed code does not own the SaveBundle merely because its
       work affects persisted state.

15.13. Adapter-executed code does not own the RuntimeHost merely because it
       runs inside a RuntimeHost-bound process, adapter, View, or entry
       surface.

15.14. SaveBundle persistence is reached through Kernel-mediated paths and
       remains constrained by Memory, Transaction, IoManager, ApplicationRun,
       and SaveBundle ownership rules.

15.15. A writable SaveBundle is not written through adapter-owned state
       authority.

15.16. Application lifecycle and ApplicationRun runtime identity are defined
       by DA-20.

15.17. RuntimeHost identity, Workspace ownership, startup modes, and command
       surfaces are defined by DA-28.

15.18. SaveBundle persistence safety is constrained by DA-04, DA-07, and the
       documents that own SaveBundle semantics.


===============================================================================
16. RELATION TO ACTIVATION
===============================================================================

16.1. DA-14 owns activation lifecycle semantics.

16.2. Activation dispatch through an adapter is one activation mechanism.

16.3. Adapter activation dispatch does not imply activation success.

16.4. Adapter artifact loading does not imply activation success.

16.5. Adapter readiness does not imply activation success.

16.6. Activation success does not imply committed-state mutation.

16.7. Activation success does not imply unrestricted capability permission.

16.8. Activation success does not imply RuntimeHost command acceptance or
      RuntimeHost operation success.

16.9. Activation plans may include cyclic activation groups and multi-adapter
      phase-barrier requirements.

16.10. DA-14 owns multi-adapter phase barriers, cyclic activation groups,
       registration publication, final Activated state, and activation failure
       semantics.

16.11. DA-23 owns only the execution-boundary implications of activation.

16.12. ExecutionAdapters load declared activation entries, communicate through
       mediated Turnix surfaces, and do not become authority because an
       activation graph is cyclic or multi-adapter.

16.13. An ExecutionAdapter does not admit cyclic activation groups.

16.14. An ExecutionAdapter does not decide activation-plan ordering.

16.15. An ExecutionAdapter does not decide final Activated state.

16.16. DA-27 defines adapter lifecycle states and adapter-domain trace reason
       identifiers used around adapter loading and dispatch.

16.17. DA-29 defines selected graph and activation-plan preparation semantics.


===============================================================================
17. RELATION TO ACTIVATION PLANS AND PACKMANAGER
===============================================================================

17.1. DA-29 owns PackManager graph-preparation semantics.

17.2. DA-29 owns activation-plan preparation semantics.

17.3. An activation plan is selected graph intent refined for activation order
      and activation readiness.

17.4. An activation plan is information, graph intent, and ordering evidence.

17.5. An activation plan is not adapter execution.

17.6. An activation plan is not mechanical loading.

17.7. An activation plan is not ModCallContext gateway authority.

17.8. An activation plan is not capability permission.

17.9. An activation plan may identify which declared activation entries should
      be loaded for an activation attempt.

17.10. An activation plan may identify strongly connected components and
       admitted cyclic activation groups.

17.11. Identifying a declared activation entry in an activation plan does not
       make that entry load successfully.

17.12. Identifying a cyclic activation group in an activation plan does not
       make that group activate successfully.

17.13. Adapter artifact loading consumes instructions derived from accepted
       activation intent.

17.14. Adapter artifact loading does not prepare the accepted activation plan.

17.15. Adapter artifact loading does not repair the accepted activation plan.

17.16. Adapter artifact loading does not replace PackManager diagnostics.

17.17. PackManager diagnostics do not replace adapter-domain error reporting.

17.18. PackManager diagnostics do not replace DA-14 activation trace evidence.

17.19. DA-23 preserves the boundary between graph preparation, adapter
       loading, and activation execution.


===============================================================================
18. RELATION TO IMPORTS AND MODULE LOADING
===============================================================================

18.1. Importing and module-loading semantics are defined by DA-12.

18.2. Native language imports cannot bypass Turnix semantics.

18.3. Python Pack code does not import backend internals as an authority path.

18.4. JavaScript Pack code does not bypass Turnix resolution, visibility,
      activation, or capability boundaries through native or arbitrary loading
      mechanisms.

18.5. Turnix-controlled import mechanisms remain Turnix-controlled loading
      surfaces where Pack code needs cross-Pack access.

18.6. Host-language module systems may be used only within boundaries allowed
      by DA-12 and this document.

18.7. A successful native import does not imply Turnix permission, activation,
      state authority, capability permission, or RuntimeHost command authority.

18.8. A successful native import does not convert a private implementation
      module into an activation entry.

18.9. A successful native import does not convert an exported module surface
      into a lifecycle participant.

18.10. A successful native import does not prove activation-plan correctness.

18.11. A successful native import does not prove dependency readiness.

18.12. A successful native import does not admit a cyclic activation group.


===============================================================================
19. RELATION TO CAPABILITIES AND PERMISSIONS
===============================================================================

19.1. Capability and permission semantics are defined by DA-16.

19.2. Adapter-executed code receives no general backend access.

19.3. Adapter-executed code receives capability-scoped access through its
      Turnix-controlled context.

19.4. Capability permission is checked by Kernel-owned authority paths.

19.5. Adapter identity may participate in permission decisions when the
      governing permission model defines such participation.

19.6. Adapter identity does not grant permission by itself.

19.7. Pack identity does not grant permission by itself.

19.8. Transport identity does not grant permission by itself.

19.9. RuntimeHost identity does not grant permission by itself.

19.10. Capability invocation that mutates state remains constrained by DA-04
       and DA-24.

19.11. Capability invocation through RPC remains constrained by DA-21.

19.12. Capability invocation that targets RuntimeHost behavior remains
       constrained by DA-28.

19.13. Activation-plan membership does not grant capability permission.

19.14. Loader success does not grant capability permission.


===============================================================================
20. RELATION TO DECISIONS AND POLICY
===============================================================================

20.1. User decision and policy handling are defined by DA-17.

20.2. Execution authorization may require policy evaluation or user decision.

20.3. Trust decisions for unsafe or unsandboxed adapter execution are
      policy-scoped decisions.

20.4. A policy decision authorizes only the scope it states.

20.5. A remembered policy decision does not silently broaden itself to new
      adapter kinds, new Packs, new capabilities, new SaveBundles, new
      RuntimeHost entry surfaces, or new trust classes.

20.6. Policy decision storage does not become Pack authority.

20.7. DA-27 defines adapter trust and isolation classification semantics
      consumed by policy decisions.

20.8. DA-28 defines RuntimeHost entry-surface, Workspace-ownership, LAN
      exposure, and command-surface semantics consumed by policy decisions.


===============================================================================
21. RELATION TO JOBS AND ORCHESTRATIONUNITS
===============================================================================

21.1. Job lifecycle semantics are defined by DA-19.

21.2. OrchestrationUnit lifecycle and mutation authority semantics are defined
      by DA-24.

21.3. Adapter-executed work may be associated with a Job when the owning
      workflow defines Job-backed behavior.

21.4. Adapter-executed work may create or enter an OrchestrationUnit when it
      seeks Turnix mutation guarantees or lifecycle authority.

21.5. Adapter execution acceptance is not Job success.

21.6. Adapter execution failure is not Job failure by default.

21.7. Adapter disconnect is not Job cancellation by default.

21.8. Adapter execution failure is not OrchestrationUnit failure by default.

21.9. Adapter execution acceptance is not RuntimeHost operation success.

21.10. RuntimeHost operation success is not adapter execution success by
       default.

21.11. Job and OrchestrationUnit relationships to adapter-executed work are
       explicit and trace-visible when they exist.

21.12. Adapter lifecycle and trace semantics are defined by DA-27.


===============================================================================
22. RELATION TO VIEWS AND FRONTEND RUNTIME
===============================================================================

22.1. View and frontend runtime semantics are defined by DA-22.

22.2. Browser JavaScript Pack code may run in a frontend-facing
      ExecutionAdapter realization.

22.3. Browser state is not authoritative Application state.

22.4. Browser state is not authoritative ApplicationRun state.

22.5. Browser reload, tab close, client disconnect, or frontend state loss does
      not redefine committed state.

22.6. Frontend-facing ExecutionAdapter realizations may hold:
      - render state
      - temporary UI state
      - input fields
      - scroll position
      - local cache
      - pending View interaction state

22.7. Frontend-facing ExecutionAdapter realizations do not own authoritative
      ApplicationRun state.

22.8. Frontend-facing ExecutionAdapter realizations do not own RuntimeHost
      authority merely because they render a launcher, management, CLI-like, or
      RuntimeHost control surface.

22.9. Frontend-facing ExecutionAdapter participation remains constrained by
      DA-22, DA-23, DA-27, DA-21, DA-28, IS-01, and IS-02.


===============================================================================
23. RELATION TO ARTIFACTS, EXPORTS, AND OFFLINE WORKFLOWS
===============================================================================

23.1. Window artifact and export semantics are defined by DA-25.

23.2. Comparison, Replay, Resume, and Retry workflow semantics are defined by
      DA-26.

23.3. Adapter execution acceptance does not by itself define artifact or export
      authority.

23.4. Adapter execution success does not by itself define artifact or export
      authority.

23.5. Adapter execution failure does not by itself define comparison, Replay,
      Resume, or Retry outcome.

23.6. Adapter disconnect does not by itself define comparison, Replay, Resume,
      or Retry outcome.

23.7. Direct-call dispatch does not by itself define artifact, export,
      comparison, Replay, Resume, or Retry authority.

23.8. Retained adapter evidence may be useful to artifact, export, comparison,
      Replay, Resume, Retry, or inspection workflows.

23.9. Retained adapter evidence does not define committed-state truth by
      itself.


===============================================================================
24. RELATION TO DA-27, DA-28, DA-29, AND DA-30
===============================================================================

24.1. DA-23 owns the abstract ExecutionAdapter authority boundary.

24.2. DA-23 owns:
      - code artifact phases
      - declared executable artifact authority meaning
      - activation-entry boundary meaning
      - mechanical loading and adapter artifact loading boundary meaning
      - Pack-provided code versus backend implementation code
      - ModCallContext authority at the execution-boundary level
      - RPC-shaped execution boundary semantics
      - relation between execution boundary and Kernel authority

24.3. DA-27 owns:
      - adapter mediation versus sandboxing
      - adapter trust and isolation
      - initial adapter classes
      - adapter lifecycle
      - adapter failure and disconnect meaning
      - adapter-domain trace reason identifiers
      - adapter trace context

24.4. DA-28 owns:
      - RuntimeHost identity
      - Workspace ownership at runtime-host level
      - startup modes
      - entry surfaces
      - command-surface semantics
      - local-first and LAN exposure semantics
      - RuntimeHost-domain trace reason identifiers
      - runtime-host trace context

24.5. DA-29 owns:
      - PackManager graph-preparation semantics
      - selected graph semantics
      - activation-plan preparation semantics
      - cyclic activation group detection and admission evidence
      - PackManager-domain trace reason identifiers
      - PackManager trace context

24.6. DA-30 owns:
      - ModCallContext invocation-gateway semantics
      - ModCallContext facade shape
      - ModCallContext absent surfaces
      - ModCallContext lifetime and retention rules
      - invocation-scoped Pack-bound context behavior

24.7. DA-27 does not weaken DA-23 authority boundaries.

24.8. DA-28 does not weaken DA-23 authority boundaries.

24.9. DA-29 does not weaken DA-23 authority boundaries.

24.10. DA-30 does not weaken DA-23 authority boundaries.

24.11. DA-23 does not define concrete adapter lifecycle state machines.

24.12. DA-23 does not define concrete adapter trust or isolation taxonomy.

24.13. DA-23 does not define RuntimeHost lifecycle, Workspace ownership,
       startup-mode, entry-surface, or command-surface semantics.

24.14. DA-23 does not define PackManager graph-preparation behavior.

24.15. DA-23 does not define concrete activation-plan schema.

24.16. DA-23 does not define the concrete ModCallContext facade set.

24.17. If DA-23 and DA-27 appear to conflict, the interpretation that preserves
       Kernel authority, capability mediation, and the RPC-shaped execution
       boundary is used until the documents are corrected.

24.18. If DA-23 and DA-28 appear to conflict, the interpretation that preserves
       Kernel authority, capability mediation, Workspace ownership, and the
       RPC-shaped execution boundary is used until the documents are corrected.

24.19. If DA-23 and DA-29 appear to conflict, the interpretation that preserves
       PackManager graph-preparation ownership, Kernel authority, adapter
       boundary limits, and DA-14 activation lifecycle ownership is used until
       the documents are corrected.

24.20. If DA-23 and DA-30 appear to conflict, the interpretation that preserves
       mediated Pack participation, ModCallContext scoping, and Kernel
       authority is used until the documents are corrected.


===============================================================================
25. DIRECT-CALL OPTIMIZATION BOUNDARY
===============================================================================

25.1. Direct in-process calls may implement transport or dispatch
      optimization.

25.2. Direct in-process calls do not bypass the RPC-shaped authority boundary.

25.3. A direct call remains valid only when it preserves:
      - route or capability target identity
      - permission checks
      - lifecycle ownership
      - trace correlation
      - structured result and error handling
      - ModCallContext boundaries
      - OrchestrationUnit boundaries when mutation or lifecycle authority is
        involved
      - transaction and commit boundaries when state mutation occurs
      - ApplicationRun state authority
      - SaveBundle persistence authority
      - RuntimeHost authority boundaries when host-level behavior is involved

25.4. A direct call that bypasses those requirements is backend implementation
      behavior, not Pack-code authority.

25.5. Pack-provided code does not acquire direct-call authority merely because
      a direct-call implementation path exists.

25.6. Direct-call optimization remains explainable and trace-visible where the
      equivalent message-shaped path would be trace-visible.


===============================================================================
26. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

26.1. The following are not supported:
      - executing code because a file exists
      - treating recognized code artifacts as executable by default
      - treating every code file as an activation entry
      - treating "adapter entry" as a separate platform concept
      - treating "pack entry" as a canonical lifecycle term
      - treating private implementation modules as lifecycle participants by
        default
      - treating exported module surfaces as lifecycle participants by default
      - treating Pack-provided Python as backend implementation code
      - treating same-language execution as authority
      - treating same-process execution as authority
      - treating direct calls as authority bypass
      - treating transport choice as authority
      - treating WebSocket as the RPC model itself
      - treating browser state as authoritative ApplicationRun state
      - treating adapter identity as capability permission
      - treating adapter execution authorization as capability permission
      - treating Pack code as a SaveBundle writer
      - treating ModCallContext as general backend access
      - retaining the ModCallContext object past its invocation
      - treating RuntimeHost identity as permission by itself
      - treating RuntimeHost entry surface as authority by itself
      - treating RuntimeHost deployment location as authority
      - treating module-level side effects as Turnix guarantees
      - treating adapter load order as activation order
      - treating adapter load order as dependency order
      - treating mechanical loading as graph preparation
      - treating mechanical loading as activation-plan preparation
      - treating mechanical loading as cyclic activation admission
      - treating activation-plan membership as loading success
      - treating loading success as activation success
      - treating loading success as activation-plan correctness
      - bypassing tracing, lifecycle, permission, policy, capability,
        RuntimeHost, OrchestrationUnit, transaction, or commit boundaries
        through native language convenience
