===============================================================================
IMPLEMENTATION SPECIFICATION IS-06 - RUNTIME HOST LAN AND CLIENT CONNECTIONS
===============================================================================

Status:
-------
EVOLVING

Description:
------------
Defines concrete RuntimeHost local bind behavior, LAN exposure flow, client
connection classification, remote-client connection flow, connection acceptance
and rejection behavior, connection relationship to startup modes and command
surfaces, and trace mapping for local and LAN RuntimeHost clients.

This document implements the LAN exposure and client-connection semantics
defined by DA-28. It uses IS-05 for startup modes and IS-04 for command-surface
handling.

Purpose:
--------
This document defines how RuntimeHost entry surfaces are exposed locally or on
LAN, how clients connect to RuntimeHost, and how Turnix preserves the boundary
between connection, authentication, command acceptance, and authority.

It defines:
- bind scope categories
- local-only exposure behavior
- LAN exposure request flow
- remote-client connection identity and classification
- client connection acceptance and rejection flow
- client disconnect and reconnect flow
- relationship to startup modes
- relationship to command surfaces
- relationship to RPC transports
- trace mapping to DA-28 trace reasons
- connection error categories

It does NOT define:
- RuntimeHost semantics (see DA-28)
- Kernel authority ordering (see DA-01 and DA-02)
- committed-state or transaction semantics (see DA-04)
- persistent I/O safety semantics (see DA-07)
- Application lifecycle, Application identity, ApplicationRun lifecycle, or
  ApplicationRun identity semantics (see DA-20)
- abstract RPC, channel, or transport semantics (see DA-21)
- UI, View, or frontend runtime semantics (see DA-22)
- execution adapter authority boundaries (see DA-23)
- OrchestrationUnit mutation authority semantics (see DA-24)
- adapter lifecycle, trust, and trace semantics (see DA-27)
- workspace ownership and host-lock record mechanics (see IS-03)
- RuntimeHost command-surface flow or command result envelope (see IS-04)
- RuntimeHost startup-mode flow (see IS-05)
- concrete cryptographic protocol
- concrete authentication token format
- concrete certificate format
- concrete firewall configuration
- concrete WebSocket frame flow
- concrete browser bootstrap flow

===============================================================================
01. INTERPRETATION BASIS
===============================================================================

01.01. This document expresses normative meaning through explicit,
      deterministic prose.

01.02. Normative meaning in Turnix derives from sentence structure and document
      context rather than from RFC-style keywords.

01.03. The CORE META-RULES documents define the general rule language and
      interpretation model used by this document.

01.04. This document defines implementation-level RuntimeHost LAN exposure and
      client-connection behavior within that shared interpretation model.

01.05. This implementation specification does not create new authority
      semantics. It implements DA-28 LAN exposure and client-connection rules.


===============================================================================
02. CORE CONCEPT
===============================================================================

02.01. RuntimeHost LAN and client-connection behavior answers:

          "How does a RuntimeHost expose entry surfaces locally or on LAN,
           accept or reject clients, and preserve the distinction between
           connection, authentication, command acceptance, and authority?"

02.02. A bind scope defines where a RuntimeHost entry surface is reachable.

02.03. Client connection means a client reached a RuntimeHost entry surface and
      entered connection classification.

02.04. Client connection is not command acceptance.

02.05. Client connection is not capability permission.

02.06. Client connection is not user identity by itself.

02.07. Client connection is not state authority.

02.08. LAN exposure is explicit and policy-governed.

02.09. RuntimeHost does not silently expose itself to LAN clients.

02.10. RuntimeHost does not silently expose itself to internet clients.

02.11. Concrete pairing and authentication mechanisms belong to later
       implementation or security specifications.

02.12. Client-provided connection metadata, remote endpoint summaries,
       frontend client identity, pairing identity, and authentication claims
       are inputs to classification, authentication, policy, and trace
       correlation only.

02.13. Client-provided metadata does not let the client forge user identity,
       authenticated principal, Kernel authority, RuntimeHost authority,
       Application identity, ApplicationRun identity, workspace ownership,
       capability permission, command authority, adapter authorization, or
       committed-state mutation authority.


===============================================================================
03. BIND SCOPE CATEGORIES
===============================================================================

03.01. bindScope identifies the reachability scope requested for an entry
      surface.

03.02. bindScope values are:
      - localOnly
      - lanExplicit
      - remoteExplicit
      - disabled

03.03. localOnly means the entry surface is reachable only through local machine
      boundaries defined by the implementation.

03.04. localOnly does not require a specific concrete binding such as loopback
      TCP, named pipe, Unix socket, browser origin, or local file IPC.

03.05. A concrete local binding preserves the localOnly security boundary and
      states its assumptions in the owning implementation specification.

03.06. lanExplicit means the entry surface may be reachable by LAN clients after
      explicit policy or configuration permits that exposure.

03.07. remoteExplicit is a reserved bind scope for future entry surfaces that
      may be reachable beyond LAN.

03.08. remoteExplicit has no enabled behavior in this document.

03.09. remoteExplicit requires a later authoritative security and deployment
      design before any implementation may treat it as available.

03.10. disabled means the entry surface is not exposed.

03.11. localOnly is the default bind scope unless a later implementation
       specification defines a different default without weakening DA-28 LAN
       exposure semantics.

03.12. lanExplicit is never selected silently.

03.13. remoteExplicit is not enabled by this document.

03.14. Bind scope selection does not grant command authority.

03.15. Bind scope selection does not grant capability permission.


===============================================================================
04. LOCAL-ONLY EXPOSURE FLOW
===============================================================================

04.01. Local-only exposure creates or enables an entry surface reachable through
      local machine boundaries.

04.02. Local-only exposure may be used by interactive host mode, one-shot
      command mode, serve mode, connect mode, test mode, or launcher mode when
      the mode requests or requires a local entry surface.

04.03. Local-only exposure does not imply LAN exposure.

04.04. Local-only exposure does not imply internet exposure.

04.05. Local-only exposure does not imply command success.

04.06. Local-only exposure does not imply ApplicationRun readiness.

04.07. Local-only exposure does not imply adapter readiness.

04.08. Local-only exposure may produce RuntimeHostEntrySurfaceCreated and
      RuntimeHostEntrySurfaceReady trace evidence.

04.09. Failure to create local-only exposure is explicit and trace-visible.


===============================================================================
05. LAN EXPOSURE REQUEST FLOW
===============================================================================

05.01. LAN exposure begins with an explicit request.

05.02. LAN exposure request emits RuntimeHostLanExposureRequested.

05.03. LAN exposure requires policy or configuration that permits LAN exposure.

05.04. If LAN exposure is denied, Turnix emits RuntimeHostLanExposureRejected.

05.05. If LAN exposure is enabled, Turnix emits RuntimeHostLanExposureEnabled.

05.06. LAN exposure enabled means the entry surface is reachable according to
      the concrete bind behavior selected by implementation.

05.07. LAN exposure enabled does not imply client authentication success.

05.08. LAN exposure enabled does not imply pairing success.

05.09. LAN exposure enabled does not imply command acceptance.

05.10. LAN exposure enabled does not imply capability permission.

05.11. LAN exposure enabled does not imply ApplicationRun readiness.

05.12. LAN exposure enabled does not imply state authority.

05.13. LAN exposure enabled does not imply policy approval for later commands.

05.14. LAN exposure disabled emits RuntimeHostLanExposureDisabled.

05.15. LAN exposure failure preserves the distinction between policy denial,
       bind failure, missing implementation feature, and authentication
       configuration failure when the implementation can distinguish them.


===============================================================================
06. REMOTE CLIENT IDENTITY AND CLASSIFICATION
===============================================================================

06.01. clientConnectionId identifies one client connection attempt or accepted
      client connection.

06.02. clientConnectionId is distinct from:
      - runtimeHostId
      - entry surface identity
      - frontend client identity
      - user identity
      - authenticated principal
      - RPC message identity
      - channel identity
      - transport identity
      - commandId
      - jobId
      - orchestrationUnitId

06.03. A client connection record includes enough context, when available, to
      relate:
      - clientConnectionId
      - runtimeHostId
      - entry surface identity
      - bindScope
      - transport kind
      - channel identity
      - remote endpoint summary
      - pairing identity when applicable
      - authenticated principal when applicable
      - frontend client identity when applicable
      - commandId when applicable

06.04. Client classification distinguishes:
      - local client
      - LAN client
      - remote client
      - test client
      - unknown client

06.05. Client classification does not grant authority.

06.06. Client classification does not authenticate the client by itself.

06.07. Client classification does not define user identity by itself.

06.08. Frontend client identity is client-side or correlation evidence only
      unless an owning authentication and View/client-binding design maps it to
      an authenticated principal or View relationship.

06.09. Frontend client identity is not View identity by itself.

06.10. Frontend client identity is not user identity by itself.

06.11. Frontend client identity is not authority by itself.


===============================================================================
07. CLIENT CONNECTION ACCEPTANCE AND REJECTION
===============================================================================

07.01. Client connection begins when a client attempts to connect to a
      RuntimeHost entry surface.

07.02. Remote or LAN client connection attempt emits
      RuntimeHostRemoteClientConnectionRequested when remote or LAN connection
      handling is entered.

07.03. Client connection handling checks bind scope, policy, and available
      pairing or authentication requirements before accepting the client.

07.04. Accepted RuntimeHost client connection emits RuntimeHostClientAccepted.

07.05. Accepted remote or LAN client connection emits
      RuntimeHostRemoteClientConnectionAccepted.

07.06. Rejected RuntimeHost client connection emits RuntimeHostClientRejected.

07.07. Rejected remote or LAN client connection emits
      RuntimeHostRemoteClientConnectionRejected.

07.08. Connection acceptance does not imply command acceptance.

07.09. Connection acceptance does not imply capability permission.

07.10. Connection acceptance does not imply state authority.

07.11. Connection acceptance does not imply ApplicationRun readiness.

07.12. Connection rejection before command handling exists does not produce a
       command outcome under IS-04.

07.13. Connection rejection before Job-backed work exists does not produce Job
       terminal outcome.

07.14. Connection rejection before OrchestrationUnit creation does not produce
       OrchestrationUnit terminal outcome.


===============================================================================
08. PAIRING AND AUTHENTICATION PLACEHOLDERS
===============================================================================

08.01. Pairing means a policy-governed process that authorizes a client or
      client device to connect to a RuntimeHost entry surface.

08.02. Authentication means verification of a client, user, device, token,
      certificate, or other principal according to a concrete implementation
      specification.

08.03. Pairing is distinct from authentication.

08.04. Authentication is distinct from capability permission.

08.05. Pairing success does not grant capability permission by itself.

08.06. Authentication success does not grant capability permission by itself.

08.07. Pairing success does not grant committed-state mutation authority.

08.08. Authentication success does not grant committed-state mutation authority.

08.09. Pairing success does not create user identity by itself.

08.10. Authentication success does not create command authority by itself.

08.11. Concrete pairing prompts, token formats, certificate formats, key
       exchange, revocation, trust storage, and authentication protocols belong
       to later implementation or security specifications.

08.12. Until such specifications exist, LAN exposure remains explicit and
       policy-governed, and implementations preserve conservative defaults.


===============================================================================
09. CLIENT DISCONNECT AND RECONNECT
===============================================================================

09.01. Client disconnect is explicit when detected.

09.02. RuntimeHost client disconnect emits RuntimeHostClientDisconnected.

09.03. Remote or LAN client disconnect emits RuntimeHostRemoteClientDisconnected
      when remote or LAN connection classification applies.

09.04. Client disconnect does not automatically stop RuntimeHost.

09.05. Client disconnect does not automatically cancel Jobs.

09.06. Client disconnect does not automatically fail an OrchestrationUnit.

09.07. Client disconnect does not automatically fail an adapter.

09.08. Client disconnect does not automatically discard command results.

09.09. Client reconnect emits RuntimeHostClientReconnected when reconnection to
      an existing client or entry-surface relationship is accepted.

09.10. Reconnect does not imply replay of all missed client-local events.

09.11. Reconnect may receive a fresh snapshot, retained result surface,
       generation update, or implementation-defined recovery surface.

09.12. Reconnect does not imply Job resume.

09.13. Reconnect does not imply command replay.

09.14. Reconnect does not imply retained result retrieval.

09.15. Reconnect does not imply state synchronization.

09.16. An owning workflow and a concrete transport or client specification
       define any reconnect behavior beyond connection recovery.

09.17. Concrete reconnect flow belongs to later implementation specifications.


===============================================================================
10. RELATION TO STARTUP MODES
===============================================================================

10.01. Startup modes that expose entry surfaces use IS-05 startup-mode behavior.

10.02. serve mode may expose localOnly or lanExplicit entry surfaces
      according to explicit policy and configuration.

10.03. connect mode may connect to existing localOnly or lanExplicit entry
      surfaces when the client can reach them and policy permits connection.

10.04. launcher mode may create browser or frontend entry surfaces under DA-22
      and IS-05.

10.05. test mode may create test clients or test entry surfaces without
      weakening connection authority boundaries.

10.06. oneShotCommand mode may connect to an existing RuntimeHost when the
      requested command is a client operation.

10.07. Startup mode selection does not by itself expose LAN surfaces.

10.08. Startup mode selection does not by itself accept clients.


===============================================================================
11. RELATION TO COMMAND SURFACES
===============================================================================

11.01. A connected client may submit commands only through a command surface or
      operation surface that accepts such input.

11.02. Client connection acceptance is not command receipt.

11.03. Command receipt, classification, acceptance, dispatch, completion,
      failure, and cancellation are defined by IS-04.

11.04. A client may be accepted but later have a command rejected.

11.05. A command may be accepted only after command handling applies the
      command-surface rules in IS-04.

11.06. Client disconnect may detach a command from the waiting client only when
      the owning command workflow defines detachment or retained result
      behavior.

11.07. Client disconnect does not silently convert command outcome to failure.


===============================================================================
12. RELATION TO RPC AND TRANSPORTS
===============================================================================

12.01. Client connections may use RPC over concrete transports.

12.02. DA-21 defines abstract RPC, channel, and transport semantics.

12.03. IS-02 defines concrete WebSocket RPC flow when WebSocket is used.

12.04. A transport connection is not RuntimeHost authority by itself.

12.05. A transport disconnect is not RuntimeHost failure by itself.

12.06. A transport timeout is not Job timeout by itself.

12.07. RPC acknowledgement is not command success.

12.08. RPC acknowledgement is not capability permission.

12.09. Concrete transport framing, retry, buffering, and reconnect details
      belong to transport-specific implementation specifications.


===============================================================================
13. TRACE MAPPING
===============================================================================

13.01. IS-06 maps implementation behavior to DA-28 RuntimeHost entry-surface,
      LAN exposure, and remote-client trace reasons.

13.02. Entry surface request, creation, readiness, rejection, and closure map
      to:
      - RuntimeHostEntrySurfaceRequested
      - RuntimeHostEntrySurfaceCreated
      - RuntimeHostEntrySurfaceReady
      - RuntimeHostEntrySurfaceRejected
      - RuntimeHostEntrySurfaceClosed

13.03. LAN exposure maps to:
      - RuntimeHostLanExposureRequested
      - RuntimeHostLanExposureEnabled
      - RuntimeHostLanExposureRejected
      - RuntimeHostLanExposureDisabled

13.04. Client connection maps to:
      - RuntimeHostClientAccepted
      - RuntimeHostClientRejected
      - RuntimeHostClientDisconnected
      - RuntimeHostClientReconnected

13.05. Remote or LAN client connection maps to:
      - RuntimeHostRemoteClientConnectionRequested
      - RuntimeHostRemoteClientConnectionAccepted
      - RuntimeHostRemoteClientConnectionRejected
      - RuntimeHostRemoteClientDisconnected

13.06. Trace evidence includes enough context, when available, to identify:
      - runtimeHostId
      - bindScope
      - entry surface identity
      - clientConnectionId
      - client classification
      - transport kind
      - channel identity
      - remote endpoint summary
      - pairing identity when applicable
      - authenticated principal when applicable
      - frontend client identity when applicable
      - commandId when applicable
      - policy decision identity when applicable
      - error category

13.07. Client connection trace evidence does not replace RuntimeHost lifecycle
      trace evidence.

13.08. Client connection trace evidence does not replace RPC trace evidence.

13.09. Client connection trace evidence does not replace UI-domain trace
      evidence.

13.10. Client connection trace evidence does not replace command trace evidence
       under IS-04.

13.11. Client connection trace evidence does not replace Job,
       OrchestrationUnit, adapter, Application, ApplicationRun, transaction, or
       Window evidence.

13.12. Trace evidence does not grant connection acceptance, authentication,
       capability permission, user identity, state mutation, or command
       acceptance.


===============================================================================
14. ERROR CATEGORIES
===============================================================================

14.01. RuntimeHost LAN and client-connection error categories include:
      - BindScopeUnsupported
      - LocalBindFailed
      - LanExposurePolicyDenied
      - LanExposureConfigurationInvalid
      - LanBindFailed
      - InternetExposureUnsupported
      - ClientConnectionMalformed
      - ClientConnectionRejected
      - ClientAuthenticationRequired
      - ClientAuthenticationFailed
      - ClientPairingRequired
      - ClientPairingRejected
      - ClientTransportUnsupported
      - ClientTransportFailed
      - ClientRuntimeHostUnavailable
      - ClientReconnectUnsupported
      - ClientReconnectRejected
      - ConnectionImplementationFeatureUnavailable

14.02. Error category names in this section define semantic categories, not
      final exception class names.

14.03. Concrete exception class names belong to implementation code or a later
      error-schema specification.

14.04. Error reporting preserves distinctions between bind failure, policy
      denial, authentication requirement, authentication failure, pairing
      requirement, pairing rejection, unsupported transport, transport failure,
      and missing implementation feature.

14.05. Error reporting does not collapse all client connection failure into
      generic network failure when the implementation can distinguish the
      cause.


===============================================================================
15. WHAT IS EXPLICITLY NOT SUPPORTED
===============================================================================

15.01. The following are not supported:
      - silently exposing RuntimeHost to LAN clients
      - silently exposing RuntimeHost to internet clients
      - treating bind scope selection as command authority
      - treating client connection as command acceptance
      - treating client connection as capability permission
      - treating client connection as user identity by itself
      - treating client connection as authenticated principal by itself
      - treating client connection as state authority
      - treating client-provided metadata as identity-forging authority
      - treating pairing success as capability permission by itself
      - treating authentication success as capability permission by itself
      - treating transport connection as RuntimeHost authority
      - treating transport disconnect as RuntimeHost failure by itself
      - treating client disconnect as Job cancellation by default
      - treating client disconnect as command failure by default
      - treating reconnect as Job resume by default
      - treating reconnect as command replay by default
      - treating reconnect as retained result retrieval by default
      - connect mode silently starting a new writable RuntimeHost
      - serve mode silently enabling LAN exposure
      - remoteExplicit exposure without a later authoritative security and
        deployment design

17. LOCKED SUMMARY
===============================================================================

17.01. LOCKED:
      - IS-06 implements DA-28 LAN exposure and client-connection semantics.
      - LAN exposure is explicit and policy-governed.
      - RuntimeHost does not silently expose itself to LAN clients.
      - RuntimeHost does not silently expose itself to internet clients.
      - localOnly is the default bind scope unless a later implementation
        specification defines a different default without weakening DA-28.
      - lanExplicit is never selected silently.
      - remoteExplicit is reserved for a future authoritative security and
        deployment design and has no enabled behavior in this document.
      - Client connection is not command acceptance.
      - Client connection is not capability permission.
      - Client connection is not user identity by itself.
      - Client connection is not state authority.
      - Client-provided metadata does not grant authority by itself.
      - Pairing and authentication are distinct.
      - Pairing and authentication do not grant capability permission by
        themselves.
      - Client disconnect does not automatically stop RuntimeHost, cancel Jobs,
        fail OrchestrationUnits, fail adapters, or discard command results.
      - Reconnect does not imply replay, resume, retained result retrieval, or
        state synchronization unless later owners define those behaviors.
      - Startup modes that expose entry surfaces use IS-05.
      - Connected clients that submit commands use IS-04.
      - RPC and transport behavior remains governed by DA-21 and relevant IS
        documents.
      - LAN exposure and client connection behavior are trace-visible.

17.02. OPEN:
      - concrete client identifiers, bind behavior, pairing, authentication,
        reconnect, retained result retrieval, browser bootstrap interaction,
        firewall guidance, error classes, and transport-specific schemas.
